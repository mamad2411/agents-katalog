# CLAUDE.md

Project conventions for cycle. Read before touching code or running the workflow.

## Core thesis (non-negotiable)

cycle exists to deliver working software and *demonstrate* it: every cycle must leave the app in a working state, shown to run locally (and when deployed) and to meet the issue's acceptance criteria. See [BRIEF.md](BRIEF.md) → *Core thesis*.

Implication for anyone changing the engine or workflows: **no false greens.** Passing unit tests is not proof the app works. Verification that is skipped, degraded, or stubbed is not verification. A cycle that cannot demonstrate the running app meets its criteria must block or fail loudly, never drain to `done/`. Gates fail closed.

The default verify gate (`src/defaults/scripts/verify.sh`, cycle 0273) operationalizes this: after the unit `npm test`, it detects a by-convention running-app (e2e/integration) suite — a `test:e2e`/`e2e` npm script, or a `playwright.config.*`/`cypress.config.*` file via `npx`, in that precedence — and runs it; either suite failing fails verify. So an **app repo's `feature` cycles must let verify drive the running app**, not just its units. Detection is convention-based and skips cleanly when no such suite exists, so **cycle's own CLI repo has no running-app suite and is unaffected** (unit-only, byte-for-byte as before). Complements the degenerate-verification gate (cycle 0272). See [docs/ENGINE.md](docs/ENGINE.md) → *Running-app verify suite*.

## Workflow style

- **Trunk-based development.** All work goes directly on `master`. Commits land via fast-forward merge from local branches that are immediately deleted.
- **Do NOT use git worktrees in this repo.** No `EnterWorktree`, no `git worktree add`. Edit master directly.
- Pushes to `master` are authorized — no PR review required. See `.claude/settings.local.json` for the `autoMode.allow` rule.
- **Trunk-based operation is enforced via `CYCLE_TRUNK_BASED=1` in `.cycle/.env`**, not via `workflows.yml`. The defaults ship `engine.commit.mode: worktree-pr`; the env var overrides it to `trunk` at engine bootstrap. Any repo needing trunk mode: create `.cycle/.env` with `CYCLE_TRUNK_BASED=1`, or pass `--trunk` to `cycle run`.

## Runtime

- Node ≥ 22.6 (`--experimental-strip-types`; no transpile step in tests).
- TypeScript floor is **ES2023** (`target`/`lib` in `tsconfig.json`). See [docs/RFC-002-typescript-es2023-floor.md](docs/RFC-002-typescript-es2023-floor.md).
- If `node --version` < 22: `nvm use 22.22.2`.

## Test conventions

- **Exactly-once engine events must be cardinality-pinned.** Use
  `filter(predicate).length === 1` (not `find(predicate) !== undefined`) when
  asserting that an engine event fires exactly once. A bare `find` only confirms
  existence — it lets double-emission bugs slip through undetected.
- Use the `expectExactlyOne(events, eventName)` helper from `tests/helpers.ts`
  for events where you also need the payload. It asserts `length === 1` and
  returns the matched event.
- Background: cycles 0022 and 0051 established this rule. `engine.halted` and
  `reflection.summary` are the canonical exactly-once events.
- **`node:fs/promises` cannot be stubbed via `mock.method`.** ESM module properties are non-configurable, so `mock.method(nodeFsPromises, "rename", …)` throws at setup time. Use `node:fs` (a CJS module with configurable exports) for `mock.method` interception — confirmed working in `tests/engine/dot-env.test.ts`. For `node:fs/promises` targets, use real filesystem manipulation (`chmod`, temp directories) or refactor the target code to accept an injectable function.

## Structural-invariants policy

The `INVARIANTS` table in `scripts/structural-invariants.mjs` is the single source of truth for build-time structural rules. Extend it to register new invariants; enforced via `npm run check:invariants` (runs automatically after `test:coverage`). Entries come in two kinds: **count-based** (`{ file, pattern, expected, reason }` — fails when the regex match count diverges from `expected`) and **relational/predicate** (`{ file, validate, reason }` where `validate(text, file)` returns `{ ok, actual?, message? }` — inspects matched lines and their successors). A thrown predicate is contained as a `FAIL`, never coerced to a silent pass; an entry with neither `pattern` nor `validate` is a `FAIL`. The residue **arm→persist** correspondence is enforced by one such relational entry (see below). Exec-lane **active-child registration** is likewise machine-checked (cycle 0267): the shared `validateActiveChildRegistration` predicate is registered as one relational entry per `src/engine/exec-*.ts` lane and fails the build if any lane that calls `spawn(` omits `registerActiveChild` or `unregisterActiveChild` (the cycle-0265 orphan-reap pairing); non-spawning lanes pass vacuously, and a new lane is covered by adding its per-lane entry. Exec-lane **detached-spawn** is likewise machine-checked (cycle 0269): the shared `validateDetachedSpawn` predicate is registered as one relational entry per `src/engine/exec-*.ts` lane (mirroring the active-child list) and fails the build if any lane that calls `spawn(` omits `detached: true` — the process-group-leader flag that makes the reaper's `process.kill(-pid, …)` group-kill (`killActiveChildren`) and group-probe (`anyChildAlive`) reach the whole subtree on suspend (cycle 0265/0268); detection is file-level (`detached: true` may live in a shared options object, not on the `spawn(` line, as in `exec-spawn.ts`), non-spawning lanes pass vacuously, and a new lane is covered by adding its per-lane entry. Verify-step-name **gate lockstep** is likewise machine-checked (cycle 0275): one relational entry against `src/defaults/workflows.yml` (the shared `validateVerifyStepNames` predicate, composing the pure `deriveGateVerifyNames`/`extractVerifyStepNames` helpers) asserts every `scripts/verify.sh` bash step is named one of the degenerate-verification gate's recognized literals (`verify`/`final_verify`), **derived from the gate's own source** (`src/engine/run-cycle.ts` — the `step.name === "…"` literals windowed from the `Degenerate-verification gate` comment's `if (`) rather than re-declared, so renaming a terminal verify step out of lockstep fails the build (naming the workflow and offending step) instead of silently disabling the no-false-greens gate (cycle 0272); fail-closed — an unreadable gate source, no derivable literals, or an unparseable `workflows.yml` is a `FAIL`, never coerced to a pass. The dispatch loop is exposed as an importable export — `runInvariants(invariants, cwd)` (returns the failure count) plus `INVARIANTS` — and the module is **import-safe**: the gate (file-read loop + `process.exit`) runs only under the `import.meta` CLI main guard, so a test can drive the real containment branches in-process (`tests/scripts/structural-invariants.test.ts`) without spawning the script. The `Invariant` shape, the `INVARIANTS` constant type, and the `runInvariants(invariants, cwd): Promise<number>` signature are declared as co-located JSDoc inside the `.mjs` (type-checked via a `// @ts-check` directive + repo-wide `allowJs`), so the test imports the real exports with no separate `.d.mts` mirror to drift — a divergence between the annotations and the implementation now fails `npm run typecheck`. CLI behavior (`node scripts/structural-invariants.mjs` exit 0/1/2, stdout/stderr text) is unchanged.

> **Note:** Agent fleet consistency (REGISTRY in `exec.ts`, `Step.agent` union in `workflow.ts`, and `exec-*.ts` files) is not yet covered by a structural invariant — all three must be updated manually when adding a new agent. When adding an agent, also: (a) resolve its binary via a `CYCLE_<AGENT>_BIN ?? "<agent>"` override in its exec lane and register the matching **agent-binary hermeticity** invariants (lane-has-override + exec-test-has-no-`env: { PATH:` PATH-stub) in `scripts/structural-invariants.mjs` — a real agent CLI on node's bin dir (which `buildChildEnv` prepends) otherwise shadows a PATH-stubbed test fake and makes the suite environment-dependent (this bit codex/gemini/opencode); and (b) document its model contract (model-set shape, `--model` forwarding, `thinking` support, default model, discovery command) per [`docs/models.md`](docs/models.md) → *Adding a new agent — model contract*; and (c) if the new exec lane spawns a child process, register its **active-child-registration** invariant entry (one per `exec-*.ts` lane, sharing `validateActiveChildRegistration`) in `scripts/structural-invariants.mjs` and ensure the lane pairs `registerActiveChild`/`unregisterActiveChild` around the `spawn(` (cycle 0265/0267 orphan-reap contract), and pass `detached: true` to that `spawn(` (machine-checked by `validateDetachedSpawn` — register its per-lane **detached-spawn** entry, cycle 0269, alongside the active-child-registration entry) so the child is its own process-group leader and the reaper's `-pid` group-kill/-probe reaches the whole subtree.
>
> **Verifying hermeticity (hostile-env check):** plant decoy binaries named after every registered agent in node's bin dir (`dirname(process.execPath)`, e.g. `/usr/sbin`) and run `npm test`; any non-hermetic test (one that PATH-stubs instead of using `CYCLE_<AGENT>_BIN`) fails. The structural invariants above are the deterministic, in-gate guard; this is the dynamic cross-check. (claudecode's lane carries `CYCLE_CLAUDE_BIN`, but its many run-cycle tests still PATH-stub `claude`; that's lower-risk because `claude` installs to `~/.local/bin`, not node's bin dir — converting them is tracked follow-up.)

## Architecture

Key modules: `src/engine/` (run-cycle, queue, triage, reflection, blocked, log, branch, exec-*, commit-cycle, issue-lifecycle), `src/cli.ts`, `src/defaults/`.

Registered step agents (via resolveAgent): `claudecode` (first-class; `model` maps to `--model` — inserted before the trailing `-p`; `thinking` is silently ignored — the claude CLI has no thinking flag; prompt delivered via argv `-p`; **also the only lane wired for the opt-in command-output compression hook** — when `engine.compress_output` is true, claudecode steps receive a generated `--settings` `PreToolUse` hook (no other agent has an equivalent mechanism here)), `codex` (first-class; optional `model` and `thinking` step fields map to `--model`/`--thinking` argv flags; `CYCLE_CODEX_BIN` overrides binary for tests; the `exec` subcommand is build-time-pinned by a structural invariant), `gemini` (first-class; `model` maps to `--model`; `thinking` is silently ignored — gemini has no thinking flag here; prompt delivered via stdin; `CYCLE_GEMINI_BIN` overrides binary for tests), `auggie` (first-class; `model` maps to `--model`; `thinking` is silently ignored — auggie has no `--thinking` flag; uses `--print --instruction-file <path>` delivery; `CYCLE_AUGGIE_BIN` overrides binary for tests), `opencode` (first-class; invokes the non-interactive `opencode run` subcommand — bare `opencode` starts the interactive TUI on a non-TTY/piped stdin — with the prompt delivered as the documented `[message..]` positional argv; the `run` element is build-time-pinned by a structural invariant; optional `model` and `thinking` step fields map to `--model`/`--thinking` argv flags; `CYCLE_OPENCODE_BIN` overrides binary for tests), `pi` (first-class; invokes the non-interactive `pi --print` entrypoint — bare `pi` defaults to interactive mode and hangs on a non-TTY/piped stdin — with the prompt still read from piped stdin; the `--print` element is build-time-pinned by a structural invariant; optional `model` and `thinking` step fields map to `--model`/`--thinking` argv flags; `CYCLE_PI_BIN` overrides binary for tests). `bash` steps are dispatched directly via `execBashStep`, not through the agent registry.

**Top-level `defaults` block.** `workflows.yml` accepts an optional top-level `defaults: { agent, model, thinking }` block. At config-load time `loadConfig` resolves `effective X = step.X ?? defaults.X` per field for every step in every workflow, so the rest of the engine keeps reading concrete `step.agent`/`step.model`/`step.thinking`. bash steps must declare `agent: bash` explicitly — `defaults.agent` never coerces a step into bash, and a bash step ignores any resolved `model`/`thinking`. The valid-agent set is derived from the `exec.ts` `REGISTRY` keys (via `knownAgents()`) plus `bash`, not re-hand-coded. A step with neither `step.agent` nor `defaults.agent`, an unknown resolved agent, or a non-object `defaults` each throw a `workflows.yml malformed: … (${path})` error naming the workflow and step (and rejected value). Configs with no `defaults:` block load unchanged. User-facing per-agent `--model` formats, known-good IDs, and live-discovery commands live in [`docs/models.md`](docs/models.md).

`src/engine/exec-types.ts` — canonical home of the `StepResult` type (the shared result shape returned by every exec lane: bash, claudecode, codex, gemini, auggie, opencode, pi). Re-exported from `exec-bash.ts` (`export type { StepResult } from "./exec-types.ts";`) for backwards compatibility; direct importers (`exec-spawn.ts`, `exec.ts`, `run-cycle.ts`) import it from `./exec-types.ts`.

`src/engine/log-fmt.ts` — shared `truncateHeadCapped(s, max)` and `stripFences(s)` helpers used by run-cycle and triage.

`src/engine/rate-limit.ts` — `isRateLimitError(result)` pure helper; returns `true` on exit 429 or exit 1 with rate-limit signal in stderr/stdout. The bare `"429"` substring pattern (`RATE_LIMIT_PATTERNS`) risks false positives on exit 1 when unrelated output contains that digit sequence; tightening to a word-boundary or context-anchored pattern is tracked in `inbox/`.

`src/engine/run-cycle.ts` — rate-limit retry loop: when a step result has `rateLimited: true`, the engine emits `engine.paused { reason: "rate_limit", retry_at }`, sleeps `engine.rate_limit_backoff_ms` ms (default 3,600,000), and retries the same step index. On first clean success after a rate-limited attempt, emits `engine.resumed { reason: "rate_limit_cleared" }`. The retry loop is bounded by `engine.max_rate_limit_retries` (default `24`): after a single step is rate-limited more than the cap times within one `runCycle`, the loop emits `step.end { status: "failed", duration_ms, exit_code, stderr }` for the rate-limited step (so the halt produces the same `step.start`/`step.end` pairing as every other terminal path), then `engine.halted { reason: "rate_limit_max_retries", retries, step_index }`, then `cycle.end { status: "failed" }` (ordering `step.end → engine.halted → cycle.end`), and returns a failed cycle result instead of pausing forever (otherwise it exits on clean success or non-rate-limit failure). Backoff is injectable via `RunCycleOpts.sleepFn` for tests. Rate-limit retries are invisible to `run-one.ts` (complete inside `runCycle`), so they do not increment `consecutive_failures`.

`src/engine/run-cycle.ts` — per-step completion-proof contract: `STEP_ARTIFACTS` is the single declarative step→artifact table (step name → `{ artifact, proof }`), and `ARTIFACT_STEPS` is derived from its keys (no second hand-maintained list). After an agent step exits 0 and its artifact is written, a table-driven check runs the step's `proof` policy (`"nonempty"` via the shared `classifyArtifact` helper — missing/0-byte/whitespace-only ⇒ empty; the `spec` `"spec-min-bytes"` and `fix` `"fix-conditional"` guards are folded in as policies), emits `step.completion_check { cycle_id, step, artifact, status }` (`status` ∈ `pass | fail`), and on `fail` sets `r.status="failed"` so an empty declared artifact is a retryable step failure routed through the unchanged failure/`max_cycle_attempts` path. The `"nonempty"` failure message branches on `r.timedOut`: a SIGTERM-killed step (timeout, typically `exit_code: 143`) gets `formatTimeoutProofError` (timeout-specific wording referencing the actual exit code) so `step.end.stderr` matches the non-zero exit code instead of falsely reading `exited 0`; the clean exit-0 path keeps `formatCompletionProofError`. The routing outcome (failed → retry) and the `step.completion_check` / `step.timeout_salvaged` behavior are unchanged — only the message text differs. `shouldSkipForArtifact` shares the `classifyArtifact` emptiness definition. The three document-workflow steps `plan_documents`, `authoring`, and `review_documents` are declared `"nonempty"` artifact steps in `STEP_ARTIFACTS` (basenames `PLAN_DOCUMENTS.md` / `AUTHORING.md` / `REVIEW_DOCUMENTS.md`), so they receive both `ARTIFACT_SUPPRESS_PROMPT` suppression (via the exported, keys-derived `ARTIFACT_STEPS`) and the completion-proof check. Bash steps and agent steps not in `STEP_ARTIFACTS` are unaffected. See [docs/ENGINE.md](docs/ENGINE.md) → *Completion-proof post-condition*.

`src/engine/run-cycle.ts` — failed-bash-step output capture: when a `bash` step fails, `step.end` gains a head-capped `stdout` excerpt (`MAX_STEP_END_STDOUT = 2000` via `truncateHeadCapped`) alongside the existing `stderr` excerpt, and the engine writes the full stdout+stderr to a per-cycle `<artifactDir>/<step>.out` artifact (header-delimited `=== stdout ===` / `=== stderr ===` layout) pointed at by a `stdout_artifact` field. Successful bash steps and all agent (non-`bash`) steps are unaffected — no new fields, no `.out` file. The `.out` write is best-effort: a write failure emits `step.output_capture_failed { cycle_id, step, artifact, error }`, omits the pointer, and never masks the original `exit_code` or terminal-failure routing. See [docs/ENGINE.md](docs/ENGINE.md) → *Failed bash-step stdout capture*.

`src/engine/run-cycle.ts` — touched.json footprint: `accumulateTouchedFiles` owns footprint accumulation when a `RESET_ELIGIBLE_STEPS` step (`build`/`fix`/`final_fix`/`quick_fix`/`test_fix`/`test_build`) executes in-process (diffs a pre/post `git status --porcelain` snapshot, unions the new in-scope paths, writes the sorted/deduped `{ files }` schema that `commitCycle` reads for `commit.scope_warning`). On the **resume / verify-only** path — when `opts.resume` is set and `startStepIndex` is past every reset-eligible step (`maxResetIdx >= 0 && startIdx > maxResetIdx`), so no mutation step runs this process — `runCycle` instead invokes `recoverTouchedFiles(repoRoot, artifactDir, log, cycleId)` once before the step loop (wrapped in a best-effort `try/catch`). Recovery reconstructs the set from `BUILD.md`'s `## Touched Files` declared footprint (shared `parseTouchedFilesSection` parser, also used by `appendDocumentationPaths`) unioned with current in-scope `git status --porcelain` paths, both `isDenied`-filtered; it **never clobbers** an already-non-empty `touched.json` (silent no-op, no event), emits `touched.recovered { cycle_id, source: "BUILD.md", count }` on success (exactly once), `engine.warning { reason: "touched_recovery_empty" }` when nothing is recoverable (missing `BUILD.md` / absent header), and `engine.warning { reason: "touched_recovery_write_failed" }` on a write error — never throws, never fails the cycle. The normal (non-resume) build path is byte-for-byte unchanged and triggers no new spawn. See [docs/ENGINE.md](docs/ENGINE.md) → *touched.json footprint*.

`src/engine/run-cycle.ts` — no-op / already-satisfied resolution: **two detection points** sharing one marker schema (`classifyNoopMarker`, `src/engine/noop-marker.ts`, fail-closed), one event set, and one drain path. (1) **Research-phase short-circuit (EARLY)** — after a `research` step exits 0 (any workflow, e.g. `feature` / `e2e-tests`; name-keyed on `step.name === "research"` with no workflow check), the engine reads `NOOP.md` and on a **valid** marker resolves the cycle to `noop` before `plan`/`build`/`review` run; there is **no empty-diff precondition and no failure branch** — an absent/malformed/unreadable marker (or any internal read error) simply continues to the next step with no new event. (2) **Build-phase fallback (LATE)** — the build/fix empty-diff guard is marker-gated: when a `build`/`fix` step exits 0 and the `src scripts tests` diff is empty, a valid marker classifies a no-op, else **the existing `formatEmptyDiffGuardError` failure is preserved byte-for-byte** (anti-slop). A **valid** marker (recognized `reason:` ∈ `already-satisfied | duplicate | not-actionable` **and** ≥1 `<path>.<ext>:<line>` evidence line) emits `cycle.noop { cycle_id, issue_id, reason, detected_at_step }` (exactly once; cardinality-pin with `filter(...).length === 1`; `detected_at_step` ∈ `research | build | fix`) then `cycle.end { status: "noop" }`, and `runCycle` returns `{ status: "noop", reason, detectedAtStep }`. The detecting step's `step.end` still fires `status: "ok"`; the no-op return is performed *after* `step.end` so the early return flows through the unchanged `finally` cleanup. `NOOP.md` is **not** in `STEP_ARTIFACTS` (the agent emits a non-empty `RESEARCH.md`/`BUILD.md`/`FIX.md` document alongside it, so the completion-proof passes — no spurious `step.completion_check { status: "fail" }`). `run-one` maps `noop` → exit code **3**; the supervisor (`src/cli.ts` main loop + `runResumeOnce`) routes exit 3 to `noopDrain` (`src/engine/issue-lifecycle.ts`) which moves the issue to `done/` with `noop_at`/`noop_reason`/`noop_step`/`last_cycle_id` stamps and emits `queue.drained { outcome: "noop", reason }`; it **skips `commitCycle`**, **does not retry**, and leaves `consecutive_failures`/`failedCycles` untouched (never calls `recordTerminalFailure`). The reason is recovered from the log via `readCycleNoop` (`src/engine/iteration-guard.ts`); unreadable ⇒ `engine.warning { reason: "noop_reason_unreadable" }` and still drains. See [docs/ENGINE.md](docs/ENGINE.md) → *No-op / already-satisfied resolution*.

`src/engine/walkthrough.ts` — walkthrough-capture orchestration (`resolveWalkthroughHook` / `execWalkthroughHook` / `collectWalkthroughMedia` / `writeWalkthroughManifest` / `walkthroughManifestName`). The `feature` workflow's final step `walkthrough_capture` (`agent: bash`, no `command`) and the `quickfix` workflow's two phase-scoped steps `walkthrough_before` (between `plan_fix` and `quick_fix`) / `walkthrough_after` (final step, after `verify`) are all handled by one **phase-aware** name-keyed intercept in `run-cycle.ts` (gated on membership in the declarative `WALKTHROUGH_PHASES` map: `walkthrough_capture → undefined`, `walkthrough_before → "before"`, `walkthrough_after → "after"`) — they never reach `execBashStep` or the completion-proof machinery. When a phase is set the engine passes **`CYCLE_WALKTHROUGH_PHASE`** (`before`/`after`) to the hook (via the `extra`/`buildChildEnv` re-inject contract, alongside `CYCLE_ARTIFACT_DIR`), collects media from the phase-scoped subdir `<artifactDir>/walkthrough/<phase>/` (`collectWalkthroughMedia(artifactDir, phase)`), and writes the per-phase manifest `walkthrough-<phase>-artifacts.json` (`writeWalkthroughManifest(artifactDir, media, phase)`, basename via `walkthroughManifestName(phase)`); a `walkthrough_before` failure fails the cycle before the fix is applied. The un-phased `walkthrough_capture` path (phase `undefined`: no `CYCLE_WALKTHROUGH_PHASE`, media under `walkthrough/`, manifest `walkthrough-artifacts.json`) is preserved byte-for-byte. Hook discovery is repo-agnostic: the `.cycle/walkthrough.sh` convention (a present, regular, executable file) or an explicit `engine.walkthrough_hook` config path (relative→repo root, else absolute). With no hook the step is inert — one `step.end { status: "skipped", reason: "walkthrough_hook_absent" }`, no `step.start`, no failure — so cycle's own CLI repo (which configures no hook) always skips it clean. When active the engine spawns the hook via `/bin/bash <abs>` (array args, `shell:false`, curated `buildChildEnv`) with `CYCLE_ARTIFACT_DIR` re-injected via `extra`; the hook writes media into `<artifactDir>/walkthrough/`, which the engine lists and (if non-empty) records in a `<artifactDir>/walkthrough-artifacts.json` manifest pointed at by a `walkthrough_artifacts` field on the step's `step.end` (mirroring the failed-bash `stdout_artifact` surfacing). A non-zero hook exit routes through the normal fatal step-failure path (`step.end { status: "failed" }` → `cycle.end { status: "failed", failing_step }`); a post-success collect/manifest-write failure is best-effort — it emits `step.walkthrough_capture_failed { cycle_id, step, artifact, error }`, omits the pointer, and leaves the cycle outcome unchanged. `execWalkthroughHook` takes an optional `{ timeoutMs, timer }` and, when armed (via the defensively-coerced `engine.walkthrough_hook_timeout_ms`), spawns the hook `detached: true` and performs a SIGTERM→SIGKILL bounded-kill on expiry (`WALKTHROUGH_KILL_GRACE_MS = 5000`), marking the result `timedOut` and routing it through the same fatal path with timeout-specific stderr. See [docs/ENGINE.md](docs/ENGINE.md) → *Walkthrough capture*.

`src/engine/walkthrough-gate.ts` — degradation **blocking gate** (cycle 0274; no false greens, Core thesis). Pure resolver module (modeled on the pure half of [[verify-counts]] / `noop-marker.ts`): `resolveWalkthroughRequired(cfg)` (defensive `=== true` of `engine.walkthrough_required`; absent/non-boolean/missing engine ⇒ `false`), `resolveExpectsUi(fm)` (the per-issue UI-scope opt-out — returns `false` **only** for an explicit boolean `expects_ui: false`, mirroring `resolveExpectsCode`'s `=== false`-only structural check; absent/non-boolean/`true` ⇒ `true`, fail-closed UI-shipping), the pure `classifyWalkthroughDegradation(text)`, and the fail-closed async reader `readWalkthroughDegradation(sidecarPath)`. The signal is the **hook-owned** sidecar `<artifactDir>/walkthrough/walkthrough-status.json` (`{ degraded: boolean, reason?: string }`). Fail-closed direction is **inverted vs noop-marker**: an **absent** sidecar (ENOENT) ⇒ **not degraded** (the hook ran and did not flag), but a **present-but-unparseable/unreadable** sidecar ⇒ **degraded** (a corrupt proof-of-work signal cannot be coerced to "the app works"); `degraded === true` folds in the hook reason as `degraded_flag[: <reason>]`, a parse failure surfaces as `unparseable: <detail>`. Wired into the **un-phased** `walkthrough_capture` intercept in `run-cycle.ts` (between the hook's fatal-exit check and the success-tail media collect), **short-circuited on the config check first** so the default-off path runs zero added I/O (no issue read, no sidecar parse) and is byte-for-byte unchanged. A cycle is **UI-shipping** (gated) when `walkthrough_required === true` **and** `resolveExpectsCode(fm) !== false` **and** `resolveExpectsUi(fm) !== false` (the per-issue source read reuses the lazy-read+`catch`-degrade pattern — any read/parse error ⇒ fail-closed UI-shipping). On a gated-degraded verdict the engine emits `walkthrough.degraded { cycle_id, step, reason, sidecar }` **exactly once** (cardinality-pin with `filter(...).length === 1`) then routes through the **existing** fatal block (`step.end { status: "failed" }` with `formatWalkthroughDegradedError` stderr "walkthrough did not demonstrate the feature: …" → `cycle.end { status: "failed", failing_step: "walkthrough_capture" }` → early `return`) — **no new halt reason**. The `quickfix` `walkthrough_before`/`walkthrough_after` phases are **not** gated (un-phased `walkthrough_capture` only). See [docs/ENGINE.md](docs/ENGINE.md) → *Walkthrough capture* and [BRIEF.md](BRIEF.md) → *Core thesis*.

`src/engine/preflight.ts` — engine-start preflight gate (`runPreflight`). Runs once in `src/cli.ts` after the lock/config load and `engine.start` emit but **before** triage and the first cycle (skipped under `--skip-preflight`). Resolves every agent the active workflow + triage will use (via the `AGENT_BINARY` table — the manual mirror of `exec.ts` `REGISTRY` and each lane's `CYCLE_<AGENT>_BIN ?? "<bin>"` resolution; **keep in sync** when adding an agent — a known agent with no entry surfaces as a loud `internal` failure) and probes each with `<bin> --version` (`spawnSync`, array args, `shell:false`, `buildChildEnv`); confirms required tools (`bash`/`git` + bare-name `argv[0]` heads of configured bash-step commands, skipping `/`-containing script paths) resolve on the curated PATH; and emits a non-fatal `wsl_shadow` warning when a resolved path is under `/mnt/c/` while WSL (detected via `/proc/version`, injectable). Read-only and never throws — every probe error is a recorded failed check and an outer `try/catch` converts any internal error into a single `internal` failure. `cli.ts` renders the result into one `engine.preflight.warning` per warning, then exactly one terminal `engine.preflight.ok { checks }` (clean pass) or `engine.preflight.failed { failures }` + `engine.stop { status: "halted", reason: "preflight_failed" }` + `process.exit(1)` before any `cycle.start`. Cardinality-pin both terminal events with `filter(...).length === 1`. See [docs/ENGINE.md](docs/ENGINE.md) → *Preflight gate*.

`src/engine/shell.ts` — resolvable shell abstraction (`resolveShell({ platform, env, config, existsSync })` → `ShellResolution` discriminated union). Pure/side-effect-free (no spawning); resolution precedence is exactly: `engine.shell` config (used verbatim, no existence check — the user owns the choice) → `CYCLE_SHELL` env (verbatim) → platform auto-discovery (POSIX: `/bin/bash`; Windows: the ordered `WINDOWS_SHELL_CANDIDATES` git-bash/WSL `bash.exe` probe list, first existing wins) → on Windows with nothing found, a structured `{ ok: false, searched, message }` whose `message` names the searched paths + remediation (install git-bash/WSL or set `engine.shell` / `CYCLE_SHELL`). An unresolved resolution ⇒ a failed `StepResult` (no spawn, no timer armed); `execBashStep` also gained a spawn-`error` handler so a *configured-but-missing* shell path surfaces as `status:"failed"` (exit `-1`) rather than an unhandled `ENOENT`. `engine.shell` plumbs through `loadConfig` (optional string; absent/empty/non-string ⇒ unset). `CYCLE_SHELL` env override also pins the shell. See [docs/ENGINE.md](docs/ENGINE.md) → *Shell resolution*.

`src/engine/verify-counts.ts` — pure reporter-output parser (`parseVerifyCounts(output): { executed, skipped, total } | null`) for the no-false-greens degenerate-verification gate (cycle 0272). Recognizes vitest (`Tests  N passed | M skipped (T)`), jest (`Tests:  N passed, M skipped, T total`), node:test (`# tests`/`# pass`/`# fail`/`# skip`/`# todo`), pytest (`===== N passed, M skipped in Xs =====`), and cargo (`test result: ok. N passed; M failed; K ignored`); `executed = passed + failed`, `skipped` folds in skip/ignored/todo, `total` = the reporter's explicit total else `executed + skipped`. Module-level regex constants, never throws, returns `null` on any unrecognized/garbage/empty/non-string input (fail-open). Modeled on the pure half of [[noop-marker]] (`src/engine/noop-marker.ts`). Consumed only by the `run-cycle.ts` verify hook (below). Coverage floor ≥95%.

`src/engine/run-cycle.ts` — degenerate-verification gate (no false greens; Core thesis): after a **bash** step named `verify` or `final_verify` exits **0**, the engine parses its full in-memory `r.stdout` via `parseVerifyCounts` and, on a **confident degenerate verdict** — `executed < verify_min_executed` **and** (`skipped > 0` **or** `total > 0`) — flips the step to a retryable failure (`r.status = "failed"`, `formatVerifyUnverifiedError` stderr `verification incomplete: N tests skipped, M executed — cannot confirm the app works`) and emits `verify.unverified { cycle_id, step, executed, skipped, total, reason: "zero_executed" }` **exactly once** (cardinality-pin with `filter(...).length === 1`). The flip reuses the existing failed-bash `.out` capture + `step.end { status: "failed" }` + retry/terminal path — **no new halt reason**. **Fail-closed** on a confident degenerate parse; **fail-open** (byte-for-byte unchanged: no event, no status change) when output is unparseable (`parseVerifyCounts ⇒ null`) or the parser throws (contained in a `try/catch`). The hook **never** fires for agent steps, non-`verify`/`final_verify` bash steps, or a non-zero exit (the native failure path is untouched). The `(skipped > 0 || total > 0)` precondition keeps a parsed `0/0/0` empty suite from blocking (it is not the "everything skipped" target). The threshold is the defensively-coerced `engine.verify_min_executed` knob (default `1`; `typeof === "number" && Number.isInteger && >= 0 ? raw : 1` at the read site — absent/non-integer/negative ⇒ `1`; `0` disables the gate). See [docs/ENGINE.md](docs/ENGINE.md) → *Degenerate verification gate* and [BRIEF.md](BRIEF.md) → *Core thesis*.

`src/cli/validate-workflow.ts` — shared pure `validateWorkflowName(workflow, available, prefix)` helper (cycle 0270) returning a discriminated `{ ok: true, name } | { ok: false, message }`; never throws for any `string | undefined`. `undefined` (flag absent) ⇒ resolves the single `DEFAULT_WORKFLOW` constant (`"feature"`) and validates it against `available` (cycle 0271) — accepted (`{ ok: true, name: "feature" }`) only when the configured set includes `feature`, otherwise rejected with `unknown workflow "feature" — available workflows: …` (the same shape as an explicit-unknown rejection), closing the cycle-0270 bug class for the no-flag path (no longer "never rejected") so a feature-less repo fails loud on the most-travelled path instead of false-greening into the deep `runCycle` throw; `""` (value-less flag) ⇒ rejected with `--workflow requires a value`; an unknown explicit name ⇒ rejected with `unknown workflow "<name>"`; both reject messages append `available workflows: …`. The `"feature"` default literal lives in exactly one place (`DEFAULT_WORKFLOW`), referenced by `parse-args.ts` rather than re-typed. Consumed by **both** `runDoctor` (`src/cli/doctor.ts`, `prefix: "doctor"`) and the `cycle run` start path (`src/cli.ts`, `prefix: "run"`), so the unknown / value-less `--workflow` diagnostic cannot drift between the two commands (AC enforced by `tests/cli/validate-workflow.test.ts`). The run-path arg parser (`src/cli/parse-args.ts`) surfaces a three-state `workflowExplicit: string | undefined` signal (absent ⇒ `undefined`; trailing value-less `--workflow` ⇒ `""` without throwing; explicit ⇒ the value) that the gate validates **after** config load and **before** `engine.start`/preflight/`markInProgress` — a rejected workflow writes no log line, mutates no queue row, and exits `2`. Both resume entrypoints in `src/cli.ts` are wired onto the same helper: resume #1 (`runResumeOnce`) emits the `run:` stderr line + `engine.warning { reason: "resume_workflow_missing" }` and returns `skipped` without `markInProgress`; resume #2 (main loop) emits the `run:` stderr line + `engine.halted { reason: "unknown_workflow" }` and halts (`break`, exit 1) before `markInProgress` — neither false-greens into the deep `runCycle` `unknown workflow:` throw and its attempt-burning retry loop.

`src/engine/iteration-guard.ts` — iteration-too-fast guard machinery used by the `src/cli.ts` supervisor: `readCycleEndFailure(repoRoot, cycleId)` (bottom-up log-tail read returning the failed cycle's `failing_step` and the matching `step.end.duration_ms`; missing/unreadable ⇒ `undefined`, degrade to normal retry) and the pure `advanceFastFailCounter(prev, opts)` state transition (same-step sub-threshold ⇒ increment; different step / `≥`-threshold / unreadable duration / guard disabled ⇒ reset; `fastBail` once count reaches `K`).

`src/engine/halt-accounting.ts` — pure `recordTerminalFailure(prev, opts)` used by the `src/cli.ts` supervisor's commit-failure, fast-bail, and budget-exhausted branches: the single source of truth for terminal-failure bookkeeping (increment `consecutiveFailures`, append `failedCycles` as a new array, set `lastHaltContext`, reset the fast-fail counter) returning a `{ halt }` decision the caller acts on. `break`/`terminalDrain` stay at the call site. Owns the exported `HaltContext` type (imported back into `cli.ts`).

`src/engine/engine-lock.ts` — shared `acquireLock(lockPath)` / `releaseLock(lockPath)` PID-lockfile helpers used by the supervisor to enforce single-engine exclusion. The lockfile is written with the supervisor's PID at `run` start and removed **only** on the supervisor's own PID-guarded `process.on("exit")` (the child `run-one` never touches it), so `.cycle/engine.lock` is held on disk for the full run lifetime. `acquireLock` throws a **typed** error (`.code === ALREADY_RUNNING_CODE`, i.e. `"ENGINE_ALREADY_RUNNING"`) when the lock is held by a live process (or `EPERM`); genuine read/probe/write failures throw their native error. The acquire fires in `src/cli.ts` **before** `createLogger`/`engine.start`/preflight/triage, so a rejected concurrent run writes **zero** bytes to `log.jsonl`: it prints `engine already running, pid X` to stderr and exits with the dedicated `LOCK_HELD_EXIT_CODE = 75` (EX_TEMPFAIL — distinct from generic `1`, `run-one`'s `2`/`3`, and signal `130`/`143`), while a genuine acquire failure exits `1`. The lock path is canonicalized via `realpathSync(cwd)` so two sessions reaching the same repo through divergent mount/symlink views (e.g. `/mnt/c/...` vs the real path) coordinate on one physical file. Stale-lock reclaim (`kill(pid,0)` ⇒ `ESRCH` ⇒ overwrite) and the `releaseLock` PID-match guard (delete only when the file's PID equals `process.pid`; idempotent, never throws) are preserved; a failed liveness probe (non-`ESRCH`/`EPERM`) or unreadable lock is never coerced to "stale". Coverage floor: 100% line / 100% function.

`src/engine/child-env.ts` — `buildChildEnv(extra)` builds the subprocess env: strips all `CYCLE_*` vars by prefix, prepends the parent Node's bin dir to PATH, then overlays `extra`. Callers must re-inject any `CYCLE_*` vars subprocesses legitimately need (e.g. `CYCLE_BASE`, `CYCLE_ID`, `CYCLE_TITLE`) via `extra`.

## Subprocess discipline

- Always `spawn` / `spawnSync` with array args. Never `exec` / `execSync`. Never `shell: true`.
- Subprocesses inherit a curated PATH via `src/engine/child-env.ts`.
- **Re-injection contract**: `buildChildEnv` strips all `CYCLE_*` vars. Any new `exec-*.ts` or subprocess wrapper that needs `CYCLE_ID`, `CYCLE_BASE`, etc. must pass them explicitly in the `extra` argument (typically via `cycleEnv`). Omitting them produces silent `undefined` in the subprocess — no runtime error.

## Workflow defaults

- Force `--workflow feature` until triage + multi-cycle decomposition land.
- **Failed cycles wipe + clean-restart; dead issues park, queue flows** (`src/engine/failed-cycle-teardown.ts` + `src/cli.ts`). When a cycle's step fails with attempts remaining, the supervisor tears down the failed attempt — reverts every non-engine-owned worktree change to HEAD, removes untracked non-engine-owned files, and wipes the cycle's artifact docs — and re-runs the cycle CLEAN from step 1 (emits `cycle.restart`), up to `max_cycle_attempts` (default 3). When attempts are exhausted (or a fast-bail), it tears down the code residue (keeping the docs for diagnosis), drains the issue to `failed/`, and **continues to the next issue** — one persistently-failing issue parks in `failed/` without blocking the queue. The engine halts only after `engine.max_consecutive_failures` (default 2) **distinct** terminal failures, via the existing `engine.halted { reason: "max_consecutive_failures", failed_cycles, threshold }` + `engine.stop` + exit 1. Teardown reuses `isEngineOwned` (so `.cycle/**`, the queue, the log, `docs/cycle/**` are never touched) and verifies the tree is clean afterward; on terminal it arms the residue context **only if teardown couldn't clean the tree** (the fallback). The same teardown runs on the **resume path** (`runResumeOnce`), so a mid-cycle crash + restart self-heals instead of residue-halting. The dirty-worktree residue guard (`failed_cycle_dirty_worktree`) is therefore now a **fallback** — it fires only on a teardown failure or at startup/resume after a mid-cycle crash, NOT on the normal failure→retry path.
- `engine.rate_limit_backoff_ms` — milliseconds to sleep between rate-limit retries (default 3,600,000 = 1 hour).
- `engine.max_rate_limit_retries` — per-step consecutive rate-limit retry cap (default `24`; `0`/negative/non-integer/malformed ⇒ default `24`, coerced defensively at the read site). When a single step is rate-limited more than the cap times within one `runCycle`, the engine emits `step.end { status: "failed", duration_ms }` for the rate-limited step (matching the `step.start`/`step.end` pairing of all other terminal paths), then `engine.halted { reason: "rate_limit_max_retries", retries, step_index }`, then `cycle.end { status: "failed" }` (ordering `step.end → engine.halted → cycle.end`), and returns a failed cycle result through the normal terminal-failure path — never a silent kill. The early return still flows through the `finally` checkout/base-pull cleanup. Increment-then-compare boundary: rate-limiting exactly the cap times keeps retrying (a later success completes the cycle); the `cap + 1`-th rate-limited attempt halts with `retries: cap + 1`.
- **Per-step / per-workflow `timeout_ms` override** (`src/engine/workflow.ts` — `resolveStepTimeoutMs`, wired in `loadConfig`). An optional `timeout_ms?: number` is accepted on any **step** and on any **workflow** (alongside the existing `engine.step_timeout_ms`). At config-load time each step's effective wall-clock budget resolves `step.timeout_ms ?? workflow.timeout_ms ?? engine.step_timeout_ms ?? (no timer)` — written back onto the concrete `step.timeout_ms`, mirroring the top-level `defaults` resolution, so the rest of the engine reads one concrete value. `run-cycle.ts` threads that resolved value into the existing `timeoutMs:` spawn arg and reports it as `step.timeout { limit_ms }`; all kill (SIGTERM→SIGKILL), salvage (`step.timeout_salvaged`), and event machinery is reused byte-for-byte — only the *value* of the budget changes. **Defensive coercion (step + workflow only):** malformed/non-positive values (non-number / non-integer / `0` / negative / `NaN` / `Infinity` / string) are ignored and fall through to the next level — never throw, never arm a zero/negative timer. The **engine** value is passed through **un-coerced** as the final fallback, so a config with no `timeout_ms` anywhere is byte-for-byte unchanged (`step.timeout_ms === engine.step_timeout_ms`; absent everywhere ⇒ `undefined` ⇒ no timer). See [docs/ENGINE.md](docs/ENGINE.md) → *Step timeout resolution*.
- `engine.min_step_duration_ms` — iteration-too-fast guard threshold (default 2,000). After `K=2` consecutive failures of the *same* step, each completing in under this many milliseconds of wall-clock, the supervisor fast-bails the cycle to `terminalDrain` instead of burning the remaining `max_cycle_attempts` budget on a tight instant-failure loop. A value of `0` (or absent/malformed) disables the guard. Each fast-bail emits exactly one `step.warning { reason: "iteration_too_fast", duration_ms, threshold_ms }` before terminating — never a silent kill. Routes through the existing terminal-failure path (counts toward `max_consecutive_failures`); no new halt reason.
- `engine.compress_output` — opt-in command-output compression for `claudecode` steps (default `false`; absent/non-boolean/malformed ⇒ disabled, resolved defensively at the read site as `=== true`). When `true`, `run-cycle` materializes `.cycle/compress-hook-settings.json` for each `claudecode` step and passes it as `--settings` (inserted before `-p`), registering a `PreToolUse` Bash hook that rewrites allowlisted operator-free read commands (`git`, `ls`, `cat`, `grep`, …) to run through `cycle compress-output`. **claudecode-only** — no other agent has this hook. **Fail-open**: the hook never blocks a tool call (any parse/classify error ⇒ original command runs), and a settings-write failure emits one `step.warning { reason: "compress_hook_settings_failed" }` and the step proceeds without `--settings`. The genuine degrade paths (parse/throw `catch`, and a `PreToolUse` event with no string `tool_input.command` — schema drift) write a one-line `cycle compress-output-hook:`-prefixed diagnostic to `process.stderr` so a persistent hook failure is observable instead of silently disabling compression — still exit 0, empty stdout, never block; normal passthroughs (shell operator / non-allowlisted binary) and the rewrite-success path stay silent to avoid stderr spam. With the flag off (the default), no settings file is written and the claude argv is byte-for-byte identical to the pre-change baseline.
- `engine.walkthrough_hook_timeout_ms` — bounded-kill wall-clock timeout (ms) for the `walkthrough_capture` hook spawn. Documented recommended value `600000` (10 min, exported as `DEFAULT_WALKTHROUGH_HOOK_TIMEOUT_MS`); `0`/negative/non-integer/`NaN`/`Infinity`/non-number/absent ⇒ disabled (no timer armed, hook runs to completion), coerced defensively at the `run-cycle.ts` read site. On expiry the hook's process group is killed SIGTERM→SIGKILL (5s grace, `WALKTHROUGH_KILL_GRACE_MS`), the result is marked `timedOut`, and it routes through the fatal step-failure path (`step.end { status: "failed" }` → `cycle.end { failing_step: "walkthrough_capture" }`) with timeout-specific stderr referencing the actual exit code. The default is **not** auto-applied — opting in is explicit.
- **Preflight gate** (`src/engine/preflight.ts`, wired in `src/cli.ts`) — runs once at engine start, after lock/config load and `engine.start` but before triage and cycle 1. Probes every agent CLI the active workflow + triage will use (`<bin> --version`, `CYCLE_<AGENT>_BIN`-aware resolution) and confirms required tools (`bash`/`git` + detected bash-step tools) resolve on PATH; a missing/wrong-platform agent or missing tool is a clean halt: `engine.preflight.failed { failures }` + `engine.stop { reason: "preflight_failed" }` + non-zero exit before any `cycle.start`. A clean pass emits exactly one `engine.preflight.ok`. WSL `/mnt/c/`-shadowed binaries emit a non-fatal `engine.preflight.warning`. `--skip-preflight` bypasses the gate (no preflight events fire). Keep `AGENT_BINARY` in `preflight.ts` in sync with the exec-lane fleet.
- **No-op / already-satisfied resolution** (`src/engine/noop-marker.ts` + `run-cycle.ts` + `src/cli.ts`) — an issue whose work is already done resolves to a distinct terminal outcome instead of burning the failure budget, via **two detection points** sharing one marker schema, event set, and drain path. **Research-phase (EARLY):** after a `research` step exits 0 (any workflow, e.g. `feature` / `e2e-tests`), a valid `NOOP.md` short-circuits the cycle to `noop` before `plan`/`build`/`review` run (no empty-diff precondition, no failure branch — an invalid/absent marker just continues to the next step). **Build-phase (LATE fallback):** when a `build`/`fix` step exits 0 with an empty `src scripts tests` diff **and** the agent wrote a valid `NOOP.md` (reason category ∈ `already-satisfied | duplicate | not-actionable` + ≥1 `file.ext:line` evidence line). Either way the engine emits `cycle.noop` (with `detected_at_step` ∈ `research | build | fix`) + `cycle.end { status: "noop" }`, the issue moves to `done/` (run-one exit code **3** → `noopDrain`), and `consecutive_failures` is **not** incremented and the cycle is **not** retried. At the build phase a marker absent/malformed ⇒ the existing `formatEmptyDiffGuardError` failure is preserved (anti-slop); at the research phase it ⇒ normal continuation. `NOOP.md` is **not** in `STEP_ARTIFACTS`. See [docs/ENGINE.md](docs/ENGINE.md) → *No-op / already-satisfied resolution*.
- **`expects_code: false` doc-only opt-out** (`src/engine/run-cycle.ts` — `resolveExpectsCode` / `parseDocDeliverablePaths`) — a per-issue YAML-frontmatter field (default `true`) that relaxes the **build-phase** empty-diff guard for research/doc-only issues. Resolved lazily inside `runCycle` (only when the `src scripts tests` diff is empty) by reading the still-in-`todo/` source issue; `resolveExpectsCode(fm)` returns `false` **only** for an explicit boolean `expects_code: false` (absent/non-boolean/malformed/`true` ⇒ `true`, fail-closed; a missing/unreadable issue degrades to the `true` default — never throws out of the guard, never coerces a silent `ok`). When `expects_code === false`, the `src scripts tests` diff is empty, **and** a non-empty in-scope doc deliverable exists (a `docs/**` path that is not denied and not under the per-cycle `docs/cycle/**` artifact tree — detected via `git status --porcelain --untracked-files=all -- docs` + `parseDocDeliverablePaths`), the build/fix step keeps `status: "ok"` and the cycle completes as a normal **`ok`** (docs committed by the unchanged `commitCycle` path, issue drains to `done/`) — **not** a `cycle.noop`/`noopDrain`. The relaxed branch is checked **before** the `NOOP.md` marker gate; with no docs deliverable the unchanged no-op/`formatEmptyDiffGuardError` branches run. An opt-out cycle that delivers **nothing** (empty code diff + no `docs/**` change outside `docs/cycle/**`) still fails the guard. **Anti-slop preserved**: an issue without the opt-out and an empty diff still fails byte-for-byte. See [docs/ENGINE.md](docs/ENGINE.md) → *`expects_code: false` opt-out*.
- **Degenerate-verification gate** (`src/engine/verify-counts.ts` + `run-cycle.ts`; cycle 0272) — operationalizes the no-false-greens thesis: a `verify`/`final_verify` **bash** step that exits **0** but executed **zero** non-skipped tests (e.g. an e2e suite that entirely `test.skip`s itself when env is unset) is treated as **unverified**, not green. After the step exits 0 the engine parses its stdout (`parseVerifyCounts`, recognizing vitest/jest/node:test/pytest/cargo) and on a confident degenerate verdict (`executed < engine.verify_min_executed` **and** `skipped > 0 || total > 0`) flips `r.status = "failed"`, emits `verify.unverified { cycle_id, step, executed, skipped, total, reason }` once, and surfaces `verification incomplete: … 0 executed …` via the existing failed-bash `.out`/`step.end`/retry path. **Fail-closed** on a confident degenerate parse; **fail-open** (unchanged) when output is unparseable (`null`) or the parser throws. `engine.verify_min_executed` (default `1`; absent/non-integer/negative ⇒ `1`; `0` disables) sets the floor. Reuses the step-failure machinery — no new halt reason. See [docs/ENGINE.md](docs/ENGINE.md) → *Degenerate verification gate* and [BRIEF.md](BRIEF.md) → *Core thesis*.
- **Walkthrough degradation blocking gate** (`src/engine/walkthrough-gate.ts` + `run-cycle.ts`; cycle 0274) — operationalizes the no-false-greens thesis for the strongest "did the app actually run" signal: in a repo that opts in via `engine.walkthrough_required: true` (default `false`; absent/non-boolean/malformed ⇒ `false`, coerced `=== true` at the read site), a **UI-shipping** `feature` cycle whose present-and-ran `walkthrough_capture` hook reports degradation **fails** instead of draining `ok`. UI-shipping = required **and** not doc-only (`resolveExpectsCode(fm) !== false`) **and** not explicitly opted out (the new per-issue frontmatter `expects_ui: false`, alongside `expects_code: false`); fail-closed — only an explicit `expects_ui: false`/`expects_code: false` exempts. The signal is the hook-owned sidecar `<artifactDir>/walkthrough/walkthrough-status.json` (`{ degraded: boolean, reason?: string }`): **absent ⇒ not degraded** (hook ran, did not flag), `degraded: true` ⇒ degraded, **present-but-unparseable ⇒ fail-closed degraded** (a corrupt proof signal cannot be coerced to "works"). The gate fires only on the un-phased `walkthrough_capture` step, only after the hook exits 0 (the non-zero/timeout fatal path is untouched), only when the hook is present-and-ran (no hook ⇒ unchanged `walkthrough_hook_absent` skip), and is **short-circuited on the config check first** so the default-off path runs zero added I/O and is byte-for-byte unchanged. A gated-degraded verdict emits `walkthrough.degraded { cycle_id, step, reason, sidecar }` once and routes through the existing fatal block (`step.end { status: "failed" }` with `formatWalkthroughDegradedError` stderr → `cycle.end { status: "failed", failing_step: "walkthrough_capture" }`) — no new halt reason. The `quickfix` `walkthrough_before`/`walkthrough_after` phases are not gated. See [docs/ENGINE.md](docs/ENGINE.md) → *Walkthrough capture* and [BRIEF.md](BRIEF.md) → *Core thesis*.
- **Failed-cycle dirty-worktree residue guard** (`src/engine/failed-residue-guard.ts` + `src/cli.ts`) — after a cycle ends in **terminal** failure, the supervisor checks the worktree for uncommitted residue (excluding engine-owned runtime state) **before** it acts on the next unit of work, so a failed cycle never piles a new cycle on top of a dirty tree. Critical in trunk mode (`CYCLE_TRUNK_BASED=1`), where the residue sits directly on the base branch. Gated at **three check sites** via an in-memory `pendingResidueContext` (set at every failure branch that loops back — every terminal-failure branch **and the within-budget retry arm**; cleared on success/noop/clean-tree): **at engine start** (cross-process re-check, below), **before `runResumeOnce`** (resume/retry path), and at the **top of the `while (!halted)` loop** (before `popNextPending`). The within-budget retry arm arms the context after `drainRetry`, so the loop-top check halts a retry before it re-runs on the dirty tree (a third gated path alongside resume and loop-top). Residue present ⇒ exactly one `engine.halted { reason: "failed_cycle_dirty_worktree", failed_cycle_id, issue_id, dirty_paths, message }` + the terminal `engine.stop { reason: "failed_cycle_dirty_worktree" }` (epilogue suppressed via `engineStopEmitted` so exactly one fires) + the `formatFailedCycleResidueDiagnostic` text (paths + cycle id + commit/`git stash`/`git reset --hard` remediation) on stderr + `process.exit(1)`. **Engine-owned exclusion**: `isEngineOwned` reuses `isDenied` and layers the whole `.cycle/**` and `docs/cycle/**` trees it doesn't cover, so issue-lifecycle moves, `run.log`, `engine.lock`, and artifact docs never trip it. **`git status` non-zero halts** (a failed check is never coerced to "clean"; `message: "Residue check failed…"`, `dirty_paths: []`) — never a silent proceed. **Clean tree** ⇒ no new event, behavior byte-for-byte unchanged. The within-budget `drainRetry` path is now residue-gated (cycle 0038). **Cross-process persistence is implemented (cycle 0039):** `pendingResidueContext` is mirrored to a `.cycle/failed-residue-context.json` state file (engine-owned; atomic tmp+rename write; `src/engine/residue-context-store.ts`) — persisted at the four terminal-failure branches **and the within-budget retry arm** (five persist sites, cycle 0042), deleted on every clear transition (success/noop/clean-tree). **The arm→persist pairing is machine-checked (cycle 0043)**, not doc-maintained: a relational `INVARIANTS` entry in `scripts/structural-invariants.mjs` (`validate`-style) fails the build if any non-whitelisted `pendingResidueContext = { … }` arm in `src/cli.ts` is not immediately followed by `await persistResidue(...)`; the tail-derived resume/startup arm (`failingStep: undefined`, around `src/cli.ts:650`) is structurally whitelisted (intentionally un-persisted). The persisted file is re-checked **once at engine start** (after lock/config/`engine.start`/preflight, before triage and resume) through the unchanged `haltIfResidue()`/`emitResidueHalt()`, so a fresh process after a terminal-failure cycle (which left no in-flight log tail) halts before stacking a new cycle on residue. A malformed/unreadable file degrades to no-context with an `engine.warning {reason: "residue_context_unreadable"}` (distinct from the `git status` non-zero halt); write/delete failures emit `engine.warning {reason: "residue_context_write_failed" | "residue_context_delete_failed"}` and fall back to in-memory-only. With the retry arm now persisted (cycle 0042), the guard is crash-safe across **every** loop-back path — there is no longer an un-persisted in-process-only gate. See [docs/ENGINE.md](docs/ENGINE.md) → *Failed-cycle dirty-worktree residue guard*.
- **Signal interruption — suspend and resume** (`src/cli/run-one.ts` + `src/engine/active-child.ts` + `src/cli.ts` + `src/engine/log-tail.ts`) — a SIGTERM/SIGINT to a running `cycle run` supervisor (operator/dashboard "pause") is a clean **suspend**, not a leak-and-halt. The supervisor tracks its in-flight `run-one` worker (`activeWorker`) and forwards a bounded **SIGTERM→grace→SIGKILL** (`WORKER_KILL_GRACE_MS = 5000`) to it after writing the `cycle.killed` interrupted marker; the worker, in turn, reaps its own detached agent/bash grandchild via the **active-child registry** (`src/engine/active-child.ts` — `registerActiveChild`/`unregisterActiveChild`/`killActiveChildren`, `WORKER_CHILD_KILL_GRACE_MS = 5000`; `run-one`'s `reapAndExit` group-kills SIGTERM→poll→SIGKILL). `exec-bash` steps are now spawned `detached: true` (own process group) so the registry's `-pid` group-kill reaches the whole subtree; `killActiveChildren` swallows ESRCH/EPERM (a reaper never throws). `anyChildAlive` — the fast-poll's liveness probe — probes **group** liveness (`process.kill(-pid, 0)`, the negated/group target), symmetric with `killActiveChildren`'s `-pid` kill (cycle 0268), so the poll declares a child's subtree dead only when the whole process group is gone: a tool forked into the group that outlives its leader and ignores SIGTERM keeps `anyChildAlive` reporting alive (ESRCH ⇒ group gone, keep checking; EPERM/any-other-error ⇒ fail-closed toward alive, never throws), so the SIGKILL backstop fires instead of the worker exiting early — closing the orphaned-grandchild window. No orphaned worker/agent keeps mutating the repo after the signal. `parseLogTail` surfaces `InFlightCycle.interrupted` — true when a `cycle.killed` marker (matching the in-flight `cycle_id`, or with an undefined `cycle_id`) interrupted a *running* cycle (no `cycle.end`, **or** the kill precedes a racy `cycle.end` the torn-down `runCycle` emitted while exiting — the kill marker wins); fail-closed otherwise (normal completion / between-cycles kill / malformed marker ⇒ `interrupted: false`). On an interrupted tail the supervisor **bypasses `haltIfResidue()`** (no `pendingResidueContext` armed) and emits `engine.resume { interrupted: true }`, routing straight to `runResumeOnce` with **no teardown** so the WIP is preserved and the interrupted step re-runs on top of it; a non-interrupted in-flight tail keeps the residue-gated path (and the whitelisted `failingStep: undefined` arm) byte-for-byte. The dirty-worktree residue guard remains the genuine-failure path only. See [docs/ENGINE.md](docs/ENGINE.md) → *Signal interruption — suspend and resume*.
