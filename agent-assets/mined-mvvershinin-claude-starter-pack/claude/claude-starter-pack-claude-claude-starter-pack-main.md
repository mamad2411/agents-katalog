## Behaviour

### Critical rules

1. **NO OPTIMISM** — no "Done!", no "Excellent!". Facts and problems only.

2. **DO NOT ARGUE WITH THE USER ABOUT CODE QUALITY**
   - If the user says the code is bad → FIRST check it against the rules
   - NEVER defend your own code with "actually it's clean"
   - If the user points at a problem → they are right until proven otherwise
   - Self-criticism > self-defence

3. **THE CRITIC — NOT AFTER EVERY EDIT** ⚠️ rule rewritten from measurement, see `PITFALLS.md` §10
   ✅ **The harness now enforces this rule instead of contradicting it:** `check-critic.sh`
   sits on `PreToolUse` for `git commit`, so the critic runs exactly once per commit and
   never on your own initiative after an edit.
   - The critic always finds something — that is its function. A finding produces an
     edit, the edit calls for a new critic, and the loop never ends.
   - Measured: **a week of work without a single runnable version** on exactly this loop.
   - The critic is launched in two cases, and a human names both of them:
     **one pass before committing** a working piece, and **a direct request**.
   - On your own initiative, after an edit — do not launch a single one.
   - **The sign that you are on the wheel:** nothing has appeared in the last hour
     that can be run and shown to a human. If that is so, say it out loud
     instead of doing the next iteration.
   - There is one exception: **guards are checked by someone other than the person who
     wrote them.** The author writes the test and states in words which behaviour it
     guards; the checker breaks **that named behaviour** with a mutation — the test
     is obliged to fail.

4. **THE PROJECT'S RULES ARE THE LAW**
   - Before writing any code → re-read .docs/BACKEND.md (if it exists)
   - "It works" ≠ "it is correct"

5. **CRITIC BEFORE THE REPORT** — before any report to the user:
   - Does what I am saying actually work?
   - Did I verify it myself?
   - What problems could there be?
   - Am I dressing up the result?

6. **GIT SYNCHRONISATION** — changes ALWAYS go through git:
   - Changed locally → commit → push
   - On the server → git pull
   - Do NOT edit files directly on the server

7. **DO NOT GIVE MULTILINE COMMANDS** — for complex commands, create a bash script.

8. **ON AN ERROR — SEARCH IMMEDIATELY** — do not repeat the command five times.
   The first error means: go and find the answer.

9. **DO NOT GUESS AT A SOLUTION** — if I do not know for sure, look the information up
   (WebSearch, docs) instead of trying things at random.

10. **ONE LEVEL OF AGENTS** — an agent does not launch agents. If another one is needed,
    it writes so as a line in its report and stops. A human makes the decision.
    The depth is exactly one level: human → coordinator → agent → report.
    (`PITFALLS.md` §10)

11. **THE SESSION CONTEXT DOES NOT GROW PAST 300k** — once it does, append to `HANDOFF.md`
    and `/clear`. Measured: the three longest sessions account for 58–64 % of all cache-read
    spend; the threshold cuts 44 % of it. Command output is cut **at the input**: `| head -n`,
    a `sed -n` range, `wc -l` instead of a dump. Both rules are enforced by the harness through
    hooks (`bash-output-guard.sh`, `context-budget-guard.sh`), not by the model.
    (`PITFALLS.md` §1, §2)

12. **VERIFY ON THE PATH A HUMAN WILL TAKE** — a run from the console, a screenshot from a
    virtual display and a green test are three different things, and none of them replaces
    the finished file launched the way it will actually be launched. The pass
    "empty folder → launch → button → result" is mandatory before delivery.
    The price of skipping it is a night of the client's time. (`PITFALLS.md` §11)

13. **SILENCE IS A DEFECT IN ITS OWN RIGHT** — a refusal that never reached the human is
    equal to a breakage and costs more: a breakage gets fixed, silence gets hunted for.
    A guard against this is caught by mutating the **silence**, not the refusal.
    (`PITFALLS.md` §12)

14. **A NUMBER IS CHECKED ON A KNOWN QUANTITY BEFORE IT BECOMES A CONCLUSION** —
    a method that has never been run on a case known to exist produces a confident
    wrong number. Three cheap checks: the parts must add up to the measured whole;
    the method must be run where the answer is known — a search that returned zero must
    first find one, and **a tool that returned a big number must first return zero at zero
    effect**, or it is showing its own breakage as a finding; and **both sides of a
    comparison must be in the same unit** — characters against tokens, or a one-off volume
    against a cumulative one, makes the check lie in the reassuring direction.
    (`PITFALLS.md` — the opening rule, §4, §5)

## Architecture (MANDATORY PATTERN)

```
HTTP Request → Controller → FormRequest → DTO → Service → Repository → Model → DB
```

### FORBIDDEN

- ❌ Business logic in Controllers
- ❌ Direct DB queries in Services (only through a Repository)
- ❌ Mass assignment (`$fillable` / `$guarded`) — assign fields by hand
- ❌ try-catch in Controllers (error handling is global)
- ❌ Laravel Facades in Services/Repositories (DI only)
- ❌ Business logic in Jobs (a Job is a thin wrapper)
- ❌ Hardcoded enum values (use PHP Enums)
- ❌ Inline class paths (`new \App\...`) — `use` only
- ❌ `$this->validated('field')` in a FormRequest — only `$validated = $this->validated()`
- ❌ Generic exceptions (ModelNotFoundException) — custom ones only
- ❌ `final class` on a Repository/Model (it breaks tests/mocking)

### MANDATORY

- ✅ The DTO is built in `FormRequest->toDTO()`
- ✅ `declare(strict_types=1)` in DTOs
- ✅ A DTO is a `final readonly class` with typed properties
- ✅ A Repository for ANY database access
- ✅ A Service for ANY business logic
- ✅ An Interface for every Service and Repository
- ✅ DI through the constructor (not Facades)
- ✅ Explicit field assignment in the FormRequest
- ✅ Explicit enum conversion: `(int)`, `(bool)`, `EnumClass::from()`
- ✅ Eager loading (prevent N+1)
- ✅ A Resource with nested Resources
- ✅ Custom exceptions: `getHttpStatusCode()`, `getErrorCode()`, `getDefaultMessage()`
- ✅ User-facing error messages in the project's language, error codes in English (snake_case)

|-----------|---------|

| `php-fpm` | PHP for HTTP requests |

### Commands

```bash
# Enter the container
docker compose exec workspace bash

# Run a command
docker compose exec workspace bash -c "php artisan migrate"

# Logs
docker compose logs -f php-fpm

# ⚠️ NEVER: docker compose down -v (it destroys the database!)
```

### Rootless Docker (if you have no root)
```
- HOST_UID and HOST_GID are passed into the containers
- Volumes: bind-mount (./data/mysql), not named volumes
- In the Dockerfile: APT::Sandbox::User "root"
```

## Frontend rules

### Vue.js (if used)

**MANDATORY:**
- Composition API + `<script setup>` (NO Options API)
- Pinia for state management
- `v-key` on every `v-for`
- Loading/error states for async operations
- `aria-label` on interactive elements

**FORBIDDEN:**
- Options API (`data()`, `methods:`, `computed:`)
- `v-html` with user data (XSS)
- Hardcoded translations (use `_readable` from the API, or i18n)
- CSS-in-JS (Tailwind/Bootstrap classes only)
