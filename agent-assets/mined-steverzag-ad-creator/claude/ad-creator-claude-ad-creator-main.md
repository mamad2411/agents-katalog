# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A prompt-driven ad generator. There is no app UI — ads are generated by asking
Claude, authored as HTML, and exported to the PNG/MP4 files ad platforms accept.

## Entry points

Either drive the whole pipeline with one command, or run a single stage.

- **`/campaign`** — plan a campaign before building anything: personas, pain
  points, and a mapped set of distinct ad concepts. Writes `campaigns/<slug>/`
  and the briefs the stages below then consume. This is the multi-ad path.
- **`/build-ad <brief path>`** — one ad, end to end, from a campaign brief.
- **An inline request** ("make me a 9:16 UGC ad for…") — goes through the
  `create-ad` skill, which gathers the brief conversationally.

**There is no brief file for one-off ads.** A single ad's brief is settled in
conversation: the five required fields get asked for, the rest are inferred from
the brand profile and stated as assumptions. Written briefs exist only inside a
campaign, where they're worth the file because they're inherited and reused.

**`/build-ad` builds exactly one ad.** A campaign is a queue of separate runs,
not a batch — deliberately, because rendering is minutes per motion ad and a
failure halfway through a batch is worse than a queue you can walk.

`/build-ad` composes the stage commands below rather than reimplementing them.
Each stage command is the single source of truth for its stage; the skills own
the craft. **Don't duplicate guidance between them** — if two files say how to
render, one of them is about to go stale.

**Commands and skills are different things with similar names.** `/build-ad`
(a command, user-invoked, the pipeline) is not the `create-ad` skill (invoked by
Claude, the craft). The command was renamed off `create-ad` precisely so the two
can't be confused.

## Commands, by stage

| | Does | Writes |
|---|---|---|
| `/campaign` | Plans a campaign: personas, pain points, concept map. Promotes concepts to briefs | `campaigns/<slug>/` |
| `/brief` | Validates a brief — gaps, contradictions, claim boundary | nothing |
| `/generate` | Scaffolds and authors the ad files. Stops before rendering | `ads/<slug>/` |
| `/render` | Exports to `out/`. No edits, no judgement | `out/` |
| `/verify` | Looks at every rendered format; technical correctness. Reports only | nothing |
| `/report` | Summarizes an ad for handoff | nothing |
| `/adjust` | Applies a requested change, then re-renders and re-checks | varies |
| `/critique` | Grades design against the rubric and fixes what's weak | varies |
| `/brand` | Builds or edits a client profile — from a URL if given one — and recompiles it into every ad using it | `brands/`, `brand.css` |
| `/variant` | Sibling ads differing in exactly one element | `ads/<slug>-a…` |

Four boundaries worth holding:

- **`/campaign` plans, `/build-ad` builds.** `/campaign` writes markdown and
  never scaffolds an ad; nothing downstream re-opens the strategy.
- **`/brand` knows the client, `/campaign` knows the pitch.** Anything true of
  the business regardless of campaign belongs in the profile, and a campaign
  that re-gathers it is a `/brand` gap to fix, not a thing to repeat.
- **`/verify` asks whether it rendered correctly; `/critique` asks whether it's
  any good.** An ad can pass one completely and fail the other.
- **`/adjust` does what was asked and stops.** Deciding what's weak unprompted
  is `/critique`.
- **`/render` never edits and `/verify` never fixes.** Both hand to `/adjust`.

## Skills

Five skills carry the domain knowledge. Use them; don't work around them.

| Skill | For |
|---|---|
| `campaign-strategy` | Planning a campaign — personas, pain points, concept map |
| `create-ad` | Generating any ad — image, carousel, video, UGC |
| `render-ad` | Exporting to PNG/MP4 and diagnosing bad renders |
| `critique-ad` | Grading a rendered ad's design against a rubric and fixing it |
| `brand-setup` | Brand profiles: colours, fonts, voice |

Ad-domain knowledge (angles, safe zones, beat sheets, copy rules, visual design,
per-type structure) lives in `.claude/skills/create-ad/references/`. Read the
relevant file before writing creative — the structure is most of the quality.

Two axes decide an ad's shape, and they're independent: the **angle** (the
argument — problem-solution, testimonial, educational…) and the **format**
(image, carousel, video, ugc). See `references/angles.md`.

## Scripts

```bash
pnpm bootstrap                          # install + playwright chromium + vendor
pnpm dev                                # preview server, index of all ads
pnpm new <type> <slug> [--brand x]      # scaffold an ad
pnpm render ads/<slug>                  # export to out/
pnpm render ads/<slug> --format 9x16    # one format only
pnpm render --all                       # every ad
pnpm brand ads/<slug> <brand>           # (re)compile brand.css
pnpm brand --all [brand]                # recompile every ad, or only that brand's
pnpm clear [--dry-run|--yes]            # remove every generated ad
pnpm report                             # regenerate docs/ad-creator-guide.pdf
```

**`pnpm render` does not recompile `brand.css`, and neither does `pnpm dev`.**
Only `pnpm new` and `pnpm brand` compile it — an export shouldn't mutate source,
and a compiled `brand.css` acts as a snapshot so editing a brand doesn't
silently restyle already-approved creative.

The cost is that an edited brand JSON changes nothing on screen until
`pnpm brand` runs. Both commands therefore *detect* it and say so — render in
its log, the preview server as a badge on the index. The shared check is
`checkBrandFreshness()` in `scripts/lib/brand.mjs`; it compares the compiled CSS
against what `brandToCss` would produce now. Content, not mtimes — mtimes lie on
OneDrive, where a sync rewrites them in both directions.

Recompiling stays an explicit step. `pnpm brand --all` does the whole fleet.

`pnpm clear` is destructive and intentionally not in the permission allowlist.
It refuses to run without a TTY unless given `--yes`, and `--dry-run` lists
without deleting. It removes two things: real ads (a directory with an
`ad.config.json`) and empty leftovers (no files anywhere beneath). A directory
holding files that isn't an ad is always left alone and reported.

Deletes retry and are verified afterwards, and one stuck directory is reported
rather than aborting the rest — on Windows a handle held by OneDrive or an
editor makes `rm` fail part-way, and a half-deleted ad that keeps its folder is
both unclearable and unrecreatable (`pnpm new` refuses an existing slug).

**pnpm, not npm.** Two consequences worth knowing:

- The install script is `bootstrap`, not `setup` — `pnpm setup` is a built-in
  pnpm command that configures pnpm's own global bin dir, and would shadow it.
- pnpm blocks dependency build scripts by default. `ffmpeg-static` needs its
  postinstall to fetch the ffmpeg binary, so it's approved in
  `pnpm-workspace.yaml` (`allowBuilds`). Without that, every video render fails
  on a missing binary. That setting lives in `pnpm-workspace.yaml` in pnpm 11 —
  a `pnpm` field in `package.json` is silently ignored.

No `--` before script arguments; pnpm forwards them, flags included.

## Layout

```
campaigns/   one folder per campaign: campaign.md, strategy.md, briefs/
runtime/     ad.css + ad.js — shared by every ad. Changes here affect all ads.
templates/   scaffolding copied by `pnpm new`, one per ad type
brands/      client profiles as JSON: styling, voice, and what the client sells
ads/         generated ads, one folder each. out/ is gitignored.
scripts/     CLI: new, dev, render, brand, clear, report, sync-vendor
docs/        guide.html — source for the PDF built by `pnpm report`
```

Format presets (`1x1`, `4x5`, `9x16`, `16x9`, `191x1`) are defined in
`scripts/lib/config.mjs`, not in the templates.

## Client profiles

`brands/<name>.json` is the whole client, not just its palette. Only `colors`,
`fonts` and `radius` compile into `brand.css`; `business`, `logo` and `voice`
are read by the skills. So an edit confined to the non-compiling half needs no
`pnpm brand`, and `checkBrandFreshness()` — which compares compiled output —
correctly ignores it.

`business` exists so `/campaign` stops asking for what the project has already
seen: what the client is, where they trade, their languages, their socials, and
`lines[]` — the product lines, each with its URL. A campaign is scoped to
exactly one line, so that array is the pick-list.

**It caches no claims, deliberately.** Prices, offers, response times and
testimonials go stale silently, and in a regulated category every later
campaign would inherit the stale copy. Those are fetched fresh from the line's
URL when a campaign is planned and dated to that run. Caching the stable half
is what makes fetching the volatile half cheap — the profile supplies the exact
URL to read.

## Campaigns

A campaign is one product line, one placement set, one language. Three moving
parts, and the reasons they're separate:

- **`campaign.md` holds what every ad in the campaign shares** — brand,
  placement, ratios, do-not-say, and the claim boundary with a source per line.
  A brief states only what *differs*, and inherits the rest. Repeating the
  claim list into fifteen briefs is how it goes stale.
- **Concepts are mapped in bulk; briefs are written on promotion.** The map in
  `strategy.md` runs to 20–40 one-line concepts, which is the point — the full
  field is what makes the built subset a choice. Briefs carry finished scripts
  and are expensive, so `/campaign promote` writes them for the concepts
  actually going into production.
- **`strategy.md`'s production map is the state.** Each concept is `mapped` →
  `promoted` → `built`. There's no other record of what exists.

**Campaign ads are prefixed, not nested** (`ads/<campaign>-<nn>-<name>`).
`findAdDirs()` in `scripts/lib/config.mjs` scans one level under `ads/`, so a
nested folder is invisible to render, dev and clear.

## Assets

Two homes. Everything is served from the repo root over http — the renderer runs
the same static server the preview does — so both are reached with a relative
path and no build step.

| | For | From an ad's `index.html` |
|---|---|---|
| `ads/<slug>/assets/` | this ad only | `assets/hero.jpg` |
| `brands/assets/<brand>/` | every ad of a brand — logo, fonts | `../../brands/assets/<brand>/logo.svg` |

**Imagery arrives after the ad, not before.** `ads/<slug>/assets/` doesn't exist
until `pnpm new` runs, so ads are generated against placeholder treatments and
real files are added with `/adjust`, which drops them in and re-renders. Don't
build a staging area upstream of that — a per-ad folder holding the ad's own
files is the whole mechanism.

**A missing asset renders as a hole, and `pnpm render` names it.** The export
still succeeds — a 404 image can't stop a screenshot — so the log line is the
signal:

```
⚠ 1 asset(s) failed to load — these render empty:
    assets/does-not-exist.png
```

`assetsReady()` in `runtime/ad.js` treats `img.complete` as terminal on its own
and records anything that never decoded into `__AD__.brokenAssets`, which
`scripts/render.mjs` reads after `ready`. Checking `complete && naturalWidth`
instead is a deadlock: a 404 image is already `complete`, so it would be sent to
wait for a `load`/`error` event that has already fired, and `ready` never
resolves. That surfaced as a bare `waitForFunction: Timeout` with nothing about
assets in it.

## Architecture

Every ad is a static page that calls `AdRuntime.define()` once. The runtime
(`runtime/ad.js`) serves two modes, selected by the `?mode=render` URL param:

- **preview** — plays on a loop in a browser with a scrub bar
- **render** — exposes the contract `scripts/render.mjs` drives headlessly

The contract between those two files is the thing to understand before changing
either:

| `window.__AD__` | |
|---|---|
| `ready` | Promise; fonts decoded, images loaded, timeline built |
| `seek(t)` | Puts the DOM at exactly time `t`, resolves once pixels settle |
| `setSlide(i)` | Isolates one carousel slide for capture |
| `duration`, `fps`, `slideCount` | Read by the renderer to plan frames |

The renderer sizes the viewport to the format, calls `seek()` once per frame,
and pipes PNG screenshots into ffmpeg (H.264, yuv420p, faststart).

**This is why animation must be a paused GSAP timeline.** CSS transitions and
`@keyframes` cannot be scrubbed, so they would export as frozen frames.
`runtime/ad.css` disables them inside `.ad-stage` to make that fail loudly.

`<video>` elements are not scrubbed by GSAP — they must be registered with
`ctx.video(el, { start })` or they render as a frozen first frame.

## Verification

There is no test suite. Correctness here is visual, so **verify by rendering and
looking at the output** — an exit code of 0 says nothing about whether the ad is
right. Render, then `Read` the PNG.

Layout bugs are routinely invisible in source and obvious in a render. When one
turns out to be in shared behaviour (a runtime rule losing a specificity fight,
for example), fix it in `runtime/` rather than patching each template.

Rendering motion costs ~3.5–4 frames/second: a 20s ad at 30fps is 600 frames,
about 2.5 minutes. That's expected — don't kill a render that looks stalled.

To check one moment of a timeline without a full encode, grab frames directly:

```bash
node .claude/skills/critique-ad/scripts/frames.mjs ads/<slug> --at 0,4,8 --thumb
```

It drives the same `__AD__` contract the renderer does, so a frame it captures
is the frame that would export. Output goes to `.critique/` (gitignored).
`--thumb` adds a 15%-scale copy, which is the size the ad is actually judged at.

Anything else that needs Playwright has to live inside the project — a script
under the scratchpad directory can't resolve `playwright` from `node_modules`.

## Invariants

- **Size in `--u`, never `px`.** `--u` is 1% of the stage's smaller side. One
  layout has to survive 1:1, 4:5 and 9:16.
- **Content inside `.ad-safe`.** Platform UI covers the edges.
- **Animation goes on the timeline.** A bare `gsap.to()` won't render.
- **Use `.set()`, not `.call()`.** Callbacks don't fire predictably when
  scrubbing backwards.
- **Nothing non-deterministic in a timeline.** No `Math.random()`, `Date.now()`,
  or rAF-driven state — frame *n* must be identical on every render.
- **`brand.css` is generated.** Edit the brand JSON and recompile; hand edits
  are silently reverted by the next `pnpm brand`.
- **No CDNs.** Assets and libraries are local, so renders are reproducible and
  work offline.

## Content rules

Never invent statistics, prices, ratings, guarantees, awards, or testimonials.
If the user didn't supply it, use an obvious placeholder and flag it. UGC-style
creative is a first-person device, not a real endorsement — never present a
fabricated person as a genuine customer.

Platform specs in `references/platform-specs.md` drift over time. They're
working defaults; verify against current platform docs before a paid delivery,
and state which spec you built to.

## Report and conversation rules

Report and conversation responses are going to be as concise and condensed as possible.
