# Task Log System

Система автоматической фиксации и логирования выполнения задач через Cline hooks.

Система включает:
- **Хуки** - автоматическая фиксация событий жизненного цикла задачи (старт, промпт, сжатие, возобновление, завершение, tool-вызовы).
- **`.tasklog/`** - каталог логов задач: `<taskId>.md` (история задачи), `<taskId>.tmp` (снапшот), `<taskId>.tools.log` (tool-вызовы).
- **TASK.md** - шаблонные инструкции для модели.
- **MEMORY.md** - персистентная память и архитектура (корневой и пер-компонентные файлы; см. раздел «Персистентная память (MEMORY.md)»).

## Общая концепция

Система использует bash-скрипты в `.clinerules/hooks/`, которые вызываются Cline в ключевые моменты жизненного цикла задачи. Скрипты используют общую библиотеку `.clinerules/hooks/lib.sh` для парсинга taskId из JSON-входа, форматирования дат, вычисления длительности и унифицированной записи в лог.

Данные пишутся в `.tasklog/` - это единственная точка хранения логов.

Каждая задача пишется в свой собственный файл. Имя файла определяется полем taskId из JSON входа, который численно соответствует UnixTime моменту старта задачи. Расширение файла md, данные пишутся в текстовом формате с маркировкой MarkDown.

Система ведения логов минимально зависит от поведения модели и работает append only. Основные данные извлекаются из JSON-входа хука, а модель дописывает согласованный план работ и его итоговые результаты при завершении задачи.

В файле [TASK.md](TASK.md) содержатся шаблонные инструкции для модели о необходимости сохранения согласованного плана работ в файле с именем `<taskId>.md` и сохранении в этот файл итога выполнения задачи.

## Персистентная память (MEMORY.md)

Персистентная память агентов и описание архитектуры хранятся в файлах `MEMORY.md` - по одному
на каталог/компонент, плюс корневой `MEMORY.md` на уровне проекта. Отдельного сервера
персистентной памяти **нет**.

- `MEMORY.md` в каталоге компонента - архитектура компонента **и** факты/инварианты/решения
  этого контекста (scope).
- Корневой `MEMORY.md` - факты, решения и связи уровня всего проекта.

### Обязательная структура файла

Каждый `MEMORY.md` начинается с блока метаданных (шапки):

```markdown
# MEMORY.md
> scope: <каталог/компонент>
> role: persistent-memory
> last_reviewed: <дата последней оптимизации/ревизии>
> review_period: <дней между ревизиями>
> max_size: <лимит размера, чтобы избежать постоянного роста>
```

и содержит обязательные разделы: `## Architecture`, `## Facts and invariants`,
`## Decisions`, `## Relations` (по мере применимости).

### Правила ведения

- **Ограничение на размер**: файл не должен превышать `max_size`. При превышении -
  провести ревизию и сокращение, не допускать неограниченного роста.
- **Периодический анализ корректности**: не реже чем раз в `review_period` дней от
  `last_reviewed` проверять соответствие содержимого актуальному коду и обновлять
  `last_reviewed`. Время оптимизации хранится в самом файле и служит ориентиром
  периодичности обновления.
- Хранить только то, что сложно вывести из API/исходного кода; без временных данных,
  без статусов задач и багов (это `.tasklog`).
- Перед добавлением - проверять на дубликаты; добавлять наблюдения, а не перезаписывать.
- **Граница ответственности**: `.tasklog/` - планы/статусы/итоги задач (append-only, не удаляется);
  `MEMORY.md` - архитектура + персистентные факты/инварианты/решения; `.clinerules/backlog/` -
  самодостаточные описания отдельных задач и техдолга (что сделать, без хода/итогов);
  `.clinerules/workflows/` - переиспользуемые методики. Не дублировать одно в другом.

## Файловая структура

```
.clinerules/
  README.md                 # Документация системы (этот файл)
  TASK.md                   # Шаблонные инструкции для модели
  backlog/                  # ТОЛЬКО техдолг, кторый НЕ вошел в согласованный план и,sk помечен "не сейчас" "позже" "в будущем"т.е. отмечен как нужный для реализации, но не на текущем этапе.
    <area>-<slug>.md        # Одна задача/пункт техдолга на файл (статус — в шапке)
  workflows/                # Переиспользуемые методики/промпты (без статусов)
  hooks/
    lib.sh                  # Общая библиотека функций
    TaskStart               # Хук старта новой задачи
    UserPromptSubmit        # Хук отправки промпта пользователем
    PreCompact              # Хук перед сжатием контекста
    TaskResume              # Хук возобновления задачи
    TaskComplete            # Хук завершения задачи
    PostToolUse             # Хук после каждого вызова инструмента
    PreToolUse              # Хук перед каждым вызовом инструмента
.tasklog/
  <taskId>.md               # Файл лога задачи (taskId = unixtime ms старта)
  <taskId>.tmp              # Снапшот (временный, удаляется при TaskComplete)
  <taskId>.tools.log        # Лог tool-вызовов (временный, агрегируется при TaskComplete)
```

**Важно: Каталог `.tasklog/` и файлы в нём являются постоянными и никогда не удаляются** - ни хуками, ни тестами, ни при каких условиях. Удаляются только конкретные тестовые файлы внутри него. Сам каталог `.tasklog/` и файлы в нём являются частью рабочего окружения.

## Backlog: задачи и техдолг

`.clinerules/backlog/` - **ХРАНЕНИЕ** информации о техдолга (не лог выполнения). Один
файл - одна задача/пункт, плоско, без подкаталогов жизненного цикла; статус - в шапке файла.

- Имя файла: `<component>-<slug>.md`.
- Тело - самодостаточное описание: что сделать и критерии готовности (DoD);
- Перед добавлением - проверить отсутствие дубля (grep по каталогу); не смешивать несвязанное в файле.

## Жизненный цикл задачи

```
1. TaskStart (новая задача)
   ├-- создаёт .tasklog/<taskid>.md
   ├-- считывает статические инструкции из файла AGENTS.md
   ├-- считывает инструкции из файла TASK.md
   ├-- заменяет в TASK.md "<taskid>.md" на реальное имя файла задачи
   └-- возвращает contextModification с AGENTS.md и TASK.md для модели

2. UserPromptSubmit (пользователь отправил промпт)
   └-- аппендит в .tasklog/<taskid>.md

3. PreCompact (сжатие контекста)
   └-- аппендит в .tasklog/<taskid>.md

4. TaskResume (возобновление задачи)
   ├-- если .tasklog/<taskid>.md существует
   └-- если .tasklog/<taskid>.md не существует - создает с нуля

5. Переход Plan→ACT
   └-- НЕ является хуком. Согласно инструкции в TASK.md при переходе
       в режим ACT модель сама должна сохранить согласованный план
       работ в .tasklog/<taskid>.md

6. TaskComplete (завершение задачи)
   └-- аппендит в .tasklog/<taskid>.md: блок с результатом и командой
```

## Хуки и их логика

### Общая библиотека lib.sh

Все хуки используют общие функции из `.clinerules/hooks/lib.sh`:

- `extract_task_id JSON jq_path` - парсит `taskId` из JSON по указанному jq-пути и выводит в stdout. Возвращает 1 при ошибке.
- `normalize_task_id task_id` - приводит `taskId` к числовому виду (Unix timestamp ms). Для нового формата `conv_<timestamp_ms>_<suffix>` извлекает числовое ядро без префикса и суффикса; для старого числового формата возвращает значение без изменений.
- `timestamp_to_iso timestamp_ms` - преобразует Unix timestamp в миллисекундах в ISO8601 строку.

Хуки после извлечения всегда нормализуют `taskId` через `normalize_task_id`, поэтому имя файла задачи всегда числовое (старый формат), независимо от того, какой формат `taskId` передал Cline.

Каждый хук формирует путь к файлу задачи самостоятельно через `"${TASKLOG_DIR}/${TASK_ID}.md"`.

**Важно: Функции не устанавливают глобальные переменные.** Все значения возвращаются через stdout и сохраняются хуком в локальные переменные.

### Проверка хуков

Реализация хуков проверяется автономным тестом (изолированный `TASKLOG_DIR` во временном
каталоге, реальный `.tasklog/` не затрагивается):

```
bash test/hooks/selftest.sh
```

Тест покрывает: идемпотентность `TaskStart` (файл задачи не перезаписывается, история не
теряется), дозапись промптов, запись `.tools.log`, агрегацию `## Completion report`
(имена инструментов обоих поколений, подсчёт `failures` по полю статуса), правила
`PreToolUse` (git/cmake/grep для текущих имён инструментов и формы `parameters.commands`),
отсутствующие поля `PreCompact`, создание файла в `TaskResume`.
