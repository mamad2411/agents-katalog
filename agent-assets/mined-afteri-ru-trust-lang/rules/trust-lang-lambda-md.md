
# Лямбды: ссылочный захват (`[&x]`) и неявный захват (`[=]`/`[&]`)

## Контекст

В первой итерации лямбды (TermID `LAMBDA`) реализован **только захват по значению**:
`[x, y]` (имена, без типов). Формы `[&x]` (ссылочный захват), `[=]`/`[&]` (неявный) и
init-capture `[name = expr]` сейчас **распознаются и отвергаются** с явной диагностикой:
- `reference capture is not supported; only capture-by-value '[name]' is allowed` (в `FuncDecl`-конструкторе);
- для `[x:Type]`/`[x = expr]` — `unsupported lambda capture; only a plain variable name '[name]' ...`.

## Что сделать

1. Семантика ссылочного захвата: разрешать `[&x]`/`[&*x]` только когда заём валиден по borrow-checker
   (регион/владение), с проверками вида ссылки; согласовать с `applyRefAttrs`/`refAxisOf`.
2. Кодоген: C++-захват по ссылке (`[&c_x]`) с учётом манглинга и модели владения trust-ссылок
   (умные ссылки уже обёртки — решить, что означает `&x` для `shared`/`weak`).
3. Необязательно: неявный `[=]`/`[&]` и init-capture — отдельная развилка.

## DoD

- `[&x]` компилируется при валидном займе и даёт явную ошибку при невалидном (по borrow-checker).
- На `[=]`/`[&]`/`[name = expr]` — точная диагностика «не поддерживается» или реализация.
- Сквозной пайплайн (parser → analyzer → codegen) + lit-тесты (codegen + diag).
- `cmake --build _build` и `make run_tests` зелёные.

## Границы

Не дублировать: архитектура и инварианты — в `MEMORY.md` компонентов (syntax/ast/semantic/transpiler/types);
ход/итог работ — в `.tasklog/1789493038905.md`.



# Функциональный тип параметра (лямбда как callback/predicate)

## Контекст

Документация позиционирует анонимные функции как callback/predicate («передаются аргументом в
другую функцию»), но **выразить функциональный тип параметра нельзя**:
- `f : :Function` → синтаксическая ошибка (`::` = CREATE_TYPE);
- `f : Function` → `error: unable to generate C++ type 'Function'`;
- параметр без типа → `std::any`, и вызов `c_g()` даёт невалидный C++ (`std::any` не callable).

Поэтому реально передать лямбду в функцию и вызвать её внутри — невозможно (лямбда-колбэк
недостижима). Это делает фичу малоприменимой вне локального значения.

## Что сделать

1. Синтаксис функционального типа (варианты): `f : (Int32) -> Int32` / `f : Func<:Int32, :Int32>` /
   переиспользование `FunctionTypeData` в `types` (уже есть) + рендер `std::function<...>`.
2. Семантика: `resolveType` функционального типа в позиции параметра; проверка совместимости
   сигнатур при передаче лямбды/функции; вызов параметра-значения (уже поддержан для переменной).
3. Кодоген: параметр типа `std::function<Ret(Args...)>` + `#include <functional>`.
4. Диагностика при несовпадении сигнатур.

## DoD

- `apply(f : <функциональный тип>) := { @return f(1); }; apply([](x:Int32):Int32 { @return x+1; });`
  компилируется и работает (`--run`).
- Несовпадение сигнатуры лямбды и типа параметра → явная ошибка.
- lit-тесты (codegen + e2e + diag), `cmake --build _build`, `make run_tests` зелёные.

## Границы

Архитектура/инварианты — в `MEMORY.md` компонентов (types/semantic/transpiler/syntax); ход/итог — в `.tasklog`.


# Вывод типа возврата функционального значения (лямбды) из тела

## Контекст

При отсутствии аннотации `:Ret` у лямбды `buildFuncType` использует `INVALID_TYPE_ID` = `void`,
поэтому `f := [](x:Int32){ ... }` получает тип `std::function<void(int32_t)>`. Согласовано, что
`:Ret` опционален и **выводится из тела** (см. `docs/content/ru/docs/types/funcs.md`), но вывод
не реализован. Сейчас это либо void, либо UB (тело без `@return`), что расходится с документацией.

## Что сделать

1. Определить правило вывода возвращаемого типа лямбды из тела:
   - последнее выражение тела (`{ expr }`) — его тип; или
   - тип значений `@return`-узлов (пост-условие/assert-like вывод); при неоднозначности — ошибка
     с требованием явной аннотации.
2. Учесть trust-условия (`kTrustFlag` — не выводится автоматически, только явная аннотация).
3. Согласовать с кодогеном: `std::function<Ret(...)>` должен совпасть с дедуцируемым типом C++-лямбды.
4. Обновить `funcs.md` и `status.md`.

## DoD

- `f := [](x:Int32){ @return x*x; };` → `std::function<int32_t(int32_t)>` (как при явном `:Int32`).
- Неоднозначность/невозможность вывода → явная диагностика (без тихого void).
- lit-тесты (codegen + diag), `cmake --build _build`, `make run_tests` зелёные.
