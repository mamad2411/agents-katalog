# 编写 Vibe Coding PRD

## 目标

把用户提供的材料转为短、明确、可实现、可验收的编码说明。保留影响产品行为和工程实现的信息，删除商业价值、市场宣传、组织汇报等与编码无关的叙述。

最终交付完整的 Markdown PRD。不要在关键产品决策未经用户确认时把草案称为“最终版”。

## 强制原则

1. 区分“材料中明确写出”“基于材料推荐”“等待用户决定”。不得把推荐或猜测写成已确认需求。
2. 不推断用户想要的功能、范围、优先级、产品形态或技术约束。缺失或存在多种合理解释时，使用原生用户输入弹框提问；没有弹框工具时，使用简短的编号选择题。
3. 每次集中询问 1–3 个最关键问题，每题给 2–4 个互斥选项，并允许用户自定义回答。先给推荐项及一句理由，但不得替用户选择。
4. 维护决策账本：`已确认`、`待确认`、`明确不做`、`以后再做`。每轮确认后更新，避免重复提问。
5. 每完成需求定义、范围与优先级、技术栈、原型四个阶段，都暂停并请求确认，再进入下一阶段。用户一次性给全信息也要展示提炼结果并确认关键决策。
6. 语言简洁、少黑话。仅保留编码 Agent 实现、测试和排错所需的信息。
7. 不把“体验良好”“响应迅速”“功能完善”等不可观察描述当作验收标准。

## 工作流

### 1. 读取并分类输入

先收集用户消息、附件和链接中的内容，再按以下类型分类。混合材料要拆分标注，不强行归为单一类型。

- **明确需求**：目标用户、发生场景、真实痛点三项都有明确证据。进入需求定义。
- **原始 PRD**：已有页面、流程、规则、接口、数据或工程实现描述，通常面向研发。提取编码 Agent 所需的功能行为、约束、数据、异常和验收信息；去除商业价值、市场规模、宣传话术、汇报过程和不影响实现的背景。
- **竞品分析**：主要描述别的产品及其能力。把竞品能力整理为“候选采用 / 候选改造 / 明确不做”，询问用户选择；不得默认照搬。
- **其他或不清晰**：无法确认目标用户、场景或痛点，或材料只有一句方案口号。先澄清真实需求。

输入含飞书/Lark 文档 URL 或 token 时，调用可用的飞书文档读取能力，优先使用 `lark-doc`，完整读取正文后再分类。若文档内嵌表格、Base、画板等对象，按其资源类型调用对应能力读取与需求有关的内容。读取失败时说明缺失内容并请用户粘贴正文，不要假装读过。

输出一段简短的分类结果和证据摘要。若需求不清晰，优先按以下顺序用选择题补齐：

1. 谁在使用；
2. 在什么具体时刻或任务中使用；
3. 当前怎么做、哪一步最痛；
4. 用户希望得到什么可观察结果；
5. 产品形态与使用入口。

不要直接问“请详细描述需求”。根据现有材料生成贴合上下文的选项。

### 2. 确认需求定义

整理为一句话：

> 为【目标用户】在【具体场景】提供【产品形态】，解决【痛点】，使其能够【可观察结果】。

同时列出材料事实、待确认项和本期不解决的问题。使用弹框让用户确认或修改。确认前不要设计功能。

### 3. 设计功能和 MVP 范围

列出功能清单，至少包含：

| ID | 一级模块 | 二级功能 | 功能描述 | 来源/依据 | MVP 建议 | 依赖 |
|---|---|---|---|---|---|---|

为每项给出 `本期做 / 以后做 / 不做` 的建议和理由。MVP 建议优先保留能闭合核心用户路径、验证关键假设、满足安全合规和支撑基础运行的功能；装饰性、自定义、高级分析及非核心自动化通常后置。

用弹框让用户决定：

- 哪些本期做、以后做、不做；
- 本期功能的优先级顺序；
- “什么时候做”：MVP、下一阶段或明确里程碑。

不得仅凭行业惯例替用户确定范围。确认后生成开发顺序与功能依赖。

### 4. 推荐并确认技术栈

先确认产品规模、复杂度、期望完成时间、部署环境、预算、数据敏感度以及用户是否需要自行维护。已从材料明确得知的内容不要重复询问。

按功能模块给技术建议，不只给一串框架名。对每个候选说明：

- 它负责实现什么功能；
- 为什么适合当前规模和时限；
- 对技术小白的维护难度；
- 主要限制、成本或迁移风险。

提供 2–3 套可行组合，明确推荐一套，但用弹框让用户选择或修改。技术选型可能随时间变化；涉及具体服务能力、价格、版本或兼容性时，先查官方资料再建议，不凭记忆写死版本。

确认后记录前端、后端/运行时、数据库、认证、文件存储、AI/模型、部署、测试和监控中实际需要的部分。无关部分省略。

### 5. 设计并确认框架原型

只设计支撑核心主流程的低保真框架，不提前做视觉品牌稿。输出：

- 页面/界面清单；
- 页面跳转或任务流程；
- 每个核心界面的 ASCII 框架图；
- 主要控件及点击后的可观察结果；
- 空状态、加载状态、错误状态和成功反馈。

先确认核心主界面，再补充次要界面。展示原型后第二次确认页面结构、信息层级和主流程；确认前不要进入明细设计。

### 6. 编写明细功能设计

为每个已确认功能使用稳定 ID，并写清：触发条件、前置条件、输入、处理规则、输出、状态变化、权限、异常/降级、依赖。只写实现所需深度。

判断产品类型：

- **AI 产品**：补充 Agent 工作流、每一步输入/输出、模型调用边界、提示词设计、变量、结构化输出、工具体系、上下文/记忆、失败重试、人工确认点、安全边界、日志与评测。
- **传统产品**：补充页面与组件行为、业务规则、数据实体、接口/事件、权限、状态机、错误处理和必要的非功能约束。
- **混合产品**：只对 AI 链路使用 AI 设计，对确定性业务链路使用传统设计，不把所有逻辑都交给模型。

AI 的提示词写成可复制模板，明确角色、任务、输入变量、规则、输出格式和失败处理。工具表至少包含工具名、用途、调用时机、输入、输出和失败策略。

### 7. 为每项功能写验收标准

每个功能 ID 必须有对应验收标准。采用“前置条件 → 用户动作/系统事件 → 可观察结果”，必要时使用 Given/When/Then。至少覆盖：

- 主成功路径；
- 关键空状态或边界条件；
- 一项重要失败路径；
- 权限、数据或 AI 输出风险（适用时）。

写具体行为，例如“用户点击‘保存’后，按钮进入加载状态；保存成功后显示成功提示并在列表首行出现新记录”。避免“交互自然”“结果准确”“速度快”等模糊词；性能或准确率必须给可测阈值，阈值不明确时标为待确认。

### 8. 生成最终 Markdown PRD

所有关键闸门确认后，读取并使用 [references/prd-template.md](references/prd-template.md)。删除不适用章节，不为完整而虚构内容。

需要查看完整成品的结构、追溯关系或验收标准写法时，再读取
[references/example-hydrogen-feasibility-prd.md](references/example-hydrogen-feasibility-prd.md)。
该文件仅作为输出深度示例，不是通用模板。不得把其中的氢能用户、功能范围、优先级、技术选型、指标阈值或已确认决策复制到其他项目；新 PRD 必须完全依据当前用户材料和本轮确认结果生成。

最终交付前自检：

- 每个本期功能都有来源、明细、依赖和验收标准；
- 原型中的控件能追溯到功能 ID；
- 技术组件能追溯到它支持的功能；
- 明确区分本期、以后和不做；
- 没有未标注的假设；
- 没有商业宣传和无法执行的空话；
- Markdown 可直接复制给 Claude Code 或 Codex。

若仍有待确认项，输出“待确认草案”和问题清单，不输出伪最终版。
