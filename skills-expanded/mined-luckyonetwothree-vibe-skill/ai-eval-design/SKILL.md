# AI 评测设计

## 核心原则

1. **先定义失败，再定义成功**——不知道哪些情况会坏，指标就没有意义
2. **确定性检查优先**——能用代码判断的不交给评委模型
3. **评委必须校准**——LLM-as-judge 与人类标注至少 10% 抽样对齐
4. **回归必须阻断**——没有阈值的 eval 只是报告，不是门禁
5. **用例覆盖分布**——正常、边界、对抗、历史回归四类都要有
6. **成本与延迟也是质量**——单任务成本和 p95 延迟进入 eval 指标

## 交互模式

🤖→👤 AI 建议人类审批

## 输入

| 输入项 | 类型 | 必填 | 来源 | 说明 |
|--------|------|------|------|------|
| 产品目标 | string | 是 | 用户提供 | AI 功能要完成的任务与用户价值 |
| 用户任务清单 | array | 是 | 上游 PRD / 用户流程 | 需要覆盖的真实任务 |
| 失败模式 | array | ○ | 上游 guardrail / 历史事故 | 已知幻觉、越权、格式错误等 |
| 真实样本 | array | ○ | MCP / 日志 / 反馈库 | 用于构建黄金集与回归集 |
| 模型与工具清单 | object | ○ | 用户提供 | 模型能力、工具边界、成本 |

## 执行步骤

1. [核心] 定义任务成功标准与失败模式——每条标准必须可观察、可判定
2. [核心] 构建 eval 用例集——至少 10 条，覆盖 happy_path / edge_case / adversarial / regression
3. [核心] 选择指标——任务成功率、事实性、格式合法率、工具调用正确率、p95 延迟、单任务成本
4. [核心] 设计评审方式——确定性断言优先；主观项用 rubric + LLM judge；10% 人类校准
5. [核心] 设定阻断阈值与回归策略——低于阈值阻断发布，进入 CI
6. [条件] 接入线上遥测——用户采纳率、转人工率、纠错率回流为回归用例

## 输出

| 输出项 | 格式 | 路径 |
|--------|------|------|
| 评测计划 | JSON | `output/pm-ai-product/ai-eval-design/eval_plan.json` |
| 评测说明 | Markdown | `output/pm-ai-product/ai-eval-design/eval_plan.md` |

Schema：`schemas/pm/ai-eval-plan.schema.min.json`。核心字段：`task_definition`、`eval_cases`、`metrics`、`judge`、`regression_policy`。

## 质量检查

- [ ] eval_cases ≥ 10，且四类用例均有覆盖
- [ ] 每条指标有定义、目标值与计算方式
- [ ] 确定性检查与 judge 检查边界清晰
- [ ] 人类校准比例 ≥ 10%
- [ ] 阻断阈值明确，且已接入 CI 或发布流程
- [ ] 成本与延迟指标已纳入
- [ ] 无真实数据时标注 `synthetic_seed`

## 决策规则

| 条件 | 决策 |
|------|------|
| 输出可结构化校验 | 使用确定性断言，不调用 judge |
| 主观质量占主导 | rubric + judge，并做人类校准 |
| 指标无基线 | 先跑 20 条种子用例建立基线，再定阈值 |
| 用例来自线上事故 | 标记 `regression`，永久保留 |
| 单任务成本超预算 | 优先模型路由 / 缓存 / 缩短上下文 |

## 降级策略

| 缺失项 | 降级方案 | 影响 |
|--------|----------|------|
| 真实样本缺失 | 用合成种子，标注 `synthetic_seed` | 只能验证流程，不能宣称效果 |
| judge 不可用 | 仅保留确定性检查 | 主观质量暂不评估 |
| 无线上遥测 | 用离线回归集 | 无法发现分布漂移 |
| 无成本数据 | 记录 token 估算 | 成本结论置信度低 |
