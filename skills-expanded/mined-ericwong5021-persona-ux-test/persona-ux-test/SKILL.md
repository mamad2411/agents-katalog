# Persona UX Test

用一个独立 Subagent 模拟精准目标用户，通过真实 UI 完成盲测。测试者只知道获准的产品介绍，不接触源代码、设计文档或内部实现。

## 适用边界

- 适用于桌面应用、Web 产品及本地 WebUI。
- 优先使用 Computer Use 和 Browser 操作真实 UI。
- 不用源代码、数据库、日志、接口调用、开发者工具或内部设计说明解释产品。
- 不执行部署、上传、发布、OTA、付款、外部消息发送、批量删除或其他不可逆动作。
- 用户提供的账号、Token 和 API Key 只能用于本次 UI 配置，不得写入 Skill、报告、截图说明或消息。

## 第一步：收敛测试合同

开始前确定：

1. 产品入口或启动方式。
2. 唯一允许给测试者阅读的产品介绍文件或页面。
3. 允许使用的真实环境工具。
4. 可执行与禁止执行的外部动作。
5. 测试凭证的输入位置和保密要求。
6. 核心用户任务与期望产物。

只有缺失信息会改变权限边界、导致不可逆操作或让产品无法进入时才询问用户。其他信息由主 Agent 合理设定。

## 第二步：设计精准用户画像

画像必须具体到足以影响操作决策，至少包含：

| 维度 | 要求 |
|---|---|
| 身份 | 姓名、年龄、所在地、职业或组织角色 |
| 技术水平 | 熟悉的工具、不理解的技术概念 |
| 业务背景 | 当前正在解决的真实问题 |
| 购买动机 | 为什么会尝试这款产品 |
| 核心顾虑 | 隐私、成本、越权、失败、结果质量等 |
| 使用环境 | 设备、语言、可投入时间 |
| 行为特征 | 耐心、探索倾向、遇错后的自然反应 |
| 成功标准 | 用户认为完成任务必须得到什么 |

画像不能为现有界面量身定制，也不能包含产品内部术语或导航答案。

## 第三步：创建隔离 Subagent

使用无历史上下文的 Subagent。只向它提供：

- 精准用户画像；
- 唯一获准的产品介绍；
- 核心用户任务；
- Computer Use 和 Browser 的使用授权；
- 本次测试所需凭证；
- 安全边界和报告格式。

明确禁止它读取：

- `AGENTS.md`、源代码、设计文档、实现计划、Git 历史；
- 测试代码、数据库、内部日志、网络接口响应；
- 主 Agent 的分析、既有缺陷列表和预期导航路径。

不得告诉测试者“正确用法”。找不到入口、看不懂概念或无法恢复本身就是测试证据。

## 第四步：执行真实 UI 盲测

测试者按普通用户直觉依次完成：

1. 找到并进入产品，描述首屏定位理解。
2. 完成首次配置、账号或模型连接。
3. 创建一个与画像业务相关的真实任务。
4. 尝试启动、观察进度、协作、失败、审批与接管。
5. 查看人员状态、工作记录、制品和最终交付。
6. 遇到错误时自然尝试恢复，最多两次。
7. 保留环境可恢复，不删除测试数据。

记录关键操作、页面反馈、等待、迷路、错误和恢复结果。敏感输入框出现完整凭证时，不保留包含凭证的截图。

## 第五步：证据分级

报告中的结论必须标记为以下一种：

- `实际观察`：测试者在 UI 中亲自看到或操作得到。
- `用户推断`：测试者根据界面产生的理解，可能与产品实际机制不同。
- `未能验证`：受入口、权限、错误或时间限制无法确认。

自动化成功、页面存在或模型自述不能替代真实用户理解。无法完成的任务不得写成完成。

## 第六步：输出测评报告

报告使用中文，包含：

1. 用户画像与测试环境。
2. 测试范围、入口和完成度。
3. 关键体验时间线。
4. 体验亮点。
5. 问题清单。
6. 用户不理解的术语。
7. 信任、隐私和安全感。
8. 是否愿意继续使用和付费。
9. Top 5 改进建议。
10. 未能验证的范围。

问题清单至少包含：

| 字段 | 说明 |
|---|---|
| 严重级别 | P0 无法使用；P1 核心任务受阻；P2 明显摩擦；P3 细节问题 |
| 场景 | 问题发生时用户正在做什么 |
| 复现步骤 | 仅写普通用户 UI 操作 |
| 实际结果 | UI 的可观察反馈 |
| 用户影响 | 对完成任务、理解或信任的影响 |
| 证据类型 | 实际观察、用户推断或未能验证 |

不要给工程实现方案，不引用源代码或设计文档，不泄露凭证。

## 第七步：主 Agent 收尾

主 Agent 接收报告后：

- 检查是否遵守了隔离、敏感信息和不可逆动作边界；
- 区分真实 UI 证据与测试者推断；
- 原样保留关键用户语言，不替产品辩护；
- 向用户交付报告和测试完成范围；
- 说明未验证项与真实环境中留下的可恢复测试数据。
