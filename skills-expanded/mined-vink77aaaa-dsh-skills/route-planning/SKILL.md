# Route Planning（路线规划）

## 核心原则

**先定"下车点"，再找班次；永远核实时效性，不轻信旧攻略。**

本 skill 源于一次真实教训：用户按旧攻略坐大巴去东莞华南MALL万达影城，
却发现紧邻影院的"东莞汽车总站"已于 2022-12-23 停止营业，旧班次全部失效，
最后只能改到分流后的南城汽车客运站再换乘。此类坑在客运领域极其普遍，
任何"按经验直接答"的做法都不可靠——**车站会停运、线路会调整、新地铁会开通**，
每次都必须现场核实。

## 使用流程

### 第1步：收集需求（缺什么问什么）

- 出发地（精确到路口/小区）
- 目的地（名称 + 城市/区，必要时先查精确地址）
- 时间约束：必须几点前到？出发时间是否灵活？
- 交通偏好：大巴 / 高铁 / 城际 / 自驾 / 公交 / 混合？未指定时按下方"交通方式比选"给出多方案对比
- 下车点要求：离目的地越近越好？还是价格优先、班次优先、时间最短？

### 第2步：定位目的地

- 查目的地的精确地址、所属区/街道（如"万达影城华南MALL店 = 东莞市万江区万道路华南MALL D区三楼"）
- 找出离它最近的客运站 / 高铁站 / 城际站 / 地铁站 / 公交站，关键词：
  `"<目的地> 地址"`、`"<目的地> 地铁站"`、`"<目的地> 旁边 汽车站"`、`"<目的地> 最近 高铁站"`
- 记录目的地所在城市的地铁/城际线情况（如"东莞地铁1号线曲海站紧邻华南MALL"）——这决定接驳方案

### 第2.5步：交通方式比选（高铁/城际 vs 大巴 vs 混合）——新场景必做

> 跨城出行往往同时存在大巴、高铁/城际、混合接驳三条路径，**不要只按用户口头偏好给单一方案**。
> 用户问"怎么去""哪趟合适""划算不划算"时，应主动给出多方式对比。

- **对比维度**：总耗时（含出发地→车站→目的地全程）、总费用、班次密度、下车点离目的地距离、确定性（高铁准点 vs 大巴受路况影响）、购票便利性
- **高铁/城际方案**：查目的地城市的高铁站/城际站（如东莞的东莞站、东莞南站、东莞西站、常平站），确认到目的地接驳（地铁/公交/打车）。跨城常用线：广深港高铁、广珠城际、莞惠城际、穗深城际、广佛肇城际等
- **混合方案**：常为"城际/高铁到枢纽站 + 地铁/公交到目的地"（如"穗深城际→东莞西站→地铁1号线→曲海站"），耗时往往比大巴短且不受高速拥堵影响
- **判断优先级**：用户明确要"最快"或"时间紧"→优先高铁/城际；"最便宜"→大巴；"下车点近"→比较各方案下车点接驳距离；时间不紧且预算敏感→大巴；拿不准→给出对比表让用户选
- **注意**：高铁/城际的班次、线路也可能调整（停运、改线），同样需要核实（搜"<线路> 停运/调整"）
- 搜索示例：`"<出发城市> 到 <目的城市> 高铁 时刻"`、`"<出发城市> 到 <目的城市> 大巴 时刻"`、`"<目的城市> 地铁 开通 站点"`

### 第3步：核实车站运营状态（最高优先级，先于查班次！）

> 全国大量客运站在近年陆续停运（东莞总站 2022、厚街 2024、石龙 2025…），
> 停运后班线会分流到其他站。**先搜"X站 停运"，再查班次，否则可能查到已作废的旧班次。**

- 搜索：`"<站名> 停运"`、`"<站名> 停止营业"`、`"<城市> 客运站 停运 2024 2025"`、`"<站名> 终止经营"`
- 本地宝（bendibao.com）、交通运输局公告最可靠
- 若车站已停运：找官方"班线分流方案"，确定广州/出发地班线现在落到哪个站
- 常见分流去向：南城站 / 汽车东站 / 客运北站，注意它们离目的地的远近差异很大

### 第4步：查班次（多源交叉验证，禁止单源采信）

- 时刻表网站（可能过时数年）：zuzuche 坐车网、aizhan 爱站工具、cncn、qichezhan
- 实时购票平台（更可靠，优先）：Bus365（bus365.com / wxcity.bus365.com）、携程/去哪儿汽车票、车站官方公众号
- 交叉验证字段：发车时间、票价、车程、途经站、车型
- 注意：旧时刻表网站数据可能停留在几年前（如票价显示 ¥30 实际 ¥48），**以实时购票平台为准**
- 数据源被反爬/维护/失效时，按 `references/data-sources.md` 的备选方案切换，不要死磕一个源

### 第5步：确定下车点与接驳方案

- 到站后如何到目的地：打车（距离/费用/耗时）、地铁（最近站）、公交（线路号）、步行
- 搜索：`"<下车站> 到 <目的地> 打车/地铁/公交 多久"`、`"<下车站> 到 <目的地> 公交 几路"`
- **留意新开通的交通**：新地铁/城际线可能彻底改变最优解（如东莞地铁1号线曲海站紧邻华南MALL，出站即达）
- **若走了高铁/城际方案**：高铁站/城际站到目的地的接驳同样要查（地铁换乘站、打车距离、公交线路）
- 接驳成本要算进总时间线，打车费用也一并估算

### 第6步：时间倒推，给出方案

```
最晚发车时间 = 目标到达时间 - 车程 - 接驳时间 - 冗余(30~60分钟)
```

- 给出：推荐班次（含发车时间、票价、车程）+ 最晚班次 + 预计到达时间
- **若做了多方式比选**：用对比表给出各方案（大巴/高铁/混合）的耗时、费用、下车点接驳，标注推荐与原因
- 提醒：班次票价以车站/铁路官方当天实际为准，建议提前线上购票（Bus365/携程/12306/车站公众号）
- 若用户出发时间灵活，给出"推荐出发时间段"而非单一班次

### 第7步：汇报

- 推荐方案（完整时间线：家→车站→班次→下车→接驳→到达）+ 备选方案
- 标注数据来源与核实日期，说明哪些信息可能变动（如"以车站当天实际为准"）
- 若过程中发现过时信息，按下方"自更新协议"处理，并告知用户已更新

## 自更新协议（Self-Update Protocol）⚠️

**本 skill 是活文档。使用中发现任何失效/过时/不适用信息，必须当场记录并更新，避免下次重蹈覆辙。**

### 触发条件（满足任一即触发）

1. **事实过时**：车站停运 / 班次取消 / 票价变更 / 新线路开通，与 `references/verified-facts.md` 中记录冲突
2. **数据源失效**：某网站打不开、被拦截、返回 404/维护中、数据明显过时
3. **流程失败**：本 skill 的某一步在当前环境无法执行、结果不可用、或方法本身有缺陷
4. **用户反馈**：用户指出方案不可行、信息错误、或提供了更新的正确信息

### 更新步骤

1. **记录**：在 `references/update-log.md` 追加一条（日期、触发类型、发现、处理结果）
2. **修正事实**：更新 `references/verified-facts.md` 对应条目（每条必须含核实日期 + 来源链接）
3. **修正数据源**：更新 `references/data-sources.md`（标记失效源及原因、新增可用源及验证方式）
4. **修正流程**：若问题出在 SKILL.md 的方法/步骤本身，直接修改 SKILL.md 对应章节
5. **告知用户**：最终回复中说明"本次发现 X 已过时/失效，已更新本 skill 的 Y 部分"，附上新信息

### 更新原则

- 每条事实必须带核实日期和来源链接，无来源不写入
- 宁可多记录一条，也不要让下次重踩同一个坑
- 更新要具体（改字段 / 改 URL / 改步骤），不要空泛"更新了信息"
- 若同一事实多次变化，保留历史记录在 update-log，verified-facts 只留最新值

## 常见失败模式（防坑清单）

| 现象 | 原因 | 对策 |
|------|------|------|
| 旧攻略说"下车就是电影院" | 车站已停运 | 先核实运营状态（第3步） |
| 时刻表显示票价 ¥30，实际 ¥48 | 数据过时数年 | 以实时购票平台为准，交叉验证 |
| 找不到离目的地近的车站 | 新地铁/城际未纳入考虑 | 查最新开通的地铁/城际线（第2.5步） |
| 只给大巴方案，用户其实时间紧 | 未做多方式比选 | 主动对比高铁/城际/混合（第2.5步） |
| 高铁站离目的地很远没算接驳 | 只算了高铁车程 | 高铁站→目的地接驳同样计入（第5步） |
| 某查询网站打不开/被拦截 | 反爬/维护/失效 | 切换 `references/data-sources.md` 备选源 |
| 搜索结果全是酒店/广告 | 关键词太泛 | 加"停运""时刻表""班次""分流"等限定词 |
| 查到多个票价互相矛盾 | 不同源时效不同 | 以 Bus365/携程/12306 等实时平台为准并标注 |
