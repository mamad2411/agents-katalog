# Cordova WebView Risks

## Scope And Authorization

- **In scope:** Cordova/PhoneGap/Ionic-Cordova apps, plugins, and build configs you own or have written authorization to assess (including enterprise internal builds and CTF/lab APKs/IPAs supplied by the owner).
- **Out of scope:** reverse-engineering or attacking third-party App Store / Play Store apps without authorization; mass distribution of modified APKs.
- Prefer non-production builds with debug symbols and clear package IDs.
- Redact API keys, push tokens, cert pins, and user data from reports.
- Pair remediations with `code-quality-standards` and mobile SSL skills when TLS is in scope.

## When To Use

- Reviewing `config.xml` / `config.xml` preferences and platform `AndroidManifest.xml` / iOS Info.plist generated by Cordova.
- Assessing `file://` origin, `CDVWKWebView`, Android System WebView, and scheme handlers.
- Auditing plugins that expose native capabilities to JavaScript (`cordova.exec`, custom bridges).
- Checking allow-navigation / allow-intent / CSP meta for hybrid shells.
- Dependency/plugin age and known CVEs in `package.json` / `plugin.xml`.

## Do Not Use As Primary

| Need | Skill instead |
| --- | --- |
| Native Android/iOS deep RE without Cordova | platform RE skills / binary-re paths |
| SSL pinning bypass on owned apps | `mobile-ssl-pinning-bypass` |
| General XSS in pure web (no hybrid bridge) | `xss-cross-site-scripting` |
| Store listing / supply-chain SBOM only | SBOM / dependency skills |
| Implementation quality baseline | `code-quality-standards` |

## Domain focus

| Area | What to inspect | Why it matters |
| --- | --- | --- |
| Navigation allowlist | `<allow-navigation>`, `<access origin=…>` | Open navigation → phishing / token theft in WebView |
| Intents / URL schemes | `<allow-intent>`, Android intent filters | Drive-by intent to dialer, browser, other apps |
| Content access | `AndroidInsecureFileMode`, file access prefs | Local file read, same-origin surprises |
| Bridge | Plugins calling into Camera, Filesystem, Contacts | XSS in WebView becomes native capability abuse |
| InAppBrowser | `_blank` vs system browser | Cookie/session isolation differences |
| Updates | Cordova CLI, platforms, plugins | Abandoned plugins with RCE/path bugs |

## Workflow

### 1. Confirm scope and success criteria

1. Record app package/bundle ID, Cordova CLI version, platforms (`cordova platform ls`), and authorization letter/ticket.
2. Success criteria examples: deny-by-default navigation; no `*`-wide access; bridge methods authorize per action; plugins patched; CSP present; secrets not in `www/`.
3. Obtain a debug build or source; note whether Live Reload / remote debug is enabled only for non-prod.

### 2. Inventory project state

```bash
# From project root (owned app)
cordova --version
cordova platform ls
cordova plugin ls
cat config.xml
# Dependencies
cat package.json
# Android generated (after prepare)
# platforms/android/app/src/main/AndroidManifest.xml
# iOS: platforms/ios/*/config.xml and entitlements
```

Collect:

1. `www/` or framework build output (Ionic `www` / `dist`).
2. Custom plugins under `plugins/` and any private git plugins.
3. Deep links / universal links configuration.
4. Auth storage: `localStorage`, `IndexedDB`, Keychain/Keystore plugins, cookies.

### 3. Baseline threat scenarios

| Scenario | Attack sketch | Evidence to gather |
| --- | --- | --- |
| Open navigation | WebView loads attacker HTTPS page | `<allow-navigation href="*">` or broad HTTPS |
| Bridge from XSS | Injected script calls `cordova.exec` / plugin APIs | Plugin JS API without origin check |
| File URL abuse | `file:///android_asset` + content access | Preferences allowing universal file access |
| Intent abuse | `allow-intent` to `sms:`, `tel:`, custom schemes | config.xml intents + HTML links |
| Outdated WebView | Old System WebView / WKWebView bugs | minSdk, WebView package version on test device |
| Insecure transport | cleartext / weak TLS | `usesCleartextTraffic`, ATS exceptions |

### 4. Review config.xml and platform prefs

#### Navigation and access (examples of patterns)

```xml
<!-- Prefer tight allow-navigation: only your app origins / CDN -->
<allow-navigation href="https://app.example.com/*" />
<!-- Avoid -->
<!-- <allow-navigation href="*" /> -->
<!-- <access origin="*" /> -->

<!-- Intents: only what product needs -->
<allow-intent href="tel:*" />
<!-- Avoid unrestricted geo/market/intent if unused -->
```

Android-oriented preferences to hunt:

- `AndroidInsecureFileMode`, `AllowUniversalAccessFromFileURLs`, `AllowFileAccessFromFileURLs`
- `scheme` / `hostname` for `https://localhost` style Ionic shells (understand origin)
- Mixed content mode preferences

iOS:

- App Transport Security exceptions in Info.plist
- WKWebView vs UIWebView (UIWebView must not ship)
- `cordova-plugin-ionic-webview` / `CDVWKWebViewEngine` settings

### 5. Bridge and plugin review

1. List every `cordova.exec` / plugin method exposed to JS; mark those that read files, run shell, load URLs, or export keys.
2. For each sensitive plugin: require user gesture + native confirmation where appropriate; never trust WebView DOM alone for authz.
3. Search for `eval`, `innerHTML` with untrusted data in `www/` and plugin JS.
4. InAppBrowser: prefer system browser for untrusted OAuth if cookie isolation is required; document `_blank` vs `_system`.

```bash
rg -n 'cordova\.exec|cordova\.plugins' www plugins --glob '!**/node_modules/**'
rg -n 'allow-navigation|allow-intent|access origin' config.xml plugins
rg -n 'innerHTML|document\.write|eval\(' www --glob '!**/vendor/**'
```

### 6. Verify with evidence (authorized lab build)

```bash
# Android debug (owned package)
adb devices
adb shell pm list packages | rg 'your.package'
# Optional: chrome://inspect for WebView remote debug on debug builds only

# Static: dependency / SCA
npm audit --prefix . || true
# Review plugin CVEs manually for abandoned plugins
```

Evidence pack:

1. Redacted `config.xml` allowlists before/after.
2. Screenshot or log of blocked navigation to out-of-policy URL (if you implement runtime checks).
3. Plugin inventory with versions and disposition (keep/replace/remove).
4. Proof that production builds disable remote WebView debugging.

### 7. Remediate and hand off

1. Tighten allowlists; remove unused plugins; upgrade Cordova platforms.
2. Move secrets to native secure storage; never ship long-lived tokens in `www/js`.
3. Add CSP meta or HTTP CSP for remote-loaded content; pair with XSS controls.
4. Document residual risks (WebView OEM variance, third-party payment SDKs).
5. Apply `code-quality-standards` for any native/JS fixes.

## Good / Bad

| Topic | Good | Bad |
| --- | --- | --- |
| allow-navigation | Explicit app + API hosts | `*` or all HTTPS |
| Bridge | Native authz + minimal plugin surface | Any page can call Filesystem/Contacts |
| Origin | Known Ionic scheme/host model | file:// with universal access |
| Plugins | Pinned maintained plugins | Random abandoned Camera forks |
| Debug | Debug flags off in release | `setWebContentsDebuggingEnabled(true)` in prod |
| OAuth | System browser / ASWebAuthenticationSession patterns | Password form in over-privileged WebView |

## Output Checklist

- [ ] Authorization and package IDs recorded
- [ ] Cordova/platform/plugin versions inventoried
- [ ] `config.xml` navigation/intent/access reviewed
- [ ] File/content access prefs reviewed per platform
- [ ] Bridge/plugin sensitive APIs reviewed

- [ ] Cleartext/ATS/WebView debug settings checked for release
- [ ] SCA/CVE notes for plugins
- [ ] Hardening changes or findings documented with evidence
- [ ] Residual risk + retest date set

## Rules

- Authorized apps only; do not redistribute patched binaries of third-party apps.
- Treat WebView XSS as potentially equivalent to partial native code execution via plugins.
- Prefer removing plugins over “trusting” wide allowlists.
- Evidence over assumptions about OEM WebView behavior — test on minimum supported OS versions.
- Keep focus on hybrid Cordova/PhoneGap WebView risk; route pure web CORS/CSP and pure native RE to neighbor skills.
