# Vibe Coding Governance Gap & SHIELD Framework

## The Problem

Vibe coding — building functional software by directing AI models in natural language without reading or understanding the generated code — has spread from fringe technique to broad enterprise adoption within ~16 months of Andrej Karpathy's coinage (Feb 2025). The practice has created a **structurally ungoverned attack surface** expanding at enterprise scale.

**The core gap:** None of the major AI security frameworks (NIST AI RMF, OWASP LLM Top 10, CSA MAESTRO, CSA AICM) provide dedicated, accessible guidance for **citizen developers** who build and deploy AI-powered applications without professional security oversight.

## The Framework Gap in Detail

### Why Existing Frameworks Don't Cover Vibe Coding

| Framework | Audience | Gap |
|---|---|---|
| **NIST AI RMF 1.0 / AI 600-1** | Organizational entities with documented roles | A business analyst who built a data tool on Copilot Studio has no role defined and no pathway to apply controls |
| **OWASP LLM Top 10 (2025)** | Developers, AppSec teams, CISOs, data scientists | Citizen developers are not in scope. OWASP's separate Low-Code/No-Code Top 10 predates vibe coding and hasn't been updated. |
| **CSA MAESTRO** | Security practitioners doing threat modeling | Seven-layer model assumes a security-aware practitioner at design stage. Citizen developers don't do threat modeling. |
| **CSA AICM (AI Controls Matrix)** | 5 actor roles, 243 controls across 18 domains | Citizen developer falls ambiguously between "Application Provider" and "AI Customer" — both carry obligations they can't fulfill |

### The Provenance Problem
Vibe-coded applications often produce **no version-controlled source code, no dependency manifest, no SBOM, no commit history**. When a vulnerability is found, there is no code to patch — the remediation path is to re-prompt the AI, generating a new application with equally uncertain security properties.

### Shadow Operations
Shadow IT has evolved into **shadow operations**: employees building autonomous, data-processing applications on approved enterprise platforms (Power Platform, ServiceNow, Salesforce) without IT or security involvement. The platform is sanctioned; the specific application is not. Standard shadow IT playbooks (discover, block, redirect) don't work because the tools are already approved.

### The Compliance Blindspot
GDPR, HIPAA, SOC 2, PCI DSS impose obligations based on data categories, not how applications were built. A vibe-coded app handling PHI carries the same HIPAA exposure as a professionally developed one — but without the security review, penetration testing, and audit logging. EU AI Act high-risk enforcement begins August 2, 2026, adding another layer citizen-built apps may inadvertently trigger.

## The SHIELD Framework (Unit 42, Palo Alto Networks)

A first-principles security control framework for vibe coding:

### S — Separation of Duties
Vibe coding platforms may over-aggregate privileges. Ensure incompatible duties (e.g., dev + prod access) are not granted to AI agents. **Restrict agents to development and test environments only.**

### H — Human in the Loop
For any code impacting critical functions: mandatory secure code review by a human + pull request approval prior to merge. **Vital when non-developers are involved.**

### I — Input/Output Validation
- **Input:** Sanitize prompts by separating trusted instructions from untrusted data (prompt partitioning, encoding, role-based separation)
- **Output:** Require AI to perform validation logic checks + Static Application Security Testing (SAST) after development and before merging

### E — Enforce Security-Focused Helper Models
Develop external/independent helper models (specialized security agents) to perform: SAST testing, secrets scanning, security control verification, identification of hard-coded secrets — **prior to deployment**

### L — Least Agency
Implement principle of least agency for all vibe coding platforms and AI agents. Only grant minimum permissions and capabilities. **Restrict access to sensitive files. Guardrail destructive commands.**

### D — Defensive Technical Controls
Employ defensive controls around supply chain and execution management:
- Software Composition Analysis (SCA) on components before consumption
- Disable auto-execution to allow for human-in-the-loop and helper agent involvement
- Secrets scanning at deploy time
- Mandatory authentication configuration before processing external data

## CSA Governance Recommendations

### Immediate Actions
1. **Establish visibility before control** — audit AI features within sanctioned platforms (Power Platform, Salesforce, ServiceNow, Google Workspace) for applications handling sensitive data. Most platforms offer governance dashboards that are underutilized.
2. **DLP at API gateway layer** — detect outbound connections from citizen-built apps to external AI services (data exfiltration risk).
3. **Lightweight registration process** — frictionless, non-punitive declaration of new applications. Goal is awareness, not gatekeeping. Monitor for unregistered apps.

### Short-Term (30–90 Days)
1. **Tiered governance model:**
   - Tier 1: Internal tools, non-sensitive data → minimal review
   - Tier 2: PII or regulated data → standard security review
   - Tier 3: AI API calls or agentic functionality → enhanced review
2. **Extend SCA and secrets-scanning** to cover no-code/low-code platform outputs where export is supported.
3. **Security awareness training** explicitly addressing vibe coding risks — concrete, scenario-based, tied to specific platforms employees use.

### Strategic
1. **Citizen-developer-accessible governance track** within existing frameworks (not a new framework). CSA AICM actor taxonomy augmented with "Citizen Developer / Non-Technical Deployer" role carrying reduced but specific control obligations.
2. **Platform vendor responsibility** — mandate baseline controls (mandatory security policy templates, automatic secrets scanning at deploy, required auth config before processing external data) rather than treating them as optional features.
3. **Regulatory implementation guidance** that acknowledges citizen developer as a distinct deployment pathway.

## The Citizen Developer Persona

The citizen developer is a **distinct actor class** that existing frameworks don't address:
- No formal engineering background
- Cannot perform code review (lacks the literacy)
- In the vibe coding paradigm, does not intend to read the code
- Builds on sanctioned platforms (not shadow IT in the traditional sense)
- May incorporate AI API calls and agentic functionality without understanding the attack surface
- Creates applications that may process regulated data without knowing compliance obligations

**Design implication for A-Tech:** A-Coder must be secure-by-default for users who will not and cannot review the code. The security must be in the platform, not in the user's expertise. This is the "opportunity" dimension of the COM-B model from the boosting skill — the environment must enable security even when competence is low.
