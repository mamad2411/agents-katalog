# Evolving Enactions of Coding Expertise with AI Assistants

## Core Finding

When AI coding assistants are available, software engineers continue to rely on familiar evaluation criteria for coding expertise but require additional evidence to validate those criteria. AI assistants introduce new ways to demonstrate expertise (extended enactions) while simultaneously reducing the visibility of established workflows that previously served as evidence of expertise (diminished enactions). The importance of these evolving enactions varies with whether evaluators prioritize code implementation or code planning.

Based on Jang, Sakashita, Niinuma, & Gupta (Fujitsu Research of America, CHI 2026). First study to introduce "enaction of expertise" as a lens for understanding how AI reshapes professional knowledge work. 16 professional software engineers in simulated live coding interviews with AI tools allowed.

## The Concept: Enaction of Expertise

**Enaction of expertise** = how expertise is put into practice through demonstration and evaluation, not just what expertise individuals possess.

Traditional view: expertise as informational property residing in individuals
This study's view: expertise as communal and interactional property — applied, demonstrated, recognized, negotiated, and evaluated by others

## Key Findings

### 1. Same Criteria, Additional Evidence (Finding 4.1)

Evaluators did not change their evaluation criteria when AI tools were available. They continued to assess:
- Task understanding
- Approach development
- Error handling
- Code explanation
- Incremental code development
- Code cleanliness
- Code effectiveness
- Requirements satisfaction

But they required **additional evidence** because AI-generated output codes were no longer sufficient on their own to demonstrate a candidate's ability:
- "AI is working pretty much fine, then I will have to evaluate the candidate on like getting in the code line by line and understand what is happening" (Evaluator, S7)
- Output codes "should be considered mostly apart from considering the result of the test" (Evaluator, S4)
- Comments generated by AI "could not count as the candidate's own expertise" (Evaluator, S4)
- Follow-up questioning became critical: "always check on the problem apart from what candidate performs in code"

### 2. Extended Enactions — New Ways to Demonstrate Expertise (Finding 4.2.1)

AI assistants introduced three new enactions of coding expertise:

**A. Choice of AI tools**: Selecting among different AI tools emerged as an enaction of expertise
- Tool selection signaled awareness of task requirements
- ChatGPT effective for "a lot of implementation at once"; integrated assistants for "write a lot of the code by yourself"
- Perplexity for authoritative sources: "Using Perplexity instead of conventional search was a smart move" (Evaluator, S5)

**B. Prompting practices**: Interaction through prompting became an enaction tied to task understanding
- "What level of detail are they using in the prompt versus letting a generative AI just do it" (Evaluator, S1)
- Even when AI produced correct code, evaluators scrutinized prompts
- Broad prompting = lack of task comprehension: "does she have understanding of the problem? I would say no. That's why her prompting was broad" (Evaluator, S5)

**C. Use of AI-generated outputs**: Discernment about whether and when to use AI outputs
- Evaluators used AI outputs as comparison: "she has to pick one at least. That understanding would be helpful" (Evaluator, S10)
- Candidates faced new challenge: AI gives "more than what I needed, and we are forced to explain it would make us look a little less experienced" (Candidate, S8)
- Skipping AI output lines signaled lack of understanding (Evaluator, S10)

### 3. Diminished Enactions — Lost Visibility (Finding 4.2.2)

AI assistants reduced visibility of established expertise-demonstrating practices:

**A. Task understanding and approach development**: Most candidates did not start by using AI to understand the task. One candidate copied all instructions to AI immediately — interpreted as lack of expertise.

**B. Incremental code development**: AI producing whole codes prevents showing iterative development. One evaluator proactively divided tasks into steps: "If I give everything at once, it becomes obvious" (Evaluator, S2).

**C. Error handling**: AI identifying and solving errors simultaneously prevents showing how candidates handle errors. "The candidate managed to not identify the main issues in case of errors and corrected them using AI" (Evaluator, S4).

### 4. Implementation vs. Planning Emphasis (Finding 4.3)

The importance of evolving enactions varied with evaluators' phase emphasis:

**Those valuing code planning (Finding 4.3.1)**:
- Enactions mattered less — AI can handle implementation
- "whether the code is actually 100% works is not as important as your understanding and the structure" (Evaluator, S1)
- "with ChatGPTs help, the code won't be a very big deal" (Evaluator, S8)
- Code planning became more important: "connecting the big picture" (Evaluator, S5)
- Preferred pseudo-code in interviews as clearer demonstration of planning

**Those valuing code implementation (Finding 4.3.2)**:
- Enactions mattered more — AI rarely produces optimal code in extendability, efficiency, readability
- "not all the solutions that AI gives are efficient and will work for all the test cases" (Evaluator, S9)
- "the final code is not extendable" (Evaluator, S12)
- Paid careful attention to new enactions (tool choice, prompting, output use) as evidence of expertise

### 5. Productivity Expectations vs. Expertise (Finding 4.4)

AI availability raised productivity expectations without clear connection to expertise:
- Evaluators expected candidates to use AI to increase productivity
- Candidates invoked productivity themselves: "my AI tools usage demonstrated my expertise to organize and speed-up the development process" (Candidate, S4)
- Tensions: some viewed AI reliance as productive; others saw it as masking lack of knowledge
- Misalignments when candidates pursued productivity via quick AI use while evaluators prioritized evidence of comprehension

## Practical Application Framework

### For Interview Design
1. **Don't change criteria, change evidence**: Keep familiar criteria but design tasks that require demonstration of understanding beyond output code
2. **Allow AI tools**: All participants agreed AI should be allowed to enhance external validity — "suiting up with the actual things that have been going on" (Evaluator, S3)
3. **Step-by-step task presentation**: Divide tasks into sequential steps to prevent AI from generating entire solutions, making reasoning visible
4. **Follow-up questioning is critical**: "always check on the problem apart from what candidate performs in code" (Evaluator, S4)
5. **Observe tool choice and prompting**: These are now enactions of expertise

### For AI Coding Tool Design
1. **Support extended enactions**: Tools should make expertise visible through:
   - Prompt reasoning logs (task → prompt)
   - Assistance processing visualization (prompt → AI output)
   - Assistance integration tracking (AI output → task)
2. **Address diminished enactions**: Provide visibility into:
   - How AI decomposed the task
   - Incremental code generation steps
   - Error identification vs. correction
3. **Evaluator support tools**: Provide evaluators with summaries/visualizations of candidate-AI interactions to reduce asymmetry

### For Organizational Practice
1. **Training for evolving enactions**: Candidates need to learn to translate existing expertise criteria into AI interactions
2. **Shared understanding**: Create spaces for HR and engineers to dialogue about how expertise is changing
3. **AI proficiency norms**: Establish norms around AI use to reduce "AI shaming" and social stigma
4. **Productivity-expertise alignment**: Clarify how AI-assisted productivity relates to expertise evaluation
