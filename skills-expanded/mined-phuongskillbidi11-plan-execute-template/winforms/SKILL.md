# Skill: winforms

## Purpose

The parts of WinForms that don't follow from general C#/.NET knowledge — the UI-thread
contract, the form/control lifecycle, and the designer-generated file's own rules. Requires
`software/csharp-dotnet` (loaded alongside it) for the platform-level facts underneath.

## Method

1. **Only the UI thread may touch a control's properties or methods** — reading or writing
   `Text`, `Enabled`, adding to a list, etc. from a background thread (a timer callback, a
   `Task.Run` continuation, a raw `Thread`) throws `InvalidOperationException:
   "Cross-thread operation not valid"` in a debug build, and can silently corrupt UI state in a
   release build where that check is sometimes bypassed. Marshal back with
   `control.Invoke(...)` (blocking) or `control.BeginInvoke(...)` (async) — check
   `control.InvokeRequired` first if the same method may run on either thread.
2. **`.Designer.cs` is regenerated by the Forms Designer — never hand-edit it.** Any manual
   change to layout, control properties, or event wiring inside a `.Designer.cs` file will be
   silently overwritten the next time the form is opened in the Designer and saved. Make the
   equivalent change in the partial class's own `.cs` file, or through the Designer UI itself.
3. **Form/control lifecycle order matters for initialization bugs.** The constructor runs
   `InitializeComponent()` (which wires up everything from the `.Designer.cs`) before any of
   the constructor's own code after that call — code that depends on a control's final state
   (e.g. reading a `ComboBox`'s selected item) must run after `InitializeComponent()`, and
   anything that depends on the form actually being shown belongs in the `Load` event, not the
   constructor, since some window-handle-dependent APIs aren't valid until the handle exists.
4. **`Dispose` order isn't automatic for manually-added controls.** Controls added via the
   Designer are disposed automatically as children of their parent container; a control created
   and added purely in code follows the same rule *only* if it was actually added to a
   container's `Controls` collection — an orphaned manually-created control (created but never
   added, or removed without disposing) leaks a native window handle.
5. **A modal dialog (`ShowDialog()`) blocks the calling thread's message loop for that form,
   but background threads and timers on other forms keep running** — don't assume showing a
   dialog pauses the whole application; only that thread's message pump for that call is
   blocked.

## Anti-patterns

- Updating a control directly from a `Task`/`Thread`/timer callback without `Invoke`/
  `BeginInvoke`, and only noticing when it works "most of the time" in release builds.
- Hand-editing a `.Designer.cs` file and having the change silently disappear after the next
  Designer save.
- Putting handle-dependent initialization logic in the constructor instead of the `Load` event.
