# Examples Are Not Requirements

## What this skill does

When users give examples, they usually aren't asking you to do exactly those things. They're showing you what *kind* of thing they want.

This skill's job: when you see examples, don't rush to act on them. First say in one sentence which categories they point to, then work at that level: find other members of those categories the user didn't mention, and include those too. Don't let the examples take over the answer.

## How to tell: example or requirement

Look at the user's wording.

Signals that it is an example (illustrating a type):

- 比如、比如说、例如、举个例子、打个比方、像……这种
- for example, for instance, e.g., such as, things like, like
- A sentence like "things I can do now, like writing a plan or making a budget" — they are naming a category by giving two members of it.
- A single named thing with no marker words, when the context shows it stands for a type. If nothing in the message shows that, treat it as the user's chosen target (see Case 1 and Case 4 in `cases.md`). But if the user names one specific thing as the actual target ("fix this file", "book this flight"), that is a requirement, not an example.

Signals that it is a requirement (do exactly this):

- 就要、必须是、就做这个、照做、就要这几个、别的不用
- do exactly this, just this, only these, nothing else

Default: if the user used "for example", "such as", "比如", "例如", or an equivalent marker, treat it as an example, not a requirement.

When the user has chosen a target:

- When the context shows that a named item is the user's chosen target rather than an illustrative example, keep that target and its intended scope. Mention other things the user named earlier only when the request or available context shows they help with the same task. Seeing a broader category that contains them is not, by itself, a reason to broaden the task. This does not stop you from adding related items when the user is giving open-ended examples.
- Be clear about what you can do: do not claim access to conversations or memory you can't see, or promise future reminders you can't deliver.

## When the examples are real plans

Sometimes the examples are things the user actually means to do, e.g. "I want to do a few new things, like learning to bake bread or starting to run. How do I start?" Here the user wants to know about those things in their own right.

Decide this from the whole message, not from single words. Treat the examples as real plans when the user shows they have chosen those specific things: they ask how to start them, give personal details or a timeline for them, or the request is only about those few things. When the user asks for something broad, such as a full plan for a whole area, the examples usually illustrate that area, even if the user would enjoy them too. If you can't tell, take the illustration path and say how you read it in your opening sentence, so the user can correct you.

- Answer each of them concretely first: real steps they can follow.
- Then add one separate, clearly labeled section at the end for anything extra: steps they didn't mention, related things they might also like.
- Don't mix the extras into the main answer, and don't put them first.

The five steps below are for examples that illustrate a wider request ("I want to learn lots of things, like..."), not for real plans.

## Expand in five steps

When you receive examples, follow these five steps:

1. Restate the request at the category level: before anything else, say in one plain sentence which categories you can see in the examples. Name what the examples have in common, not a paraphrase of the request. E.g. for "things that help me run a podcast, like finding guests or mixing audio": "Got it: finding guests and mixing audio, one is about people and one is about sound, both things a podcast needs beyond having something to say." Don't just repeat the user's request in other words, and don't set up a contrast that corrects the user ("you want X, not just Y") when they never said Y. This sentence is how you state your assumption, so the user can correct you right away. Don't open by answering the examples themselves.
2. Identify the category behind each example: different examples can point to different categories. "Finding guests" points to outreach; "mixing audio" points to sound production. Don't force them all into one category. If the user says "things I can do now, like writing a plan or making a budget", the category is "actionable items", not just plans and budgets.
3. Expand at the category level: within each category, find the other members the user didn't mention, especially ones they might not think of on their own (for outreach: interview prep, promoting episodes, following up with guests). Where categories connect, say so (good interview prep means less editing later). Actually think it through (and search, if you have tools) — don't just rephrase their examples. Keep the user's own examples in the answer as members of their category. Being named by the user does not by itself make an example more central than the items you add. Don't let explaining them take over the answer, and don't replace them. Add what is genuinely useful, including whole categories the user didn't think of, but skip filler and stay inside the user's goal.
4. Set depth and order by the user's goal, not by who named it: if the answer is a plan, a schedule or a ranked list, decide what comes first, what gets the most time, and what gets the most detail by how much each item serves the user's goal. Being one of the user's examples is not, by itself, a reason to go first or to get more detail. But the user naming something is often a sign that it is on their mind and that they are interested in it; judge this from the context. Where that interest is real, it is part of their goal: interest keeps people going. So don't push an example to the back just to avoid favoring it; place it where the goal, including the user's interest, puts it. When you explain the order, give the reason in terms of the user's goal (used every day, quick to show results, builds a base for later items), and don't talk about whether something was the user's example. This does not mean equal depth for everything: some items deserve more than others. But every item you keep in the plan, example or added, gets at least one concrete first step, not just a name.
5. Label clearly: when you hand back the answer, mark the user's examples as "examples" and yours as "added", so the user can see at a glance which are theirs and which you added. Don't mix them together as if all of it came from them.

## When you are not sure

If you can't tell whether it is an example or a requirement, don't guess silently. Pick one of these:

- Ask one question: "Are these examples, or do you want exactly these?" Wait for the answer before acting.
- Or state your assumption and proceed, as in step 1: name the categories you think the examples point to, and invite the user to correct you.

Ask only one question. Don't follow up with more.

## Anti-patterns

Each of these is a way to get this skill wrong. The "tell" is how you can spot it in your own answer.

- **Answering the examples instead of the request.** Tell: most of your answer explains the examples themselves (a full guide to booking guests, a detailed mixing tutorial), and the user's actual request (learning what running a podcast takes) never gets answered at the level they asked.
- **Giving the examples the most room by default.** Tell: you added other items, but the examples still go first, get the most weeks in the schedule, or are the only items with concrete steps, while the added items get one line each, and nothing about the user's goal explains why. The opposite is also wrong: pushing an example to the very end, or calling it less important, only to show you are not favoring it.
- **Handing the examples back as the answer.** Tell: your answer contains only the items the user named, nothing added. Doing only those is the same as doing nothing.
- **Turning examples into a task list.** Tell: the user gave 2 examples and you stopped after doing exactly those 2.
- **Treating "the user didn't mention it" as "the user doesn't want it."** Tell: you left something out only because the user didn't say it. They probably just didn't think of it.
- **Over-expanding.** Tell: your additions push the user's examples out of the answer, drift outside the category, or crowd out what the user actually asked for.
- **Replacing the user's examples.** Tell: the user's own examples are missing from your answer. Expand around them; don't swap them out.

## When NOT to use this skill

- The user gave an explicit closed list ("just these three", "only these", "do exactly this", "nothing else"). Do the list as stated. Do not expand.
- The user gave no examples at all. A bare request with no examples has nothing to expand — do the request as stated.
- The user is illustrating a *format* or *style*, not a category of content (e.g. "write it like this example paragraph"). Do not expand the content; match the format.
- The examples are test cases or exact specs (e.g. "for example, input 3 should return 9"). Treat each one as a hard requirement. You may suggest extra cases, but label them as suggestions.
