# loop-review

产物是**收敛**：多轮 review → 修 → 重审，直到一轮找不到必须处理的问题。

用户明确要求优先于本 skill。项目的 `AGENTS.md`、`CONTRIBUTING`、构建与测试命令更具体时，指出冲突并采用项目规则。

## 先定范围和模式

动手前用一句话声明，不臆测。两档同样说得通才问。

| 范围 | 认出来 | 证据边界 |
|---|---|---|
| 改动 | 「最近的这个功能 / 这次改动」，或工作区只有这一处未提交 | 未提交的工作区 diff；已提交的用相对 merge-base 的三点 diff。加上直接相关的文档和测试 |
| 局部 | 点名模块、目录、文件 | 该范围、被调用的接口、调用方、相关 spec 段落 |
| 全项目 | 「整个项目 / 各模块」 | 入口、模块边界、公共接口、文档索引、全部 spec |

**模式**：用户说「看看 / 审一下」时只读，只出报告。用户说「直到没有问题」时允许修。删除只列候选，确认前不删。

## 改动标准

范围内已有的代码和文档，以及本循环写入的改动，都要**完整、必要、最小**。次序固定，后面的不能否定前面的。

- **完整** — 一条行为只留一套说法。代码、测试，以及陈述同一事实的文档和 spec，要么已经一致，要么一起改完。还有矛盾，或只改了一半，就没完整。
- **必要** — 留下的每段都守着一条现役义务：用户可见行为、不变量、失败语义、资源上限，或 spec 写明的非目标。没有义务的抽象、段落、文件列为删除候选，确认前不删。本循环写入的每个 hunk 还要指回一条已确认的发现。
- **最小** — 守住这些义务的最小 diff：能删不增，同一规则只改权威处，不重写没变的部分。只有缺了就无法完整时才新开文件。

最小不是落下文档；完整不是顺手重写周围。代码和 spec 不一致时，先判定哪边才是义务。判定不了就写入「待你确认」，两边都不改。判定之后同一次收完。不要默认改 spec 去迁就代码，也不要默认改代码去迁就 spec。

只读模式不写入。过不了的项和改法放进报告。

## 核心代码优先

力气不平均分配。**核心代码**：用户可见行为的主路径、公共接口、状态迁移、持久化与资源生命周期、并发与失败路径；按下面八项严格过。外围代码只要求不与之矛盾、不自造规则，不为它补防御层。

「精简」由「必要」「最小」和第 1 项承担；「易维护」由第 2、6、7 项承担。只有「可靠与稳定」此前只出现在义务清单里，所以第 3 项是新增的实质要求。

## 每轮必看的八项

能划出 diff 的范围，先交给 `code-review`（`~/.agents/skills/工作流/code-review/SKILL.md`）审这一轮的证据边界，并带上已找到的 spec。全项目按模块或子系统分批。固定点就用证据边界，不要另问；没有 spec 时，Spec 轴记「无 spec」，接着做第 8 项，不要停下去找 issue tracker。划不出 diff 的局部或全项目，按下面八项直接审当前代码和文档。

取回的 Standards 和 Spec 只是原料。用八项收口，不要原样当结论。每项都给结论，没有就写「无」。

1. **过度设计** — 没人要的抽象、参数、hook、配置项、缓存层、兼容分支。没有第二个实现者或调用者，删掉后行为不变，就列为删除候选。不留「以后可能用」。
2. **模块权威边界** — 每条业务规则、状态迁移、错误分类、资源上限只有一个权威 module。其余模块只调用或呈现，不另行推断。`grep` 同一规则的实现处数。
3. **核心代码可靠与稳定** — 核心路径的每条失败路径都要显式：错误分类、失败语义、资源收尾（超时、重试、释放、`finally`）、上限（数量、大小、时间）能指到权威处，指不到就是缺口。这些算发现：吞异常、失败当成功返回、靠默认值兜底掩盖错误、失败后留下半截状态、无上限的累积或递归、并发/重入下结果依赖时序。边界条件与并发只对核心代码要求，外围代码有自己的硬约束时才管。
4. **过度测试** — 为中间实现、私有细节或已替代方案写的测试；同一义务被多次断言。改动业务逻辑后不会失败的，是假测试。
5. **测试消融** — 多轮之后还并列的旧测试、已被取代的机制测试、靠 sleep 或时序的测试。义务不变就合并，义务变了就删，不层层叠加。
6. **文档过期冗余非必要** — 被 diff 打脸的现役说法、同一事实的多份解释、已完成仍列着的待办、中间态叙事。机制进 docs，历史进 git。
7. **spec / 代码 / 文档一致性** — 三处对同一行为的说法要能互相推出。有一处是猜的，就不算一致。
8. **最终 spec 权威** — 有一份始终最新的 spec，只写当前契约：用户可见行为、不变量、失败语义、资源上限、明确的非目标。没有就给出最小版：只读放进报告；允许修且未被禁止时才写入。与代码不符时按改动标准裁定，不单方面改写。

## 循环怎么走

粒度逐轮变细。八项每轮都要有结论，表里是该轮重点：

| 轮次 | 粒度 | 重点 |
|---|---|---|
| 1 | 架构级 | 范围、模块边界、明显过度设计、失败语义与资源上限是否缺位、spec 是否缺位 |
| 2 | 模块/接口级 | 权威归属、接口形状、重复规则、错误分类与上限的归属、文档与 spec 对齐 |
| 3 | 函数/分支级 | 死代码、无用抽象、假测试、失败路径与资源收尾遗漏 |
| 4+ | 细节级 | 命名与残留、注释与过期指代、边界条件、半截状态与静默失败 |

- 只报有行动价值的发现，附文件:行、权威来源、改法与验证方式。不写风格偏好，不按行数判优劣。
- 写入前过改动标准，过不了就不写。修完重审受影响的部分，不假设改对了。能跑项目已有检查就跑；跑不了标 `pending`。同一失败第二次出现就停，先查假设和命令，不盲重试。
- 只剩风格意见、判断题，或「可以但没必要」的改动，就停下并写明「已收敛」。不为凑轮次继续挖。
- 同一问题连续两轮出现，回到第 2 项找权威 module，不再补一层补丁。

```text
**模式**：只读报告 | 已修
**轮次**：N 轮，收敛于第 N 轮（理由：<最后一轮的判据>）

**主题结论**（逐项：结论 / 依据 / 处理）
1 过度设计 …  2 权威边界 …  3 可靠与稳定 …  4 过度测试 …
5 测试消融 …  6 文档 …  7 一致性 …  8 最终 spec …

**改动验收**：完整 — …；必要 — …；最小 — …

**改动**
- <文件> — <改了什么，对应哪条发现>

**待你确认**
- 删除候选：<文件 + 理由>（未确认前没删）
- 无法裁决：<冲突 + 两边证据>

```

## 收工前

- 范围外没有写入。每个「已修」都有对应 diff 或检查结果。
- 改动验收三条都有结论。未过的在「待你确认」，没有半截 diff。
- 八项都有结论，包括「无」。第 3 项对核心代码给出的是失败路径清单，不是「无问题」三个字。
- 最终 spec 与代码不矛盾，或已列为缺位，或冲突已在「待你确认」。旧测试、旧机制、旧文档没有当无标记的历史版本留下。
