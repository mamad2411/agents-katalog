# 缓存工程实践

## 一、适用范围与默认决策

适用于可丢弃、可从权威数据源重建的业务缓存，不依赖特定语言或 Agent 平台。Redis 也可承载持久业务状态；不能仅因使用 Redis 就将其按缓存删除或降级处理。

默认采用 **Cache-Aside（旁路缓存）**：读取未命中时回源，写入时先提交数据库事务，再删除受影响缓存，后续读取被动重建。以下用“数据库”代表权威数据源。

- 默认方案允许短暂不一致；先明确允许旧数据的范围和时长，再选择增强机制。
- 不默认先写缓存再写数据库，也不默认主动更新缓存。已有读穿、写穿或预热方案应依据其一致性和失败处理评审，不仅为统一模式而重写。
- 业务正确性优先；余额扣减、库存扣减、权限撤销等关键决策不能仅凭可能过期的缓存结果完成。

## 二、执行流程

1. **检查现状**：先读相关代码、配置和已有约定，识别权威数据源、事务边界、所有写入入口及现有失效机制。
2. **补齐决策条件**：确认新鲜度要求、读写量与热点、缓存产品及版本、单机或集群、本地缓存、租户隔离和已有基础设施。只追问会改变方案的缺失信息，其余标注假设并继续可独立完成的工作。
3. **设计或审查**：按下文确定读写、键、TTL、失效范围及故障行为。复杂机制仅在默认方案不足时引入；并发与传播细节按需读[一致性与重建](references/consistency-and-rebuild.md)。
4. **验证与交付**：针对改变的行为验证正常、并发及失败路径，输出结论、风险和验证结果。简单任务只覆盖相关部分，不机械执行全量检查。

## 三、读取、写入与失效

### 3.1 读取与回填

```text
读缓存 → 有效命中 → 返回
       → 未命中 → 查询数据库 → 回填缓存并设置 TTL → 返回
       → 缓存异常 → 按降级策略受控回源或快速失败
```

- 区分未命中、缓存故障和数据损坏；格式不兼容或反序列化失败可视为无效缓存并回源，同时记录异常。
- 数据库查询成功后，缓存写入或序列化失败通常不影响返回已取得的结果；数据库超时、异常不得缓存为“不存在”。
- 回填与 TTL 应使用产品支持的原子操作，避免写入成功、设置过期失败留下永久键。
- 热点回填需要请求合并或受控重建；同时检查旧请求晚回填和只读副本延迟，不能把“回源”自动等同于“读到最新值”。

### 3.2 写入与失效范围

```text
提交数据库事务 → 成功 → 删除受影响缓存 → 后续读取重建
               → 失败 → 返回数据库错误，不执行成功后的失效流程
```

- 在事务**成功提交后**失效，不能仅在执行更新 SQL 后、提交前删除。数据库提交与缓存删除不是一个原子事务。
- 覆盖新增、更新、删除、批处理、后台任务及其他服务的写入；失效范围包含详情、列表、聚合、查询结果及空值缓存。以数据依赖关系确定范围，避免漏删或无差别全量清理。
- 删除须幂等。失败时记录并按一致性要求做有界重试、补偿或告警；还要考虑提交后进程崩溃、根本未发起删除的窗口。
- 删除失败不能回滚已提交的数据库事务。默认不因此将已成功的业务写入报告为失败；若接口契约要求额外确认，明确已提交状态和请求幂等性，避免客户端盲目重试。

## 四、一致性方案选择

优先采用满足业务要求的最简单方案，高并发本身不是引入双删、消息队列或独立服务的理由。

| 需要解决的问题 | 可选方案与边界 |
| --- | --- |
| 普通读取可容忍短暂旧值 | 提交后删除，结合 TTL 和按需补偿；仍存在删除失败和旧数据回填窗口 |
| 旧读请求在删除后回填 | 按风险评估延迟双删或版本校验；前者降低概率，后者需完整的版本与原子写入协议 |
| 提交后失效任务不能丢失 | 评估事务 Outbox 或变更数据捕获（CDC），复用已有设施；传播延迟仍然存在 |
| 多服务或多级缓存 | 明确失效所有者、传播范围和各层的新鲜度；删除共享缓存不等于清除各进程本地副本 |
| 写后立即读到新值或严格新鲜度 | 考虑返回已提交结果、相关读取绕过缓存并使用满足要求的权威读路径；异步失效不提供强一致保证 |

实现或深入评审双删、Outbox、CDC、版本控制、多级失效时，先读[一致性与重建](references/consistency-and-rebuild.md)。

## 五、缓存键与隔离

### 5.1 命名与数据维度

沿用清晰的项目约定；新键推荐“命名空间:业务域:资源:标识”，使用小写英文描述、稳定业务 ID 和清晰缩写，例如：

```text
order-service:order:detail:ORD10001
user-service:tenant:t10001:profile:u20001
```

- 命名空间通常采用服务名；跨服务共享时约定统一所有者和格式，按需加入环境或结构版本，避免冲突。
- 将所有影响结果的维度纳入键，如租户、用户可见范围、查询条件、分页、排序和语言。组合顺序固定，规范化编码并处理分隔符冲突；必要时哈希，避免直接拼接不稳定对象序列化结果。
- 租户与权限上下文来自可信来源。禁止在键中放入密码、Token、密钥及直接暴露隐私的信息；哈希不等于加密。

### 5.2 Redis Cluster Hash Tag

涉及要求同槽的多键命令、事务或 Lua 脚本时，核对目标产品和客户端的槽位约束。仅在需要时使用 `{}` 指定共同哈希标签，例如：

```text
user-service:{t10001:u20001}:profile
user-service:{t10001:u20001}:permissions
```

同一标签内的键进入同一槽；单键操作无需强制标签。不要默认以整个大租户或固定常量为标签，避免集中热点。客户端把跨槽操作拆成多次请求，不代表具备跨槽原子性。

## 六、TTL、生命周期与缓存对象

### 6.1 过期策略

TTL（存活时间）依据允许陈旧时间、更新频率、回源成本及容量共同确定，不使用脱离业务的统一秒数。

| 数据特征 | 选择依据 |
| --- | --- |
| 高频变化或要求较新 | 较短 TTL 或主动失效；不能满足正确性时绕过缓存 |
| 稳定字典、配置 | 可较长 TTL；无限 TTL 需说明容量、更新及清理机制 |
| 热点数据 | 先满足新鲜度，再用请求合并、受控预热或允许范围内的逻辑过期降低回源压力 |
| 空值、临时状态 | 空值通常较短 TTL；临时状态不得超过业务有效期 |

- 集中过期时采用随机抖动；若存在最大允许 TTL，可使用 `TTL = MaxTTL - Random(0, Jitter)`，保证 `0 <= Jitter < MaxTTL`，不能因抖动延长业务有效期。
- 逻辑过期须区分刷新时间与停止提供旧值的硬期限，限定后台重建并发及失败后的旧值使用范围。
- TTL 从回填开始计时，不自动保证数据年龄上限；慢请求、滞后副本及滑动续期可能延长旧值影响。严格期限需配合来源版本、数据时间或满足要求的读路径。

### 6.2 数据表示与兼容

- 缓存最小必要字段，避免敏感完整对象；评估对象大小、序列化、压缩和网络开销。
- 空值用可与正常值、未命中区分的标记表示，新增数据时处理其失效。
- 结构升级考虑新旧应用并行运行；按需使用结构版本或新命名空间，并明确旧键清理和回滚行为。结构版本与业务数据版本用途不同。
- 进程内缓存还需容量上限；共享可变对象应使用不可变表示或防御性复制，避免调用方污染缓存。

## 七、击穿、穿透与雪崩

| 问题 | 优先处理 | 实施边界 |
| --- | --- | --- |
| 击穿：热点失效引发并发回源 | 请求合并（Singleflight）、受控预热；按需跨实例锁或逻辑过期 | 本地合并只覆盖当前进程；等待有界，仅在业务允许时返回旧值 |
| 穿透：反复查询不存在的数据 | 参数校验、短期空值缓存、限流；按需布隆过滤器 | 区分不存在与依赖故障；过滤器同步滞后不能误拦真实新数据 |
| 雪崩：集中失效或缓存整体故障 | TTL 抖动、分批预热、限流、熔断及降级 | 抖动不能解决服务整体不可用；高可用、多级缓存与容量规划按实际故障需求选择 |

使用分布式锁或布隆过滤器前，读[一致性与重建](references/consistency-and-rebuild.md)中的租约、原子释放、同步和重建规则。

缓存不可用时，给缓存操作设置合理超时，限制回源并发和重试预算，避免拖垮数据库。数据库也不可用时，仅返回业务允许的旧值，否则快速失败；不无限等待、无限重试，也不把故障伪装为正常空结果。

## 八、容量、安全与可观测性

### 8.1 容量与性能

- 依据实际瓶颈优化：衡量命中收益与读写、序列化、失效、运维成本，而非只追求命中率。
- 检查内存预算、连接池、网络延迟、淘汰策略及淘汰后的数据库压力。过期与容量淘汰是不同机制；Redis 的 `noeviction` 可能拒绝写入，`volatile-*` 只淘汰带过期时间的键。
- 大键按访问模式评估拆分、分页或压缩及其 CPU 代价；热键可评估本地缓存或受控副本。普通分片不能自动分散单个热键的访问。

### 8.2 安全与监控

- 命中不替代权限校验。按数据敏感度配置访问控制、网络隔离、传输保护及必要的加密、清理机制；日志不输出敏感键值。
- 按场景观察命中/未命中/错误、读写延迟、失效失败、重建耗时、回源率及数据库负载、内存/淘汰、大键/热键、锁竞争，以及适用时的补偿积压和一致性延迟。
- 故障至少有可定位的日志或指标，统一命名和低基数标签；不将用户 ID、完整缓存键作为指标标签。

## 九、验证与输出

选择能覆盖本次变更的场景，不要求每次搭建全部基础设施：

- 正常命中、未命中、空值，以及写入提交/回滚后的行为。
- 旧请求晚回填、重建竞争、适用时的锁过期、任务重复/乱序及进程重启。
- 缓存超时、回填/删除失败、数据库失败和受控回源；确认已提交写入的响应语义。
- 租户及权限维度隔离、相关缓存失效、结构升级；涉及集群时验证同槽约束。

按任务规模输出方案或具体问题、依据与修复建议，列明键、TTL、读写及失效流程、一致性边界、故障行为和必要的监控。区分已验证、推断及待验证项；静态审查或模拟时序不能声称通过了真实并发、性能或部署验证。
