# 統計学の基礎（図解ドリル）

**先に `question-authoring`（共通ルール・適用手順）と `explanation-clarity`（わかりやすさの方法論）を読むこと。** ここは本ドリル固有の情報だけ。

## この問題集の性格（他の区分と根本的に違う）

資格試験対策ではなく**教養ドリル**。ユウが読んでいる統計教科書（363ページ）の用語を、前提知識ゼロで腹落ちさせるのが目的。

- **問題は入口、解説が主役。** 問題は暗記チェックではなく、解説を読ませるためのフック。お小遣い・靴屋・アイスの売上のような身近な場面から入る
- **解説は小学生でも分かるレベルに振り切る**（ユウ確認済み 2026-07-29）。ただし漢字は普通に使う。読者は大人
- **全問に `viz`（1枚の図解SVG）を付ける。** これがこのドリルの看板。図なしの問題を足さない

## 大量生産の型と教訓（2026-07-30 のセット2〜8、76問で確立）

**体制**: Workflow オーケストレーション。Sonnet 作問7並列（各自スキル3枚＋Set1雛形を読み、SVGのPNG目視検証まで担当）→ 別 Sonnet がセットごと監査 → 指摘があったセットのみ Sonnet 修正。PM（メインループ）は用語リストの発注・検収・DB適用・コミットのみ。21エージェント・約24分・レビュー指摘17件全修正。

### 効いたこと（再利用時も維持する）

- **作問者と監査者を別エージェントに分ける。** 機械チェックでは絶対に拾えない「事実レベルの誤り」が7セット全部で出た（中心極限定理の収束要因の曖昧さ、回帰直線と重回帰の呼び分け、相関係数と傾きの因果逆転、など）。自己レビューでは出ない種類の指摘
- **雛形スクリプト（生成 Python）ごと渡す。** 形式・自己チェック・SVGヘルパーが揃い、機械ルール違反（位置参照・opt数）は納品時点でゼロだった
- **発注書に「用語リスト＋依存順＋図のヒント」まで書く。** 内容のブレと手戻りがほぼ消える。PMの主な仕事はこの発注書の質
- **DB適用と git は PM 専任。** 並列エージェントに書かせない（migration 番号の衝突と適用事故の防止）
- **監査の観点は「統計的な事実の誤り最優先、重箱の隅は拾わない」と明示。** 指摘が must/nice の17件に収まり、修正コストが小さかった

### 反省点（次回の発注書で直す）

- **構造化出力のフィールド定義は解釈の余地なく書く。** `figures_verified` を「viz変更なしなので対象外＝false」と返したエージェントがいて、検収時に紛らわしかった。「検証したか」ではなく「未検証の図が存在するか」のような一義的な定義にする
- **長さ偏り・UTF-8 meta など既知の落とし穴は発注書に先回りで書く。** 各エージェントが同じ問題を各自再発見して直した（結果は正しいがトークンの無駄）。このスキルの該当節を発注書に引用するだけでよい
- **修正エージェントには「指摘範囲外でも、同じ誤りの別表現（terms/opt への波及）は直してよい」と明示する。** 今回は良い判断で勝手にやってくれたが、運任せにしない
- **作問エージェントへの発注書には「DB適用・コミット・pushはしない、ファイル作成のみ」と禁止形で明示する。** 中級4カテゴリ追加（2026-08-02）では、同じ発注書を渡した4体のうち2体がCLAUDE.mdの包括許可（問題集の適用/コミット/pushは確認不要）を根拠に、監査を待たず自分でDB適用・コミット・pushまでやってしまった（残り2体は指示通りファイル作成で止まった）。包括許可の存在自体は問題ないが、「監査前に本番へ出さない」という**このワークフロー固有の順序**は発注書側で明示しないと守られない。実害は出なかった（監査のmust指摘はUPDATE文の新規migrationで本番の該当行を直接修正して回収できた。INSERTの再適用は`ON CONFLICT DO NOTHING`で無害なno-opになるため効かない点に注意）が、先に適用されてしまうと修正コストが上がるので次回は明示する。**この教訓は準1級レベル6カテゴリ追加（2026-08-02午後）で反映済み**：全12エージェント（作問6＋監査6＋修正）に禁止を明示した結果、先走りは0件だった
- **migration番号は他の問題集ドメインの並行セッションと衝突しうる。** 準1級レベル追加時、事前に確認した「次の空き番号」00099/00100が、同時に走っていた応用情報(ap-server)セッションの採番と衝突した（ファイル名が違うため上書き事故は無かったが、番号の一貫性が崩れた）。適用・コミット直前に改めて `ls supabase/migrations/ | grep -oE '^[0-9]+' | sort -n | tail` で最新番号を確認し、衝突していたら `git mv` で採番し直してから適用・コミットする

- セット内の並びは**「前の用語が次の用語の前提になる」依存順**（例: 分散、その次に標準偏差、その次に偏差値）
- マニアックな検定名（ブルーシュ・ペーガン検定等）は土台の8セットが済むまで足さない

## 問題の形

- 4択 single。問題文は1〜3文の**身近なシナリオ**（クラスのテスト・お小遣い・靴屋の仕入れ・アイスの売上）
- 誤答は「隣の概念」を置く（平均を問うなら中央値・最頻値の値、第3四分位数を問うなら第1四分位数）。共通ルールの長さ縛り（正解を単独最長にしない）を厳守
- **長さ偏りの定番の原因（Set2〜8で7セット中6セットが初稿で引っかかった）**: ①問う対象の用語（「ロジスティック回帰」等）が誤答の用語より字面で長い用語単体4択 → 全選択肢を「用語（短い説明）」の同一形式に揃えると密度も長さも自然に揃う。②正解にだけ根拠を盛った文章選択肢 → 誤答も同じ粒度で書く。③4択の先頭を「正しい/正しくない」で始める構造的ヒントにも注意（Set2 q12 で発生）
- `code` 列と `snippet` は基本使わない。数式を見せたいときも `think` の文中で言葉に開く

## 解説の流儀（ユウの要望4点に全キーを対応させる）

| 要望 | キー |
|---|---|
| 何がどういう意味か | `asked` + `kid`（ざっくり言うと） |
| たとえで直感 | `eg`（一番力を入れる。やじろべえ・両替・記念写真の真ん中の人、のレベル） |
| なんのためにあるか | `why_asked`（「この概念が無いと何に困るか・なぜ発明されたか」を書く） |
| どういうことに役立つか | `usecase`（実生活・仕事の場面） |

加えて `point`（決め手1文）・`terms`（2〜4個）・`think`（因果の背骨。「なぜ2乗するのか」「なぜ外れ値に強いのか」を鎖でつなぐ）・`vs`（平均vs中央値、外れ値vs偏差値のような隣接概念）・`opt`（選択肢と同数）・**`viz`**。

## 計算系解説の3段ロケット（`calc` キー、2026-07-30〜）

読者の数学は**小学校算数＋α**を前提にする（ユウは中1以降の学校数学を経ていない。負の数・文字式・√・Σ・log・微分は「未習」として扱う）。計算が絡む解説は必ずこの順:

1. **日本語で言う**（`kid`/`think`）— 「分散＝みんなが平均からどれだけ離れてるかの平均」
2. **小さい数字で全ステップ**（`calc`）— 5人の点数 56,58,60,62,64 のような暗算で追える数で、1行1手で最後まで。途中を省かない。例:
   ```
   点数     56  58  60  62  64
   平均     (56+58+60+62+64) ÷ 5 = 60
   平均との差  -4  -2   0  +2  +4
   2乗      16   4   0   4  16   ← マイナスが消える
   2乗の平均 (16+4+0+4+16) ÷ 5 = 8 …これが分散
   ```
3. **最後に記号版**（`calc` の末尾 or `terms`）— 「いまやったのがこの式 σ² = Σ(x−x̄)²÷n。Σは『ぜんぶ足す』、x̄は『平均』」

鉄則: **式を先に見せて後から説明する順は書かない**。記号は初出のその場で読み方を書く（Σ=シグマ=ぜんぶ足す）。`calc` は等幅・縦積みで描画されるので桁を揃える。矢印(→)は `calc` 内の注記では使ってよい（自由文の位置参照検出とは無関係だが、正誤の選択肢位置は指さない）。数値は監査者が全ステップ再計算して検収する。

## viz（図解SVG）の書き方

`explanation_data.viz` にインラインSVG文字列。描画は `RichExplanation`（`src/features/quiz/components/rich-explanation.tsx`）の「図で見る」セクション（`eg` の直後）。型は `ExplanationData.viz`（`src/features/quiz/lib/types.ts`）。

- `viewBox="0 0 340 150"` 前後（高さは内容に合わせ 120〜150）。幅340pxに収まらない文字は必ず見切れる
- 配色（静かな計器・ダーク。背景は描画側が `#141720` を敷くので塗らない）:
  - 文字 muted `#8892a4` / 強調 `#e8eaf0` / アクセント `#3b82f6`・`#60a5fa`
  - 罫線 `#2a2f3f` / 緑（正しい・OK） `#6ab08d` / 赤（外れ値・注意） `#c47070` / 琥珀（対比） `#c9a04a`
- font-size 9〜13。1枚に伝えることは1つ。目盛り・凡例を盛らない
- 定番の型: 数直線＋点＋支点（平均）、点列＋真ん中強調（中央値）、棒の高さ（最頻値・ヒストグラム）、帯の4等分（四分位）、箱ひげ、ベル曲線＋マーカー（偏差値・z値）、散布図＋破線トレンド、2×2マス（混同行列・検定の過誤）

### 制作と検証の手順（Set 1 で確立）

1. **Python 生成スクリプト**で問題 dict＋SVG から SQL を生成する（`explanation-clarity` の流儀。手書きSQLはエスケープ事故のもと）。スクリプト内で位置参照の正規表現チェックと「正解が単独最長でないか」を自動チェックする
2. **SVG は必ずPNG化して目視する。** 文字の重なり・見切れはコードだけでは気づけない（Set 1 では12枚中4枚、Set 2〜8 でも7セット中5セットが初回レンダリングで何かしら発見した。「初稿の図は必ずどこか壊れている」前提で回す）:
   ```bash
   qlmanage -t -s 680 -o . viz01.svg   # macOS標準。ダーク背景を style で敷いてから
   ```
   SVG を HTML に包んでレンダリングする場合は **`<meta charset="utf-8">` を必ず入れる**（無いと日本語が文字化けPNGになる。Set2/Set7 で再発）。頻出の壊れ方: 340px 右端の見切れ（anchor=middle の長文タイトルは中央 x=170 に置く）、帯とラベルの対応が視覚的に逆に見える配置、意味のない描き残しパス。
3. 適用・件数検証は共通ルールどおり。`viz` の充足も数える:
   ```sql
   select count(*) filter (where explanation_data ? 'viz') from ...;
   ```

## 内容の注意

- 数値例は**その場で検算できる小さい数**にする（5人の点数、310÷5=62 のように読者が暗算で追える規模）
- 「相関＝因果ではない」「偏差値は割合ではない」のような**世間で誤解されがちな点**を `vs` で必ず拾う
- 教科書の索引にある用語でも、依存する前提（例: 正規分布を知らないと偏差値の16%が出せない）があるときは、先行セットで前提を張ってから出す。先に出すなら「分布が正規分布に近ければ」のような留保を付けて接地する
