# 解説を世界一わかりやすくする

対象読者は **資格合格を目指す成人だが、その分野は初めて**という人。判断基準はただ一つ:

> **前提知識ゼロで読み、一度で100%わかるか。**

原則: **「短くて謎」より「長くても因果が全部つながる」を採る。** 一歩も飛ばさず鎖でつなぐ。噛み砕きすぎて不自然になってもいけない（下の②）。

これは G検定 Set A 全50問で確立した基準（2026-07-16）。⑥因果の背骨は G検定 A/B/C/D の仕組み系30問で確立（2026-07-17）。他の試験区分に横展開するときの雛形。共通のDB手順・スキーマは `question-authoring` を読む。UIを触るなら `ui-design`（静かな計器）も読む。

## 6つのテコ

### ① たとえ（`eg`）を全問に
抽象概念は必ず**身近な比喩1つ**に落とす。世界一の説明者に共通する最大のテコ。`kid`（噛み砕いた言い換え）とは**別角度**にする（kidが既に比喩なら、egは別の場面で刺す）。

- ○ ロジスティック回帰＝「たい焼きに鯛は入っていない。名前(回帰)と中身(分類)は一致しない」
- ○ 勾配消失＝「伝言ゲームで後ろほど声が小さくなり最後に届かない」
- ○ 再現率＝「空港の手荷物検査。見逃さないことを最優先」

### ② 決め手（`point`）を一撃で立てる
**これだけ覚えれば正解できる判断ルールを1文**で。解説の主役として `asked` の直下に強調表示（UIで実装済み。細い青の左罫線＋やや大きい文字＝1画面1箇所の“大胆さ”）。`think` の要約版。

- 形は「〜なら○○」。例:「出力を確率に変えてグループ分けするなら分類。名前の『回帰』に惑わされない。」

### ③ 学習動線順（UI）
直感を先に固めてから理屈へ。`RichExplanation`（`src/app/(main)/learning-app.tsx`）の描画順:

```
asked → point → kid → eg → terms → think → snippet → vs → why_asked → usecase → opt
```

（何を問われ → 決め手 → ざっくり → たとえ → キーワード → 考え方 → 正しい書き方 → 混同 → なぜ問われる → 使いどころ → 選択肢別）

### ④ 自然な日本語（噛み砕きすぎない）
やさしくしようとして**不自然・幼稚**になった箇所を避ける。実際にやらかした例:
- 「当てっこ」→「予測」、重みを「みんなを」→「重み全体を」、「書き下す」→「書き出す」
- 口語の「〜よね」を残さない
- **文中の矢印 `→` を多用しない**。「A→B→C」は節に展開する（「Aから、B、Cへとたどって」）

### ⑤ 前提ゼロ接地（最重要・一番やりがち）
**説明していない前提の上に説明を積まない。** 専門用語が出たら、その場で正体を言う。これを怠ると「何言ってるか分からん」になる（G検定 q18 勾配消失で実際に指摘された）。

無説明で使いがちな前提と、その場での言い換え例:
| 前提用語 | その場で言う |
|---|---|
| 重み | 各項目の「効き具合のつまみ」 |
| 学習／最適化 | 「成績が一番良くなる場所へ、少しずつ坂を下る」 |
| 勾配・学習の信号 | 「どれだけ間違えたか＝『直してね』の合図が、出口から入口へ伝わる」 |
| 特徴マップ | 「画像のどこに線や角があるか」 |
| RNN | 「順番のあるデータを前から一語ずつ読むAI」 |
| 判定ライン／閾値 | 「『何%以上なら陽性』と引く線」 |

例（勾配消失 q18・接地後）:「AIは『どれだけ間違えたか』を出口から入口へ順番に伝えて、各層のつまみ(重み)を直しながら賢くなる。でもシグモイドを通るたび『直してね』の合図が必ず小さくされる。層が深いと小さくが何度も重なって合図が消え、手前の層まで届かない→直せない→学べない。これが勾配消失。」

### ⑥ 因果の背骨（`think`）＝なぜそうなるか
**手法・仕組み系の問いでは、「何をするか(What)」「どう役立つか(Use)」で止めず、「なぜそれが効くのか(Why)」を `think` に一本の鎖で通す。** これが抜けると、正しいのに腹落ちしない解説になる（ユウ「SVMの使い道は分かるが、なぜマージンが広いと効くのか因果が見えず頭に入らない」が起点。2026-07-17）。

- **形**: 「なぜ〜なのかがカギ。[前提を置く]…[一歩ずつ理由をつなぐ]…だから○○。」。② point（一撃の判断ルール1文）の"詳細版"として、think がその判断が成り立つ理由を展開する。
- **鎖の典型パターン**（手法がなぜ効くか）:「本当に効かせたいのは未知データ ＝ 手元の訓練データではない」「この工夫をしないとこう失敗する」「この工夫を入れるとその失敗がこう防げる」「だから効く」。
- **対象を選ぶ**。因果の背骨が要るのは**仕組み系**（SVMのマージン、L1が重みを0にする、ReLUが勾配消失を防ぐ、ドロップアウト、正則化、勾配降下法…＝「なぜ効くか」がある手法）。**事実・歴史・法律・用語弁別**（ELIZA、MYCIN、特許法、正規分布68%…）は因果の背骨が存在しないので**通さない**。無い所に無理に足すと逆に濁る。
- **矢印を使わず節に展開**（④と同じ）。「A→B→C」ではなく「Aだと…になる。だからBして、Cになる」。

例（L1正則化・因果の背骨）:「なぜL1だけが重みをちょうど0にできるのかがカギ。正則化は『重みを小さくせよ』という罰を足す仕組み。L2は重みの2乗を罰するので、重みが0に近づくほど引っぱる力も弱まり、0の手前で止まって完全には0にならない。L1は絶対値を罰するので、0のすぐそばでも引っぱる力が一定のまま働き、小さい重みを0まで押し切る。結果、効かない項目が消え、効く項目だけ残る。」

Before（What止まり・NG）:「0にするか、しないかで見分ける。0にするのがL1、全体を小さくするのがL2。」← 見分けはつくが「なぜL1は0にできるのか」が無く腹落ちしない。

## explanation_data の各キーと役割

`src/lib/quiz/types.ts` の `ExplanationData` と一致させる。UIに描画コードが無いキーは**画面に出ない**（`RichExplanation` に追加が要る）。

| キー | ラベル | 役割 |
|---|---|---|
| `asked` | 何を問われているか | 設問の言い換え。1文 |
| `point` | 決め手 | ①これだけで正解できる判断ルール。主役 |
| `kid` | ざっくり言うと | 噛み砕いた言い換え（前提ゼロで） |
| `eg` | たとえると | 身近な比喩1つ。kidと別角度 |
| `terms` | キーワード | `[["用語","やさしい説明"],...]` 2〜4個 |
| `think` | 考え方 | 見分け方「〜なら○○」。pointの詳細版。仕組み系では⑥因果の背骨（なぜ効くか）をここに通す |
| `snippet` | 正しい書き方 | コード模範解答（概念問題では不要） |
| `vs` | 混同ポイント | 紛らわしい選択肢との違い |
| `why_asked` | なぜ問われるか | 出題意図・落ちる思考の癖 |
| `usecase` | 使いどころ・どう役立つか | 実務のどこで使い何に効くか |
| `opt` | 選択肢の解説 | **選択肢と同数**。正解は「正解。」で始める |

## 仕上げ前セルフチェック

1. **前提ゼロで読めるか。** 各文の用語を、その分野を知らない人が全部わかるか。1つでも未説明の前提があれば接地する。
2. **因果が飛んでいないか。** 「なぜそうなる」を一歩も飛ばさず鎖でつなげたか。
3. **仕組み系なら因果の背骨(⑥)が通っているか。** What/Useで止めていないか。逆に、事実・用語弁別系に無理な因果を足して濁らせていないか。
4. **たとえは別角度か。** eg が kid の焼き直しになっていないか。
5. **決め手は1文で言い切れているか。**
6. **不自然な日本語はないか。**（④の癖）

## 実務手順（事故らないやり方）

共通の適用・検証は `question-authoring` に従う。ここは clarity 作業に特有の注意。

- **Python で SQL を生成する。** 50問×リッチJSONを手書きするとエスケープ事故が起きる。dict→`json.dumps(ensure_ascii=False)`→`'` を `''` に置換→`UPDATE ... explanation_data = ...`。scratchpad に生成スクリプトを置く。
- **非破壊マージ。** キー追加は `explanation_data || jsonb_build_object('eg', ...)` や `|| '{...}'::jsonb`。全書き換えのときだけ丸ごと `= '{...}'::jsonb`。既存キーを消さない。
- **`opt` は DB の選択肢インデックス順を厳守。** シャッフルはアプリ側(`shuffleOptions`)が追従させる。正解(通常index0)は「正解。」始まり。適用後に **opt長 == options長** を全問確認。
  ```sql
  select count(*) filter (where jsonb_array_length(explanation_data->'opt') = jsonb_array_length(options)) from ...;
  ```
- **`asked`/`think`/`vs`/`explanation` に選択肢の位置参照（A/B/C/D・「選択肢A」・「正解はC」・「(C)」）を書かない。** 書くと `referencesOptionPositions`（`src/lib/quiz/selection.ts`）が検知してその問だけシャッフルを止め、正解位置が固定される。`point`/`kid`/`eg`/`terms`/`usecase`/`opt` は検査対象外だが、いずれも位置参照は書かない。適用前に正規表現でスキャンする:
  ```
  (選択肢\s*[A-DＡ-Ｄa-dａ-ｄ])|([（(]\s*[A-DＡ-Ｄ]\s*[）)])|(正解は\s*[A-DＡ-Ｄ])|([A-DＡ-Ｄ]\s*が正解)
  ```
- **新キーは描画コードが要る。** `point`/`eg`/`usecase` は `RichExplanation` に実装済み。新しいキーを足すなら型(`ExplanationData`)と描画の両方に足す。**キーを足しただけでは画面に出ない。**
- **本番DBが唯一のDB＝適用即公開。** 適用前に対象行を JSON でダンプしてバックアップ。
- **確認用プレビュー。** ローカルが Node 16 で `npm run dev` が動かない環境なら、本番配色(ダーク・静かな計器)の Artifact を作って見え方を確認・共有できる（G検定で実施。3問プレビュー）。
