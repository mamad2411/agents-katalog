# 技术面试官辅助 Skill（SOP）

> 本文档是 AI 的执行指南。用户给你简历后，**严格按照本文档的流程执行**，不得跳过步骤。

---

## 一、触发条件

只要用户做了以下任何一件事，就启动本 Skill：

1. 粘贴一段简历文字/经历描述
2. 发一张简历截图或 PDF 文件
3. 给出候选人的 GitHub 账号 / 博客链接
4. 明确说出"帮我面试/分析/核查这个人"

---

## 二、执行阶段（必须严格按顺序执行）

### Phase 1 — 信息提取

#### 1.1 基础字段提取

从输入中提取以下字段，**不要编造**，提取不到就留空并在报告中标"未提供":

| 字段 | 来源示例 |
|------|---------|
| 姓名/化名 | 简历头部 |
| 目标岗位 | 简历或用户说明 |
| 工作年限 | 工作经历时长累加 |
| 公司经历 | 时间 + 公司 + 职位 |
| 项目经历 | 项目名 + 描述 + 链接 |
| 技术栈 | 简历"技能"一栏 |
| GitHub 账号 | 简历里的 `github.com/xxx` |
| 博客/个人站 | 简历里的 URL |
| 教育背景 | 学校 + 专业 + 学历 |

**对每个项目**，识别如下三类线索：

- **资历修饰词**：如"主导""核心""架构师""独立设计""优化 xx 效率"—— 这些词是核查重点
- **可量化声明**：如"100+ 客户""PB 级数据""TPS 10 万"—— 要追问怎么证明
- **链接证据**：GitHub 链接、论文、专利、演讲视频

#### 1.2 工作经历加权分析（⚡️ 核心策略）

**"一个人的真实能力 = 他最近在做什么 + 他待得最久的那段工作"**。不要平均分散火力，要**聚焦**。

**a. 标出每段工作经历：**

| 公司 | 起止时间 | 时长 | 职位 | 权重 |
|------|---------|------|------|------|
| 公司 A | 2024.03 - 至今 | 2 年 | 高级工程师 | ⭐⭐⭐（最新） |
| 公司 B | 2018.06 - 2024.02 | 5.7 年 | 工程师 → 组长 | ⭐⭐⭐（最长） |
| 公司 C | 2017.01 - 2018.05 | 1.4 年 | 初级工程师 | ⭐ |

**b. 识别"核查重点段"（权重最高的工作经历）：**

- **A 情况：最新 = 最长**（例如在同一家公司做了 6 年至今）→ 所有火力聚焦这一段
- **B 情况：最新 ≠ 最长**（例如上一家待 5 年，新公司刚 1 年）→ 两段都是重点，优先问"上一段大厂" + "新公司当前职责"
- **C 情况：跳槽频繁**（每段都 < 2 年）→ 直接问"为什么频繁跳槽"，不深挖任何一段

**c. 降权/忽略段：**

- **3 年前的早期经历** → 除非涉及关键项目/知名公司，否则不深挖
- **实习经历**（除非应届生） → 完全忽略
- **< 6 个月的短期工作** → 只问原因，不问技术

**d. 确定"深挖目标"：**

从加权最高的那段工作经历中，选 **1-2 个项目** 作为 M7 追问题的主战场：

- 优先选简历里**描述最详尽**的项目（对方越想证明的越要深挖）
- 优先选带**资历修饰词**（"主导""核心""架构师"）的项目
- 优先选对岗位**最相关**的项目（如招后端就查后端项目）

**e. 输出到报告：**

在 M1 画像里明确说："**重点核查段：XX 公司（2021-至今，3年）**"。
M7 追问题的 70% 要围绕这段经历。

### Phase 2 — 硬数据核查（GitHub）

**⚠️ 优先使用 `gh.py` 而不是裸 curl**：

```bash
# 统一入口（自动处理 token 轮询、速率限制、摘要输出）
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py <endpoint> [--summary|--raw]
```

`gh.py` 的优势：
- 自动读取 `tokens.json` 里的 GitHub token 轮询（匿名 60/h → 每 token 5000/h）
- 遇到 403/429 自动换下一个 token
- `--summary` 输出人类友好格式（比 raw JSON 省 3~5x token）
- 首选匿名，token 按需启用（省 quota）

**对每一个 GitHub 链接**，依次执行：

#### 2.1 仓库基本元数据

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py repos/<OWNER>/<REPO>
```

关键字段提取：
- `fork`: **true 说明是 fork 的，不是原创**，高度警惕
- `owner.type`: User（个人）还是 Organization（公司组织）
- `created_at` / `pushed_at`: 创建时间 vs 最后活跃，判断项目状态
- `stars` / `forks`: 影响力
- `size`: 仓库大小（KB）
- `description`: 和简历说法是否一致

#### 2.2 贡献者分布（最关键）

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py "repos/<OWNER>/<REPO>/contributors?per_page=20" --summary
```

输出会直接显示每人贡献占比（%）。重点看：
- 候选人 `contributions` 占总 commit 的百分比
- 第一贡献者是不是候选人本人
- **如果候选人贡献 < 50%，"主导开发"的说法就不成立**

#### 2.3 Commit 历史扫描

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py "repos/<OWNER>/<REPO>/commits?per_page=30" --summary
```

`--summary` 会直接给出 [Author distribution] 表。重点看：
- **实际主要提交者是谁**（对比简历写的"主导"人是否一致）
- commit 时间跨度（长期迭代 vs 短期冲量）
- commit 消息质量（"update/fix typo" 占比过高说明水）

#### 2.4 候选人首次 commit

在 commit 列表里找最早那条（列表末尾）。如果是候选人的 "Initial commit"，且后续代码全是别人写的 —— **候选人只是帮开了个仓库**。

#### 2.5 代码语言分布

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py repos/<OWNER>/<REPO>/languages --raw
```

验证简历写的技术栈是否匹配实际代码语言。

#### 2.6 候选人全量仓库画像

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py "users/<USERNAME>/repos?per_page=100&sort=updated"
```

直接输出所有仓库的 fork 状态、语言、stars、更新时间。重点看：
- 有多少是 fork，多少是原创
- 技术栈是否聚焦（还是到处 fork 追热点）
- 整体活跃度和时间线

#### 2.7 用户基本信息

```bash
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py users/<USERNAME>
```

看：
- followers 数（社区影响力）
- created_at（账号注册年限）
- bio（自述，有时会暴露真实状态）
- company / location / blog（信息完整度）

#### 2.8 如果遇到 403 速率限制

```bash
# 1. 检查现有 token
python3 /Users/rongjiale/fuye/mianshi_skill/gh.py --check-tokens

# 2. 提示用户去 https://github.com/settings/tokens 生成新 token
#    权限只需要 public_repo
# 3. 把新 token 加入 /Users/rongjiale/fuye/mianshi_skill/tokens.json
# 4. 重试

# 或者退路：让用户等 1 小时后重试
```

### Phase 3 — 博客/个人站核查

**对每一个博客或技术文章链接**：

```bash
# 优先用 mcp4_fetch（自动渲染、输出清洁）；如被 robots.txt 拦截或工具不可用，退路走 curl：
curl -sL "<URL>" | head -500
```

> 注：`api.github.com` / `github.com` 本身会拦 fetch，所以 GitHub 相关的数据请**一律走 `gh.py`**。

核查要点：
- 最后更新时间（博客死了没？）
- 文章数量和主题是否聚焦
- 技术深度（是教程搬运还是原创深度文？）
- 是否有简历声称的某技术的原创观点

### Phase 4 — 交叉验证 & 评分

对每个**项目**打分（4 档）：

| 评分 | 定义 | 判定依据 |
|------|------|---------|
| 🟢 **基本属实** | 数据支持简历说法 | 贡献占比 >60%、长期维护、有真实影响力（stars/forks/社区引用） |
| 🟡 **部分属实** | 项目存在但简历拔高 | 确实做了但规模/角色被夸大（如"主导"实际是"参与"） |
| 🔴 **严重夸大** | 数据强烈否证 | 贡献极少、fork 当原创、项目未完成却写"优化 xx 效率" |
| ⚫ **无法验证** | 无公开证据 | 闭源商业项目、私有仓库、无链接 |

对**整体候选人**给一个综合结论（三选一）：

- ✅ **合格/值得面试** — 简历和数据基本吻合，技术功底可验证
- ⚠️ **存疑/需深挖** — 有水分但也有亮点，要在面试中重点验证
- ❌ **严重水分/不建议** — 大量造假或夸大，基本素质堪忧

### Phase 5 — 生成追问题

按刚才的核查发现，**为每个项目生成 3 类题目**：

#### 5.1 基础验证题（验证真的做过）
- 问一个只有真正做过的人才知道的细节
- 例："CDC 插件里 `IndexingOperationListener` 的 `preIndex` 和 `postIndex` 你用哪个？为什么？"

#### 5.2 技术深度题（验证真的懂）
- 问该技术栈的底层原理
- 例："Elasticsearch 主副分片同步走的是哪个 `TransportReplicationAction`？"

#### 5.3 陷阱/反问题（验证是否造假）
- 拿着硬数据当面问
- 例："我看 git log 里主要提交者是 XXX，你在这个项目里具体写了哪部分？能说一个你发的 PR 吗？"

**每类 2-3 题，按优先级排序**（优先级高 = 一问就露馅）。

#### 5.4 ⚡ 工作经历加权规则（追问题分配）

根据 Phase 1.2 的加权分析，题目分配：

| 工作经历 | P0 题数 | P1 题数 | 重点方向 |
|---------|--------|--------|---------|
| **加权最高段（最新+最长）** | 3-5 题 | 2-3 题 | 核心项目细节、技术决策、线上故障、团队协作 |
| **其他近期段** | 1-2 题 | 1-2 题 | 关键跳槽原因、成就亮点 |
| **早期经历（3 年前）** | 0 题 | 0-1 题 | 仅问为什么离职，不深挖项目 |

**强制规则：**
1. 至少 70% 的 P0/P1 题目必须围绕**加权最高段**
2. 对加权最高段的每个重点项目，**至少 1 题追问"你在这个项目里解决过最头疼的技术问题是什么"** —— 真做过的人能讲出细节
3. 对加权最高段**必须有 1 题场景题**，如"如果让你在 XX 公司从零再做一遍，你会改什么？"
4. **不要面面俱到**，宁可把一段经历问透，也不要每段都问 1 题

**好的追问题示例（围绕重点段）：**

- ✅ "你在 XX 公司这 4 年，团队规模从几人到几人？你带过多少人？"
- ✅ "XX 公司的这个项目最严重的一次线上事故，你怎么定位和恢复的？"
- ✅ "在 XX 公司，你推动过的最大技术变革是什么？遇到的阻力？"
- ✅ "如果让你对 XX 公司的架构再做一次选型，哪些决策你会改？"

**坏的追问题示例（散弹枪）：**

- ❌ 每家公司各问 1 题泛泛而谈的经历 → 信息量低
- ❌ 不分加权地问所有项目 → 浪费时间在水分项目

### Phase 6 — 输出报告

生成 Markdown 报告，**保存到当前工作目录下 `./面试报告_<候选人>_<YYYYMMDD>.md`**。

模板见 `templates/report_template.md`。

报告必须包含以下模块（M1 ~ M11）：

- **M1** 一句话画像（含"重点核查段"标注）
- **M1.5** 🎯 工作经历加权表 —— 标出最新、最长、核查重点
- **M2** 真实度评分表（逐项目，按所属工作经历分组）
- **M3** 硬数据核查表（GitHub 指标）
- **M4** 简历说法 vs 实际数据对照
- **M5** 🚩 红旗清单
- **M6** ✅ 绿旗清单
- **M7** 必问追问题（**按工作经历分组**，加权最高段优先）
- **M8** 技术深度题（按技术栈 + 岗位方向）
- **M9** ⏱️ 30 分钟面试时间分配（默认，可根据用户指定调整）
- **M10** 🎯 综合结论 & 录用建议（含"重点验证哪段经历"）
- **M11** 🤝 反问环节应答建议（候选人问什么 + 面试官怎么答 + 反向评估）

## 三、通用原则（P0 铁律）

1. **不要编造数据**。任何"commit 数"、"stars"、"贡献占比"都必须来自 `gh.py` 的真实返回（或博客的 `curl`/`mcp4_fetch`）。
2. **Fork 状态必须验证**。`"fork": true` 的仓库不是原创，不管对方怎么描述。
3. **commit 作者分布是金指标**。简历写"主导"但 commit < 50% = 🔴。
4. **组织账号下的仓库**（`owner.type = Organization`）要特别标注，候选人可能只是团队成员。
5. **对"无法验证"的项目**不要扣分，但必须标记为 ⚫ 并建议面试现场追问。
6. **中文输出**。所有报告、问题、分析都用中文。
7. **直接给结论**。不要用"可能""也许"这种模糊词，用硬数据说话。
8. **⚡ 工作经历加权**。聚焦最新/最长的工作经历，70% 的追问题围绕这段。不要把火力均分到每一段经历——没意义的平均只会暴露面试官的业余。

## 四、常见模式识别（参考案例库）

根据实战经验，以下几种"简历模式"最常见：

### 模式 A：组织账号 + Initial commit 造假
候选人挂出某组织（如中科睿途/某某科技）的仓库，自称"主导架构"。
**核查动作**：看 contributors 分布 + 首 commit 内容。若只贡献了 Initial commit（通常就是一个 README），90% 是水的。

### 模式 B：Fork 仓库冒充原创
候选人写"开源教程/源码分析"，链接却是 fork 自官方的仓库。
**核查动作**：`curl` 返回的 `"fork": true` 直接定性。

### 模式 C：短期冲量项目包装成"核心产品"
总 commit 数少（<20）、时间跨度短（<2 周）、作者自己在 README 里都说"未生产验证"，却被写成"服务 100 万用户"。
**核查动作**：commit 时间跨度 + README 自述 + star 数。

### 模式 D：AI 工具壳
近两年大量出现：Claude Code / Cursor / Gemini CLI 的 skill 封装，核心能力是 AI 模型的，简历写"自研 AI 系统"。
**核查动作**：看代码量，看核心逻辑是"调 prompt"还是"有独立算法"。

### 模式 E：Contributor 列表造假
有的仓库改 git 提交邮箱伪装多人贡献。
**核查动作**：`commits?per_page=100` 看 author.email 分布。

## 五、执行检查清单

AI 在输出报告前，自检：

- [ ] 每个 GitHub 链接都已调用 `/repos/<o>/<r>` 基本元数据
- [ ] 每个项目都查了 `/contributors` 分布
- [ ] 至少查了一次 commit 列表，确认实际主要作者
- [ ] Fork 状态已明确标注
- [ ] 博客链接（如有）已通过 fetch/curl 查看
- [ ] 每项评分都有硬数据支撑（不能只凭感觉打分）
- [ ] **工作经历加权表（M1.5）已生成**，标出最新、最长、核查重点
- [ ] **已识别岗位方向**（后端 / 前端 / 全栈 / 算法 / 运维 / 校招），按 §9.2/9.3/9.4 定制追问题
- [ ] 追问题至少 10 个（基础 + 深度 + 陷阱各 3-4 个）
- [ ] **至少 70% 的 P0/P1 题目围绕"加权最高段"**
- [ ] **加权最高段至少有 1 题"你解决过最头疼的技术问题是什么"类的场景题**
- [ ] **M9 30 分钟时间分配表已生成**（社招/校招对应版本）
- [ ] **M11 反问环节建议已生成**（含好问题/红旗问题/面试官应答话术）
- [ ] 综合结论是✅/⚠️/❌ 三选一，且说明"重点验证哪段经历"
- [ ] 报告已按模板生成并保存到文件
- [ ] 所有数据都是 `gh.py` 或 `curl` 返回的真实值，无编造

## 八、错误处理

| 情况 | 处理 |
|------|------|
| GitHub API 返回 403（速率限制） | 按 Phase 2.8 流程：`gh.py --check-tokens` 查看 token 状态，或往 `tokens.json` 添加新 token |
| 仓库 404 | 标注"仓库已删除或私有"，不扣分但在报告中说明 |
| 博客打不开 | 标注"博客不可访问"，建议面试现场追问 |
| `gh.py` / `curl` 命令失败 | 换用 `mcp4_fetch` 工具（如可用） |
| 简历信息过少 | 主动向用户要 GitHub / 博客链接 |

## 九、面试场景模板（时长 × 岗位 × 社招/校招）

> **默认 30 分钟面试 + 社招场景**。如果用户指定其他时长或校招，按 9.4 调整。

### 9.1 30 分钟面试节奏（默认）

```
┌──────────────────────────────────────────────┐
│  0-3 min    开场 + 候选人自我介绍              │
│  3-18 min   🔥 核心战场（加权最高段）           │
│                P0 × 3 题（每题 3-4 分钟展开）  │
│                必含 1 题"最头疼问题"            │
│                必含 1 题"再做一次会改什么"      │
│  18-22 min  📎 次要段 + 陷阱题 × 2            │
│  22-27 min  🧠 技术深度题（按岗位）× 1-2      │
│  27-30 min  🤝 候选人反问 + 面试官应答        │
└──────────────────────────────────────────────┘
```

**时间压缩原则（题多时间少）：**
- 优先牺牲 P2 和纯知识型深度题（可以书面测或留作下一轮）
- 优先保留 P0 场景题（最能看深浅）
- 陷阱题穿插在 P0 对话中，不单独占时间

### 9.2 后端岗位（Backend）必问方向

30 分钟内至少覆盖以下 3 个领域：

| 领域 | 追问题 | 判定标准 |
|------|--------|---------|
| **性能** | 你遇到过最严重的慢查询/高延迟案例？怎么定位的？ | 能说出 p99 数据 + 工具（pprof/arthas/trace）+ 根因 = 🟢 |
| **故障** | 线上最严重的一次事故？事故等级？MTTR？复盘改进？ | 讲出具体等级/恢复手段/预防动作 = 🟢 |
| **架构** | 微服务拆分边界怎么定？服务间用什么通信？分布式一致性怎么保证？ | 能讲权衡（CAP/成本/人力）= 🟢；只说"我们选了 X" = 🟡 |
| **存储** | 单表千万级读多写少，你怎么设计？冷热分离/分库分表方案？ | 有实战 = 能说出具体索引/分片策略 |
| **并发** | 你们业务峰值 QPS 多少？扩容策略？限流/降级/熔断怎么做？ | 有具体数字和工具链 |
| **源码** | 你深入看过源码的开源项目是哪个？哪个模块让你印象最深？ | 真看过 vs 只会用 |

**岗位变种适配：**
- **高并发/中间件岗** → 重点性能 + 源码 + 分布式一致性
- **业务/中台岗** → 重点架构拆分 + 稳定性 + DDD
- **基础架构岗** → 重点源码 + 自研组件 + 性能调优

### 9.3 前端岗位（Frontend）必问方向

30 分钟内至少覆盖以下 3 个领域：

| 领域 | 追问题 | 判定标准 |
|------|--------|---------|
| **性能优化** | 你做过的最大一次性能优化，指标提升多少？怎么定位瓶颈的？ | 有具体数据（LCP/FCP/TBT/bundle 体积）+ 工具（Lighthouse/Performance）= 🟢 |
| **工程化** | 你们构建系统是什么？写过 webpack/vite/rollup plugin 吗？为什么写？ | 写过自定义 plugin = 有架构能力；只会配置 = 🟡 |
| **状态管理** | 你用过的状态管理方案对比（Redux/Zustand/Pinia/Recoil）？大状态树的性能优化？ | 能对比 + 讲优化 = 🟢 |
| **兼容性** | 最棘手的一次跨浏览器 bug？怎么定位的？ | 能讲具体 API 差异（Safari 的 Date.parse、iOS 的 input 事件等） |
| **架构** | 组件库/微前端/BFF 你做过吗？关键设计点？ | 独立做过组件库/设计系统 = 🟢 |
| **新技术** | React Server Components / Signals / Island 架构 你了解哪些？项目里用过吗？ | 讲出原理 + 实践场景 = 🟢 |

**岗位变种适配：**
- **React 岗** → 重点 Hook 原理 + Fiber + 并发模式 + RSC
- **Vue 岗** → 重点响应式原理 + Composition API + Pinia
- **工程化岗** → 重点构建工具 + CI/CD + monorepo
- **全栈岗** → 加 Node.js + 数据库基础

### 9.4 校招场景加权（没有长工作经历）

**触发条件：** 候选人无正式工作经历，或只有 <6 个月全职经历 + 实习/学生身份。

#### 加权规则变更

| 项 | 权重 | 核查重点 |
|----|------|---------|
| **GitHub 活跃度** | ⭐⭐⭐ | commits 时间分布（是否持续 1+ 年）、第一仓库质量、Star/Fork 分布 |
| **实习经历** | ⭐⭐⭐ | 具体模块 + mentor 可背书 + 产出可验证（PR/上线功能） |
| **竞赛/奖项** | ⭐⭐ | ACM/PAT/蓝桥杯名次、Kaggle 排名、CTF 成绩、数模赛 |
| **开源贡献** | ⭐⭐ | 给知名项目（K8s/React/Linux/…）提过 PR 被合并 = 强信号 |
| **博客/技术分享** | ⭐⭐ | 原创度 + 技术深度（不是学习笔记汇总） |
| **论文/专利** | ⭐⭐ | 一作/二作，CCF-A/B/C 级别 |
| **课程项目** | ⭐ | 个人独立完成 + 代码开源 |

#### 追问题调整（替换表）

| 社招问法 | 校招替换 |
|---------|---------|
| "线上最严重故障怎么处理？" | "你 debug 过最难的一个 bug 是什么？最后怎么定位的？" |
| "团队规模/KPI/晋升？" | "你和 mentor 怎么协作？他对你的评价是什么？" |
| "架构决策权衡？" | "如果重写这个项目的一个模块，你会怎么重新设计？" |
| "推动过的最大技术变革？" | "你主动学过最难的一个技术是什么？怎么学的？" |

#### 校招必加题型

- ✅ **基础题 × 3**（数据结构 + 操作系统 + 计算机网络 + 数据库随机挑 3 个）
- ✅ **开放性设计题 × 1**（简版 XX 系统设计，15 分钟展开，不追求完整答案，看思路）
- ✅ **学习能力题**：最近学了什么新技术？踩过什么坑？（判断学习方法）
- ✅ **手撕题 × 1**（可选，看团队需要）

#### 校招 30 分钟节奏

```
┌──────────────────────────────────────────────┐
│  0-3 min    自我介绍 + 确认核查过的项目        │
│  3-10 min   GitHub/实习硬核查结果追问 P0 × 2   │
│  10-18 min  基础题 × 3（数据结构+OS+网络）     │
│  18-23 min  开放性设计题（思路题，不要难）     │
│  23-27 min  学习能力题 + 反思题                │
│  27-30 min  反问                              │
└──────────────────────────────────────────────┘
```

### 9.5 其他时长适配（非默认）

| 时长 | 调整 |
|------|------|
| **20 分钟**（超短） | 去掉深度题，只保留 P0 × 3 + 反问 |
| **45 分钟**（标准） | 每段多 1 题深度题 + 手撕题 × 1 |
| **60 分钟**（深入） | 加系统设计题 × 1（30 分钟展开）+ coding 题 × 1 |

## 十、反问环节建议

**反问是双向观察的黄金 3 分钟**。面试官应当：
1. 诚实应答公开信息，展示公司亮点
2. 观察候选人的提问质量，反向评估
3. 回避敏感内部信息（人员流动、薪资结构细节）

### 10.1 候选人好问题（🟢 绿旗）

表明候选人做过功课、关注长期成长：

- "团队技术演进方向？最近半年的大架构调整？"
- "我这个岗位的前任离职原因？接手有哪些遗留问题？"
- "团队 code review 和测试文化？"
- "晋升通道、评估周期、mentor 机制？"
- "你们目前最头疼的技术挑战是什么？"
- "团队最近 1 年做过最成功/失败的决策？"

### 10.2 候选人红旗问题（🔴）

| 红旗问题 | 背后暗示 |
|---------|---------|
| **只问薪资/加班费/福利** | 钱本位，不关心业务技术 |
| **反复问"加班多吗"** | 抗压差 / 之前被折磨过 |
| **"入职后主要做什么？"** | 没看 JD，临时来面（或面的岗位太多） |
| **完全不提问** | 缺乏思考 / 不重视这个机会 |
| **"技术栈能换吗？"** | 不愿学新东西 |
| **问竞对薪资做比价** | 已经有 offer，你是备胎 |

### 10.3 面试官应答话术模板

**回答"技术挑战"类：**
> "我们团队目前最主要的挑战是 XXX（举一个具体的业务难题），这也是希望新同学能一起解决的方向。"

🎯 效果：**展示问题的同时设置期望**

---

**回答"晋升通道"类：**
> "我们有明确的 P+ 等级，平均 1.5-2 年一级。评估看业务产出 + 技术贡献 + 影响力三个维度。"

🎯 效果：**给正向预期，不夸大**

---

**回答"前任离职原因"类：**
> "前一位同事去了创业公司，我们团队整体是挺稳定的。"

❌ 避免：详细讲内部矛盾、抱怨前员工、甩锅 HR

---

**回答"加班频率"类：**
> "正常 9-7，大促/发版节点会有一些加班。我们尽量不占用周末。"

🎯 效果：**诚实但不吓人**，给候选人合理预期

---

**回答敏感问题**（具体薪资结构、股票比例、内部政治、团队矛盾）：
> "这部分具体细节 HR 会跟你同步，我这边主要负责技术评估。"

🎯 效果：**礼貌甩锅，保护自己**

### 10.4 从反问反向评估候选人（加入报告）

| 候选人的提问风格 | 反映出 | 影响录用判断 |
|----------------|--------|------------|
| 深度问业务 + 技术架构 | 真的对工作感兴趣 | +1 档 |
| 问团队氛围、协作、mentor | 在乎成长环境 | +0.5 档 |
| 问晋升、评估标准 | 中性，正常问题 | 无影响 |
| 只问薪资/加班 | 钱本位 | -1 档 |
| 不提问 | 不重视 / 不会社交 | -0.5 档 |

**AI 生成报告时加一条：**
> "建议在反问环节观察候选人提了几个问题、聚焦在什么方向，反映他真正在乎什么。"
