# Configuration and delivery

Policy and configuration supplies trusted, validated settings and their effective version to the components that enforce them. Delivery and operations identifies the code and configuration actually activated for an observed run. These are logical responsibilities, not a mandatory configuration service or deployment pipeline. Begin with validated constants and a recorded local revision when they satisfy the change and evidence requirements; introduce independent publication or release machinery only when its pressure warrants it.

**Scope.** Use this skill to design, build, debug or review the agent system named by the current task. Component rules describe that target system; reading routes and engineering procedures guide your work on it. This separates product requirements from session instructions: actions remain governed by the current task and permissions, including when your own agent or harness is the target.

## Configuration and delivery instinct map

Separate the benefit of faster change or delivery from its consistency, availability and proof costs before adding machinery.

For capability design or problem-solving with a human counterpart, first use supported research or established practice to describe effective human performance, connect it to an option/check, and test transfer against agent differences; carry over only applicable human limits and label unsupported explanations as hypotheses; skip routine use and purely technical mechanisms without a counterpart ([design rule](../agent-system-engineering/references/engineering-process.md#design)).

| Need | Lever and trade-off | Build it as |
|---|---|---|
| Settings need to change without a code release | **External versioned configuration** buys independent cadence and ownership but adds validation, publication and availability/freshness paths; start with validated constants until that independence warrants them. [Configuration choices](references/policy-and-configuration.md#3-decision-table) | Typed configuration schema, versioned store and validating resolver. |
| Resolution is slow or a source sometimes fails | **Caching** can reduce reads and tolerate a permitted outage but trades freshness for invalidation and race controls; try direct versioned reads first, then bound staleness and failed-refresh behavior under measured pressure. [Cache contract](references/policy-and-configuration.md#4-conditional-invariants-and-defaults) | Resolver cache keyed by scope/version, with invalidation generation and refresh handler. |
| A long run must stay coherent while settings change | **Admission pinning** buys reproducibility but delays newer values; live overlays buy freshness with another owned version and failure seam. Pin the base, then explicitly select fields and boundaries needing refresh. [Version choices](references/policy-and-configuration.md#4-conditional-invariants-and-defaults) | Admission hook storing the effective configuration version in run state; named-boundary overlay resolver. |
| Parts must update while users keep working | **Compatible overlap** preserves availability but costs real old/new contract tests and temporary maintenance; an admission hold/drain buys simpler incompatible cutover at caller-paid downtime or wait. Prove overlap or expose the cutover. [Compatibility](references/delivery-and-activation-evidence.md#4-conditional-invariants-and-defaults) | Version-compatible producer serializers and consumer parsers, checked by old/new wire-contract tests; admission gate and drain routine for incompatible cutover. |
| Repeated changes consume operator time | **Release automation and provisioning reconcilers** reduce manual work but add drift, ownership and ambiguous-effect recovery; establish a repeatable verified path first and automate for actual pressure. [Provisioning choices](references/policy-and-configuration.md#3-decision-table) | Repeatable release pipeline; desired/observed-state reconciliation worker for provisioning. |
| A successful publish still produces the old behavior | **Source-to-artifact-to-run evidence** costs inspection but separates publication, activation and semantics; identify actual code and effective settings before retracing logic, using a compact local record when no remote delivery exists. [Activation evidence](references/delivery-and-activation-evidence.md#2-minimal-mechanism-interface-state-and-failure) | Build/activation manifest linked to run metadata; representative behavior assertion. |

## Choose the contract

- Read [policy and configuration](references/policy-and-configuration.md) when deciding who can change a setting, how values are validated and combined, which version applies, or how consumers handle compatibility, freshness and unavailable policy. It explains minimal constants, versioned publication, effective values, update and invalidation choices, and checks for stale or inconsistent consumers.
- Read [delivery and activation evidence](references/delivery-and-activation-evidence.md) when code or configuration must reach an execution outside the author's immediate process. It explains artifact and revision identity, release, activation, rollback and evidence connecting the intended change to the actual run. A local run still needs identifiable code and effective settings for reproducibility; it does not necessarily need a deployment mechanism.

Follow [configuration change and activation](../agent-system-engineering/references/system-flows.md) to trace publication through admission to an observed run. A published version is eligible to be used; publication alone does not prove that a particular run used it. A configuration fingerprint alone does not prove code identity. If evidence cannot identify either, report the corresponding claim as unverified.

## Route the work

1. **Design or plan:** identify the authority for each setting, its consumers, compatibility requirements, acceptable freshness and whether in-flight work may keep its admitted version. Compare constants, a versioned file and independent configuration by the real need for change, multiple consumers or freshness. Identify the environment and evidence needed to connect a change to a run before choosing a delivery mechanism.
2. **Build:** validate values and their relationships at the trusted boundary; record the effective version or projection at admission and pass it to consumers under the declared consistency policy. Make a version eligible only after its required validation. When release is needed, associate source revision, built artifact, activation and observed run, preserving separate evidence for each step.
3. **Debug:** identify the affected run and actual code and effective settings before tracing a suspected mismatch. Follow the setting from authoring and validation through publication, cache or invalidation, admission and consumption; distinguish an unavailable value from an absent setting and an intentionally pinned run from a stale consumer. For a release issue, locate the first unproven hand-off between revision, artifact, activation and execution.
4. **Optimize:** measure the change latency, freshness, operational burden or other problem first. Compare simpler distribution or caching choices against the declared freshness and compatibility requirements; an invalidation notification or subscriber count alone does not establish that every consumer applied the new value. Preserve version evidence while reducing delay or operational overhead.
5. **Review:** check unauthorized changes, invalid and incompatible values, concurrent publication, missed invalidation, mixed versions, unavailable required policy and rollback. Inspect both a new run and an in-flight run against the declared policy; require actual activation and run identity before claiming that a change is serving. A successful release is not proof of semantic correctness.

## Boundaries and evidence

The [task and interaction boundary](../agent-runtime-and-interaction/references/task-and-interaction-boundary.md) admits work and the [execution host](../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) owns scheduling and run lifecycle. They carry or check the applicable version; configuration does not itself enforce every downstream decision. The [action and tool boundary](../agent-harness-model-and-tools/references/action-and-tool-boundary.md) and other effect owners enforce their own authority. [Trust and privacy](../agent-trust-and-privacy/references/trust-and-privacy.md) governs sensitive configuration and who may change it; [diagnostics](../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md) connects run evidence without turning missing observations into success.

For acceptance, trace one valid change from its authorized source to an observed run and show the effective settings and code identity separately. Exercise an invalid or incompatible change, an unavailable required setting and the declared stale or pinned-version behavior. Where release and rollback apply, inspect their actual activation evidence and a run after each; where they do not, record the local revision and effective settings. These checks establish only the observed scope and do not establish behavior in an unobserved environment.
