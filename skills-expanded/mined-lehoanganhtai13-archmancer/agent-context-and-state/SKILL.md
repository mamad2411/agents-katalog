# Context and state management

Context and state management decides what information is available to each model call, where it comes from, what survives, and what loss means. It is a logical responsibility, not necessarily a service. A single request may need only its input; a long task may need durable history, a validated continuation, and a checkpoint that the execution host can restore. Shared storage or one process does not merge ownership: the harness selects the next step; this component owns information and state semantics; the host owns scheduling and liveness. Trust and privacy cut across these boundaries.

**Scope.** Use this skill to design, build, debug or review the agent system named by the current task. Component rules describe that target system; reading routes and engineering procedures guide your work on it. This separates product requirements from session instructions: actions remain governed by the current task and permissions, including when your own agent or harness is the target.

When deciding how information should steer the next step, use the [behavior-steering instinct map](../agent-harness-model-and-tools/SKILL.md#behavior-steering-instinct-map), then follow its carrier links for provenance, composition and lifetime requirements.

## Working method

1. Establish the task, caller authority, data visibility, expected duration, relevant model route, and what loss the user can tolerate. A fact that must survive is different from a detail that merely improves fluency. Identify the system of record for each.
2. Draw the current call from trusted instructions through current input, selected history, tool observations and output reserve. Label each carrier by authority, frequency, lifetime and source; tool output, recalled memory and quoted user text are data, not higher-priority instructions.
3. Choose the least stateful design that meets continuity needs. A bounded window can be sufficient when old context may be lost; durable raw history and compaction need explicit ownership, failure behavior and a restore contract. A cache is optional and never a reason to keep unsafe or stale data.
4. For each irreversible or externally visible effect, preserve stable logical-turn and operation identities at the host/action boundary. A summary is not evidence that an action happened; use durable receipts and reconcile ambiguity with the owner of the effect.
5. Define admission and failure before implementation: estimate the provider-effective request, reserve output, decide whether a product hard limit fails closed, and specify whether a missing page, stale version or failed reduction stops the run or permits a visibly degraded result. Never silently substitute missing data for an empty history.
6. Check real assembled requests and restored state, not merely a prompt template or a synthetic object. Trace a request and a failure path; inspect evidence and report route-specific, unmeasured behavior as such. For model-dependent measurements, define the comparison and obtain the applicable call authority first.

A useful analogy is a person's external working notes: a compact task record can free attention but may omit a qualification or preserve an obsolete claim. The analogous agent mechanism is a structured, source-linked continuation checked against authoritative state; unlike a person, the model has no reliable independent access to omitted context and a fluent summary does not prove fidelity. Preserve indispensable constraints mechanically when the task requires them rather than relying on the analogy or on a summary alone.

## Boundaries and acceptance

A context checkpoint identifies the source version and consumed boundary, continuation, required working state, and applicable policy; the host restores it only for the matching execution/session and must honor the ownership fence. An action receipt or current external state remains authoritative for side effects. A cache entry is an optimization of the model request, not an authority source or a substitute for authorization. A durable memory is a scoped, provenance-bearing data record; it must not acquire instruction authority merely because it was recalled.

Before accepting a design, demonstrate the normal call, a missing or changed source, an over-budget request, and the chosen recovery or refusal. If compaction is enabled, demonstrate a tool-call pair, a corrected fact, an indispensable constraint, repeated reductions and restore. If memory is enabled, exercise correction, forgetting and a stale producer. If caching is enabled, compare final provider-effective requests, counters and all cost components on the actual route. Optional checks drop out only when their premise is absent. Source and deterministic inspection support design claims; they do not establish provider behavior, deployed performance, quality or privacy coverage.
