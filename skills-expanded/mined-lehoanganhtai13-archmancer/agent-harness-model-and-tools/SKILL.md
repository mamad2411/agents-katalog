# Agent framework design

Use this skill to design the decision loop and its two immediate boundaries. The agent engine / harness selects the next step and determines whether work is complete; the model boundary translates a request and response faithfully; the action and tool boundary validates and executes an authorized proposal and reports what actually happened. These are logical responsibilities, not required services. Start with the smallest mechanism that satisfies the admitted task, authority, failure and evidence requirements. Read the system-wide [architecture](../agent-system-engineering/references/architecture.md), [flows](../agent-system-engineering/references/system-flows.md) and [engineering process](../agent-system-engineering/references/engineering-process.md) when the question crosses components.

**Scope.** Use this skill to design, build, debug or review the agent system named by the current task. Component rules describe that target system; reading routes and engineering procedures guide your work on it. This separates product requirements from session instructions: actions remain governed by the current task and permissions, including when your own agent or harness is the target.

## Behavior-steering instinct map

Choose the smallest carrier that reaches the decision with the right authority and lifetime; compare its token, cache and adherence costs rather than adding every layer.

For capability design or problem-solving with a human counterpart, first use supported research or established practice to describe effective human performance, connect it to an option/check, and test transfer against agent differences; carry over only applicable human limits and label unsupported explanations as hypotheses; skip routine use and purely technical mechanisms without a counterpart ([design rule](../agent-system-engineering/references/engineering-process.md#design)).

These model-visible levers do not grant action authority or prove an external effect. Preserve each contribution's source, scope and lifetime, retain enforcement at the responsible boundary, and verify a lever by inspecting the actual outbound request after all composition. Fit each lever to the agent's target model(s); when choosing prompting or tool-use practices, consult current provider guidance for the exact generation rather than assuming another model's results transfer.

## Route the task

1. **Design or plan:** write the outcome, actors, authority, workload, failure tolerance and observable acceptance evidence. Compare a single call, coded workflow and bounded agent; add a capability for a named behavior as an independent plugin, realized as middleware owning its needed tools, state, hooks, prompt contribution and configuration flag; add delegation or a gateway only for a named pressure, and defer registry/discovery machinery until independently authored or multiple deployable extensions require it. State which component owns each hand-off and the simplest acceptable failure response.
2. **Build a capability:** specify its purpose, activation, eligibility, typed inputs, dependencies, contributions, state ownership, ordering, failure behavior and checks. Resolve and validate the definition and backend requirements before constructing the executable. Trace the added action through authorization and its actual result; a model instruction is not enforcement.
3. **Debug a loop or false completion:** identify the actual execution, effective definition, model request, observed tool calls and terminal status. Distinguish model steps, physical calls, retries and resumed attempts. Locate the first divergence, then inspect the responsible boundary; a limit, timeout, unknown effect or empty answer is not success.
4. **Change models or clients:** inspect the effective adapter request and response, stream and tool-call forms, limits and usage. Preserve raw data needed for integrity and compare actual effective requests for cache claims. Qualify provider and client behavior on the selected route; examples from another route are not guarantees.
5. **Add tools or delegation:** define the target, input, principal, resource, operation, version, permitted effects, cancellation and result evidence. A child receives a self-contained bounded brief and no authority from model-authored text. Treat a pending or timed-out child as potentially running until its authoritative state is known.
6. **Optimize:** identify the measured bottleneck and freeze the comparison, safety constraints, costs, uncertainty and stopping rules before an experiment. Compare outcomes and losses by case as well as aggregate metrics. A smaller prompt, fewer graph steps or an apparent cache hit is not proof of an improved user outcome.
7. **Review:** follow each proposal to its enforcing executor and each completion to its supporting evidence. Check failure, cancellation, stale state, ambiguous outcomes and counterfactuals for the selected premises. Separate source inspection, local checks, deployment and observed runtime evidence.

## Boundaries and omissions

The [task and interaction boundary](../agent-runtime-and-interaction/references/task-and-interaction-boundary.md) admits calls and carries the desired outcome and caller authority; the [execution host](../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) schedules and keeps work live. The [context owner](../agent-context-and-state/references/context-and-state-management.md) decides information and state semantics; the [evidence owner](../agent-evidence-and-knowledge/references/evidence-and-knowledge-access.md) supplies visible and version-qualified external information. The [policy owner](../agent-configuration-and-delivery/references/policy-and-configuration.md) validates effective settings, while [trust and privacy](../agent-trust-and-privacy/references/trust-and-privacy.md) crosses every boundary. [Diagnostics and resource control](../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md) records what happened and what it cost; [delivery and operations](../agent-configuration-and-delivery/references/delivery-and-activation-evidence.md) connects changes to observed runs when deployment applies.

For a short in-process task, a bounded function can implement several of these responsibilities without a queue, distributed worker, plugin registry or durable memory; any capability added to it still keeps its plugin independence boundary and may be wired by a direct contribution list. When work must survive interruption, consult the host and context contracts before claiming recovery. Preserve a stable logical-turn identity across attempts and reconcile uncertain external effects before retry; verified idempotent replay is permitted for the same operation and body, otherwise stop for manual reconciliation. A model-facing example, proposed fix or historical observation is evidence only within its stated premise and scope.
