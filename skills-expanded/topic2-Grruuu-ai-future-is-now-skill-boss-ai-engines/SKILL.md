# 给一号位装四个引擎：全域感知 / 执行闭环 / 战略推理 / 组织文化

## R — 原文 (Reading)

> 仪表盘……更多是朝后看的……全域感知引擎要做的是把这面后视镜换成一块前挡风玻璃，让你能够盯住前方那个正在逼近的弯道。
>
> ……全域感知引擎让信息透明可信；执行闭环引擎的记录托住信任；战略推理引擎借助多个智能体替人模拟出那些令人惧怕的冲突；组织文化引擎能发现组织中真正有才华的人。

> — 李开复，第7章《给CEO装一套"老板AI"》

## I — 方法论骨架 (Interpretation)

组织是一套会失真的信息系统。往上走的每一层都在做三件事：把细节压缩成摘要（刺耳的信号在这一步消失）、只看得见自己那一块（碎片拼不成整图）、把坏消息"优化"成中性消息。所以坐在顶端的人，往往是掌握信息最少的那个人。

传统解法是加仪表盘。但仪表盘是后视镜——指标变红的时候，损失已经发生了。这个方法论换了个入口：不看被汇总过的第一版记录，直接读那些**已经存在、但从没参与过任何决策**的第二版记录——会议录音、文档编辑轨迹与批注、代码提交、客服工单、现场与空间数据。它们凌乱、零散、没被美化，因此可以充当前挡风玻璃。

在这个入口之上装四个引擎，各解一类一号位无法外包的活：

1. **全域感知**——绕开滤镜看清运营现实，核心动作是给每个你在乎的结果指标找出上游那些"还没变红"的过程痕迹；配套一个交叉核验法：把三份平时归不同的人管、从不会被同时打开的记录并排放，异常不在任何一份记录内部，而在它们之间的不一致里。
2. **执行闭环**——确保定下的事真的被做（本 skill 只做接口，机制细节交给 `commitment-ledger`）。
3. **战略推理**——重大决策落子前先辩论、再沙盘、换十组假设重推，目的不是更准的预测，而是摸清这个决定的边界与最脆弱的假设；并把预测原样存档，以后逐条对账。
4. **组织文化**——让"看不见的东西变得可见"（识别具体的人交给 `ruler-before-ranking`）。

有一条贯穿全篇的判据：**任何依赖个人意志的管理机制都有有效期，人在药效在，人走药效停**。这套东西的意义是把靠人换成靠系统。但作者本人也划了一条红线：它读的是工作记录不是隐私，看的是聚合模式不是某个人的某一句话；这条线守不住，它就从一双眼睛退化成一台监控器。本 skill 把这条红线升级为**执行前的强制闸门**（见 E 步骤 1 与 B 段）。

## A1 — 书中的应用 (Past Application)

### 案例 1：那个已经停止"呼吸"的重点项目
- **问题**：一个重点项目的每周进度汇报"都显示'按计划推进'"，没有任何人宣布过暂停。管理层没有任何理由起疑。
- **方法论的使用**：不看周报，去读周报上游的过程痕迹——书中读到的是"核心工程师的代码仓库最后一次进行实质提交是5周前；项目群里最新的消息停在2周前"，并且群里"有人问了一个问题，但没有人回答"。
- **结论**：书中原话是"虽然没有人宣布这个项目暂停，但它实际上已经停止了'呼吸'"。
- **结果**：管理者发现这件事时，距离原定交付日期还有 6 周——留下了纠偏窗口，而不是在交付日当天才知道。

### 案例 2："续约意向良好"的客户其实正在流失
- **问题**：季度报告显示某重要客户续约意向良好，销售预计下个月签约。
- **方法论的使用**：同时读三组沉睡数据——客服工单数量在过去 6 周增加了 3 倍且集中在同一个功能模块；一份工单标注"已解决"，下一份工单里同一个问题再次出现；关键联系人过去两个月没给客户回过一封邮件。
- **结论**：书中的对照句是"续约意向良好只是销售人员的判断，客户正在失去耐心是'老板AI'基于数据做出的判断"。
- **结果**：两个判断被并排摆上桌面，差异不需要任何人指出就自动呈现。

### 案例 3：三份从不同时打开的记录揪出"毒药合同"
- **问题**：交付团队加班数月，项目成本一再上升，却查不出问题的根源。在任何单一系统里看，一切正常。
- **方法论的使用**：把三种从来不会被同时打开的记录并排放——销售人员与客户的日常聊天记录、走完审批流程的正式合同、交付工单。
- **结论**：有人为了快速签单私下许诺免费定制、放宽验收标准、超额赔付，与正式合同完全不一致，风控人员全然不知。书中的原句是"3种记录单独看来都是正常的，将它们放到一起，就成了一份份签了字的'毒药合同'"。
- **结果**：成本黑洞的根因从"交付团队效率低"改判为"销售端的表外承诺"，处置对象完全换了一个。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **汇报与现实对不上**：所有报告都是好消息，但业绩、交付或客户侧的体感在恶化；用户想知道"我到底哪里被瞒着"。
2. **想确认某件事的真实状态**："这个项目到底还活着吗""这个客户是不是要走了""这条线的成本为什么一直在涨"——用户问的是状态真伪，不是要方案。
3. **异常查不出根源**：某个数字持续异常，各部门各自的系统里看都正常，用户已经查过一轮但没有结论。
4. **重大决策落子前**：进不进新市场、砍不砍一条业务线、对手降价跟不跟——低频、高代价、几乎不可逆，用户想在真下注前先推演。
5. **想给管理团队建"眼睛"**：CEO 或 CXO 想设计一套穿透层级的信息机制，问的是"该看哪些数据、怎么看"。

### 语言信号（用户的话里出现这些就应激活）

- "汇报上来的全是好消息，但我总觉得不对劲"
- "周报写着按计划推进，我不太信"
- "我怎么知道这个项目/这个客户是不是真的还在"
- "成本一直在涨，查了一圈查不出原因"
- "我是不是这家公司里知道得最少的那个人"
- "要不要进这个新市场？我想先推演一下再定"
- "有没有办法在指标变红之前就看到问题"

### 与相邻 skill 的区分

- 与 `commitment-ledger` 的区别：本 skill 回答"**现在真实情况是什么**"；`commitment-ledger` 回答"**他说过的话做到了没有**"。用户在问状态真伪 → 本 skill；用户在问某人的承诺、问责、考核口径、绩效结算 → 转 `commitment-ledger`。
- 与 `ruler-before-ranking` 的区别：本 skill 看的是**事**（项目、客户、成本、决策）；`ruler-before-ranking` 看的是**人**（谁厉害、谁被埋没、要不要提拔）。一旦问题变成"谁是最优秀的 N 个人"，立即转出。
- 与"数据看板 / BI 需求"的区别：用户要的如果是把已有指标做得更好看、更实时，那是后视镜的升级，本 skill 不适用；本 skill 的入口是**尚未进入报表的过程痕迹**。

## E — 可执行步骤 (Execution)

### 步骤 1（不可跳过的前置闸门）：先立边界，再碰任何数据

- **动作 A**：写下作者原书的四条读取边界——读工作记录不读私人通信 / 看聚合模式不揪某个人的某一句话 / 员工知道它的存在也知道使用边界 / 数据留在公司之内只为经营所用。
- **动作 B（书中缺失，本 skill 强制补齐的三条）**：
  1. **谁来审计**：指定一个不向 CEO 单线汇报的审计角色（如审计委员会、合规负责人 + 员工代表），写明审计频率与审计范围。
  2. **员工能否申诉**：当事人对基于这套数据得出的结论有异议时，向谁申诉、多久内答复、结论如何更正。
  3. **越界如何被发现**：这套系统自身的访问日志由谁看、什么样的读取属于异常、异常如何告警。
- **动作 C（法域合规）**：在中国大陆及欧盟等法域，读取员工通信与工作记录受《个人信息保护法》《劳动合同法》/GDPR 约束，实施前须完成合法性基础评估与员工告知。本 skill 不构成法律意见。
- **完成标准**：七条（四条边界 + 三条制度）全部落到纸面，每条有具名责任人与生效日期，且已向全员书面告知。
- **判停条件**：任意一条写不出具名责任人 → **停止，不进入步骤 2**，并如实告诉用户：这套东西的全部风险控制目前只剩 CEO 自律，而书中刚论证过靠人对抗人性不可持续。

### 步骤 2：按五类清单盘点你已经拥有的沉睡数据

逐类核对（**这五类都已经存在，不需要新建采集**）：

| # | 类别 | 它能说明什么 |
|---|---|---|
| 1 | 会议录音与转写稿 | 被轻描淡写带过的异议、散会前 5 分钟才冒出的补充、没进入正式纪要的顾虑 |
| 2 | 协作文档的编辑轨迹与批注 | 中途被删掉的疑虑、被忽视的不同意见、留在批注里从未被回应的问题 |
| 3 | 代码仓库提交记录 | 技术团队最真实的进度表：谁在实质提交、哪个模块最后一次改动在何时 |
| 4 | 客服工单与用户反馈 | 外部真实声音最集中处；同一问题被标"已解决"后有没有再出现 |
| 5 | 现场与空间数据 | 车间监控、门禁记录、会议室预约与实际使用、人员动线（作者另加：报销、差旅、系统使用日志） |

- **动作**：每一类回答三问——我们公司有没有这类记录？归谁管？过去 12 个月有没有任何一个决策用过它？
- **完成标准**：五类各有一行结论，且至少标出 2 类属于"存在，但从未进入过任何决策"。
- **判停条件**：若第 5 类涉及监控录像、门禁、动线，需在步骤 1 的边界文件里单列一条"是否纳入"的明示决定；未明示的默认不纳入。

### 步骤 3：全域感知引擎——给每个你在乎的结果指标找出上游的领先信号

- **动作**：列出 3 个你最怕出事的对象（一个重点项目 / 一个重点客户 / 一条重点业务线），为每个写出至少 2 个"还没变红"的过程痕迹并设定阈值。可直接照抄书中的两组模板：
  - 项目：核心贡献者最后一次实质提交距今 ≥ N 周 / 项目群最新消息距今 ≥ N 天 / 存在无人回应的提问。
  - 客户：工单量环比倍数 ≥ N / 同一模块重复工单 ≥ N 次 / 关键联系人最后一次回邮距今 ≥ N 天。
- **完成标准**：产出一张 3 行 × ≥2 列的信号表，每格都有一个具体数值阈值（"最近有点少"不算完成）。
- **判停条件**：若某个信号只能靠人工填报才能拿到，划掉——它已经回到被美化的第一版记录里了。

### 步骤 4：交叉核验——把三份从不会被同时打开的记录并排放

- **选记录的标准**：不是"哪份最权威"，而是"**哪几份平时归不同的人管、从不放在一起看**"。组织的部门边界就是信息盲区的边界。
- **动作**：针对一个查不出根源的异常，选 3 份分属不同部门的记录（典型组合：一线沟通记录 / 走完审批流程的正式文件 / 交付或履约工单），对同一笔业务逐条比对三方口径。
- **完成标准**：产出一张差异表，列明"哪一笔业务、三份记录各说什么、差在哪里"。
- **判停条件**：若三份完全一致，换一组记录再来一轮（最多 2 轮）；两轮都一致，则结论是"异常不在表外承诺上"，转去查流程或定价，不要继续加记录。

### 步骤 5：战略推理引擎——辩论 → 沙盘 → 换假设推 10 遍 → 存档

1. **辩论**：为待定决策设三个固定角色——一个只替客户说话，一个死盯这笔账在财务上算不算得过来，一个专门把最大的风险摆上台面。要求每一方除了论据，还必须自报"我这一方最脆弱的假设是哪一条"。原则句：决定应该建立在一场充分的争论之上，而不是一片客气的沉默之上。
2. **沙盘**：把争论结果放进推演，看销量、利润、现金流怎么变，对手大概率怎么接招，老客户流失会出现在第几个月。
3. **换假设重推 10 遍**：每遍换一组假设（需求弹性更高？宏观突然收紧？）。目标不是更准的预测，而是摸清这个决定的边界在哪里、关键风险是什么。
4. **存档**：决策落地当天把预测原样存档，约定一个季度或半年后逐条比对——存档必须发生在结果揭晓之前，否则复盘只会变成事后合理化。
- **完成标准**：拿到的不只是一个结论，还有完整的争论记录（每一方的论据 + 最脆弱的假设）和一份带日期、将来会被翻出来打脸的预测存档。
- **强制附注**：辩论的结论**不能直接当决定用**。理由见 B 段"作者的自相矛盾"——同一套训练机制在书里被相反地使用了两次。使用时必须人工检查：三个角色是否只是换了措辞的同一种主流意见。
- **作者自划的边界**：沙盘只给推演结果，"该不该冒险、愿意为什么付出代价"没有任何沙盘能替你回答。

### 步骤 6：组织文化引擎——只做到"发现异常模式"为止

- **允许的动作**：发现聚合层面的异常模式（例如：几起离职事件排在同一条时间线上是否指向同一个交叉点；两个团队是不是在互不知情地做同一件事）。
- **判停条件（硬）**：
  - 一旦问题变成"谁是最优秀的 N 个人""谁该被提拔""谁要走" → **停止，转 `ruler-before-ranking`**（该 skill 对第三问附有更严的使用约束）。
  - 一旦问题变成"他答应的事做到没有""考核该怎么算" → **停止，转 `commitment-ledger`**。
  - 一旦问题变成"某个具体的人对我有没有意见""他私下说了什么" → **停止，拒绝，并说明这已越过步骤 1 立下的第一条边界**。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **用户想定位到个人的言论或私人通信**。"把某人的私聊调出来看看他对我有没有意见""看看谁在群里说我坏话"——这类请求不属于本方法论的任何一步，应当直接拒绝，并指出作者本人划的第一条边界：读的是工作记录，不是人的隐私。
- **用户想找"谁想离职"以便提前处置**。这属于 `ruler-before-ranking` 第三问的范围，且该 skill 对它附加了严格约束（输出只能到一号位、只允许用于给机会，不允许用于防御性处置）。在本 skill 里一律拒绝。
- **步骤 1 的七条制度没有落地**。这不是"建议先做"，是判停条件。没有审计者、没有申诉通道、没有越界发现机制时继续往下走，产出的就是一台监控器。
- **用户要的是数据看板/BI/实时报表**。那是后视镜的升级，与本方法论的入口相反。
- **小微团队（十几个人、天天在一张桌子上）**。信息失真的三重机制需要层级才成立；十几个人的团队直接问比建系统快得多，此时本方法论是过度工程。
- **纯技术选型问题**（选哪个模型、上哪个平台）——那是另一类问题。

### 作者在书中警告的失败模式

- **退化成监控器**：作者亲笔写下"这条边界守不住，'老板AI'就会从一双眼睛退化成一台监控器，而监控器治不了人心，只会让想法藏得更深"。注意后半句——它的失败方式不是被员工反对，而是**让真实信息藏得更深**，也就是让这套系统自己失效。
- **仪表盘幻觉**：以为多加几块看板就解决了信息失真。作者明说被人性扭曲的信息失真"靠再多的仪表盘和商业智能都治不好"。
- **靠人对抗人性**：谷歌中国顺义别墅那次团建真的修复了团队（爬树建立信任、自我批评彼此批评，之后地图组和移动组联手，市场份额双双上升），但作者自己的结论是"人在，药效在；人走，药效停"——他离开后团队重新内斗，最终散了。桥水是同一条路的极限版本：25%～30% 的新员工在头 18 个月里离开，流失率约同行两倍，创始人交出掌舵权后机制被逐步弱化。
- **沙盘替不了下决心**：推演给的是地图，往哪里走仍然要人决定。

### 作者的盲点 / 时代局限

- **产品叙事耦合（三个 skill 共同）**：作者是零一万物创始人兼 CEO，书中第 6、7 章描述的"企业 AI 决策中枢"和"老板AI"正是他公司在售的产品，他在书中承认"我每天都在用，也开始卖给客户用"。本 skill 已把它抽象为**四引擎能力清单**，不绑定任何供应商——这也是作者本人给出的授权："你不一定非得用我的。"使用时请把它当作对照检查表，不是采购建议。

- **★ 监控器风险：保障全是原则性表述，没有任何制度化制衡。** 作者划的四条边界（读工作记录不读隐私 / 看聚合模式不揪个人 / 员工知情 / 数据留公司内）全部是原则宣示。书中没有回答三个问题：**谁审计这套系统？员工能否申诉？越界如何被发现？**
  而就在同一章，作者刚刚论证完桥水"靠人对抗人性"成本过高、不可持续——**靠 CEO 的自律来守这条边界，是同一种不可持续**。一个只由被监督者的上级自己执行的边界，在制度上不成其为边界。
  因此本 skill 把这三条设为步骤 1 的**执行前置闸门**：补不上，就不要开始。

- **法域合规风险**：在中国大陆及欧盟等法域，读取员工通信与工作记录受《个人信息保护法》《劳动合同法》/GDPR 约束（合法性基础、最小必要、告知同意、跨境传输等）。实施前须做合法性基础评估与员工告知。本 skill 不构成法律意见，涉及具体实施应咨询法务。

- **★ 作者的自相矛盾：同一个训练机制在两章里被相反地使用。**
  - 第 3 章论证智能体优于人类评审会时说：对抗式批评者模式的智能体"不会因为方案提出者的职级更高就换一种温和的说法。这种'制度性诚实'，是人类很难稳定做到的。"
  - 第 10 章论证 AI 不能替人拍板时说："尤其是经过对齐训练之后，它更偏向主流、稳妥、不冒犯……让AI替你拍板，它只会让你向共识靠近。"

  这两处指向同一件事——对齐训练——却得出相反结论。如果对齐让模型偏向不冒犯，那么"制度性诚实"就没有机制保障；**这直接动摇了步骤 5 里对抗式批评者与战略推理引擎的可靠性**。实践含义：三个角色的辩论必须被当作"生成候选论点的工具"，而不是"独立的反对意见来源"；使用时要人工检查它们是不是只是换了措辞的同一种主流意见，并至少保留一个由人扮演的反对者。

- **"沉睡数据里的信号是真信号"未经因果验证**：代码提交停滞 = 项目停摆、群聊沉默 = 风险积累、工单重开 = 客户流失，这些都是相关性叙事。一旦它们成为考核依据，就会被喂养（刷提交、刷群消息）。使用规则：这些信号只能用来**触发一次人的核查**，不能直接作为结论，更不能直接进考核。

- **样本偏向大型、有钱、数字化基础扎实的企业**：作者的一手材料来自世界 500 强董事长、全球前 20 矿业巨头。小微企业、低毛利行业、无 IT 底子的公司能否走通，书中没有验证。

- **全书没有一个 AI 造成实质损失的案例**：数据泄露、误判导致的错误人事处置、供应商锁定等下行风险几乎不被讨论。

### 容易混淆的邻近方法论

- **季度财报电话会测试**：那是判断一个 AI 项目值不值得做；本 skill 是判断公司现在实际发生了什么。先用本 skill 拿到真实状态，再用财报测试判断该不该投。
- **口袋否决识别**：当"看不清"的原因是中层的隐性抵抗（理由常伪装成"数据不干净""流程复杂"），那是归因问题，属于转型失败诊断的范畴；本 skill 提供的是证据来源，不提供归因框架。
- **企业 AI 决策中枢四拼图**：那是技术架构的缺口定位（模型/本体/实时上下文/操作系统）；本 skill 是一号位的使用场景。用户问"为什么我们的 AI 不好使" → 那是四拼图；问"公司现在到底怎么样了" → 才是本 skill。
- **传统的 BI / 高管仪表盘**：入口相反。仪表盘的输入是结构化的结果指标，本 skill 的输入是未被汇总的过程痕迹。
