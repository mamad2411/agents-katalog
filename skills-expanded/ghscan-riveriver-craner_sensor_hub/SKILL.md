# 固件测试用例编写规范

## 目标

测试文档的读者是不需要阅读源码的测试人员或实习生。每条用例必须能使用已烧录设备和明确列出的工具执行，并能根据可观察输出直接判定通过或失败。

## 固定结构

每份功能文档按以下顺序组织：

1. 测试范围与不包含内容
2. 测试工具、连接方式和开发者必须提供的输入
3. 结果状态定义
4. 验收概览表
5. 逐条详细用例
6. 缺陷证据要求
7. 附录测试执行表、数据记录表和缺陷提交表

每条用例必须包含：测试目的、前置条件、具体操作或命令、预期结果、判定标准和恢复步骤。概览表中的每个编号必须在详细章节中出现。

## 测试边界

- 不要求测试人员阅读源码、修改 DTS/Kconfig、重新编译、连接调试器或检查构建目录。
- 硬件阈值、Modbus 地址、OTA 镜像版本和产品默认值必须列为开发者输入，并提供填写位置。
- 破坏性操作，如恢复出厂、清除 Fault Dump、格式化存储和故障注入，必须标明风险并要求负责人授权。
- 不同传感器必须使用独立文档，不把编码器、IMU、风速仪或其他类型混在同一条用例中。

## 常用工具

- MobaXterm Telnet：执行串口之外的 Shell 命令。
- MQTTX：订阅 `<short_id>/sh/tx`，向 `<short_id>/sh/rx` 发布 Shell 命令。
- `ping`、`Test-NetConnection`、Wireshark、`iperf3`：网络验证。
- OpenModScan 或等效客户端：Modbus TCP 验证。
- `mcumgr`：OTA 上传、测试和确认。

## 结果状态

统一使用：`通过`、`失败`、`阻塞`、`不适用`。失败必须有缺陷编号；阻塞必须记录阻塞原因；不适用必须由测试负责人确认。

## 详细用例写作要求

命令必须使用可复制的代码块，topic、端口、地址、payload 和期望输出必须明确。等待、重启、断电、网络恢复等动作必须写出时间或完成条件。修改数据的用例必须有恢复步骤。

## 附录要求

每份文档至少包含：

- 一张逐条执行记录表；
- 一张功能数据或前后状态记录表；
- 一张缺陷提交最小信息表。

表格的结果字段保持空白，交给测试人员填写。

## 领域规则

- 参数持久化：先确认 `param status`，再执行 `param set`、`param save`、重启和 `param list`；Modbus 寄存器持久化放在 Modbus TCP 文档。
- MQTT Shell：默认 topic 为 `<short_id>/sh/rx` 和 `<short_id>/sh/tx`；订阅响应后再发布命令；普通系统日志不应持续进入 Shell topic。
- Modbus TCP：必须明确 Unit ID、端口、0-based/1-based 地址换算、功能码和开发者提供的寄存器表。
- OTA：必须明确当前版本、目标版本、镜像文件、传输方式、升级后确认和回滚预期。
- 故障注入：只允许专用测试固件和台架环境，生产固件不得执行 panic/oops 注入。
- 网络与老化：必须填写测试时长、流量、并发数、丢包/延迟阈值和电源条件。
