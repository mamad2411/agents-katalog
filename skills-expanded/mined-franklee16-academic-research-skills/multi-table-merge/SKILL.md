# 多表合并策略

## R — 原文 (Reading)

> "It's also common to find data values about a single type of observational unit spread out over multiple tables or files. These tables and files are often split up by another variable, so that each represents a single year, person, or location. As long as the format for individual records is consistent, this is an easy problem to fix."
>
> "Datasets often involve values collected at multiple levels, on different types of observational units. During tidying, each type of observational unit should be stored in its own table."
>
> — Hadley Wickham, Section 3.5 & 3.4

---

## I — 方法论骨架 (Interpretation)

多表合并策略处理两种情况:

**情况 A: 一种观察类型分散在多文件 (合并)**
数据按某个变量(年/人/地区)拆成了多个文件, 每个文件结构相同。修复合并为三步: (1) 读取所有文件为列表, (2) 给每个文件添加来源列(通常是拆分变量的值, 如文件名含年份), (3) 纵向堆叠成一个表。前提: 各文件结构一致。

结构不一致时更复杂: 变量名不同、缺失列、编码差异 — 需要先逐一标准化, 再合并。

**情况 B: 一个表里混了多种观察类型 (拆分)**
一张表里同时有不同粒度的实体(如歌曲元数据 + 每周排名)。这导致事实冗余(同一首歌的 artist/time 在每周重复)。修复: 拆成多张表, 每张对应一种观察类型, 用外键关联。

两个方向看似相反(一个合并、一个拆分), 但核心原则相同: **每种观察类型一张表**。合并和拆分都是为了实现这个原则。

## A1 — 书中的应用 (Past Application)

### 案例 1: Baby Names 数据集 (合并)
- **问题**: 美国社保局提供的婴儿名字数据, 129 年 × 每年一个文件, 共 129 个文件
- **方法论的使用**: Step 1 — 列出目录下所有匹配的 CSV 文件; Step 2 — 用文件名(含年份)作为来源标识; Step 3 — 循环读取并纵向合并为一个数据框
- **结论**: 只要各年文件结构一致, 合并是机械性操作
- **结果**: 单一表 (year, name, sex, count), 覆盖 129 年

### 案例 2: Fuel Economy 数据集 (复杂合并)
- **问题**: EPA 燃油经济性数据, 1978–2008 每年一个文件, 但格式经历了 4 次重大变化(变量不同、列名不同、缺失值约定不同)
- **方法论的使用**: 不能简单堆叠。需要: (1) 按格式版本分组, (2) 每组分别标准化列名/类型, (3) 取各组交集变量, (4) 合并。这是"结构不一致"合并的典型案例
- **结论**: 当文件结构随时间漂移, 合并前必须先做格式归一化; 这往往占整个工作的 80%
- **结果**: 单一表覆盖 30 年 50,000+ 车辆, 可做跨年代分析

### 案例 3: Billboard 排行榜 (拆分)
- **问题**: 每首歌的 artist/time 在每周排名行中重复 — 歌曲和排名是两种观察类型混在一张表里
- **方法论的使用**: 拆成两张表: 歌曲表(id, artist, track, time, genre) + 排名表(id, date, rank, week); id 是外键
- **结论**: 拆分消除了冗余, 确保每个事实只出现一次; 分析时通过 id join 回来
- **结果**: 两张表可独立维护, 且消除了不一致风险(如同一首歌的 artist 名字在不同行写法不同)

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 下载了一组按年份/月份/地区拆分的 CSV/Excel 文件, 需要合并成一个数据集
2. 发现一个表里有明显的数据冗余(同一实体的属性在多行重复), 想拆分规范化
3. 多人协作, 每人维护一个 Sheet, 需要汇总
4. 不同来源的数据表格式相似但有细微差异(列名不同、多几列少几列), 需要统一后合并
5. 数据随时间积累, 早期和晚期格式不同, 需要做历史数据整合

### 语言信号 (用户的话里出现这些就应激活)

- "有一批文件需要合并/拼接"
- "每年/每月/每个省一个文件"
- "多个 Excel sheet 要合在一起"
- "这个表里重复数据太多了, 需要拆分"
- "数据分成了好几部分, 怎么合起来"
- "不同年份的格式不太一样"

### 与相邻 skill 的区分

- 与 `tidy-data-diagnosis` 的区别: 诊断 skill 识别模式 4/5 的存在; 本 skill 执行具体的合并/拆分
- 与 `messy-to-tidy-pipeline` 的区别: 本 skill 处理的是多表/多文件问题(模式 4/5); `messy-to-tidy-pipeline` 处理单表内的 reshape(模式 1/2/3)。但二者经常顺序配合

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **判断问题方向**
   - **合并方向**: 数据分散在多文件/多表 → 需要堆叠
   - **拆分方向**: 一个表混了多种实体 → 需要分离
   - 完成标准: 明确方向和目标表结构

2. **合并方向: 读取 + 标准化 + 堆叠**
   - 列出所有待合并的文件/表
   - 检查结构一致性: 比较列名、列类型、缺失值约定
   - 若不一致: 识别差异, 制定映射规则 (统一列名 → 补缺失列 → 统一类型)
   - 添加来源列 (从文件名/表名提取拆分变量的值)
   - 纵向堆叠
   - 完成标准: 合并后行数 = 各文件行数之和; 无数据丢失; 来源列正确填充

3. **拆分方向: 识别观察类型 + 分表 + 建外键**
   - 识别表中不同的观察类型 (哪些列属于哪种实体)
   - 识别冗余: 哪些属性在每行重复但实际属于另一种实体
   - 为每种观察类型创建独立表, 分配唯一 id
   - 用外键关联各表
   - 完成标准: 每个事实只出现在一张表中; 外键关联完整

4. **验证**
   - 合并方向: 抽查 N 行, 确认来源列正确, 无数据丢失
   - 拆分方向: 确认 join 回来能还原原始信息; 检查无不一致(同一实体的属性在不同表中是否矛盾)
   - 完成标准: 数据完整性校验通过

5. **交付**
   - 输出合并后的表 或 拆分后的多表
   - 说明表间关系和外键
   - 标注格式差异的处理方式(若有)

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **数据库 join (两个已有整洁表的横向合并)**: 这是标准的数据操纵, 用 merge/join 即可, 不需要本 skill
- **单表内的 melt/pivot**: 属于 `messy-to-tidy-pipeline`
- **实时流数据的窗口合并**: 本 skill 假设批量操作, 不处理流数据
- **跨系统数据集成 (ETL)**: 超出范畴 — 本 skill 处理结构问题, 不处理接口/协议问题

### 作者在书中警告的失败模式

- **盲目堆叠不一致的文件**: 如果各文件列名/类型不同, 直接堆叠会导致数据错位或大量缺失。必须先检查一致性
- **拆分后无法还原**: 拆表后分析通常需要 denormalize (join 回来), 但大多数统计工具不直接支持关系操作, 可能需要额外的合并步骤
- **忽略文件名中的变量**: 合并多文件时, 文件名通常包含重要的分类变量(如年份), 不提取就丢失了

### 作者的盲点 / 时代局限

- 论文以 R 为背景, 用 plyr::ldply 做循环合并; 如今推荐用 purrr::map_dfr 或 pandas concat, 但逻辑相同
- 未讨论大文件合并的内存问题: 当单个文件就很大时, 需要分批或使用数据库作为中间层
- 未讨论 schema drift (随时间演化的表结构) 的系统性处理框架 — 只是简单提到"需要分别处理"

### 容易混淆的邻近方法论

- **数据库 JOIN**: 横向合并 (添加列), 本 skill 的合并方向是纵向堆叠 (添加行)
- **数据仓库 ETL**: 更宽泛, 包括抽取、转换、加载; 本 skill 只涉及"合并/拆分"这一个转换子问题
- **数据湖分区**: 概念类似 (按变量分文件存储), 但数据湖侧重存储策略, 本 skill 侧重如何把分区文件读回为分析用表
