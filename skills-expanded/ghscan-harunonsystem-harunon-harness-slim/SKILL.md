# Derive Optimal Solution

ユーザーが設定した問題空間に閉じず、問いを再構成し、関係する案を比較して推奨を返す汎用プロトコル。ドメイン非依存。

## 使うとき

次のいずれかに当たるときに使う。

- 問題の捉え直し、上流の要因、または本質的な問いの再構成
- 複数の案・方針・戦略の比較と推奨
- 提案を複数の観点から評価し、トレードオフを整理すること
- 実装依頼の目的と既存コードを確認しても、受け入れ条件・運用負荷・可逆性に影響する異なる解法が複数残ること

依頼文にある手段が合意済みの制約か、目的達成の一案かを区別する。合意済み仕様や既存パターンで解法が決まる実装、routine details、既知のバグ原因の診断には起動しない。既知のバグ原因は `diagnosing-bugs` を使う。依頼で許可された情報とスコープを守り、無関係な機密情報を扱わない。

## 進め方

### 問いと境界を確認する

求められている成果、対象の粒度、制約、権限、時間軸を確認する。観測された症状と構造上の問題を分け、必要なら上流の要因まで遡る。ただし、技術の問いを組織の方針へ変えるなど、依頼の粒度やスコープを勝手に広げない。

### 問題を再構成する

事実と仮定を分け、相手の提案が所与としている前提を確認する。上流を変えれば問題が消えるか、制約を変えずに解けるか、時間・主体・境界・抽象レベルを変える意味があるかを、依頼に関係する範囲で検討する。情報が足りず判断が変わる場合だけ、判断に必要な質問をする。

### 関係する案を出す

問題を解く場所、抽象レベル、時間軸のいずれかが異なる案を比較対象にする。ユーザーの案や現状維持を含め、延期・縮小・やらない案は意味がある場合に候補にする。案の数を満たすために無関係な案を足さない。

### 帰結とトレードオフを比べる

文脈に合う評価軸だけを選ぶ。たとえば根本性、堅牢性、耐久性、コスト、可逆性、明快性などから、判断に効くものを使う。スケール、変更、引き継ぎ、時間経過、例外、関連領域への波及は、必要な範囲で帰結を予測する。比較は質的に行い、点数の合計で順位を決めない。

独立した調査や視点分担が実質的に役立つ場合は、利用可能な委譲手段を使ってよい。自動並列化を前提にせず、同じ調査を重ねない。得られた結果は本体で統合する。

### 推奨する

主要なトレードオフ、選ばなかった案の理由、不確実性を示して推奨を一つに絞る。条件付きの順序や段階的な案が適切ならその形で示す。実装依頼から起動した場合は、ユーザー固有の未決事項が残らなければ推奨に沿って実装を続ける。別スコープの行動を、依頼されていないのに結論へ混ぜない。

## 最終チェック

- 依頼された粒度とスコープに答えているか。
- 既存の事実と仮定を区別し、根拠のない確定をしていないか。
- ユーザーの目的に効く案を比較し、重要な帰結を見落としていないか。
- 不足情報がある場合、判断に必要な箇所だけを明示しているか。

このチェックは品質確認であり、固定のステップ数・質問数・案数・点数を満たすことを目的にしない。

## 出力

必要な節だけを使う。

```markdown
## 問いの再構成
- 相手が設定した問題: ...
- 観測している症状と構造: ...
- 本質的な問い: ...

## 比較した案
- 案 A: ...
- 案 B: ...

## 帰結とトレードオフ
- ...

## 推奨
...

## 不確実性 / 確認事項
...
```
