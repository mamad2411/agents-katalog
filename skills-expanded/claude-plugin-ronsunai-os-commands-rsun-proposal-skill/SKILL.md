# rsun-proposal — 提案到簽約 SOP

估價完成只是起點。提案是一場叙事——從「客戶的問題」出發，到「為什麼是我們來解決」，最後到「現在就開始」。

**適用時機：**
- 估價（`/rsun-estimate`）完成後，準備向客戶提案
- 客戶要求提案簡報 / 正式報價前
- 議價過程中需要回應客戶的壓價

---

## 提案前準備（15 分鐘）

在見客戶前，確認以下：

```
□ Lean Canvas 已完成（你真的理解客戶問題）
□ PRD 已與客戶對齊（功能範圍一致）
□ 估價已完成（WBS + 人月）
□ 競品研究做了嗎？（知道客戶的其他選項）
□ 客戶決策者是誰？（付錢的人 ≠ 使用的人 ≠ 決策者）
□ 客戶的預算大概在哪個範圍？（先探）
```

## 提案簡報結構（5 段式）

### Slide 1-2：開場 — 我們理解你的問題

**不要先介紹公司。先說客戶的問題。**

```
「根據我們的討論，你們現在面對的核心挑戰是：
  1. [問題 1，具體數字化：「每次審核需要 3 天」]
  2. [問題 2]
  3. [問題 3]

這讓你們 [損失或痛苦：每月浪費 X 小時人力 / 流失 X% 業績]。」
```

> 技巧：用客戶自己說過的話，不是你創造的語言。他會點頭。

### Slide 3-4：解方 — 我們怎麼解決

```
「我們設計的解方分三個核心模組：
  1. [功能 1] → 解決 [問題 1]
  2. [功能 2] → 解決 [問題 2]
  3. [功能 3] → 解決 [問題 3]

上線後，你們預期：
  - [成功指標 1]：從 X 改善到 Y
  - [成功指標 2]」
```

> 技巧：成功指標要量化，不要只說「提升效率」。

### Slide 5：為什麼是我們

**不要列公司簡介。列我們獨特的能力。**

```
「為什麼找容晟而不是其他團隊：
  1. 我們做過 [類似案例] — [一句結果描述]
  2. [技術專長] — 直接影響這個案子的執行效率
  3. 我們的交付方式：[草稿審核制 / 分期付款 / 固定週 review]
```

> 技巧：如果有做過類似的案子，這是最強的說服力。

### Slide 6-7：報價 — 三方案呈現法

**永遠呈現三個方案，不要只呈現一個數字。**

```
方案 A — 核心版（P0 功能）
  功能：[列 P0]
  報價：NT$ XXX,XXX
  上線：X 週

方案 B — 標準版（P0 + P1）← 你希望客戶選的
  功能：[列 P0 + P1]
  報價：NT$ XXX,XXX  ← 標注「推薦」
  上線：X 週

方案 C — 完整版（P0 + P1 + P2）
  功能：[列所有功能]
  報價：NT$ XXX,XXX
  上線：X 週
```

> 心理學：呈現三個選項，客戶注意力集中在「比較」而非「要不要」。大多數人選中間。方案 C 讓方案 B 顯得合理。

**付款分期（必須主動說）：**
```
簽約款 30%：簽約時 — NT$ XXX,XXX
開發款 40%：核心功能完成 — NT$ XXX,XXX
驗收款 30%：客戶驗收通過 — NT$ XXX,XXX
```

### Slide 8：下一步 — 降低行動門檻

**不要說「請考慮一下」。說清楚下一步是什麼。**

```
「如果方向 OK，我們建議：
  1. 本週確認方案選擇
  2. 下週簽合約 + 支付簽約款
  3. [日期] 正式開工

我們 [週五] 前先發一份正式報價單給你，
你這邊有什麼問題，這週內可以直接問我。」
```

## 議價回應腳本

### 情境 1：「太貴了，可以便宜嗎？」

**不要直接降價。先問是什麼讓他覺得貴。**

```
回應 A — 縮減範圍：
「我理解預算考量。如果要在同樣品質下降低費用，
 最直接的方式是縮減方案——我們先做 [P0 核心功能]，
 [P1 功能] 留到第二期。這樣可以控制在 NT$XXX,XXX 以內。
 你覺得哪些功能是絕對必要的？」

回應 B — 說明價值：
「這個報價對應的是 [X 週] 的完整開發工時。
 如果用你們自己招 [N 個工程師] 做，
 光薪資就是 NT$XXX,XXX / 月。
 我們幫你省掉招聘、管理、試錯成本。」

回應 C — 分期降低門檻：
「我理解一次付清的壓力。我們的付款是分期的：
 [說明分期結構]。這樣每期的現金流壓力就降低很多。」
```

> **不要說的話：** 「我幫你問問看能不能打折」（你的報價沒有底氣）

### 情境 2：「我再考慮看看 / 要問一下 OO」

**這通常意味著有疑慮，不是真的在考慮。要挖出疑慮。**

```
「當然，請問是有什麼特別的考量讓你想再想想？
 是功能範圍、時程、還是預算方面？
 我希望能直接幫你解答，省你來回的時間。」
```

### 情境 3：「XX 公司報比你們便宜」

**不要降價競爭。要問清楚他們在比什麼。**

```
「我理解。可以問一下，他們的報價包含什麼？
 [等對方說]

 我們的報價包含 [列清楚：設計稿 / 測試 / 部署 / 維護期]。
 如果去掉 [某項]，我們也可以調整。
 但如果範圍一樣，我需要理解品質和交付保障的差異。
 
 我的建議是，讓他們也出一份 PRD，
 你就知道兩個方案在說同一件事嗎。」
```

### 情境 4：「能不能先做一部分，看看效果？」

**這可以接，但要設好條件。**

```
「可以。我們可以先做 Phase 1（[P0 核心功能]），
 驗證效果後再繼續 Phase 2。

 但有幾個前提：
 1. Phase 1 的報價是 NT$XXX,XXX（非整體打折）
 2. Phase 2 如果要繼續，優先權給你，但需要重新排程
 3. Phase 1 完成後，Phase 2 的報價可能因通膨或工時調整

 這樣你是否可以接受？」
```

## 合約重點條款

簽合約前，確認以下條款都清楚（如果客戶有自己的合約，也要檢查這些項目）：

### 必須有的條款

```
1. 功能範圍（Scope）
   → 附上 PRD 或功能清單作為附件，明確 In Scope / Out of Scope

2. 付款條件
   → 分期比例、付款觸發條件、逾期罰則

3. 交付物定義
   → 「什麼叫做完成？」的明確標準（對應 Acceptance Criteria）

4. 需求變更條款
   → 「超出 PRD 範圍的需求，需要另行估價」要明確寫進去

5. 著作權 / IP 歸屬
   → 驗收款付清後，著作權轉移給客戶；驗收款未付清前，著作權在容晟

6. 保固期
   → 驗收後 X 週內的 bug 免費修正（不含新功能）

7. 終止條款
   → 客戶無故終止：已完成工作包按比例收費，最少 50%
```

### 風險信號（客戶合約的地雷）

```
⚠️ 沒有明確 Out of Scope → 容易被要求無限加功能
⚠️ 驗收標準模糊（「客戶滿意」）→ 要求改成具體功能 Checklist
⚠️ 付款與「上線」掛鉤 → 改成「核心功能完成」，避免環境問題卡付款
⚠️ 智慧財產權歸屬不清楚 → 明確要求加上 IP 條款
⚠️ 保固範圍包含「優化建議」→ 限定保固僅為 bug fix
```

## Follow-up 節奏

提案後的跟進是成交率最大的槓桿之一：

```
提案當天：發正式報價單（PDF）
提案後 2 天：確認有收到，問有無問題
提案後 5 天：（如無回應）「我們這週有個時段可以 30 分鐘線上 Q&A，你方便嗎？」
提案後 10 天：最後一次跟進，說明排程壓力（誠實的版本）

「我們 [日期] 後可能有另一個案子進來，
 如果你這邊希望確保 [日期] 開工，
 建議本週前確認。如果時程調整了，我會重新告知。」
```

> 不要說謊製造緊迫感，但如果真的有排程壓力，說出來是合理且有效的。
