对 `HEAD` 与用户提供的固定点之间的 diff 进行双轴审查:

- **规范** —— 代码是否符合本仓库文档中记载的编码规范?
- **规格** —— 代码是否忠实地实现了原始 issue/规格说明?

两条轴线以**并行子代理**的方式运行,避免相互污染上下文,然后由本 skill 汇总它们的发现。

issue 跟踪工具应当已经提供给你 —— 如果缺少 `docs/agents/issue-tracker.md`,请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所说的任何内容都可以是固定点 —— 提交 SHA、分支名、标签、`main`、`HEAD~5` 等。如果用户没有指定,就向他询问。

将 diff 命令一次性确定下来:`git diff <fixed-point>...HEAD`(三点语法,即与 merge-base 比较)。同时用 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

在继续之前,确认固定点可以解析(`git rev-parse <fixed-point>`)且 diff 非空。无效的引用或空 diff 应当在此时失败 —— 而不是在两个并行子代理内部才失败。

### 2. 确定规格来源

按以下顺序寻找原始规格说明:

1. 提交信息中的 issue 引用(`#123`、`Closes #45`、GitLab `!67` 等)—— 通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果都找不到,询问用户规格在哪里。如果用户说没有规格,**规格**子代理将跳过,并在报告中注明"无可用规格"。

### 3. 确定规范来源

仓库中任何记录代码应当如何编写的文档,例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库文档记载的内容之外,规范轴线始终附带下面的**坏味道基线** —— 一组固定的 Fowler 代码坏味道(《重构》第 3 章),即使仓库没有任何文档记录也同样适用。有两条规则约束它:

- **仓库规范优先。** 有文档记载的仓库规范始终胜出;当仓库规范认可基线会标记的写法时,抑制该坏味道。
- **始终是判断性意见。** 每种坏味道都是带标签的启发式提示("疑似 Feature Envy"),绝不是硬性违规 —— 并且,与此处的任何规范一样,凡工具已经强制执行的都跳过。

每种坏味道都按*它是什么* → *如何修复*的格式列出;将其与 diff 逐一对照:

- **Mysterious Name(神秘命名)** —— 函数、变量或类型的名字无法揭示它做什么或存什么。→ 重命名;如果想不出诚实的名字,说明设计本身含糊。
- **Duplicated Code(重复代码)** —— 相同的逻辑形态出现在变更的多个代码块或文件中。→ 提取公共形态,两处都调用它。
- **Feature Envy(依恋情结)** —— 一个方法访问其他对象的数据多过访问自己的数据。→ 把该方法移到它所依恋的数据上。
- **Data Clumps(数据泥团)** —— 同样几个字段或参数总是一起出现(一个亟待诞生的类型)。→ 把它们打包成一个类型,传递该类型。
- **Primitive Obsession(基本类型偏执)** —— 用基本类型或字符串代替一个本应拥有自己类型的领域概念。→ 给这个概念一个专属的小类型。
- **Repeated Switches(重复的 switch)** —— 针对同一类型的 `switch`/`if` 级联在变更中反复出现。→ 用多态替代,或用两处共享的一张映射表。
- **Shotgun Surgery(霰弹式修改)** —— 一个逻辑变更迫使 diff 中许多文件被零散修改。→ 把一起变化的东西收拢到一个模块中。
- **Divergent Change(发散式变化)** —— 一个文件或模块因多个互不相关的原因被修改。→ 拆分,使每个模块只因一个原因而变化。
- **Speculative Generality(夸夸其谈的通用性)** —— 为规格中并不存在的需求添加抽象、参数或钩子。→ 删掉它;内联回去,直到真实需求出现。
- **Message Chains(消息链)** —— 调用方不应依赖的长链式导航 `a.b().c().d()`。→ 把这段遍历隐藏在第一个对象的一个方法背后。
- **Middle Man(中间人)** —— 一个几乎只做转发的类或函数。→ 砍掉它,直接调用真正的目标。
- **Refused Bequest(被拒绝的遗赠)** —— 子类或实现者忽略或覆写了它继承的大部分内容。→ 放弃继承,改用组合。

### 4. 并行启动两个子代理

**规范子代理的提示词** —— 包含:

- 完整的 diff 命令和提交列表。
- 第 3 步中找到的规范来源文件清单,**外加完整粘贴的第 3 步坏味道基线** —— 子代理没有其他途径获得它。
- 任务说明:"报告 —— 按文件/代码块(在相关处)列出 —— (a) diff 违反文档规范的每一处:引用该规范(文件 + 具体规则);(b) 你发现的任何基线坏味道:点名并引用对应代码块。区分硬性违规与判断性意见 —— 违反文档规范可以是硬性违规,但基线坏味道永远是判断性意见,且有文档记载的仓库规范优先于基线。跳过工具已经强制执行的内容。400 字以内。"

**规格子代理的提示词** —— 包含:

- diff 命令和提交列表。
- 规格的路径或已获取的内容。
- 任务说明:"报告:(a) 规格要求但缺失或只完成了一部分的需求;(b) diff 中未被要求的行为(范围蔓延);(c) 看似已实现但实现方式看起来不对的需求。每条发现都引用规格的原文。400 字以内。"

如果规格缺失,跳过规格子代理,并在最终报告中注明。

### 5. 汇总

将两份报告分别放在 `## Standards` 和 `## Spec` 标题下呈现,原样引用或仅做轻微整理。**不要**合并或重新排序发现 —— 两条轴线是有意分开的(见_为什么是两条轴线_)。

最后用一行总结收尾:每条轴线的发现总数,以及_每条轴线内部_最严重的问题(如有)。不要跨轴线选出唯一的"最严重" —— 这正是两条轴线分开所要防止的重新排序。

## 为什么是两条轴线

一次变更可能通过一条轴线却在另一条上失败:

- 代码符合所有规范,但实现的东西是错的 → **规范通过,规格失败。**
- 代码完全实现了 issue 的要求,但破坏了项目约定 → **规格通过,规范失败。**

分开汇报可以防止一条轴线掩盖另一条。
