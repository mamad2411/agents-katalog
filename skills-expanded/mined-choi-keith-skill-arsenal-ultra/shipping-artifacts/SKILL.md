# 交付工件:让 AI 构建的代码可评审的文档

## 目的

AI agent 写代码很快,但不会留下关于*意图*的持久记录——系统应该做什么、谁被允许做什么、密钥放在哪里、哪些规则真正得到了验证。没有这些记录,任何人(以及任何审计 agent)都无法判断代码是否可以安全发布。本 skill 定义了恢复可评审性所需的一小组文档。

这些文档存放在仓库根目录的 `documentation/` 下,写给两类读者:人类评审者和下一个 AI 编码 agent。它们是后续每次审计的**预期状态**那一半——安全或性能审计的质量,取决于它能拿来和代码对比的意图记录有多好。

## 文档集的组织方式

这套文档**不是**一份固定清单——它由一小部分**核心**文档加上仅在对应能力存在时才添加的**条件**文档组成。

- **核心文档** —— 每个可评审的应用都有这些面,因此必须始终产出。
- **条件文档** —— 仅当应用确实具备该能力时才包含。如果不具备,就在 `architecture.md` 里写一行说明(“无定时任务——无 `cron.md`”),而不是编造一份空文档。可评审性来自一份诚实的地图,而“我们不做 X”也是地图的一部分。
- 大多数文档由 `/document-app` 从代码逆向生成。唯一的例外是 `tests.md`,它由 `/derive-tests` *从其他文档推导而来*——它是验证地图,而不是对某个子系统的描述。

对当前状态要毫不留情地诚实,但不必疑神疑鬼。目标是准确的地图,而不是一纸健康证明。每份文档都简短、以表格和要点为主,并略过泛泛的理论。

## 核心文档

每条:文件 · 一句话目的 · 必须捕获的内容 · 评审者如何使用。

1. **`architecture.md`** —— 系统是什么,以及各部分如何组合在一起。
   - 必须捕获:产品概述 + 关键假设;技术栈;认证/会话/声明(claims)如何端到端流转;信任边界(如 service-role 与客户端);一份简短的**已知风险/假设**清单(每条都有代码中的对应位置支撑,而不是泛泛的检查清单);以及一个收录其他所有已产出文档的“相关文档”索引。
   - 评审者用途:根文档——其他一切都从这里交叉引用。

2. **`flows.md`** —— 真正行使权限并产生副作用的旅程。
   - 必须捕获:每个关键流程,以 操作者 + 前置条件 + 成功结果 的形式;跨 UI → 服务端 → 数据 → 任务 → 外部服务 → agent 的逐步序列;**每个受保护步骤的授权检查**(哪个 claim/角色/scope、作用于哪个资源,以及预期的*拒绝*情形);**信任边界的跨越**(浏览器→服务端、服务端→外部服务、任务→应用、agent→工具、webhook→应用);每个步骤引起的状态变化和副作用(写入、邮件入队、任务触发、对外调用)。
   - 评审者用途:静态的 `permissions.md` 矩阵无法展示的运行时视图——授权在*哪里*、以*什么顺序*执行,以及在哪里可能被跳过。
   - **反 PRD 规则:** 不涉及权限、数据完整性、外部副作用、资金、隐私或运维安全的流程不属于这里。这是一份安全/运维地图,不是功能规格说明书。

3. **`permissions.md`** —— 谁被允许做什么。
   - 必须捕获:角色/claims;scope 的来源(token 还是数据库);资源 × 操作 × 角色矩阵;哪些表启用了行级安全(row-level security),哪些依赖代码强制检查。
   - 评审者用途:访问控制审计拿来对比代码的基线。`flows.md` 展示其动态过程,这份是静态参照。

4. **`variables.md`** —— 配置与密钥,映射到风险。
   - 必须捕获:一张 名称 · 使用方 · 作用域(服务端/客户端) · 来源 · 轮换 · 风险 的表格;明确确认没有任何密钥被打包到客户端;上线前检查清单。
   - 评审者用途:密钥/PII 泄露面,以及事故响应时的轮换计划。

5. **`tests.md`** —— 验证地图:哪些记录在案的规则真正被检查了,哪些只是提议,哪些没有任何检查。
   - 必须捕获,分成三个清晰分隔的部分,避免地图产生“假绿”:
     - **现有覆盖** —— *当前*就在仓库中的测试,每条都绑定到它所锁定的规则(让地图反映现实,而不是愿望清单)。
     - **提议的测试** —— 推荐但尚未编写的用例,按**测试类型**标注(自动化单元/集成测试 · 受控实时测试 · 人工评审)。
     - **缺口** —— 完全没有任何验证的记录在案规则,按跨越它们会暴露什么来排序。
   - 每行包含:用例 → 规则 → 预期行为(包括拒绝/负向情形) → 证据来源(文档 + 代码) → 状态(现有 / 提议 / 无)。还要注明哪些检查是 CI 强制的、哪些会拦截合并到 `main`。
   - 评审者用途:“文档 == 实现”的落地形式——它展示其他文档声称的每条规则,今天是否真的被测试锁定、只是被提议,还是完全没有验证。
   - 由 `/derive-tests` 产出(而非 `/document-app`),因为它是从其他文档和现有测试套件推导出来的,而不是从某个子系统直接读出来的。

## 条件文档(仅在对应能力存在时包含)

6. **`emails.md`** —— 系统发送的每一条通知。*仅当应用发送事务性或自动化邮件时包含。*
   - 必须捕获:队列 → 处理器 → 服务商 的路径;模板及其接受的变量;重试/退避行为;发送失败时去哪里排查。
   - 评审者用途:发现未校验的模板输入和 PII 暴露边界。

7. **`cron.md`** —— 所有定时任务以及如何安全地运维它们。*仅当存在定时或后台任务时包含。*
   - 必须捕获:清单表(任务 → 调度 → 函数 → 密钥 → 限制 → 重试);每个任务如何保持幂等;内部调用如何认证;在哪里查看最近的运行记录。
   - 评审者用途:发现可伪造的触发器和无上限的后台任务。

8. **`seo.md`** —— 单页应用如何处理 SEO 和社交分享预览。*仅当存在公开/可被索引或面向爬虫的路由时包含。*
   - 必须捕获:预览方案(静态 meta / 预渲染 / 边缘 HTML);路由 → 是否需要 SEO → 仅限公开数据 的表格;动态元数据如何消毒;爬虫与真人的分流。
   - 评审者用途:抓出仅限公开数据的违规,以及爬虫路由上的元数据注入。

9. **`automation.md`** —— 内嵌 agent 及其他自动化路径。*仅当应用内嵌 AI agent、LLM 工作流、工具调用、webhook 或外部自动化时包含。*
   - 必须捕获,按每个自动化/agent 记录:触发方式 + 负责人 + 自动运行还是需审批后运行;它可读取的输入,以及**它可调用的确切工具/API**(工具面本身就是硬性护栏);**引导**(prompt)放在哪里,与**非 prompt 的硬性护栏**如何分工;返回给应用的**输出契约**(schema、校验、失败处理);**应用拥有的副作用与 agent 提出的建议**的区分;以及控制手段——审批关卡、审计/时间线日志、速率限制、重试、紧急开关。
   - 评审者用途:让隐藏的自动化路径现形,并划清 agent *提议*与应用*强制*之间的界线——这是现代 AI 构建应用中风险最高的面。

## 备注

- 每份产出的文档都在 `architecture.md` 的“相关文档”一节中添加对自身的引用,使整套文档保持可发现。
- 跳过任何不适用的条件文档,并用一行说明,而不是编造内容。
- 让这些文档远离示例和现成模板——它们描述的是*这个*系统,而不是通用方法。
- agent 运行上下文文件(`CLAUDE.md` / `AGENTS.md`)是*另一种*工件——从这些文档派生的指令,而不是系统文档。它由 `/ship-check` 在交接步骤产出,不在本 skill 范围内。
- `tests.md` 由 `/derive-tests` 产出;其余由 `/document-app` 产出。
- 不要包含“更新日期”行;文件历史才是事实来源。
