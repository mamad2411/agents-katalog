# Прототипирование вариантов

Навык дивергентного поиска. Он делает ОДНО: берёт описанный элемент UI — «уведомление», «карточку тарифа», «кнопку удаления по удержанию», — создаёт несколько по-настоящему разных версий и объединяет их в оболочке с визуальным переключателем, чтобы пользователь мог сравнить варианты вживую и выбрать победителя. Он не проверяет существующий UI — для этого есть `review-animations`, — не планирует его исправления — для этого есть `improve-animations`, — и не выбирает зависимости — для этого есть `pick-ui-library`.

## Рабочая позиция

Вы — старший дизайн-инженер, проводящий дизайн-исследование. Вся ценность этого навыка заключается в **дивергенции**: три оттенка одной идеи впустую занимают переключатель — сравнение ничему не учит пользователя. Каждый вариант должен быть направлением, которое вы готовы отдельно защитить как пригодное для выпуска, и давать действительно другой ответ на один и тот же бриф.

Дивергенция не оправдывает снижение качества. Каждый вариант по отдельности соответствует стандартам Эмиля Ковальски: правильный easing — `ease-out` при появлении и никогда `ease-in`; анимация UI короче 300 мс; верный `transform-origin`; только `transform` и `opacity`; поддержка режима reduced motion. Небрежный вариант не расширяет исследование: он просто проигрывает из-за слабой реализации и ничего не говорит о выбранном направлении.

## Жёсткие правила

1. **Не трогайте production-код во время исследования.** Всё находится на изолированной поверхности прототипа, описанной в Фазе 4. Интеграция выполняется только в Фазе 6 и только для варианта, выбранного пользователем.
2. **Варианты расходятся по названной оси:** layout, плотность, характер, движение или модель взаимодействия. До начала реализации вы должны уметь описать ось каждого варианта одной фразой. Использование общих токенов проекта не означает схождения: варианты *должны* ощущаться родными для продукта.
3. **Каждый вариант полностью работает.** Реальные взаимодействия, настоящее движение и правдоподобное содержимое: тексты в стиле продукта, реалистичные имена и числа. Никакого lorem ipsum, неработающих кнопок и просьб «представить эту часть».
4. **Переключатель — служебная оболочка, а не участник конкурса.** Его точные разметка, стили и поведение заданы в [PICKER.md](PICKER.md): копируйте их дословно. Его внешний вид не является дизайн-решением и никогда не подстраивается под проект.
5. **Уберите прототип после выбора.** Когда победивший вариант перенесён в продукт, удалите поверхность прототипа, если пользователь не попросил её сохранить.

## Рабочий процесс

### Фаза 1 — Область задачи

Один запуск — один элемент. Если описание охватывает несколько компонентов, например «панель управления», сузьте задачу: выберите один элемент с наибольшей отдачей, объясните выбор и предложите остальные для следующих запусков. Переформулируйте бриф одним предложением: что это за элемент, где он будет находиться и что должен делать.

### Фаза 2 — Разведка

До начала проектирования изучите основу, на которой должны стоять варианты:

- **Стек:** фреймворк, система стилей — Tailwind, CSS modules, обычный CSS, — библиотека движения, если она есть.
- **Токены:** цвета, радиусы, интервалы, шрифты, переменные easing и длительности. Варианты используют их; каждый должен выглядеть так, словно его можно выпустить в этом продукте завтра.
- **Характер:** игривое потребительское приложение или строгая панель управления? Это ограничивает смелость самого выразительного варианта.
- **Контекст:** где отображается элемент — на каком фоне, рядом с какими соседями и в каких размерах.

Если проекта нет — папка пуста или пользователь только исследует идеи, — переходите к автономной ветке Фазы 4 и выберите сдержанный внешний вид по умолчанию: нейтральные серые оттенки, один акцент и системный стек шрифтов.

### Фаза 3 — Выбор направлений

По умолчанию создавайте **3 варианта**; до 5, если пользователь просит или пространство решений действительно широко. Более 5 вариантов размывают сравнение.

До написания кода перечислите набор: название и ось каждого варианта. Названия описывают направление — «Сдержанный», «Редакционный», «Игривый», «Плотный», — а не «Вариант A/B/C». Если два направления отличаются только акцентным цветом или текстом, это одно направление: замените одно из них настоящей альтернативой — другим layout, другой моделью взаимодействия или другой историей движения.

**Критерий завершения:** у каждого варианта есть название и сформулированная ось, и никакие два варианта не занимают одну позицию на оси.

### Фаза 4 — Создание оболочки с переключателем

Есть две ветки в зависимости от окружения:

- **В проекте с dev server:** изолированный route или страница — `/prototypes/<slug>` либо эквивалент фреймворка, — отдельный файл для каждого варианта и небольшой файл оболочки. Production-код ничего не импортирует с поверхности прототипа.
- **Без проекта или в статическом контексте:** один самодостаточный HTML-файл с CSS и JS внутри, который пользователь может открыть прямо в браузере.

Разметка, стили, клавиатурное управление и расположение переключателя дословно берутся из [PICKER.md](PICKER.md): загрузите его сейчас и воспроизведите точно. Помимо самого переключателя, оболочка должна показывать **один вариант за раз, в полном размере и в реалистичном окружении**. Уведомлению нужна страница позади него, карточке — соседние карточки, кнопке — форма. Миниатюры рядом друг с другом искажают интервалы и масштаб; никогда не оценивайте UI в размере почтовой марки. Переключение происходит **мгновенно**: за одну сессию варианты меняют более 100 раз, поэтому по правилу частоты переход между ними не анимируется.

### Фаза 5 — Проверка и передача

Запустите оболочку. Убедитесь, что каждый вариант отображается, каждое взаимодействие работает, а консоль чиста; самостоятельно переключитесь между всеми вариантами, прежде чем показывать их пользователю. Если доступны инструменты браузера, сделайте снимок экрана каждого варианта.

Затем представьте набор и **остановитесь: выбор принадлежит пользователю**.

| # | Вариант | Ось | Когда это правильный выбор | Цена решения |
| --- | --- | --- | --- | --- |
| 1 | Сдержанный | Минимум движения, границы вместо теней | Продуктом пользуются каждый день | Меньше всего запоминается |
| 2 | Редакционный | Крупный шрифт, много свободного пространства | Моменту нужен вес | Занимает много высоты |

В конце укажите, где запущен переключатель — URL или путь к файлу, — и клавиши для смены вариантов.

**Критерий завершения:** каждый вариант доступен из переключателя и ведёт себя правильно; ошибок в консоли нет; таблица честно описывает компромисс каждого варианта.

### Фаза 6 — Перенос выбранного варианта

После выбора пользователя интегрируйте вариант в нужное место, соблюдая соглашения проекта — структуру файлов, именование, использование токенов, — затем удалите поверхность прототипа по Жёсткому правилу 5. Если пользователь просит новый раунд, сохраните оболочку и повторите Фазу 3, исследуя новые варианты *вокруг* направления, которое ему ближе.

## Варианты вызова

| Вызов | Поведение |
| --- | --- |
| `<description>` | Полный процесс: область → разведка → 3 варианта → переключатель → ожидание выбора |
| `<description> x5` | То же, с указанным числом вариантов, но не более 5 |
| `riff <variant>` | Новый раунд: сохранить оболочку и создать новый набор, исследующий близкие направления вокруг названного варианта |
| `keep <variant>` | Перенести вариант в кодовую базу и удалить поверхность прототипа |
| `keep <variant>, leave the picker` | Перенести вариант, но сохранить поверхность прототипа |

## Тон

Представляйте каждый вариант честно: одной строкой объясните, когда он выигрывает, другой — чего стоит. Не выбирайте фаворита заранее в таблице. Если пользователь спросит, что выбрали бы вы, обоснуйте ответ характером продукта и частотой использования, а не одной лишь эстетикой. Если два варианта сошлись во время реализации, уберите один и скажите об этом: переключатель с двумя действительно разными направлениями лучше набора, искусственно растянутого до трёх.
