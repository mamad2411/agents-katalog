# Живой и отзывчивый интерфейс

Проектировать движение как поведение системы, а не как декоративный ролик. Хороший интерфейс мгновенно отвечает на ввод, следует за указателем, продолжает движение с набранной скоростью и позволяет изменить решение в любой момент.

Материал основан на общих принципах прямого манипулирования и адаптирует идеи публичных докладов о fluid interfaces к веб-платформе. Названия компаний используются только для указания источника; навык не является официальным руководством какой-либо платформы.

## Главный критерий

Элемент с прямым управлением должен:

1. ответить в момент нажатия;
2. двигаться вместе с указателем без разрыва;
3. на отпускании сохранить скорость жеста;
4. прийти к предсказуемой точке покоя;
5. позволить пользователю снова захватить элемент до завершения движения;
6. оставаться понятным без анимации.

## 1. Сокращать задержку обработки ввода

- Давать визуальный отклик на `pointerdown`, а не ждать `click`.
- Во время drag или swipe обновлять положение непрерывно и 1:1.
- Не ставить искусственные таймеры, debounce и блокировки между жестом и откликом.
- Измерять INP и длительные задачи: плавная кривая не исправит зависший главный поток.

```css
.action:active {
  scale: 0.96;
}

@media (prefers-reduced-motion: no-preference) {
  .action {
    transition: scale 100ms ease-out;
  }
}
```

## 2. Сохранять точку захвата

Объект не должен прыгать центром под курсор. Запоминать смещение от границы элемента до места захвата и использовать Pointer Events с `setPointerCapture()`.

```js
element.addEventListener('pointerdown', (event) => {
  element.setPointerCapture(event.pointerId);
  const bounds = element.getBoundingClientRect();
  const grabOffset = {
    x: event.clientX - bounds.left,
    y: event.clientY - bounds.top,
  };

  // Сохранить несколько последних position + timestamp для расчёта скорости.
});
```

У drag-сценария должен быть клавиатурный эквивалент: кнопки перемещения, изменение порядка стрелками или понятная альтернативная форма.

## 3. Делать переходы прерываемыми

Пользователь может изменить намерение в середине анимации. Поэтому:

- не блокировать ввод до `transitionend`;
- начинать новый путь с текущего видимого значения, а не с прежней целевой точки;
- при смене направления переносить текущую скорость;
- для жестовых элементов выбирать пружину или API, допускающий изменение цели во время движения;
- для независимых осей X и Y использовать независимые значения движения.

CSS transitions подходят для hover, раскрытия и других простых переключаемых состояний. Жёсткий `@keyframes` плохо подходит элементу, который можно схватить во время движения.

## 4. Настраивать пружину через характер движения

Начинать с критически затухающей пружины без перелёта. Добавлять небольшой bounce только после физического жеста, который действительно передал импульс.

| Сценарий | Характер | Ориентир |
| --- | --- | --- |
| Обычное перемещение | без перелёта | коэффициент затухания `1,0`, отклик `0,3–0,4 с` |
| Карточка после flick | лёгкий перелёт | коэффициент затухания около `0,8`, отклик `0,3–0,4 с` |
| Sheet/drawer | быстрый и собранный | коэффициент затухания `0,8–1,0`, отклик около `0,3 с` |

Пружина не имеет фиксированной «длительности»: она успокаивается по физическим параметрам. Если API предлагает `bounce` и `duration`, считать их дизайнерским приближением, а не точной физической моделью.

```js
import { animate } from 'motion';

animate(panel, { y: 0 }, {
  type: 'spring',
  bounce: 0,
  duration: 0.4,
});
```

Не добавлять Motion только ради короткого fade: для него достаточно CSS.

## 5. Передавать скорость от жеста к анимации

Записывать несколько последних событий, рассчитывать скорость в px/s и передавать её в пружину. Без этого на отпускании виден шов: объект сначала останавливается, затем начинает новый путь.

Некоторые API требуют относительную скорость:

```text
relativeVelocity = gestureVelocity / (targetValue - currentValue)
```

Проверять контракт конкретной библиотеки: многие веб-API принимают абсолютную скорость.

## 6. Проецировать точку покоя

При flick выбирать цель не по месту отпускания, а по прогнозируемой конечной точке. Благодаря этому короткий быстрый жест может переместить элемент дальше, чем медленный длинный.

```js
function project(initialVelocity, decelerationRate = 0.998) {
  return (initialVelocity / 1000) * decelerationRate / (1 - decelerationRate);
}

const projected = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projected);
animateTo(target, { velocity: releaseVelocity });
```

Ограничивать результат допустимым диапазоном и тестировать медленный drag, быстрый flick и смену направления перед отпусканием.

## 7. Сохранять пространственную логику

- Вход и выход проводить по одному пути.
- Popover раскрывать от триггера, а не из геометрического центра экрана.
- Выдвижную панель возвращать к той границе, из которой она появилась.
- При развороте зеркалить траекторию и не создавать скачок скорости.
- Для русских интерфейсов не путать физическое «слева/справа» с логическим «начало/конец»: если понадобится RTL, использовать логические CSS-свойства.

## 8. Подсказывать будущий результат

Промежуточные кадры должны объяснять, куда движется объект. Карточка, которую переносят в колонку «Согласовано», может слегка принять цвет и форму будущего состояния ещё до отпускания. Не показывать успех до подтверждения операции сервером.

## 9. Смягчать границы

У края применять возрастающее сопротивление вместо жёсткой остановки:

```js
function rubberband(overshoot, dimension, constant = 0.55) {
  return (overshoot * dimension * constant) /
    (dimension + constant * Math.abs(overshoot));
}
```

После отпускания возвращать объект в допустимую область. Сопротивление — это подсказка, а не разрешение сохранить недопустимое значение.

## 10. Корректно различать жесты

- Tap: отклик при нажатии, действие при отпускании, отмена при уходе за разумную границу.
- Drag: небольшой порог движения около `8–10px`, затем отслеживание 1:1.
- Сначала параллельно распознавать все допустимые жесты, а после определения намерения отменять остальные.
- Не использовать события вида `swipeleft`, которые сообщают только итог и скрывают непрерывный путь.
- Не добавлять double-tap туда, где он задержит обычный tap без заметной пользы.

## 11. Следить за кадрами и стоимостью

Анимировать прежде всего `transform` и `opacity`. Не применять `will-change` постоянно; включать его только перед тяжёлым движением и убирать после. Проверять на слабом устройстве и с искусственным замедлением CPU.

Высокая частота кадров не гарантирует качество: слишком большой шаг между кадрами всё равно создаёт стробирование. Уменьшать расстояние и скорость раньше, чем добавлять размытие.

## 12. Использовать глубину по назначению

Полупрозрачность и blur должны показывать иерархию, а не быть фоном по умолчанию.

- Предусматривать для `backdrop-filter` непрозрачный запасной вариант.
- На сложном фоне повышать контраст текста и поверхности.
- Не складывать несколько слабоконтрастных стеклянных слоёв.
- Для модальной задачи применять scrim; для параллельной панели сохранять контекст без полного затемнения.
- Чем больше поверхность, тем сильнее может быть отделение тенью, но не обязательно blur.

```css
.toolbar {
  background: rgb(250 250 252 / 0.94);
  box-shadow: 0 1px 0 rgb(15 23 42 / 0.08);
}

@supports (backdrop-filter: blur(1rem)) {
  .toolbar {
    background: rgb(250 250 252 / 0.72);
    backdrop-filter: blur(1rem) saturate(140%);
  }
}
```

## 13. Сочетать каналы обратной связи

Звук, вибрация и движение должны:

1. иметь очевидную причину;
2. срабатывать синхронно с изменением состояния;
3. использоваться только в значимых точках: подтверждение, ошибка или фиксация в точке привязки.

Не полагаться на вибрацию: API поддерживается не везде, а пользователь мог её отключить. Всегда оставлять текстовый или визуальный сигнал.

## 14. Уважать reduced motion и контраст

Движение включать через `prefers-reduced-motion: no-preference`. В режиме reduced motion:

- заменять slide, zoom, parallax и bounce мгновенным состоянием или коротким opacity-переходом;
- не запускать фоновые циклы;
- сохранять цвет, иконку и текст статуса;
- не отключать загрузочные индикаторы и функциональный прогресс.

```css
.sheet {
  opacity: 1;
}

@media (prefers-reduced-motion: no-preference) {
  .sheet {
    transition: translate 220ms cubic-bezier(0.2, 0, 0, 1),
                opacity 160ms ease-out;
  }
}

@media (prefers-reduced-transparency: reduce) {
  .toolbar {
    background: Canvas;
    backdrop-filter: none;
  }
}
```

## 15. Настраивать типографику для кириллицы

- Использовать системный стек или шрифт с полноценной кириллицей и явной лицензией.
- Не переносить отрицательный `letter-spacing` с латинского макета без проверки: кириллица часто выглядит плотнее.
- Проверять реальные строки «На согласовании», «Провести и закрыть», ФИО и длинные названия организаций.
- Для крупных заголовков применять более плотный line-height, для пояснений — более свободный.
- Размеры текста и связанные отступы задавать в `rem`, чтобы интерфейс выдерживал увеличение до 200%.

```css
:root {
  font: 100%/1.5 system-ui, -apple-system, "Segoe UI", sans-serif;
}

.display {
  font-size: clamp(2rem, 7vw, 4.5rem);
  line-height: 1.02;
  letter-spacing: -0.015em;
  text-wrap: balance;
}
```

## 16. Проверять базовые принципы

Перед полировкой ответить:

- **Цель:** какую задачу пользователя поддерживает движение?
- **Контроль:** можно ли отменить, прервать или вернуть действие?
- **Предсказуемость:** одинаково ли выглядящие элементы ведут себя одинаково?
- **Гибкость:** работает ли сценарий с мышью, клавиатурой, сенсорным вводом и увеличенным текстом?
- **Простота:** не скрывает ли эффект важную информацию?
- **Качество:** выдержаны ли состояния загрузки, отсутствия данных, ошибки, работы без сети и reduced motion?

В рабочем интерфейсе 1С ценить скорость повторяющихся операций выше выразительности. Hover-состояния строк таблицы и переключение вкладок должны быть почти мгновенными; более заметное движение допустимо для редких событий — первого появления, успешного завершения или смены контекста.

## 17. Проверять в работающем прототипе

1. Собрать интерактивный вариант, а не только статический макет.
2. Проверить обычную скорость и замедление до 10%.
3. Прервать каждое движение в начале, середине и перед завершением.
4. Пройти сценарий клавиатурой.
5. Включить reduced motion и повышенную контрастность.
6. Проверить ширину 320 пикселей и масштаб 200%.
7. Испытать на реальных русских данных, включая длинные значения.

## Краткая памятка

| Потребность | Решение |
| --- | --- |
| Обычное UI-движение | критически затухающая пружина без bounce |
| Flick после жеста | небольшой bounce и передача скорости |
| Точка приземления | прогноз по скорости, затем ближайший snap point |
| Прерывание | старт с текущего видимого значения |
| Drag | Pointer Events, capture и сохранение grab offset |
| Граница | прогрессивное сопротивление |
| Reduced motion | статическое состояние или короткий cross-fade |
| Частая операция | мгновенный отклик или ≤ 150 мс для цвета/opacity |
| Кириллица | системный шрифт, реальные строки, ручная проверка межбуквенного интервала |
