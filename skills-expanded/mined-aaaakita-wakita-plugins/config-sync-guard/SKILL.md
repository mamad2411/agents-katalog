# 跨环境配置同步守卫

适用对象：有管理后台可在线编辑的 DB 数据（提示词、章节、配置项）。这类数据入库后**不再是迁移种子的副本，而是用户的工作成果**。

## 铁律：先定新旧方向，再谈同步

"目标环境与源不一致"有两个方向：**目标陈旧**（该推过去）或**目标领先**（用户在目标上刚改过，推过去就是事故）。

- 不一致 ≠ 陈旧。"长度/内容和种子不一样"什么都不能说明。
- 判方向看 `updated_at`、用户最近操作时段、binlog/审计记录，**不看内容像不像种子**。
- 方向不确定时：停下来问用户，或先给目标做快照再动手。覆盖用户未备份的在线编辑是最难挽回的事故类型。

## 同步 Checklist（按顺序执行）

### 1. 双侧快照

源（如本地 dev）和目标（如生产）各导出完整数据集到临时文件。导全量，不导"你以为改过的那几行"——用户可能在任何字段上动过手（本项目实例：用户一上午改了 9 个章节 + 4 个报告配置 + 1 个系统提示词 + 2 个固定块，还有改名和新建）。

### 2. 逐字段 diff 并打印确认

- 按**业务键**匹配记录（name、output_key+allowed_types 签名），**绝不按自增 id**——两环境的 id 序列独立生长。
- 改名场景用签名兜底匹配（实例：生产"传播分析" → 本地"专题传播分析"，按 `(output_key, sorted(allowed_types))` 签名认出是同一行，执行更新而非新建，避免重复行）。
- diff 覆盖所有可变字段：content/intro/sort_order/is_enabled/allowed_types，不只是主文本。
- 把 diff 清单打出来看一眼再写。源侧明显是测试垃圾的行（如 intro="测试"、content="不要生成本章节"）也要同步——用户建的，保持镜像一致并知会用户，不自作主张过滤。

### 3. 写目标：走管理 API，不直接改库

- 用目标环境的管理后台 API（认证走正常登录），让校验、缓存失效、日志都生效。
- 顺序：先更新/新建明细行 → 再调排序端点（全量有序 id 列表）→ 最后写引用它们的配置（外键按"源 id → 目标 id"映射表重映射，实例：chapter_refs 存的是 id 列表）。
- 新建的记录若要保持"禁用"态：API 通常默认创建为启用，创建后补一次 toggle。
- 系统键值类配置只推"已定制"的段；两侧都用默认值的段不动。

### 4. 回读验证

写完后**从目标环境重新拉取全量**，与源快照做同一套 diff，输出必须是 ALL MATCH。不要信写入时的 200 回包——回包只证明请求被接受，不证明最终状态一致。

### 5. 清理与留痕

- 删除：目标机器上的 token 文件、两侧快照副本、临时授权。token 就是钥匙，不留痕。
- 向用户报告：同步了哪些行（新建/更新/改名识别）、验证结果、以及"图纸 vs 房子"遗留——迁移种子若仍是旧内容，全新环境会盖出旧房子，提醒用户是否把当前内容回写成新种子（这是独立决策，不默认做）。

## 反模式（都出过事）

- ❌ 看目标内容"不像种子"直接拿种子覆盖 → 覆盖了用户当天定稿（2026-09-04 本项目实例，靠 binlog 才找回，恢复手法见 `mysql-binlog-recovery` skill）
- ❌ 按 id 匹配两环境的行 → 错行覆盖或错位引用
- ❌ 改名行当新建 → 重复行 + 旧行引用残留
- ❌ 只验证写入回包不回读 → 静默不一致
