# 隐性失效功能排查（Silent Failure Audit）

核心命题：**「失败了也不影响主流程」的防御代码，一旦每次都失败，就是无人知晓的摆设。** 单元测试可能和实现错在同一个假设上互相背书，日志因被刻意吞掉而永远干净。唯一的真相来源是生产数据的「成功痕迹」。

## 何时触发

- 用户怀疑某功能"好像从来没真正起作用"
- 审计任务提到兜底、回写、补偿、通知、重试、同步、心跳类链路
- 审查含 `try/except` 且 except 只记日志的改动
- 例行体检：列出系统所有防御性吞异常点，逐个验证"发生过吗"

## 排查步骤

### 1. 先查生产数据的「成功痕迹列」，别看日志

每个此类功能必然在某张表/某个字段留下成功痕迹（回写时间戳、事件行、计数器、状态翻转）。直接查：

```sql
SELECT success_marker_col, COUNT(*) FROM feature_table;
-- 全零 / 全 NULL = 从未成功。这比读一万行日志快得多，也硬得多。
```

全零即确诊「从未生效」，直接跳到第 3 步找原因。非零但量异常少（对比调用频率）= 间歇失效，去日志里按时间窗捞跳过/警告记录。

### 2. 定位「静默吞异常」的 catch 块

从功能入口反向 grep 到副作用落库点之间的每一层，重点检查：

- `except Exception:` 后只 `logger.warning/info` 不重抛、不置失败状态、不告警
- 「宁多发勿漏发」「失败只记日志不阻塞主流程」之类注释——它们是合理设计，也是 bug 的藏身之处
- finally 块里依赖的资源在其执行时**可能已被上层回收**（连接池关闭、event loop 关闭、浏览器 teardown、事务回滚后）——生命周期顺序错误是此类 bug 的高发区

### 3. 复现并抓到真实现场

在测试/本地环境真实触发一次完整流程（不是单元测试），观察：
- 副作用是否真的发生（数据库行、文件、外发请求）
- 被吞的异常现场长什么样（往往需要临时把 swallow 改成 raise 才能看见）

**注意单元测试的盲区**：若测试 fixture 少了某个关键字段，实现里的 dict 展开/默认值逻辑会走另一条分支，测试全绿但生产行为完全不同。审查 fixture 是否镜像生产返回的**完整字段**；修复后做负向验证（旧实现跑新测试必须失败）。

### 4. 修复原则

- 把副作用挪到资源回收**之前**（finally 里、with 块内、teardown 前），加幂等标记防重复
- 吞异常可以保留，但给「从未成功」留一个可观测口：计数器、metrics、或至少 error 级日志配告警
- 修复后必须在真实环境端到端验证一遍副作用落地，单测通过不算数

### 5. 横向排查同类

确诊一例后，同模式扫全仓：
- grep 相同的 swallow 注释/写法（`失败.*不阻塞`、`只.*日志`、`non-critical`、`best effort`）
- 同作者/同模块/同设计模式的防御链路
- 其他平台/通道的同款功能（常见：A 平台实现了某机制，B/C 平台根本没有）

## 输出格式

 findings 报告按链路列出：功能 → 成功痕迹列的查询结果 → catch 块位置（文件:行号）→ 失效根因 → 修复建议 → 是否同类扩散。只报「痕迹全零/量异常/资源已回收」三类高置信问题，不罗列普通错误处理。

## 反面教材速查（真实案例）

- Cookie 回写写在 `close()`，而 `async with playwright` 在 close() 前已 teardown → dump 每次必败，生产回写字段全 NULL 数年无人知
- 测试 fixture 缺 `status` 字段，`{"status": "success", **result}` 的默认值幸存 → 与实现的覆盖行为互相背书
- 通知事件注册了但触发条件里状态枚举写错（success vs completed）→ 事件零触发
