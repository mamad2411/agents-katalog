# 单向同步反模式审查

## 核心反模式

**设计文档里说"A 和 B 双向同步"，代码里实际只实现了"单向"：只 A→B 或只 B→A，
但函数名听起来像完整闭环。审查时如果只看"函数是否存在 + 函数体有持久化调用"，
会漏掉这种偏差。**

典型场景：
- cookie 同步：设计说 DB 与浏览器 profile 双向同步 → 实际只 DB 写入，浏览器没收到
- 配置热更新：设计说改 DB 配置立即生效 → 实际只更新 DB 没通知内存缓存
- 缓存与源数据：设计说写 DB 同时失效 Redis 缓存 → 实际只写 DB 没删 Redis
- 状态同步：设计说主进程状态变更通知 Worker → 实际只写了状态表没发消息

## 审查方法：画数据完整生命周期

不要只看"函数是否存在 + 是否调了持久化"。要画数据的完整生命周期：

```
[来源] → [中转: DB] → [中转: 文件/缓存] → [中转: 内存/进程] → [实际使用]
                              ↑
              当审查时缺一环就要追问"谁把它送下去"
```

### 三个关键追问

**追问 1：写方真的把数据送到了所有下游吗？**

如果数据只写到了 DB，那下游（缓存、文件、浏览器 profile、内存状态）谁来同步？
答案若是"下一次启动时自动加载"——那启动时怎么读 DB 的？显然不会自动读。

**追问 2：读方的数据来源是什么？**

当某个操作需要读取数据时，它从哪里读？
- 如果是「文件/缓存自动恢复」，那文件/缓存谁来填？
- 如果是「用户操作时写入」，那自动化路径（导入、定时任务）有没有写入？

**追问 3：跨进程/跨实例一致性如何保证？**

当多个进程或服务实例共享同一份逻辑数据时：
- 谁负责在修改后通知其他进程？
- 通知机制是推送还是轮询？轮询间隔多久？
- 如果通知丢失，有没有兜底机制？

## 泛化场景速查表

| 场景 | 数据流 | 常见缺失环节 |
|------|--------|-------------|
| Cookie/Token 同步 | 用户导入 → DB → 浏览器 profile → 页面加载 | DB → 浏览器 profile 的注入环节缺失 |
| 配置热更新 | 管理后台 → DB → 内存缓存 → 业务逻辑 | DB → 内存缓存的刷新/通知缺失 |
| 缓存失效 | 业务写入 → DB → 缓存删除 → 下次读重建 | 缓存删除环节缺失（写了 DB 没删缓存） |
| 状态同步 | 主进程 → 状态表 → 消息队列 → Worker | 消息队列发送缺失（只写表没发消息） |
| 文件同步 | 上传 → 临时目录 → 持久存储 → CDN | 持久存储 → CDN 的推送缺失 |
| 搜索索引 | 数据变更 → DB → 搜索引擎索引 | 索引更新缺失（只改 DB 没重建索引） |

## 审查时的反面信号

| 信号 | 含义 |
|------|------|
| 函数名含 `import`/`refresh`/`sync`，但函数体只有 DB 写操作 | 高概率只做了单向 |
| 设计文档出现"双向同步""实时生效""自动更新"等词 | 需要验证每个方向是否都有代码路径 |
| 代码里有 `repository.save()` 但没有后续的 `cache.delete()`/`notify()`/`inject()` | 链路不完整 |
| 测试只在单进程中跑，没有跨进程验证 | 同步问题在单进程测试中不可见 |
| 用户反馈"导入了但没生效""改了配置但没变化" | 典型的单向同步症状 |

## 审查流程

1. **找到设计文档中的"同步"声明**：搜索"同步""更新""刷新""生效"等关键词
2. **画出数据生命周期**：列出所有涉及该数据的存储/缓存/进程
3. **逐环验证代码路径**：对每个环节，确认是否有代码把数据送到下一环
4. **区分"自动"和"手动"**：设计说"自动"但代码是"手动触发"的，也算偏差
5. **报告时标注缺失环节**：明确指出数据流在哪一环断裂，以及断裂的后果

## 与其他 skill 的衔接

- 发现单向同步问题后，修复时参考 `root-cause-no-patch`：不要加补丁绕过，要补齐缺失的同步链路
- 涉及跨进程/跨容器操作，参考 `operate-through-channels`：走公开接口，不进容器直接改
- 如果同步的是 cookie/浏览器状态，参考 `playwright-cookie-injection-pitfalls` 了解机制层陷阱
- 涉及数据库 Schema 同步，参考 `schema-migration-convergence`
- 涉及 commit message，用 `chinese-commit-messages`
