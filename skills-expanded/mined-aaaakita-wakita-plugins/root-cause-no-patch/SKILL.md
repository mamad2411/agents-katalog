# 根因优先，禁止补丁

修 bug 必须定位根因并根治。补丁/临时方案/降级容忍只是掩盖症状，问题会在别处以更难排查的形式复现，浪费更多时间。

## 核心原则

**补丁的特征**（出现以下任一即可疑）：
- 让错误"消失"而非解决：`cmd || echo warn`、`except: pass`、`|| true`
- 降级而非修复：装不上就跳过、连不上就换备选、功能缺失就隐藏入口
- 绕过而非定位："重启就好了""换个环境试试""加个超时跳过"
- 治标不治本：清缓存缓解、增大限制掩盖、加 retry 掩盖偶发崩溃

**根因修复的特征**：
- 能回答"为什么会崩"并指向具体原因
- 修复后同一根因的其他表现也一并消失
- 不依赖"重启""清缓存"等一次性操作

## 工作流程

### 1. 先理解为什么崩，再动手

不要急于"让它不报错"。先问：
- 这个错误的**直接原因**是什么？（如 esbuild 进程退出）
- 进程为什么退出？（socket 连接关闭 → `Socket.afterClose`）
- socket 为什么关闭？（容器内 esbuild 长驻服务不稳定）
- 为什么不稳定？（版本 bug / 环境不匹配 / 资源不足）

**追问 3-5 层"为什么"**，直到找到可操作的根因。

### 2. 区分"现象"和"根因"

| 现象（补丁治这个） | 根因（根治这个） |
|---|---|
| 页面 504 | esbuild 预构建崩 → 按需引样式触发二次预构建 |
| `The service was stopped` | esbuild 0.21.5 容器内 socket bug |
| 构建卡 13 分钟 | 缺 .dockerignore，COPY 1GB 本地目录 |
| Chrome 装失败 | apt 源用 http 被 80 端口干扰 |

**判断方法**：如果修了"现象"后换个环境/数据量/版本又会复现，那只是补丁。

### 3. 修复根因，验证根因消失

- 修复后，确认**根因链上每一环**都不再触发
- 不只看"不报错了"，要看"原来报错的路径现在正常走通"
- 用自动化验证（build/health/Playwright 控制台）而非"看起来好了"

## 真实案例：esbuild 504（追问 5 层）

```
现象：页面 504 Outdated Optimize Dep
  → 为什么？动态 import 的模块加载失败
    → 为什么？Vite 二次预构建时 esbuild 崩（The service was stopped）
      → 为什么崩？esbuild 0.21.5 长驻服务在 Docker 内 socket 不稳定
        → 为什么触发二次预构建？按需引组件样式运行时才被发现
          → 根因①esbuild 版本 bug ②按需引样式机制
```

**补丁路径**（错误，会复现）：
- 清 .vite 缓存 → 临时缓解，下次又 504
- 加 retry → 掩盖崩溃，偶发仍出现
- `optimizeDeps.include` 列组件 → 漏 loading/message，仍 504

**根因路径**（正确，彻底消失）：
- esbuild 升级到 0.28.1（修 socket bug）
- 样式改全量引入（消除二次预构建触发点）
- 验证：Playwright 控制台 0 错误，刷新多次稳定

## 真实案例：构建卡 13 分钟

```
现象：docker build 卡在 mkdir + chown 13 分钟
  → 为什么慢？chown -R 递归改 1GB 文件属主
    → 为什么有 1GB？COPY . . 把本地 venv(947MB) 拷进去了
      → 根因：缺 .dockerignore
```

**补丁**：加大超时、跳过 chown → 治标，每次构建仍慢
**根因**：加 .dockerignore 排除 venv → COPY 从卡死降到 2.5s

## 真实案例：CSS class 无效迭代

```
现象：`px-6`、`px-8` 不生效，padding-left/right 始终 0px
  → 为什么？class 不存在（项目用手写工具集，不是 Tailwind）
    → 根因：未验证 class 是否定义就开始迭代调值
```

**补丁**：换 `px-4`、`px-10`、`px-12` → 全部无效，因为 class 根本不存在
**根因**：首次无效时 grep 样式表确认 class 存在 → 发现不存在 → 改用自定义 style，一次生效

## 禁止清单

| 禁止 | 应该 |
|------|------|
| `cmd \|\| echo warn`（静默错误） | 修复 cmd 本身 |
| `except: pass`（吞异常） | 定位异常原因 |
| `--build-arg` 传代理重试 | 修网络/镜像源根因 |
| "重启容器就好了" | 找出为什么需要重启 |
| "清缓存试试" | 找出缓存为什么坏 |
| 降级容忍 `A \|\| fallback_to_B` | 修 A 或明确 B 是设计而非降级 |
| 加 retry 掩盖偶发崩溃 | 定位崩溃根因 |

**例外**：降级是设计意图时允许（如 patchright chromium 作为 chrome 的 fallback，且明确文档化）。但"装不上就跳过"不是设计，是掩盖。

## 验证标准

修完后问自己：
1. 我能一句话说清"为什么会崩"吗？不能 → 可能还是补丁
2. 去掉我的修复，问题会复现吗？不会 → 修了不该修的地方
3. 同一根因的其他表现也消失了吗？没有 → 只治了表象
4. 换个环境/数据量还会出吗？会 → 根因没除干净

## 调试技法：值不变时的排查流程

核心教训：调试"某值应该变却没变"时，第一反应往往是**猜测这个值为什么算错了**（钳制？引用丢失？异步时序？），然后花大量时间沿猜测方向找证据。**正确做法是先确认产生这个值的代码分支到底执行了没有。** 如果分支根本没进去，你猜测的"为什么算错"全是白费。

### 技法 1：值没变 → 先确认分支是否执行

当某个值 `X` 理应变化却恒定不变，**不要**先去推演 `X` 的计算公式哪里可能钳制了它。**先**在产生 `X` 的那个代码分支内部，加一行最简单的日志，确认这个分支被进入了。

```text
错误路径（浪费时间）：
  "newHeight 恒定 686，一定是被 imageObj.height 钳制了"
  → 花一小时推导 imageObj.height 的值
  → 加好几轮诊断日志打印 imageObj
  → 结果发现根本不是钳制问题

正确路径（5 分钟解决）：
  "newHeight 恒定，在 Bottom 分支里加一行 console.log"
  → 发现 Bottom 分支没打印
  → 分支没执行
  → 立刻定位到 handleType.includes('Bottom') 返回 false
  → 大小写问题，结束
```

**如果分支执行了，日志会打印出来。如果没打印，就是没执行——直接查分支条件。**

### 技法 2：改条件判断后，一句话验证

当你修改一个 `includes` / `===` / `startsWith` 等条件判断时，**改完立刻用 `node -e`、Python 交互式、或一行 print 验证新条件能匹配目标值**。不要凭"我改成小写了应该能匹配"的直觉就提交。

```text
错误路径：
  把 includes('Top') 改成 includes('top')
  → 没验证就部署
  → 纵向修好了，但横向又坏了（因为 Left/Right 在 camelCase 里是大写）
  → 用户又测一轮才发现

正确路径：
  改完后立刻跑：
    node -e "console.log('bottomRight'.includes('right'))"  // false!
  → 立刻发现小写匹配不上大写的 Right
  → 改成 toLowerCase() 统一比较
  → 一次搞定
```

**camelCase 方向词是经典陷阱**：`topLeft` 里 `top` 是小写（第一单词），`Left` 是大写首字母（第二单词）。任何按"全大写"或"全小写"统一匹配的修复都会顾此失彼。遇到 camelCase 方向匹配，直接 `str.toLowerCase()` 后再用全小写比较。

### 诊断日志写法规范

加诊断日志时，**用单行字符串模板，不要用对象**。控制台打印对象时可能被折叠/截断（显示 `…`），导致关键值看不到。

```text
错误（会被截断）：
  console.log('[debug]', { a, b, c, d, e })  // 可能显示 {a:1, b:2, …}

正确（单行不截断）：
  console.log(`[debug] a=${a} b=${b} c=${c} d=${d} e=${e}`)
```

如果怀疑某个分支没执行，在那个分支**内部**（不是外部）加日志。如果日志没打印，就是没进入。这是最快定位"分支是否执行"的方法。

### 自检清单

当你发现自己在做以下任何一件事时，停下来，回到上面的技法：

1. **你在推导一个值"为什么算错"，却没验证产生这个值的代码执行了没有。**
   信号：你在心里演算公式、猜测钳制边界、推导变量赋值。停下来，先确认分支进没进。

2. **你改了一个条件判断，准备直接提交/部署，却没验证新条件能匹配。**
   信号：你刚把 `=== 'X'` 改成 `=== 'x'` 或反过来，准备 build。停下来，先 `node -e` 跑一句。

3. **你写的回归测试只覆盖了修复的一个方向。**
   信号：你修复的 bug 影响多个对称场景（如四个方向的缩放），但测试只写了一个方向。停下来，补全。

4. **你基于一个假设改了代码、部署了、让用户测，结果用户说"还是不行"。**
   信号：你的假设大概率是错的。停下来，不要换一个新假设继续猜，回到技法 1：加日志验证分支执行了没有。

### 何时不适用

- 值确实变了，但变得不对（比如算大了、算小了、符号反了）。这是计算逻辑错误，不是分支没执行，直接查计算公式。
- 问题是偶发的、和时序/并发相关。这类问题加日志可能改变时序，需要别的手段。但即使如此，"确认相关代码执行了没有"仍是第一步。
