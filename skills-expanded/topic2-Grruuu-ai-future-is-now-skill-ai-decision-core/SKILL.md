# 企业 AI 决策中枢的四块拼图

## R — 原文 (Reading)

> 第一块是大脑：模型。……第二块是地图：本体（Ontology）。……第三块是导航系统：企业实时上下文。……第四块是操作系统：由4个子系统构成。……模型是会思考的大脑，可一个再聪明的大脑也需要一张地图以认清全貌、一个导航系统以了解实时状态，并搭配操作系统才能动起来。
>
> — 李开复，第6章《建设企业AI决策中枢》· "企业AI决策中枢的4块拼图"

## I — 方法论骨架 (Interpretation)

一个通用大模型进入企业时的处境，跟名校第一名毕业生入职第一天是一样的：足够聪明，但不知道规则在哪、入口在哪、这里的话是什么意思。区别在于新员工会开口问，模型不会——它会用很专业的语气，给出一个建立在错误前提上的答案。

所以让 AI 在企业里真正跑起来，缺的从来不是"更强的模型"。要补的是四样性质完全不同的东西，作者把它们叫四块拼图：

- **大脑 = 模型**：推理引擎，正在快速平价化，像 CPU 一样会越来越不构成差异。
- **地图 = 本体（Ontology）**：把客户、合同、订单、审批节点及其**关系**定义清楚的静态结构。没有它，模型只是个"自信的外人"。
- **导航 = 企业实时上下文**：把地图上每天发生的事件按时间顺序完整记录并实时传给所有相关实体。它不是数据库快照，是一条持续延伸的业务时间线。
- **手脚 = 操作系统**：四个子系统——调度（拆任务、会等审批、能从断点续跑）、执行（先在沙盒演练，再"执行—检查—修正"）、接入（用统一协议连 CRM/ERP/OA/财务）、控制（权限继承、身份不可伪造、全程留痕）。

这个框架的全部诊断价值在一句话：**闭环会精确地断在缺失的那一块上，而每一块缺失都有各自可辨认的症状**。所以出问题时不该问"要不要换个更强的模型"，而该问"断在哪一节"。

两处最容易被读错的地方需要先钉死：

1. **"企业实时上下文" ≠ LLM 的 context window**。作者说的是企业级事件时间线，不是往 prompt 里塞多少 token。把它读成上下文窗口，就会给出"多塞点资料""做个 RAG"的建议——方向完全反了。
2. **控制系统与执行同级，不是"以后再补的合规工作"**。作者把它列为四个子系统之一，因为没有它，系统有判断也没有举证能力。

## A1 — 书中的应用 (Past Application)

### 案例 1: 名校第一名毕业生的入职第一天 → 模型的五个能力缺口

- **问题**：CEO 们接触模型后的第一反应是"把最强的模型买进来，接上企业的数据，上几个智能体，让它直接干活"。结果普遍不好使。
- **方法论的使用**：作者不直接讲技术，先讲一个招进来的名校第一名——没人带、没告诉他内部规则和系统入口，他很快"寸步难行"：分不清 CRM 里"潜在商机"和"跟进中"的实质区别，查回款没有财务系统权限，写的拜访报告重点全错，同事给的流程文档是 3 年前的。然后他把新员工换成顶级 AI 模型，逐条对照。
- **结论**："把这个问题拆开来看，会发现AI模型有5个性质不同的能力缺口。"——不懂私有数据、不懂行话、不知此刻状态、没有手、不懂责任边界。这五个缺口正好对应四块拼图（前两个 → 地图，第三个 → 导航，后两个 → 手脚）。
- **结果**：作者由此得出那句关键的不对称——新员工"至少能开口问，知道自己不知道什么"，靠 3~6 个月能自愈；而"如果不给模型地图，它就会永远停留在入职第一天的状态"。时间不会解决模型的问题，只有补拼图会。

### 案例 2: 全球前 20 矿业巨头董事长的 "What is the endgame?"

- **问题**：作者服务一家市值全球前 20 的矿业巨头，项目启动会二三十名管理人员悉数到场（含董事会成员）。他先讲了 AI 宏观趋势和它将如何改变矿产业务。
- **方法论的使用**：董事长没有问"选哪个模型""先做哪个试点"，而是直接跳到终局："What is the endgame?"（做这个的终局图景是什么样的？）
- **结论**：作者的回答是 "Autonomous Mine, Autonomous Money Making."（全自动挖矿，全自动赚钱。）
- **结果**：这个对话在书里被用作**先定终局、再倒推缺哪块拼图**的锚点——因为终局是"自动执行 + 自动赚钱"，四块拼图里哪一块都不能缺：光有大脑和地图只能给建议，没有手脚就永远停在 PPT 上。它也是数据飞轮第一步"坚定的转型决心"的现场样本。

### 案例 3: DeepSeek 私有化部署热潮之后没有后文（反例）

- **问题**：2025 年春节后中国出现私有化部署热潮，"部署AI甚至在政企单位成了KPI，但部署之后往往就没有后文了"。同时 CEO 们发现员工自己用豆包、DeepSeek 都挺好，企业一部署就没动静。
- **方法论的使用**：用四拼图反查——个人使用时，人自己承担了"分辨来源、判断相关性、核查结果"的全部工作，等于人肉充当了地图、导航和控制系统。企业部署只交付了大脑那一块。
- **结论**："企业要的不是一段流畅的文字，而是一个可追溯、可核查、可承担后果的判断。"
- **结果**：把部署当终点，等于把最难的三块留在系统之外。这也是判断"我们到底缺哪块"时最常见的起始状态：**只有大脑**。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **已经投过钱、但卡在"不能上生产"**：买了模型、建了向量库、接了几个 API、上了两三个智能体，demo 很漂亮，真业务一跑就翻车，团队开始讨论"是不是该换个更强的模型"。
2. **AI 的回答"正确但不贴合现实"**：它答的是政策和流程规定的应然状态，而不是这家企业此刻的实然状态；追因型问题（"这个风险是什么时候埋下的"）完全答不了。
3. **有判断但落不了地**：AI 给了很好的建议，可它没法真的在 CRM/ERP 里改一个状态、提一个审批；或者敢让它动手但出了问题查不到记录、合规检查无法举证。
4. **采购/立项前想核对架构完整性**：供应商方案摆在桌上，用户想知道这套东西买回来会不会又是一次"部署完就没下文"。
5. **部署完之后使用率两个月内衰减**：员工继续用外部工具，不用内部部署的那套。

### 语言信号 (用户的话里出现这些就应激活)

- "我们模型也接了、数据也导了，为什么还是不能上生产？"
- "AI 答得挺像回事，但跟我们实际情况对不上。"
- "它只知道按规则应该怎样，不知道现在实际怎样。"
- "换了更强的模型也没用，是不是数据的问题？"
- "它能给建议，但没法真的动手改系统。"
- "出了争议我没法追溯是谁让它做的。"
- "部署完就没下文了 / 上线两个月就没人用了。"

### 与相邻 skill 的区分

- 与 `living-ontology` 的区别：本 skill 回答"**缺哪一块**"，living-ontology 回答"**地图这一块具体怎么建、谁来建**"。用户还没定位到缺口时用本 skill；已经确认缺的是地图（或用户直接在问本体/知识图谱/语义层怎么做）时转 living-ontology。
- 与 `data-flywheel` 的区别：本 skill 是**静态的架构缺口定位**（现在缺什么零件），data-flywheel 是**动态的长期壁垒构建**（怎么让它越用越强、别人抄不走）。中枢是飞轮的载体，但"我们的护城河是什么"不该用本 skill 回答。
- 与 `agent-four-components`（智能体 = 模型+工具+记忆+知识）的区别：那是**单个工具级**的诊断（"这个 AI 工具为什么不好使"），本 skill 是**企业系统级**的诊断（"我们整套 AI 体系为什么不能上生产"）。用户手里是一个采购来的工具 → 用四组件；用户在建自己的一套 → 用四拼图。
- 与 `earnings-call-test` 的区别：那把尺子问"这个项目该不该做/该不该砍"，本 skill 假定项目该做，只问"技术上断在哪"。若用户其实在问"这钱值不值得花"，先转财报电话会测试。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **先抓一个真实的失败样本，不在抽象层讨论**
   - 完成标准：能说清四要素——谁问的、问了什么、系统给了什么、正确答案本该是什么。
   - 判停条件：四要素凑不齐 → 停下，让用户去取一个真实案例再回来。没有样本的架构诊断一定会退化成通用建议。

2. **四块拼图逐一判"有 / 半有 / 无"，用症状表反查**
   - 完成标准：四块各得出一个"有/半有/无 + 一条现场证据"的结论，不允许留空。
   - 症状对照表（**从下往上查，模型放在最后**）：

   | 缺哪块 | 现场症状（用这些反查） |
   |---|---|
   | 缺**地图**（本体） | 模型是个"自信的外人"：把"有效客户""成交""在途库存"按通用语义理解；同一个客户在三个系统里三种叫法对不上；凡是答案藏在几个事实**关系**里的问题一律答错，且语气笃定 |
   | 缺**导航**（企业实时上下文） | "它回答的是'按规则应该怎样'，而不是'现在实际是怎样的'"；追因型问题完全答不了（"这个风险是什么时候埋下的""它在哪个节点开始出现异常信号"）；系统里只有快照，没有时间线 |
   | 缺**手脚**（操作系统） | 有判断但要人工转录进业务系统；跨天等法务/财务审批的长流程一断就崩，无法从断点续跑；换个软件供应商就要重建接口；"出了争议查不到原始记录"；不敢让它真动手，因为没有沙盒 |
   | 缺**大脑**（模型） | 罕见。只有当任务本身是开放式推理、且换更强模型后立刻好转，才成立。**若不满足这一条，不要建议换模型** |

   - 判停条件：若四块判下来都"有"、症状仍在 → 不要继续往中枢上加东西。先查数据质量（"垃圾进，垃圾出"在 AI 时代依然成立），再考虑这其实是闭环没跑真（转 `data-flywheel`）或项目本来就不该做（转 `earnings-call-test`）。

3. **只补最上游的那一块，并写出一句可判真假的验收句**
   - 补齐顺序固定：**地图 → 导航 → 手脚**（控制子系统与执行同级，不许后置）。跳过上游去补下游，等于在没有地图的情况下加装导航。
   - 完成标准：产出一句三个月后能判真假的验收句。反例（不合格）："本体建设完成度达 80%"。正例（合格）："业务负责人能直接问'这个客户在哪个节点开始出现异常信号'，并得到一条带时间戳与来源的事件链。"

4. **控制系统单独过一遍，它最常被当作"以后再说"**
   - 逐项核对四条：智能体是否自动继承发起人权限（不会比用户权力更大）；身份标识是否不可伪造（越权指令在门口被拦截）；每个动作是否完整留痕、可溯源可举证；动手前是否有沙盒预演。
   - 完成标准：四条各有明确的"已具备 / 未具备"结论；未具备的一律写进上线前置条件，而不是待办清单。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **用户在问单条 prompt 怎么写、怎么调**。这是 prompt 工程，跟四拼图无关。特别注意"上下文"这个词的陷阱：用户说"上下文不够"通常指 context window，那不是本 skill 的"企业实时上下文"。
- **用户在做模型选型比价**（哪家便宜、哪家 benchmark 高）。本书的立场恰恰是模型正在平价化、不构成差异。
- **个人 / 小团队使用场景**。个人用 AI 时，人自己就充当了地图、导航和控制系统，四拼图框架会把简单问题复杂化。
- **常规软件工程问题**：接口设计、数据库选型、微服务拆分。这些不因为出现"AI"两个字就变成中枢缺口。
- **用户在问"这个 AI 项目值不值得投"**。转 `earnings-call-test`。
- **用户已经明确在问本体/知识图谱怎么建、谁来建**。直接转 `living-ontology`，不要先绕一遍四拼图。

### 作者在书中警告的失败模式

- **把企业档案柜整个塞给模型**。"它会一视同仁地把所有东西吞下去，再一本正经地把充满错误和噪声的内容当成真相输出。"接入数据的核心动作若是"把知识库全量导入"、且没有任何来源可信度/时效性分级，这一步一定会反噬。
- **把 RAG 当成本体的替代品**。"它依靠的是字面相关性，不是逻辑正确性。"用于日常简报只是尴尬，用于采购决策、合同谈判、风险预警"代价可能非常高昂"。
- **把"完成部署"写成 KPI**（DeepSeek 私有化部署热潮）。部署只交付了四块里的一块。
- **ERP/CRM 沦为"数据坟墓"**：资产在，使用权不在。若报表需求还要提工单、平均等待以天计，接入系统这块就是缺的。
- **出问题先怪模型**。作者的排查顺序把模型放在**最后**。

### 作者的盲点 / 时代局限

- **作者是零一万物创始人兼 CEO，第 6 章描述的这套"企业 AI 决策中枢"正是他公司在售的产品**。书中原话："我每天都在用，也开始卖给客户用。"第 6 章因此同时承担方法论与销售论证两种功能，使用者必须自行拆分：四拼图作为**诊断清单**是可用的；"所以你需要买一套完整的中枢"这一步不是它的逻辑推论。作者本人也留了口子——"你不一定非得用我的"。
- **"我们是学习者，也是接棒者"这一叙事结构本身服务于产品定位**。作者把自己放在 Palantir 的下一棒位置上，这既是致敬，也是竞位。引用 Palantir 的部分请剥离这层。
- **样本严重偏向大型、有钱、数字化基础扎实的传统企业**。一手材料来自"世界各地数百家优秀传统企业的CEO"、世界 500 强、全球前 20 矿业巨头。小微企业、低毛利行业、强监管行业、没有 IT 底子的公司能否走通这条路径，书中没有验证。对这类用户，四拼图仍可作为**诊断语言**，但"补齐四块"的投入产出比未被证明。
- **几乎完全不谈下行风险**：数据泄露、供应商锁定、智能体误操作造成的不可逆业务损失、合规处罚。第 6 章列了控制系统的三道机制，但**全书没有一个 AI 造成实质损失的案例**——这意味着那三道机制没有被任何失败经验校准过。使用第 4 步时，请把它当成起点而非完备清单。
- **成书于 2026 年上半年，核心论据是极新且未经时间检验的数据点**。"模型正在快速平价化、不构成差异"这一判断支撑着"别换模型、去补另外三块"的建议；若模型能力再次出现断层式跃迁，这条排查顺序需要重估。

### 容易混淆的邻近方法论

- **数据中台 / BI 仪表盘**：中枢要输出的是"一个可追溯、可核查、可承担后果的判断"，不是一张报表。仪表盘是后视镜。
- **MLOps / 模型平台建设**：那管的是模型训练、部署、监控的工程链路，跟"模型懂不懂这家企业"是两件事。
- **RAG 架构优化**（切片策略、嵌入模型、rerank）：若每次质疑输出，解法都是"再调一下切片策略"，说明团队还在第一类问题里打转，而真正的缺口在地图。
- **智能体四组件（模型+工具+记忆+知识）**：同源但不同层。四组件诊断单个工具，四拼图诊断整套企业系统。
- **企业架构（EA）/ TOGAF**：那是组织与流程的治理框架，产出物是蓝图和规范；四拼图产出的是一份缺口清单和一句验收句。
