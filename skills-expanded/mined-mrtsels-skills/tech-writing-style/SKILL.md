# 技术文档写作规范（中英双语）

<!-- 整合自 Fenng/Tech-Doc-Style-Chinese（MIT，2026）与技能库原 simplified-technical-english；许可证见 references/LICENSE-tech-doc-style-chinese.txt -->

## 适用范围

用于中文或英文技术内容的撰写、改写、校对和审阅：

- 文档首页、产品介绍、解决方案页和更新日志
- API 文档、参数说明、错误码和常见问题
- 操作手册、故障排查、运维 Runbook 和安全说明
- 界面文案、按钮、导航、状态和提示信息

不要改写代码字面量、JSON 键名、URL、API 路径、数据库字段名、命令、配置项、LaTeX 数学公式或其他机器可读标识符。

## 规则优先级

发生冲突时按以下顺序处理：

1. 保留事实、逻辑、限制、安全信息和法律含义。
2. 服从用户明确要求和目标项目约定（先查目标项目 AGENTS.md、术语表、品牌规范）。
3. 保持技术术语和机器可读内容准确。
4. 改善结构、语义、语气和可扫读性。
5. 最后处理标点、留白、大小写等排版细节。

不得为了句子更短、语气更确定或格式更统一而牺牲更高优先级的信息。

## 先判断任务模式

- **撰写**：先确定受众、内容类型、事实来源、发布载体和篇幅；缺少会改变结论的事实时先标记缺口。
- **改写**：保留事实、逻辑关系、信息层级、限制和必要例外；默认交付完整改写稿。
- **校对**：只处理约定范围内的错字、标点、留白、大小写和术语一致性，不改结构、语气或事实。
- **审阅**：先列问题再给建议，按影响程度排序并引用具体原文；未经授权不直接修改文件。

## 事实保真与内容保真

- 不新增原文或可靠上下文没有提供的日期、数字、时限、SLA、能力、条件、因果关系或结论。
- 不删除前置条件、适用范围、例外、风险、安全警告、兼容性说明或失败处理。
- 不把「可能、计划、建议、通常」等不确定表达改成确定事实；信息不足时标记「待确认」。
- 改写引用、法规、合同、错误原文或用户提供的固定文案时，优先保留原文并将建议单独列出。
- 机器可读与结构元素一律原样保留，不当作散文处理：

| 内容 | 处理方式 |
| --- | --- |
| 代码块 / 行内代码 | 原样保留，不检查内部文本 |
| Markdown 表格及其对齐标记 | 原样保留 |
| LaTeX 数学（`$$…$$`、`$…$`） | 原样保留 |
| 非目标语言文本（中文文件中的英文缩写除外） | 不修改 |
| Mermaid 图、任务清单 `[x]`/`[ ]` | 原样保留 |
| URL、链接、引用编号 `[1]`、路径 | 原样保留 |

## 核心写作规则

### 语义与语气

- 准确先于修辞，清晰先于热闹；使用克制、直接、可执行的语言。
- 避免问候式开场、宣传口号、空泛形容和连续堆叠黑话。
- 优先说明「是什么、适用于什么、需要做什么、接着看哪里」。

### 句子长度与结构

- **英文**：句子不超过 20–25 个单词；在连词、关系从句等自然断点拆分。分点条目超过 25 词也要拆。
- **中文**：一个句子保持一个清晰主干，不连续堆叠多个条件、动作和例外。
- 一个段落承载一个主要信息点；列表项保持相同层级、句式和信息密度。
- 指代可能不清时，用具体名称替代「该」「其」「此」「上述」。

### 语态（英文）

程序性技术写作不使用被动语态：

| 被动 ❌ | 主动 ✅ |
| --- | --- |
| The model is trained on RICO data. | Train the model on RICO data. |
| The config file is read at startup. | The system reads the config file at startup. |
| Elements are detected by the VLM. | The VLM detects elements. |

例外：执行者未知（"the button was pressed"）或学术摘要中的惯例用法。

### 时态（英文）

- 操作步骤：一般现在时祈使句（"Run the script."）。
- 描述：一般现在时（"The model loads 220K parameters."）。
- 未来事件不用 "will"：用现在时加时间标记（"The next release **adds** this feature"）。
- 需求用 "must"，不用 "shall"（STE100 仅允许正式/法律声明使用 "shall"）。

### 词汇选择

- **英文禁用词**：`etc.`（删除或用 "such as" + 具体项）、`e.g.`（"for example"）、`i.e.`（"that is" 或改写）、`approximately`（具体值或范围）、`several`/`various`（具体数字或 "multiple"）、`quite`/`rather`/`somewhat`（删除或量化）。
- **中文空泛词**：`赋能`、`抓手`、`闭环`、`沉淀`、`对齐`、`拉通`、`打通`、`洞察`、`兜底`、`落盘`、`透传` 等只在其有明确业务定义时使用；优先写清实际指什么（`赋能`→`提供`、`闭环`→`完整流程`、`兜底`→具体保障机制）。完整清单见 [术语与排版](references/terminology-and-typography.md)。
- 同一概念使用同一首选术语，不因追求变化而替换同义词；首次出现的缩写给出全称。

### 标点、大小写与留白

- **中文**：正文使用全角标点；引号默认直角引号「」；并列词语用顿号；避免连续感叹号和口号式断句。
- **中文与英文、数字之间留白**：可见正文中中文与半角英文单词、独立数字、版本号之间保留空格（`HTTP 请求`、`版本 2.0`），但代码、URL、字段名、产品官方拼写不机械处理。
- **术语大小写**：`id`→`ID`、`api`→`API`、`json`→`JSON`、`javascript`→`JavaScript`、`nodejs`→`Node.js`、`github`→`GitHub` 等，不覆盖产品官方命名。
- **英文**：遵循目标项目拼写约定（美拼/英拼一致）；排版细节放最后处理。

### 称呼与执行者

- 中文技术文档默认不直接称呼读者，使用无主句或明确角色（`开发者`、`实施人员`）；`你`/`您` 属于风格选择。
- 英文操作步骤用祈使句（无主语）；可能出现责任或指代歧义时写出执行者，明确区分系统自动行为和人工操作。

## 按内容类型处理

### 入口页和介绍页

首段回答：内容覆盖什么、适合谁使用、从哪里开始读。避免标题、正文和按钮重复同一信息。

### API 文档

- 请求方法、路径、字段和值使用代码环境保护。
- 参数说明一列一义，写清类型、单位、默认值、限制和是否必填。
- 状态和错误文案根据实际语义翻译，不机械对应单个英文词（`Invalid` 不默认译成 `非法`、`Unauthorized` 不机械译成 `未授权`）；常见状态词见 [API 状态与错误文案](references/api-status-copy.md)。
- 写明前置条件、成功结果、失败结果和恢复方式。

### 界面文案

按钮说明动作和目标，不重复页面标题；错误提示说明发生了什么、影响是什么、如何恢复；危险操作写清对象、后果和是否可撤销；空状态区分「没有数据」「尚未创建」「无权限」「加载失败」。

### 操作与故障排查

对操作手册、故障排查、运维 Runbook、安全说明和多步骤 API 流程：

- 中文：读取并应用 [受控中文技术写作](references/controlled-technical-chinese.md)。
- 英文：应用 ASD-STE100 程序规则——编号步骤、一步一个动作、条件先于动作、明确执行者/对象/结果。

不把这些规则机械应用于品牌文案、叙事文本或固定引用。

## 受控语言应用强度

- **完整应用**：操作手册、安装部署步骤、故障排查、运维 Runbook、安全警告、多步骤 API 调用流程。
- **选择性应用**：API 概念说明、常见问题、更新日志、产品能力说明（只应用术语一致、指代明确、事实保真）。
- **不机械应用**：品牌和落地页文案、叙事性文章、法律原文和正式引用、需要保留作者风格的内容、极短按钮和导航标签。

## 项目覆盖规则

先检查目标项目自己的 AGENTS.md、术语表、品牌规范和用户指示；不要把本技能仓库中的示例约定当成目标项目约定。需要建立项目覆盖文件时参考 [项目覆盖模板](references/project-overrides-example.md)。

## 编辑与审计流程

1. 确认任务模式、内容类型、受众和项目约定；标记事实、数字、限制、引用和机器可读内容的不可改动边界。
2. 修复语义错误、歧义、遗漏和不一致；再调整信息顺序、段落、标题和列表；最后处理语气、术语、标点、留白和大小写。
3. 中英混排文件只改目标语言散文，非目标语言文本、代码、表格、数学原样保留。
4. 优先修复精确匹配（禁用词、错词），再处理语态、句长等需要判断的问题，避免级联误报。
5. 小文件（<50 行）整体重写；中等文件（50–300 行）按类型逐类 patch；大文件（>300 行、50+ 处问题）用 delegate_task 派发子代理，提示词写明文件路径、适用规则和保留范围。
6. 复核：重扫应清零；`git diff` 确认只改了散文；代码块、表格对齐标记、数学公式完整。
7. 每个文件单独提交（`docs: apply tech-doc-style to <filename>`），提交后立即推送。

## 配套检查器

仓库自带三个脚本（stdlib only，Python 3.10+）：

- `scripts/lint_copy_rules.py` — 中文检查器：错词（error）、语境词（warning）、直角引号/称呼/术语大小写/中西文留白提示（style）。
- `scripts/lint_ste_english.py` — 英文检查器：禁用词（error）、shall/will/被动语态（warning）、超长句（style）。
- `scripts/lint_tech_docs.py` — 统一入口：按文件内容自动识别语言并调用对应检查器。

用法一致：`python3 scripts/lint_* [文件或目录…]`；error 存在时退出码 2，`--strict` 把 warning/style 也视为失败；行尾加 `<!-- copy-lint-disable-line -->`（中文）或 `<!-- ste-lint-disable-line -->`（英文）忽略该行。两者都自动跳过 front matter、代码块、行内代码、URL 和 API 路径。

## 自动检查边界

- 可以稳定自动检查：确定错字、明确术语大小写、机器可读内容是否被错误处理、项目词表中的确定映射、英文禁用词。
- 只应提示人工判断：句长、被动语态、代词歧义、条件顺序、主语是否显式、是否过度简化、改写是否改变事实或确定程度。
- 检查器输出只是提示，不能证明文本符合规范，也不能代替作者判断。

## 最终检查

- 是否新增了来源不明的日期、数字、时限、能力或结论；是否遗漏条件、例外、风险、单位、默认值或恢复方式。
- 主语、对象、否定范围、因果关系和确定程度是否准确；同一概念是否使用同一术语。
- 标题、正文、卡片和按钮是否重复；代码、路径、字段、命令和引用是否保持原样。
- 内容是否便于目标读者扫读和执行；项目覆盖规则是否来自目标项目而非示例文件。

## 常见陷阱

1. **学术文本的被动语态是惯例**（摘要、相关工作）：主要对程序性章节应用主动语态修正，除非用户明确要求完整 STE100。
2. **中文文件中的英文缩写**：`模型使用 etc. 参数` 只修正英文 "etc."，不动周围中文。
3. **代码注释和行内代码中的禁用词**：只处理散文中的 `etc.`，反引号内的不处理。
4. **长表格单元格不是句子**：句长规则不适用于表格数据，不要拆分表格内容。
5. **大文件多问题会陷入 patch 循环**：50+ 处问题时用 delegate_task 派发，不要顺序 patch。
6. **语义词不自动替换**：`截止/截至`、`登陆/登录`、`配置/配制`、`即时/实时` 依赖语境，检查器只提示。
