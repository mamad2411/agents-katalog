# Doc/Skill 规格审校（claims audit）

触发：用户要求审校/规格合规性检查一个 SKILL.md、指南或配置文档，其断言（文件路径、行号区间、prompt 原文、数量、性能、目录结构）需要对照真实代码仓库核实；典型是 review-only 任务（不修改被审文件、不碰 git），交付物是一份分级问题清单。

## 工作流

1. **先完整读**被审文件（文档 + 被引用的脚本），不要跳读；同时列出技能目录全貌（scripts/、references/ 是否真的存在）。
2. **盘点断言清单**：把所有可验证声明列出来——文件路径、行号区间（`file.py:20-47`）、函数签名、prompt 原文约束（"结尾必须写 X"）、数量断言（"13 个指标"）、耗时/性能声明、commit hash、节点数/架构、目录结构。
3. **逐条对仓库核对**：
   - 行号：先 `wc -l` 确认文件长度 ≥ 引用行号，再 read_file 精确区间读，验证内容确实落在区间内（off-by-one、prompt 换行位置偏差常见）。
   - 数量/白名单：grep 名单中的每个名字，**自己数一遍**，别信文档的计数（见 Pitfall：13 vs 12）。
   - 签名：`grep -n "^def "` 核对函数签名与调用参数是否匹配。
   - commit hash：`git cat-file -t <hash>` 或 `git log --oneline | grep` 验证存在；hash 数字易手滑。
   - 节点数/架构：直接跑 smoke test（如 `len(list(graph.get_graph().nodes.keys()))`），不手工数。
4. **实跑脚本/命令**（网络允许时）：验证行为断言——用法、段数、退出码、UNVERIFIED 兜底、窗口大小（前 45 天/7 天）、每段来源+耗时标注。读代码只能验证"意图"，实跑才能验证"行为"。测试输出写 /tmp，不落在被审仓库里。
5. **文档自洽性检查**（审校特有的盲区）：
   - 输出目录锚点：目录结构图里的 `<输出目录>/` 占位符，正文有没有定义怎么建/命名？
   - 回退路径：文内每个路径（`~/.agents/skills/...`、references 文件）都 ls 验证存在；并确认"clone 某仓库"是否真能拿到文中所指的文件（脚本可能是技能自带、fork 里根本没有）。
   - 跨步骤矛盾：Step A 说"数据只有 5 个指标"，Step B 说"从 13 个白名单选 ≤8"——只按文档行动的新 agent 会卡住。
   - 指代含糊："我直接给出最终信号"里的"我"是谁。
6. **对照仓库核对角色/行为约束**：每个 prompt 级约束（"禁止默认 Hold"、"不得虚构"、"Markdown 要点表结尾"）grep 原文确认；注意约束可能三人都有而文档只提一人。
7. **输出报告**（用户约定格式，中文）：
   ```
   ## 🔴 严重问题 / ⚠️ 警告问题 / 💡 建议
   ### W1. [文件:段落/行号] 一句话标题
   - 说明: 事实 + 证据（实测结果/原文引用）
   - 建议修法: 可执行的具体改法
   ## ✅ 核对通过项（逐条列出，注明验证方式）
   ## 总评（能否直接投入使用 + 修复工作量）
   ```
   没有问题的项明确写 ✅，不要沉默跳过。

## 勘误模式（用户要求直接修，而非仅报告）

用户说"勘误 / 改一下"时，审校结论直接落地为修改，不写报告。流程扩展：

1. 核对阶段同上（读源码 + git log + references 实测数据），但**修改前先 grep 出所有待改字符串**，且检查同仓库兄弟文档（README 与 SKILL.md 常带同样的错）。
2. 用 python 精确替换，每个替换断言 `assert s.count(old) == 1`——旧串不匹配当场报错，绝不盲 sed（实测踩过：仓库内 SKILL.md 比假设的旧一版，断言拦截了错误替换）。
3. 修完 `grep -n` 确认无残留 → `git add <具体文件>`（禁 add ./-A）→ commit → push。
4. **用户路径约定（公开仓库）**：脚本/文件一律**仓库相对路径**（`./validate.js`），禁 `~/...` 家目录路径——克隆位置因人而异，写死即错。用户原话："不要写绝对路径，写基于 <repo> 的相对路径"。相对路径依赖 cwd 时在文档注明前提（"cwd 须为仓库根"）。

## Pitfalls（实测验证）

- **数量断言 vs 事实源集合**：文档常把"数据层支持集"与"prompt 白名单"混为一谈。trading-agents 案例：数据层 y_finance.py 支持 13 个指标（含 mfi），但 market_analyst.py prompt 白名单只有 12 个（无 mfi）——文档写"13 个白名单（…mfi）"就是两层混淆。核对时分别 grep 两个层。
- **行号引用**：必须读实际区间；只核对文件名会漏掉"文件名对但区间内容不符"的错误。
- **commit hash 手滑**：`358ff56` vs 实际 `35856ff`（数字换位）。`git cat-file -t` 一验便知。
- **性能声明**：实跑测量对比；同数量级即判合理（0.2s vs 0.64s 属正常波动），只标记真正的夸大；好文档会加"环境相关"限定。
- **review-only 纪律**：任务明确"不修改任何文件、不碰 git"时，交付物只有报告文件；发现的问题写进报告让所有者决定，不要顺手改。
- **副本可能已更新**：同一技能在 `~/.agents/skills/<cat>/<name>/`（farm/SSOT）和独立仓库里可能有两个副本，一个已修一个没修。核对前先确认审的是哪个版本；宣称某路径"不存在"前，先 ls 所有副本路径（farm 副本可能正好有该文件）。
- **占位符检查**：`<输出目录>/`、`<TICKER>-<DATE>` 这类占位符如果正文从未给出取值规则，就是真实遗漏（新手 agent 会乱放产出）。
- **引用的运行时日志必须是源码原文**：README 常把脚本 log 截短引用（`Selected 1 course(s).` 实际源码是 `Selected 1 course(s). Newly selected: 1.`）。核对时 grep 源码里的字符串字面量逐字比对。
- **实测数据分解要自洽**："+102ms = 轮询滞后 + 80ms 缓冲"若写 50ms 滞后则 50+80≠102——查 references 实测（实际滞后 ~22ms、上界 50ms）。文档里任何"数字=几部分之和"都验一遍算术。
- **read_file 可能把合法 UTF-8 .md 报成 binary**（遇过 cusis-auto/README.md，`file` 确认是 text）：用 `python3 -c "io.open(p,encoding='utf-8').read()"` 读、同法写回；patch 工具可能同样拒绝，python 替换更稳。
- **同仓库兄弟文档同步修**：README 指向"同目录 SKILL.md"时，两处的路径/断言往往同一批错，一次审校全部覆盖，别只改被点名的那个。
