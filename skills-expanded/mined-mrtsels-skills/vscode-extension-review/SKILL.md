# VS Code Extension Review

Independent code review of a VS Code extension — especially contract-driven reviews ("red lines" in TASK.md/AGENTS.md) where the deliverable is a graded findings list + a review doc committed to `docs/reviews/`. Built from the dsh-for-vs-code Phase 0/1/2 reviews; see `references/dsh-for-vs-code-phase-1.md`, `references/dsh-for-vs-code-phase-2.md`, and `references/dsh-for-vs-code-phase-3.md` (projection seed race, dead-code persistence, archive-cleanup claims), and `references/dsh-for-vs-code-phase-4.md` (G2 delivery-gate run: lint-warning gate failure, missing phase-2/3 review docs, VSIX dev-config leakage) for worked examples with concrete findings.

## When to Use

- User asks you to review/audit a VS Code extension repo as an independent reviewer (fresh context, "审查"/"复检" tasks)
- Repo has red-line contracts (TASK.md §0.5-style: thin bridge, append-only events, webview CSP, disposer coverage, no empty catch) and a `docs/reviews/` ritual with PASS/FAIL verdicts
- Reviewing webview apps for XSS surface, event duplication/ordering, state desync, or resource leaks
- Follow-up re-check of a prior phase's P1 findings (verify each with file:line evidence, not just G0 green)

## Official-spec compliance checklist (VS Code API docs / samples)

Verified 2026-08 against `code.visualstudio.com/api` (extension-anatomy, extension-guides/webview,
tree-view, chat, ai/ai-extensibility-overview) and `microsoft/vscode-extension-samples`. The user
expects extension UX to follow VS Code conventions, NOT browser-UI ports — run this when reviewing
an extension that embeds a vendored web UI:

- **Hide internal commands from the Command Palette.** Every contributed command shows in the
  palette by default; view-internal commands (tree click handlers that need args, refresh buttons
  that already live in `view/title`) must add
  `"menus": { "commandPalette": [{ "command": "<id>", "when": "false" }] }`.
- **Redundant activationEvents.** `onView:<viewId>` is auto-generated by `contributes.views`;
  declaring it manually is redundant (and conflicts with `onStartupFinished`). Docs stress minimal
  activation — flag manual `onView` entries.
- **`createTreeView` vs `registerTreeDataProvider`.** Docs: use `createTreeView` ONLY when you
  need the TreeView API (selection/visibility events, reveal). Plain display-only tree →
  `registerTreeDataProvider`; a discarded `createTreeView` return value is a code smell.
- **chatParticipants official pattern** (chat-sample): contribution supports
  `commands: [{name, description, disambiguation}]` (slash commands); handler must return
  `Promise<ChatResult>` (e.g. `{metadata:{command}}`) — a `void` handler forfeits followups;
  followups come from `participant.followupProvider.provideFollowups(result, ctx, token)`
  returning `ChatFollowup[]` (`{prompt, label}` plain, or `{prompt, command, label}` to trigger a
  slash command). `name` lowercase, `fullName` Title Case.
- **AI extensibility fit (four capabilities)** — chat participant / language-model tools / MCP /
  language-model API. A **viewer-type extension** (maps an EXTERNAL agent instance; model + loop
  live server-side) fits ONLY chat participant. LM tools & MCP extend VS Code's own Copilot agent;
  LM API consumes VS Code's models — none applies when the model is external. Say so explicitly in
  the review instead of recommending them.

## Workflow

1. **G0 gate first, actually rerun it** (background it while reading files): `pnpm typecheck && pnpm lint && pnpm test && pnpm build` using the project's own scripts. Note: `@live` tests may hit a real local service (auto-skip when unreachable) — report whether they ran or skipped. Lint: 0 warnings is the bar; an untracked dev script causing a warning is a finding.
2. **Layer reading order** (each layer's contract depends on the previous): wire/protocol types → runtime/transport → session/state manager → controller → extension wiring (activate/commands/handlers) → webview bridge (both sides) → UI components → tests → build script + probe scripts → golden-sample docs.
3. **Trace the wiring, not just the files**: single-slot callback assignments, construction order, and who-posts-what are where state-sync bugs live. Reconstruct every message path end-to-end (who emits → who forwards → who consumes → what the UI does with duplicates).
4. **Verify empirically, not just by reading**: if a pure display/render function exists, replay the REAL wire samples through it (see technique below). If tests encode a bug as "golden behavior", say so explicitly.
5. **Triage findings**: P0 (blocks delivery) / P1 (must fix) / P2 (later), each with `file:line | problem | fix suggestion`. Verdict: PASS / PASS WITH NOTES / FAIL (FAIL while any P1 is open — matches the phase-0 review convention).
6. **Write the review doc** into `docs/reviews/<phase>.md`, mirroring the prior phase's format: 范围 / G0 摘要 / 审查清单逐类核查 / 发现清单(分级) / 遗留跟踪. Chinese if the repo's docs are Chinese.

## Red-line checklist (six focus areas)

1. **Thin bridge**: the runtime/transport layer must not cache domain state or contain business logic (no session buffers, no message models inside the transport). It may cache only transport-level facts (last host description for readiness).
2. **Event flow**: session history is append-only; UI renders ONLY from events (no self-maintained `messages[]` that re-syncs). Check: dedup handles *batches* (full-history re-delivery) not just single events; reconnects re-seed history or events emitted during the gap are silently lost; buffers are not replaced while live events are still appending (overwrite race).
3. **Webview security**: CSP with no inline script (`script-src 'nonce-X'`, single nonce generated once and reused in both CSP meta and script tag — two calls = blank panel); postMessage inbound whitelist validation that throws on unknown shapes (and the panel catches → warning, not crash); no `dangerouslySetInnerHTML` anywhere; markdown renderer escapes HTML by default (react-markdown ≥9 sanitizes `javascript:` URLs); no API keys/credentials sent to the webview; `connect-src` absent so the webview can't fetch; localResourceRoots narrowed.
4. **Resource lifecycle**: every `on*`/`onDid*` registration returns a disposer; deactivate cleans everything; `DisposableSet.dispose` idempotent (splice(0) pattern); panel `onDidDispose` self-reclaims; reconnects invalidate the old generation (generation counter on sockets) AND clean up the old sockets (watch for partial-open leaks: `Promise.all` on two sockets leaks the one that already opened if the other fails).
5. **Error handling**: every empty `catch {}` must have a comment saying what is swallowed; network-path failures visible to the UI (error postMessage, status bar) — `logger.debug`-only swallowing of session-list failures is a P2; malformed wire frames must not crash the extension (validate payloads at the protocol boundary before casting to the discriminated union; the cast + `ensure(id)` + `.seq` access is a classic crash point); HTTP non-200 / non-JSON → explicit throw, never silent drop. **Async webview handlers**: `onDidReceiveMessage → onRequest(request)` is called without await/catch — any throwing async handler (ask failure, session.create failure, rollback of a deleted file whose `openTextDocument` rejects) becomes an unhandled rejection AND leaves webview-side in-flight locks (e.g. `pendingAsk` released only on event/error) armed forever → user silently blocked. Fix: catch at the dispatch point and post `{type:'error'}`; rollback/undo paths must handle the file-deleted case (re-create via `workspace.fs.writeFile`). **Respond/approval flows**: `void handleApproval(...)` needs try/catch — `respond()` without an HTTP-status check (asymmetric with `request()`), a throw inside, or a missing rpcId policy that logs "auto-reject" but sends nothing → approval hangs server-side until its timeout. Require: status check, rejection-fallback on error, explicit rpcId-missing behavior.
6. **Protocol narrowing**: no `any`/`@ts-ignore`; discriminated unions closed with `assertNever` or catch-all default; narrowing points commented; test mocks use `as unknown as` only at the boundary with a comment.

## Technique: replay golden wire samples through pure functions

When the repo ships a probe/doc with real wire samples (e.g. `docs/http-bridge.md` goldenTimeline), don't reason about rendering — run it:

```sh
# extract the JSON array from the doc, reconstruct SessionEvents, then:
node --experimental-strip-types /tmp/check.mjs   # runs .ts pure functions directly (node ≥22.6)
```

This caught the Phase 1 triple-render bug (two `block-end` + final flush → 3 identical bubbles) that the unit tests missed because the test fixture used a synthetic shape (no block-end, ends with `assistant/message`) that the real wire never produces. Rule: **test fixtures must match the real wire shape** — flag it when they don't.

## Common bug classes seen in this class of repo

1. **Single-slot callback clobber**: `runtime.onStatus = ...` assigned in a controller constructor, then overwritten by the app-assembly code → controller state machine dead (never `disconnected`, stuck `error`). Fix: multi-listener subscribe, or one owner distributes.
2. **Full-history double delivery**: `seedHistory` fires `onEvents` with the whole array AND the caller posts the snapshot again → UI appends everything twice (dedup guard only covers single-event appends). Fix: seq-monotonic dedup in the UI, or single delivery path.
3. **Accumulator flush duplication**: streaming accumulator pushed at every `block-end` AND at final flush (or on `assistant/message`) → same text rendered 2–3×.
4. **Unvalidated WS payload cast**: `payload as Frame` without checking `sessionId`/`event` fields → `TypeError` inside `onmessage` with no try/catch → extension host crash. Validate at the manager entry, wrap dispatch.
5. **Reconnect without re-seed**: `connected` handler refreshes the list but never re-fetches the active session's history → seq gaps forever (until user re-opens the session).
6. **Dead/stub code shipped as implemented**: no-op `handleHostFrame` stubs, a `Pseudoterminal` that never spawns a shell (sendText goes to an emitter nobody consumes) — flag anything "implemented" that no code path executes.
7. **Snapshot-watcher re-records its own rollback**: rolling back via `WorkspaceEdit` fires the watcher's own fs events; with the baseline snapshot not updated, the rollback is recorded as a NEW change with the diff direction flipped → the "回滚" button appears to do nothing (item never leaves the list). Fix: on rollback success, delete the change record AND set the snapshot baseline to the restored content; suppress the watcher's own writes (or the change disappears). Same class: accept/rollback flows that don't update the tracking baseline.
8. **Seed-drop race in seq-dedup**: UI dedup "keep only events with `seq > lastSeq`" drops the ENTIRE seed batch if ≥1 live event for that session lands before the seed response completes — opening a RUNNING session or reconnecting mid-turn makes this likely, not rare (chunks flow every ~100ms; history fetch is local but the window is real). Fix: merge by seq (union, dedupe by seq value) instead of drop; or seed-side merge into the buffer and push only the delta.
9. **Seed/restore overwrites newer state (projection variant of #8)**: the restore path (e.g. `seedHistory` consuming a `projections` block with `asOfSeq`) does `state.projections.set(key, …)` unconditionally — if live `session/projection` frames with higher seq already landed (running session, goal changing every ~100ms), the older `asOfSeq` baseline overwrites them: UI regresses to a stale goal/revision and CAS controls start failing. Fix: apply the same higher-seq-wins check in the seed path (`asOfSeq > prev.seq`) as in the live-frame path. Unit tests for this class must include "live frame arrived before seed response" ordering, not just sequential frames.
10. **Claimed persistence with no write path**: commit message / manual-test doc claims "restore last session from storage", but grep finds only `storage.get('key')` and zero `storage.update(...)` — the restore feature is dead code reading an unwritten key, and it can never fire. Always grep for the write side of any storage key before believing a persistence/restore claim.
11. **Cleanup claims vs list-API reality**: probe/test scripts claim "side effects cleaned up" via archive endpoints, but the list API may still return archived items (dsh `workspace.archiveSession` does NOT remove sessions from `session.list`; no delete endpoint exists). Verify empirically: re-list after cleanup and count leftovers. Also: on a live harness `goal.create` starts a REAL agent round (model calls, token cost) even with `maxGoalRounds: 1` — budget and document it honestly instead of claiming zero side effects.

## Pitfalls

- Root repo may lack tsconfig; ad-hoc `npx tsc` uses a wrong ancient version → false positives. Always use the project's `pnpm typecheck`.
- **oxlint exits 0 even with warnings**: `pnpm lint` returns EXIT=0 while printing `Found N warning(s)` — a gate bar of "0 warnings" (TASK §6.2-style) FAILS on warnings despite the green exit code. Grep the lint output for `warning`; don't trust the exit code. Each warning is a P1 finding when the contract says 0 (real case: unused `ctx` param in `native.ts:33` failed Q2 while the G0 log showed EXIT=0).
- `noUncheckedIndexedAccess` forces `arr[i]!` — audit non-null assertions on array tails (used as "last event" markers).
- `await` inside `??` RHS (`a ?? (await b())`) is a readability trap but works — check semantics, not style.
- Keyed lists with `key={index}` are acceptable for append-only lists; flag if the list is ever filtered/reordered.
- Tests asserting the bug as expected output (e.g. expecting BOTH streaming-final AND `assistant/message` bubbles) are the strongest evidence the fixture diverges from the real wire.
- **HEAD drift mid-review**: in multi-agent repos the target commit can move while you read (parallel agents commit on top). Pin file reads to the target SHA (`git show <sha>:<path>`), re-check `git rev-parse HEAD` before writing conclusions, and check whether later commits already fixed your findings before filing them.
- **Write the review doc FIRST, incrementally**: create `docs/reviews/<phase>.md` with the header skeleton (范围 / G0 摘要 placeholders) BEFORE reading code; append confirmed findings (file:line + verdict) as you go; write the verdict + checkbox table EARLY once findings stabilize, then spend the remaining budget verifying. Tool-iteration budgets regularly cut review subagents mid-run — the Phase 4 G2 gate review completed all analysis (12+ files, full findings) but the deliverable docs were never written because the write was saved for the end. A half-written doc survives; an empty one loses everything.
- **Verify protocol semantics live, not just from fixtures**: unit-test fixtures can encode plausible-but-wrong seq semantics. Collect real frames (e.g. a short WS capture during a goal lifecycle) to confirm seq domains are monotonic per session before trusting a higher-seq-wins implementation.

## Delivery-gate (G2) checks beyond the phase gate

- **VSIX content audit from the `vsce package` output**: it prints the full file tree — verify no `**/*.map` (sourcemaps), no `src/`/`web/`/`test/`/`scripts/` source; media/ + dist/web assets + LICENSE + readme + main entry present. Dev configs leak by default: `.oxlintrc.json`, `tsconfig.json`, `vitest.config.ts` are auto-included despite `.vscodeignore` (which only excludes what's listed) — file as P2 hygiene (add to `.vscodeignore` or use the `files` field). Also confirm `dist/` and `*.vsix` are gitignored so the working-tree artifacts never get committed.
- **All prior phase review docs must exist**: the G2 precondition "all G1 passed" needs artifacts — `docs/reviews/phase-N.md` for EVERY phase, not just the current one. Missing phase-2/3 docs while TASK.md claims reviews were "已派/delegated" = Q4/D5 failure; file it P1 (blocking) and demand backfill before PASS.
- **§7 checkbox table with evidence split**: mark each row 实测 (automated evidence: Q1 typecheck / Q2 lint / Q3 test counts incl. @live / PK1 package / PK3 VSIX contents / D1–D5 doc existence) vs 人工 F5 (functional F1–F18, Q6–Q8, PK2). Report F5 rows as "code path inspected at HEAD, human verification pending" — never claim them verified.
- **Prior-phase P1 regression spot-check**: re-verify each earlier phase's P1 fixes at HEAD with file:line evidence (multi-cast status subscribe, seq monotonic dedup, single-emit display, WS frame narrowing, reconnect re-seed) and report each explicitly as 未回退 ✅.
- **Leftover P2 ownership**: end the report with the P2 list + which phase/iteration owns each, so the follow-up session can pick them up without re-deriving.

## Verification checklist

- [ ] G0 rerun with real output captured (typecheck/lint/test/build + whether @live ran)
- [ ] All six red-line areas checked with file:line evidence
- [ ] Golden-sample replay done for pure render functions (if samples exist)
- [ ] Findings: P0/P1/P2, each `file:line | problem | fix`
- [ ] Review doc written to docs/reviews/ following prior phase format
- [ ] VSIX content audit (no .map/src, media+dist present, no dev-config leakage) + all prior phase review docs exist
