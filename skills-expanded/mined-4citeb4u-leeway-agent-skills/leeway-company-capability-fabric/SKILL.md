# LeeWay Company Capability Fabric

## Target

Agent Skills should model the breadth and coordination of a mature technology company, not merely isolated LLM tasks. Skills remain reusable capability nodes; departments/roles are contextual views over those capabilities, not separate sovereign agents.

## Core law

FOCAL != SILOED. Selecting one focal skill narrows full execution depth, not the Ambient Capability Field. Every materially relevant skill, primitive, verifier, dependency, safety constraint, leadership decision, recovery pattern, and cross-functional consequence remains eligible to influence the task weave.

## Organizational views

At minimum support Software Engineering, SRE/Platform, Product Management, Product Design/UX/Research, Product Security/Compliance, Data/AI/Research, Business/Finance/Go-to-Market, Operations/Support/Logistics, and Department/Executive Leadership. Extend when evidence/task demands.

## Role depth

Represent role/tier as responsibility/decision context, not prestige: practitioner/entry-mid, senior/lead, principal/architect, manager, director, VP/executive. A tier changes expected scope, verification burden, dependency horizon, and decision rights; it does not erase lower-level execution knowledge.

## Cross-functional program weave

For substantial product/system work, ask which departments must participate. Build parallel lanes where independent: product/specification; architecture/engineering; SRE/platform; security/compliance; UX/accessibility/research; data/measurement; cost/capacity; release/operations; leadership/risk. Converge at shared acceptance/shiproom gates.

## Decision-rights law

Execution expertise does not imply authorization. Preserve Creator/Human authority, platform/legal boundaries, and explicit approval requirements. Leadership skills coordinate resource/risk decisions but do not override higher authority.

## Context expansion probes

What departments are affected? What role/tier perspective is absent? What downstream team inherits this decision? What upstream dependency constrains it? What security/SRE/UX/product/business evidence is missing? What parallel lane can proceed now? What convergence gate proves the whole program rather than one team's slice?

## Composition examples

A release may weave PM acceptance criteria + architecture + implementation + database + security + accessibility + SRE/SLO + observability + testing + CI/CD + cost/capacity + release readiness + Veritas + receipt + learning. A host repair may weave systems administration + debugging + SRE + security + change management + rollback + communication. A research product may weave research + data + product + design + engineering + security + deployment + GTM.

## Final law

A skill is a lens and capability, not a wall. Use as many materially relevant capabilities as needed; expand full execution only where required.
