# 프로젝트 정의
1. 목표가 “RDBMS 검색으로 시작 → 한계가 명확히 드러남 → ES 도입이 ‘당위’로 체감됨 → 그리고 마이그레이션이 쉽고 안전한 구조” 이거니까, 상품 도메인은 검색을 위한 최소 필드만 남기고, 구조는 ‘검색 포트/어댑터’ + ‘인덱싱 파이프라인’ 중심으로 잡는다.
2. “RDBMS만으로 검색이 빡센” 예제 요구사항 (ES 당위 만들기)
    - 검색 요구사항 (처음엔 RDB로 구현)
      - 부분 일치 검색
        - “김치”로 “김치찌개”, “열무김치”, “김치전”이 나와야 함
      - 초성/오타/띄어쓰기 케이스(난이도 포인트)
        - “김치 찌개” = “김치찌개”
        - “김치찌게(오타)”도 어느 정도 잡히면 좋음(선택)
      - 정렬
        - 최신순(updatedAt), 가격순
      - 필터
        - category, price range 
3. RDBMS로 구현했을 때 “문제 시나리오” (기획에 명시)
  - LIKE %keyword%는 인덱스 효율이 떨어지고 데이터가 늘수록 느려짐
  - 한글/토큰화/띄어쓰기/오타 대응을 RDB에서 하려면
    - ngram 컬럼, 별도 테이블, 정규화된 search_key, 복잡한 쿼리/인덱스가 필요 → 유지보수 지옥
  - 복합 필터 + 정렬이 붙으면 실행계획/튜닝이 점점 어려움
    - 여기서 ES 도입의 당위를 “성능”만이 아니라 검색 품질 + 구현 복잡도로 확실히 만들 수 있음.

4. 마이그레이션이 쉬운 구조: “검색 포트/어댑터” 설계
   - 핵심은 비즈니스(상품) 서비스가 ‘검색 구현체’를 몰라도 되게 만드는 것.
   - 중요한 포인트(안정성)
     - DTO/쿼리 모델을 고정: ProductSearchQuery, ProductFilter, SortSpec, PageSpec[]
     - 결과도 고정: ProductSearchHit(id, name, category, price)
     -  ES 도입 시 API/컨트롤러/서비스 시그니처를 바꿀 필요가 거의 없어짐.

5. Outbox 기반 동기화: “RDB 원장 ↔ ES 인덱스” 정합성을 안정적으로
  - “ES 붙이면 검색이 좋아져요”만 보여주면 반쪽짜리고,
    “운영에서 안전하게 굴리는 방식(Outbox)”까지 보여주면 학습 가치가 급상승

6. 코드는 중복이 없어야 하며 코드 작업을 진행할 때는 항상 개발자인 나의 승인을 받고 코드를 반영할 것.
