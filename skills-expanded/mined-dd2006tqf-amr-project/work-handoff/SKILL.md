# Work Handoff: 工作交接文档生成

当用户要求「交接」「交接文档」「汇总交给别人」「我要新开会话继续」「把这个工作写下来」等意图时，调用此技能。

<HARD-GATE>
**交接文档必须是事实，不是叙述。**
- 严禁编造文件路径、类名、函数名、行号、测试结果或部署状态。
- 严禁把「计划要做的」写成「已经做完的」；未验证的事项必须显式标注为「未验证」或「待确认」。
- 文档只在对话框内输出，**不主动写文件**；用户明确要求落盘时才落盘。
</HARD-GATE>

---

## 阶段一：事实采集（禁止凭记忆）

交接文档的可信度完全取决于这一阶段。必须主动执行只读命令与阅读源码，而不是依赖对话记忆。

### 1. 仓库与工作区状态
```bash
git status -s          # 未提交改动、未跟踪文件
git log --oneline -10  # 近期提交，尤其是本次相关工作
git stash list         # 是否存在暂存的工作
```
判断：工作是否已提交？是否处于「改了但没提交」的中间态？是否有未跟踪的新文件？

### 2. 本轮工作涉及的真实文件
- 优先从 `git status` / `git diff --stat` / 最近提交的 `--stat` 中提取**真实变更文件清单**；
- 对每个关键文件，`Read` 其当前内容，确认：
  - 文件真实职责（不是名字听起来像什么）；
  - 关键符号（class / struct / enum / 方法名）是否真的存在；
  - 是否处于「改了一半」的状态。
- 若工作与某模块相关但文件尚未改动，也需要列出并说明其在待办中的位置。

### 3. 验证与运行状态
- **测试**：记录真实执行过的测试命令与结果（通过/失败数量）。未运行过的测试不得写成通过。
- **编译**：x86 本地编译是否通过？ARM64 容器编译是否通过？
- **部署**：是否已部署到开发板？服务是否 `active`？接口是否真实返回过预期数据？
- 上述任何一项没做，就在文档中明确标注「未执行」或「未验证」。

### 4. 若工具不可用（降级模式）
如果当前会话工具链故障（命令报错、文件读不到），**不要停摆，也不要编造**：
- 基于对话上下文产出交接文档；
- 在文档开头显著标注：`⚠️ 本文档在工具不可用状态下生成，文件路径与状态未经二次核验`；
- 单独列出「**交接前必须人工核验的清单**」，把需要确认的命令与文件逐条给出。

---

## 阶段二：六段式交接文档输出

严格按以下六个板块输出（顺序不可调整，标题清晰可扫读）。

### 一、工作背景与目标概述
- **项目定位**：本工作在整个系统中的层级与角色（例如：内核 eBPF 采集层 / 服务端生命周期中枢 / D-Bus IPC / 客户端库 / Web 前端 / AI 诊断）。
- **为什么做**：触发的真实痛点或需求是什么（给出可复现的场景描述，而非抽象目标）。
- **本次目标**：一句话说明本次工作要达成的结果，以及明确的**不做范围**（Out of Scope）。

### 二、相关代码文件清单及各文件功能说明
以表格或列表统一格式逐个列出，**每条都必须可核验**：

| 文件路径 | 当前职责 | 关键符号 | 本次改动状态 |
|---|---|---|---|
| `相对路径:行号` | 该文件实际做什么 | class / struct / enum / 函数名 | 已改 / 新增 / 待改 / 仅阅读 |

- 路径必须写**仓库相对路径**（可点击跳转）；
- 「本次改动状态」必须如实：新增 / 修改 / 删除 / 未动但相关；
- 若涉及删除，明确列出**已删除**与**待删除（含删除门禁条件）**。

### 三、当前工作进度详细描述
按「已完成 / 进行中 / 未开始」三态组织，每项都要有**证据**：
- **已完成**：写清楚做到了什么程度，附上验证方式（测试名、命令、真机输出摘要）。
- **进行中**：卡在哪一步、当前文件处于什么中间状态、哪些代码是半成品。
- **未开始**：列出尚未触碰的部分。
- 明确标注：工作区是否干净、是否已提交、提交哈希（若有）。

### 四、下一步具体实施计划
必须是**可执行**的，而不是方向性描述：
- 按步骤编号，每一步包含：**动作、涉及文件、验证方式（怎么证明这步做对了）**；
- 指出步骤之间的依赖顺序；
- 标出**关键前置门禁**（例如：必须先做某项能力验证，才能进入实现）；
- 给出「交接后的第一条命令」。

### 五、项目最终目的与预期成果
- **最终形态**：这套东西做完之后，系统具备什么此前不具备的能力；
- **可观测的验收标准**：用可测量的方式描述成功（接口返回什么、状态如何变化、指标落在什么区间）；
- **对既有系统的影响**：是否改变对外契约（D-Bus 方法、信号、数据库字段、schema 版本）？是否向后兼容？

### 六、技术难点、解决方案与经验教训
这是最容易写空的一段，必须写具体：
- **难点**：描述问题本身为什么难（协议语义、并发竞态、内核限制、时钟、统计陷阱等）；
- **解决过程**：尝试了哪些路径、为什么放弃其中一些（**被否决的方案往往比最终方案更有交接价值**）；
- **教训/约束**：沉淀成后续不能再踩的规则（例如：「X 字段不能当作 Y 使用」）；
- **遗留风险**：已知但未解决的不确定性，注明影响范围与触发条件。

## 阶段三（可选）：交接引导语

若接收方是**新会话 / 新 Agent**，在文档末尾附一段可直接复制的引导语，包含：
- 仓库路径与当前分支；
- 一句话任务定位；
- 必读文件清单（按优先级）；
- 第一步动作；
- 环境要点（编译器、容器、开发板地址、构建命令等）。

---

## 质量铁律（Guidelines）

1. **事实优先**：所有路径、符号、命令、结果都必须来自真实核验；不确定就标注不确定。
2. **状态如实**：交接文档的价值在于让接收方知道「真实停在哪里」，粉饰进度是最严重的失职。
3. **可执行**：第四段的每一步都要能被直接执行，避免「继续优化」「完善实现」这类无法开工的表述。
4. **保留决策痕迹**：被否决的方案、被验证不可行的路径，必须写进第六段，避免接收方重走弯路。
5. **遵守项目规则**：文档中涉及的操作建议不得违反本仓库硬性约束（如禁止自动 commit/worktree、eBPF 必须 ARM64 容器编译、脚本不可中途修改等）。
6. **长度服从信息密度**：宁可写长但要具体，也不要为了简洁丢掉关键事实；反之，不写与交接无关的项目背景科普。
