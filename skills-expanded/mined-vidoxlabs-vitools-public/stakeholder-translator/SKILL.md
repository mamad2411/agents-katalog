Stakeholder Translator Skill

When to use

Activate when the user needs to communicate the same information to different audiences — reframing substance without changing facts.

Audience Profiles

Executives / Leadership





Lead with: Business impact — revenue, competitive positioning, market timing



Format: BLUF (Bottom Line Up Front), then 3-5 supporting bullets. Max 1 page.



Language: Strategic, decision-oriented. "This unlocks _" / "The risk of not doing this is _"



Include: Clear ask — what you need from them (decision, resources, alignment)



Avoid: Implementation details, technical architecture, feature lists

Technical Leads / Engineering





Lead with: The problem and constraints, not the solution



Format: Problem → proposed approach → open questions → acceptance criteria



Language: Precise, technical-friendly. Explain WHY, not just WHAT.



Include: Edge cases, dependencies, scope boundaries, what's explicitly out of scope



Avoid: Marketing language, vague timelines, hand-wavy requirements

Field / Solutions Engineers





Lead with: Customer pain point and what changes for them



Format: What's shipping → how it works → what they can tell customers → known limitations



Language: Practical, customer-facing. Think "field enablement."



Include: Talking points, competitive positioning, timeline



Avoid: Internal politics, architectural debates, tentative plans they can't share

Sales / Go-To-Market





Lead with: Customer value prop and deal impact



Format: Elevator pitch → key differentiators → objection handling → packaging implications



Language: Outcome-oriented. "Customers can now _" / "This replaces _"



Include: Competitive positioning, which segments benefit most, what NOT to promise



Avoid: Technical depth, internal roadmap details, speculative timelines

External Developers / API consumers





Lead with: What's new and how it affects their integration



Format: Changelog style — what changed → migration steps → code examples



Language: Direct, technical, no marketing fluff. Show, don't tell.



Include: API changes, breaking changes, deprecation timelines, links to docs



Avoid: Business rationale, internal context

Rules





Same facts, different framing. Never change the substance.



One audience per section. Each version should stand alone.



Flag conflicts: if what one audience needs to hear conflicts with another, surface it explicitly.
