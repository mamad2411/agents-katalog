# Issue Tracing

On-call triage assistant. Takes a Grafana or Kibana/ELK URL, **autonomously traces from the filtered logs down the call chain to the root cause**, and produces a structured **Root Cause / Impact / How to Resolve / Unknowns** report in both Traditional Chinese (full) and English (short).

> **This skill is a step-by-step SOP, not a reference document.** Read the operating principle below first — it sets the working contract. Several steps ask you to write a short artifact in chat (scope/chain note, query plan, evidence dump) — internal discipline for auditability, not a request for approval: write it, then keep going.

**Input** (`$ARGUMENTS` optional):
- Kibana / ELK Discover URL (carries the filter directly)
- Grafana dashboard / panel / alert URL (carries the filter or alert condition)
- Plain alert description (then ask user for a URL)

---

## Operating principle: filter-driven, autonomous to root cause, minimal check-ins

The URL's filter (or alert condition) **is the user's scope and intent** — you do not re-decide what to investigate. From there you run the investigation to completion yourself and produce the report. Do not stop after the first look to ask "want the full report?" — finding the root cause and reporting it IS the task.

**Proportionate depth — navigate fast, deep-verify ONCE, at the suspected root cause.** On a **server-log family** stream the errors typically carry the full exception + call chain with `file:line` (controller → SDK → proxy → the failing downstream call, the exception type, the timeout value). While tracing, that IS your map. (A structured-telemetry stream usually carries **no** stack trace and navigates by trace id instead — see 5.0; the same rule applies, only the map changes.) Each hop's log is for finding the next hop, not for re-confirming the hop with latency / baseline / infra numbers the map already gave you. **There is exactly one place that earns a deep-verification pass: once you have a suspected root cause, confirm it is actually right before writing the report** — that is where the baseline (spike vs chronic → is this really the trigger?), infra metrics (if infra-shaped), and the breadth query (if a shared dependency) belong. The only checks that legitimately fire earlier are step 4's spike-vs-chronic on the anchor (it feeds the trigger classification) — **together with the same count extended to the anchor's sibling deployments** once the trigger question is live, because an anchor-only count reads a sibling's surge as "no surge" (`references/next-hop-drill.md`, the caller-direction drill) — and 5d's breadth fork for a shared dependency. Two rules that keep the trace lean: (a) once one pattern is a clear majority, stop partitioning the rest — you need the dominant pattern's identity + rough share, not an exact 100% split; (b) apply the same at **every** hop, not just the first — drop <~10% side patterns, do not chase a minority error into its own subtree.

**Minimal check-ins (do NOT make the user drive):** anything the tools can answer, answer yourself — do not defer it to Unknowns and do not ask the user to run it for you. Pause only for a decision that needs a human or for data you cannot reach after trying — the *No fabricated unknowns* guardrail's (b) and (c); its (a), another team's service, is a stop at the boundary (5a), not a question for the user.

## Steps

1. **Preflight: preload tools + resolve project root + load environment knowledge** (do this FIRST)

   ### 1a. Preload core deferred tools

   One `ToolSearch` for the always-used entry points so the first queries don't break narrative:

   - `mcp__elasticsearch__search`
   - `mcp__elasticsearch__list_indices`
   - `mcp__grafana__list_datasources`

   Load everything else on demand (Grafana panel/alert queries, Prometheus/Loki/InfluxDB queries, code-host / decode / id-lookup MCP tools, panel image). `ToolSearch` is cheap; preloading unused schemas is not.

   **If one of those tools does not resolve, that whole capability is absent — say so here, not mid-query.** Name what is missing and what it costs: no `mcp__elasticsearch__*` means no log queries at all (stop, and say which server has to be wired); no `mcp__grafana__*` means panel, alert, and metric reading are unavailable, so an ELK-only investigation can still proceed on a Kibana URL. Discovering it three steps later reads as an empty result rather than a missing tool.

   ### 1b. Resolve the project root (reading code is part of the normal flow)

   You will read service code in step 5 to confirm root cause and user impact, so resolve where the repos live up front:

   a. **Use the root that is already known** — the session's working directory, an `add-dir` path, or the local-repo convention recorded in the environment knowledge (see 1c). If the root is already granted/known, just use it; do not ask.
   b. **Only if no root can be resolved**, ask the user once to `/add-dir <their service repo root>`.

   Cache the resolved root. When a *specific* repo you need turns out not to be present under the root, that is not a reason to stop the whole investigation — read what you can, and tell the user which repo is missing (see step 5). Continue to 1c.

   ### 1c. Load environment knowledge (this is what fills the skill's placeholders)

   This skill is deliberately generic — it names no real hosts, indices, projects, clusters, or domains (see the open-source guardrail). When the URL points at an internal system and the session exposes a knowledge skill / doc describing **this organization's conventions**, load it now and pull the concrete values from it:

   **AUTHORITY — what you load here OVERRIDES every field name, field value, and index name written anywhere in this skill.** Field and value names appearing in the steps below (`project`, `env`, `level`, `prod`, `error`, …) are **illustrative of one common shape, not defaults to fall back on**. When the loaded knowledge gives a mapping for the stream you are querying, that mapping wins — do not reconcile it against the examples here, do not "also try" the example name, and do not treat a `0` from an example name as evidence about the data. This ordering is the point of 1c: a real environment routinely runs several log streams with **different field names for the same concept**, so a skill-side default is a false-zero generator, not a safety net.

   - **Kibana / Grafana host + real index / data-stream names** → steps 3–4 (query the right source; know when one service's logs are split across multiple streams / clusters).
   - **Per-stream field mapping** → step 3 / step 4. Not one convention — **one mapping per stream family**, because the same concept is named differently in each. Pull, for every stream you may touch: service identity, environment (field **and** value casing / wording), severity (field and value form — a text value, a numeric range, or both), log text, timestamp field **and its format**, HTTP path / status / latency, user identity, and whether `.keyword` sub-fields exist. Two traps worth pulling explicitly: **the field you filter on is not always the field you read** (a data view can expose runtime fields / aliases that are absent from `_source`), and a substring `match_phrase` against a keyword-typed field silently returns `0`.
   - **Logging exceptions** (services whose logs are NOT in the default index — routed to APM / a separate stack) → step 3's 0-hits ladder, so you don't misread "different backend" as "no data".
   - **Project ownership + dependency / topology docs** → step 5 (which services are your team's vs another team's = the drill boundary; and a service's upstreams when its logs don't name them).
   - **Local-repo convention** (where each project is cloned, how a project name maps to a directory) → step 1b / step 5.
   - **Dashboard UIDs + metrics mental model** (shared vs per-project boards, template vars) → step 5's infra check.
   - **Decode / lookup tools** for opaque log values (encoded payloads, status bitflags, id↔id mapping) → step 4.
   - **Config / settings lookup tools** for a runtime value the repo does not contain (a feature toggle, a rate-limit or threshold setting, a tuning parameter held in a settings store) → step 5's mechanism read and step 6's How to Resolve. When the mechanism, or the fix you are about to recommend, turns on such a value, **read the value; do not infer it from the code path alone.** Two things it settles that nothing else can: whether an observed behavior is **deliberate** (a configured delay / throttle, so its slowness is not evidence of this incident) rather than a symptom, and whether the obvious mitigation lever is **already switched off** — which is usually the real recommendation, and is invisible from code that merely reads the setting.

   If no such knowledge source exists, discover live as the steps describe. Continue to step 2.

2. **Recover the filter from the input**

   The output of this step is a concrete query scope — index / stream (to resolve in step 3), time range, and field filters by role (environment / service / severity / free-text query) — **regardless of whether the input was ELK or Grafana**. Record each filter as the role it fills *plus* the literal field path and value the input gave you; the literals are what you replicate in step 4, the roles are what let step 3 re-resolve them if the stream turns out to use different names.

   **No URL at all** (the plain-alert-description input) — there is nothing to recover, so **ask once** for the Kibana / Grafana URL they are looking at and wait for it. Do not invent a scope from the description: a symptom in prose is not a filter, and substituting your own is the one thing the operating principle above forbids. If they genuinely have no URL, build the scope explicitly from the alert's own condition (service + error / metric + time window), then say in the report that the scope was **reconstructed, not recovered** — everything downstream inherits that uncertainty.

   ### 2a. ELK / Kibana URL (`*/app/discover#/...` or `.../view/<savedSearchId>`)

   - Extract `time.from` / `time.to`.
   - Extract each filter's **exact clause** — field path + query type + value, e.g. `match_phrase:(<service-field>:<value>)` OR `match_phrase:(<service-field>.keyword:<value>)` — to replicate verbatim later (see step 3's filter-mapping note). The field path differs per data view; the type is `match_phrase`, never `term`. Note each clause's **role** (service / env / severity) alongside the literal, and note that a filter's `meta.index` can name a **different** data view than the search's own `dataSource.dataViewId` — the clause is still yours to copy verbatim, but don't assume every filter belongs to the primary data view.
   - Extract `dataViewId` — an opaque id, NOT an index name; resolve it in step 3.
   - For `view/<id>` (saved search), note the id; its bundled query + filters + referenced data view resolve from `.kibana` in step 3. URL-state filters override/extend the saved-search filters.

   This embedded filter **is** the scope — do not broaden or narrow it.

   ### 2b. Grafana URL (`*-grafana.*/d/<uid>/...`, panel, or alert)

   Goal: recover the *condition*, translate to an ELK filter, then investigate in the logs.

   - **Dashboard / panel URL**: extract `uid`, `viewPanel` (panel id, optional), `from` / `to`, `var-*` template vars. For the anomalous panel(s), read the query and grouping with `mcp__grafana__get_dashboard_panel_queries` (or `get_dashboard_property` for raw targets). Pull the filter dimensions (service / project / level / env) and any log query behind the panel.
     - If a panel's datasource is `elasticsearch`, take its query/filters straight across into your ELK filter.
     - If it's `prometheus` / `loki` / `influxdb`, the panel tells you *which service and what condition* is anomalous → map that service + severity to the equivalent service filter + severity filter on the log stream you resolve in step 3, using that stream's field names from 1c's mapping (a panel gives you no field paths to copy, so this is the one input where you must build the clauses yourself).
   - **Carry the panel's exclusions across too.** A panel query commonly ends in a `NOT (...)` / negative clause removing exception types the team has already classified as noise. That exclusion is signal: drop it and your anchor's dominant pattern is computed over noise the panel author deliberately removed. Replicate it as `bool.must_not`. **Then verify the exclusion actually fired** — a negative clause on the log-text field silently no-ops on a stream where that field is not searchable (step 4's dominant-pattern note, and the full rule in `references/es-query.md`), so compare the count with and without it; if they match, the exclusion did nothing and you must filter those patterns out client-side instead.
   - **Alert URL / alert context**: get the alert rule's firing condition (metric + threshold + labels) via the alerting MCP (`mcp__grafana__list_alert_groups` / alerting rule tools). Map its labels (service / project / severity) to the ELK filter.
     - **The firing condition is fact; the alert's remediation text and its definitions are NOT.** An alert commonly also carries a first-response instruction ("add N pods first", "call 2nd-line") and a definition of the entity it fires on ("X means a name in setting `<key>`"). Both were written for an earlier incident shape and drift silently — the setting it names can have been superseded by a newer mechanism, and the scale-out it prescribes can be flatly contradicted by the infra numbers you pull in 5d. Treat them as leads to verify (against code + the config lookup in 1c), and when your own data contradicts one, **say so in How to Resolve** instead of repeating it as the fix.
   - Resolve relative time (`now-1h`) to absolute UTC.

   **Time buffer — expand the parsed range by ±5 minutes when querying, and treat that as a boundary correction rather than insurance.** The URL's window is where the user happened to be looking; it is not the event's edge, and the two are rarely the same because a person zooms to the part they noticed. What sits just outside is routinely decisive: in one run the buffer surfaced an earlier, larger burst that fell entirely outside the URL's 69-second window — and that burst was the only place a second service appeared, which is what turned the verdict from "one service's problem" into fleet-wide. Never narrow to the URL's literal range, and when the signal reaches either edge of the buffered window, widen further (step 4's boundary check) rather than assuming you have seen the whole thing.

3. **Resolve the target index** (BEFORE any ES query)

   You need the real ES index pattern for the filter from step 2. **Pick it by input type first — do not guess the index name:**
   - **ELK URL** → you have a `dataViewId` (and maybe a saved-search id), **not** an index name → resolve it via 3a. Do not guess from the display name; do not lean on `_all`. **The env-knowledge stream list (1c) does NOT replace 3a for the anchor** — resolving the dataView tells you which stream(s) the URL actually scopes to; a project doc's "this service logs to streams A and B" is a *fallback* for the Grafana / unresolvable case (see 3a's "do not broaden" note), not a licence to query both when the URL already resolves to one. A `0` on a stream you added from the doc rather than from the resolved `title` is *expected* — not a false zero to walk the 3d ladder on.
   - **Grafana URL** → you have **no** `dataViewId`. Get the index from, in order: (a) an `elasticsearch` panel's own datasource — it references a Kibana index-pattern by uid; resolve that uid via 3a exactly like a `dataViewId`; (b) the env-knowledge index / data-stream names (step 1c) for the service the panel / alert pointed at; (c) the 3e discovery flow. Then apply 3b–3d the same way.

   ### 3a. Resolve from `.kibana` (authoritative — do this first)

   Every data view is a saved object in `.kibana*`:

   ```
   index: ".kibana*"
   queryBody: { "size": 5, "query": { "ids": { "values": ["index-pattern:<dataViewId>"] } },
               "_source": ["index-pattern.title", "index-pattern.name"] }
   ```

   - `index-pattern.title` = the **real ES index pattern** to query — often a data-stream name or comma-separated list.
   - `index-pattern.name` = display label only, frequently differs from `title` (display `foo-bar` → title `bar-logs-foo`). **Never query the display name.**

   For a saved search (`view/<id>`), read `search:<savedSearchId>` the same way: `search.kibanaSavedObjectMeta.searchSourceJSON` holds the bundled query + filters, `references[]` maps each to an `index-pattern` id — resolve those the same way. The `title` / `description` also confirm which service the view is for.

   Query the resolved `title` **verbatim** — a data-stream title auto-expands its backing indices.

   **Then classify the stream FAMILY before writing any query — resolving the index is only half of step 3.** A real environment runs several families of log stream side by side (a server-log family, a structured-telemetry / OTEL-sink family, a browser / client-log family, a per-team or per-product family, an APM family), and **each names the same concepts differently**. The resolved `title` tells you which family you are in; 1c's mapping then tells you that family's field vocabulary. Write the family and its resolved fields into your scope note before querying:

   ```
   Stream: <resolved title>   Family: <server-log | otel-sink | client-log | other>
   service=<field>=<value>  env=<field>=<value>  severity=<field>=<form>
   log text=<field>  timestamp=<field>,<format>  user id=<field | absent>
   ```

   Two failure modes this prevents, both of which return **`0` with no error** rather than an error you would notice:
   - **Right concept, wrong family's field name** — e.g. filtering the server-log service field against a telemetry stream that keys service identity differently.
   - **Right field, wrong family's value spelling** — the same service, environment or severity is spelled differently per family (separators, casing, full word vs abbreviation, text value vs numeric code). This one is the more dangerous of the two, because the field path is valid, the query is well-formed, and the `0` looks exactly like real absence.

   When the family's identity value is not recorded in 1c, **resolve it against real data instead of transforming a value from another family** — never derive one family's spelling from another's by a substitution rule, because a rule that fixes one service breaks the next. Resolve by **probing candidate spellings**: `match_phrase` that stream's identity field for each variant of the name you already have (separator swapped, separator dropped, case changed). A hit confirms the spelling *and* proves the service is present in that stream at all.
   - **Probe by COUNT, one variant per query, all variants in ONE block.** Each probe is `match_phrase` on the identity field + the time range, `size: 0` + `track_total_hits: true`. Two or three variants fit inside the concurrency ceiling, so a single block returns *both* answers at once — whether the service is there, and which spelling is the real one. Use counts rather than documents: a count is exact and per-variant, so nothing can hide behind a louder neighbour. If you have more candidate spellings than fit one block, first send **one** combined query — every variant in a `bool.should`, still `size: 0` — purely to rule the service out cheaply; a `0` there ends it, and a non-zero total tells you only that *some* spelling exists, so the per-variant counts still have to follow. Never add a sample to that combined query hoping to see which variant hit: sorted by time it is swamped by the highest-volume match, so a quiet spelling is invisible next to a loud one.
   - **Do not resolve it by sampling the stream to see which identities are in it.** On a busy stream a sort-by-time sample is swamped by the highest-volume services, so a quiet service is missing from the sample while being perfectly present. Nor can you enumerate the identities with an aggregation — the search wrapper strips agg results outright (`es-query.md`). Probing is the only reliable direction.
   - Two guards on the probe: the identity field is usually keyword-matched, so **only a whole-value hit counts** (a substring probe returns `0`) — which also means a short identity does not accidentally match a longer one containing it; and before concluding "this service is not in this family", **prove the filter is biting with a POSITIVE control** — include, in the same query shape, an identity you already know is present in that stream (any service from the anchor, or a fragment you have seen hit). If the control returns hits and the target returns `0`, the `0` is real. Do **not** use a deliberately nonexistent name for this: it returns `0` whether your filter works or is silently broken, so it cannot tell those apart — which is the one thing a control exists to do. It costs the same either way (two queries: control-plus-target, then target alone), so there is no reason to take the weaker signal.
   - **One service can own more than one identity in a family**, so a resolved single spelling can still under-cover: a commit-pinned clone repo deployed alongside its origin, and a second component shipped from the same repo, each register their own identity — and those spellings need not follow the origin's convention. Whenever the question is about a service's *scope* (an error count, "is this service failing"), establish whether it has siblings and query them together; 1c's mapping is where that list belongs once known.

   **Do NOT append `*` to the resolved title** (3b) — pass it exactly as stored, honoring only a `*` already part of it.

   **The resolved `title` IS the anchor's scope — do not broaden it.** If the environment knowledge (step 1c) says the originating service *also* logs to another cluster's / tier's stream, do NOT add that sibling stream to the anchor query when the URL already resolved to one specific `title` — the URL's data view is the user's chosen scope (operating principle: replicate, don't broaden). Add the sibling stream only if (a) the input was a Grafana URL with no resolved data view, or (b) the resolved stream returned 0 and you're walking the 0-hits ladder (3d).

   **In case (a) there is no URL scope to respect, so do not walk streams serially — query the candidates in ONE block.** When the environment knowledge says a service's logs are split across sibling streams (per cluster / tier / sink), fire those candidates concurrently within the ≤2–3 ceiling instead of trying one, waiting, and laddering to the next. A `0` from a candidate **you** chose (rather than one the URL resolved to) is an expected outcome of the fan-out, not a false zero to diagnose — take the stream that returned hits and move on. This bounds only the **anchor**: a downstream callee you trace to in step 5 is queried in **its own** cluster / stream (the cluster where *that* service is deployed) — that is following the call chain, not broadening the anchor.

   ### 3b. Why not `_all` / bare wildcards — the silent data-stream trap

   `_all`, bare `*`, and `<name>*` wildcards **do NOT match hidden indices, and data-stream backing indices (`.ds-*`) are hidden.** So any of them + a perfect filter can return **0 hits while the data exists**. **A `0` from `_all` or a `<name>*` wildcard is never authoritative** — not "no such error", not grounds for a wrong-cluster conclusion. Always query the resolved `title` from 3a verbatim. (`_all` is fine only for a quick cross-check once you know the data lives in a plain, non-hidden index.)

   ### 3c. Match your filter type to the field mapping — `.keyword` may not exist

   **Copy the URL's filter clause verbatim — same field path, same query type, same value.** URL filters carry the exact query, e.g. `match_phrase:(<service-field>:<value>)` OR `match_phrase:(<service-field>.keyword:<value>)` — replicate as-is; do NOT "upgrade" to `term <field>.keyword`, and do NOT normalize the value. A stream commonly maps its service / env / severity fields as plain `text` with **no `.keyword` sub-field**, so a `term <field>.keyword` matches **nothing** — a false `0` with no error (this has burned whole investigations). `match_phrase` on whichever field the URL names sidesteps this, and it also survives value casing (one stream's `error` is another's `Error`, one's `prod` is another's `production` — the URL already carries the right one, so copying beats guessing).

   **When the URL did NOT give you the filter** (a Grafana input, or a filter you must add yourself): take the field path and value form from 1c's per-stream mapping first. Only if the mapping is silent, sample one doc (`size: 1, _source: "*"`) or `get_mappings` to confirm the field exists and whether it has a `.keyword` sub-field. Never carry a field name over from a *different* stream — that is the single most common false zero here.

   ### 3d. "0 hits" diagnostic ladder — five causes to exclude before concluding "not found"

   1. **Querying the resolved `title` verbatim** — not `_all`, the display name, or `<name>*` (3b)? If not, re-run against the 3a title.
   2. **Drop filters one at a time** (keep the time range) — remove the severity filter, then the service filter, then the env filter. First removal that yields hits is the culprit. Three traps, in the order they bite: **wrong field name for this stream** (a name that is correct on a sibling stream and absent here — check it against 1c's per-stream mapping before anything else), **`.keyword` sub-field missing** (3c), and **value form** (a severity filter for `error` misses `Error`; an env filter for `prod` misses `production` — `match_phrase` on an analyzed field absorbs casing, a keyword-typed field does not).
   3. **Confirm the index has *any* data in the window** (time-only query). Data present but filters yield 0 ⇒ field/value/mapping mismatch, not a missing cluster.
   4. **Try the SIBLING stream family — a lateral move, in whichever direction you are not already facing.** The same service commonly logs into more than one family (a server-log stream *and* a structured-telemetry / OTEL-sink stream, per 3a's family classification), and the copies are not equivalent: coverage is partial, so some services appear in one family only, and a service can be present in one env's stream while its other env goes elsewhere. So a `0` here is never absence until you have tried the sibling family. **The direction depends on where the anchor already is** — if you are on a server-log stream, try the telemetry family; **if the anchor IS already the telemetry stream, this step is not a no-op — reverse it and try the server-log family.** Get the sibling stream name from 1c.

      **When you switch family, switch the field names AND the identity value together.** This is where the step is usually lost: the agent moves to the sibling stream but reuses the previous family's service-identity spelling, gets `0`, and concludes the service is not there. The field path can be perfectly valid while the *value* is wrong — a well-formed query, no error, and a `0` indistinguishable from real absence. Resolve the sibling family's spelling **per 3a** — probe candidate variants, do not sample the stream, and check whether the service owns more than one identity there — before calling it absent.

      A telemetry-family stream is also worth a lateral move even when the server-log stream *did* return hits, for a different reason: it commonly carries structured access-log fields (path, status code, response time) that the server-log family only has buried inside free text — which is what makes a latency check on a callee one query instead of a text-parsing exercise.
   5. **Cross-cluster — the one cause that costs a check-in, so exclude the four above first**: `mcp__elasticsearch__search` hits ONE ES endpoint, but the Kibana may federate via cross-cluster search to a remote ES you don't include. Say so and ask the user which ELK / datasource matches the URL. If browser tools + the user's session are available, offer to open the URL and read it directly.

   ### 3e. Discovery flow (fallback only — when 3a can't resolve, e.g. no `.kibana` read access)

   1. **List data streams** — `mcp__elasticsearch__list_indices`, extract unique prefixes from `.ds-<prefix>-*`.
   2. **Data-stream name / wildcard returns 0 despite backing indices existing**: pull concrete backing index names from the (often truncated) `list_indices` output with `jq`, filter to the days in your window, pass them as an explicit comma-separated `index` list. An exact single-day index is also the fastest path (least shard fan-out).
   3. **Match by name** — a display like `<x>-<y>` typically maps to `<y>-logs-<x>` / `<x>-<y>` / similar. Query each candidate by exact name (no trailing `*`), pick the one that returns hits with the expected service filter.
   4. **Ask once** if still ambiguous after looking at hits. Cache in conversation context only.

   Honor any **excluded patterns** the user mentions (test / lower-priority lines). Default: include everything. If the cluster is unclear, query all confirmed patterns (respecting the concurrency ceiling).

4. **Run the filter, surface the logs, read the dominant pattern**

   **Run the recovered filter verbatim** (from step 2, resolved per step 3: same index, same field paths, `match_phrase`): `sort @timestamp desc`, small `size` (5–10) to surface the matching logs, plus one `size: 0` + `track_total_hits: true` for the total. This is the anchor — everything downstream explains these logs.

   **GATE — Read `${CLAUDE_PLUGIN_ROOT}/skills/issue-tracing/references/es-query.md` NOW** (before firing ANY of the queries described in this step — including the third one below) for filter requirements, the aggs ban, `track_total_hits`, `size`/token budget, stack-trace dedupe, and the dominant-pattern weighting method.

   **FIRST, the short-circuit: is the anchor already ON the trace-carrying family?** If step 3 resolved the anchor's stream to the family that natively carries the trace-correlation id, the question is answered by construction — the id is in the hits you are about to read. Record `trace: available` and **send no probe at all**; this block is two queries, not three. This is not a rare corner: when the user's URL already points at the telemetry stream, it is the normal case, and probing it asks a question whose answer is in your hands. (Confirm it the moment the anchor sample returns, by checking the trace-id field is populated — not by spending a query.)

   **Otherwise, put a THIRD query in the same block: is this investigation trace-navigable?** When the anchor is on a *different* family and 1c says some family in this environment carries a **trace-correlation id** (one id shared by every log line of one request, across services), then the whole call chain may be recoverable in a single query later — which is the difference between one round-trip and one per hop. Determining that costs one query, and it belongs **in this block** alongside the two above, within the ≤2–3 concurrency ceiling.

   The query is the identity-resolution **probe** described in 3a, pointed at the trace-carrying stream — and here it must be the **single combined form**: every candidate spelling of the *originating* service in one `bool.should`, `size: 0` + `track_total_hits: true`. That keeps this block at three queries. Do **not** put one query per variant here: the anchor's two plus a per-variant fan-out breaks the ≤2–3 concurrency ceiling, and exceeding it does not merely slow things down — it exhausts the backend's connection limit and the calls never return (see guardrails). A `0` from the combined probe ends the question. A non-zero total means some spelling exists but not which, so resolve the exact spelling with 3a's per-variant counts in the **next** block — and only then, since you now know you are going to use it. Coverage is normally **partial** — a service can be absent from that family entirely — so this is a live lookup every time, never a remembered list. Probe, never sample (3a).

   **Read the result as a positive indicator for this one service only.** A hit proves it is covered. A `0` is a legitimate answer once step 3's rule — the identity value may be spelled differently in this family — has been applied, but never proof the service is uncovered (it may have logged nothing in that window), and never evidence about any *other* service: what you record is this service's spelling, not a set of covered services, and every later hop re-probes for itself (5f).

   Record the outcome in the scope note as one of:
   - **`trace: available`** + the trace-id field + **the identity spelling that hit** (and any sibling identity you established for this service) → step 5 opens with trace-first chain recovery.
   - **`trace: not covered`** (no candidate spelling for the originating service hit, and a positive control — an identity known to be present — did hit, proving the filter was biting) → step 5 uses stack-trace navigation exactly as before. Say this explicitly; an unrecorded answer means step 5 re-asks it.

   Then, still in this step:
   - **Read the dominant pattern** — do NOT trust the first sample (recent ≠ most frequent). Weight patterns by pulling `_source` and bucketing the leading lines **client-side**. Take the log-text field from 1c's per-stream mapping — it is **not** the same field on every stream, and requesting the wrong one returns hits with an empty text field, which reads as "no patterns to weight" rather than as an error. The log-text field is also usually NOT filterable, so a `match_phrase` on it silently returns a false `0`; only weight via `match_phrase` once you have proven the field is searchable (see the reference for the full method).
   - **Decode opaque values before interpreting.** If a hit carries an unreadable value (encoded payload, status bitflag, an id needing mapping) and the environment (step 1c) exposed a decode / lookup MCP tool, use it — do not guess or report the raw blob.
   - **Distinct users** — take the user-identity field from 1c's per-stream mapping; on some streams it is a top-level field, on others it sits nested inside a structured-attribute container, and on some it is an opaque / hashed subject rather than a customer id (still countable, but say in the report that it is not a customer id). If the mapping is silent, sample 1 hit (`size: 1, _source: "*"`) and look. If genuinely absent → `n/a`. If present → pull `size: 100`, dedupe client-side, report as a lower bound (note the cap). Do not spend more if the field is absent.
   - **Spike vs chronic** — when it matters for Root Cause, run the same filter over an **equal-length pre-incident window** and compare. Ratio ≈ 1 ⇒ chronic background / by-design, not caused by this incident (exclude from Root Cause). Sharp spike ⇒ event-driven.
   - **Then find the event's actual boundary — widen the window until you can see the signature's background rate.** A ratio tells you the signal rose; it does not tell you where the event starts and ends, and those edges are what make the report actionable. Re-run the *same signature* over a much longer window (an hour, a few hours) with `size: 0` + `track_total_hits`: if the total is unchanged from your incident window, the background rate is **zero** and the event is fully contained — a far stronger statement than any multiple, because "it never happens otherwise" beats "it happened 8× more". If the total keeps climbing as you widen, it is chronic and the incident window was an arbitrary slice of it. Then pull the matching hits sorted ascending and descending to get first and last occurrence: that is the burst shape, and a flat rate across it versus a tight cluster distinguishes a steady per-request condition from a batch job or a single upstream event — a distinction that changes How to Resolve, not just the narrative.

   **Before leaving this step, when the stream exposes structured access fields (status / path / duration): the list of requests that actually failed.** Filter status ≥ 500 over the same window and keep the paths and durations. Gather it here, while you are already in the anchor — discovering at report time that you never established which requests failed means going back for it with the investigation's context half gone. It is also the input to `report.md`'s HARD RULE 6, which forbids writing an error count into Impact as if it were a failure count.

   **When the stream carries no structured access fields but does log an access-severity line, that line is the substitute — and it is usually positional.** A framework's request-logging middleware writes the same field order on every line, so pulling the raw log-text field over a narrow window and splitting it client-side yields all three outcome numbers above. It is a client-side parse rather than a query because that text field is typically not filterable, so no numeric range on status or duration exists. **Derive the field order from one sampled line and parse against that** — the order varies by middleware (e.g. timestamp, method, host, path, status, duration, client address), and a positional guess carried over from another service produces wrong statuses silently. The client address it also yields is the cheapest evidence for the caller-concentration question the trigger classification needs (`report.md` HARD RULE 4, axis C). On this path the latency paragraph below spends no query of its own — the same parse already carries the durations to bucket.

   **A request that succeeded after twenty seconds is an impact too — measure the spread, do not count against a guessed threshold.** Failure is not the only outcome that reaches a user, and the degraded ones are usually the larger group. Pull the duration field for the window (one query, `_source` limited to duration + path) and **bucket the values client-side** — aggregations are stripped by the wrapper, so a histogram is not available, but a few dozen numbers bucket fine in one pass. Report the shape: median, worst, and how many fall in each band.
   - **Choose the cut FROM the distribution, never in advance.** A threshold picked before looking sweeps in whatever chronic slowness the service always has: one run guessed "≥5s", got a 1.8× ratio against baseline, and learned nothing — while the actual incident sat at 12–19s, far above anything normal. Look first, then draw the line where the incident population separates from the background.
   - **Sample for the tail, not for the median.** The affected requests *are* the tail, so a slice that misses them reports the window's ordinary latency as the incident's. Cover the whole window, and **do it by the mechanism the token budget allows, never by raising `size`** — that is where the paragraph's one-query assumption breaks, so say how many queries it took. Which mechanism depends on where the durations come from: a **structured duration field** projects small, so walk the window with successive `from` + `size` pages until it is covered; a **positional parse of the log-text field** is still under that field's `size: 5` cap (`es-query.md`, token-budget rules), and paging it 5 at a time does not scale to a whole window, so take that file's other route — let the wrapper truncate the response to a file and `grep` / `jq` the whole dump. Where neither covers the window, state what share you did cover — one arbitrary offset page of a large result set is not a sample of the distribution. One run reported a 390ms median and a 1.2s max from 60 of 1245 access lines, while the requests that had actually queued ran to 4.4s in the very same log, and the figure reached a ticket before it was caught.
   - Skip this entirely when nothing succeeded slowly, and say so. The point is a number for each outcome, not a section that must be filled.

   **Last on the outcome list: did the clients whose requests failed come back and succeed?** A retry happens after the failure by definition, so the buffered anchor window cannot contain it, and an empty result inside that window looks exactly like nobody retrying. Widen to a window that starts at the burst and **runs past its end until no further attempt appears**, then match each failed request's client identity against the later successes. **Route that match by what the stream offers, exactly as the two paragraphs above did**: a structured client field can be filtered server-side, while on the access-line path the client address sits inside the log text — not filterable, so a `match_phrase` there returns a false `0` that reads as "nobody retried", and the honest route is to widen the same client-side parse. Measure each gap from the **end** of the failed attempt, which is when the user saw the error. **The widened window is a bigger pull, so it lands under the same token budget the tail bullet above already routes** — page a structured field, dump-and-grep a log-text parse; a `size: 5` pull over the wider window produces a false "none" from the other direction. On the access-line path one wide pull serves this and the outcome list together, so widen once instead of pulling twice. `report.md` HARD RULE 8 turns the answer into the difference between "<N> users were blocked for half a minute" and "<N> users were lost", so this is the cheapest severity-defining number in the whole report.

   Output of this step: the originating project, the error shape, the weighted dominant pattern, scale, affected users (if available), and a number for each request outcome (failed / degraded / unaffected) plus how many of the failures the user retried into a success — off the structured access fields where the stream has them, off the access-line parse where it does not. Only then enter the trace loop.

   **Infra-first pivot (no log correlate).** If the filtered logs are genuinely empty but the signal is real — typically a pure-infra Grafana alert (CPU / memory / saturation / restart) with no error-log correlate — and you have confirmed via the 0-hits ladder (3d) that the query is correct and the index has data, do NOT stall waiting for a failing code path. Set `current` = the service the alert/panel pointed at, still run **5a** to classify ownership (an infra check on another team's service stops at the boundary too), then jump to the **infra check (5d)** — skipping 5b/5c, which need a log-derived code path you don't have — and continue the loop normally (5e onward) from whatever the infra numbers reveal.

5. **Trace to the root cause — the autonomous loop**

   **If step 4 recorded `trace: available`, recover the chain FIRST — one query, then verify. Do not walk it hop by hop.**

   The default loop below discovers one hop per round-trip: read a hit, extract a host, resolve it to a service identity, query that service's logs, repeat. When a trace-correlation id is available, the same chain comes back in **one** query, because every service's log lines for that request already carry the same id.

   ### 5.0 Trace-first chain recovery

   1. Take the trace id off the anchor's dominant-pattern hit (the one you would have started reading anyway — this costs nothing extra).

      **If the anchor's family has no trace field, check whether it carries a request / correlation id that IS the trace id.** A stream family without an explicit trace field often still stamps a per-request id (`requestid` / `correlationid` / a request header echo). Where the whole platform shares one request-id propagation, that value **is** the same id the telemetry family stores as its trace id — which means an anchor on the *non*-trace family is still trace-navigable, at the cost of zero extra queries. **Screen the id's shape first** (first bullet below) — one shape retires the bridge with no query spent. Otherwise test it once: take the id off the anchor hit and query the telemetry family's trace field for it. Non-zero ⇒ the two are the same id, and you have the bridge for the rest of the investigation; zero ⇒ this service does not carry that id, so fall back to hop-by-hop for it without concluding anything about the remaining hops.
      - **The shape rules a bridge OUT cheaply; it never rules one IN.** A `<connection>:<counter>` pair is a per-connection identifier the web server minted for its own log, has no counterpart in the telemetry family, and retires the bridge with no query spent. A fixed-length hex value only *may* bridge — a correlation id generated as a plain random uuid carries the identical shape and joins nothing — so a hex value is settled by the test query above, never by its shape alone.
      - **Normalize the value before using it.** A correlation id in a free-form log line can arrive with parsing debris attached (a trailing bracket, a concatenated second value, whitespace). Extract just the id-shaped token — a trace id is a fixed-length hex string, so anything after it is debris, not part of the id. Querying the raw value returns `0` and looks exactly like "the ids are unrelated", which would wrongly retire the bridge for the whole investigation.
   2. Query that id: `match_phrase` on the trace-id field **plus a time range**, `sort` ascending, bringing back service identity + logger / code-location field + log text + the per-hop span id. **The time range is mandatory** — a trace-id filter with no time bound scans the whole stream and times out; it is selective, not cheap. **Widen the window slightly past the anchor's**, since a downstream hop can be timestamped just outside it.
   3. Read the chain off the result, ordered by time: the entry-point service and its status, each service it called, and where the failure first appears. Group by span id for the per-hop boundary.
   4. **Then run the loop below over that chain — as verification, not discovery.** 5a still classifies ownership at each hop (a trace shows you a boundary service's line; it does not make its internals yours). 5b still reads the code at the hop you suspect. 5d still fires when the shape is infra-shaped. What the trace removes is the *hop-identification* round-trips (step 5e's work), not the judgment.

   **The two families are complementary, so use both rather than switching allegiance.** Where the telemetry family carries the chain (trace id, next-hop identity, structured access fields), the server-log family typically carries the **local mechanism** — the full exception with inner exceptions and `file:line`. Neither is a superset: the trace tells you *where* to look, the stack trace tells you *what broke there*. So at the hop you suspect, read that hop's server-log exception even though you found the hop via the trace.

   **A trace shows what was instrumented, not what exists.** See 5f's coverage-end rule before treating the last hop as the origin.

   ---

   Set `current` = the originating project and start at 5a (on the infra-first pivot from step 4, still run 5a, then jump to 5d). Then loop:

   ### 5a. Classify `current` (the drill boundary)

   Using the environment knowledge (step 1c):
   - **Another team's service / not in your knowledge base → BOUNDARY. STOP the drill.** Record the hop and the boundary in Unknowns. The report may state what this upstream returned (e.g. 503 / timeout); *why it failed inside* belongs to its owner.
   - **Your team's service, resolvable locally under the project root** → read its code (5b).
   - **Your team's service but the repo is not present locally** → the root should let you read it (per step 1b / the environment's local-repo convention). If you still cannot read it, say so precisely (which repo, where you looked) and list it in Unknowns; continue only with what you can confirm. Do not silently guess its internals.

   ### 5b. Read the failing code path in `current`

   - **Locate the failure** from log clues (URL path, controller / method / function name). Inspect its error handling and outbound calls.
   - **Is the error produced here, or a downstream symptom?**
     - *Produced here* = a real defect or intended behavior in this service. Use `git blame` on the failing line + the introducing commit message to tell intent from defect. Intent being correct (e.g. deliberately rejecting a bad token) does NOT make the implementation correct — returning an unhandled 500 instead of a 403 is still a defect.
     - *Downstream symptom* = an outbound call failed / timed out / returned 5xx; the top-of-stack exception here is the *effect*, the cause is the next hop.
   - **User-visible surface** (mandatory when the report's Impact will describe what the user sees, and the frontend repo is present): if `current` is a `-backend` / `.backend`, locate its frontend repo under the root (`<base>.frontend` / `<base>-frontend`) and read the call site — is the error caught? fallback / placeholder / blank? retry? Backend code alone cannot tell you how it surfaces.
     - **A grep by the backend endpoint name (`GetPopup`, `GetUnreadInfo`) often misses** — the frontend names the call differently (generated client, wrapper method, i18n key). When it does, do NOT give up and punt to Unknowns; widen the search: the **route path string** (`/Notification/`), the **frontend API-client / composable method name**, the **feature / widget / component name**, or the **i18n key** shown in the UI. And the surface may live in a **shared header / footer or a parent SPA repo**, not the page repo (a mobile notification badge / popup is a shared component) — check those repos under the root too.
     - Only put frontend behavior in Unknowns when the repo is genuinely absent, or the call path truly cannot be located after the above — say which repo you searched and how. Do not leave Impact's user-visible line as a guess when the repo is right there.

   ### 5c. Confirm against ELK

   For a **pass-through hop** (its error points downstream), you usually already have what you need without another query — from the stack trace on a server-log family hit (the failing outbound call + host + timing are in it), or from the recovered chain if 5.0 ran (the next hop's identity and URL are already there). Do not stop to deep-confirm every hop; a light check to identify / confirm the next hop is enough, then move on (proportionate-depth rule). Query `current`'s own logs here only to fill a genuine gap the trace didn't show (which outbound call, which host, the burst window). The **deep confirmation — timing, burst window, baseline/correlation — belongs to the suspected root-cause hop**, as the single verification pass before Root Cause; apply the baseline/correlation check there before folding any sibling pattern in. Do not assert a *root cause* from code alone.

   ### 5d. Verify infra when the error shape is infra-shaped

   This is the **deep-verification pass** for an infra-shaped root cause (proportionate-depth) — you run it to confirm whether `current` (or the shared dependency it hits) is actually the root, not as a reflexive metric pull on every hop you pass through. **Gate it first: does the log already name the fault?** If the hop's own error log already states the mechanism (an explicit `Timeout of Ns elapsing`, a downstream line naming its failing resource, a FusionCache / Redis / connection-pool exception), you already have what Root Cause needs — record it and skip the metric pass. Otherwise, when the shape is infra-shaped **and** the logs don't say why (or the report needs the number), verify infra metrics before writing Root Cause.

   **First, a cheap breadth classifier — is this isolated or fleet-wide?** When the infra-shaped signal points at a **shared dependency** (a shared Redis / DB / cache cluster, DNS, a shared gateway — anything many services use), run the breadth check **BEFORE drilling deeper**: the same infra exception (e.g. the `*TimeoutException` / connection error), the same window, with the **service filter dropped** — a `size: 0` + `track_total_hits` for the total, a small sample with `_source` limited to the stream's service-identity field, and the same `size: 0` count **with the service filter restored** (the subtraction below needs it). Send all three in **one block** — three concurrent queries, at the ≤2–3 ceiling — and it forks the whole investigation.

   **Decide the fork by ARITHMETIC, not by the sample's service list.** The sample is sorted by time, so it is swamped by whichever service emits most — a second, quieter service can be in the result set and never appear in the documents you see (3a's rule, same trap). So read it in one direction only: **another service showing up is positive proof of fleet-wide.** Its *absence* proves nothing. To settle absence, run the **same query once more with the service filter restored** (`size: 0` + `track_total_hits`) and subtract. The two counts must use the **identical exception signature and window** — the anchor's count from step 4 is NOT this number (it covers all of that service's errors, not this one signature), so comparing against it makes the fork meaningless in whichever direction the two filters happen to differ. With matched filters the arithmetic is exact: total equals `current`'s count ⇒ genuinely only `current`; any excess is other services' documents whether or not the sample showed them ⇒ fleet-wide, and identify them by probing candidates rather than by re-sampling. (A small excess whose timing does not line up with the incident is background noise — the discipline note below already covers that; it does not make the subtraction unreliable.)
   **Before taking either branch, write down the SIBLING deployments of `current` this query surfaced** — the same service's other identities serving the same endpoint, which you naturally `must_not` away to see whether *unrelated* services were hit. That exclusion is right for the isolated-vs-fleet question and wrong for the **trigger** question, which `report.md` HARD RULE #4 demands on **both** branches: those siblings are the first candidate load sources for axis **C**, and an anchor-only count reads a sibling's surge as "no surge". Record the list with the scope note — the home 3a already gives a service's sibling identities — and take it into the caller-direction drill in `references/next-hop-drill.md`. Discarding it with the query is how the trigger verdict silently lands on B or D.

   - **Isolated** (the arithmetic above shows the filter-dropped total is `current`'s own count) → it is a per-service problem (a real bug / a specific downstream / a caller-side change). Continue the chain drill normally (fall through to the infra check, then 5e's next hop).
   - **Fleet-wide** (the same exception hits several unrelated services / pods at once) → the root is the **shared infra layer**, not any one service. **Stop extending the single call-chain** — do not keep drilling service→service→its-redis when the breadth query already proves it is shared. Keep the chain you already have (originating user-facing service → the point it hits the shared resource) — you still need it for Impact — then pivot to: identify the shared resource instance(s), judge datastore-itself vs network path, and escalate to the infra owner (see the infra-metrics and report references loaded at 5d's and step 6's GATEs). This is faster than a 5-hop drill and avoids mis-blaming one downstream service. Treat the fleet-wide branch as a **loop exit** (root layer identified) — do NOT fall back into 5e looking for another service hop; after the §11g datastore-vs-path judgment in `references/infra-metrics.md`, go to step 6 and report.

     **A fleet-wide verdict obliges you to quantify the OTHER callers it names — same cause, so they belong in Impact.** Reporting "the shared layer failed" while showing a single victim contradicts itself, and it is the first thing a reader will challenge: a shared dependency that hurt exactly one of its consumers is not a shared-dependency story. You already have what you need — the same signature, the same window — so peel the other services out of the breadth query (`must_not` the ones you have accounted for, repeat until it returns 0; that also proves you found them all) and get **the same few numbers you got for the anchor**: how many failed, how many of those the user retried into a success, how many were slow, how many distinct users. A bare failure count misreads as user loss for a caller exactly as it does for the anchor (`report.md` HARD RULE 8), and `not checked` is a legal answer for the retry number as long as Impact says so. That is two or three queries per caller, not a second investigation — do not drill their call chains, read their code, or check their infra.
     - **Same signature is the test, not the same alert.** A service hit by a *different* exception, or by the same one outside the burst, is a separate story: name it and move on. What obliges coverage is sharing this root cause.
     - **Breadth discovery does not need a particular stream family** — the query is "same signature, service filter dropped", which works wherever your anchor already is. (Verified on one incident: the co-affected caller was present in both families, with *more* lines in the server-log family than the telemetry one.) Only the per-caller *outcome* numbers need a family carrying structured status / duration; without one, say what you could establish and mark the rest as not quantified.
     - If you genuinely cannot cover a co-affected caller, the report must say the impact figure is a **lower bound** and name who is missing from it — not quietly scope Impact to the anchor.

   The classifier keys on the **signal shape** (an infra exception against a shared dependency), not on any specific technology — do not hardcode one exception name; it is a general "isolated vs shared" fork.

   **Discipline — the breadth query is the ONLY early fork; everything else stays on the chain.** The isolated-vs-fleet breadth query above is the one query you may fire before drilling deeper — and only when the signal genuinely points at a **shared datastore / network layer** (Redis / DB / DNS / shared gateway), NOT when `current` is an ordinary service whose own logs / metrics you are about to read next anyway. For anything else — hunting other root causes, corroboration, sibling services that are not the shared resource — stay on *this* chain (5a→5e) until it reaches the root cause or is genuinely stuck; eager divergence wastes the user's time and tokens. Two hard rules when you do fire the breadth query: (1) it is the **same-signature** query (same exception + window, service filter dropped), **never a generic all-service error count** — that only drags in unrelated chronic noise you then burn queries ruling out; (2) if `current`'s own data already shows it **healthy + serving normal traffic**, shared-saturation is already falsified — **skip the breadth query**. A fleet number whose exception signature or timing does not match the incident is background noise: note it and move on, do not chase it with baseline queries.

   **GATE — Read `${CLAUDE_PLUGIN_ROOT}/skills/issue-tracing/references/infra-metrics.md` NOW** for the full procedure (anchor on prod config first, service-token extraction, datasource-first query flow with Prometheus + InfluxDB recipes, mandatory CPU + Memory + restart/replica + throttle scan, mean+max at ≤1-min bins, the reverse-signal sanity check, and the enumerate-then-batch rule).

   ### 5e. Decide the next move

   - **Root cause confirmed at `current`** → exit the loop.
   - **Points to a downstream hop** → set `current` to the next hop, then repeat from 5a. **If 5.0 recovered the chain, the next hop is already known — take it from the chain and do NOT re-derive it here**; re-running the identification ladder against a hop the trace already named is the round-trip 5.0 exists to remove. Otherwise identify it now; read `${CLAUDE_PLUGIN_ROOT}/skills/issue-tracing/references/next-hop-drill.md` for how to identify the next hop (URL/host in the error → log naming another service → outbound config in code → the environment's dependency docs), the **slow-but-healthy pointer** (a 200-but-slow hop is blocked on *its* downstream — keep going, don't blame it), the **caller-direction drill** (when the question is *who triggered* it — bot / surge / new data), and the correlation check.
   - **Stuck — cannot confirm a root cause at `current` AND cannot identify a next hop** (e.g. `current`'s repo or logs are unreachable per 5a) → exit the loop and report what you have, recording the gap in Unknowns. Do not spin waiting for a signal that isn't reachable.

   ### 5f. Loop discipline

   - **HARD RULE — a chain that ENDS is not the same as a root cause found.** When the last hop you can see is a service, there are two indistinguishable explanations: that service **is** the origin, or your **visibility** ended there. On a trace-recovered chain (5.0) this is the dominant failure mode, and it is worse than the hop-by-hop equivalent: hop-by-hop, running out of leads *feels* like running out of leads, whereas a trace that simply contains no further service reads as a complete picture. Before naming the last hop as root cause, rule out visibility-end on all three of its forms:
     - **Coverage end** — the service emits nothing to the trace-carrying family, so its callees are invisible by construction. **Check it with a query against that service specifically; do NOT settle this from step 4's sample.** Step 4 sampled whichever services happened to log in a slice, so a service missing from it may simply not have appeared — treating that absence as "uncovered" (or its presence as the only way to be covered) decides the root cause on sampling luck. Resolve this hop's identity value per 3a, query the trace-carrying family for it directly, and if it is genuinely absent, resume normal navigation in the *other* family. Absence from a trace is never evidence a call did not happen.
     - **Ownership end** — it is another team's service (5a). That is a legitimate stop, but it is a *boundary*, not a root cause: report what it returned and leave its internals to its owner.
     - **Instrumentation end** — the service is covered, but the specific outbound call is not instrumented (a client library, a raw socket, a datastore driver). Its logs and its code still name the dependency; the trace just does not.

     Only when all three are excluded may the last hop be reported as the origin. If you cannot exclude them, say so — Root Cause states the chain you confirmed and Unknowns names what ended the visibility and where. **Never write a root cause whose only support is "the chain stopped here."**
   - **Every hop must be backed by real call data** — a host in an error, a log naming the service, an outbound call in code, or a documented dependency. Never invent a hop. A trace-correlation id shared with the anchor **is** real call data, and it is the strongest kind (it is the request itself, not an inference from a hostname).
   - **Boundary-driven, not count-capped**: keep drilling through your team's services until you reach the root cause or an ownership boundary (5a). There is no fixed hop limit — but if the chain runs unusually long (**runaway guard: ~5 hops**), stop, lay out the full chain, and hand the decision to the user.
   - **Write the running chain in chat as a short note** (`originating → hop A → hop B …`, with each hop's role: erroring / slow-but-healthy / root cause / boundary), and the infra query list when 5d fires. This is internal auditability — write it and keep going; do not wait for the user.

6. **Produce the report**

   **GATE — Read `${CLAUDE_PLUGIN_ROOT}/skills/issue-tracing/references/report.md` NOW** for the full procedure (pre-report evidence dump, HARD RULES on Impact wording, the GMT+8 rule, the two-layer Root Cause with trigger-source-first, and the Chinese-full + English-short templates). Do not start writing before reading.

   Write the report once the loop exits with a confirmed root cause, or with a clearly-recorded ownership boundary (state what the boundary upstream returned and that the internal cause is the owner's).

- **The output is confidential even though the skill is not — check where you are writing it.** This guardrail governs the skill's own files; the report and any run log it produces are the opposite, because a real investigation collects exactly what the skill must never contain: internal hosts and FQDNs, pod names, internal IPs, customer ids, player IPs, tokens. **Before writing any of it to a file, establish whether that destination is public** — a repo (check its remote / visibility), a shared drive, an issue tracker, a paste service. If it is public, or you cannot tell, do not write it there: keep it in the conversation, or write it somewhere local and ignored, and say plainly why. Writing to the same repo the skill lives in is the easy mistake, because that repo is open by design.
- **No unbounded ES queries.** Every search MUST include a time-range filter + a service filter + a severity filter + a `size` cap — using whatever those fields are called on the stream you are querying (1c's mapping). The severity filter is not optional on a high-volume stream: a stream carrying every level (not just errors) holds orders of magnitude more documents than an error-only one, so omitting severity is how a scoped query still turns into a full scan.
- **Cap concurrent ELK / Grafana MCP calls.** These backends sit behind a connection / rate ceiling; firing many `mcp__elasticsearch__search` / `mcp__grafana__*` calls in one block exhausts it and the investigation hangs. Send **at most 2–3 in parallel per block, wait, then send the next**; on any connection / timeout / rate error, drop to **sequential**.
- **Filter type follows the URL clause or 1c's mapping, never a defaulted `term <field>.keyword`** — 3c owns the rule, `references/es-query.md` the query shape.
- **Field names and values are per-stream; 1c's mapping outranks every example in this skill** (1c, AUTHORITY). A `0` from a field name you did not get from the URL or from 1c is a bug in your query, never a fact about the data.
- **Resolve the data view before trusting any count** — a `dataViewId` and a display `name` are not index names; query the `.kibana*` `title` verbatim, never with `*` appended (3a / 3b).
- **Where `*` is dangerous vs fine** — the heap-killer is an unbounded full scan, not the character `*`:
  - `query` / `match_all` with no filter → **forbidden** (exhausts ES heap).
  - Index-level wildcard (`.ds-...-prod-*`) or `_all` → allowed ONLY with a strong filter (project + time + level), but prefer an exact single-day backing index (faster, avoids multi-shard fan-out); a `0` from any of them is never proof of absence (3b).
  - `_source: "*"` → fine, but use it once to inspect schema, then list only the fields you need.
- **Counting rows: `size: 0` + `track_total_hits: true`, NEVER aggs** — the search wrapper strips agg results, and an untracked total caps at 10000 (`references/es-query.md`). One filtered `size: 0` query per bucket.
- **Never carry a credential out of a log line.** On an auth / token / session failure the log text can **be** the credential: name it by exception type and role and truncate the value, in everything written to chat from the first sample on — a quoted log line, the chain note, the evidence dump — not only in the report. `references/report.md` HARD RULE 0 holds the full rule.
- **No fabricated numbers.** Distinct users, request counts, customer ids — only what the query actually returned. Missing field → `n/a`, never estimate.
- **No fabricated root causes.** If code is needed and unavailable, Root Cause says "需要看 code 才能確認" and Unknowns requests the repo path. Do not pattern-match a guess.
- **No fabricated unknowns.** Unknowns may contain only: (a) facts about a service owned by another team (the boundary at 5a), (b) data the tools / permissions cannot reach after trying — say precisely what you tried and what you need, (c) a decision that needs a human. Anything an MCP query can answer is NOT a valid Unknown — go check it.
- **Same-name service across clusters is the default, not the exception.** A service may run in multiple tiers (RKE / GKE / VM / multi-region) at once. Anchor on prod config (hostname / DNS / IP from the caller's source) before touching metrics — see `references/infra-metrics.md`.
- **Project → repo mapping is per-user.** Resolve from the known root (working dir / add-dir / the environment's local-repo convention). Never hardcode paths in this skill and never persist them to memory.
- **Honor user-mentioned excluded indices.** Exclude patterns the user says to skip; include them only if explicitly asked.
- **Output language order is fixed**: Traditional Chinese first (full), English second (super-short two lines). No language headings. Order: Root Cause → Impact → How to Resolve → Unknowns.
- **Warning level**: include only when the originating signal is warning-level or the user asks. Always count warning separately from error/fatal.
