# 变更风险检查清单

## 概览

从代码 diff、配置、依赖和运维控制面评估生产发布风险。核心原则：区分已验证证据和推测。

## 使用场景

用于 Java / Spring Boot 发布评审、分支或 tag 对比、生产配置核查，以及用户提到变更风险、上线评估、发布风险、配置核查、回滚方案、兼容性检查等场景。

除非用户明确要求发布风险评估，不要用于普通代码风格评审或本地问题调试。

## 必要输入

只询问无法推断的缺失信息：

- 基线版本：线上分支、tag 或 commit
- 目标版本：待发布分支、tag 或 commit
- 生产生效配置文件或 profile 名称
- 必要的部署上下文：实例数、JVM 内存、DB/Redis 限额、网络隔离、监控平台

信息不全时，先评估可验证部分，并把受影响检查项标记为 `⚠️ 待确认`。

## 执行流程

1. 通过 `git diff --stat`、变更文件列表和关键配置文件确定范围。
2. 先读取生产生效配置，再判断环境配置风险。
3. 沿调用方、运行时装配和配置引用追踪变更代码路径。
4. 套用 [change-risk-checklist.md](change-risk-checklist.md) 的详细检查项。
5. 先报告阻断级问题，再输出完整检查明细。

## 证据规则

| 结果 | 使用条件 |
|---|---|
| `✅ 通过` | 证据直接证明该项安全或未变化。 |
| `❌ 不通过` | 证据表明存在真实违规、回归或缺少必要控制。 |
| `⚠️ 待确认` | 代码无法证明、需要外部平台数据，或缺少发布上下文。 |
| `N/A 不适用` | 该项与当前服务或变更范围无关。 |

每个非 `N/A` 结论都必须给出具体证据：文件路径、配置键、类名、接口路径、依赖名称或执行过的命令。

## 严重程度

| 严重程度 | 使用条件 |
|---|---|
| `🔴 阻断级` | 发布前必须修复，或由负责人明确接受风险。 |
| `🟠 高风险` | 强烈建议发布前修复。 |
| `🟡 中风险` | 建议优化或纳入跟踪。 |
| `🔵 低风险` | 可作为后续改进。 |

出现安全暴露、生产误连非生产系统、不兼容的公开 API 删除、运维端点缺少鉴权、不可逆 DB 变更且无回滚方案、核心行为变更且无回滚方案时，提升为 `🔴 阻断级`。

## 检查重点

优先关注 API 兼容性；生产配置中混入 `beta` / `sit` / `dev` / `test` / `localhost`；定时任务、消费者、连接池、线程池、重试、超时；DB/Redis/HTTP/Tomcat/JVM/日志变更；监控指标；密钥和敏感日志；端点鉴权；DDL 和配置回滚。

## 输出模板

按以下顺序输出：变更概要 → 🔴 阻断级问题 → 🟠 高风险问题 → 🟡/🔵 中低风险 → ⚠️ 待确认事项 → ✅ 正面改进 → 检查明细。

每个问题包含严重程度、问题描述、证据、影响和建议动作。

## 常见错误

- 没有平台证据就把平台项标为通过。应标记为 `⚠️ 待确认`。
- 只看变更文件。还要追踪调用方、配置、生成产物和运行时装配。
- 认为生产配置中的 test/dev 关键词无害。
- 报告风险但不给精确文件、配置、类或接口证据。
- 把阻断级问题埋在完整检查表里，而不是优先列出。
