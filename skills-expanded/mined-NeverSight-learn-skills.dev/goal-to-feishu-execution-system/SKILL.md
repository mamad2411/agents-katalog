# Goal to Feishu Execution System

当前合同版本：`0.7.0`。

把长期目标推进为经过验收的计划和飞书执行系统。核心不是复制固定模板，而是保留目标澄清、计划收敛、本地 Markdown 交接、系统建模、写入和读回验收的决策链。

核心循环是 **读回闭环**：核验 → 确认 → 读现状 → 设计 → dry-run → 写入 → 读回 → 分类 → 交付。写入返回只能证明请求被接受；完成结论必须以同一目标的本次读回为证据。

真源按职责分层：

- `goal-plan.md` 是目标与约束真源。
- 实时 Base 读回是实现真源。
- `feishu-system-contract.md` 是证据索引，记录真实 ID、配置、读回结果和未完成项。
- `system-guide.md` 和 `manual-setup-guide.md` 是用户交付物，必须与前三者保持一致。

**运行时依赖只有 `lark-cli`。** `lark-shared` 和 `lark-base` 是可选的参考 Skill：如果本机已经安装，就读取它们来获得认证和 Base 命令护栏；如果没有安装，不因此阻断流程，改用当前 CLI 的 `--help`、`schema` 和本 Skill 的最小权限/读回门禁。不得为了运行本 Skill 自动安装整套飞书 Skill。

## 状态机与阶段出口

| 状态 | 可执行范围 | 进入条件 |
| --- | --- | --- |
| `blocked` | 停止外部写入 | 工具、凭证、身份、目标资源或组织策略阻断 |
| `planning_only` | 澄清、计划和系统草案 | 预检可用，但目标基线、计划交接物、写入目标或 schema 尚未完整确认 |
| `ready` | 可开始外部写入 | `goal-plan.md` 已读回，且目标 Base、shared schema、通知对象、身份与最小 scope 全部确认 |
| `partial` | 继续补齐结构、读回或人工验收 | 已有真实写入，但关键合同、权限或运行时验收尚未通过 |
| `complete` | 交付并停止扩张 | 八项交付物均完成读回，且没有未完成的关键权限、运行时或人工验收项 |

状态只能按证据前进；后续读回发现缺口时，应从 `complete` 或 `ready` 回退到真实状态。

## 0. 工具与身份门禁

先运行：

```bash
bash .agents/skills/goal-to-feishu-execution-system/scripts/preflight.sh
```

- `blocked`：停止外部写入，报告具体缺口。
- `planning_only`：可以继续形成计划和系统草案，但不能声称已经创建飞书系统。

CLI 缺失时，只能在用户明确同意后单独安装 CLI；不要调用会顺带安装整套 Lark Skill 的一键向导：

```bash
npm install -g @larksuite/cli@latest
```

如果用户明确需要认证和 Base 操作参考，再按白名单安装可选 Skill：

```bash
npx skills add larksuite/cli -g -y --skill lark-shared lark-base
```

检测到其他全局 `lark-*` Skill 时只报告，不在运行时自动删除；清理必须作为单独、明确确认的维护动作执行。

配置、登录或新增权限都属于外部状态变化。不得静默执行；不得把网页端登录当作 CLI 登录；不得输出 Token、用户码、组织敏感信息。

**阶段出口：** 已读回预检的 `status`、`reason` 和当前身份；`blocked` 时停止，否则以 `planning_only` 继续目标澄清。

## 1. 澄清目标

内部数据模型不等于用户提问文案。不要向用户暴露内部字段名；用日常语言提问，并在问题可能抽象时给一个与用户目标相关的简短例子。用户可以回答“不知道”“还没想好”或“你先建议”，此时根据已经确认的信息给出少量候选，让用户选择或修正，不能替用户直接确认。

默认使用两段式逐题澄清：

1. **先问形成候选计划所需的必答问题**：想完成什么、希望什么时候看到结果、现在进行到哪一步、一周大概能拿出多少时间、有哪些不能被计划打破的限制。每轮只问一个会改变计划的问题。
2. **系统偏好在候选计划之后再问**：再忙时也愿意完成的最小一步、多久回看一次进度、是否需要提醒、是否让其他人参与监督、哪些内容不能被他人看到。只问与最终飞书结构有关的问题。

用户希望一次回答时，提供批量模板；允许留空或用自然语言自由描述，由 Agent 在内部映射为目标、期限、基础、时间、限制、最小执行单元、反馈节奏、提醒和隐私边界：

```text
1. 你想完成什么？为什么现在想做这件事？
2. 你希望什么时候看到结果？没有硬期限也可以写“大约三个月”。
3. 你现在已经做到哪一步了？完全没开始也可以。
4. 你一周大概能拿出多少时间？哪些时间比较固定？
5. 有什么事情不能被这个计划打破？例如不能熬夜、预算有限、周末要陪家人。
6. 特别忙的时候，你觉得自己最少还能做哪一步？不知道可以写“请你建议”。
7. 你希望多久回头看一次进展？例如每天简单看、每周复盘或每月调整。
8. 需要飞书提醒你吗？什么时候提醒不会打扰你？
9. 只给自己使用，还是希望其他人也能看到进展？有什么内容不能共享？
```

不得把当前对话、工作区文件或历史记忆中的个人信息直接当作已确认输入。发现可复用上下文时，先列出拟导入的信息并询问是否采用；用户没有明确同意时，从空白输入开始。快速验证也不得跳过目标澄清，不能为了省时间自行确定目标或约束。

澄清完成后先输出“候选目标基线”，区分已确认事实、假设和待验证项。只有用户明确确认后，才形成正式目标基线并进入计划收敛。

**阶段出口：** 用户已明确确认目标、期限、当前基础、可用时间、现实限制和关键系统偏好；假设与待验证项已单独列出。

## 2. 收敛计划并生成本地交接物

计划收敛必须由本 Skill 独立完成，不得要求或默认依赖 `brainstorming` 或其他规划 Skill。只内化本场景必要的有限能力：

1. 根据已确认目标和约束，给出 1–3 条可执行路线。
2. 对比时只解释会改变选择的取舍，不做无边界发散。
3. 校验期限、可用时间、现实限制和最小行动是否自洽。
4. 明确给出推荐路线、不选其他路线的理由，以及需要用户修正的假设。
5. 将推荐路线收敛为候选计划：目标与边界、阶段计划、每周节奏、最小执行单元、指标与复盘方式、风险与停止条件。

如果宿主环境因更高优先级规则调用了外部规划 Skill，必须在输出中披露；该轮候选计划不得记为本 Skill 的纯复测证据。对外发布时也不得宣称这轮结果完全由本 Skill 产生。

输出候选计划时，同时给出拟保存路径。用户未指定时，默认为：

```text
./goal-to-feishu/<goal-slug>/goal-plan.md
```

用户确认候选计划后，必须先生成本地 `goal-plan.md`。若文件已存在，先读取现有内容，再增量更新并递增 `version`；不覆盖无关内容。文件至少包含：

```markdown
---
status: confirmed
version: 1
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
---

# <目标名称>

## 已确认事实
## 假设与待验证项
## 目标与边界
## 阶段计划
## 每周节奏
## 最小执行单元
## 指标与复盘方式
## 风险与停止条件
## 飞书建模输入
```

写入后读回文件，核对状态、版本、目标、约束、阶段和节奏与用户确认的内容一致。未生成并读回确认 `goal-plan.md` 前，不得进入飞书系统建模。

**阶段出口：** `goal-plan.md` 已生成并读回，其状态、版本、目标、约束、阶段、节奏和飞书建模输入与用户确认结果一致。

## 3. 建模系统

以已读回确认的 `goal-plan.md` 为计划真源，推导任务、打卡、提醒、反馈和复盘机制。先给出表、字段、关系、视图、自动化和验收草案，等待用户确认 shared schema 与通知对象。

不同目标重新设计结构；不要复制四级或 CPA 的表数、字段名和任务粒度。

处理 Dashboard、动态视图、formula/lookup、workflow 或权限分支时，先读取 [`references/lark-cli-contract.md`](references/lark-cli-contract.md) 中对应章节；该文件保留命令与 JSON 形状，本文件只保留阶段决策和安全门禁。实际执行仍以当前 CLI `--help` / guide / schema 为准。

### 3A. Dashboard 合同

**真实 Dashboard 是必需交付。** 普通 Grid View、看板视图或名为“仪表盘”的表视图不算 Dashboard。系统草案必须单独列出 Dashboard 名称、组件、数据来源和读回验收方式。

Dashboard 至少覆盖四类信息：

1. 当前结果、目标值、差距或完成率。
2. 当前阶段、已完成执行单元和剩余执行单元。
3. 今天/本周应该进入哪里、下一步做什么。
4. 风险、逾期项或尚未自动完成的系统能力。

默认视觉结构按“指标卡 + 趋势图 + 分布图 + 执行图”设计，而不是只放说明文字：

- 顶部指标卡：当前结果、目标、差距、完成量或剩余量。
- 至少一个目标结果趋势图：按日期、周或执行单元展示结果变化。
- 至少一个执行状态分布图：展示待开始、进行中、完成、跳过或目标特有状态的数量分布。
- 至少一个执行投入或产出图：展示时间投入、任务数量、作品表现或其他目标特有的执行信号。

纯文本和记录总数卡片不能代替核心进度图表。图表方案必须逐项写明图表类型、数据表、分组字段、指标字段、聚合方式和空数据表现。

如果现有 schema 缺少目标结果的时间序列数据，先提出只包含日期、结果值和来源的最小快照表，说明为什么需要并等待用户确认 shared schema；不能把一次性目标总览记录伪装成趋势。不得为了填满图表写入虚假数据；允许图表在真实数据尚未产生时显示为空，并在使用说明中解释何时开始出现数据。

能创建数据驱动组件时，至少一个核心进度组件必须从真实字段或记录计算；静态文本快照不能作为唯一进度展示。写入后必须读回 Dashboard、block 数量、关键 block 配置和可计算 block 的真实数据。Dashboard 计算结果必须串行读回；遇到 `GetChartLatestSnapshot` 或 `GetChartDataV3` 的 1 QPS / timeout 错误时，按 block 逐个重试，不能并发轰击。未创建并读回 Dashboard 前，系统不得标记为 `complete`。

如果当前 CLI 无法安全创建某个动态图表，不要把普通视图包装成 Dashboard，也不要只报告“暂不支持”：先创建当前能力允许的真实 Dashboard 骨架和安全组件，再把缺少的动态图表写入 `manual-setup-guide.md`，说明如何补齐和验收。此时系统状态保持 `partial`。

### 3B. 小白可用性交付合同

默认假设用户是第一次使用飞书多维表格，除非用户明确说明自己熟悉 Base。字段名、视图名和自动化术语必须用日常语言解释；用户不应依赖本轮聊天记录才能使用系统。

系统 schema 确认时，同时确认以下本地交付物的拟保存路径；默认与 `goal-plan.md` 同目录：

- 必须生成 `system-guide.md`：每次创建或重建系统都要交付。
- 只要存在经 3D 审计确认的人工项才生成 `manual-setup-guide.md`；Agent 尚未执行但 CLI 已支持的工作不得触发人工指南。
- `feishu-system-contract.md`：记录真实 ID、结构、读回证据和完成状态。

`system-guide.md` 必须回答：第一次打开看哪里、每天怎么用、特别忙时怎么做、每周怎么用、发布后怎么更新数据、怎么看懂仪表盘、遇到异常怎么办。

`manual-setup-guide.md` 对每个人工项必须说明：为什么需要、当前真实状态、从哪里开始、逐步操作、应填写的具体值、完成标志、验证方法和找不到入口时怎么办。不要只写“需要人工配置”或只列功能名称。

### 3C. 提醒与记录跳转合同

**提醒不是默认人工项。** 用户已经确认提醒时间、通知对象和筛选条件后，按当前 `lark-cli base +workflow-*` 的 `--help`、workflow guide 和 schema 自动创建或更新、启用并读回。不得仅因 steps JSON 较复杂就默认转成人工项；网页入口更直观或 Agent 尚未手写过该结构，也不是转人工的理由。

创建前先 `+workflow-list`，再对候选执行 `+workflow-get`，按真实 ID、标题、触发时间和通知对象识别目标；发现同名、同时间或用途重叠的流程时先消歧，不能直接再建一个。写入前确认日期字段、提醒时间、**Base 时区**、筛选条件和通知对象；用户只说“21:00”而 Base 时区与用户预期不明确时先确认，不自行猜测。

按用户需要选择结构：

- 每条记录按自身日期提醒，并需要点击消息打开这条记录：使用 `ReminderTrigger → LarkMessageAction`。触发器的记录链接输出是 `recordLink`；消息 `btn_list` 使用 `openLink`，引用 `$.<reminderStepId>.recordLink`。需要固定视图时，先读真实 `view_id`，再引用对应的 `recordLink.<viewId>`。
- 固定时间汇总查找多条记录：可以使用 `TimerTrigger → FindRecordAction`。无结果时必须停止后续发送；若用户要求按钮打开某一条精确记录，而当前 Find/Loop 输出没有已验证的记录链接，则改用记录级 `ReminderTrigger`，不能把普通表链接冒充精确记录链接。

若同一天可能存在多条记录，记录级提醒会对每条满足条件的记录分别触发。建模时必须确认这是预期行为；若用户只要一条汇总提醒，改用定时汇总结构，不能擅自选择第一条记录。

用户只要求“点击提醒打开记录，再手动编辑”时，按钮只使用 `openLink`。**不得把“打开记录后手动编辑”扩写为自动修改字段**；只有用户明确要求按钮直接新增或修改记录，并确认目标字段和值时，才考虑 `addRecord` / `setRecord`。

现有 workflow 更新采用完整替换门禁：先 `+workflow-get`，保留未要求变化的标题、状态、接收人、消息配置、未知字段和扩展配置；再做**完整定义 dry-run**并与读回定义比较，执行 `+workflow-update`，最后 `+workflow-get` 读回并确认仍为 `enabled`。新建流程按 dry-run、create、get、enable、再次 get 的顺序验收。

只有当前 CLI 明确不具备所需能力、目标或通知对象尚未确认、所需 scope 缺失且用户拒绝授权、组织策略阻断，或安全写入后无法读回确认时，才把提醒创建列入 `manual-setup-guide.md`。CLI 能完成而只缺一次真实定时运行时，状态写为“配置已完成、真实运行证据待补”；把运行日志和手机端点击结果列为待验收证据，不要要求用户重新人工创建流程。当前 CLI 没有立即试运行入口时，不得未经确认临时改时间或制造测试记录。

### 3D. 自动化能力审计与人工降级门禁

本 Skill 的“3D 审计”是三证审计：命令面证据（命令、`--help`、guide/schema）、权限面证据（身份、scope、组织策略）和结果面证据（dry-run、执行、读回）。三类证据必须共同支撑人工降级结论。

**“尚未验证”不等于“CLI 不支持”。** 在提出人工操作前，必须逐项核验当前 CLI 的命令入口、`--help`、guide/schema、所需 scope、目标对象现状，以及 dry-run、执行和读回结果。配置复杂、以前没做过、网页端更直观、需要用户确认或暂时缺少权限，都不能直接归类为 CLI 不支持。

shared schema 变更需要用户确认，但确认后仍由 Agent 使用 CLI 执行；不得把“需要确认是否新增关联、公式、lookup、快照表或视图”偷换成“请用户到页面手工创建”。权限扩大同样先确认；用户同意后由 Agent 补最小 scope 并继续，用户拒绝时才记录为权限阻断。

动态日期视图必须按当前 view filter API 的真实 operator 写入。日期等于今天使用 `== Today`；包含今天的区间使用 `< Tomorrow` 和 `> Yesterday`。不得把 `<= Today` / `>= Today` 直接写入视图筛选；若 API 返回 datetime operator 白名单，以错误中的实际白名单改写等价条件后重新 dry-run。

字段自动化不得绕过类型转换白名单。现有存储型数字字段不能安全转换为公式时，保留旧字段，新建自动公式字段并切换下游 Dashboard 或其他消费者；只有用户明确接受整列数据丢失时才考虑非白名单原位转换。

在生成 `manual-setup-guide.md` 前先建立“自动化能力审计”表，每项至少记录：功能、CLI 命令、help/schema 证据、所需 scope、是否需要用户确认、dry-run/执行/读回结果和分类。分类只允许：

- `AUTO_DONE`：CLI 已执行并读回，或已确认无需写入。
- `CLI_UNSUPPORTED`：当前 help、guide/schema 或命令面明确缺少所需能力；必须写出检查过的具体命令和缺口。
- `PERMISSION_BLOCKED`：缺少明确 scope、权限错误或用户拒绝授权；必须记录具体 scope 或错误。
- `POLICY_BLOCKED`：组织、管理员或安全策略明确阻断；必须记录可核验的策略或错误证据。
- `HUMAN_ACCEPTANCE`：配置已完成，但手机点击、视觉显示、真实定时运行、运行日志或其他现实环境结果只能由用户验收。

“复杂”“没试过”“不确定”“尚未验证”“暂未验证”不得作为人工降级证据。目标、schema、通知对象尚未确认时先暂停确认，不要预先生成操作教程；确认后重新进入 CLI 审计与执行。

人工指南必须最后生成，只收录 `CLI_UNSUPPORTED`、`PERMISSION_BLOCKED`、`POLICY_BLOCKED` 和 `HUMAN_ACCEPTANCE`。`AUTO_DONE` 只能留在能力审计和系统合同中，不得出现在人工项中。`manual-setup-guide.md` 是阻断与人工验收清单，不是未完成任务堆积区。

每个人工项必须包含分类、阻断证据、CLI 尝试记录和解除阻断后的 Agent 后续动作。CLI 新能力或新增 scope 被验证后，必须反向清理旧人工项，并同步更新 `feishu-system-contract.md`、`system-guide.md` 和 `manual-setup-guide.md`，不能让旧指南继续要求用户重复配置。

交付前运行：

```bash
python3 .agents/skills/goal-to-feishu-execution-system/scripts/validate_manual_guide.py <manual-setup-guide.md>
```

校验不通过时不得把人工指南交付给用户，也不得据此把系统标记为 `complete`。

**阶段出口：** shared schema、Dashboard 方案、workflow/提醒结构、通知对象、交付物路径和人工降级分类已逐项确认；每个组件都有明确的读回验收方式。

## 4. 执行门禁

设计确认后、首次写入前：

1. 用当前 `--help` / `schema` 确认实际命令，不依赖历史语法。
2. 从计划执行的命令推导最小 scopes；用 `auth check --scope` 核验，缺什么只补什么。
3. 显式使用 user 身份，核对 CLI 当前用户、目标组织和目标文件夹/Base。
4. 对既有目标先执行 URL/title resolve 和只读访问；多候选时让用户消歧。
5. 批量写入若由脚本或子进程执行，必须在同一执行上下文先跑只读命令，防止 macOS Keychain 差异。

**阶段出口：** 上述五项均有本次读回证据后，状态才可变为 `ready`。目标未确认、资源不可读或 scope 不足时保持 `planning_only` 或 `blocked`。

## 5. 创建、返工与验收

- 写入前读取真实结构；名称和 ID 只使用真实返回。
- schema 先确认；支持 `--dry-run` 的写操作先预览。
- 批量记录单批不超过 200，串行写入，并保留稳定来源 ID，避免失败重跑产生重复数据。
- 超时、部分成功或结果不明确时，先读回实际状态，不盲目重试。
- 写入后核对表、字段、记录数、日期连续性、关键视图和提醒能力。
- 写入后创建并读回真实 Dashboard；普通表视图不能代替这一步。
- 必须生成并读回 `system-guide.md`；存在人工项时必须生成并读回 `manual-setup-guide.md`。
- 生成人工指南前执行 3D 的自动化能力审计；只有 CLI 已核实不支持、权限或组织策略明确阻断，或确需用户完成现实环境验收的事项才列为人工项。不得因为实现复杂、尚未尝试或需要确认就转交用户，并按模板给出小白可以独立完成的步骤。
- `manual-setup-guide.md` 生成后必须通过 `scripts/validate_manual_guide.py`；CLI 能力变化后先反向清理旧人工项，再更新完成状态。
- 提醒是用户确认过的系统行为时，必须核对真实 workflow/automation 状态；只有“提醒已创建、已启用、通知对象正确、时间与时区正确、测试或读回通过”才能写成已完成。
- 提醒创建与精确记录按钮必须遵守 3C 合同；使用“查找记录 → 发送消息”时，必须验证无匹配记录会停止后续发送（例如 `should_proceed_when_no_results:false`），避免任务已完成仍收到提醒。
- Dashboard、提醒或关键关系仍靠人工补齐时，交付状态保持 `partial`，不能因为表和记录已经存在而提前结束。

**阶段出口：** 每个计划写入项都已进入读回闭环；成功项有真实 ID 与读回结果，未完成项已归入有证据的阻断或人工验收分类。

## 6. 完成输出与状态门禁

交付八项：

1. 确认后的目标基线。
2. 本地 `goal-plan.md`。
3. 系统结构合同。
4. 真实飞书 Base 结果或阻断状态。
5. 真实 Dashboard 及读回结果。
6. 本地 `system-guide.md`。
7. 存在人工项时的 `manual-setup-guide.md`。
8. 自动完成与人工补齐的验收报告。

只有以下条件同时满足，系统状态才能标记为 `complete`：

- 计划、schema、写入目标和通知对象均已确认。
- 表、字段、关系、记录、关键视图和自动化达到确认合同，或用户明确取消对应能力。
- Dashboard 已创建并读回，包含当前结果、阶段进度、执行入口和风险提示。
- 用户确认需要提醒时，提醒已创建、启用并完成通知对象与时间验收。
- `system-guide.md` 已生成并读回。
- 存在人工项时，`manual-setup-guide.md` 已生成并逐项说明完成人工项后如何验收；只要关键人工项尚未实际完成，状态仍是 `partial`。
- 隐私和权限已读回确认；关键项仍属于 `PERMISSION_BLOCKED` 或 `HUMAN_ACCEPTANCE` 时，状态必须保持 `partial`。

**阶段出口：** 对照八项交付物和状态机逐项核验；只有全部关键条件得到当前证据支持时标记 `complete`，否则写明 `partial`、`planning_only` 或 `blocked` 的具体原因。

一次跨目标跑通只证明一次复用，不宣称通用、保证坚持或保证目标结果。

## 7. 可选周度复盘自动化

系统达到 `complete` 后，主动询问用户是否开启周度复盘；这是可选能力，**只有用户明确同意后才创建**。

用户同意后：

1. 优先读取 `goal-plan.md` 中已确认的复盘星期、时间和时区；缺失时再询问。
2. 根据每周计划提出最低有效记录门槛并让用户确认，不使用固定条数套用所有目标。
3. 使用 [`templates/weekly-review-automation.md`](templates/weekly-review-automation.md) 生成平台无关的任务说明，让当前宿主 Agent 使用**宿主 Agent 的原生能力**自然语言创建周期任务。
4. 创建后核对**真实任务详情**中的任务名、频率、时间、时区、运行项目和启用状态；只有聊天回复“已创建”不算完成。
5. 宿主明确不支持周期任务时报告能力缺口并停止，不默认改用外部调度器，也不默认让用户手工创建。

周度任务只读上一完整复盘周期的计划、打卡和目标进度。数据不足时只说明缺少什么，不生成调整方案；数据充分时列出完成情况、有记录支持的卡点、下周建议和精确修改清单。

用户回复“同意”只批准当前清单。清单只能包含下一周及以后尚未开始的任务，并写明目标任务、原值、新值和依据。执行前重新读回目标记录；原值变化时停止并重新提案。写入遵守原有 dry-run 和最小权限门禁，执行后再次读回。阶段目标、执行频率和核心指标需要单独提案和确认。

**阶段出口：** 周度自动化未启用、已经用户明确取消，或已创建并读回真实任务详情；不得因该可选能力未启用而阻止系统保持 `complete`。

## 8. 停止条件

- 安装、登录、权限扩大或目标组织需要用户确认。
- 目标、写入位置、schema 或通知对象不明确。
- CLI 身份与目标组织不一致。
- 执行上下文无法读取凭证。
- 写入结果不明确且尚未读回。
