Write commits terse and exact. Conventional Commits with required scope. No fluff. Why over what.

## Format

```
<type>(<scope>): <imperative summary>

<body — only when "why" is non-obvious>

<footer — only for BREAKING CHANGE notice or issue refs>
```

## Rules

**Subject line:**
- `<type>(<scope>): <imperative summary>`
- **Scope is required.** Match the touched package, monorepo workspace, or domain area.
- Imperative present tense: `add`, `fix`, `migrate`, **not** `added`, `fixes`, `migrated`.
- ≤ 50 chars total. No period.
- Lowercase after the colon, unless quoting a proper noun, file path, or identifier.

**Types:**
- `feat` — new capability the user can call / observe
- `fix` — corrects broken behavior
- `refactor` — same behavior, better shape
- `perf` — measurable speed/memory win
- `docs` — `.md`, comments, JSDoc
- `test` — only test files changed
- `chore` — tooling, deps, ci, config (anything not user-observable)
- `build` — build config / output / packaging
- `ci` — `.github/workflows`, release infrastructure
- `style` — whitespace/format only (rare in Biome repos)

**Scope picking (in order of preference):**
1. Touched package shortname: `result`, `codemod`, `eslint-plugin`, `core`, `storage`, `agent-tools`, `dashboard`, `mcp-server`
2. Repo-wide infrastructure: `repo`, `deps`, `ci`, `docs`
3. Feature/domain area (when the change cuts across packages): `auth`, `ingestion`, `graph`, `chat`

If a target repo's `commitlint.config.cjs` defines `scope-enum`, use only those scopes.

**Body:**
- Only when the "why" isn't obvious from the diff.
- Plain prose, hard-wrap ≤ 100 cols (or per repo's commitlint config).
- Bullets allowed for multi-point rationale.
- Reference issue numbers as `Refs #123` or `Closes #123`.

**Footer:**
- `BREAKING CHANGE: <what now breaks + migration>` when applicable.
- Issue trailers (`Refs`, `Closes`).
- **Never** `Co-Authored-By: <bot>`, **never** `🤖 Generated with …`, **never** any tool/agent attribution.

## What NOT to include

- Emoji in subject or body (target repo convention overrides only when commitlint config requires `gitmoji`).
- "WIP" — squash before committing.
- "address review comments" / "fix tests" without scope. Make these specific: `fix(result): widen andThen accept Result|ResultAsync returns`.
- AI co-author lines.
- Marketing language: "powerful", "robust", "comprehensive".

## Good examples

```
feat(result): widen andThen to accept Result | ResultAsync returns

Lets callers swap a Result-returning callback for a ResultAsync without
splitting the chain. Aligns inference with neverthrow's signature.
```

```
fix(codemod): handle dynamic import() specifier rewrites

Regex previously only matched static `from "x"` and `import "x"` lines.
Bun-style `await import("x")` is the actual call site in lazy-loaded
package entrypoints.
```

```
refactor(storage): switch chain → ts-pattern over ArtifactStatus

No behavior change. Adds exhaustiveness guarantee — next status variant
will be a typecheck error rather than a runtime "unhandled" fallthrough.
```

```
chore(repo): initialize @onrails monorepo
```

```
docs(result): add compat surface migration table
```

## Bad examples

```
update stuff               ❌ no type, no scope, no detail
fix: bug                   ❌ no scope, no detail, no "why"
feat: 🚀 super fast API    ❌ emoji, marketing language
feat(result): added support for Map → Set conversion   ❌ past tense
WIP                        ❌
fix tests                  ❌ no scope; what tests? why broken?
```

```
fix(result): andThen

Co-Authored-By: <ai-bot>
🤖 Generated with <some-ai-tool>
```
❌ Agent/AI attribution, footer noise.

## Multi-package change

When one logical change spans multiple packages (e.g. an API contract change):

```
feat(result): expose isOk/isErr as type predicates
feat(codemod): rewrite r.isOk()/.isErr() to isOk(r)/isErr(r) calls
```

Two commits, one per package. Easier to revert, easier for release-please to bump per-package versions.

Don't combine unrelated changes under one commit; split them.

## Workflow

1. `git status --short` — see what's staged.
2. `git diff --staged` — read the actual diff, not what you remember writing.
3. Pick scope from the touched package(s).
4. Subject in imperative present, ≤ 50 chars.
5. Body only if "why" is non-obvious.
6. **Never** `--no-verify`, **never** `--no-gpg-sign`, **never** `-c commit.gpgsign=false` unless the user explicitly asked.
