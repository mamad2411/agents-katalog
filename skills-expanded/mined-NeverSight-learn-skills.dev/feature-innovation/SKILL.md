# 功能创新与扩展

## 何时使用

用户希望基于现有项目/产品，梳理已有功能并探索**可扩展的新功能方向**。

**不适用或简化**：用户已明确要做什么新功能，只需要直接实现；纯 bug 修复或重构请用 [`code-optimization`](../code-optimization/SKILL.md)；生成 commit message 请用 [`git-commit`](../git-commit/SKILL.md)。

---

## 用户既定流程

1. **梳理**当前功能与文档，弄清楚现状与能力边界
2. **发散**基于现有能力提出可扩展的新功能方向
3. 输出每个方向的描述、依据、价值与实现要点
4. **用户挑选**要落地的方向
5. **设计与实现**选中的方向

---

## 步骤 1：梳理当前能力（必须先做）

- 阅读根目录 README、文档（`docs/`、各 `*.md`）、配置（`package.json`、`manifest` 等）、入口文件、主要模块
- 列出**已有功能清单**，按职责分组（核心能力 + 辅助能力）
- 标注每个功能对应的入口、接口、数据流
- 识别**能力边界**：哪些场景、用户、数据已被覆盖，哪些还没被覆盖

输出：一份简洁的「现状能力地图」，后续所有扩展方向都要回到这张图找依据。

## 步骤 2：扩展方向探索

基于步骤 1 的能力清单，从以下维度发散（**不限定单一维度**，鼓励跨维度组合）：

- **现有功能的自然延伸**：已被部分支持的场景，可补齐闭环
- **相邻场景扩展**：核心能力可平移到的新场景、用户或数据类型
- **能力组合创新**：把两个及以上现有功能组合，产生新用法
- **数据/接口复用**：基于现有数据模型或对外接口可衍生什么
- **生态集成**：与外部系统、工具、平台可对接的点

## 步骤 3：输出扩展建议清单

每个方向用以下结构描述：

| 维度 | 内容 |
| --- | --- |
| **方向** | 一句话概括这个新功能 |
| **能力依据** | 依赖现有哪些能力，复用哪些模块、接口、数据 |
| **价值** | 用户获得什么 / 业务或产品提升什么 |
| **实现要点** | 关键技术点、风险、外部依赖 |
| **预估工作量** | 小 / 中 / 大 |

**强约束**：每个方向都必须填「能力依据」，明确连接到现状能力地图上的哪一项；凭空创造的、与现有体系无关的需求**不要写**。

## 步骤 4：等待用户挑选

- **不直接动手实现**，等用户从清单中挑选要落地的方向
- 用户选中后，再进入设计与实现阶段

---

## 注意

- 「创新」必须**立足现状**，每条扩展方向都要回到现状能力地图找依据
- 不为创新而创新；优先价值高、复用现有能力多、风险可控的方向
- 清单**不要堆得过长**，聚焦 5–8 个最值得做的方向，宁缺毋滥
- 已被现有功能覆盖的方向不要重复列出；已明确不做的方向可在「不适用」段落说明
