# 标书方案撰写引擎

通用写作引擎。不关心方案类型——只执行 plan_budget.md 给出的写作蓝图。

```
analyze-tender → plan-scheme → **write-solution** ← 你在这里
```

---

## 一、执行流程

### Step 1: 准备

**1.1 参数匹配**：参数 = $ARGUMENTS（如 `technical`、`01`、`项目技术方案`），在 plan_budget.md 方案清单中按名称/序号/后缀模糊匹配。匹配失败则列出所有可选方案。

**1.2 预检查**：Glob 确认 `output/plan_budget.md`（含"审核通过"）和 `output/canon_current.md` 存在，缺失则终止。

**1.3 加载蓝图**（并行读取）：

- `output/plan_budget.md` — 唯一蓝图
- `output/canon_current.md` — 口径
- [writing-rules-examples.md](references/writing-rules-examples.md) — 禁用词替换+去AI策略
- [evidence-placeholder.md](references/evidence-placeholder.md) — 证据占位规范

从 plan_budget.md 提取当前方案的全部信息：

| 信息 | 来源 |
|------|------|
| 角色定位、方案边界、差异化定位、域特有检查项 | 写作指导块 |
| 评审对照索引（评分项→章节→满分策略→扣分陷阱） | 评审对照索引 |
| 目录结构（H2/H3 列表） | 目录草案 |
| 每个 H2 的章节类型、字数预算、是否主响应章 | 章节作战清单 |
| 每个 H2 的评分点、需求项、项目锚点、图表配额 | 章节作战清单 |
| 每个 F2 评分点的主响应章节、辅助支撑章节、评分档次详情（优秀/良好/一般） | 评分点归属表 |

从 canon_current.md 按方案关键词过滤相关口径。

**1.4 动态编号**：Glob 扫描 `output/summaries/*_summary.md`，`本次编号 = max(已有编号) + 1`，两位数（01, 02...）。

**1.5 提炼 Win Theme**：从 plan_budget 差异化定位提炼 2-3 个主旋律关键词，贯穿全篇。

**1.6 生成章节执行表**（仅内部使用，不写入正文）：至少列出 `H2章节 | 章节类型 | 预算字数 | 本章最低目标字数 | 计划分段 | 计划功能块数 | 单块目标字数` 七列。规则：

- 方案概览：最低目标 = 固定预算的 90%，且不得低于 1,000 字
- 主响应章：最低目标 = 预算的 92%
- 补充支撑章：最低目标 = 预算的 85%
- 最终论证章：600-900 字
- 章节预算 `>=7000` 字的主响应章：计划功能块数 `>=5`
- 章节预算 `<7000` 字的主响应章：计划功能块数 `>=4`
- 单块目标字数 = 章节预算 ÷ 计划功能块数（写作时允许 ±20% 浮动，但块间最大差异不超过 40%）

**1.7 预设提交结论初值**：默认先按“建议微调后提交”写作。只有 Step 3 终检确认高优先级证据、真实待填项、口径冲突均已处理后，才允许提升为“可直接提交”。

---

### Step 2: 按章节生成方案正文

> **核心原则：信任模型能力，但靠“章节执行表 + 分段写满”逼近预算字数。段内一次生成即成品，段间只按既定分段继续 append；不逐章回读打磨，不触发外部 Skill。**

#### 2.1 评委阅读模型（指导写作策略）

评委时间极有限，写作必须服务于评委的阅读路径：

1. **快速翻阅**(30-60秒)：看目录/篇幅/图表密度 → 目录标题贴近评分点关键词，篇幅充实
2. **关键词扫描**(2-3分钟)：持评分表逐项查找 → 关键数字加粗或表格化，逐条响应"应/须/必须"
3. **深度阅读**(仅有竞争力的方案)：判断可行性与专业性 → 具体到操作层面（谁+怎么做+标准）
4. **对比打分**：横向比较同评分点 → 提供差异化内容，超越"基本满足"

**F2格式冲"优"**：完整覆盖 + 措施具体(谁+做什么+标准) + >=1 创新亮点 + 引用招标条款
**F1格式满分**：结构与评分子项一一对应 + 标题/段首句用评分子项关键词 + 每子项附证据

#### 2.1.5 写作密度指导

执行表给出了每章字数目标和功能块数，但模型需要更细粒度的锚点才能在一次生成中逼近目标。以下密度规则帮助将章节目标分解为可操作的块级内容量：

每个功能块应包含的实质内容：
- **1 个核心措施/机制**（含 HOW + WHAT + 验收，>= 400 字）
- **1 个配套支撑**（工具/人员/流程/标准，150-300 字）
- **1 个项目适配说明**（本项目为什么选择这个做法，100-200 字）
- 合计 ~650-900 字/功能块 × 功能块数 ≈ 章节目标字数

写作时以执行表的「单块目标字数」为参照，每完成一个功能块后心中粗估已写字数，不足则在下一功能块中适当增加展开深度。

#### 2.2 输出策略

按**章节类型 + H2 数量 + 章节执行表**拆分为多段输出。概览章固定首段，最终论证章固定末段，主响应章优先单独占段，补充支撑章放在倒数第二或最后一段前：

| 段 | 操作 | 内容 | 预估字数 |
|----|------|------|---------|
| 第1段 | **Write** 创建文件 | 索引表 + 第1章方案概览 + 第1个主响应章 | 本段所含章节执行表目标之和 |
| 第2段 | **Edit** append | 第2个主响应章 | 本段所含章节执行表目标之和 |
| 第3段 | **Edit** append | 第3个主响应章 | 本段所含章节执行表目标之和 |
| 第4段 | **Edit** append | 第4个主响应章 | 本段所含章节执行表目标之和 |
| 第N段 | **Edit** append | 补充支撑章 + 最终论证章 | 本段所含章节执行表目标之和 |

**规则**：
- 小方案（<=25,000字，如质量方案）：一次 Write 完成
- 中方案（25,000-40,000字）：分2段
- 大方案（>40,000字）：固定分4-5段，**每个高预算主响应 H2 独占1段**；禁止把 2 个高预算主响应章挤在同一段。章节预算 <5000 字的相邻主响应章可合并为一段（但每段不超过 2 个主响应章）
- 每段是完整章节，不在 H2 中间断开
- 第1章必须是方案概览
- 最后一章必须是方案完整性与可行性论证
- 每段完成后只允许继续 append 下一段，不回头重写前段
- 总字数优先追平 `plan_budget.md` 的目标字数；最低不得低于 `max(目标字数×90%，章节最低目标字数之和)`
- **段间衔接**：段 2 及之后的每段首行，以一句过渡语衔接前文（如"在第X章明确了…的基础上，本章聚焦于…"）。跨方案引用也在此完成（如"详见XX方案第X章的XX设计"），引用须与 summary 中的依赖关系一致

#### 2.3 正文结构

```markdown
# {方案名称}

> 响应范围：{评审要求摘要列表} | 编号：{NN} | 字数：{字数} | 预算：{动态预算}字 | 结论：{可直接提交/建议微调/不建议提交}

## 评分点响应索引

【表1-1：评分点响应索引】

| 评分点 | 分值 | 主响应章节 | 辅助支撑 | 关键承诺 |
|--------|------|-----------|---------|---------|
| {评分点描述} | {X}分 | {章节编号 章节标题列表} | {概览/补充/论证章节列表} | {关键承诺摘要} |

**表注**：本表列出本方案覆盖的全部评分点及对应章节位置，便于评审专家快速定位。

## 第1章 方案概览

{以甲方面临的核心挑战开头 → 核心技术路线/管理思路 → 关键量化承诺3-5个 → 与其他方案协同}

## 第2章 {H2标题，复刻评分标准原文}
（按作战清单生成，满足写作约束）

## 第N章 方案完整性与可行性论证
（固定600字：完整性+可行性+需求满足度，详见 [completeness-proof.md](references/completeness-proof.md)）
```

**主响应章默认骨架**：除非 `plan_budget.md` 明确给出其他结构，否则每个主响应 H2 默认拆成 4-6 个实质功能块（可用 `###` 或加粗小标题承载），至少覆盖：

1. 项目场景/评审要求转译
2. 方案主体/组织或机制设计
3. 执行动作/流程/控制点
4. 交付物/证据/验收方式
5. 重难点分析与差异化收束（预算较高时必写）

**大章节内部层次**：章节预算 >=7000 字时，每个功能块内部应拆出 2-3 个 H3 子节，形成更清晰的阅读层次。示例：

```
### X.1 {功能块标题}
#### X.1.1 {核心措施主体}（300-500字）
#### X.1.2 {执行细节/技术规格/流程分解}（200-400字）
#### X.1.3 {验收方式/质量保障}（100-200字）
```

大章节的 H3 子结构帮助评委在深度阅读阶段快速定位，避免 7000+ 字的章节沦为无层次的长文。

#### 2.4 写作约束

> 约束分为两组：**A 组（写作时必须满足）** 在每段生成时直接执行；**B 组（终检时验证）** 在 Step 3 集中检查。这样分组是为了降低单次生成的认知负载——写作时聚焦结构和内容，终检时补查语言和风格。

**A 组：写作时必须满足**

**结构与覆盖**

1. **章节骨架固定**：第1章必须是方案概览，最后一章必须是方案完整性与可行性论证；补充支撑章最多 2 章
2. **评分点全覆盖**：每个评分点至少有 1 个主响应章节；同一评分项可由多个主响应 H2 合计覆盖，但方案概览/补充支撑章/最终论证章不得替代主响应章节
3. **单章边界清晰**：单个 H2 只负责本章被分配的关键词维度，不把其他评分章主体内容塞进来
4. **字数达标**：按 Step 1.6 章节执行表中的最低目标字数逐章达标。总字数优先追平方案预算，最低不得低于 `max(方案目标字数×90%，章节最低目标字数之和)`
5. **展开深度足够**：每个主响应 H2 至少有 4 个实质功能块；预算 `>=7000` 字时至少 5 个。禁止只靠长表格、长列表或重复措辞把字数堆满
6. **图表完整**：>= 作战清单中的图表配额。评分响应章至少 1 图 1 表；方案概览至少 1 表；补充支撑章至少 1 图或 1 表；最终论证章至少 1 表。标注格式：【图/表X-X：标题】+ 代码/表格 + 空行 + 图注/表注。密度：每 1,200 字 >= 1 图表。Mermaid 约束：节点 <=15、subgraph <=2 层、文字 <=8 字/行。配色：核心#E3F2FD 处理#FFF8E1 决策#FFEBEE 完成#E8F5E9 中性#F5F5F5 强调#F3E5F5
7. **口径一致**：关键数值/术语与 canon_current.md 一致
8. **内部编号隔离**〔B 组〕：SP*/F*/P*/B*/S* 不进入正文，包括表注、图注、方案概览等任何评审专家可见的文本。如需引用评分点，用自然语言描述（如"供货方案评分项"而非"SP2"）
9. **禁止虚假人名**〔B 组〕：组织架构图、人员表、正文叙述中不得出现编造的具体人名（如"张工""李经理"）。一律使用职位名称（如"供货项目总负责人""生产调度负责人"）。人员占位使用【人员占位：投标时填写】格式
10. **方案边界**〔B 组〕：不越界代写其他方案主体内容

**内容质量**

11. **可验收三要素**：每项承诺 = 怎么做 + 产出什么 + 怎么验收，每承诺 >= 400 字展开（背景→方案→细节→验收，四层自然过渡）。每个主响应 H2 至少包含 `ceil(章节预算 ÷ 2000)` 个完整承诺/措施（如 9,800 字章节至少 5 个），确保承诺密度撑满字数目标
12. **证据与交付物**：证据占位和交付物已显式声明
13. **项目锚点**：每个 H2 体现作战清单中的「项目锚点」，至少 1 处用项目特异性细节替代通用描述
14. **重难点分析**：每个 H2 包含至少 1 处「重难点识别→应对措施→预期效果」结构。重难点从 plan_budget 的项目锚点和扣分陷阱推导，体现项目经验
15. **Win Theme 贯穿 + 评分收口**：每个 H2 至少 1 处自然呼应 Step 1.5 提炼的主旋律（不是机械重复，而是从不同角度体现差异化优势）。每个主响应 H2 末段（最后 100-200 字）应回扣评分标准原文，总结本章如何达到该评分项优秀/良好档要求，形成"开场呼应评分—展开论述—收尾回扣评分"的闭环

**语言与风格（写作时注意 17-18，其余终检验证）**

16. **禁用词分级**〔B 组〕：详见下方禁用词表。如 plan_budget.md 头部有「禁用词豁免」按其规则放行；如有「行业特有禁用词」追加到禁用列表
17. **现在时态**：描述方案设计用现在时（"系统采用…"），不用将来时（"系统将采用…"）。将来时仅用于尚未发生的项目实施动作
18. **客户痛点导向 + 关键词前置**：方案概览以甲方面临的核心挑战开头。每个 H2 开场优先用项目背景/甲方痛点引入，再展开解决方案。每个 H2 开头 100 字内必须出现该评分点的核心关键词（从章节作战清单"评分维度标签"取），便于评委在关键词扫描阶段 30 秒内定位到本章
19. **结构多样性**〔B 组〕：相邻 H2 禁止相同开场，全方案 >= 4 种开场模式（参见 [writing-rules-examples.md](references/writing-rules-examples.md) 开场模式菜单）。段落节奏：相邻段落长度差异 >= 30%。每 H2 内 >= 3 种段落结构（总分/因果/对比/案例/流程）
20. **人味要素**〔B 组〕：每 H2 至少 1 个——场景描述(>=50字) / 选型对比(>=2选项) / 风险预判 / 经验教训
21. **数据分级**〔B 组〕：A级（招标要求）精确引用 | B级（行业标准）建议精确 | C级（经验值）模糊化 | D级（夸张）禁止

**避免扣分陷阱**

写作时对照 plan_budget.md 中每个评分点的扣分陷阱：
- 不通用化：包含本项目特定细节（项目名称、具体模块名、性能指标）——用项目锚点落地
- 不指标空转：每个性能指标都有实现措施支撑
- 不关键词缺失：评分标准中的每个关键词都在正文中出现
- 不前后矛盾：数值/术语与 canon_current.md 严格一致
- 不主次错位：方案概览/补充支撑章/最终论证章只做导航、补强、论证，不承担评分项主体响应

#### 2.5 禁用词表

**硬禁（出现即违规）**：
- 空洞承诺：全方位、一站式、无缝对接、零风险、100%保证
- 官八股：赋能、打造、助力、抓手、底层逻辑
- 虚假修饰：卓越、一流、强大

**限频（单篇每词 <=2 次，且须有实质支撑）**：
- 第一组（评审常见词）：高效、智能、先进、全面、完善、领先、优质、专业、精准、灵活、便捷、快速
- 第二组（易高频词）：清晰、可靠、完整、合理、科学、规范、严格、有效、系统
- **统计范围**：仅统计正文叙述句中的修饰性用法；固定章标题、评分标准原词、规范编号、表头字段、图表标题、术语名称、固定终章名不计入限频
- 放行条件：后接具体量化指标或实现方式（如"专业资质"OK，"专业团队"不OK）
- 自查要求：写作完成后心中默数每个限频词的使用次数，超过2次的用同义词替换或删除修饰

**禁用句式**：
- "我们将…"、"本公司致力于…"（→ 改用现在时）
- "首先…其次…再次…最后…"（→ 用非顺序连接词）
- "确保…的同时，兼顾…"
- 排比三连："通过X实现Y，通过A保障B，通过C确保D"（→ 拆散为独立段落）
- "值得注意的是"、"需要指出的是"、"总的来说"

替换对照和去 AI 深层策略见 [writing-rules-examples.md](references/writing-rules-examples.md)。

### Step 3: 终检 + 输出 + 闭环

#### 3.1 终检

全部段落写入文件后，Read 回来做**一次**终检。允许使用轻量模式检查图表数量、内部编号、禁用词和证据占位编号，但不得因此扩大为探索性全文搜索：

Read [quality-checklist.md](references/quality-checklist.md)，按清单的「一、全域通用提交清单」逐项检查。重点关注：
- 图表标注完整（【图/表X-X】+ 图注/表注 + 空行）
- 总字数优先达到方案预算；最低不得低于 `max(方案预算×90%，章节最低目标字数之和)`
- 第1章为方案概览，最后一章为方案完整性与可行性论证
- 每个评分点都有主响应章节，且辅助支撑章节未替代主响应章节
- 正文无内部编号（SP*/F*/P*/B*/S*）——包括表注和图注
- 每个 H2 有至少 1 处项目锚点、1 处重难点分析、1 处 Win Theme 呼应
- 每个主响应 H2 已达到章节执行表中的最低目标字数，且高预算章节没有少于 5 个功能块
- **无虚假人名**：检查 Mermaid 图和人员表中是否出现"X工""X经理"等具体人名，全部替换为职位名称
- **限频词自查**：浏览全文，对第一组和第二组限频词逐个心中计数，超过2次的替换为同义词或删除修饰
- **排比句式**：检查是否有连续3个以上"通过X…"或"采用X实现Y"的排比结构，有则拆散为独立段落
- **提交结论校正**：如仍存在真实联系电话、真实人员信息、关键附件、关键证据页、关键时间窗口等待填项，结论只能写“建议微调后提交”，不得写“可直接提交”

如有问题，**一次 Edit** 批量修复（不做多轮循环）。Edit 范围：可补充遗漏的功能块、扩展字数不达标的段落、修复格式/标签/禁用词；不可重写已有段落、调整章节结构、新增 H2 章节。

#### 3.3 闭环回写

**口径更新**：写作中产生的新口径（新 SLA 承诺、新术语等），Edit `output/canon_current.md` 追加到对应分类末尾。每条新增口径标注来源方案，格式：`[新增: {NN}-{方案名}]`。后续方案可据此判断是原始口径还是前序方案新增的。

**需求矩阵回写**：Edit `output/scoring_map.md` 的需求响应矩阵，填写本方案覆盖的需求项的「响应方案」和「响应位置」列。

#### 3.4 完成报告

输出：方案编号、总字数、图表数、评分点覆盖率、项目锚点落实情况、Win Theme 贯穿情况、可提交性结论、各章节统计表。

**结论判定规则**：
- **可直接提交**：全域清单通过；高优先级证据已具备或已有正式附件引用；无真实值待填项；无口径冲突
- **建议微调后提交**：主体完整，但仍有真实联系电话/人员/附件/窗口待补，或存在少量图表标签、补证、表述边界问题
- **不建议提交**：评分点遗漏、需求未响应、口径冲突、关键章节严重欠字数、关键图表缺失、证据链断裂、明显 AI 味

## 二、边界与禁止

以下规则保护 context 窗口和执行效率。

1. **仅按指定路径读取文件**，不进行探索性 Search/Glob。
   原因：探索性搜索每次消耗 1-2K token，对已知路径的项目无意义。
   例外：Step 1 中 Glob 扫描 `output/summaries/*_summary.md` 获取编号。

2. **禁止逐章 Write→Read→Edit 循环**。每段一次生成即成品。
   原因：每次循环消耗 ~5K token context，4 章循环一次即耗尽 20K。
   例外：Step 3 终检的一次性 Read + 一次性 Edit 修复不在此限（Edit 可补充不足功能块/扩展欠字段落，但不得重写已有段落或调整章节结构）。

3. **字数以模型估算为准**，不运行 Bash 统计。
   原因：wc 命令的 token 开销 + 结果解析不划算。
   补偿：写作时按"每千字约 600 个汉字"估算，终检时凭 Read 回来的行数粗估。

4. **不触发其他 Skill**。本引擎自包含。
   原因：跨 Skill 调用会引入不可控的 context 膨胀和指令冲突。

5. **不回读上游分析文件**（tender_facts / scoring_map / bid_strategy）。
   原因：这些信息已由 plan_budget.md 消化整合，重复读取浪费 context。
   例外：Step 3 闭环回写 scoring_map.md 需求矩阵时可 Edit。
