默认待办任务路径`wiki/raw/todo.md`

## 步骤

1. 理解任务, 阅读相关文档(如有), 文档包括技能文档和项目文档,规格文档等.
  1.1 当发现文档存在以下情况必须先得到人类用户的确认后修正主动修正相关文档后再继续完成原本的任务.
    1.1.1 文档的知识已经过时.
    1.1.2 文档知识存在矛盾和冲突.

2. 完成任务.
3. 回填任务结果.

> ⚠️ **警告**：程序员的任务描述不一定正确。系统中可能已存在类似或更优的实现。若盲目按描述修改，可能破坏原本更好的设计。**必须先理解现有实现，再决定如何修改**。
**按需启用技能** - **非常重要**
| 前置条件 | 效果 | 不变量 |
|---------|------|-------|
| 数据库工具不可用 | **立即终止**所有后续任务 | 参见 [数据库查询工具](#数据库工具) |
| 开始任何任务 | 完整阅读任务列表（禁止跳读） | 仅锁定并执行**一个**待办任务 |
| 开始任何任务 | 先搜索既有实现，了解现状 | 禁止在不理解现有代码的情况下动手 |
| 全程 | 多 Agent 并行时，尊重他人的代码变更 | 不惊愕，不覆盖 |
| 全程 | 使用简单优雅的方式实现 | 满足功能需求，不要过度设计 |
| 涉及技能 | 根据任务类型按需启用对应技能 | 技能数量不限，缺技能 → 乱项目 |


# 任务执行指引

当任务来自 todo.md 时, 采用以下工作流(步骤)进行

> 仅执行**一个**待办任务。就算执行中发现了其他任务，也不执行。遇到阻碍时主动查手册，而不是凭经验埋头苦干。

## 工作流

```text
步骤 1: 读任务列表，锁定目标任务
  → 步骤 2: 按任务类型加载上下文和手册
    → 步骤 3: 执行任务（含迭代验证）
      → 步骤 4: 工具验证
        → 步骤 5: 任务完成后按专用技能回填结果
```

### 步骤 1：读任务列表，锁定目标任务

**任务选定规则**:

0. **本文末尾明确的任务** - 如有,通常来自于任务列表.
1. **顺序原则**: 默认 **自上而下 (Top-down)** 扫描，锁定 **第一个** 未完成的任务 (`- [ ]`)。
   - *理由*: 靠前的任务通常是依赖项或被搁置的高优任务。
2. **元任务优先**: 若列表中存在"更新本规则"的任务，优先执行。
3. **用户覆盖**: 若用户输入包含明确意图，则该意图优先级高于默认顺序。
4. **用户明确的描述优先**: 例如本技能文档加载后紧接着描述的任务优先.

**操作步骤**:

- 扫描 `todo.md` 或用户指定的任务列表。
- 跳过已完成 (`[x]`) 任务。
- 根据任务选定规则找到**一个** `- [ ]` 任务作为 `target_task`。
- 再次确认该任务是否具备执行条件。

### 步骤根据任务类型选定任务流程

| 任务类型 | 判断信号 | 执行要求 |
|---------|---------|----------|
| **调研/分析** | 含「调研」「分析」「研究」「为什么」 | 不修改源码；输出中文报告 |
| **反思重构 / 坏味道清理** | 含 `reflect` 或 `bad smell`、`坏味道` | **必须使用`gomtm-refactor`技能**；功能不变；使用 `code-reflect` / `code-review` 技能 |

#### 新增或修改功能流程

- 涉及数据库变更时：
  1. 查找已有测试用例，参考已有用例进行修改；若无则新建
  2. 先运行测试，**预期测试失败**（若通过则说明测试用例不完善）
  3. 迭代修正源码 → 微调测试 → 直到测试通过且符合任务要求
- 仅前端布局/样式变更时：无需修改测试用例

#### 「修复」流程

**临时测试用例存放**: 主测试目录下的 `.tmp_test/` 子目录

**步骤**:

1. 编写临时测试用例,**复现**用户描述的问题. 这一点**非常重要**, 因为确认了问题确实出现了, 是后续修复的前提.
  - 若无法复现 → 终止任务，要求提供更多细节 / 引导用户确认问题是否存在
2. 当成功复现了问题后,编写**合适**的测试用例, 并运行测试,确保新的测试是失败的而且是因为还没修复导致失败.(如果新的测试依然成功,说明测试用例无效)
3. 按需阅读关键文档和关键代码,确认问题的关键点.
4. 编写修复代码,并运行测试,确保新的测试是通过的.
5. 按需编写回归测试.
- 修复完成后，将有效测试用例移至正式测试目录


### 步骤 4：执行任务

> ⚠️ **关键约束**：如确信源码实现本身无误（用户操作失误导致问题），应以报告形式说明，**拒绝修改源码**。随意修改已正确的实现会造成更严重的问题。
> 工具验证,根据变更涉及的技术栈，执行对应的自动化验证：

```bash
# Go 静态检查（涉及 Go 代码时）
go vet ./...

npx ts-prune ...

# TypeScript 类型检查 + Lint（涉及前端代码时）
bun run check

# 数据库 pgTAP 测试（涉及数据库逻辑变更时）
bash testing/db-testing.sh

# 集成测试（完整验证）
go test -v ./testing/integration/...

# (前端)清理不需要的代码
npx ts-prune

# (golang) 检查未使用的变量
go run github.com/golangci/golangci-lint/cmd/golangci-lint@latest run -E unused --no-config --disable-all ./pkg/... ./cmd/...

# 格式化代码
bun run biome format | tail -n 50

# Lint 检查
bun run biome lint | tail -n 50

# 类型检查
bun run check

# 检查未使用的导出
npx ts-prune --project {projectRoot}/tsconfig.json

# 生成 mtmsdk openapi 客户端,含typescript,golang 客户端, 以及相关typescript supabase 类型定义
gomtm gen

# 部署 (开发环境)
gomtm deploy --skip-test=e2e

gomtm deploy --prod ...

# 运行集成测试
go test -v ./testing/integration/...

# 运行 go 静态检查
go vet

# golangci-lint 检查
go run
```

### 步骤 5：任务完成后回填结果

- 当任务来自 `todo.md` 或显式任务清单时，任务完成后必须回填结果。
- 详细回填格式、字段要求、后续任务追加规则，不放在全局流程中；在需要回填时启用专用 skill `gomtm-fill-task-results`。
