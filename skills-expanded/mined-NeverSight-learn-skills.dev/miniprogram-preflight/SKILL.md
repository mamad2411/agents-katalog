# 微信小程序上线前检查指南

## 核心原则

上线前检查的目标是**在上传代码给微信审核之前，发现所有可能被拒审或导致线上事故的问题**。检查完再上传。

按**阻断级别**分三类：
- **🔴 阻断**：不修不能发，发了必被拒审或出 Bug
- **🟡 警告**：建议修，不修有风险但不是一定会出问题
- **🔵 提示**：可优化的点，不影响上线

## 检查流程

收到检查请求后，按以下顺序逐项检查。**不要跳步，每项都跑完**。

### 第一步：项目识别

确定项目类型和相关路径：

| 项目类型 | 特征 | 编译产物路径 | 关键配置 |
|---------|------|------------|---------|
| Taro 项目 | 有 `package.json` + `@tarojs/cli` 依赖 | `dist/` | `src/app.config.ts` 或 `project.config.json` |
| uni-app 项目 | 有 `package.json` + `uni-app` / `@dcloudio` 依赖 | `dist/build/mp-weixin/` | `src/manifest.json` 或 `project.config.json` |
| 原生小程序 | 有 `app.json` 在根目录 | 根目录 | `app.json`、`project.config.json` |

如果无法自动判断，问用户。

### 第二步：逐项检查

按以下清单全部检查完，再汇总输出。每项检查后标注状态：[✓ 通过]、[✗ 不通过]、[- 跳过及原因]。

---

#### 🔴 1. 分包大小检查

**为什么**：主包超过 2MB（或总包超过 20MB）会导致真机预览/上传失败。

**检查方法**：
- 读取 `project.config.json` 或 `app.json` 查看有无分包配置（`subPackages` / `subpackages` 字段）
- 估算编译产物目录下各分包大小：
  - Taro：`dist/` 下各目录
  - uni-app：`dist/build/mp-weixin/` 下各目录
  - 原生：根目录各分包目录
- 如果项目已构建但有 `.gitignore` 排除了产物，提醒用户先构建

**判断标准**：
- 主包 < 2MB（实际建议留 300KB 余量，即 < 1.7MB）
- 总包 < 20MB（实际建议 < 18MB）

---

#### 🔴 2. 云开发环境检查

**为什么**：开发/测试环境的数据和配置不同，错用测试环境发布了谁也救不了。

**检查方法**：
- 搜索 `cloudbase` / `tcb` 相关配置中的 `envId`（如 `project.config.json`、`.env*`、源码中的环境初始化代码）
- 搜索环境变量文件（`.env`、`.env.production`、`.env.development`、`.env.local`）
- 搜索代码中硬编码的环境 ID（如 `new CloudBase({ env: 'xxx' })`、`cloudbase.init({ env: 'xxx' })`）

**判断标准**：
- 扫描项目中出现的所有 env ID，列出清单
- 如果只有**一个环境 ID**，且项目构建设置正确（`NODE_ENV=production` 或 `--mode production`），视为通过
- 如果有**多个不同的环境 ID**（比如开发环境和正式环境混用）：
  - 确认每个 ID 对应的用途
  - 检查构建流程是否在发布时正确切换了 ID（如 CI 中设置的环境变量）
  - 标记为 **阻断**，需要用户确认哪个是正式环境、引用是否正确
- 如果发现 `test`、`dev`、`development` 等关键词出现在环境变量名或 envId 中，标记为**警告**并让用户确认
- 不需要预判用户用什么环境 ID，只需要检测一致性并让用户确认

---

#### 🔴 3. 服务域名/白名单检查

**为什么**：微信小程序要求所有网络请求域名必须在后台配置白名单，少了就请求失败（线上直接挂）。

**检查方法**：
- 搜索代码中所有 `wx.request`、`wx.uploadFile`、`wx.downloadFile`、`wx.connectSocket` 的 URL
- 搜索 HTTP 请求库的 baseURL 配置
- 搜索配置文件中可能列出的域名白名单

**判断标准**：
- 所有请求的域名都已在微信公众平台配置
- HTTPS 协议（微信要求生产环境必须 HTTPS）
- 注意区分开发环境 API 域名和正式环境

---

#### 🔴 4. appid 与环境匹配检查

**为什么**：用错 appid 会导致提审失败或发布到错误的 App。

**检查方法**：
- 读取 `project.config.json` 中的 `appid`
- 读取 `project.tt.json`、`project.swan.json` 等跨端配置（如果是 Taro/uni-app）
- 读取 `src/manifest.json`（uni-app 项目）

**判断标准**：
- appid 是否与提审小程序匹配
- 是否有测试 appid 残留
- 跨端项目是否混淆了各端的 appid

---

#### 🟡 5. 基础库版本兼容性检查

**为什么**：用了高版本 API 但设置的最低基础库版本不够，低版本用户打开就报错。

**检查方法**：
- 读取 `project.config.json` 中 `libVersion` 或 `setting` 下的 `es6`、`minified` 等配置
- 搜索代码中是否有 `wx.canIUse()` 调用（说明开发者在注意兼容性）
- 扫描用到的小程序 API（如 `wx.login`、`wx.getUserProfile`、`wx.requestSubscribeMessage` 等），判断是否需要特定的基础库版本

**判断标准**：
- 用到的 API 是否在设置的最低基础库版本中可用
- 建议最低基础库版本：2.30.0+（覆盖绝大多数活跃用户）

---

#### 🟡 6. 废弃/即将废弃 API 检查

**为什么**：微信经常废弃 API，用了可能随时挂。

**检查方法**：
- 搜索 `wx.getUserInfo`（弹窗授权模式已废弃）
- 搜索 `wx.openSetting`（即将废弃）
- 搜索 `wx.getSystemInfoSync` 等常见废弃 API

**判断标准**：
- 是否有废弃 API 调用
- 是否使用了新版 API（如 `wx.getUserProfile` 替代 `wx.getUserInfo`）

---

#### 🟡 7. 代码残留检查

**为什么**：console.log 影响性能、TODO 表示未完成、调试代码直接影响线上功能。

**检查方法**：
- 搜索 `.js`/`.ts`/`.wxs` 文件中是否有 `console.log` / `console.info` / `console.warn`（仅检查非注释的）
- 搜索 `TODO` / `FIXME` / `HACK` 标记（低优先，仅做提示）
- 搜索调试相关的 mock 数据、测试账号、硬编码 token

**判断标准**：
- 原则上生产环境不应有 `console.log`（建议保留 `console.error` 用于监控）
- 调试代码不应出现

---

#### 🟡 8. 图片/静态资源检查

**为什么**：大图片导致首屏慢、分包大。

**检查方法**：
- 搜索项目中用到的图片资源，检查大小
- 检查是否使用了 webp 等压缩格式（仅提示）
- 检查 CDN 资源是否为 HTTPS

**判断标准**：
- 单张图片建议 < 200KB
- Tabbar 图标必须用本地图片（微信限制不支持网络图片做 tabbar）

---

#### 🟡 9. 审核相关检查

**为什么**：被拒审是上线最普遍的卡点。

**检查方法**：
- 检查**登录/授权逻辑**：是否在首页强制要求授权（微信审核标准：用户不授权也能浏览）
- 检查**用户隐私协议**：是否有隐私协议弹窗
- 检查**虚拟支付**：小程序内是否有非法的虚拟商品购买（iOS 小程序禁止虚拟支付）
- 检查**类目资质**：提示用户确认所选类目与内容是否匹配

**判断标准**：
- 首屏不应强制授权登录
- 涉及个人信息必须有隐私协议
- iOS 不能有虚拟商品购买流程

---

#### 🔵 10. 版本号与更新日志

**为什么**：版本号不更新会导致线上用户无法识别新版。

**检查方法**：
- 读取 `project.config.json` 中是否有版本号字段

**判断标准**：
- 确认版本号是否已递增
- 建议准备更新日志供提审填写

---

#### 🔵 11. project.config.js 检查

**检查方法**：
- 读取 `project.config.json` 确认 `minified`（代码压缩）已开启
- 读取 `project.config.json` 确认 `es6`（ES6转ES5）已开启（针对低版本手机）
- 检查 `project.config.json` 的 `setting` 下 `urlCheck` 是否关闭（开发时关的，上线无所谓但提个醒）

---

### 第三步：输出检查报告

所有检查项完成后，按以下格式输出报告：

```markdown
# 小程序上线前检查报告

**项目**: [项目名称]
**类型**: Taro / uni-app / 原生
**检查时间**: [当前时间]
**构建状态**: [已构建 / 未构建 - 记得先构建]

---

## 🔴 阻断项（必须修复）

详见各条目

## 🟡 警告项（建议处理）

详见各条目

## 🔵 提示项（可选优化）

详见各条目

---

## 摘要

| 级别 | 通过 | 不通过 | 跳过 |
|------|------|--------|------|
| 🔴 阻断 | n | n | n |
| 🟡 警告 | n | n | n |
| 🔵 提示 | n | n | n |

**结论**: ✅ 可以发布 / ⚠️ 建议修复后再发 / 🔴 不建议发布
```

## 注意

- 不要假设用户已经构建了项目——如果产物目录不存在，提醒用户先构建
- 各项评估尽量给出具体的文件和行号引用，方便用户定位问题
- 对于需要人工判断的项（如域名白名单），标注"需人工确认"
- 报告中每项的结论要清晰，不要模糊表达
