# teire

日本語の文章を、必要な範囲で手入れする。

目的は、AIらしさを隠すことではない。

結論が分かること。理由が分かること。必要な説明があり、余計なものが残っていないこと。そのうえで、文章そのものが固定されたテンプレートに見えないことを重視する。

## 適用方針

依頼された文章の目的、媒体、読者、文体指定を最優先する。

このSkillのルールは、それらを上書きする絶対的な規則ではない。

技術解説、レビュー、比較、説明文では、要点や結論を必要以上に後ろへ置かないことを基本とする。

一方で、創作、会話文、コピーライティング、エッセイなど、結論を先に示すことが適切でない文章では、その文章に合った構成を優先する。

既存の文章を編集する場合は、元の文体や意図を必要以上に変えない。

## 大原則

文章を直すこと自体を目的にしない。

すでに自然で分かりやすい文章は、そのまま残す。修正するのは、意味、具体性、正確性、読みやすさのどれかが実際に改善する場合だけとする。

基本的には、要点や結論を早めに示し、その根拠を説明する。ただし、

`結論 → 根拠 → 説明 → コード → 再度結論`

という順序をテンプレートとして固定しない。

短い回答なら結論と理由だけでよい。比較なら候補を説明してから判断してもよい。技術説明ではコードを先に示した方が分かりやすいこともある。

必要な情報は残す。文章の形は固定しない。

書いた後に確認する。

- 何を伝えたい文章なのか分かるか
- 判断がある場合、その理由が分かるか
- 事実、推測、意見を区別できるか
- 一般論や抽象語だけで説明を済ませていないか
- 同じ文型や構造を繰り返していないか
- 修正前より本当に読みやすくなっているか



## コアルール



### A. 判断と根拠

1. **判断には軽く根拠を添える**

判断を示す必要がある場合は、単に言い切るだけで終わらせない。

「自分ならAを選ぶ」のように判断を示し、その理由へ短く触れる。

理由を説明するために長い前置きを置く必要はない。

例:

> [一人称]なら○○を選ぶ。○○との組み合わせの相性が良くて、○○をそのまま使いやすいからだ。

判断を必要としない事実説明まで、無理に意見へ変えない。

1. **比較では判断の理由を示す**

複数の選択肢を比較する場合、最終的な判断が必要なら明示する。

採用する選択肢については、なぜ選ぶのかを説明する。

主要な比較対象については、採用しない理由にも必要な範囲で触れる。候補が多い場合、判断にほとんど影響しない選択肢まで個別に説明する必要はない。

比較対象の利点を無視して、採用しない理由だけを強調しない。

ただし、

`結論 → Aの理由 → Bの理由 → 再結論`

という構造を毎回繰り返さない。

理由は本文に織り込んでもよい。比較表を使ってもよい。不採用理由から先に説明してもよい。

必要な情報は残すが、順序は固定しない。

1. **強度を根拠に合わせる**

評価や断定の強さは、根拠の強さに合わせる。

人間らしく見せるために「悪くない」「まあまあ」「微妙」などの中間表現を意図的に挿入しない。

根拠が十分なら明確に判断する。根拠が限定的なら、その範囲が分かる表現にする。

必要以上に煽らず、必要以上に弱めない。

例:

根拠が限定的:

> この条件なら候補にはなると思う。

判断材料が十分:

> 自分ならこちらを選ぶ。構成を単純にできるからだ。

明確な問題がある:

> この設計は採用しない。認証情報をLocalStorageへ保存しているからだ。

1. **情報の確度を正しく示す**

確認済みの事実を、人間らしく見せるために「らしい」「ようだ」「そうです」と伝聞化しない。

確認済みの事実は明確に書く。

推測、可能性、未確認情報は、それぞれの確度が分かるように表現する。

例:

> 公式ドキュメントでは、この機能に対応している。

> この挙動になる可能性が高い。

> 現時点では確認できていない。

文体上の都合より、情報の正確さを優先する。

### B. 具体性

1. **一般論だけで終わらせない**

「多くの人」「現代では」「一般的に」などの広い表現を、説明の代わりに使わない。

一般論そのものが必要なら使ってよい。

ただし、判断や説明に必要な場合は、対象、条件、具体例、数値、固有名詞などへ降りる。

例:

悪い:

> 多くのエンジニアは状態管理に悩んでいる。

改善:

> Reactで複数画面から同じクライアント状態を更新するようになると、状態管理の方法を決める必要が出てくる。

「自分は」「あなたは」を無理に追加する必要はない。

1. **具体性のために情報を作らない**

具体性を高めるために、元の文章、与えられた資料、確認済みの情報に存在しない事実、数値、経験、引用、固有名詞を作らない。

具体的な情報が不足している場合は、もっともらしい内容を補うのではなく、元の情報だけで書ける範囲に留める。

必要なら、

> 詳細な数値は確認できていない。

> この条件については元の文章から判断できない。

のように、不足している情報をそのまま示す。

文章を具体的に見せることより、内容を正しく保つことを優先する。

1. **false agencyは必要な場合だけ修正する**

モノが主語になっているだけでは修正しない。

次のような普通の表現は、そのままでよい。

> データが示している。

> APIがリクエストを受け取る。

> エラーが発生した。

> この変更によって問題が解消された。

修正を検討するのは、次の場合とする。

- 誰が判断や決定をしたのか分からなくなる
- 責任主体が不必要に隠れている
- 因果関係を抽象的な表現で済ませている
- 主体を具体化すると説明が明確になる場合
- 擬人化された表現によって意味が分からない

能動態への変更を目的にしない。

日本語として自然なら受動態をそのまま使う。

例:

> 不正ログイン検知ルールが5回連続で発生したため、認証サービスによってアカウントが一時停止した。

主体と因果関係が十分に分かるなら、それ以上書き換えない。

### C. 構造

1. **文章の形を固定しない**

文章全体を同じテンプレートへ当てはめない。

基本として要点や結論を早めに示すことは推奨するが、内容に応じて位置を変えてよい。

次の要素を毎回同じ順序、同じ段落数、同じ文型で配置しない。

- 結論
- 根拠
- 比較
- 詳細な説明
- コード
- 注意点
- 最終確認

短い質問に長い構成を持ち込まない。

長い説明を無理に短文へ分割しない。

文章の目的と情報量に合った構造を選ぶ。

1. **見出しは短く具体的にする**

見出しだけで、その節に何が書かれているか分かるものを優先する。

好ましい例:

> Session認証

> Session認証の採用する理由

> Reduxを採用しない理由

> キャッシュに関してはAPI側で行う

> エラーハンドリング

> 注意点

不要な状況語は省く。

例:

> 今回はSession認証を採用する

より、

> Session認証を採用する

を優先する。

次のような、内容より表現が目立ち、文章としての意味が皆無になる見出しは避ける。

> 認証設計の本質を見つめ直す

> 状態管理という迷宮を抜ける

> 開発体験を変える新しい地平

主張型の見出しそのものは禁止しないが、

具体的な方針や節の内容が明確なら使ってよいが、伝える意図が分かりづらくなるため非推奨

1. **二項対比を連続させない**

「AではなくB」「単なるAではなくB」のような二項対比は、必要なら使ってよい。

ただし、説明を強く見せるためだけに繰り返さない。

直接Bと書いた方が分かりやすいなら、そうする。

例:

> これは単なるキャッシュではなく、状態管理の仕組みだ。

より、

> これは状態管理の仕組みとしても機能する。

の方が自然なら、後者を使う。

1. **項目数を先に決めない**

「3つのポイント」「5つの理由」のように、見栄えのために項目数を決めない。

必要な内容が2つなら2つでよい。4つ必要なら4つ書く。

逆に、3項目あるという理由だけで削る必要もない。

内容の区切りが自然かどうかで判断する。

1. **リズムを自然にする**

文や段落の長さを機械的に揃えない。

ただし、人間らしさを演出するために意図的に崩す必要もない。

説明の内容に応じて、自然に長短が変わる状態を目指す。

次のような連続を確認する。

- 同じ長さの段落が続く
- 同じ接続詞から始まる
- 「〜だからです」が何度も続く
- 全段落が小さな結論で終わる
- 同じ形式の箇条書きが連続する
- 毎節で同じ位置にコードや表が入る

直前の節と同じ構造になっていても、それが最も読みやすいなら無理に変更しない。

### D. 語彙と表現

1. **抽象語を重ねない**

「本質」「思想」「文脈」「設計」「解像度」などの単語そのものは禁止しない。

問題は、意味を具体化しないまま抽象語を重ねることにある。

例:

> この設計の本質は、開発体験の解像度を高め、プロダクトの文脈を再定義することだ。

のような文章は、何がどう変わるのか具体化する。

技術的な意味を持って使われている「設計」「Context」などはそのままでよい。

1. **技術用語を無理に日本語化しない**

技術的な話題では、その分野で一般的に使われる語をそのまま使ってよい。

例:

- Component
- State
- Context
- API
- Middleware
- Cache
- Routing
- Query

一方で、意味を大きく見せるためだけの横文字やメタファーは避ける。

例:

> 思考のOSをアップデートする

より、

> 考え方を変える

の方が意味が変わらないなら、後者を使う。

1. **強調と装飾を必要以上に使わない**

太字、引用符、記号などを、文章の勢いを作るためだけに繰り返さない。

太字は重要な結論や、読み飛ばされたくない箇所に限定する。

コードブロックは、説明の理解に役立つ場合は積極的に使ってよい。

技術説明では、文章だけで長く説明するよりコードを示した方が早い場合がある。

装飾目的の絵文字は原則として追加しない。

元の文章に絵文字が含まれている場合は、媒体、文体、依頼内容に必要かを見て残すか判断する。

装飾の少なさそのものを目的にしない。

### E. 人間らしい表現

1. **自然な主観は残す**

「悪くない」「ここは少し微妙」「自分なら採用しない」など、判断を分かりやすくする自然な表現は残してよい。

人間らしさを演出するために、毒、皮肉、自虐を追加する必要はない。

逆に、元の文章に意味のある軽い皮肉や感情があり、削ることで文章が不自然になるなら残す。

目的は人格を消すことではなく、読みやすくすること。

## クイックチェック

書き終わったら、必要な項目だけ確認する。

### 判断

- [ ] 結論や判断が必要な文章で、何を選ぶのか分かるか
- [ ] 判断の理由が最低限示されているか
- [ ] 主要な比較対象について、採用理由と不採用理由が分かるか
- [ ] 「場合による」だけで判断を避けていないか
- [ ] 根拠以上に強く断定していないか



### 正確性

- [ ] 事実、推測、意見を区別できるか
- [ ] 確認済みの情報を不必要に伝聞化していないか
- [ ] 未確認情報を事実として書いていないか
- [ ] 具体性を出すために、元にない事実、数値、経験、引用を追加していないか
- [ ] false agencyによって主体や因果関係が分かりにくくなっていないか



### 具体性

- [ ] 一般論だけで説明を終えていないか
- [ ] 抽象的な評価を、必要に応じて具体化しているか
- [ ] 手元にある数値、条件、対象、具体例を使った方が分かりやすくならないか
- [ ] 抽象語を連続させていないか



### 構造

- [ ] 文章の目的や媒体に合った構成になっているか
- [ ] 要点や結論が必要以上に後ろへ隠れていないか
- [ ] 毎節が同じ構造になっていないか
- [ ] 同じ接続詞や文末を連続して使っていないか
- [ ] 段落の長さが不自然に揃っていないか
- [ ] 箇条書きや表を使うこと自体が目的になっていないか
- [ ] 項目数を先に決めて内容を水増ししていないか



### 見出し

- [ ] 見出しだけで節の内容を予測できるか
- [ ] 不要な「今回は」などが入っていないか
- [ ] 抽象語や比喩を重ねていないか
- [ ] 普通の名詞句へ変えても情報が失われない装飾的見出しになっていないか



### 表現

- [ ] 太字や強調が多すぎないか
- [ ] 装飾目的の絵文字を追加していないか
- [ ] 技術用語を不自然に日本語化していないか
- [ ] 意味の薄い横文字やメタファーを使っていないか
- [ ] 自然な主観まで削って無機質な文章にしていないか
- [ ] 同じ文章構造を避けるためだけに、不自然な表現へ変えていないか



## 評価

必要に応じて、次の5軸を1〜10で確認する。

点数は品質を証明する指標ではない。

修正が必要な箇所を見つけるための補助として使う。


| 軸   | 質問                 |
| --- | ------------------ |
| 判断  | 必要な場面で結論と理由が分かるか   |
| 具体性 | 一般論や抽象語だけで終わっていないか |
| 正確性 | 事実、推測、判断の確度が適切か    |
| 自然さ | 文型や構造が機械的に反復していないか |
| 削減  | 不要な説明、装飾、繰り返しを削れるか |


低い項目がある場合は、その理由を確認して必要な箇所だけ修正する。

合計点や固定された閾値だけを理由に、文章全体を書き直さない。

## 修正の優先順位

時間が限られている場合は、次の順で確認する。

1. **正確性**
  - 事実関係を変えていないか
  - 推測を断定していないか
  - 元の意味を壊していないか
  - 元にない情報を追加していないか
2. **判断と根拠**
  - 結論が必要な文章で判断が見えるか
  - 判断の理由が分かるか
  - 主要な比較対象を雑に切り捨てていないか
3. **具体性**
  - 一般論だけで終わっていないか
  - 手元にある情報の範囲で、抽象語を具体的な内容へ置き換えられないか
4. **構造**
  - 文章の目的や媒体に合っているか
  - 文章の形がテンプレート化していないか
  - 結論、段落、比較、コードの配置が内容に合っているか
5. **語彙と装飾**
  - 不要な強調、抽象語、メタファーを削れるか
  - 技術用語まで過剰に言い換えていないか
  - 不要な絵文字を追加していないか

表面上のAIらしさを消すために、正確性や読みやすさを犠牲にしない。

## 修正時の禁止事項

次の処理を機械的に行わない。

- すべての文章を短文化する
- すべての受動態を能動態へ変える
- すべての一般論を一人称へ変える
- 比較のたびに同じ順序で理由を並べる
- 候補すべてについて採用・不採用理由を機械的に列挙する
- 人間らしさのために伝聞表現を追加する
- 人間らしさのために毒や皮肉を追加する
- 具体性を出すために事実、数値、経験、引用を作る
- 技術用語を片端から日本語へ置き換える
- 3項目という理由だけで2項目へ減らす
- 命題型見出しという理由だけで名詞句へ変える
- リズムを崩すためだけに文の長さを変更する
- 評価点を上げるために意味のない修正を加える
- 依頼された文体や媒体の性質を、このSkillのルールで上書きする



## 最終判断

修正後または作成後の文章について、最後に確認する。

> 与えられた情報、意図、事実を保ったまま、本当に読みやすくなっているか。

明確に改善していないなら、その修正は戻してよい。

teireは文章を書き換えるためのルール集ではない。

必要なところだけ手入れし、すでに問題のない部分には触らない。
