# Adversarial PR Review (Claude only) → 머지 블로커 코멘트

서브 에이전트가 적대적으로 리뷰하고, 리드가 **머지 블로커만** 걸러 표로 정리해 PR 에 코멘트로 남긴다.
`ip-code-review` 와 결과물은 같고, codex 구독이 필요 없다.

| 역할 | 주체 | 하는 일 |
|------|------|---------|
| 리뷰어 | Opus 5 서브 에이전트 3개 | 각자 다른 관점으로 구현·설계·가정을 공격 |
| 리드 | 이 세션 (Opus 5) | 체크아웃, 서브 에이전트 실행, 머지 블로커 선별, 해결 방안 작성, 코멘트 등록 |

리드는 **직접 리뷰하지 않는다.** 서브 에이전트가 뱉은 것 중에서 고르고, 각각에 대한 해결 방안을 붙인다.

## 입력

- **브랜치** — 체크아웃할 브랜치. 필수.
- **PR 번호** — 리뷰 대상 PR. 필수.

둘 중 하나라도 없으면 물어본다. 추측하지 않는다.

## 절차

### 1. 체크아웃

체크아웃 전에 워킹 트리를 확인한다.

```bash
git status --short
```

- **커밋 안 된 변경이 있으면 멈추고 사용자에게 알린다.** 체크아웃은 남의 작업을 날릴 수 있다. stash 를 임의로 하지 않는다.
- 깨끗하면 진행한다.

```bash
git fetch origin
git checkout <브랜치>
git pull --ff-only
```

리뷰가 끝나도 원래 브랜치로 되돌리지 않는다. 보통 이어서 수정하게 된다.

### 2. PR 메타 확인

```bash
gh pr view <n> --json number,title,url,baseRefName,headRefName,additions,deletions,changedFiles
```

- `headRefName` 이 방금 체크아웃한 브랜치와 다르면 **멈추고 사용자에게 알린다.** 엉뚱한 코드를 리뷰하게 된다.
- `baseRefName` 을 base ref 로 쓴다. 아래 프롬프트에 `origin/<baseRefName>` 형태로 박아 넣는다.

### 3. 적대적 리뷰 서브 에이전트 3개 실행

Agent 툴로 `subagent_type: "general-purpose"`, `model: "opus"` 서브 에이전트 3개를 **한 메세지에서 동시에** 띄운다. 순차로 돌리지 않는다.

각 프롬프트에 공통으로 넣는다:

```
브랜치 <브랜치> 가 origin/<base> 에 머지되기 직전이다. 적대적으로 리뷰해라.

대상 diff:
  git diff origin/<base>...HEAD

규칙:
- diff 에 실제로 있는 코드만 지적한다. 기억이나 추측으로 코드를 만들어내지 마라.
- 지적할 때마다 해당 파일을 직접 열어 주변 맥락(호출부 포함)을 확인한다.
- 스타일·네이밍·취향 문제는 보고하지 마라.
- 파일을 수정하지 마라. 읽기만 한다.

각 지적을 이 형식으로 반환한다:
  위치: <파일:줄>
  문제: <한 줄>
  실패 시나리오: <어떤 입력/상태 → 어떤 잘못된 결과>
  근거: <해당 코드 인용>
지적할 게 없으면 "없음" 이라고만 답한다.
```

관점은 서브 에이전트마다 다르게 준다:

| # | 관점 | 공격 지점 |
|---|------|-----------|
| 1 | 정확성 | 로직 오류, 경계 조건, null/undefined, 에러 삼킴, 되돌릴 수 없는 실패 경로 |
| 2 | 보안·데이터 무결성 | 인증/인가 우회, 인젝션, 검증 누락, 데이터 유실·손상, 마이그레이션 역방향 |
| 3 | 통합·회귀 | 기존 호출부 파괴, 인터페이스 변경 누락, 동시성·경합, 설정/환경 가정 |

- 서브 에이전트가 서로의 결과를 보지 못한다. 중복 지적은 리드가 4단계에서 합친다.
- 결과가 빈손으로 오면 그대로 받아들인다. 리드가 대신 리뷰해서 채우지 않는다.

### 4. 머지 블로커 선별

세 결과를 합쳐 지적을 하나씩 통과시킨다. **아래를 전부 만족해야 블로커다.**

- diff 에 실제로 있는 코드다. 서브 에이전트가 추측으로 만든 코드가 아니다 — **인용된 줄을 직접 열어 확인한다.** 없으면 버린다.
- 구체적 실패 시나리오가 성립한다. 어떤 입력/상태 → 어떤 잘못된 결과인지 쓸 수 있다.
- 그 실패가 **머지 후 프로덕션에서 터지거나 데이터·보안이 깨진다.**

나머지는 전부 버린다. major / minor / 취향 문제 / 리팩터링 제안은 코멘트에 넣지 않는다. 블로커 목록에 노이즈가 섞이는 순간 이 코멘트는 안 읽힌다.

같은 문제를 둘 이상이 지적했으면 한 줄로 합친다. 두 번 지적됐다고 더 심각한 것은 아니다.

각 블로커에 **추천 해결 방안**을 한 줄로 붙인다. 코드를 고치는 것이 아니라 무엇을 어떻게 바꾸면 되는지 지시한다.

### 5. 코멘트 등록

먼저 표를 사용자에게 보여준다. 그다음 등록한다.

```bash
gh pr comment <n> --body-file <파일>
```

- 본문은 heredoc 으로 임시 파일에 쓰고 `--body-file` 로 넘긴다. `--body` 에 여러 줄 마크다운을 인라인으로 넣지 않는다.
- **블로커가 0이면 그 사실을 한 줄로 코멘트한다.** 표는 생략한다.

## 코멘트 형식

```markdown
## 🚫 머지 블로커 (Claude adversarial review)

| # | 위치 | 문제 | 실패 시나리오 | 추천 해결 방안 |
|---|------|------|---------------|----------------|
| 1 | `src/a.ts:42` | 락 없이 카운터 증가 | 동시 요청 2건 → 하나가 유실 | `Atomics.add` 로 교체하거나 트랜잭션 안으로 이동 |

블로커 N건. 전부 해결 전에는 머지하지 않는다.
```

- 셀 안에서 줄바꿈하지 않는다. 표가 깨진다. 길면 `<br>` 를 쓴다.
- 위치는 반드시 `파일:줄`. "인증 로직 부근" 같은 건 위치가 아니다.
- 서브 에이전트 원문을 그대로 붙이지 않는다. 표에 맞게 다시 쓴다.

**파일을 고치지 않는다.** 이 스킬의 산출물은 코멘트다. 수정은 사용자가 따로 요청할 때 진행한다.

## 하지 말 것

- 더러운 워킹 트리에서 체크아웃 강행하기. 멈추고 알린다.
- 리드가 직접 리뷰해서 항목을 추가하기. 선별과 해결 방안이 리드의 일이다.
- 서브 에이전트를 순차 실행하기. 한 메세지에 3개를 같이 띄운다.
- 인용된 줄을 확인하지 않고 표에 올리기. 없는 코드를 지적한 코멘트는 신뢰를 통째로 날린다.
- major / minor 를 표에 섞기. 블로커만 남기는 것이 이 스킬의 전부다.
- 사용자에게 안 보여주고 바로 코멘트 등록하기.
