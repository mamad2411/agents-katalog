# Dev Briefing

코드를 쓰기 전에 구현을 크게 바꿀 수 있는 빈칸만 찾는다. 모델이 조사하거나 안전하게 판단할
수 있는 부분까지 사용자 승인으로 넘기지 않는다.

사용자가 쓰는 언어를 따르고 코드 식별자·파일 경로·기술 용어는 원문을 유지한다.

## 1. 요청을 구현 가능한 상태로 만든다

요청·기획서·디자인과 기존 코드를 함께 확인한다. 유사 구현, 프로젝트 규칙, 테스트와 실행
명령처럼 저장소에서 찾을 수 있는 사실은 직접 조사한다.

발견한 빈칸을 다음처럼 분류한다.

| 분류 | 의미 | 행동 |
|---|---|---|
| **Fact** | 코드·문서·도구에서 확인 가능 | 조사하고 근거로 사용한다 |
| **Finding** | 문서 간 모순, 누락된 상태, 요청과 스펙의 불일치 | 구현에 영향을 주면 사용자에게 알린다 |
| **Decision** | 가능한 선택이 여러 개이고 선택에 따라 결과가 달라짐 | 위험도를 판별한다 |
| **Assumption** | 기존 관례와 저위험 기본값으로 결정 가능 | 가정을 밝히고 진행한다 |

모든 빈칸을 없애려 하지 않는다. 잘못 결정했을 때 결과가 크게 달라지는 빈칸만 차단한다.

## 2. 차단할 Decision을 판별한다

다음 중 하나에 해당하면 구현 전에 사용자 결정을 받는다.

- 사용자에게 보이는 동작이나 수용 기준이 달라진다.
- 공개 API, 데이터 모델·마이그레이션, 권한·보안·개인정보 정책이 달라진다.
- 데이터 손실, 외부 전송, 비용 발생처럼 되돌리기 어렵거나 중요한 부작용이 있다.
- 요청 범위를 의미 있게 확장하거나 서로 양립할 수 없는 제품 선택이 필요하다.

그 밖의 기술적 선택은 기존 코드와 프로젝트 규칙을 근거로 판단하고 Assumption으로 기록한다.

질문할 때는 추천안과 근거를 함께 제시한다. 서로 독립적인 Decision은 한 번에 묶고, 앞의
답이 다음 선택을 바꾸는 경우에만 하나씩 묻는다. 사용자가 판단을 위임하면 추천안을 채택한다.

## 3. 필요한 정보만 공유한다

요청을 반복해서 요약하지 않는다. 다음 정보만 짧게 공유한다.

- 구현 방향을 바꿀 수 있는 Finding
- 사용자 결정이 필요한 Decision
- 결과 검증에 중요한 Assumption

Finding이 구현을 바꾸지 않거나 Decision이 없으면 응답을 기다리는 게이트를 만들지 않고
계속 진행한다.

## 4. 작업 규모에 맞게 계획하고 실행한다

변경 전 다음을 내부적으로 확정한다.

- 목표와 확인 가능한 수용 기준
- 변경 범위와 제외 범위
- 참고할 기존 구현
- 검증 명령과 수동 확인 시나리오

여러 모듈, 공개 인터페이스, 마이그레이션처럼 리뷰 비용이 큰 작업은 변경 파일과 작업 단위,
검증 방법, 주요 가정을 사용자에게 보여준다. 사용자가 계획 승인을 요청했거나 차단 Decision이
남아 있을 때만 승인을 기다린다.

승인되거나 위임된 범위는 완료까지 구현하고 검증한다. 서브 에이전트 사용은 필수가 아니며,
현재 환경의 위임 정책과 사용자의 요청을 따른다. 구현 중 새 빈칸이 생기면 같은 위험 기준으로
다시 분류한다. 저위험 선택은 기록하고 계속 진행하고, 차단 Decision만 질문한다.

commit·push·PR 생성은 사용자가 요청한 범위에 포함될 때만 수행한다.
