# 概述

这个技能用于 `todo.md` 或其他显式任务清单的收尾阶段。它的职责不是执行任务本身，而是在任务已经完成、验证已经结束之后，把结果准确回填到原任务项，确保后续 agent 能直接从任务历史理解发生了什么。

若任务来自其他文件，例如计划文档或用户明确给出的任务清单，应优先更新原任务项所在文件；只有当原任务项本身来自 `todo.md` 时，才更新 `todo.md`。

# 何时使用

只在以下时机使用：

1. 当前处理的任务已经完成，或已经得出“无需改代码”的明确结论。
2. 你正准备结束本次任务。
3. 原任务来自 `todo.md`、计划文档，或用户提供的显式任务列表。

不要在任务开始阶段使用，不要在任务尚未完成时提前标记完成。

# 执行顺序

1. 找到本次实际完成的原任务项，只处理这一项。
2. 保留原任务描述不变，将 `- [ ]` 改为 `- [x]`。
3. 立刻追加 `[任务结果]`，用中文概括真实结果，不写空话。
4. 追加 `[关键源码]`，至少给出一个可点击路径；能带行号时优先带行号。
5. 如有报告，追加 `[详细报告]`。
6. 如有关键验证命令或验证事实，追加 `[验证]`。
7. 仅当存在明确后续开发建议且待办数量较少时，才追加新的待办任务。

# 固定格式

最小回填模板：

```markdown
- [x] {原任务描述，不得更改}
  [任务结果] {中文说明本次实际完成了什么，或最终结论是什么}
  [关键源码] [file_a](path/to/file_a#L1) [file_b](path/to/file_b#L1)
  [详细报告](docs/reports/xxx.md#L1)
  [验证] `command 1` `command 2`
```

规则：

1. `[任务结果]` 必填。
2. `[关键源码]` 在涉及源码、配置、技能、文档变更时必填。
3. `[详细报告]` 只在确实产出报告时填写；没有报告就省略整行。
4. `[验证]` 只记录真正执行过的命令或真实完成的验证事实；没有验证内容时可以省略整行。

# 后续任务追加规则

只有同时满足以下条件时，才追加后续任务：

1. 本次任务自然暴露出明确下一步。
2. 当前待办任务数量较少，不会让列表失控膨胀。

追加优先级：

1. 降低系统复杂度、删除残留兼容层、收敛坏味道。
2. 修正明显设计问题。
3. 延续当前任务尚未完成但已明确的部分。
4. 补足缺失功能。
5. 修复已确认的缺陷。

禁止追加这种空泛任务：

1. `补充测试`
2. 没有明确目标的“继续优化”
3. 无验收标准的泛化重构项

追加任务时，保持与现有 `todo.md` 风格一致，至少包含：

1. 任务标题
2. 提示或要求
3. 验收标准
4. 必要时附 `[关键源码]`

# 边界与禁止项

1. 不要改写原任务描述。
2. 不要顺手把无关任务标记完成。
3. 不要把结果写到额外历史文件代替更新原任务项。
4. 不要伪造“已验证”或“已完成”。
5. 调研任务即使没有改源码，也应回填真实结论，并附报告链接。
6. 若本次结论是“源码无需修改”，也应如实写入 `[任务结果]`，而不是跳过回填。

# 常见错误

错误：

1. 只写“已完成”，没有说明完成了什么。
2. 漏掉关键源码链接，导致后续无法快速定位修改点。
3. 把结果写到其他文档，而不是原任务项。
4. 提前回填，后续又继续改动，导致记录失真。
5. 机械追加一堆模糊后续任务，污染任务列表。

正确做法：

1. 把回填视为任务的最后一步。
2. 只记录真实完成的结果与真实验证。
3. 让下一位 agent 仅靠任务条目就能快速理解本次产出。
