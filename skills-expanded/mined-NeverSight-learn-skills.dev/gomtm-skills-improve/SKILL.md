## when to use

- 用户明确指出真实源码中错误并给出正确修正方法
- 用户明确指示对某一类型源码进行开发指示
- 用户明确对 `gomtm:*`名称空间下的具体技能进行编辑或者重写时。
- 用户明确要求补充技能例子、修正触发条件描述、或让技能文档与真实工程约定对齐时。

### 通用步骤

1. 完整阅读相关源码或文档，确认用户指出的问题真实存在。
2. 确认用户提供的修正方法**完整有效**；如果存在歧义，应**先与用户确认**。
3. 阅读目标技能的 `SKILL.md` 与相关 `references` 文档，确认问题属于：
   - 触发条件描述错误
   - 规则缺失
   - 例子缺失
   - 与真实源码/工程约定不一致
4. 如果简单扩充即可覆盖目标问题，优先最小修改；只有在原文结构已无法承载时，才新增章节。
5. 修改技能文档时，优先保持：
   - 触发条件清晰
   - 规则精简
   - 例子最少但足够
   - 与真实工程约定一致
   - 描述足够泛化；不要把一次性任务中的真实服务名、真实域名、真实端口、真实账号或临时环境值写成技能规范
6. 按需使用 `skill-creator`、`writing-skills` 等相关技能辅助修正。

### 技能文档泛化规则

- 面向复用的技能正文优先使用 `<service>`、`<host>`、`<domain>`、`<port>`、`<path>`、`<owner>` 等占位符，或使用 `SERVICE="..."` 这类变量化示例。
- 真实项目名、真实域名、真实端口、真实账号只在它们是该技能的稳定触发条件或 canonical 工程事实时出现；否则只应出现在用户任务、目标主机 README、报告或运行产物中。
- 示例应展示结构和决策，不应把上一次任务的具体值固化为后续 agent 会照抄的模板；命令示例优先用变量，代码示例优先用中性命名。
- 若技能本身是某个具体应用的专用技能，仍应避免在通用流程中写死公网域名、临时端口或一次性部署名称；用“该服务”“公网入口”“运维 README”等泛化表达。

### 例子编写规则

- 错误例子优先展示会导致 agent 误判的结构，不依赖真实文件名、真实类名或真实域名。
- 正确例子只在能显著减少误解时提供；如果规则本身已经足够，省略正确代码以节约篇幅。
- 示例中的名称使用中性角色，例如 `ThinWrapperPage`、`FeatureView`、`SERVICE`、`PUBLIC_HOSTNAME`。
- 需要体现项目专属事实时，只写事实类型，不写一次性值，例如“应用运维 README”优于具体绝对路径。

## 类别：反思

### refactor 技能文档规范

- 足够泛化，不是针对某一具体源码文件，不是针对某特定函数。
- 精简描述，不要啰嗦，必须假定阅读文档的是专家，只需要给出刚好足够的提示，对方能够正确领悟。
- 可能当前技能库可能存在多个不同方面（大类）的反思技能。须确保在合适的技能文档进行编辑。
- 所有源码反思技能文档不能有重复的反思点(反思描述指引)。
- 技能文档描述应当确保符合skill规范且有刚好且**足够**线索让 agent在最合适的时机正确加载和使用技能。

### 例子

#### 例子1：薄封装反模式

  return <FeatureView />;

## 类别：风格实现规范

### gomtmui design 技能

通常对应于前端的功能性的页面和组件开发约定，一般是`gomtmui-design`这个技能。
`gomtmui-design` 技能文档通常根据不同功能类型在`references`子文档下进行详细设计和说明，`SKILL.md`对`references`文档进行摘要描述并引用`references`目录下的子文档。

当用户指出前端页面约定存在错误时，优先检查：

1. `SKILL.md` 的触发条件是否足够准确
2. `references` 中是否已存在对应主题
3. 主题文档中的规则是否和真实工程约定一致
4. 是否缺少一个足够小但正确的例子
