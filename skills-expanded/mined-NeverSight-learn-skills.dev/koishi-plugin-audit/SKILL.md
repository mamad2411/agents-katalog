# Koishi 插件领域审计

这个 skill 用于审计 Koishi 插件的 **机器人领域功能风险**：指令、中间件、`Session`、消息元素、数据库、控制台、适配器、权限和用户体验。

> 边界：
>
> - 插件形态、`Context`、`Service/inject`、生命周期、Schema、可逆性、热重载、通用测试与资源清理：使用 `cordis-v3-plugin-dev`。
> - package 元信息、Koishi 市场、`peerDependencies.koishi`、`koishi.service`、preview / hidden：使用 `koishi-plugin-publish-audit`。

## 审计目标

优先回答：

1. **机器人功能是否符合预期**：指令、消息、中间件、平台适配是否能正确工作。
2. **用户是否会被误伤或困惑**：权限、默认行为、帮助、错误提示是否清晰。
3. **Koishi 服务使用是否符合领域规则**：数据库、控制台、assets、server、adapter 等能力是否按 Koishi 方式使用。

结论建议：

- `可合并`
- `需修复后再合并`
- `可合并但存在可接受风险`

问题等级：

- `严重`：会导致主要机器人功能不可用、误拦截大量消息、权限绕过、数据错误、平台接入失败。
- `建议`：影响用户体验、兼容性或维护性，但不一定阻断。
- `备注`：需要确认的信息或非阻断提示。

## 1. 指令审计

检查：

- 指令名、别名、子指令是否清晰且不易冲突。
- 必选参数和可选参数顺序正确。
- `:text` 贪婪参数不会吞掉后续选项。
- `.option()` 的 fallback、权限、隐藏状态合理。
- `.usage()` / `.example()` 对普通用户有帮助。
- `authority` 是否符合功能风险。
- `action()` 中是否正确使用 `argv.session`。
- 指令失败时是否有可理解的用户提示。

常见严重风险：管理命令无权限限制、危险操作缺确认、文本参数导致选项失效。

## 2. 中间件与 Session 审计

检查：

- 普通中间件是否在未处理时 `return next()`。
- 异步中间件是否 `return next()` 或 `await next()`。
- 前置中间件是否过度拦截消息。
- 临时中间件是否用于兜底而不是污染全局处理链。
- `session.prompt()` 是否可能接管用户后续输入导致误判。
- `session.user` / `session.channel` 是否在合适位置观察和访问。
- 是否对群聊、私聊、平台、频道差异有判断。

常见严重风险：忘记 `next()` 导致所有后续指令失效；异步中间件时序错误导致重复回复或无回复。

## 3. 消息元素审计

检查：

- 是否优先使用标准消息元素或 JSX。
- 是否把用户输入安全地作为文本节点或属性值传入。
- 是否避免直接拼接用户输入到元素字符串。

严重风险：用户输入造成元素注入。

## 4. 数据库使用审计

数据库 API 细节使用 `koishi-database-query`。这里重点检查 Koishi 插件层风险：

- 是否声明 `database` 依赖。
- `ctx.model.extend()` 是否在首次读写前执行。
- 用户、频道、权限等内置表扩展是否类型声明同步。
- 写操作是否检查 `matched` / `inserted` 等结果。
- 正则、列表、聚合、join 是否考虑不同数据库后端兼容性。
- 用户输入是否直接变成危险查询或过宽查询。

严重风险：未声明数据库依赖、模型未扩展就读写、升级导致数据丢失或长时间阻塞启动。

## 5. 控制台扩展审计

检查：

- 是否声明或局部注入 `console` 服务。
- `ctx.console.addEntry({ dev, prod })` 路径是否正确。
- 前端页面 `path` 是否冲突。
- DataService key 是否前后端一致。
- 返回数据是否可 JSON 序列化。
- 页面是否声明需要的 `fields`。
- 数据变化后是否调用 refresh。
- 菜单、action、settings、slot、theme 的 id 是否一致。
- authority / disabled 是否导致页面注册了但不可见。

严重风险：生产构建产物漏发、DataService 返回不可序列化对象、未授权页面暴露敏感操作。

## 6. 权限与安全体验

检查：

- 管理命令是否设置 `authority`。
- 控制台页面和 listener 是否设置合适 authority。
- 危险操作是否二次确认。
- 是否避免把 token、secret 输出到日志或消息。
- 公网相关功能是否提醒启用 auth。
- 用户输入是否会造成消息元素注入、过宽数据库查询、路径穿越或 SSRF 风险。

## 7. 用户体验

检查：

- 指令帮助、错误提示是否清楚。
- 配置描述是否说明凭据来源。
- 平台限制是否提前说明。
- sandbox 能否验证基础流程。
- 日志能否帮助定位问题。
- 默认行为是否保守，不会刷屏、误删、误发或暴露控制台。
