# PRD Flow

Этот skill — самостоятельный пакет инструкций для Codex. Он помогает довести идею до утверждённого PRD: продуктового документа с постановкой задачи, который постепенно вводит непогружённого читателя в проблему, объясняет решение и даёт продуктовую постановку, готовую к архитектурной оценке.

Область skill узкая: единственный итоговый документ — PRD. Все выводы research, Devil's Advocate, AI-slop и chief-architect должны быть обсуждены с пользователем, превращены в правки PRD или отброшены. Рабочие заметки subagents можно хранить только внутри `.agent-work/`; нельзя создавать отдельные текстовые документы в корне проекта, `docs/`, `docs/prd/` или `docs/design/`.

Для ветки `last30days` память по умолчанию задаёт PRD Flow, а не пользователь. Директория памяти `last30days` равна памяти текущего проекта: `${PROJECT_ROOT}/.agent-work/last30days`. Если маршрут уже ведёт отдельный run, используй `${PROJECT_ROOT}/.agent-work/runs/<run-id>/last30days`. Всегда запускай `last30days` с `LAST30DAYS_MEMORY_DIR`, указывающим на эту проектную память; внешняя папка по умолчанию этого skill не используется.

Локальные снимки зависимостей лежат в `vendor/`. При маршрутизации сначала используй эти файлы, а оригинальные абсолютные пути воспринимай как запасной источник и ссылку на происхождение снимка.

В этом пакете `gate` означает контрольный этап с явным результатом, `review` — проверку документа выбранной ролью, а `scope` — границы работы, которые нельзя расширять без решения пользователя. Эти английские слова оставлены как служебные токены для статусов, шаблонов и внутренних рабочих записей PRD Flow.

## No Preflight

Не загружай, не используй и не упоминай PRD Flow для запросов, которые не начинаются с ведущего префикса PRD Flow.

PRD Flow не является preflight, классификатором, проверкой применимости, fallback или локальным project default. Если этот skill-файл открыт во время запроса без ведущего PRD Flow-префикса, сразу прекрати использовать его и продолжи вне PRD Flow, не объявляя, что PRD Flow был пропущен.

Проектные или локальные `AGENTS.md` не могут принудительно включать PRD Flow для запросов без ведущего префикса. Они могут задавать локальный контекст и команды, но PRD Flow всё равно требует видимый пользователю префикс в начале сообщения.

## Модель запуска

Публичный запуск skill возможен только в начале запроса:

- `prd-flow <задача>`;
- `$prd-flow <задача>`;
- `PRD Flow <задача>`;
- `прд-флоу <задача>`.

Текстовые формы без `$` регистронезависимы. Упоминание `prd-flow` позже в сообщении не запускает этот маршрут.

Ведущий префикс PRD Flow считается явным поручением пользователя использовать subagents для ролей этого маршрута, когда `spawn_agent` доступен. Оркестратор ведёт маршрут, ручные `gate`, обзор результата и финальный ответ; PRD-драфт, AI-slop проверки, Devil's Advocate review и chief-architect review делегируются отдельным subagents, если это возможно. Это делегация внутри PRD Flow Skill, а не подключение внешнего маршрута.

Если `spawn_agent` не виден, сначала проверь active tools, затем при наличии `tool_search` ищи `spawn_agent subagent multi-agent tools`. Если после этого subagent tool недоступен, верни `blocked-for-subagents` для этапов, где нужна делегация, пока пользователь явно не разрешит manual fallback.

Запросы про PRD без ведущего префикса PRD Flow не запускают этот skill автоматически. Не выполняй PRD Flow preflight для таких запросов: не читай этот `SKILL.md`, не проверяй применимость PRD Flow, не создавай рабочие записи PRD Flow и не ссылайся на PRD Flow в статусах.

## Subagents, модели и skills

Бандл ролей живёт в `agents/*.md`. Frontmatter каждого файла — источник настроек роли:

- `model` и `reasoning_effort` — обычные runtime-настройки;
- `escalation_model`, `escalation_reasoning_effort` и `escalation_triggers` — усиление для сложных PRD-задач;
- `skills` — зависимости роли, а не команда установки;
- `tools` — ожидаемый набор инструментов в delegation packet.

Перед каждым `spawn_agent` оркестратор должен получить конфиг роли:

```bash
python3 scripts/resolve-agent-config.py --role <role> --trigger <trigger>
```

Передавай `model` и `reasoning_effort` из JSON в `spawn_agent`. `service_tier` передавай только если значение не `null`. Если триггер не нужен, запускай resolver без `--trigger`.

После установки PRD Flow запусти dependency wizard:

```bash
python3 scripts/check-agent-deps.py --post-install
```

Wizard показывает missing `core` и `full` skills. Он ничего не ставит молча: локальные bundled skills копируются только после явного `yes`, manual/plugin/prompt entries печатаются как инструкции.

## Когда использовать

Используй skill только когда запрос начинается с ведущего префикса PRD Flow и нужно:

- создать первый PRD по новой продуктовой идее;
- привести сырую постановку к понятному документу для команды;
- проверить, поймёт ли непогружённый человек, что это за продукт, какую проблему он решает и как работает;
- пройти ручные контрольные этапы с пользователем, проверку Devil's Advocate, AI-slop очистку — удаление машинно звучащего текста без полезного смысла — и финальное решение архитектора.

## Границы

Разрешено:

- задавать продуктовые вопросы через `brainstorming`;
- создавать и править итоговый PRD;
- использовать `humanizer-ru` и `ai-slops-hunter` для качества русского текста;
- заменять англицизмы точными русскими терминами, если английская форма не нужна для точности;
- делегировать role-owned этапы через доступные subagents;
- по явному выбору пользователя проводить market research: поиск похожих решений, конкурентов, рыночных практик, свежих сигналов последних 30 дней через `last30days` и источников для PRD-выводов;
- делегировать проверку роли Devil's Advocate PM через доступного product/reviewer subagent, если отдельного агента нет;
- запрашивать ручное подтверждение пользователя на указанных этапах;
- хранить рабочие заметки research/review только внутри `.agent-work/`;
- завершать работу ссылкой только на итоговый PRD.

Запрещено:

- создавать план реализации (`implementation plan`), список задач разработки (`backlog`), дорожную карту (`roadmap`) или технический дизайн (`technical design`);
- автоматически переходить к `writing-plans` после подтверждения PRD;
- писать product code, runtime scripts, тесты, миграции, CI/CD или deploy-инструкции;
- добавлять дизайн/Figma/Pencil/UI flow;
- расширять границы до архитектуры реализации, кроме финального решения о готовности PRD;
- создавать словарь терминов в PRD;
- добавлять в PRD раздел `Открытые вопросы`;
- добавлять в PRD разделы `Критерии готовности PRD` и `История проверок`;
- создавать отдельные user-facing research/review/AI-slop/chief-architect документы в корне проекта или `docs/`;
- ссылаться в финальном ответе на внутренние research/review/AI-slop/chief-architect рабочие записи;
- отдавать PRD пользователю как `готовый к ревью`, если остаются открытые продуктовые вопросы или развилки, которые могут изменить конечный документ;
- утверждать факты, которых нет в исходном контексте или ответах пользователя.

## Протокол уточнений Q-A

Если после анализа контекста у оркестратора возникает вопрос, без ответа на который нельзя надёжно сформировать конечный PRD, он переключается в Q/A mode и задаёт этот вопрос пользователю до написания или ревью PRD.

PRD нельзя отдавать пользователю как `готовый к ревью`, пока остаются открытые продуктовые вопросы. Открытый вопрос — это развилка про проблему, аудиторию, scope, первый сценарий, критерии успеха, ownership, ограничения, риски или другое решение, которое может изменить текст PRD. Такие вопросы не переносятся в PRD разделом `Открытые вопросы`: они закрываются через Q/A до формирования документа.

Если вопросов больше одного, оркестратор не выдаёт весь список сразу. Вместо этого он ведёт последовательное уточнение.

Правила:

- задавай пользователю только один вопрос за раз;
- начинай с вопроса, который сильнее всего влияет на продуктовую постановку, `scope` или дальнейший маршрут PRD;
- к вопросу давай 2-3 разумных варианта ответа, основанных на контексте проекта и best practices;
- после нескольких ответов пользователя определи вероятную нишу или домен продукта из контекста и задай отдельный вопрос на подтверждение;
- вопрос о нише не должен быть пустым: предложи 2-4 вероятных варианта, коротко объясни, по каким признакам они выбраны, и добавь вариант «нет, другая ниша»;
- если есть предпочтительный вариант, помечай его как рекомендуемый и коротко объясняй tradeoff;
- после ответа пользователя заново оценивай ситуацию, а не переходи механически к заранее подготовленному следующему вопросу;
- один ответ пользователя может снять часть вопросов, изменить порядок следующих вопросов, выявить новый более важный вопрос или позволить сразу перейти к следующему этапу workflow;
- не спрашивай то, что можно надёжно вывести из уже данного контекста;
- не используй Q-A для необязательных предпочтений, polish-вопросов или вопросов, которые можно безопасно закрыть явным предположением.

Цель Q-A — закрыть продуктовые развилки до создания PRD и получить минимальное число пользовательских решений, нужных для качественного документа, не перегружая пользователя длинным списком уточнений.

Q-A применяется оркестратором во всех user-facing уточнениях PRD Flow: первоначальный intake, спорные выводы Devil's Advocate, правки после `review` и возврат после `reject` или `blocked` от архитектора.

## Обязательный маршрут

1. Запусти `brainstorming` из `vendor/skills/brainstorming/SKILL.md`; если локального снимка нет, используй fallback `/Users/ucnlejumper/.agents/skills/brainstorming/SKILL.md`. Используй его только для первоначальных продуктовых вопросов и согласования постановки. До создания PRD закрой все продуктовые развилки, которые могут повлиять на конечный документ. После первых ответов пользователя выведи вероятную нишу или домен продукта и задай вопрос на подтверждение с несколькими вариантами, включая «нет, другая ниша». Если вопросов больше одного, оркестратор задаёт их через протокол Q-A: по одному, с 2-3 вариантами ответа и переоценкой после каждого ответа. Не переходи к `writing-plans`.
2. После первичной постановки спроси пользователя, нужен ли market research перед PRD. Дай варианты: короткий market scan, срез обсуждений за последние 30 дней через `last30days`, глубокий competitor research или пропуск исследования. Если пользователь выбирает исследование, передай задачу `market-researcher`; его рабочие заметки можно сохранять только в `.agent-work/`. Если используется `last30days`, используй проектную директорию памяти PRD Flow по умолчанию: `${PROJECT_ROOT}/.agent-work/last30days` или `${PROJECT_ROOT}/.agent-work/runs/<run-id>/last30days` для отдельного run. Это не пользовательский вопрос и не отдельная настройка маршрута. Отчёт `last30days` не показывай как отдельный user-facing документ. Выводы research сначала обсуди с пользователем, чтобы закрыть неясности. В PRD могут попасть только source-backed findings или явно помеченные допущения. Если исследование создаёт продуктовую развилку, вернись в Q/A mode до PRD draft.
3. Создай первую версию PRD по `templates/prd.md` только после того, как блокирующие продуктовые вопросы закрыты. Documenter обязан писать современным русским языком: убрать англицизмы, использовать точные русские термины, а английский оставлять только при необходимости с русским пояснением. Не добавляй в PRD разделы `Открытые вопросы`, `Критерии готовности PRD` и `История проверок`: готовность и проверки живут в маршруте и внутренних `.agent-work/` заметках, а не в финальном тексте PRD.
4. Проведи первый контрольный этап: `humanizer-ru` из `vendor/skills/humanizer-ru/SKILL.md` плюс `ai-slops-hunter` из `vendor/agents/ai-slops-hunter.md`; если локальных снимков нет, используй fallback `/Users/ucnlejumper/.claude/skills/humanizer-ru/SKILL.md` и `/Users/ucnlejumper/.codex/agents/ai-slops-hunter.md`. Правки в PRD вносятся автоматически, если они не меняют смысл.
5. Передай PRD на проверку Devil's Advocate в роли Senior Product Manager. Проверяющий не добавляет нишевые допущения, если ниша не подтверждена пользователем. Он ищет дубликаты, двусмысленности, непонятные места, противоречия, неподтверждённые факты, слабые формулировки, размытость, тавтологию, перефразирование одной мысли в разных пунктах, слабые переходы между разделами и всё, что раздувает объём или усложняет понимание документа человеком. Результат review сохраняется только как внутренняя рабочая запись в `.agent-work/` и передаётся оркестратору.
6. Оркестратор разбирает вывод Devil's Advocate. Если есть продуктовые развилки или вопросы, которые требуют точной информации от пользователя, передай их `product-manager`: он формулирует минимальный набор Q/A-вопросов, а оркестратор задаёт их пользователю по одному. Если продуктовых развилок нет, `product-manager` превращает рекомендации reviewer в change set для PRD без новых фактов.
7. Передай change set `documenter`. Documenter вносит изменения в PRD, убирает дубликаты, проясняет непонятные места и сохраняет структуру документа. После правок можно запустить только один повторный Devil's Advocate review. Лимит этого gate — два review-прохода всего: первый review из шага 5 и один повторный review после triage/change set/documenter edit. Если первый review вернул `pass` без actionable objections, переходи дальше без повторного прохода. Если второй review всё ещё возвращает `pass-with-risks`, `fail` или `blocked`, немедленно останови автоматический цикл: не запускай documenter, AI-slop или третий review. Вернись к пользователю в Q/A mode с минимальным набором явных вопросов по спорным развилкам. Каждый вопрос должен показывать 2-3 направления решения и кратко объяснять, как выбор изменит PRD. После ответа пользователя можно внести выбранные правки и начать новый ограниченный Devil's Advocate gate, снова максимум на два review-прохода.
8. Проведи второй `ai-slops-hunter` через `vendor/agents/ai-slops-hunter.md`; если локального снимка нет, используй fallback `/Users/ucnlejumper/.codex/agents/ai-slops-hunter.md`.
9. Перед full-read gate проверь, что в PRD и в маршруте нет открытых продуктовых вопросов, которые могут изменить документ. Если такие вопросы есть, вернись в Q/A mode и закрой их до передачи PRD на чтение. Затем попроси пользователя прочитать весь PRD и явно подтвердить готовность или дать комментарии.
10. После подтверждения пользователя передай PRD в `chief-architect` из `vendor/skills/chief-architect/SKILL.md`; если локального снимка нет, используй fallback `/Users/ucnlejumper/.claude/skills/chief-architect/SKILL.md`.
11. Архитектор даёт комментарии и решение: готова ли постановка к передаче в разработку.
12. Если архитектор дал `approve` или `approve-with-risks`, проведи финальный `ai-slops-hunter` через `vendor/agents/ai-slops-hunter.md`; если локального снимка нет, используй fallback `/Users/ucnlejumper/.codex/agents/ai-slops-hunter.md`. При `approve-with-risks` обсуди риски с пользователем и внеси принятые формулировки в PRD. Если архитектор дал `reject` или `blocked`, вернись к пользователю и исправлению PRD.
13. Заверши работу ссылкой только на итоговый PRD. Не прикладывай и не линкуй внутренние рабочие записи research/review/AI-slop/chief-architect. На этом skill останавливается.

Подробности этапов: `references/prd-workflow.md`.

## Критерий завершения

Работа завершена только когда:

- PRD существует и включает продуктовую постановку/описание;
- документ ведёт читателя от проблемы к работе решения без скачков и не требует внешнего контекста;
- документ компактный и ёмкий: покрывает все части продуктовой фичи или изменения, но не повторяет одну мысль разными словами;
- все продуктовые развилки, влияющие на конечный текст, закрыты до передачи PRD на ревью;
- ниша или домен продукта подтверждены пользователем через Q/A-вопрос с вариантами, построенными по исходному контексту;
- если пользователь выбрал market research, включая ветку `last30days`, выводы исследователя обсуждены с пользователем, учтены как source-backed findings, отклонены или оставлены во внутренних `.agent-work/` заметках как слабые доказательства;
- русские термины раскрыты по ходу текста, без отдельного словаря;
- лишние англицизмы, кальки, клише и тавтология убраны; нужные английские термины даны с русским термином и пояснением при первом употреблении;
- сложные места объяснены в стиле ELI18;
- пройдены контрольные этапы humanizer/AI-slop, ограниченный Devil's Advocate gate с максимум двумя review-проходами до `pass` без actionable objections, ручные подтверждения пользователя и финальное решение chief-architect;
- после `approve` или `approve-with-risks` архитектора выполнена финальная AI-slop проверка;
- при `approve-with-risks` принятые пользователем риски внесены в PRD;
- финальный ответ содержит ссылку только на PRD;
- в корне проекта и `docs/` нет отдельных research/review/AI-slop/chief-architect документов.
