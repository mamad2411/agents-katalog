# Adaptive Development Workflow：自适应开发工作流

<SUBAGENT-STOP>
如果你是为边界明确的工作单元派发的子代理，跳过本技能的任务级路由，按派发边界和指定主要方法执行。
</SUBAGENT-STOP>

## 入口职责

根代理开始任何项目开发或技术调查任务时，先使用本技能判断任务类型、当前增量和最低充分流程，再决定是否调用其他开发技能。不要先调用下游技能，再为了满足其局部流程反向升级整个任务。

下游技能负责具体工作单元，不能单独把微小或常规任务提升为完整计划、委派、测试或评审流程。新证据改变真实影响面时，返回本技能重新分级和路由。

## 核心原则

先确定当前请求要产生的实际增量，用能保证正确性的最低充分级别决定计划、确认、委派、验证、评审与交付节点是必需、条件触发还是跳过；再把需求拆成可验证的工作单元，根据每个单元的不确定性、风险、真实调用方、结果性质和证据来源选择主要方法。

能写出失败测试，只说明某种输入输出可以断言，并不说明 TDD 优于直接实现、行为基线、快照、评估或独立审查。一个需求可以组合多种方法，不必让所有单元走同一套流程。开发任务也不等于完整流程：微小任务直接完成，常规任务按收益选择节点，复杂或高风险任务才强制落盘计划和最终独立评审。

如果为项目改动创建或检出开发分支，用户又没有指定位置，就通过 [using-git-worktrees](../using-git-worktrees/SKILL.md) 使用独立工作树。临时的纯只读分支审查，只要能安全保持或恢复干净的默认基线，可由执行者选择根路径或工作树。

## 判断任务类型

判断标准是最终是否保留项目产物。需要项目保留、集成、提交或交付代码、配置、依赖与锁文件、构建或 CI 脚本、准备保留的测试、数据模型、迁移、生成规则、技能、插件、工作流或版本控制文档，就是开发任务。

以下任务本身不是开发任务：

- 纯解释、咨询、翻译或回答问题；
- 只读调查、只运行检查、只报告评审意见，或只交付已经完成开发的提交、推送、PR/MR 或部署；
- 以结论和证据为交付结果的调查或技术探索，即使过程中产生可丢弃的示例、脚本、原型、测试或诊断插桩。

是否写过代码、改过文件或执行过写操作都不是判据。临时产物必须隔离，不得混入最终差异；调查结束时检查工作区。外部写入、破坏性操作、正式环境和权限扩大仍受授权与安全边界约束。

决定保留调查产物时，停止扩展临时代码，转为开发任务，按准备保留的实际增量重新定级并明确保留、重写和删除范围。一开始就要求“调查并实现”的请求，本身就是开发任务。

## 按当前增量分级

先写清当前请求的目标、准备新增或改变的状态，以及最小完成证据。后续请求发生在复杂功能分支或大型 PR/MR 上，不自动继承父任务的级别；只处理一处机械文档冲突仍可以是微小任务。文件数和行数只是信号，运行行为、公共契约、影响范围、不确定性、可逆性、外部副作用和证据成本更重要。

| 任务级别 | 可观察条件 | 默认流程 |
|---|---|---|
| 微小 | 目标明确，修改局部可逆，不改变运行行为或公共契约，不涉及依赖、生成规则、权限或产物自身的外部副作用，并能直接检查结果 | 直接实现、审阅差异、运行必要的直接检查并简要总结；不落盘计划，不派独立评审 |
| 常规 | 有边界明确的行为或配置变化，或者需要若干相关步骤，但没有高风险或重大不确定性 | 按协调成本决定是否落盘计划，使用定向验证；只在独立视角能补充真实风险证据时评审 |
| 复杂或高风险 | 跨模块或公共契约、架构与依赖迁移、安全、身份、资金、数据、并发、破坏性或难回退操作、正式环境、显著未知，或者多代理需要共享状态 | 通过 [writing-plans](../writing-plans/SKILL.md) 落盘计划，按风险验证，并通过 [requesting-code-review](../requesting-code-review/SKILL.md) 完成独立评审 |

从最低充分级别开始。发现真实影响面后立即升降级，不因为已经写了计划、运行了测试或派了代理就维持过重流程；也不能用“改动小”掩盖高风险语义。无法确认微小条件时使用常规级，出现任一复杂或高风险条件时升级。

用户明确要求直接修改、提交或推送，或者没有要求 PR/MR，是判断预期交付强度的重要信号；它不单独决定风险级别，也不授权未明确要求的提交、推送、PR/MR、合并、部署或业务外部写入。已明确授权的普通 Git 交付动作单独核对权限和执行结果，不因修改远端引用而提升内容任务级别；产物自身或其他系统的外部副作用仍按真实风险定级。

## 决定流程节点

对每个准备执行的计划、确认、委派、测试、评审或交付节点，先回答：它会发现当前增量引入的哪一种合理错误，现有证据是否已经覆盖？无法给出具体答案，或者新增证据只重复已有结论时跳过。不要调用下游技能只为证明该技能没有必要。

已有测试、评审、观测和 CI 在适用输入、环境、版本、调用路径与风险面没有被当前变化影响时继续有效。新事实只使对应结论失效，重新验证或复审受影响范围，不因任意新提交从头重复完整流程。CI 运行在最终推送提交或合并结果上时，是分支集成的一等证据；本地检查只有覆盖 CI 缺口或更快发现当前风险时才补充运行。

处理分支同步或冲突时，先检查实际冲突文件、双方语义和目标分支新增内容。机械文档冲突通常只需审阅解决差异、确认没有冲突标记并查看新提交的 CI；只有运行代码、契约或相关依赖发生真实交互时，才升级并补充对应测试或评审。

## 确定事实

证据冲突时按以下顺序判断：

1. 明确需求与不变量；
2. 真实生产调用方与运行行为；
3. 依赖、协议与框架契约；
4. 实现与测试；
5. 计划、检查清单与方法偏好。

测试是证据，不是最高权威；计划是可修正的工作假设，不能覆盖当前系统事实。测试判据必须来自更高优先级的需求、真实调用方或契约，不能因为目标模糊就由测试自行发明业务行为。

## 控制任务范围

先识别原任务的直接工作与既有伴生产物。任务开始前已经存在、并直接描述、演示或指导本次所改功能的维护文档、示例或说明，是该功能的伴生产物；本次变更会使其失真时，最小同步属于原任务的收尾工作，即使需求没有逐项列出，也不按计划外发现或阻塞前置条件处理。只同步本次变更直接影响的内容；新建资料、扩写非必要内容或修复本次变更未触及的历史问题不自动纳入。

伴生产物属于原任务不等于自动取得修改授权。最小同步仍在现有写入授权内、不涉及业务取舍、高风险或难以回退的操作、正式环境、外部写入、权限扩大或新增副作用时直接处理；否则请求确认并只暂停该同步路径，但不把伴生产物降级成任务外发现。

排除上述直接工作后，执行中发现额外缺陷、风险或改进机会时，再判断：保持该问题不变，是否仍能正确实现、验证和交付当前任务？

- 如果能，该问题就不属于当前任务。只收集足以确认任务边界的最小证据，不修改相关实现、测试、配置或文档，也不把它加入当前计划或差异。证据可信且值得跟进时简要报告；扩大调查、建立外部问题单或实施修复都需要另行授权。
- 如果不能，该问题就是当前任务的必要前置条件或当前改动引入的回归。说明阻塞证据、最小处理方案和默认动作，向用户发出非阻塞询问，同时继续不依赖它的工作；用户未及时回复时，在适用计划中加入最小必要处理并继续。

只有实现路径受需求、真实调用方或契约约束，保持原目标和交付结果，可逆且仍在当前项目写入授权内，并且不涉及业务取舍、高风险或难以回退的操作、正式环境、非普通 Git 交付的外部写入、权限扩大或新增重大副作用时，才能默认纳入。否则等待明确确认，但只暂停受影响路径。任务级别要求落盘计划时，具体边界按 [writing-plans](../writing-plans/SKILL.md) 处理。

伴生产物是否纳入，由它与本次功能的直接维护关系以及本次变更是否使其失真决定；目录位置、运行时影响和评审严重性都不能单独决定范围，用户明确的路径边界仍然优先。其他问题即使技术上相关、位于同一模块或调用链、修复成本低、问题严重，或者恰好被测试和评审发现，也不自动扩大任务范围。严重性只影响报告时机和醒目程度。计划、测试、评审意见和已经投入的工作也不能替代用户授权。

## 重构前行为证据

行为保持型重构在修改实现前，必须有办法发现核心业务行为的意外漂移。证据不必全是自动化测试，也不追求测试数量或极致覆盖率。可以用少量测试约束确定性的核心逻辑，再用冒烟步骤观察真实装配或调用链。

先运行并复用覆盖受影响行为的已有测试。存在必要缺口时，再通过 [evidence-based-testing](../evidence-based-testing/SKILL.md) 补充最小核心测试；已有测试足够就不追加无关覆盖。这项要求适用于涉及业务逻辑、状态变化、公共契约或框架边界的行为保持型重构。

难以自动化测试时，使用可重复的冒烟步骤观察输入、输出、状态和副作用，并记录相同条件下重构前后的结果。如果测试和可比较观测都无法约束核心行为，就缩小工作单元、先建立验证接缝或暂停重构。构建、类型检查和代码审查不能单独证明行为保持。纯注释、格式化等不影响运行行为的机械改动不受此要求约束。

## 选择主要方法

当结果、调用方、证据来源、风险或改动类型不同时拆分工作单元。每个单元选择一个主要方法，辅助技能只补充必要证据。

| 可观察条件 | 主要方法 |
|---|---|
| 第三方 API、SDK、框架、协议或 CLI 边界不确定 | [contract-verification](../contract-verification/SKILL.md) |
| 需要在测试、快照、评估或观测之间选择证据，或处理测试与实现冲突 | [evidence-based-testing](../evidence-based-testing/SKILL.md) |
| 行为保持型重构缺少覆盖核心行为的测试或可比较观测 | [evidence-based-testing](../evidence-based-testing/SKILL.md)，先建立最小行为基线 |
| 明确的确定性行为变更具有来自需求、真实调用方或契约而非普通字面量镜像的稳定判据、真实接缝与具体回归风险 | [test-driven-development](../test-driven-development/SKILL.md) |
| 整体或局部真实输出可稳定复现，逐项断言成本高且需要发现非预期漂移 | [evidence-based-testing](../evidence-based-testing/SKILL.md)，使用行为基线或快照回归 |
| 结果主要是已指定的提示词、文案、静态常量或声明式内容，且不改变确定性生成逻辑 | 直接实现并按影响验证，不复制目标字面量制造测试 |
| 结果具有主观性、概率性或多种合理实现，但已有样例或评价标准 | [evidence-based-testing](../evidence-based-testing/SKILL.md)，按需组合独立评估、实验或冒烟 |
| 需求、调用方式和契约已明确，且无需专项调查、技术探索或依赖变更 | 直接实现，并按影响选择验证 |
| 删除适配器、依赖、导出项或无效路径 | [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md) |
| 根因未知或行为间歇出现 | [systematic-debugging](../systematic-debugging/SKILL.md) |
| 技术可行性未知 | [technical-spike](../technical-spike/SKILL.md) |
| 依赖或工具链版本变化 | [dependency-upgrade](../dependency-upgrade/SKILL.md) |

可测试不等于适合 TDD。TDD 和直接实现都说得通时，默认直接实现。只有判据有独立来源、失败测试能识别合理的错误实现，而且存在具体回归风险时，才选择 TDD。精确文本本身属于协议、安全、合规或其他外部契约时，可以按契约风险测试，但普通内容修改不适用。

## 执行生命周期

1. 按最终交付意图判断任务类型，明确当前增量并选择最低充分级别。
2. 决定各流程节点是必需、条件触发还是跳过，澄清会改变方案的关键歧义。
3. 拆分工作单元，为每个单元选择主要方法；需要落盘计划时再使用 [writing-plans](../writing-plans/SKILL.md)。
4. 按依赖顺序调查和实现；只在上下文收益或独立证据收益高于交接成本时委派。
5. 复用仍有效的证据，验证当前增量及受影响组合链路；新事实改变影响面时重新定级、选法并按需更新计划。
6. 任务级别或具体风险要求时，由未参与实现、证据设计或相关差异修改的独立子代理评审受影响的最终完整差异；实质修复后只重新验证和复审失效范围。
7. 按授权完成提交、推送、PR/MR、集成与交接，按任务级别说明结果、证据、未完成事项和剩余风险。

非开发任务不强制计划或独立评审。复杂功能调研只有在独立检查确实有助于覆盖目标或提高结论准确性时，才使用评审代理。微小开发任务同样不为形式增加计划、子代理或评审；其他节点按实际收益选择。

## 安全边界

- 调查和验证期间不得写正式环境数据源；只读证据不授权数据修复。
- 修改状态前确认可逆性、工作树和并发状态、外部写入权限以及支撑最终声明的验证。
- 保留用户的无关改动，不把当前范围静默扩大到额外设计、发布或清理。
