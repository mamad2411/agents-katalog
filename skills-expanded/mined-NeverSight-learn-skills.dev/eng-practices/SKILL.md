# eng-practices Skill

## 目标

将 Google eng-practices（代码评审主线）转化为可执行的审查助手，用于：

- 快速形成高质量 reviewer 意见，减少“主观偏好式”争论。
- 指导作者写出更易审、可追溯的 CL 描述与更小粒度的 CL。
- 在速度与质量之间做平衡，避免评审流程成为瓶颈。
- 在争议场景下给出可落地的协作与升级路径。

## 来源与许可

- 官方文档：https://google.github.io/eng-practices/
- 参考索引：`reference-code-review.md`
- 许可：CC-BY 3.0（https://google.github.io/eng-practices/LICENSE）

使用本技能时以“归纳和执行建议”为主，不进行大段逐字转载。

## 术语

- `CL`：changelist，可对应多数团队的变更集/PR/patch。
- `LGTM`：Looks Good To Me，表示认可可合入。

## 何时触发

满足任一条件可启用本技能：

- 用户请求“帮我 review 这段代码/这个 PR”。
- 用户询问“评论怎么写更专业/更有说服力”。
- 用户遇到“review 卡住、反复拉扯、争议升级”。
- 用户需要“写 CL/PR 描述、拆小变更、加速评审周转”。
- 用户提到“紧急修复需要快速审查”并需要边界判断。

## 总体执行规则

1. 先判定变更是否提升整体 code health，再讨论细节打磨。
2. 技术事实和数据优先于个人偏好；风格争议以团队/语言规范为准。
3. 评论优先作用于代码，不作用于人；礼貌、清晰、可执行。
4. 除紧急场景外，不接受“先合后补”的复杂度透支。
5. 无法达成一致时，先同步上下文求共识，再走升级路径。

## Reviewer 速查清单

### 1) 评审标准（先判断是否可批准）

- 只要 CL 明确提升代码健康，且不存在阻断性风险，可倾向批准。
- 不以“完美”为门槛；对非阻断建议可标记 `Nit` 或 `Optional`。

### 2) 审查内容（按优先级）

- 设计是否合理、是否符合系统边界。
- 功能是否满足意图，是否覆盖关键用户路径与边界条件。
- 复杂度是否可控，是否存在过度工程。
- 测试是否与行为改动配套，是否真正能失败。
- 命名、注释、风格、文档是否可读且一致。

### 3) 审查顺序（三步法）

- 先看 CL 描述与总体意图。
- 先审主干文件（核心逻辑），尽早指出方向性问题。
- 再覆盖剩余文件并确保不漏关键部分。

### 4) 评论写法

- 用“代码影响 + 原因 + 建议”结构表达。
- 需要时标记严重级别：`Nit` / `Optional` / `FYI`。
- 鼓励好的实践，不只指出问题。

### 5) 速度与节奏

- 非深度专注时，尽量在一个工作日内给出响应。
- 跨时区或仅剩小问题时，考虑 `LGTM with comments`。
- 大 CL 优先要求拆分，减少评审阻塞。

## Author 速查清单

### 1) CL 描述

- 首行简洁、可独立理解，说明“改了什么”。
- 正文补齐“为什么这样改、权衡与背景”。
- 提交前回看描述是否仍准确反映最终改动。

### 2) Small CL 实践

- 一个 CL 只做一个自包含改动，并带相关测试。
- 可采用堆叠 CL、横向分文件、纵向分子功能来拆分。
- 重构与功能变更尽量分离，降低审查认知负担。

### 3) 回应评论

- 不个人化，先理解问题，再协作讨论取舍。
- 优先改代码/注释让未来读者受益，不只在评审工具里解释。
- 分歧无法收敛时，按冲突流程升级。

## 紧急变更边界

- 仅在真实紧急情况（重大线上影响、严重安全/法律风险等）走快速通道。
- “想早点发版”“周五下班前合入”等通常不构成紧急场景。
- 紧急变更合入后应补做更完整审查与清理。

## 冲突处理流程

1. 双方基于技术事实与本文档原则先达成共识。
2. 必要时改为同步沟通（当面/视频）并在 CL 留结论记录。
3. 仍无法解决时，按团队路径升级（TL/维护者/经理等）。

## 使用模板（可直接套用）

### Reviewer 评论模板

```text
结论：这条建议是 [Required/Nit/Optional]。
观察：当前实现在 [设计/功能/复杂度/测试/可读性] 上存在 [具体问题]。
原因：这会导致 [风险/维护成本/用户影响]。
建议：建议改为 [具体做法]，可保持 [收益]。
```

### Author 回复模板

```text
感谢建议，我理解你的关注点是 [要点]。
我当前选择 [方案A] 的原因是 [上下文与权衡]。
若按 [方案B] 调整，我计划这样落地：[具体修改]。
请确认我对你的意图理解是否准确。
```

## 与团队规范的优先级

当项目已有强制规范（如代码风格、评审门禁、发布流程）时，优先遵循项目规范；本技能作为通用审查原则与补充框架。
