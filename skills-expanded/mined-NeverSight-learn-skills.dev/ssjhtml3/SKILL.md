# SSJHTML3 — Relationship-first Report Deck

1280×720 단일 HTML 파일로 발표·검토·편집·PDF 인쇄가 가능한 슬라이드 덱을 제작한다. 색상과 카드 모양보다 먼저 `메시지 → 근거 → 관계 → 의사결정`을 설계한다.

## 필수 자원

- 기본 키노트 구조: `assets/reference_deck.html`
- 관계형 중간보고 구조: `assets/reference_report_deck.html`
- 팔레트: `assets/palettes.css`
- 도식 선택·구성 규칙: `references/diagram-grammar.md`
- 보고서 스토리라인: `references/report-blueprints.md`
- 최종 품질 판정: `references/qa-rubric.md`
- HTML 구조·글자·패널 감사: `scripts/audit_deck.py`
- PNG 빈 띠 검사: `scripts/check_fill.py`

보고서·제안서·성과보고를 만들 때는 `diagram-grammar.md`와 해당 보고 유형의 `report-blueprints.md`를 반드시 읽는다. 최종 검토 때는 `qa-rubric.md`를 읽는다.

## 1. 산출물 유형과 톤 확정

1. 산출물을 `강의안 / 착수보고 / 중간보고 / 최종보고 / 경영진 보고 / 제안·의사결정 보고` 중 하나로 분류한다.
2. 사용자가 톤을 지정하지 않은 신규 덱이면 색 톤을 질문한다. 기존 덱 수정이면 현재 톤을 유지한다.
3. 기본값은 쿨그레이 종이 + 네이비 + 코랄레드 + 골드의 관공서 보고 톤이다.
4. PPTX가 필요해도 HTML 정본을 먼저 완성하고, PPT는 동일 화면 또는 별도 PPT 스킬로 변환한다.

## 2. 장표를 쓰기 전에 Exhibit 명세 작성

각 본문 장표마다 아래 5개 필드를 먼저 한 줄씩 작성한다. 이 명세 없이 HTML을 시작하지 않는다.

```text
MESSAGE: 이 장에서 판단할 한 문장
EVIDENCE: 날짜·수치·사례·산출물 4~8개
RELATION: 비교 / 흐름 / 인과 / 계층 / 네트워크 / 시간 / 성숙도 중 하나
LAYOUT: diagram-grammar.md에서 선택한 패턴명
DECISION: 다음 판단·행동 또는 결론 사실
```

- `RELATION`이 있는데 카드나 표만 나열하지 않는다.
- 단순 목록은 실제로 관계가 없을 때만 사용한다.
- 콘텐츠 슬라이드에 `data-layout="hub-spoke|evidence-matrix|timeline|before-after|..."`와 `data-purpose="..."`를 표시한다.

## 3. 관계에 맞는 도식 선택

| 내용 관계 | 기본 도식 | 필수 구조 |
|---|---|---|
| 도구·조직·생태계 | 허브-스포크 | 중앙 명제 1개 + 주변 4~6군 + 연결선 |
| 문제에서 결과까지 | 문제-원인-해결-산출물 | 좌→우 흐름 + 단계별 근거 |
| 기관·사례 반복 비교 | 증거 매트릭스 | 행=사례, 열=현상·규모·대응·결과 |
| 상·하반기 또는 현행·개선 | Before/After | 동일 평가항목으로 대응 비교 |
| 일정·진행 경과 | 타임라인 | 시점 + 상태 + 산출물 + 다음 관문 |
| 대안 선택 | 대안 비교 + 결정 | 기준별 장점·한계·전제·권고 |
| 역량·교육·성과 연결 | 3열 와이어 맵 | 좌·중·우 노드 + 실제 연결선 |
| 현재 수준과 목표 | 성숙도 사다리 | 완료·진행·목표 단계 + 판정 기준 |
| 협의 요청 | 요청-행동-성과 | 승인 항목 + 승인 후 행동 + 목표 시점 |

세부 규칙과 HTML/CSS 골격은 `references/diagram-grammar.md`를 따른다.

## 4. 시각 위계 규칙

모든 본문 장표에 다음 4단계를 만든다.

1. **판단 제목**: 32px, 한 장의 결론을 사실 서술 또는 명사구로 표현한다.
2. **시각 중심축**: 허브, 비교 기준, 시간축, 단계 흐름 중 하나를 화면 중앙 또는 상단에 둔다.
3. **근거 단위**: 4~8개 사실을 그룹화한다. 그룹마다 역할이 달라야 한다.
4. **앵커 바**: 하단에 결론 사실·요청·다음 행동을 1개만 둔다.

- 색은 관계와 상태를 표현한다. 단순 장식 목적으로 여러 색을 쓰지 않는다.
- 연결선은 실제 의미가 있을 때만 사용하고, 시작·도착 노드가 명확해야 한다.
- 모든 요소를 같은 크기·같은 강조로 만들지 않는다.

## 5. 박스와 정보밀도 — 강제 기준

- 박스는 정보를 담는 컨테이너이지 캔버스 채움용 장식이 아니다.
- 캔버스의 10%보다 큰 패널에는 제목 외 **사실 2개 이상** 또는 설명 1줄+항목 3개를 넣는다. 18%보다 큰 패널에는 **사실 3개 이상**, `현상·원인·대응`, 또는 관계선 2개 이상을 넣는다.
- 큰 패널의 텍스트가 2줄 이하이면 패널 높이를 줄이거나 행 리스트·도식으로 전환한다.
- 카드 내부 유효 정보 점유율 목표는 30~65%다. 20% 아래이면 높이를 줄이거나 행·열·설명을 추가한다. 배경색만 넓게 칠해 점유율을 높이지 않는다.
- 동일 크기 카드 4개 이상을 한 줄로 나열하지 않는다. 비교 기준이 있으면 표, 관계가 있으면 도식으로 바꾼다.
- 본문·표·카드 글자는 14~16px, 핵심 설명은 16~18px를 우선한다. 보조 정보도 12.5px 미만으로 내리지 않는다.
- 내용이 넘치면 글자를 줄이지 말고 페이지를 분리한다.
- 표지·명제형을 제외한 본문 콘텐츠 점유율은 70~88%를 목표로 한다.
- 한 장에 최소 2개 정보층을 둔다: `근거+해석`, `비교+권고`, `진행상태+다음 관문`, `문제+해결 경로`.

## 6. 캔버스·타이포·컬러

- 슬라이드: 1280×720, `@page{size:1280px 720px;margin:0}`.
- 기본 패딩: 좌우 48px, 상단 28px. 앵커 54px, 푸터 34px를 먼저 고정한다.
- 폰트: `Pretendard Variable`, Pretendard, `Noto Sans KR`, `Malgun Gothic`, sans-serif.
- 제목: 30~36px / 900. 표지: 60~72px / 900. 본문: 14~16px. 앵커: 16~17px.
- 기본 토큰은 `assets/palettes.css`에서 가져온다. 네이비 `#101827`, 잉크 `#102139`, 코랄 `#b94a48`, 그린 `#2e7d5b`, 골드 `#c38424`를 기본 시맨틱 색으로 사용한다.
- 어절 중간 줄바꿈을 막는다: `word-break:keep-all; overflow-wrap:break-word`.

## 7. 보고서형 스토리라인

- 표지의 주제목은 공식 사업명 + 보고유형으로 한다.
- 진행 경과는 날짜·담당·내용·산출물·상태가 판독되게 한다.
- 교육 내용은 도구 목록이 아니라 업무 문제와 산출물의 연결 관계로 표현한다.
- 현장자료는 `페인포인트·요구사항·업무 흐름·운영 시사점`으로 종합한다. 녹취록·전사·파일명·내부 메모·분석 건수는 사용자가 요구하지 않으면 노출하지 않는다.
- 비용·인력은 수행기관 수익성 호소가 아니라 성과 창출 시간, 전문가 동시 투입, 제작·검증 시간으로 설명한다.
- 마지막 장에는 승인 항목, 승인 후 행동, 담당 주체, 목표 시점을 넣는다.
- 문서 유형별 권장 페이지와 패턴은 `references/report-blueprints.md`를 따른다.

## 8. 문체

- 제목은 명사구 또는 사실 서술문으로 작성한다.
- 비유·은유·대구법·구어체 질문·감상 문장을 사용하지 않는다.
- 카드 헤더는 주체·대상·조건·기준·산출물·주기 같은 명사로 쓴다.
- 수치·고유명사·날짜·상태를 우선한다. 확인되지 않은 값은 추정하지 않는다.
- 앵커 바는 구호가 아니라 결론 사실 또는 요청사항으로 쓴다.

## 9. HTML 기능 유지

`assets/reference_deck.html`의 다음 기능을 유지한다.

- `?slide=N` 단일 슬라이드 렌더
- 브라우저 `✏ 편집`, `💾 저장 HTML`, `📄 PDF`, `▶ 발표`
- `P` 발표, 방향키 이동, `Esc` 종료
- 발표 모드 요소 순차 등장
- SVG 와이어·네트워크의 load/resize/slide-show 재계산

새 컴포넌트 클래스를 만들면 발표 애니메이션 선택자에 추가한다. 와이어는 DOM 좌표를 측정한 뒤 SVG를 그리며, 숨겨진 슬라이드에서는 측정하지 않는다.

## 10. 제작·검증 절차

1. 자료를 사실·수치·사례·요구·결정으로 분류한다.
2. 전체 스토리라인과 장표별 Exhibit 명세를 작성한다.
3. `diagram-grammar.md`에서 각 장표의 관계형 레이아웃을 선택한다.
4. 참조 덱의 구조와 팔레트를 복제해 HTML을 작성한다. 보고 목적에 맞는 구조용 CSS·SVG는 추가할 수 있다.
5. 각 장표를 1280×720 PNG로 렌더한다.
6. HTML 감사 실행:

   ```bash
   python scripts/audit_deck.py output.html
   ```

7. PNG 빈 띠 검사:

   ```bash
   python scripts/check_fill.py renders/*.png
   ```

8. `qa-rubric.md`로 메시지·근거·관계·위계·가독성을 채점한다. 85점 미만 또는 치명적 실패가 있으면 수정한다.
9. 최종 PNG를 눈으로 검사한다. 자동검사 PASS만으로 완료 처리하지 않는다.
10. HTML·PDF 페이지 수, 번호, 잘림, 링크, 발표 모드를 검증한다.

## 완료 조건

- 본문 모든 장표가 `MESSAGE/EVIDENCE/RELATION/LAYOUT/DECISION` 명세를 충족한다.
- 관계가 있는 내용을 단순 카드 나열로 처리한 장표가 없다.
- 큰 빈 패널, 12.5px 미만 보조본문, 14px 미만 주요본문이 없다.
- HTML 감사와 PNG 빈 띠 검사가 통과한다.
- QA 점수 85점 이상이며 메시지·근거·관계 항목이 각각 기준을 통과한다.
- 최종 렌더를 사람이 확인해 시각적 중심축과 정보 흐름을 한눈에 설명할 수 있다.
