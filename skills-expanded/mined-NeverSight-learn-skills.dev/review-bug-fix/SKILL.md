# Review Bug Fix Skill

## 目标

将 wk-code-review 代码审计报告转换为可执行、可追踪的缺陷修复任务列表，**并按计划自动执行代码修复**，全程跟踪修复状态。

## 核心原则

> **依赖 wk-code-review 的输出结果**
>
> 本 Skill 读取 wk-code-review 生成的审计报告（markdown 格式），解析其中问题后生成修复任务，然后按优先级自动执行修复。

> **修复计划是为了执行，不是为了归档**
>
> 生成的修复计划是 AI 执行修复的行动指南，每个问题必须包含足够上下文让 AI 能准确定位和修改代码。

## Phase 0：读取审计报告

### 0.1 确认报告路径

询问用户审计报告路径，或使用传入的路径：

```
请提供审计报告路径（或直接拖入报告文件）：
```

| 选项 | 说明 |
|---|---|
| 默认 | `{OUTPUT_DIR}/{branch-name}.md` |
| 自定义 | 用户输入绝对路径 |

### 0.2 读取报告内容

优先读取结构化 JSON 数据，再以 Markdown 报告作为补充：

**数据源优先级**：
1. `{报告所在目录}/{branch-name}-result-all.json`（结构化数据，问题不遗漏）
2. `{报告所在目录}/{branch-name}.md`（如果 json 文件不存在，读取报告）

**读取步骤**：
1. 检查同目录下是否存在 `{branch-name}-result-all.json`
2. 若存在：使用 Read 工具读取 JSON，从 `问题列表` 字段获取全部问题，从 `文件清单` 字段获取涉及文件
3. 若不存在：使用 Read 工具读取 `.md` 报告，解析各维度章节的问题表格
4. 读取 `.md` 报告的头部元信息（分支名、基准分支、审计时间、审计结论）和审计结论

> ⚠️ **强制要求**：解析后必须校验提取的问题数量与报告中"问题统计总览"的数量一致。若不一致，说明有遗漏，必须重新解析。

解析以下关键信息：

1. **元信息**：分支名、基准分支、审计时间、审计结论
2. **问题统计**：按严重程度（CRITICAL/WARNING/SUGGESTION）和维度分类
3. **问题详情**：每个问题的文件路径、行号、严重程度、维度、类型、描述、问题代码、修复建议

## Phase 1：解析报告问题

### 1.1 提取统计信息

解析报告头部的统计表：

```markdown
| 严重程度 | 数量 |
|---|---|
| 🔴 CRITICAL | {n} |
| 🟡 WARNING | {n} |
| 🟢 SUGGESTION | {n} |
```

### 1.2 提取问题列表

解析报告各维度章节的问题表格，提取每个问题的结构化信息：

```json
{
  "severity": "CRITICAL|WARNING|SUGGESTION",
  "file": "文件路径",
  "line": "行号",
  "dimension": "维度",
  "type": "子类型",
  "description": "问题描述",
  "code": "问题代码",
  "crashConsequence": "宕机后果（F维度）",
  "fixSuggestion": "修复建议"
}
```

### 1.3 分类问题

按以下维度对问题分类：

| 维度 | 说明 | 修复优先级 |
|---|---|---|
| G. 安全审计 | SQL注入、XSS、越权等安全问题 | **P0-阻塞** |
| E. 可靠性 | 幂等、分布式锁、资源泄漏 | **P1-紧急** |
| F. 宕机恢复 | 状态机、补偿机制、两阶段操作 | **P1-紧急** |
| B. 业务逻辑 | 边界条件、空指针、数据一致性 | **P2-重要** |
| A. 规范审计 | 日志、异常、事务、循环规范 | **P3-常规** |
| C. 方案合理性 | N+1查询、重复代码 | **P4-优化** |
| D. 性能 | 分页限制、批量操作 | **P4-优化** |

## Phase 2：生成修复任务

### 2.1 按文件分组

将同一文件的问题归为一组，生成该文件的修复任务：

```markdown
## {文件名}.java 修复任务

### 文件信息
- 模块：{模块名}
- 问题数：{n} 个
- 最高优先级：{P0/P1/P2/P3/P4}

### 修复步骤

#### 🔴 CRITICAL 问题

1. **[{行号}] {问题类型}**
   - 描述：{问题描述}
   - 问题代码：```java\n{问题代码}\n```
   - 修复建议：{修复建议}
   - 状态：待修复

...
```

### 2.2 按优先级排序

| 优先级 | 条件 | 命名 | 处理方式 |
|---|---|---|---|
| P0-阻塞 | CRITICAL × G安全维度 | `[P0-BLOCK]` | 必须立即修复，否则阻塞合并 |
| P1-紧急 | CRITICAL × E/F维度，或 CRITICAL × B业务逻辑 | `[P1-URGENT]` | 优先修复，影响系统稳定性 |
| P2-重要 | WARNING × B/E/F维度，或 WARNING × G安全维度 | `[P2-IMPORTANT]` | 重要修复，需纳入迭代计划 |
| P3-常规 | WARNING × A/C/D维度 | `[P3-NORMAL]` | 常规修复，可计划处理 |
| P4-优化 | SUGGESTION 级别 | `[P4-OPTIONAL]` | 优化建议，可选择性修复 |

### 2.3 生成修复计划文件

输出位置：`{报告所在目录}/{branch-name}-fix-plan.md`

文件结构：

```markdown
# 缺陷修复计划

> 分支：{branch-name}
> 基准分支：{base-branch}
> 审计时间：{audit-time}
> 修复计划生成时间：{current-time}

---

## 1. 问题统计

| 优先级 | 数量 | 说明 |
|---|---|---|
| P0-阻塞 | {n} | 必须立即修复 |
| P1-紧急 | {n} | 优先修复 |
| P2-重要 | {n} | 重要修复 |
| P3-常规 | {n} | 常规修复 |
| P4-优化 | {n} | 优化建议 |

---

## 2. 修复任务清单（按优先级排序）

### 2.1 P0-阻塞问题

（所有 P0 问题列表）

### 2.2 P1-紧急问题

（所有 P1 问题列表）

### 2.3 P2-重要问题

（所有 P2 问题列表）

### 2.4 P3-常规问题

（所有 P3 问题列表）

### 2.5 P4-优化建议

（所有 P4 问题列表）

---

## 3. 按文件修复清单

（按文件分组的问题列表，便于开发者一次性修复同一文件的所有问题）

---

## 4. 修复进度追踪

| 文件 | P0 | P1 | P2 | P3 | P4 | 状态 |
|---|---|---|---|---|---|---|
| {文件1} | {n} | {n} | {n} | {n} | {n} | 待修复 |
| {文件2} | {n} | {n} | {n} | {n} | {n} | 待修复 |
| 合计 | {n} | {n} | {n} | {n} | {n} | - |

---

## 5. 修复验收标准

- [ ] 所有 P0 问题已修复并通过自测
- [ ] 所有 P1 问题已修复并通过自测
- [ ] 所有 P2 问题已修复或已评估延后理由
- [ ] P3/P4 问题按计划处理
- [ ] 修复后重新执行 wk-code-review 验证
```

## Phase 4：确认修复范围

### 4.1 输出修复计划摘要

```
缺陷修复计划已生成

分支：{branch-name}
问题总数：{total} 个

问题优先级分布：
  P0-阻塞：{n} 个（必须立即修复）
  P1-紧急：{n} 个（优先修复）
  P2-重要：{n} 个（重要修复）
  P3-常规：{n} 个（常规修复）
  P4-优化：{n} 个（优化建议）

修复任务文件：{plan-file-path}
缺陷追踪JSON：{json-file-path}
```

### 4.2 确认修复执行范围

向用户确认本次修复的范围：

```
是否开始自动修复？请选择修复范围：

1. 全部修复 - 按优先级从 P0 到 P4 依次修复所有问题
2. 仅修复 P0+P1 - 只修复阻塞和紧急问题
3. 仅修复 P0+P1+P2 - 修复阻塞、紧急和重要问题
4. 自定义范围 - 指定要修复的问题ID列表
5. 仅生成计划 - 不执行修复，稍后手动处理
```

| 用户选择 | 行为 |
|---|---|
| 全部修复 | 进入 Phase 5，修复所有问题 |
| 仅 P0+P1 | 进入 Phase 5，只修复 P0 和 P1 |
| 仅 P0+P1+P2 | 进入 Phase 5，修复 P0/P1/P2 |
| 自定义范围 | 根据用户指定的问题ID列表修复 |
| 仅生成计划 | 停留在 Phase 4，输出计划文件 |

## Phase 5：执行代码修复

> 核心原则：**按文件、按优先级顺序执行，每修复一个问题立即更新追踪状态**

### 5.1 修复执行前置检查

在开始修复前，确认以下条件：

1. **确认工作区干净**：检查 `git status`，确认没有未提交的修改。若有，提醒用户处理
2. **确认项目可编译**：执行编译命令（如 `./mvnw compile -pl <module>`），确保基线可编译
3. **创建修复分支**（可选）：询问用户是否需要创建修复分支，如 `bugfix/{version}/{username}/{issue-id}`

### 5.2 修复执行循环

按优先级从高到低，逐个问题执行修复。使用 TodoWrite 工具跟踪全局进度。

#### 修复执行流程（每个问题）

```
对于 issues.json 中 status=pending 且在修复范围内的问题，按优先级排序依次处理：

1. [读取] 读取问题对应的源文件，定位到问题行号
2. [分析] 结合问题代码、修复建议、文件上下文，确定修复方案
3. [修复] 使用 Edit 工具修改代码
4. [验证] 编译验证修改后代码无语法错误
5. [更新] 使用 Write 工具将 issues.json 中该问题 status 更新为 "fixed"
6. [更新] 使用 Write 工具将 fix-status.json 中 pending-1, fixed+1
7. [下一个] 继续处理下一个问题
```

> **强制要求**：每个问题修复完成后，必须更新 issues.json 和 fix-status.json 的状态，不可跳过。

#### 单个问题修复详细步骤

**Step 1 - 读取源文件**

使用 Read 工具读取问题对应的文件，重点关注问题行号附近的代码上下文。如果问题涉及多个文件（如需要同时修改 Entity 和 Mapper），一并读取。

**Step 2 - 分析修复方案**

根据以下信息综合判断修复方案：
- 审计报告中的修复建议
- 问题代码的实际上下文
- 项目现有的代码模式和规范
- 是否涉及接口变更（需同步修改调用方）

修复决策规则：
- 修复方案应遵循项目现有代码风格和规范
- 优先采用最小改动原则，避免重构式修复
- 如果修复建议不明确或有多种方案，向用户确认
- 如果发现修复会引入新问题，暂停并报告给用户

**Step 3 - 执行代码修改**

使用 Edit 工具修改代码。每次修改遵循以下约束：
- 每个问题的修复尽量独立，不依赖其他问题的修复
- 修改时保留代码原有风格和格式
- 不修改与当前问题无关的代码
- 如果同一文件有多个问题，从文件末尾向前修复，避免行号偏移

**Step 4 - 验证修复**

根据优先级执行不同级别的验证：

| 验证项 | P0 | P1 | P2 | P3 | P4 |
|---|---|---|---|---|---|
| 编译检查 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 单元测试 | 必须 | 建议 | - | - | - |
| 影响范围检查 | 必须 | 建议 | 建议 | - | - |

编译检查：执行 `./mvnw compile -pl <module> -am`，确认无编译错误。

**Step 5 - 更新追踪状态（强制要求）**

每个问题修复完成后，必须更新两个 JSON 文件的状态：

1. **读取 issues.json**：使用 Read 工具读取当前内容
2. **定位并修改问题状态**：找到对应 `id` 的问题，将 `"status": "pending"` 改为 `"status": "fixed"`，同时添加 `fixedAt` 和 `fixedBy` 字段
3. **写入 issues.json**：使用 Write 工具覆盖文件
4. **更新 fix-status.json**：读取 → 修改 `pending` 和 `fixed` 计数 → 写入

示例 issues.json 更新：

```json
{
  "id": "P0-001",
  "status": "fixed",
  "fixedAt": "2026-05-16T10:30:00+08:00",
  "fixedBy": "ai-assistant",
  "fixedFile": "xxx.java",
  "fixedLine": 42
}
```

> **警告**：跳过状态更新将导致追踪数据不一致，中断恢复无法正常工作。AI 在每次修复后必须执行此步骤。

### 5.3 修复异常处理

#### 修复失败

当修复无法完成时：

1. 将问题状态标记为 `fix_failed`，记录失败原因
2. 在 issues.json 中添加 `failureReason` 字段
3. 继续处理下一个问题，不阻塞整体流程
4. 在最终摘要中汇总所有失败的问题

```json
{
  "id": "P1-003",
  "status": "fix_failed",
  "failureReason": "修复涉及接口签名变更，需人工确认调用方影响范围",
  "failedAt": "{timestamp}"
}
```

#### 修复需人工介入

当遇到以下情况时，标记为 `needs_manual` 并跳过：
- 修复方案不明确，有多种可能
- 修改涉及跨服务接口变更
- 需要业务领域知识才能判断正确修复方式
- 修复可能影响数据一致性，需人工评估

```json
{
  "id": "P2-005",
  "status": "needs_manual",
  "reason": "状态机转换逻辑需业务方确认，无法自动修复"
}
```

#### 用户选择延后

当用户选择延后某个问题时，标记为 `deferred`：

```json
{
  "id": "P3-002",
  "status": "deferred",
  "deferredReason": "本迭代排期已满",
  "expectedFixTime": "下个迭代"
}
```

### 5.4 同文件多问题修复策略

当同一文件有多个问题时：
1. 按优先级从高到低排序
2. 同优先级按行号从大到小排序（从文件末尾向前修复，避免行号偏移）
3. 所有同文件问题修复完毕后，统一执行一次编译验证
4. 更新该文件所有问题的状态

## Phase 6：验证与总结

### 6.1 全量编译验证

修复完成后，执行全量编译：

```bash
./mvnw compile
```

如果编译失败：
1. 定位编译错误
2. 回退最近一次修改
3. 重新尝试修复
4. 重复直到编译通过

### 6.2 更新修复计划文件

在修复计划文件的「修复进度追踪」章节，更新每个文件的修复状态：

```markdown
## 4. 修复进度追踪

| 文件 | P0 | P1 | P2 | P3 | P4 | 状态 |
|---|---|---|---|---|---|---|
| {文件1} | 1/1 | 2/2 | 0/1 | 0/0 | 0/0 | 部分修复 |
| {文件2} | 0/0 | 1/1 | 2/2 | 1/1 | 0/0 | 已完成 |
| 合计 | 1/1 | 3/3 | 2/3 | 1/1 | 0/0 | 进行中 |
```

### 6.3 更新验收清单

在修复计划文件的「修复验收标准」章节，勾选已完成项：

```markdown
## 5. 修复验收标准

- [x] 所有 P0 问题已修复并通过自测
- [x] 所有 P1 问题已修复并通过自测
- [ ] 所有 P2 问题已修复或已评估延后理由（P2-003 延后至下迭代）
- [ ] P3/P4 问题按计划处理
- [ ] 修复后重新执行 wk-code-review 验证
```

### 6.4 输出最终摘要

```
缺陷修复执行完成

分支：{branch-name}
问题总数：{total} 个

修复结果：
  已修复：{n} 个
  修复失败：{n} 个
  需人工处理：{n} 个
  用户延后：{n} 个
  未处理：{n} 个

按优先级统计：
  P0-阻塞：已修复 {n}/{total}
  P1-紧急：已修复 {n}/{total}
  P2-重要：已修复 {n}/{total}
  P3-常规：已修复 {n}/{total}
  P4-优化：已修复 {n}/{total}

需人工处理的问题：
  - P2-005: 状态机转换逻辑需业务方确认
  - P1-003: 接口签名变更需评估调用方影响

后续建议：
  1. 处理标记为 needs_manual 的问题
  2. 运行完整测试套件
  3. 执行 wk-code-review 验证修复效果

修复文件：{plan-file-path}
追踪数据：{json-file-path}
```

3. 提交代码

## 附录：与 wk-code-review 的衔接说明

### 衔接设计

```
wk-code-review 输出           →    review-bug-fix 输入
─────────────────────────────────────────────────────────
{branch-name}.md             →    作为报告源输入
问题统计表格                  →    解析并重新分类
按维度分组的问题列表          →    重组为按优先级和按文件两种视图
审计结论                     →    作为整体判断依据
─────────────────────────────────────────────────────────
输出                         →    输出
─────────────────────────────────────────────────────────
{branch-name}-fix-plan.md    →    修复指南 + 修复进度追踪（按优先级组织）
{branch-name}-issues.json    →    可导入缺陷管理系统的结构化数据（含修复状态）
{branch-name}-fix-status.json→    修复进度汇总
代码修改                     →    AI 自动修复的代码变更
```

### 推荐的 Skill 调用流程

1. **wk-code-review**：执行代码审计，生成审计报告
2. **review-bug-fix**：读取审计报告 → 生成修复计划 → **自动执行修复** → 输出修复结果
3. **开发者处理**：处理需人工介入的问题
4. **wk-code-review**（可选）：重新审计，验证修复效果

## 示例对话

| 用户输入 | 处理方式 |
|---|---|
| `review-bug-fix /path/to/report.md` | 读取报告 → 解析问题 → 生成修复计划 → 确认修复范围 → 执行修复 → 输出结果 |
| `review-bug-fix /path/to/report.md --plan-only` | 仅生成修复计划，不执行修复 |
| `对审计报告生成修复任务` | 询问报告路径 → 生成修复计划 → 询问是否执行修复 |
| `review-bug-fix`（无参数） | 使用默认路径或询问用户 |
| `继续修复上次未完成的问题` | 读取 fix-status.json → 从中断处继续执行 |
