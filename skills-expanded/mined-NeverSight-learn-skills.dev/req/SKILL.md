# Req - 需求管理

## 职责
收集用户需求 → 结构化文档 → 状态追踪

## 触发条件
- 用户描述新功能/新需求/用户故事
- dev 路由判定为"需求类"意图
- 需要澄清或补充已有需求

## 工作流程

### Step 1: 原始输入记录
```
用户描述 → 存入 wiki/raw/user-inputs/YYYYMMDD-HHMMSS-{slug}.md
```

### Step 1.5: KB 模式检索（深挖前）

在开始深挖需求前，检查**正式目录**中是否有类似需求的模式：

```
Grep pattern: "{功能领域关键词}"
target: wiki/knowledge/patterns/*.md       ← 只读正式目录，不含 raw/
```

**如果找到相关 pattern**:
→ 将其中的"适用场景/边界条件/常见陷阱"作为深挖提问的**基准参考**
→ 例: "上次做搜索功能时我们考虑了分页、防抖、空状态处理——这次需要吗？"

**目的**: 不从零开始深挖，基于已有经验加速收敛。

### Step 2: 需求深挖（分层提问，不要猜测）

#### 2.1 输入深度评估

先判断用户输入的丰富度：

| 等级 | 特征 | 例子 | 行动 |
|------|------|------|------|
| **L1 一句话** | 只有动词+名词，无细节 | "做个登录"、"加个搜索" | → 必须走完整深挖流程 (2.2~2.5) |
| **L2 有轮廓** | 说了核心功能点，缺边界/约束 | "用户用手机号登录，支持验证码" | → 走 2.2 + 2.3 补充维度 |
| **L3 有细节** | 功能、场景、约束都有提及 | 可直接进入 2.6 验证确认 |

**永远不要对 L1/L2 输入直接开始设计。**

#### 2.1.5 深挖裁剪（每层入口判断）

不是所有需求都需要走完全部 4 层。在进入每层前做快速判断：

| 深挖层 | 适用条件 | 跳过条件 |
|--------|---------|---------|
| **2.2 功能拆解** | 几乎总是适用 — 确认"做什么"的边界 | 需求本身就是单一原子操作（如"改个按钮颜色"） |
| **2.3 场景反推** | 涉及用户交互 / 多角色 / 多端 | 纯后端/纯工具/无 UI 的需求可简化为只列输入输出 |
| **2.4 边界探测** | 涉及数据持久化 / 用户生成内容 / 权限 / 支付 / 第三方API | 只读展示类/纯计算类/内部工具可跳过安全与并发问题 |
| **2.5 优先级收口** | 功能点 ≥ 5 个 或 用户未明确说先做哪个 | 单一功能点需求直接跳到输出 |

**裁剪原则**: 宁可多问一句无关紧要的，也不要漏掉一个关键假设。不确定是否适用时——问。

#### 2.2 第一层：功能拆解（What 拆细）

用户说"做个 XX"，拆成最小功能单元：

```
核心问题: 这个功能具体包含哪些子能力？

提问方式（按顺序）:
  ① 主流程是什么？→ 用户操作步骤一步步来
  ② 有哪些分支路径？→ 成功/失败/取消 各怎么处理
  ③ 需要管理什么数据？→ 输入/输出/存储各是什么
  ④ 跟现有功能的交集？→ 是否替换/增强/独立

示例:
  用户: "做个登录"
  → ① 主流程: 输入凭证 → 验证 → 登录成功跳转
  → ② 分支: 密码错误? 账号不存在? 验证码过期? 网络断开?
  → ③ 数据: 用户名/密码/手机号/验证码/token/会话状态
  → ④ 交集: 现有注册页面? 个人中心? 权限系统?
```

输出：**功能清单**（3-8 项）

#### 2.3 第二层：场景反推（Who × When × Where）

从用户角色和使用场景反推隐含需求：

```
核心问题: 谁在什么情况下用它？不同角色看到的一样吗？

提问方式:
  ① 有几种用户角色？→ 普通用户/管理员/访客/第三方？
  ② 每个角色的核心场景是什么？→ 用"作为XX，我希望YY，以便ZZ"格式
  ③ 移动端和桌面端行为一致吗？→ 响应式还是分开做
  ④ 高并发/低网络/离线等特殊环境呢？→ 非功能性需求

示例:
  用户: "做个登录"
  → 角色: C端用户(手机号) / B端管理员(账号密码) / 运营后台(SSO)
  → 场景: 首次登录 / 忘记密码 / 换设备登录 / 长时间未操作重新登录
  → 环境: 弱网下验证码重试? 公共设备需"记住我"关闭?
```

输出：**用户故事清单**（按角色分组）+ **非功能性需求初稿**

#### 2.4 第三层：边界探测（Negative Case 挖隐含假设）

这是最关键的一层——用户不会主动说的需求都在这里：

```
核心问题: 什么事情不应该发生？边界在哪里？

必须问的 4 类反向问题:

  A. 数据边界
     → 最大值/最小值/空值/超长/特殊字符 怎么处理?
     → 例: 密码最多几位? 手机号格式不对怎么办? 用户名能重复吗?

  B. 并发与竞态
     → 同一账号多地登录? 同时提交两次订单? 编辑冲突?

  C. 异常与降级
     → 服务不可用时给什么提示? 缓存策略? 超时多久算失败?
     → 第三方服务挂了(短信/支付/OAuth) 怎么办?

  D. 安全与权限
     → 谁能看到什么? 操作需要二次确认吗? 审计日志?
     → 敏感数据如何存储? 会话过期策略?

判断标准: 每类至少问 1-2 个与当前需求相关的问题
```

输出：**边界条件清单** + **异常处理规则**

#### 2.5 第四层：优先级与约束（Why + How 收口）

```
核心问题: 最重要的是什么？什么条件下可以不做？

提问方式:
  ① 如果只能做一半，先做哪部分？→ MVP 范围界定
  ② 有参考实现或竞品吗？→ 截图/链接/体验描述
  ③ 技术上有什么不能用的？→ 不兼容的库/版本/平台
  ④ 上线时间期望？→ 影响技术方案选型（快速上线 vs 长期维护）
```

输出：**P0/P1/P2 分级** + **技术约束列表**

#### 2.6 停止条件

满足以下任一条件即可停止深挖，进入 Step 3 输出文档：

- [ ] 功能清单 + 用户故事 + 边界条件 + 优先级 **四层都覆盖**
- [ ] 用户明确表示"就这些，先这样做"
- [ ] 连续 2 轮追问后用户回答没有新增信息

**禁止**: 自行补全/猜测用户没确认的需求。不确定的标记为 `TBD` 在文档中。

### Step 3: 输出结构化文档

输出到 `wiki/requirements/{slug}.md`，frontmatter 格式：

```yaml
---
id: "user-auth"
type: requirement
status: draft                    # draft | reviewing | approved | implemented | deprecated
title: "用户认证系统"
depends_on: []
created: "2026-04-25T10:00"
updated: "2026-04-26T10:00"
stale: false
---
```

正文结构见 `references/requirement-document.md`

### Step 4: 状态流转

```
draft → reviewing → approved → implemented
         ↘ rejected  ↗               → deprecated
```

| 状态转换 | 触发条件 | 必须执行的动作 |
|---------|---------|--------------|
| draft → reviewing | 信息收集完毕 | 通知相关方 review |
| reviewing → approved | Review 通过 | **触发变更传播** (见下方) |
| approved → implemented | feat-accept 通过 | 更新 status |
| any → deprecated | 需求取消 | **标记下游全部 stale** |

## 变更传播（核心规则）

当 REQ 文档被**修改**时（任何状态）：

### 1. 更新自身 frontmatter
- 改 `updated` 时间戳
- 如果是重大变更，设 `stale: true`

### 2. 找下游依赖者（Grep 按需扫描）
```
Grep pattern: "depends_on.*REQ-001"
target: wiki/**/*.md
```
找到所有引用了本 REQ 的 ARCH / FEAT 文档。

### 3. 标记下游 stale + 提示
对每个找到的下游文档：
- 将其 frontmatter 中 `stale` 改为 `true`
- 更新 `updated` 时间戳

> ⚠️ {slug} 需求已变更，以下关联文档可能需要同步更新:
> - wiki/architecture/xxx.md
> - wiki/features/xxx/design.md

### 4. 重大变更（approved → draft）
- 通知所有下游 FEAT 暂停实现
- 建议: 重新走 arch 审查流程

## 与其他技能的协作

| 场景 | 下一步 | 条件 |
|------|--------|------|
| 需求涉及系统设计/技术选型 | → `arch` | 非 trivial 改动、涉及多模块 |
| 需求明确且简单 | → `feat` | 单一功能、无需架构决策 |
| 需求变更/补充 | 更新本 REQ 文档 | 触发变更传播 |
| 需求被否决 | 标记 rejected | 清理 downstream 引用 |

## 输出规范

| 项目 | 格式 |
|------|------|
| 原始输入文件 | `wiki/raw/user-inputs/YYYYMMDD-HHMMSS-{slug}.md` |
| 需求文档 | `wiki/requirements/{slug}.md` (含 frontmatter) |
| ID 命名 | kebab-case 语义化名, 如 user-auth / payment-flow / search-v2 |
