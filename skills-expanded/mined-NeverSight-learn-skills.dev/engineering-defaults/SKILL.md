# 工程默认值

两条默认值，方向都是**少造**：

- **复用优先于新建。** 已有的、已装的、成熟的，依次穷尽之后才手写。
- **测试必须挣得自己的位置。** 覆盖率不是目标；一个不可能因真实原因失败的测试
  比没有测试更糟——它要维护，它会在合理改动时挂掉，还会让整个套件看起来在保护
  一些它并没有保护的东西。

**项目自带的 skill 比本 skill 更具体时，以项目 skill 为准。** 本 skill 不写
任何仓库路径、包名或命令；那些是项目层的事。

## 触发场景

- 准备引入一个新依赖
- 准备手写一个通用控件、hook、工具函数或格式化器
- 被要求新增或修改测试
- **你正准备加一个没人要求的测试**
- 功能写完了，正在决定验证什么
- 在 review 一个新增依赖或新增测试的 diff
- 某个测试文件要被移动、改名或删除

## 加载顺序

1. 准备造任何东西 → `references/reuse-before-build.md`。**动手前读，不是 review 时读。**
2. 在判断要不要写测试 → `references/tests-earn-their-place.md`
3. 决定要写了 → `references/do-not-test.md`（每次都读；这些写法很有迷惑性）
4. 决定不写测试，需要说明怎么验证的 → `references/verification-gates.md`

## 硬性约束

1. **造任何东西之前先走完复用梯。**
   Why：仓库里已经装好、已经接好主题、已经处理过无障碍和边界情况的东西，
   手搓的等价物会逐条漏掉，而且漏在你不会去测的地方。

2. **提新依赖必须同时给出三样：包名、为什么已装的这批覆盖不了、维护状态。**
   Why：为一件已装依赖已经能做的事再引入第二个库，是会被打回的改动；
   三样齐全才能让人在不重做一遍调研的情况下判断。

3. **第三方库经内部封装使用，业务调用点不直接引。**
   Why：直接引会让换库、加默认值、统一错误处理变成全仓改动。

4. **加测试是成本，默认不加。** 先过 `tests-earn-their-place.md` 的闸门。
   Why：这份清单存在，是因为不过闸门写出来的测试后来都被删了——
   它们一个问题都没抓到，却全程要维护。

5. **一个行为一次证明，取能证明它的最低层。**
   Why：纯函数测试比路由测试快、稳、失败原因清楚。同一段逻辑在两层各断言一遍时，
   高层那条只在低层已经红了之后才会红——它没有增加任何信息。

6. **gate 没跑或没通过，就不许把改动描述成已验证。**
   Why：「应该没问题」和「typecheck 过了」在读者眼里长得一样，但只有后者可复核。

## 项目接线

首次在一个仓库里用本 skill 时，把下面几项落到该仓的 AGENTS.md 或项目 skill 里；
本 skill 不持有它们：

- 本仓的 gate 命令（typecheck / lint / build / 结构化 checker / 测试）
- 已有 UI 原语和已装依赖的清单在哪个文件
- 测试 runner 的划分与文件名约定
- 新增或删除测试文件需要连带改的接线（脚本里点名的路径、死代码检测的入口 glob）

## 汇报

测试失败就直说，并引用失败输出里最短的决定性一行。
没跑的 gate 不要说成跑了。手写了一个本可以复用的东西时，说明你查过什么、为什么不合适。
