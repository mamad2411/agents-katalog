# 结构化调试修复

## 为什么需要这个技能？

修 BUG 时最容易犯的错误是**看到报错就改那里的代码**。这是人的本能，也是 AI 的本能——但它是错的。

原因很简单：代码崩溃的位置通常不是错误产生的位置。就像发烧不是病根，体温计坏了也不是病因。崩溃处的函数可能只是被上游传了一个 null，你在这个函数里加空值检查，修的是症状。真正的根因在上游——那个产生 null 的地方。

这个技能教给你一套方法论，让你在改任何代码之前，先回答两个问题：
1. **数据在哪一步首次偏离了预期？** （源头，不是症状）
2. **有没有至少两个独立证据同时指向这个结论？** （交叉验证，不是猜）

---

## 你的角色

你是调试者，不是修理工。修理工看到漏水就换水管，调试者先找到水源。

你的工作方式是：**理解问题 → 收集证据 → 定位源头 → 一次修复。** 在证据不足以锁定源头之前，你不写任何修复代码。这不是保守，是效率——每次猜错方向都是在浪费用户的时间。

**关于用户交互：** 每次对话回合结束时，你必须调用 AskUserQuestion，让用户选择 Proceed（继续调试）或 Mark Fixed（已修复）。这是用户掌控调试节奏的唯一方式。没有这个出口的回合是不完整的。具体定义见下方「用户交互」章节。

## 常见失败模式（请先读完再开始）

以下模式来自本技能的真实失败案例。每一条都浪费了用户 3 轮以上的对话：

- **"我觉得可能是 X，先改了试试"** → 用户报告"放大到 100% 后失效"，AI 却去修改滚轮方向。猜错了，用户纠正，AI 又猜另一个方向。连续猜错 4 次。**正确做法：不知道自己不知道时，埋点收集数据，不要猜。没有 2 个证据就不修。**

- **"用户说东我修西"** → 用户说滚轮缩放有问题，AI 给加了两个按钮。用户说不要按钮，AI 还在加按钮。**正确做法：用户纠正你时，立刻停手，回到第一步重新理解问题。被纠正 2 次必须触发方向自疑。**

- **"用 console.log 埋点"** → instrumentation-guide.md 明确禁止 console.log，要求用标准 fetch/file 模板。跳过参考文档直接操作就会犯这种错。**正确做法：注入埋点前必须先读 instrumentation-guide.md，严格按模板来。**

- **"跳过交叉验证门禁"** → AI 口头说"有两个证据"，但没有显式列出证据是什么，就直接动手修了。**正确做法：必须显式写出"证据 1 是 XXX，证据 2 是 YYY"。写不出来说明只有一个证据，该埋点埋点。**

- **"把行为确认当成证据"** → AI 在第一步末尾收到用户的行为选择（"数值在变但画面不变"），加上自己看代码的推测（"CSS 优先级问题"），就宣布两个证据通过门禁。但用户只是描述了现象，你只是在猜原因——这本质上是**一个信息源的两个角度的解读**，不是两个独立证据。**正确做法：第一步末尾的行为确认帮你选了一条调用链分支，不是证据。进入交叉验证时必须用上面的自检清单逐项打勾——选完你通常只有静态代码推理这一个维度，不及格就去埋点。**

## 用户交互

**每次对话回合结束时强制执行 AskUserQuestion。**

除 1.1 确认理解外，所有回合使用以下两个固定选项：

### Proceed

**含义**：BUG 尚未修复，需要继续调试。

AI 根据当前所处阶段，智能选择后续操作：
- 处于第一步（多维分析）→ 进入第二步（交叉验证）
- 处于第三步（埋点分析）→ 根据当前阶段智能继续：阶段一等待复现中 → 进入阶段二分析日志；阶段二分析完毕 → 源头定位则回到第二步交叉验证、未定位则追加埋点、矛盾则进入第五步
- 处于第四步（源头修复）→ 说明修复未生效，携带失败信息（改了哪里、为什么没生效）回到第三步
- 处于第五步（方向自疑）→ 进入分层重启

连续两次 Proceed 是重要信号——说明前两轮方向可能整体偏离，应主动检查是否触发第五步方向自疑。

### Mark Fixed

**含义**：BUG 已修复，用户确认问题解决。

执行完整清理链后，整个调试流程结束：
1. 删除 `.debug/logs/{session_id}.log`
2. `node <skill base directory>/scripts/cleanup-debug-blocks.js --session-id {id} --files {文件列表}`
3. 按 `<skill base directory>/templates/memory-fix.md` 模板生成记忆文件到 `.debug/memory/`
4. 更新 `MEMORY.md` 索引：追加 `- [标题](文件名.md) — 一句话描述`（文件不存在则先创建，格式见 `<skill base directory>/references/memory-system.md`）

禁止手动删除埋点代码——直接使用清理脚本完成全部清理。

```
用户报告 BUG
    ↓
【多维分析】: 确认理解 → 记忆检索 → 重建调用链 → 行为分叉澄清
    ↓
交叉验证门禁: 至少两个维度指向同一根因?
    ├─ 是 → 【源头修复】
    │         ↓
    │    【用户交互】Proceed / Mark Fixed

    │
    ├─ 证据不足 → 【埋点分析】
    │               ├─ 日志埋点（注入探针 + 等待复现）
    │               └─ 日志分析（读日志 → 偏差定位）
    │                     ├─ 定位源头 → 回到【交叉验证门禁】（用运行时日志补足第二维度）

    │
    └─ 证据矛盾 → 【方向自疑】
                      ↓
                 【方向重启】: 回退代码 + 清理埋点代码 → 回到【多维分析】（携带负向约束）
```

## 第一步：多维分析——建立假设，不碰代码

**为什么这是第一步？** 没有假设的调试是随机游走。你需要先有一个"你认为问题在哪"的 mental model，后续的埋点和分析都在验证这个 model。而且此时你还没有任何运行时数据，凭静态推理去改代码就是在猜——猜错的代价是浪费时间，猜对的概率很低。

**用户纠正你的理解时**，立刻停手，回到这一步重新理解问题。连续被纠正 2 次，直接触发第五步方向自疑，不要再继续猜。

### 1.1 确认理解问题

用自己的话复述用户的 BUG 描述，包括三个要素：
- **触发条件**：用户做了什么操作？
- **实际表现**：发生了什么（或没发生什么）？
- **用户期望**：用户认为正确的行为应该是什么？

复述后直接发给用户确认。不要用"我理解对了吗"这种开放式提问——用户已描述过一遍了。用陈述句："你做了 X，期望 Y，但实际发生了 Z。"

然后调用 AskUserQuestion（这是唯一不用 Proceed/Mark Fixed 的回合——这里只是确认理解，还没开始调试）：

- "理解正确，继续分析"
- "需要纠正"

用户选"理解正确" → 一口气跑完 1.2~1.4，第一步结束时用 Proceed/Mark Fixed 收尾。
用户选"需要纠正" → 在 Other 中输入纠正内容，更新理解后重新确认，直到用户认可为止。

### 1.2 搜索历史记忆

用 `Grep` 工具从用户描述中提取关键词（模块名、文件名、症状关键词），搜索 `.debug/memory/` 目录。命中则直接读对应记忆文件——历史记录能直接告诉你根因在哪，省掉后面所有步骤。未命中就跳过，不要为了"找全"逐个读取记忆文件浪费 token。此步骤不强制关联，30 秒内完成。

### 1.3 重建完整调用链

**读 `<skill base directory>/references/root-cause-tracing.md`。** 这个文档是这一步的执行说明书——包含调用链重建方法论、链路覆盖清单、源头判定表、每步对照检查表。不读它你就不知道调用链应该覆盖到什么程度。

按照 `root-cause-tracing.md` 中的方法，从异常表现点出发，沿数据流向反向追溯，画出一条完整的调用链。

覆盖要求：
- **逻辑 BUG**：函数调用链，从异常函数沿调用栈反向追溯。异步边界（await/.then/setTimeout）、中间件注册顺序（Express/Koa）、组件层级与 props 传递（React/Vue）——每层都算一跳，不能跳过。
- **视觉 BUG**：DOM/CSS 继承链，从异常元素沿 DOM 树向上追溯。重点检查父容器 overflow/position/display、CSS 优先级冲突、JS 动态样式注入。
- 动态派发（策略模式、DI 容器）无法静态确定 → 标注为"动态节点"，后面用埋点 stack 揭示。
- 第三方库内部路径不明 → 标注为"黑盒节点"。

### 1.4 行为分叉澄清——用代码发现追问用户观察

**为什么不是列假设让用户选？** 1.3 之后你确实应该有假设了，但用户可能不知道 ResizeObserver 是什么、也不清楚 clampScale 在哪。把代码层面的假设直接抛给用户，用户没法选——这不是用户的问题，是你的问题弄反了。

正确的方向：从代码中识别出**行为分叉点**——哪些代码分支会导致用户看到不同的现象？把行为差异描述出来让用户确认，用户一定能回答，因为他看到了实际发生什么。

示例（搜索框输入关键词后没反应）：

1.3 重建出调用链 onInput → debounce(300ms) → buildQuery → fetchResults → setSearchResults → renderList。识别出三个行为分叉点后，调用 AskUserQuestion：

```
- question: "我分析了搜索代码，有几个细节需要你帮忙确认："
- multiSelect: true
- options:
  - "输入后界面上什么都没发生，连 loading 都没有"
  - "出现 loading 了，但一直在转，结果列表始终是空的"
  - "结果列表有更新，但显示的内容和搜索关键词无关"
  - "都不是，我描述一下实际情况……"
```

每个选项对应调用链上的不同位置：输入无反应 → onInput/debounce 环节未触发；一直 loading → fetchResults 未返回或抛错未处理；结果不匹配 → buildQuery 构建查询参数有问题。

**选项设计原则**：
- 必须是用户**能看到的现象**，不是代码内部原因
- 每个选项对应调用链上**不同的代码分支**
- 必须包含一个兜底选项"都不是"，让用户有出口
- 用户选择后，AI 内部就知道该在调用链的哪一段重点排查——但你不需要告诉用户"我排查到了 clampScale"，直接用这个方向进入第二步交叉验证

**重要区分**：1.4 是在收窄排查范围（行为分叉），不是在收集证据（交叉验证）。用户选了某一项只表示"现象确实是这个"，你的代码推测仍然是未经证实的推测。这一步的用户确认**不计入第二步的证据维度**——进入第二步后，你依然只有一个维度（静态代码推理），不够 2 个就必须去埋点。

## 第二步：交叉验证——统计证据维度

**为什么需要这个门禁？** 因为这个行业最经典的错误就是"代码里看到一个可疑的地方，觉得很可能是它，直接改了，然后发现不是"。交叉验证强制你对证据计数——必须至少两个独立维度的证据同时指向同一根因，才能动手修。

### 显式统计证据维度（逐项打勾，不可跳过）

每次进入交叉验证门禁时（无论是第一步结束后首次进入，还是从日志分析定位源头后返回），必须逐项完成以下自检：

```
证据自检（逐项回答，缺一项即为不及格）：

[ ] 证据一：_______________
    来源：[ ] 静态代码 [ ] 历史记忆 [ ] 运行时日志 [ ] 视觉/布局 [ ] 用户确认
    它指向什么结论：_______________

[ ] 证据二：_______________
    来源：[ ] 静态代码 [ ] 历史记忆 [ ] 运行时日志 [ ] 视觉/布局 [ ] 用户确认
    它指向什么结论：_______________

独立性检查：证据一和证据二是否来自不同的信息源类型？
  [ ] 是，确实独立
  [ ] 否 → 只有一个维度，不及格

陷阱检查：以下组合不是独立来源，算同一个维度：
  - "代码推测了原因 A" + "用户描述了现象 B" → 它们指向同一个观察
  - "代码推测了原因 A" + "代码推测了原因 A（另一种表述）" → 它们来自同一个脑袋
  - "代码显示某处缺少某逻辑" + "用户说功能因此不正常" → 同上。代码结构描述和症状描述只是同一件事的两种说法，不是独立验证。例如：代码里 handleWheel 没调 setOffset + 用户说鼠标没跟随缩放 → 这只是你读了代码后用症状验证了自己的猜测，本质是一个维度
```

**重要：清单必须逐项打 `[x]` 勾选，不得用自由文本代替。** 缺少勾选动作会降低执行严肃性——自由文本容易跳过来源类型和独立性检查。

**根据自检结果决定下一步：**

- **2+ 维度同时指向同一根因** → 门禁通过，进入第四步「源头修复」
- **只有 1 个维度有证据** → 证据不足，进入第三步「埋点分析」
- **2+ 维度互相矛盾** → 你的理解模型错了，进入第五步「方向自疑」

从日志分析返回时，你已拥有运行时日志数据——将日志分析结论作为"运行时日志"来源的证据填入清单，通常与静态代码证据组合即可满足双维度要求。

## 第三步：埋点分析——用运行时数据验证假设

**什么时候做？** 只在交叉验证证据不足时做。如果你已经有 2+ 证据指向根因，跳过这一步直接修复。

**为什么用二分法而不是全量散点？** 在一串 10 层的调用链上做二分查找，最多 3 轮（log₂10 ≈ 3）就能收敛到单个节点。全量散点不仅浪费，还会产生大量日志噪音掩盖真正的信号。

**回合节奏规则**：埋点分析是唯一需要用户反复复现 BUG 的阶段，最容易变成来回拉扯。这里要遵守一条额外的约定——**不要在回合结束时额外问"复现完了吗"、"重试一次？"之类的确认。** Proceed 本身就隐含了"已复现"的含义。两次用户点击之间，AI 把分析链路一口气跑完，不中断。

埋点分析分为两个小阶段：

---

### 阶段一：日志埋点

### 3.1 判定运行环境

**读 `<skill base directory>/references/environment-detection.md`**，按文档中的缓存优先策略判定代码运行在客户端还是服务端。

1. 优先读 `.debug/config.yaml`，用 glob 规则匹配目标文件 → 命中则直接使用缓存结果
2. 未命中则按文档规范动态检测（浏览器 API → 客户端，Node 核心模块 → 服务端）
3. 双端代码优先选服务端埋点（避免启动 HTTP 服务）
4. **必须执行**：检测结果写入 `.debug/config.yaml`（glob 规则覆盖目标文件所在目录，非单个文件；写入前检查不重复）。不做这一步，下次调试同一模块还要重检，浪费回合。

### 3.2 注入埋点

**读 `<skill base directory>/references/instrumentation-guide.md`**，这是这一步的执行说明书。关键规则：

**1. 生成 session ID**：`debug_YYYYMMDD_HHmmss_随机4位`（如 `debug_20260518_143025_a3f2`），首轮埋点开始时生成，全流程统一使用。

**2. 确保日志服务已运行**（仅客户端需要）：
- 先健康检查 GET `http://localhost:9220/health`，通 → 直接注入
- 不通 → `node <skill base directory>/scripts/launch-debugger.js` 启动服务 → 复检通过 → 注入

**3. 按模板注入埋点代码**：
- **禁止 console.log / print / fmt.Println / echo 等语言自带日志方式**
- 所有埋点用 `#region DEBUG [sessionId: xxx]` / `#endregion DEBUG` 包裹
- 首轮 ≤3 处，追加每次 ≤2 处，总共 ≤3 轮
- 位置基于调用链二分法选择（链中点注入首处，分叉点补充）
- 埋点只能读取数据，禁止修改业务变量或程序状态

**4. 注入前检查**：已有 #region DEBUG 块？→ 不重复注入。注入位置在可执行代码内？健康检查通过？服务端路径可写？

**5. 日志内容必须回答四问**：函数收到了什么？返回了什么？走了哪个分支？对外产生了什么影响？

**6. 清空日志文件**：`echo "" > .debug/logs/{{DEBUG_SESSION_ID}}.log`。每次注入埋点后必须清空，确保下一轮收集的是干净数据，不会混入旧日志干扰分析。

阶段一的工作就是注入探针。注入完成后清空日志，然后你需要用户去复现 BUG 才能收集到运行时数据——所以你**必须在这里停下**，按【用户交互】章节执行 AskUserQuestion。用户选 Proceed 即表示"已复现"，你进入阶段二读取日志并分析。

---

### 阶段二：日志分析

上一轮用户选了 Proceed，现在你有日志数据了。依次完成以下分析：

#### 调用链核验（不可跳过）

按时间戳排序日志，用 `location` 字段还原实际执行顺序 → 与步骤 1.3 的静态调用链逐层对比：
- 埋点的 `location` 都出现在预期位置，且 data 中的变量值符合调用链推导 → 调用链正确，继续偏差分析
- 某处埋点未触发（预期该有日志但没出现）→ 实际执行路径与静态分析不同，可能走了其他分支，修正调用链后继续
- 日志顺序与预期调用顺序不一致 → 异步时序或事件触发顺序与静态分析不符，修正后继续

这一步无需额外代码，仅检查已有日志的 `location` 和 `data`，但能避免在错误调用链上浪费全部埋点轮次。

#### 偏差分析

每条日志对照正确性假设，判断：

| 情况 | 判定 | 动作 |
|------|------|------|
| 入参符合预期，但输出偏离了 | 本地产生 | **源头定位 → 回到第二步交叉验证** |
| 入参就已经偏离了 | 上游传入 | 向上二分继续 |
| 未捕获到偏差 | 未覆盖链段 | 在未覆盖段中点继续埋点 |
| 连续两轮未捕获 | 方向问题 | 进入第五步方向自疑 |
| 三轮埋点耗尽 | 无法定位 | 进入第五步方向自疑 |

#### Heisenbug 检查

埋点后 BUG 消失且涉及异步/竞态 → 这是 Heisenbug 信号。埋点引入的微小时序变化改变了执行顺序。此时不应继续埋点，应转为静态代码推理，重点检查 Promise、setTimeout、await 的时序依赖。

分析完成后，按偏差分析的结果决定去向（定位到源头→回到第二步交叉验证、未定位→回到阶段一追加埋点、矛盾→第五步方向自疑）。**无论哪种去向，分析完成后立即清空日志文件**（`echo "" > .debug/logs/{{DEBUG_SESSION_ID}}.log`），确保下一轮数据干净。做完该做的动作后，回合结束时按【用户交互】章节执行 AskUserQuestion。

## 第四步：源头修复——一次修对

**为什么只能改源头？** 修复症状位置（比如崩溃处加个空值检查）会产生两个问题：一是根因还在，同样的异常数据会在别处引发新崩溃；二是代码里积累越来越多的防御性代码，掩盖真正的逻辑漏洞。

### 修复前确认（四项全部通过才能动手）

- [ ] 至少两个独立信息源指向这个根因？（回顾第二步的显式统计结果）
- [ ] 你要改的是数据首次偏离的源头节点，不是下游症状？
- [ ] 修复涉及公式/算法？→ **先用日志中的实际数据手工验算**，代入公式确认输出值正确，再改代码。验证方式：取一条日志的入参，手算预期输出，对照日志中实际输出是否吻合偏差方向。验算未通过之前禁止碰代码。
- [ ] 只改根因，不动无关代码？

### 4.1 输出传播路径

先输出完整的偏差传播路径，让用户看到你理解问题是怎么传导的：

```
getCart 返回 null → checkout 收到 cart=null → applyCoupon 访问 null.discount → TypeError
【源头】getCart：应确保返回空对象而非 null
```

### 4.2 执行修复

在源头节点一次性修复，不改无关代码。

### 4.3 结果处理

**修复成功** → Mark Fixed 时执行完整清理链（详见「用户交互」章节）。

**修复失败** → **禁止再次直接修改代码。** 你的交叉验证证据可能指向了错误的方向。必须携带失败信息（改了哪里、为什么没生效）回到第三步埋点分析，让运行时数据纠正你的理解。

### → 【用户交互】

执行「用户交互」章节定义的 Proceed / Mark Fixed 流程。

## 第五步：方向自疑——承认可能走错了

**触发条件**（任一满足即进入）：

| # | 条件 | 类型 |
|---|------|------|
| 1 | 用户纠正你的方向 ≥2 次 | 主动 |
| 2 | 用户描述与代码静态分析结果根本矛盾 | 主动 |
| 3 | 埋点日志调用链与用户复现步骤严重不一致 | 主动 |
| 4 | 同一假设被证据否定 ≥2 次 | 主动 |
| 5 | 代码修改 ≥3 次但 BUG 仍在 | 主动 |
| 6 | 排查超过 5 个回合无实质性进展 | 主动 |
| 7 | 连续两轮埋点未捕获偏差 | 被动 |
| 8 | 三轮埋点耗尽仍无法定位源头 | 被动 |

进入第五步后，**必须先读 `<skill base directory>/references/direction-doubt.md`**，再依次执行 5.1→5.2→5.3→5.4→5.5→5.6。不允许跳过任何子步骤。

### 5.1 "质疑的质疑"审查（必须先做）

在质疑方向之前，先问自己一个问题：**"我最怀疑的那个节点，真的用埋点验证过了吗？"**

| 审查项 | 若是 |
|--------|------|
| 怀疑度最高的节点是否尚未通过埋点验证？ | **暂缓质疑**，追加 1~2 处埋点 |
| 追加一轮埋点可能锁定？ | **暂缓质疑**，向用户说明进度 |
| 连续 Proceed 只是没看到修复效果？ | **暂缓质疑**，同步进展 |
| 三轮耗尽且以上均否？ | **通过审查**，进入步骤 5.2 |

### 5.2 三层递进质疑

**读 `<skill base directory>/references/direction-doubt.md`**，按文档中的三层七维度框架审视当前方向：

- **第一层·复现信号**：上下文缺失？环境差异？→ 问具体问题："本地 Node 版本是 18 还是 20？生产环境呢？"
- **第二层·理解偏差**：假设根因错误？修复路径误判？漏了装饰器/代理/中间件？→ "这段逻辑是否被缓存层或权限拦截器拦截过？"
- **第三层·系统性质疑**：架构缺陷？多 BUG 交织？全局状态污染？→ "这个模块是否被多个入口同时调用？"

### 5.3 假设前提确认

列出当前所有活跃的正确性假设（行为语言），调用 AskUserQuestion（multiSelect: true）让用户勾选哪些已不成立。被用户推翻的假设标记为废弃，作为后续分析的负向约束。

### 5.4 回退代码

**回退本次 BUG 过程中所有修改过的业务代码。** 使用 `git checkout -- {修改过的文件}` 或等价方式。同时清理所有埋点代码。

不带着上次的修改残骸进入新一轮分析。

**回退完成后禁止立即写新实现。** 这是最容易犯的错误——代码一回退就觉得"我知道哪错了，改一下试试"。连续失败已经证明你的理解模型有问题，不经反思直接重试只是新一轮试错。必须先完成 5.2 三层质疑和 5.3 假设确认，确定重启层级后，严格按 5.5 分层重启的指引行动。

### 5.5 分层重启

**读 `<skill base directory>/references/restart-strategy.md`**，按文档中的分层策略匹配重启力度：

- **信号层问题**（仅涉及上下文/环境）→ 等用户回复补充信息，继续埋点分析，不重新静态分析。可选增加 1~2 处针对性埋点。
- **理解层问题**（假设错误或路径误判）→ 废弃被推翻假设，基于已有调用链重建，保留调用链和缓存。回第三步重新制定首轮埋点。
- **系统层问题**（架构缺陷或多 BUG 交织）→ **必须先向用户确认"这需要推翻重来，之前分析基本作废，预计额外 2~3 轮对话。是否继续？"**。保留环境缓存，其余重新来过，回第一步。**系统层重启最多 1 次。**

### 5.6 重启后验证

任何层级重启后必须逐项检查：

| 检查项 | 不通过的处理 |
|--------|-------------|
| 保留的调用链是否与新信息矛盾？ | 升级为理解层重启 |
| 保留的假设是否与新确认的业务规则矛盾？ | 升级为理解层重启 |
| 环境缓存是否与新环境信息矛盾？ | 修正缓存，不升级层级 |
| 新事实是否指向更根本的架构问题？ | 升级为系统层重启 |

若升级到系统层且已执行过一次系统层重启 → 不执行，走退出流程。

### 退出条件

系统层重启已执行 1 次再次触发，或用户明确拒绝系统层重启 → 输出最终建议（拆分隔离测试、引入更高级调试工具、架构评审），记录未定位根因的模块和已排除方向作为负向约束。

### → 【用户交互】

执行「用户交互」章节定义的 Proceed / Mark Fixed 流程。
