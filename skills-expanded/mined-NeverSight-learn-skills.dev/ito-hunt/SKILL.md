# ito-hunt：假設驅動除錯診斷

## 概覽

從 error message 出發，用假設驅動的方式找到 root cause，再決定後續行動（直接修復或開 GitHub issue）。核心原則：沒有可測試的假設，不動任何程式碼。

## 使用時機

- 使用者貼出 error message、exception、stack trace、crash 日誌
- 使用者說「報錯了」、「有錯誤訊息」並提供具體錯誤內容
- 使用者問「這個 error 是什麼意思」且附上錯誤訊息

**不應使用的情況：** 需要直接修改程式碼、需要寫新功能、需要 code review。

## 核心流程

### 步驟 1：觸發前置檢查

確認使用者有提供 error message 或 stack trace。

若無，引導使用者提供錯誤資訊，不開始診斷：

```
看起來有問題，請提供完整的 error message 或 stack trace，才能追查 root cause。可以從 console、terminal 輸出或日誌中找到。
```

使用者提供後，進入步驟 2。

### 步驟 2：假設驅動診斷

**提假設前的強制格式：**

> 我認為 root cause 是 [X]，因為 [具體證據]。

沒有這句話不得提假設，沒有假設不得建議任何變更。

**診斷規則：**

1. 一次只驗證一個假設
2. 找到反證後立刻完全拋棄該假設，不保留、不修改
3. Stack trace 指向外部函式庫或 node_modules → 先回溯到自己的程式碼（往上走約 3 個呼叫層），bug 幾乎都在那裡，不在依賴本身挖
4. 不從記憶中說出版本、函式名、檔案位置，先跑工具驗證

假設通過驗證後，進入步驟 4。若連續三次假設均被反證，強制進入步驟 3。

### 步驟 3：三次假設失敗 → 強制 Handoff

三次假設都被反證後，強制停下並輸出以下格式，不再猜測：

```
已測假設：
1. [假設 1] → [測試方法] → [結果：排除原因]
2. [假設 2] → [測試方法] → [結果：排除原因]
3. [假設 3] → [測試方法] → [結果：排除原因]

已收集證據：
- [日誌 / stack trace / 環境資訊]

已排除：
- [排除的 root cause]

未知項：
- [仍不清楚的部分]

建議下一步：
1. [下一個調查方向]
2. [需要使用者提供的資訊]
```

狀態：**受阻**

### 步驟 4：診斷成功輸出

假設通過驗證後，輸出：

```
root cause：[一句話，含 file:line]
證據：    [驗證假設的具體依據]
影響範圍：[檔案數 / 模組 / 影響面描述]
推薦行動：[見步驟 5]
```

### 步驟 5：影響範圍評估與行動推薦

根據以下因素評估影響範圍（自行判斷，無硬閾值）：
- 影響檔案數
- 是否涉及架構層面的改動
- 是否有對外介面合約變動

輸出推薦行動，使用者可覆蓋：

```
推薦行動：
A. 直接修復 ← 適合影響範圍小、邊界清楚的修復
B. 開 GitHub issue ← 適合影響範圍大、需要討論或排期的問題
請選擇（A/B）或告訴我你的想法：
```

### 步驟 6：Issue 路徑

使用者選 B 時，用繁體中文模板建立 GitHub issue：

```markdown
## 發生了什麼

## 預期行為

## 重現步驟
1. [第一步]
2. [第二步]

## 補充資訊
root cause 診斷：[步驟 4 的輸出]
```

執行 `gh issue create` 自動建立並回傳 URL。

`gh` 不可用或無 GitHub remote 時，存至本地：
`docs/ito-temp/issues/[issue-title].md`

## 常見合理化藉口

| 合理化藉口 | 實際情況 |
|-----------|---------|
| 「我來試試這個」 | 沒有假設，在亂猜，停下先寫假設 |
| 「我很確定是 X」 | 信心不是證據，跑一個能證明的工具再說 |
| 「大概跟之前那個一樣」 | 拿舊模式套新症狀，從頭重讀執行路徑 |
| 「重啟一下應該就好」 | 在逃避 error message，把最後一條 error 逐字讀完 |
| 「這個部分不重要」 | 主動迴避的地方往往是問題所在，重點檢查 |
| 「error 很明顯，不需要先提假設」 | 明顯的 error 也可能是症狀，不是 root cause，跳過假設會修到錯的地方 |
| 「函式庫的 stack trace 指出問題在依賴本身」 | 依賴本身極少出 bug，問題幾乎都在自己呼叫它的方式 |
| 「再試幾個假設應該就找到了」 | 三次失敗代表需要更多資訊，不是多猜幾次就能解決 |

## 警訊

- 提假設前沒有「我認為 root cause 是...因為...」
- Stack trace 指向 node_modules 卻直接在依賴裡找原因
- 三次失敗後繼續提第四個假設
- 影響範圍評估沒有列出判斷依據
- Issue 模板用英文填寫

## 驗證

- [ ] 有 error message 或 stack trace 才開始診斷
- [ ] 每個假設都有明確的測試方法和結果
- [ ] root cause 輸出含 file:line（可查驗，非泛稱）
- [ ] 推薦行動有影響範圍評估依據
- [ ] Issue 路徑：URL 已回傳或本地檔案已存

## 不在範圍內

- 修改程式碼
- git bisect
- MCP tool 失敗的處理
- 沒有 error message 的模糊問題描述
