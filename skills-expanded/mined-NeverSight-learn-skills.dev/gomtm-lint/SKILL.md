---
name: gomtm-lint
description: 程序源码规格化,让项目的源码符合项目要求.
---

随着项目的推荐以及反复多次的重构和迭代升级,项目的源码可能出现不规范进而影响后续的开发的效率和正确性.

完成源码规格化后应当确保不改变原本程序的逻辑, 不增加新功能,不删除已有功能, 不改变程序逻辑.

## 检查清单

### gomtm / 大仓补充

- [ ] 当已接入 GitNexus 的大仓做“规格化”前，先对准备修改的函数/方法做 impact 分析。
- [ ] 优先做“行为等价”的收敛：删除重复判断、抽出重复接口类型、减少匿名接口噪音、按语义集中小型辅助类型；不要在规格化任务里顺手改路由语义或启动流程。
- [ ] 若刚完成拆文件/移动函数且尚未重建 GitNexus 索引，`impact` / `context` 可能仍指向历史文件路径，或找不到本轮新拆出的叶子辅助函数；此时应结合当前源码与实际 diff 判断，避免被旧索引误导，也不要因为新 helper 尚未入索引就阻塞本轮行为等价规格化。
- [ ] 若候选点只是私有布尔指针 helper（如 `boolPtr(true)` 这类仅服务默认值装配的薄封装），优先收窄成语义更直接的 helper（如 `truePtr()`）或局部变量；但先确认没有其他非 `true` 调用点，再统一更新同文件剩余引用，避免留下真实编译错误。
- [ ] LOW 风险也不等于无风险：若 `impact` 落在运行时装配链、代理链、`Start` / `ResolveRuntimeSpec` 一类活跃流程上，纯规格化只做局部实现整理（early-continue、容量预分配、空值过滤、薄 helper 收窄）；若位于 installer / 本地工具安装链路，则只做重复 map 初始化、局部条件合并、`+=` 风格字符串拼接这类收敛，不要顺手改变路径拼接、环境变量语义、安装命令、下载 URL、重试策略或启动参数行为。
- [ ] installer helper 即使 `impact` = LOW，也要按“活跃流程上的局部整理”对待：可改 `settings := make(map[string]any)` 一类重复初始化、多个 `return true` 分支合并、固定字符串匹配整理；不可改 skip 判定语义、配置键名、真实外部副作用边界。
- [ ] 当一次纯规格化把通用 helper 改成更窄语义 helper 后，立即在同文件搜索剩余旧引用并重新编译；这类错误常不是 patch 工具的假失败，而是本轮改动引入的真实编译回归。
- [ ] 若只是做行为等价的顺序调整或局部去重，`gitnexus_detect_changes` 可能把同文件邻近符号、局部变量，甚至历史上已删除的 helper 继续标成 `touched`；应结合 `git diff` 与当前源码复核真实改动，再判断是否异常。
- [ ] 如果仓内不存在某个外部项目常见验证脚本（例如 `scripts/run_tests.sh`），不要假定它存在；应先检查真实仓库，再退回到该仓当前可用的最小相关验证命令，并在汇报里明确说明。
### 源码组织

- [ ] 文件名符合变成语言的规范.
- [ ] 文件名符合功能实现.
- [ ] 单个文件函数不应超过1000行, 对于大文件,应当分割为多个文件.
- [ ] 避免碎片化文件, 例如只有几行源码的源码文件,应合并到更加合适的地方. (常量,配置之类的除外)

### 消除多余源码

- [ ] 多余的变量定义.
- [ ] 多余的变量赋值和变量传递.
- [ ] 结构体或者类中多余的字段定义.

### 就近原则

- [ ] 根据函数的调用关系,顺序,依赖关系,尽可能写在一起.

### 适合人类阅读

- [ ] 源码的实现应当符合人类的阅读习惯.
