# Git 提交信息

根据用户提供的事实和目标仓库约定生成提交信息，不把某个仓库的语言、类型或标点格式硬编码到其他项目。

## 输入模式

- **用户直接提供内容**：用户提供现有提交信息、改动摘要、需求描述或 diff 时，以这些内容作为事实来源。只要求改写或校验措辞时，不强制访问 Git 仓库；没有仓库不是阻塞条件。
- **当前仓库改动**：用户要求根据当前工作区生成提交信息时，检查暂存区、工作区和相关未跟踪文件。存在暂存内容时，以暂存区作为默认提交范围。
- **上一条提交**：用户要求修改上一条提交信息时，检查 `HEAD` 的提交信息与实际差异，确保新消息准确覆盖该提交。

## 工作流

1. 先判断输入模式和事实范围。用户已提供足够内容时直接使用；需要检查仓库时，使用 `git rev-parse --show-toplevel` 确认仓库根目录。
2. 需要匹配目标仓库习惯时，读取 `AGENTS.md`、`CONTRIBUTING.md`、提交规范或同类说明，并使用 `git log -30 --no-merges --format=%s` 检查稳定的近期历史。
3. 当前仓库模式下，检查 `git status --short`、暂存区差异、工作区差异和相关未跟踪文件；上一条提交模式下，检查 `git show --stat --patch HEAD`。
4. 概括主要改动结果。若内容包含互不相关的多个目的，建议拆分提交。
5. 按“用户对当前结果的明确要求 → 仓库书面规则 → 稳定的近期历史 → 通用回退格式”的优先级确定语言和格式。仓库规则和历史只补充用户未指定的部分。
6. 对照选定的事实来源复核提交信息，避免描述未发生的改动。

只有在当前仓库模式下确认没有可提交改动时，才说明当前没有可生成提交信息的变更。用户已经提供现有消息、摘要或 diff 时，继续完成改写或校验，不因本地仓库为空或不可用而拒绝。

## 类型选择

用户未指定类型时，优先沿用仓库书面规范或稳定历史中的类型。两者均不可用时，从以下常见类型中选择：

- `feat`：新增用户可见能力。
- `fix`：修复缺陷或错误行为。
- `refactor`：不改变预期行为的结构调整。
- `perf`：性能优化。
- `test`：新增或调整测试。
- `docs`：仅修改文档或注释说明。
- `build`：构建系统或依赖调整。
- `ci`：持续集成配置调整。
- `chore`：不属于以上类别的维护工作。
- `revert`：撤销已有提交。

仅当用户明确指定，或仓库历史和规范已有依据时，才使用自定义类型（如 `data`）。按主要改动意图选择类型，不按修改文件数量选择。

## 编写要求

- 描述改动带来的结果，不罗列文件名或实现步骤。
- 保持简洁、具体，使读者无需查看差异也能理解主要目的。
- 用户未指定语言时，根据仓库规则和历史选择；没有仓库依据时，沿用用户输入语言。
- 用户未指定 scope 时，仅在仓库惯例明确或 scope 能有效区分模块时添加。
- 用户未指定分隔格式时，遵循仓库现有的冒号后空格习惯；无法判断时回退为 `type: summary`。
- 标题末尾通常不加句号；只有需要解释动机、迁移方式或兼容影响时才添加正文，并在标题后留一个空行。
- 没有证据时，不添加 issue 编号、破坏性变更标记、测试结果、共同作者或签名。
- 用户指定了语言、类型、scope、大小写、空格或标点时按其要求编写；仓库规则和历史仅用于用户未指定的部分。

## 示例

好的提交信息描述结果，不罗列文件名或实现步骤：

```
fix: 修复日期解析在闰年时溢出
```

差的提交信息：罗列改动步骤，读者需查看 diff 才能理解：

```
fix: 修改 parseDate 函数，增加了对二月的判断，改了两处 if 条件，把 day 的校验挪到了前面
```

> 示例为示意写法，具体语言、类型和格式以用户要求及目标仓库约定为准。

## 输出方式

- 用户只要求一个提交信息时，仅输出推荐结果，并使用代码格式方便复制。
- 用户要求多个方案时，最多给出三个候选，并简短说明差异。
- 用户要求校验现有提交信息时，先给出通过或不通过，再给出最小修改版本。

## 操作边界

- 默认只生成或校验提交信息，不执行 `git add`、`git commit`、`git commit --amend` 或 `git push`。
- 仅在用户明确要求执行 Git 操作时才执行相应命令。
- 实际提交前遵循仓库要求检查差异并运行必要验证；提交后核对 `HEAD` 和工作区状态。
- 除非用户明确要求推送，否则只创建本地提交。
