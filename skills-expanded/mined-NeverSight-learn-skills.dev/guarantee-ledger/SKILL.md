# Guarantee Ledger — 保証台帳

保証台帳とは、壊してはいけない約束を一枚の人間可読な文書に宣言し、その約束を裏付ける実装とテストへ索引を張る仕組みである。外部から観測できる面（HTTP API・CLI 出力・スケジューラ・Webhook・画面等）ごとに整理する。

## ① 目的と責務分割

台帳が持つのは「壊してはいけない約束の宣言」と「その約束を担う実装・裏付けテストへの索引」だけである。

その面にインターフェース定義（OpenAPI・CLI のヘルプ・型定義等）があるなら、それが形の正本である。次の文がその面と台帳の関係を定める。

> その面にインターフェース定義があるなら、それが形の正本である。台帳はそれを読んでも分からない振る舞いだけを持つ。

path・HTTP method・フィールド名と型のような、形の正本を読めば分かることは台帳に載せない。台帳が持つのは、正本を読んでも分からない振る舞い（条件分岐・副作用・エラー語彙の安定性等）である。

形の正本が存在しない面（バッチ処理等）では、載せる／載せないの線が消えて台帳が何でも入る箱になる。この場合は次のいずれかを選ぶ。

1. 先に形の正本を作る
2. その面を台帳の対象外とする

### 出自ルール

保証を台帳へ載せる根拠は、実装とテストの存在ではない。

> 保証は、指示・判断の出来事へ遡れるものだけを載せる。実装とテストが存在しても、遡れなければ載せない。実装が指示の隙間を埋めた振る舞いは、正しく動いていても保証ではない。

実装から拾うと、エージェントが指示されずに決めた振る舞いが契約へ昇格し、誤りを台帳が守る側へ回してしまう。

### 復元の天井

実装とテストを事後に棚卸しして保証を起こす手順（初回棚卸し）を検討したくなることがあるが、それには天井がある。

> 事後棚卸しが復元できるのは、過去の判断がテストへ化石化した分までである。規範の新規宣言はやりとり（レビュー・設計判断）からしか来ない。迷ったら載せない。

## ② 表書式と面のセクション

台帳の表は 6 列とし、列順は次のとおりとする。

| 列 | 内容 |
|---|---|
| `ID` | 保証を一意に識別する連番 `G-###` |
| `保証` | 壊してはいけない観測可能な振る舞い |
| `対応実装` | 保証を担う実装ファイル。リポジトリルートからの相対パス。複数は `, ` 区切り |
| `裏付けテスト` | 保証を実証するテストへの索引 |
| `pin確認` | 保証を壊して裏付けテストが赤くなることを観測した証跡。空欄、または `YYYY-MM-DD <壊し方の散文>` |
| `出自` | 保証の根拠となる指示・判断の出来事。`<リポジトリルートからの相対パス>::<見出し>` |

書式の worked example は `fixtures/guarantees.md` を参照。

### 面のセクション

面ごとに表を分けてセクションを作る。

> 保証が生まれてからセクションを作る。空のセクションを先に置かない。保証 0 件の面は、セクションが存在しないことで表現される。

### 出自列の仕様

- 形式は `<リポジトリルートからの相対パス>::<見出し>` の一形式
- `::` は**最初の 1 つ**で分割する。見出しに `::` が含まれても壊れない
- 見出しに `|` を含むものは表セルを壊すため使えない
- PR やレビューでの裁定も、まず `.docs/reviews/` か `.docs/plans/` へ書いてから参照する

> 文書に残らないやりとりは保証にできない。

## ③ ID 体系

- ID は `G-###` の連番
- 欠番は再利用しない
- 保証をやめるときは行を削除せず `(retired: YYYY-MM-DD 理由)` を付けて残す

理由は「破棄した約束を削除すると、後から見たときに『そんな約束は最初から無かった』という履歴へ化ける」ためである。

### 退役提案（人間の判断待ち）

`(retired: ...)` は確定した退役を表す。エージェントが退役を提案し、人間が行ごとに判断する場合は、確定と区別できる最小形にする。

- `出自` 列にだけ `(retired: YYYY-MM-DD 理由)` を置く
- `保証`・`対応実装`・`裏付けテスト` は変更しない

keep と判断されたら `出自` セルを裁定文書の該当節へ書き換えるだけで戻る。裏付けテストはこの提案では撤回されないため、失われるのは「台帳上の約束」という地位だけである。checker の挙動は確定退役と変わらない（⑨参照）。

### 並行採番の衝突

複数ブランチが並行して `G-###` を採番すると衝突する。rebase 後に台帳全体の G-ID 重複と単調増加を確認し、`main` に存在する ID を保持したまま、自ブランチで追加した衝突 ID だけを現在の最大 ID の次から繰り下げる。繰り下げ後も単調増加させ、空いたように見える番号を再利用しない。

## ④ 載せる／載せないの二段の門

| 段 | 判定 |
|---|---|
| 第 1 門（出自） | ユーザー指示・設計文書の決定・レビュー裁定・PR rubric のいずれかへ遡れるか。遡れなければ載せない |
| 第 2 門（書き方） | 条件分岐の振る舞い／検証の網羅性／副作用の有無・冪等性／エラーコード語彙の安定性／存在秘匿・テナント分離 |

載せないもの: 形の正本が持つ内容（path・HTTP method・フィールド名と型・単純なステータスコード一覧）、内部実装。

> 実装もテストも存在するのに指示へ遡れないものは載せない。

### 昇格経路

> 観測は昇格させない。裁定が昇格させる。中間の振る舞いを保証したければ、まず判断の出来事を作る（レビューで裁定する / 設計文書へ決定として書く）。それから台帳へ載せる。

CLI や画面に固有の判定基準はここでは定めない。上記は原則であり、面ごとの具体的な判定基準を新たに発明しない。

## ⑤ テスト索引形式

- 索引は `<ファイル名>::<describe>` または `<ファイル名>::<describe> > <it>`
- 複数テストが 1 保証を裏付けるなら `describe` 単位で束ねる
- 1 索引で保証全体を裏付けられないなら、保証そのものを分割する
- 索引に件数・行番号など変動する値を書かない。正しいテスト追加のたびに台帳が陳腐化するため

## ⑥ 必須フィールド

`対応実装`・`裏付けテスト`・`出自` は必須である。空欄と不在パスは checker が `BROKEN` とする。

「約束したいがテストが無い」振る舞いは台帳へ載せず、Action へ積む。検出結果を握りつぶさない。

## ⑦ pin 確認の意味と限界

`pin確認` は、保証を意図的に壊して裏付けテストが赤くなることを観測した証跡である。`YYYY-MM-DD <壊し方の散文>` を記録し、mutation patch 自体は保存しない。

> pin 確認が示すのは、その 1 つの壊し方を裏付けテストが検出できることまでであり、保証の実効性全体を証明するものではない。

実施手順は `guarantee-pin-check` スキルを使う。

## ⑧ 導入手順

1. `scripts/check-guarantees.sh` と `scripts/check-guarantee-cochange.sh` を **`<リポジトリルート>/scripts/`** へコピーし、既定値（`check-guarantees.sh` は `LEDGER` / `TEST_DIR`、`check-guarantee-cochange.sh` は `LEDGER` / `BASE_REF`）をプロジェクトの実パスへ書き換える。両スクリプトは `ROOT` を自身の置き場所（`$(cd "$script_dir/.." && pwd -P)`）から導出しており、`<リポジトリルート>/scripts/` の 1 階層下に置かないと台帳のパス解決がずれる
2. 台帳を空で開始する。または指示の情報源（`.docs/plans` の決定・PR rubric・レビュー裁定・risk-registry）から起こす
3. プロジェクトの `CLAUDE.md` / `AGENTS.md` へ追記トリガーを 1 行加える
4. PR 前チェックへ checker を配線し、exit code 契約（⑨参照）を明記する

> 実装とテストを掃いて保証を起こす手順（初回棚卸し）は行わない。台帳が空であることは「まだ何も約束していない」という正しい状態を表す。

### 既存台帳を出自ルールへ移行する場合

出自ルールより前に作られた台帳には、定義上どの行も出自が無い。移行の作業は「出自を探す」ではなく「**今ここで裁定し直す**」である。過去の実装から出自を後付けで構成すると、出自ルールが防ごうとしているもの（実装が決めた振る舞いの契約化）を別ルートで再現する。

1. 裁定文書を 1 本起こし、既存行を読み返して判断する
2. 各行を 3 分類へ振り分ける — **A**: 元の裁定がリポ内に実在する（その文書を指す）／ **B**: 元の裁定は無いが再裁定して維持する（裁定文書の該当節を指す）／ **C**: 出自へ遡れず維持しない（退役を**提案**する。③参照）
3. C の確定は人間が行ごとに決める。エージェントは提案に留める
4. **日付を遡らせない。** 遡及付与した出自は遡及した日付を持つ
5. checker への出自検査の追加と、既存行への出自付与は**同一のコミット群**に含める。分けると、その間 checker が全行を `BROKEN` と判定して赤くなる期間が生まれる

PR のマージが判断の出来事になる。裁定文書はその出自として機能する。

> この節は manako で 1 回実施した移行（2026-08-17、有効 26 行）から起こしたものであり、n=1 である。

## ⑨ 機械検査の境界と移植限界

> 機械はポインタの健全性を検査する。意味は人間が検査する。テストは pin が検査する。

checker が検査すること:

- 対応実装・裏付けテスト・出自の実在
- テスト索引の `describe` / `it` 宣言の実在
- pin 確認の日付形式

`(retired:` を含む行は検査せずスキップする。**判定は行単位であり、その文字列がどの列にあるかを問わない。** ③の退役提案（`出自` 列にだけ置く最小形）が確定退役と同じように扱われるのはこのためである。

### 意図的に検査しないこと

| 検査しないこと | 理由 |
|---|---|
| 出自の見出しの実在 | 形式検査を意味検査と誤認させるため。もっともらしい見出しを指していれば通る |
| `describe` と `it` の所属関係 | 同一ファイル内に独立に存在すれば通る |
| テストの中身が保証を実証しているか | pin 確認の担当 |
| 台帳の主張範囲（「12 endpoint」等）の被覆 | checker はポインタの実在しか見ない |

### 移植限界

- vitest 形式の `describe` / `it` / `test` 宣言をパースする前提
- テスト索引のファイル名部分にサブディレクトリを含められない
- ID は `G-` + 3 桁固定
- `check-guarantee-cochange.sh` は ROOT がリポジトリルートでないとき、追跡済みファイルの変更を検出できず `cochange_warn=0` を返す（silent no-op）。同梱 fixture に対する cochange の実行は、この理由により配線の確認にはならない
- 両スクリプトは `rg`（ripgrep）と `git` を必須とし、`check-guarantees.sh` は `realpath` にも依存する。bash 3.2（macOS 既定）で動作確認済み。`realpath` が無い環境では fail-closed に倒れるが、全行が「出自の形式が不正」と報告され、原因が読み取れない

### 出力形式

- 出力は最終行の `checked=N broken=N unpinned=N`
- `checked` は最後まで到達した行だけを数える（`BROKEN` になった行は含まない。したがって `checked + broken` は総行数にならない）
- `unpinned > 0` は exit 0 のままで PR をブロックしない。pin 未確認は正常にありうる状態であり、潰すときは `guarantee-pin-check` を使う

### exit code 契約

0 = 続行 ／ 2（cochange のみ）= WARN（PR をブロックしない）／ それ以外の非 0 = FAIL。

## ⑩ 段階 2 エージェント突合

台帳と実装を読み合わせ、差異を `missing` / `partial` / `contradicts` / `unrequested` へ分類する。`unrequested` は指示の中間で生まれた振る舞いの検出器である。**この段階はまだ一度も実行されていない。**

## ⑪ 効果判定 rubric

台帳へ保証を追加する PR で、出自が実際に記入され、その出自が既存の判断の出来事を指しているかを確認する。出自欄が「台帳更新のために作られただけの文書」を指すようになったら、形骸化と判定する。

判定は次に台帳へ保証を追加する PR のレビューで、レビュアーが行う。

## ⑫ `decision-test-chain` との境界

テスト注釈 → 設計見出しの一方通行で「注釈が付いたテスト＝意図的な仕様、注釈のないテスト＝たまたまそうなっている挙動」を判別する別機構が todoke で並走している。同じ判別線を逆向きに引いた実装であり、アドレス体系（`<path>::<見出し>`）も共有する。**機構は統合しない。** 合否判定が持ち越し中である。
