# Coco 交付验证

验证必须证明真实行为，而不只是命令退出码。Build 成功不能替代用户可见 UI、API、数据或权限行为验证。

完整流程使用本技能生成 `verification.md`。轻量流程按风险执行聚焦测试或可重复人工验证，并在最终回复中列出范围和结果，不强制创建 `verification.md`。

涉及 Server/API 时，使用 Apifox MCP 刷新并读取最新 OpenAPI 契约，将实际请求响应与路径、方法、参数、Schema、鉴权、状态码和错误模型逐项比对。若实现与 Apifox 不一致，结果不得标记 `Pass`，除非已确认 Apifox 契约本身需要变更。

## 验证层次

按改动风险选择并执行：

- 静态检查、类型检查、单元和整合测试。
- 数据库 Migration、约束、回滚或数据兼容检查。
- API Smoke/契约、错误码、认证和权限边界。
- 真实浏览器工作流、响应式状态、控制台和网络错误。
- 安全、并发、性能、可观测性和部署后健康检查。

对 UI 改动应实际启动应用并检查目标桌面/移动视口。引用截图、Trace 或日志时保留可定位路径和生成条件。

## 追踪

建立“需求故事/缺陷 -> 验收标准 -> 测试或步骤 -> 证据 -> 结果”的矩阵。结果只允许：

- `Pass`：实际执行且结果符合。
- `Fail`：实际执行但不符合。
- `Partial`：只验证部分范围。
- `Blocked`：环境或依赖阻止执行。
- `Not Applicable`：说明为何不适用。

受阻时记录具体 Blocker、已取得的最接近证据、未验证风险和后续任务，不得将其包装为通过。

## 团队验收检查点

- G3：开发者和审查人确认实现、测试和代码审查结果。
- G4：产品/验收责任人根据 `verification.md`、真实运行证据和残余风险确认验收；人工验证不能用 Build 成功替代。
- 若 Jira 有验收状态或评论要求，先准备映射和草稿；写回 Jira 需用户明确授权。
- 前端 API 变更必须核对接口调用清单与 Apifox 契约，验证路径、方法、参数、响应、错误码和权限；页面逻辑必须覆盖设计中确认的分支和状态。

## 产物

更新 `docs/plans/{Work-Item-Key}/verification.md`，包含环境、版本/提交、命令或操作、Apifox 契约版本/读取时间（如适用）、结果摘要、证据位置、失败/警告、未验证范围和回归结论。验证发现的新方向交给变更控制；发现实现偏差时先更新当前 Work Item，只有独立且需要单独跟踪的问题才建立关联缺陷。

最终对用户输出实际测试范围：测试场景、层级、命令/操作、覆盖模块、结果、证据和未测试范围。

创建或维护前读取 [verification-contract.md](references/verification-contract.md)。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
