# 完整页面共创

把开发者的想法和素材转化为可进入页面库的完整页面候选。由 Agent 负责需求澄清、设计对齐、实现和验证；开发者只需提供意图、素材并确认关键方案。

## 边界

- 适用于公共页面、方法页面、服务页面和其他可独立选择的完整报告页面。
- 适用于新增页面，也适用于基于现有页面迭代；不要要求开发者先填写技术任务单。
- 短期不建设或改造计划配置编辑器。若需求实际改变配置、`planPack`、历史报告兼容或数据契约，先停止并切换到项目公共能力或架构流程。
- 不处理单张行业实践案例卡；改用 `case-contribution`。
- 不执行开发仓或生产仓晋级；开发者确认后生成交接单并停止。负责人另行调用 `module-promote`。

## 开工

1. 先完整阅读开发者提供的文字、图片、文档、参考页面和入口上下文。不要边读边零散提问。
2. 定位项目仓库，先读最近的 `AGENTS.md`，再按其路由读取页面开发、架构、安全和本地开发权威文档。
3. 用 remote URL 和 `.spark/meta.json` 核实目标是开发仓；无法确认仓库身份时停止。
4. 检查现有页面库、已有页面分类、页面数据契约、渲染器和视觉规范。
5. 只复用项目已有分类。不要因为本次共创新增一套阶段或标签；分类确实不足时，把它作为负责人决策项。

## 澄清策略

从现有素材和代码可以判断的内容直接判断。只把会实质影响以下事项的问题集中为一轮提问：

- 页面要解决的用户问题和使用场景；
- 属于已有哪个页面分类、放在报告什么位置；
- 新增页面，还是基于哪个现有页面迭代；
- 必须复用的内容、素材或交互；
- 明确不能改变的范围。

入口已带入页面、位置或需求时，直接继承，不要再次让开发者选择。后续反馈只确认新增决策，不重复询问已回答内容。

## 先对齐方案，再编码

编码前输出一张简短的“页面开发方案卡”，使用 [页面方案与验收](references/page-plan-and-gates.md) 中的结构。方案必须让开发者能判断：做什么、放哪里、基于什么、最终如何验收。

等待开发者确认方案卡。确认前保持只读，不改代码。

## 开发闭环

1. 保留用户现有改动；需要隔离时使用安全的本地分支或工作树。
2. 按已确认方案实现最小完整切片，同时保持页面库元数据、渲染契约和默认报告组合一致。
3. 在本地提供真实可交互预览，不用静态占位图替代页面正文。
4. 单独做一次视觉检查：信息层级、正文可读性、图片裁切、页面比例、响应式和与既有报告风格的一致性。
5. 运行项目要求的工程检查；至少包含权威文档要求的 verify、测试、diff 检查，并按影响面补充构建和浏览器验收。
6. 开发者反馈修改时，在同一方案上下文中迭代；不要重新启动整套访谈。

开发仓在线检查只有在本轮得到明确发布授权后才能执行。没有授权时，把它标记为晋级阶段待办，不要把本地预览说成在线效果。

## 交付

开发者确认效果后，按参考文件生成一份简洁交接单，包含页面分类、实现方式、变更范围、预览、检查证据、素材处理和未决事项。随后停止，不自动调用 `module-promote`，不推送或发布生产仓。

## 立即停止

- 需要改变数据库、`planPack` 历史兼容、报告分享语义或页面编辑器；
- 无法确认开发仓身份；
- 质量门无法通过；
- 需要外部授权、开发仓发布或生产仓操作，但本轮没有明确授权；
- 开发者素材不足以确定页面目标或关键方案。
