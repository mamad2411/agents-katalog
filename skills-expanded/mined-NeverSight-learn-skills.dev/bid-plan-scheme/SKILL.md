# 方案规划

## 三级职责定位

本技能负责**规划**阶段——口径统一、风险预警、将策略落地为可执行的写作蓝图。不需要读招标原文，只读分析产物。

```
analyze-tender: 提取什么(facts) → 怎么评(scoring) → 怎么赢(strategy)
         ↓
plan-scheme: 口径 + 风险 + 将策略落地为写作蓝图  ← 你在这里
         ↓
write-solution: 按蓝图执行写作
```

---

前置检查：确认 `output/tender_facts.md`、`output/scoring_map.md`、`output/bid_strategy.md` 存在，否则提示先执行 `/bid-analyze-tender`。

---

## 步骤1：读取分析产物

并行读取：
- `output/tender_facts.md` — 项目基本信息、资质要求、技术要求
- `output/scoring_map.md` — 评分点详情（含 F1-F5 分类、需求矩阵、★项）
- `output/bid_strategy.md` — 本地化策略（ROI分析、得分空间、项目锚点、隐性需求、应答策略）

**项目规模判断**：根据 tender_facts 中的预算金额、项目周期、功能模块数判断：

| 规模 | 条件 | CHARS_PER_POINT |
|------|------|----------------|
| 小型 | 预算 < 100万 或 功能模块 < 5 | 2,000 |
| 中型（默认） | 预算 100-500万 或 功能模块 5-15 | 3,000 |
| 大型 | 预算 > 500万 或 功能模块 > 15 | 4,000 |

**禁用词行业适配**：根据 tender_facts.md 的行业分类、专业术语库和行业研究结论，在步骤10中判断：
- 哪些全局禁用词在本行业属于正当术语（如医疗行业的"精准度"、工程行业的"先进工艺"），列为豁免
- 本行业有哪些应避免的不当表述，列为行业特有禁用词

## 步骤2：生成 canon_current.md

> **Read** [init-canon.md](references/init-canon.md)

从 tender_facts + scoring_map + bid_strategy 三源生成全局口径文件。关键改进：scoring_map 中的量化指标（SLA、性能参数、服务承诺）是评分依据，必须纳入口径统一管理；bid_strategy 中的采购人特有表述和痛点关键词纳入「甲方习惯用语」分类，确保 write-solution 能使用甲方语言。

## 步骤3：生成 risk_alert.md

> **Read** [generate-risk-alert.md](references/generate-risk-alert.md)

从 tender_facts + scoring_map 双源评估废标风险。scoring_map 的★项和 F3/F4 合规性评分点提供额外风险信号。

## 步骤4：评分点聚类

> F1-F5 分类已由 bid-analyze-tender 完成（scoring_map.md 中的 `格式` 字段），直接使用。

将 F1/F2 评分点聚类为方案。聚类核心原则：**独立评分 = 独立方案**。

### 4.1 聚类规则（按优先级排序）

1. **独立评分项独立成方案**（最高优先级）：评分表中每个有独立分值和独立评分标准的评分项，无论是否在同一大类（如"技术部分"）下，都应成为一个独立方案。评标专家对每个评分项单独打分，合并为一个方案会导致评委无法快速定位对应内容。
2. **招标文件投标文件格式**：参考投标文件格式章节中的文件组成列表（如"技术方案""售后服务方案""优惠承诺"等），将对应评分点映射到对应文件。
3. **同一评分项内的子项归同一方案**：如果一个评分项包含多个子项（F1格式的①②③），这些子项归属同一方案，通过 H2/H3 层级区分。

### 4.2 方案命名

使用评分表中的**评分项原文名称**作为方案名称。不自行创造名称，不将多个独立评分项合并重命名为"技术方案""综合方案"等笼统名称。

> 示例：评分表列出"供货方案（15分）""质量保障措施（5分）""进度保障措施（5分）""应急保障方案（5分）"四个独立评分项 → 生成四个独立方案，分别命名为"供货方案""质量保障措施""进度保障措施""应急保障方案"。

## 步骤5：分配评分点归属

每个评分点有且仅有一个归属。先按格式分类（F3/F4/F5→不生成方案）→ 再按聚类规则（F1/F2→对应方案，独立评分项独立成方案）→ 确保无遗漏。

## 步骤6：生成目录草案（评标专家视角优化）

> 目录映射规则与满分策略框架见 [scoring-classification.md](references/scoring-classification.md)

### 6.1 固定章节骨架（硬约束）

每个方案的章节骨架固定为：

1. **第1章 方案概览**：强制存在，非计分章节
2. **第2章起为评分响应章节**：按评分标准原文关键词动态拆分多个 H2
3. **可选补充支撑章节**：0-2章，位于评分响应章节之后、最终论证章节之前
4. **最后一章 方案完整性与可行性论证**：强制存在，非计分章节

规则：

- `方案概览` 只承担导航、边界、关键承诺摘要，不承担评分点主体响应
- `方案完整性与可行性论证` 只做收束、映射、证明，不替代中间评分响应章节
- `可选补充支撑章节` 只做跨章节补强，不承担主评分响应职责

### 6.2 评分项与 H2 映射原则

> **独立评分项 = 独立方案；每个评分项 = 该方案的目录域。**

评标专家先按评分项找内容，再在评分项内部按关键词定位细分章节。因此：

- 独立评分项不得跨方案合并
- 同一评分项内允许拆分多个 H2
- H2 颗粒度优先采用 **评审关键词颗粒度**
- 每个 H2 只负责一个关键词维度簇，不跨评分项
- 概览章、补充支撑章、最终论证章不参与评分点拆分

**动态拆分规则**：

1. 从评分标准原文提取并列关键词组
2. 以并列关键词组作为 H2 切分依据
3. 同一语义簇允许合并为一个 H2（如“联系电话/地点/组织”）
4. 强检索词或强证据词优先独立成 H2（如“运输保障控制”“质量问题处理时限”）
5. 若评分标准只有 1 个核心维度，允许仅生成 1 个评分响应 H2

### 6.3 H2 标题命名

> **标题直接复刻评分标准原文关键词**，不改写、不美化。评标专家做关键词匹配，标题越贴近原文匹配越快。

命名公式：`H2 标题 = [评分标准核心名词] + [章节聚焦维度关键词]`，两部分都必须溯源到评分标准原文。当单个评分项拆为多个 H2 时，各章标题通过不同的"聚焦维度关键词"区分，让评标专家扫描目录即可定位。详见 [scoring-classification.md](references/scoring-classification.md) 2.2 节的命名公式、对比示例和关键词覆盖校验。

### 6.4 章节排序

按评标专家注意力优先级排序：
1. `第1章 方案概览` 固定排首位
2. 评分响应章节按评分权重和关键词检索优先级排序
3. 可选补充支撑章节排在评分响应章节之后
4. `方案完整性与可行性论证` 固定排末尾

### 6.5 F2 满分策略 + 扣分陷阱

对每个 F2 评分点，结合 bid_strategy.md 的「得分空间分析」和「应答策略矩阵」，生成：

**满分策略**（3-5 个客观可验证要素）：
- 从评分标准"优秀"档提取可量化或可判断的维度
- 每个要素标注"怎么做 + 产出什么"
- 融入 bid_strategy 的差异化锚定方向

**扣分陷阱**（2-3 个常见失分点）：
- 通用化、指标空转、关键词缺失、篇幅不足等

### 6.6 评审对照索引（章节级粒度）

为每个方案生成评审对照索引表，**粒度为一个 H2 章节一行**（而非一个评分点一行）。

表结构：评分项 → 分值 → 对应章节 → 是否主响应章 → 辅助支撑章节 → 本章响应的评分维度 → 评分标准摘要（本章相关部分） → 满分策略。

**关键规则**：
- `对应章节` 填具体章节编号和标题（如"第3章 运输保障控制"），**禁止填"全文"**
- `是否主响应章` 仅对评分响应章节标记为“是”；概览章、补充支撑章、最终论证章只能作为辅助支撑出现
- `辅助支撑章节` 可填写方案概览/补充支撑/最终论证章节，但这些章节不得成为某评分项的唯一响应位置
- `本章响应的评分维度` 填该章节聚焦的评分标准关键词组，须与章节作战清单的「评分维度标签」一致
- `评分标准摘要` 仅摘录与本章相关的部分（50-100字），不重复整条标准
- write-solution 不回读 scoring_map.md，此表是写作引擎对照评分标准的唯一依据，细化到章节级后可生成精确的响应索引表

### 6.7 完整性校验

每个 F1/F2 评分点及其子项/关键词都有对应章节。

## 步骤7：融入本地化策略

将 bid_strategy.md 的洞察织入作战清单和写作指导：

| 策略来源 | 融入位置 |
|---------|---------|
| 项目特异性锚点 | 章节作战清单的「项目锚点」列 |
| 应答策略矩阵 | 各方案的「差异化定位」 + 满分策略补充 |
| 隐性需求 | 各章节的覆盖要求补充 |
| ROI 分析 | 影响篇幅分配权重（高 ROI 评分点可获得额外篇幅系数） |
| 得分空间分析 | 满分策略的具体突破动作 |

每个 H2 的作战清单必须有「项目锚点」——至少 1 个来自 bid_strategy 的项目特异性细节，write-solution 写作时必须体现。

**锚点充足性检查**：统计 bid_strategy.md 提供的锚点数量与 `方案概览 + 全部评分响应H2 + 补充支撑H2` 的数量。如果锚点数不足，从 tender_facts.md 的技术要求和商务条件中补充提取项目特异性细节（如具体功能模块名、性能指标值、特定接口对象名称），确保每个需承载项目理解的章节都有至少 1 个锚点可用。

## 步骤8：计算篇幅配额

> **Read** [budget-calculation.md](references/budget-calculation.md)

**动态预算公式**：

```
scheme_budget = max(8000, min(60000, 域评分点总分值 × CHARS_PER_POINT + 3000))
```

- CHARS_PER_POINT 由项目规模决定（见步骤1）
- 方案概览固定预留：small `800` / medium `1200` / large `1500`
- 最终论证章节固定预留 `600`
- 可选补充支撑章节每章默认预留方案总预算的 `5%-8%`，最多 `2` 章；未触发时预算回流到评分响应章节

**评分响应H2预算按维度权重分配**（不均分）：
```
评分响应章节池 = 方案总预算 - 概览预留 - 最终论证预留 - 补充支撑章节预留总额
H2预算 = 评分响应章节池 × (该H2维度权重 / 所有评分响应H2维度权重之和)
```

维度权重：
- 强检索/强证据维度：`1.2`
- 常规主维度：`1.0`
- 收束型维度：`0.8`

## 步骤9：生成写作指导块

> **关键**：plan_budget.md 是写作引擎的**唯一蓝图**。写作引擎从此文件获取角色、边界、目录、预算等全部信息。

为每个方案生成以下写作指导信息（根据招标文件和评分标准动态推导）：

### 9.1 角色定位（必填，2-3句话）

根据方案类型和评分标准推导写作角色。

### 9.2 方案边界（必填）

明确本方案覆盖范围和**不写**的内容（防止方案间重复）。

### 9.3 差异化定位（必填，2-3句话）

来自 bid_strategy.md 的应答策略，明确本方案应突出什么能力、回避什么方向、如何用项目特征锚定差异化。

### 9.4 域特有检查项（选填，3-5条）

从评分标准的"优秀档"要求推导本方案的特殊质量检查点。

## 步骤10：生成 plan_budget.md

> **Read** [plan-budget-template.md](references/plan-budget-template.md)

按模板输出 `output/plan_budget.md`，每个方案的目录草案必须包含：
1. **写作指导块**（角色定位 + 方案边界 + 差异化定位 + 域特有检查项）
2. 评审对照索引
3. 目录结构
4. 章节作战清单（含项目锚点列 + 字数预算列）
5. 方案清单、评分点归属表（含评分档次详情）、非方案评分点、人工审核清单

每个方案的目录结构必须明确区分：

- `第1章 方案概览`
- `评分响应章`
- `可选补充支撑章`
- `最后一章 方案完整性与可行性论证`
