# 🔧 Git Commit Message 与工时报告生成器

你正在执行 `git-commit-and-workhour-report` 技能。该技能有两种运行模式，根据用户意图自动判断：

- **模式 A — Commit Message 生成**：为当前工作区的未提交改动（staged 或 unstaged）生成规范的 commit message，并附带逐条工时预估。
- **模式 B — Work Report 生成**：根据指定分支或时间段的已有 commit 记录，生成一份含工时评估的完整工作报告。

---

## 1. 前置校验

在执行任何操作之前，必须先确认：

### 1.1 项目定位
- 确认当前工作区是一个有效的 Git 仓库（检查 `.git` 目录是否存在）。
- 如果用户有多个工作区项目，且用户未在 prompt 中指定目标项目，则必须中断并询问用户明确目标。

### 1.2 模式判断
- 用户提到"commit message"、"提交信息"、"帮我写提交" → **模式 A**
- 用户提到"work report"、"工作报告"、"工时报告"、"统计工时"、"报告" → **模式 B**
- 如果模式不明确，询问用户。

### 1.3 模式 B 额外校验
对于 Work Report 模式，以下参数**必须**明确，缺少时必须中断并询问用户：
- **目标分支**（必填）：要统计的分支名（如 `story-lark3181`）
- **对比基准分支**（必填）：用于计算差异提交的基准分支（如 `master`、`mplm-260629`）。未指定时**必须中断并询问**。
- **时间范围**（可选）：如 "本周"、"上周"、"7月1日到7月5日"
- **作者过滤**（可选）：指定提交者

💬 缺少对比分支时的中断提示：
> "为了生成准确的工作报告，请补充**对比基准分支**（如 `master` 或 `mplm-260629`），我需要知道和哪个分支对比来提取独有提交。如需限定时间范围或筛选提交者也请一并告知。"

## 2. 模式 A — Commit Message 生成

### 2.1 数据采集

按以下顺序采集变更：

```bash
# 1. 检查暂存区是否有变更
git diff --cached --stat

# 2. 检查工作区是否有变更
git diff --stat

# 3. 获取具体的 diff 内容（优先暂存区，没有则取工作区）
git diff --cached    # 暂存区
git diff             # 工作区
```

如果暂存区和工作区都有变更，以暂存区的变更为优先（因为用户通常已经 `git add` 了想提交的内容），但也要在输出中提示"工作区还有 X 个文件的变更未暂存"。

如果两者都没有变更，提示用户"当前没有可提交的变更"并终止。

### 2.2 Diff 分析策略

为每个变更文件执行 diff 分析：
- 如果单文件 diff 行数 < 300 行，直接读取完整 diff
- 如果单文件 diff 行数 ≥ 300 行，使用 `git diff --stat` 获取概要，再用 `git diff <file> | head -200` 获取局部 diff 以理解改动意图，避免 token 浪费

### 2.3 Commit Message 格式

生成的 commit message 必须遵循以下格式：

```
<type>(<scope>): <简洁中文描述>    合计工时: X.Xh

- <改动点 1 的具体描述>    <工时>h
- <改动点 2 的具体描述>    <工时>h
- <改动点 3 的具体描述>    <工时>h
```

**type 类型说明**：
| type | 含义 |
|------|------|
| feat | 新功能 |
| fix | 缺陷修复 |
| refactor | 重构（不改变外部行为） |
| style | 样式/格式调整（不影响逻辑） |
| perf | 性能优化 |
| docs | 文档变更 |
| chore | 构建/工具/配置变更 |

**scope 说明**：
- 从变更文件的路径 and 业务上下文中提取，使用中文简写
- 例如：`打样2.0`、`工业移交`、`产品样册`、`基础数据`

**工时格式**：
- 最小粒度 0.1h
- 每条改动点独立标注工时
- 第一行标题行标注「合计工时」，值为所有改动点工时之和

### 2.4 工时预估模型

工时预估基于以下四个维度综合评判，口径为 **需求理解 + 编码 + 自测**，若涉及接口变动则额外计入联调时间：

#### 维度 1：代码变更量
| 变更规模 | 行数范围 | 基准工时 |
|----------|----------|----------|
| 微型 | 1-10 行 | 0.1-0.2h |
| 小型 | 11-30 行 | 0.2-0.5h |
| 中型 | 31-80 行 | 0.5-1.0h |
| 大型 | 81-200 行 | 1.0-2.0h |
| 超大型 | 200+ 行 | 2.0h+ |

#### 维度 2：改动复杂度
根据改动内容的技术复杂度调整系数：
- **低复杂度**（×0.8）：纯 UI 文案/样式调整、添加 ref 引用、简单的 disabled 条件修改
- **中复杂度**（×1.0）：组件属性/接口切换、表单校验逻辑、计算属性修改
- **高复杂度**（×1.3）：异步流程改造、状态快照/恢复机制、弹窗交互链路、新增完整业务组件
- **极高复杂度**（×1.6）：跨组件/跨模块联动、工作流节点逻辑、全新业务流程开发

#### 维度 3：影响范围
- **单文件局部改动**（×0.9）：修改集中在单个文件的少数几处
- **单文件大范围改动**（×1.0）：单个文件内多处散落修改
- **跨文件改动**（×1.2）：涉及 2-3 个文件的协调修改
- **跨模块改动**（×1.4）：涉及 API / 组件 / 页面 / 工具函数等多层

#### 维度 4：调试联调成本
- **无需联调**（+0h）：纯前端 UI 调整
- **轻度自测**（+0.1-0.2h）：需要在页面上验证交互效果
- **接口联调**（+0.3-0.5h）：涉及后端接口变动，需要联调验证数据流
- **复杂场景联调**（+0.5-1.0h）：涉及多角色审批、流程流转等业务场景测试

**工时计算公式**：
```
单条工时 = 基准工时 × 复杂度系数 × 影响范围系数 + 联调成本
```

最终结果四舍五入到 0.1h。

### 2.5 输出示例

```
feat(工业移交): 型号切换增加二次确认与快照恢复机制    合计工时: 2.5h

- 新增 modelSnapshot 快照数据，记录当前已确认的型号信息    0.3h
- 切换型号时，若已有产品规划数据则弹出确认提示    0.5h
- 取消切换时通过 restoreModelSnapshot 还原型号字段    0.4h
- 变更流程切换型号提示"重新带出产品规划数据"    0.3h
- 非变更流程切换型号提示"清空产品规划数据"    0.3h
- 模具号输入同步更新快照，避免还原时丢失手动输入    0.2h
- 接口联调与多场景自测    0.5h
```

## 3. 模式 B — Work Report 生成

### 3.1 数据采集

通过目标分支与基准分支的 merge-base 差异来提取独有提交：

```bash
# 获取目标分支相对于基准分支的独有提交（非 merge commit）
git log <target-branch> --not $(git merge-base <target-branch> <base-branch>) \
  --pretty=format:"%H|%h|%ad|%an|%s" \
  --date=short --no-merges [--author=<author>]
```

如果 merge-base 与目标分支 HEAD 一致，说明目标分支已完全合并进基准分支，应提示用户并建议换一个基准分支。

对于每条提交，获取变更统计：
```bash
git diff --stat <commit>^ <commit>
```

安全阈值：单次 commit 涉及 50+ 文件时，仅获取 stat 概要，不深入 diff。

### 3.2 工时预估流程

对每条 commit：
1. 解析 commit message 的 type 和 scope
2. 获取 `--stat` 中的增删行数
3. 对行数 < 100 的 commit，读取具体 diff 以判断复杂度
4. 按 §2.4 的四维度模型计算工时

### 3.3 Work Report 输出格式

#### 阈值降级策略

根据筛选后的提交数量决定输出详细程度：
- **≤ 15 条提交**：输出完整报告（工时总览 + 详细改动说明）
- **> 15 条提交**：仅输出工时总览表格，并在末尾提示用户可通过缩小时间范围或指定作者来查看详细改动说明

#### 完整报告模板（≤ 15 条）

```markdown
# [项目名称] 工作报告

**周期**：[开始时间] — [结束时间]
**分支**：[目标分支] ← 对比基准：[基准分支]
**统计**：共 [X] 次有效提交 | 合计预估工时：[Y]h
```

## 4. 关键约束

### 4.1 语言规范
- 所有输出内容使用**简体中文**（commit message 中的 type 保持英文，如 feat/fix/refactor）
- scope 使用中文业务术语（如"打样2.0"、"工业移交"而非 "proofingPlus"、"industrialHandover"）

### 4.2 工时诚实性
- 工时预估应当客观反映实际开发工作量，不虚报也不低估
- 对于已知的"AI 辅助编码"场景（如 AI 生成了大量样板代码），可适当标注但不影响工时计算，因为工时反映的是"正常人工开发"的预期工时
- 如果某条改动工时不确定，可以给出范围（如 0.3-0.5h）并取中值

### 4.3 性能保护
- 单次最多处理 30 条 commit（超过时提示用户缩小范围）
- 对超大 diff（500+ 行）的 commit 使用 stat 概要而非完整 diff
- 避免对 merge commit 进行工时评估（通常无实际编码工时）

### 4.4 输出方式
- **模式 A**：直接在对话中输出 commit message（以代码块格式呈现），方便用户复制
- **模式 B**：直接在对话中输出 markdown 格式的工作报告（以代码块格式呈现），方便用户复制
