# 概述

项目中,有些设计错误或者潜在的BUG, 通常作为日常开发的程序员在开发的时候, 由于赶进度而遗留了潜在的问题.导致在实际运行的时候出现莫名其妙的问题, 通常程序员很难简单的发现. 现在的目标就是发现潜在的bug

## 理论

1. 潜在的bug通常在常规操作的时候,很难察觉,但是在运行到某些阶段可能及出问题.
2. bug的存在一般不会在日常操作中出现,而是满足特定条件就触发, 最终导致用户在使用过程中出现以下症状
  - 莫名其妙的错误, 但是重新来过又能用,用着用着又不行.

## 范围

1. 如果没有明确指定具体范围,则以最新的任务历史,报告文件等为线索找出最有价值的范围, 分析任务历史中,反反复复修改的相关开发任务, 立即安排任务的开发者修改某些功能的意图, 以同理心的方式了解开发者的焦虑和困惑,以及识别开发者自己可能没有实际意识到的潜在问题.

2. 确定了最有价值的访问后,使用独立的 docker容器,在容器中进行问题的复现和验证, 以及自动尝试进行修复.

3. 当你确认你成功修复一个非常有价值的潜在问题后, 最终以报告的形式汇报你的发现和解决办法.

## 优先级

1. 先底层,后上层.
2. 跨系统,跨模块的问题优先.


## 要求

1. 必须以隔离的方式进行探索和修复, 不能影响日常的开发. 日常开发,程序员会在主分支中进行,而且启动了很多服务, 如果你在本开发环境(如果没有使用隔离环境,例如docker), 会因为资源冲突,跟日常开发程序员造成困扰.
2. 报告文档写到主分支中.
