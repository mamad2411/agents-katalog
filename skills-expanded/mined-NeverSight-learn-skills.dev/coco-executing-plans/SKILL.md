# Coco 执行计划

开始前读取 `analysis.md` 或 `defect-analysis.md`、有效设计、`plan.md` 和开放变更；检查当前代码与计划假设是否一致。计划明显过期时不要盲目执行。

本技能用于完整流程。轻量流程不要求先生成计划，直接按“影响确认 -> 最小修改 -> 聚焦验证 -> 结果报告”执行；发现范围扩大时停止并转本技能。

执行前必须确认 G1 已完成，且 G2 的设计/技术方案和计划已由指定人工负责人批准。没有批准记录时暂停，不以 AI 自检替代人工 Gate。

若 `analysis.md` 表明工作项涉及前端，但 UI 设计状态缺失或为 `Provisional`，不得开始实现，必须提醒用户是否先设计 UI。确认 `Required` 时进入 `coco-product-design`；确认 `Reuse Existing` 或 `Not Applicable` 时在 `analysis.md` 记录依据，并确认计划与该决定一致后继续。

## 执行循环

1. 选择依赖已满足的最小垂直切片，将状态改为 `In Progress`。
2. 使用 `coco-tdd` 先建立失败测试或等价的可观察失败证据。
3. 实现最小变更，同时维护公开契约、数据迁移、安全和观测能力。
   - 前端 API 接入前确认 Apifox MCP 契约读取记录；按契约生成方法，并将实际方法、路径和调用文件回填接口清单。
   - 页面逻辑实现对照已确认的原型/流程设计；发现设计缺口或分支变化时先走 `coco-change-control`。
4. 运行聚焦测试，再运行受影响回归、静态检查和构建。
5. 对用户可见行为使用真实运行环境验证，不能只以 Build 成功代替。
6. 更新任务状态、执行记录和验证证据。
7. 在高风险切片、批次结束或交付前运行代码审查。

每个批次结束后更新执行记录、测试证据和待确认项，向人工检查点报告已完成内容、验证结果、剩余风险和下一批范围；收到新方向时停止当前批次并交给 `coco-change-control`。

全部执行完成后，必须列出实际测试范围及结果：原缺陷/验收场景、执行的测试层级、测试命令或操作、覆盖模块、未执行范围和残余风险；不得只报告“测试通过”。

批次大小由风险和反馈速度决定；高耦合或高风险任务缩小批次。

## 变更与阻塞

- 人工测试发现实现偏差：先判断是否属于当前 Work Item；属于当前范围时更新原任务记录、修复并补回归测试，不新建缺陷；独立问题才建立关联缺陷。
- 用户提出新方向：立即进入 `coco-change-control`；L3/L4 暂停相关任务。
- 只有格式或说明整理可延后到批次结束，指导当前开发的规格必须先更新。
- 无法执行验证时记录 Blocker、最接近的证据和未验证范围，不得标记完全通过。

未经用户要求不提交、推送、创建 PR 或部署。完成计划不等于自动获得这些外部操作权限。

PR 只能在 G3 审查通过、`verification.md` 已更新且 G4 验收责任人确认后准备；创建 PR 和更新 Jira 仍需用户明确授权。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
