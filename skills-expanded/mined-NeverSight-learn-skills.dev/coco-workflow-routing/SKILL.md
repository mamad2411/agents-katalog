# Coco 团队工作流路由

先识别任务性质，再决定需要哪些产物和质量关卡。不要因为流程存在就扩大用户要求；回答、调查或评审请求不自动授权写文件或改代码。

## 分类

- **需求**：新增能力、主动改变既有行为、体验优化或技术改造。进入 `coco-requirement-analysis`。
- **缺陷**：实现偏离已确认规格，或既有行为出现非预期退化。进入 `coco-defect-analysis`，需要定位时再进入 `coco-debugging`。
- **开发中反馈**：先比较当前基线与用户新表述。符合基线的是缺陷；改变基线的是变更，进入 `coco-change-control`。
- **纯咨询/审查**：只做证据支持的回答或审查，不初始化完整工作项目录。

## Jira 类型判定

- 用户提供 Jira 单号、链接或明确说明来源为 Jira 时，先调用 Jira MCP 读取 Issue、Issue Type、状态、描述、验收标准、评论、附件和关联事项。
- `Story`、`Task`、`Epic` 等新增能力或行为调整按需求流程；`Bug`、`Defect` 等实现偏差或退化按缺陷流程。
- Jira MCP 不可用、未配置或读取失败时，提示配置/修复 Jira MCP，并将任务标记为 `Blocked`；未取得 Issue Type 前不得假定是需求或缺陷。
- 没有 Jira 输入时，才根据用户描述和现有基线判断需求、缺陷或变更。

## 无 Jira 语义判定

- 用户说“实现、增加、新增、开发、支持、优化、调整、改造、重构某功能”时，默认按需求处理；再根据影响判断轻量或完整流程。
- 用户说“报错、异常、失败、不能使用、不符合预期、分析原因、排查、定位、为什么、修复问题”时，默认按缺陷/诊断处理。
- 用户只要求“分析原因、排查、定位”时，只执行调查和根因分析，不自动修改代码。
- 用户询问概念、使用方式、现有实现或要求审查时，按纯咨询/审查处理，不创建工作项文件。
- 同一句话同时包含新增能力和现有异常时拆分需求与缺陷；只有语义歧义会实质改变执行范围时才提问确认。

读取 Jira 后，首次分析输出按固定顺序给出：工作项类型与理解、关键证据/待确认项；缺陷还必须给出根因分析、修改方案、方案影响范围和测试范围。根因未确认时必须标为假设，不得直接执行修复。

## 流程等级

### 轻量流程

同时满足以下条件时使用：范围局部且明确；不改变业务规则、验收标准、公开 API/数据/权限/安全契约；无 Migration；无跨模块共享影响；风险低且可快速回滚。

适用示例：文案、注释、局部样式、明确的小范围实现缺陷、非行为性配置说明。

执行：Jira 读取与类型确认（如有） -> 简要理解/原因/影响确认 -> 最小修改 -> 聚焦测试或可重复验证 -> 简洁结果报告。默认不创建 `analysis.md`、`defect-analysis.md`、`plan.md`、`verification.md`、原型或完整 Gate；仅更新确实受影响的现有文件。

### 完整流程

存在以下任一条件时使用：需求或验收变化；根因未知；跨模块/共享组件影响；需要产品确认的 UI 视觉、布局、组件、交互或用户流程变化；API、数据、权限、安全、并发、性能、Migration、兼容或发布风险；影响范围无法快速证明。

轻量执行中发现范围扩大、假设不成立或测试暴露共享影响时，立即升级完整流程。

## 上下文续问与测试反馈

- 用户在当前需求/缺陷下继续提问、补充信息、要求复测或报告与当前范围直接相关的失败时，默认沿用原 Work Item、原目录和原文档，不重新启动流程。
- 测试发现的问题若属于原验收标准、原缺陷复现路径、原方案影响范围或同一实现改动，更新现有 `analysis.md`/`defect-analysis.md`、`plan.md` 或 `verification.md`，不新建缺陷。
- 只有问题独立于当前 Work Item、需要不同负责人/版本/发布节奏，或用户明确要求单独跟踪时，才新建关联缺陷并重新路由。
- 同一工作项内的测试偏差先作为当前任务的失败项、待修复项或变更记录；确认需要独立跟踪后再拆分。

同一句反馈同时包含缺陷和新方向时，拆成两个关联项：先记录可复现缺陷，再记录需求变更。不要通过把新期望描述成“修 Bug”来绕过影响分析。

## 协作门禁

- **G0 输入确认**：有 Jira 单号或链接时读取 Issue、评论、附件和关联事项，确认 Work Item Key、类型和当前状态。轻量流程完成 G0 后可直接进入修改。
- **G1 基线确认**：由产品/需求负责人确认目标、范围、验收标准和来源差异。
- **G2 设计与计划确认**：涉及 UI 时确认 `prototype.html` 的浏览器预览；仅在明确要求 Pencil 时确认 `design.pen`；涉及架构、API、DB、权限或安全时确认 `technical-design.md`；执行前确认 `plan.md`。
- **G3 实现质量检查**：高风险切片或批次后由人工检查测试、审查结果和剩余风险；P0/P1 未关闭不得交付。
- **G4 交付验收**：验收责任人确认 `verification.md`、PR 材料、残余风险和发布/回滚范围。

AI 可以准备材料，但不能代替用户批准方向、范围、风险接受或验收。

从 `analysis.md` 继续编写计划或执行实现前，若工作项涉及前端，必须检查 UI 设计状态。状态缺失或为 `Provisional` 时暂停并提醒用户是否先设计 UI；确认需要设计时进入 `coco-product-design`，确认复用现有设计或不适用时在 `analysis.md` 记录依据后继续。

## 默认路径

- 轻量调整/局部缺陷：G0（如有 Jira） -> 最小影响确认 -> 修改 -> 聚焦验证 -> 报告。
- 完整需求：G0 -> 需求分析 -> G1 -> 前端 UI 设计检查 -> 按需 HTML 原型/Pencil/技术设计 -> G2 -> 开发 -> G3 -> 验证 -> G4 -> PR/交付。
- 完整缺陷：G0 -> 缺陷分析 -> G1 -> 调试 -> 修复计划 -> G2 -> 开发 -> G3 -> 验证 -> G4 -> PR/交付。
- 开发中方向变化：`coco-change-control` 判定 L0-L4，只更新实际受影响的基线、任务和测试。

## 外部事实来源

- 用户提供 Jira 单号、Jira 链接或明确表示需求/缺陷来自 Jira 时，必须使用 Jira MCP 读取 Issue；按需读取评论、附件和关联单，再进行需求或缺陷分析。
- Jira MCP 读取结果必须记录 Issue Type、Issue Key、读取时间和来源链接；不得只凭标题猜测类型。
- 工作项涉及 Server、后端 API、接口字段、请求响应、鉴权或错误码时，必须使用 Apifox MCP 刷新并读取最新 OpenAPI 契约；需要 `$ref` 内容时继续读取关联资源。
- 前端实现只要调用后端接口，也必须使用 Apifox MCP 读取接口契约并按契约接入；未读取到契约时不得把接口接入标记为完成。
- Jira 是工作项描述和协作记录的事实来源；Apifox 是已发布接口契约的事实来源；当前代码和运行结果用于确认实际实现。三者冲突时必须列出差异，不得静默选择其一。
- Jira 评论、状态、字段、附件及 Apifox 接口的任何写操作，都需要用户明确授权；分析阶段默认只读。

## 工作项契约

完整流程统一使用 Aile 兼容路径 `docs/plans/{Work-Item-Key}/`，例如 `docs/plans/PROJ-123/` 或 `docs/plans/BUG-456/`。轻量流程不创建工作项目录，除非已有记录必须更新或用户明确要求。

- 需求核心文件：`analysis.md`、`plan.md`、`verification.md`。
- 缺陷核心文件：`defect-analysis.md`、`plan.md`、`verification.md`。
- 涉及 UI 时创建 `prototype.html`；仅在明确要求 Pencil 时创建 `design.pen`；涉及 API、DB、权限或架构时按需创建 `technical-design.md`。
- 开发中发生方向调整时按需创建 `change-log.md`；需要正式验收时按需创建 `acceptance.md`。
- 进入交付时生成 `pr-description.md`，使用 `coco-delivery-report/references/pr-description-template.md`。
- 不创建空占位文件；`plan.md` 首次创建后不得覆盖，历史版本使用 `plan-1.md`、`plan-2.md`。

每次继续任务先读核心分析文件、有效设计、当前 `plan.md`、`verification.md` 和开放变更。若代码或 Git 状态证明文档过期，先走变更控制。

需要代码导航、影响分析或跨文件修改时，直接检查实际代码、配置、入口、调用方和测试；不能把未找到的文本或路径解释为不存在。

纯咨询、单文件文案/注释调整或明确不涉及代码关系的操作，可以跳过代码检查，但应说明跳过原因。

## 人工决策点

产品方向、范围取舍、重大架构权衡、不可逆数据操作、生产部署及残余高风险接受必须由用户决定。AI 可以整理选项和证据，但不得替用户作最终业务决定。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
