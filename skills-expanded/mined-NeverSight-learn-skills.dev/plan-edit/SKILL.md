# Plan Edit

## 适用场景

当用户要求：
- 创建/编写/生成项目计划
- 修订/更新已有 plan 文件
- 根据需求生成带步骤的实施方案

## 工作流程

1. 收集需求：明确计划标题、目标、范围、约束与关键文件。
2. **探索代码库**：使用只读工具（read_file / grep / find_path / list_directory）勘察相关代码，确认涉及的文件、函数、数据流与现有约定。计划中的文件路径、符号名与步骤必须来自真实代码，禁止臆测。
3. 确定目标目录：当前项目根目录下的 `.agents/plans/`。
4. 如果是**创建**：
   - 生成文件名：`${yyMMddHHmm}_${title}.plan.md`，其中 `yyMMddHHmm` 为当前本地时间。
   - 直接写入 `.agents/plans/`。
5. 如果是**修订**：
   - 读取用户指定的已有 plan 文件。
   - 保留原有结构，仅修改用户要求的部分。
   - 按用户指示决定是否更新时间戳或保留原文件名。
6. 编写 plan 内容（见下方模板与编写规则）。
7. 写入文件并返回最终文件路径。

## Plan 模板

必备章节：标题、概述、实现任务、实施清单。其余章节按需取舍。

```markdown
# [标题]

## 概述
[一段话说明计划要解决什么问题、涉及哪些组件]

## 架构与数据流（如涉及流程或架构变更）

    ```mermaid
    flowchart LR
        subgraph a [组件 A]
            ...
        end
        subgraph b [组件 B]
            ...
        end
        a --> b
    ```

[图下用文字说明各方职责与数据流向]

## 关键设计决策（按需）
- **[决策点]**：选择 [方案 A]，因为 [理由]。备选 [方案 B] 的代价是 [代价]。

## 实现任务

### 1. [任务名]

需要修改的文件：
- `[文件路径]`（修改 / 新增）

具体工作：
1. [具体动作；涉及接口、Schema、协议时，必须给出具体示例或签名]
2. [具体动作]

验证方式（可选）：
- [如何确认此任务完成，如运行某测试]

### 2. [任务名]
...

## 风险与注意事项
- [风险 1]

## 需要修改的文件（汇总）
按组件分组，标注变更类型：

- [组件 A]：
  - `[文件路径]`（修改）
  - `[文件路径]`（新增）
- [组件 B]：
  - `[文件路径]`（修改）

---

## 实施清单
[与"实现任务"一一对应，供 plan-implement 解析勾选；放在文件最底部]

[ ] [任务 1 标题]
[ ] [任务 2 标题]
```

## 编写规则

- **任务格式**：每个任务必须包含「需要修改的文件」清单与「具体工作」编号列表；「验证方式」可选。
- **任务质量**：按依赖关系排序；每个任务可独立验证；具体到不熟悉该任务的人无需猜测即可执行。
- **具体契约**：涉及接口、数据结构、Schema、协议时，在「具体工作」中给出 JSON 示例、函数签名或模型清单，而非抽象描述。
- **实施清单**：唯一进度记录，位于文件最底部；格式为有序列表 + `- [ ]` checkbox，编号与「实现任务」的编号一一对应，供 plan-implement 勾选。
- **章节取舍**：架构与数据流、关键设计决策、目标等章节按需添加；有设计权衡时必须写「关键设计决策」，说明备选方案与代价。
- **工具约束**：写入 plan 文件使用写文件工具，禁止用 shell heredoc（内容含反引号会断裂）；修订时对已有文件做定向编辑，不重写全文。

## 修订规则

- 不得删除未要求修改的章节或步骤。
- 若用户未指定新文件名，保留原文件名。
- 若用户希望基于当前计划创建新版本，则生成新的时间戳文件名。
- 实施过程中如需更新进度，仅将「实施清单」中对应项的 `- [ ]` 改为 `- [x]`，不改动任务正文。
