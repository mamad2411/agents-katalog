# ADR Engineering

## Use this skill when
- Capturing the why behind technical decisions
- Reviewing past decisions and alternatives
- Onboarding context

## Do not use this skill when
- Trivial implementation details
- A stale doc nobody updates (keep lean)

## Instructions
1. Title the ADR with the decision, not the debate.
2. Include context, decision, alternatives considered, and trade-offs.
3. Date and number ADRs; link superseded ones.
4. Keep ADRs short enough to stay maintained.
5. Add status: proposed, accepted, superseded.
6. Review ADRs at design checkpoints, not after.

## Checklist
- Why recorded
- Alternatives documented
- Status maintained

## Output Format
- ADR | status | context | decision | trade-offs

## Common Mistakes
- ADRs written to justify after the fact
- Epics documents nobody rereads
- No supersession tracking
