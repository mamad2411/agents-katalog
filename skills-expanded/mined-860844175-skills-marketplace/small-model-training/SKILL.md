# 小模型垂直任务训练（LLaMA-Factory）

把「一个需求（± 数据）」变成「一版可评测、可复现、可迭代的模型」。训练引擎只用 LLaMA-Factory；目标模型 <8B（典型 0.5B–4B）。

## 这份 skill 是什么

**它是一次整合，不是一套原创方法。** 里面几乎每一条单独拿出来，都能在别处找到出处：训练怎么跑，工具文档写得比这里全；评测要先于训练建立，Hamel Husain 早就论证过；底座选择比大多数超参重要，是 LoRA Land 的实验结论；质量重于数量，是 LIMA 的发现。

**整合本身加的三样东西，是散落的来源各自给不了的：**

| | 单独的来源给你 | 整合之后多出来 |
|---|---|---|
| **顺序** | 一堆都对的做法 | 什么时候做哪一条 —— 例如「冻 golden」必须在「增广数据」之前，反过来做，前面全部作废 |
| **门禁** | 建议 | 上一步没做完不许进下一步，且判据可执行（`check_dataset.py` 退出码非 0 就是不许训） |
| **产出物** | 知识 | 每阶段交出什么、给谁看 —— 《我们的理解》给客户签字，三件套给自己对账 |

第四样是**回写**：`pitfalls.md` 规定每踩一个新坑就补一条通则。这套东西的复利全在这一步 —— 一份不再更新的经验集，半年后只剩历史价值。

## 来源与可追溯性

这份 skill 自己就是 `references/external-research.md` 那套纪律的产物：**外部经验只进候选名单，只有自己 golden 上的实测能进结论；每条经验记出处、日期与适用条件。**

| 类别 | 来源 | 在本 skill 中的位置 |
|---|---|---|
| 工具事实 | LLaMA-Factory 官方文档与源码（字段默认值均在 0.9.6.dev0 实例上核对） | `llamafactory.md`、`training-ops.md` |
| 公开工业实践 | LIMA、LoRA Land、Llama Guard、Zephyr、OpenAI / Unsloth / Thinking Machines 微调指南、Hamel Husain 与 Eugene Yan 的评测方法论 | 数据规模判据、底座选型、policy 条件化、评测纪律 |
| 实战事故 | 一个健康领域输入审核模型（0.8B SFT，自建 golden 上 F1 0.95，超过 GPT-4.1-mini）+ 语音双工复刻、图像标注等项目 | `pitfalls.md` 的 36 条通则，每条附真实事故 |

看到与你环境不符的结论时，以你自己实测为准 —— 这条纪律对本 skill 自身同样适用。

## 本 skill 不解决什么

- **预训练、≥8B 全参训练、RLHF 全流程** —— 不在范围内
- **云端训练基础设施**（任务提交、成本估算、GGUF 转换、Unsloth 加速）—— 这些工具型 skill 覆盖得更好，需要时直接用它们
- **提示词工程与 RAG** —— 但 P0 的决策树会先帮你判断该不该微调，很多时候答案是不该

## 硬规则（先读，全程有效）

这些是从真实事故里换来的，违反任何一条都可能让整次训练作废：

1. **客户说场景，我们做翻译。** 默认需求方**不懂任何机器学习**。不要向客户索要 golden、指标阈值、schema 或底座型号 —— 任务形态判定、两类错误的定义与成本排序、指标换算，全部由我们完成，再用他听得懂的话回读确认。P0 的产出是《我们的理解》给客户点头，不是一张让客户填满技术字段的表。**逐条自检：这个问题客户不查资料、不问人，能 10 秒内答出来吗？** 答不出来是我们没写好。必答项超过 3–4 条就重新审视 —— 技术决定应移进「我们已定的事」清单，不占用他的决策注意力（见 `intake.md` 降低 effort 五条）。
2. **双轨：先给推荐，再问自带。** 底座、训练数据、测试数据、指标、标签体系、部署形态 —— 每一项都是"我们出默认方案 + 客户可以覆盖"。客户自带的资产**先审计再用**（自带测试集默认不能直接当 golden）；客户指定的底座**进 bake-off 当候选**，用数字说话，不替客户否决。
3. **没有冻结的 golden 测试集 + baseline 数字之前，不开始训练。** 没有评测系统的微调是盲飞；baseline 决定项目性质（蒸馏 or 攻坚）甚至该不该做。
4. **泄漏门禁**：任何数据进入 train 前，必须跑 `scripts/check_dataset.py` 过 normalized-text 去重 + 对 golden/valid 的重叠检查。实战中最高频的事故就是人工增广数据把 golden 原文带进了 train；训到脏数据的模型无法事后洗净，只能重训。
5. **golden 只用于打分**。错误分析看 valid/silver；golden 文本不得出现在任何数据生成 prompt、增广模板或参与者文档里（描述其分布也算泄漏）。
6. **训前预检**：template 与底座精确匹配（训练/推理/导出三处一致）+ 肉眼检查 LLaMA-Factory 启动时打印的预处理样例（labels 落在 response 上、EOS 在）。这 30 秒能避免报废一整次训练。
7. **不做 bake-off 不定底座。** 底座由约束反推尺寸上限 → 主动检索候选 → 2–4 个候选在同一 golden 上实测对比 → 用数字拍板。底座选择比大多数超参重要（LoRA Land），凭记忆选型是最贵的省事。
8. **不训练可派生字段**。模型只输出语义标签；路由/动作等能由代码从语义字段确定性推导的东西写在代码里，否则模型会输出内部矛盾的组合。
9. **Coverage（合法输出率）是一等指标**。parse 失败/schema 不合法的输出永远不计入"安全/正确"一侧；正式结果要求 Coverage 接近 1。
10. **每次正式评测产出三件套**：`preds.jsonl` + `report.md` + `manifest.json`（模型、数据 SHA256、config、template、seed、git commit）。不可复现的结果等于谣言。
11. **迭代靠错误分析 → 定向补数据，不靠调参考古**。v1→v2 的主要收益来自数据，不来自超参搜索。
12. **外部经验进候选名单，不进结论。** 检索到的做法只能改变"我们要试什么"，只有自己 golden 上的实测能改变"我们相信什么"。每条外部经验必须记发布日期和适用条件。
13. **★ 任何指标在用于判断前，必须先拿金标跑一遍。** 金标（人类/已知正确答案）跑出 100% 或 0%，说明尺子坏了，不是模型好或差。checkpoint 的 monitor 量同样要自检 —— 选不出档往往是 monitor 饱和了。见 `pitfalls.md` P-1。
14. **★ 数据优先找真实的，合成是最后一步。** 训练集和评测集都走 客户自带 → 生产日志 → **公开真实数据集（HF/Kaggle）** → teacher 蒸馏 → 人工标注 → 合成增广。开始合成前必须留下公开数据集检索记录（搜了什么、为什么不合用）。**评测集里不放合成数据。**
15. **超参我们定，环境问客户。** bf16 / liger kernel / LoRA r·α·dropout / lr / batch / packing 一律按 `training-ops.md` 的默认值走，不向客户征询；但**跑在什么环境、机器上有没有别的线上服务、要交付什么形态**必须问（客户表 G 块）。
16. **开训前先回答"我在哪看 loss"，上线前先回答"客户在哪看进度"。** 前者看不到就是盲飞（常见于框架的 logger 互斥配置）；后者是交付物的一部分，不是可选项。
17. **★ 训练是循环，客户要始终知道自己在循环的哪一步。** 每版训完先做**版本自省 + 归因四选一**再决定下一步。客户不需要批准每一步，但沉默是最伤信任的：改我们做法的自主推进，改约定的必须停下等他拍板，中间那一档做了立刻告知（见 P5 三档契约）。**预期在 P0 就设好**：一般训 2–4 版，重训是计划内的事。
18. **★ 沟通阶段只探索，不下载。** P0/P1 定案前，评估一份数据只用**元数据与抽样预览**（datasets-server 的 `/size`、`/rows`、model card、`config.json`），**不 clone 仓库、不下权重、不落盘大文件**。理由是时序：这时候方案还没被客户点头，下载来的东西有一半概率作废，而沟通速度本身是交付质量的一部分。真正下载发生在 P2 数据定稿之后、P3 开训之前。
19. **★ 客户层与技术层分开，客户层 5 屏读完。** 给客户的《我们的理解》只放：场景复述 / 两类错 / 回读句 / 验收 / 假设 / 拍板栏，且**不出现指标名、模型名、参数名**。证据卡、底座对照、数据集清单、环境探测、超参一律收进默认折叠的技术层 —— 不是删掉，是收起来。用 `assets/client_brief_template.html`，**只改 DATA 对象不改结构**（既统一版面也让产出变快）。信息密度高不等于沟通到位；把要拍板的三件事淹掉就是沟通失败。
20. **★ 每份数据必须说清「为什么要它」。** 只列名字、行数、URL 不算说明白。四问缺一不可：**为什么要它**（它填我们哪个缺口）/ **它是什么情况**（谁出的、多少条、谁标的、什么形态）/ **能不能用**（许可证、可及性、与我们口径的匹配度）/ **风险**（污染、标签是否藏、分布是否符、标注一致性是否未知）。同一格式适用于外部经验证据卡。
21. **★ 训练集的分布/类别/难度设计是我们的活，不进客户文档。** 类别配比、难度分层、难负例比例、去重阈值、采样策略由我们按 `data.md` 决定并写进《训练方案》；向客户只回读一件事：**"我们会按你线上真实流量的分布来配，不人为凑均衡"**。反之，**客户自带数据时要反向加码沟通**：先审计再用，且必须把「你这份数据当初是为什么标的、标的时候口径是什么」问到底 —— 自带数据的口径分歧是 P4 吵架的第一来源。

## 工作流总览

```
P0 客户对齐 → P1 Golden+Baseline+选底座 → P2 数据工程 → P3 训练 → P4 评测 → P5 迭代 → P6 交付
  (三轮/验收合同)  (go-no-go + bake-off)      (泄漏门禁)    (预检)   (三件套)  (飞轮)  (部署门禁)
```

每个阶段有明确的产出物和放行条件（gate）。客户带数据来 = P2 提速，但 P0/P1 一步都不能跳 —— 跳过 P0 的代价不是返工，是 P4 时客户说"我觉得效果不行"而双方都拿不出对账依据。

## P0 客户需求受理 → 三轮对齐

读 `references/intake.md`。**这是三轮交互，不是一份问卷。**

```
Round 1  客户填《需求速写》     ~10 分钟  assets/intake_form.html（14 项，零术语，"不知道"合法）
Round 2  我们出《我们的理解》   离线      assets/client_brief_template.html　★ 核心产物（固定模板，只改 DATA）
Round 3  客户点头 / 纠正        ~15 分钟  → 冻结成《验收合同》，P4 逐条对账
```

Round 2 的五节，第 ② 节是心脏：

1. **① 我们理解你要的是什么** —— 复述目标 + **我们判定形态**（分类 / guard / 抽取 / 结构化输出 / QA / 改写），查 intake.md 形态表拿最小数据量和主指标。同时列出**不进模型目标的可派生字段**（硬规则 #8）。
2. **② 这个模型会犯两种错** —— 把 Type I / Type II 翻译成客户的业务后果，给出我们对"哪个更贵"的判断。**节末一句大白话回读，是客户全程唯一必须点头的地方**：「每 100 个正常用户里误伤不超过 2 个；每 100 条真违规里漏 10 条以内可以接受 —— 对吗？」不许出现指标名。
3. **③ 所以我们这样验收** —— 由 ② 机械换算：主指标、方向性约束、分 slice 下限、Coverage、p95 延迟。不另立一套。
4. **④ 我们替你做的假设** —— 客户每个"不知道"一行：默认值 + 依据 + **改动它的代价**。
5. **⑤ 红黄绿初判 + 建议路线** —— 附候选底座对照表和带日期的行业参照（`external-research.md` 触发点 1）。

同时在内部走**该不该微调决策树**（intake.md 第 4 节）：prompt 工程做过吗 → 缺的是知识还是行为 → prompted 大模型达标吗。经济动因（延迟/成本/隐私/格式一致性）至少占一条才立项。

客户自带数据、测试集或指定底座的，走 intake.md 第 5 节**审计清单**。

**Gate**：客户在 ② 的回读句和 ③ 的验收表上明确确认。标签口径有分歧的，先小样本双人标注测一致性（κ < 0.7 说明 spec 坏了，不是数据不够）。之后用 `assets/training_plan_template.md` 出内部训练方案。

## P1 Golden 测试集 + Baseline + 底座候选（训练前！）

读 `references/evaluation.md` 和 `references/base-model-selection.md`。顺序固定：

1. **建 golden v1 并冻结**：几百到 ~1000 条人工核验样本，覆盖刻意设计的 slices（每类、每来源、对抗、难负例），分布贴近部署流量而非人为 50/50。命名版本（golden_v1），记 SHA256，从此只读。客户自带测试集要先过审计才能升格。
2. **约束反推尺寸上限**：从 P0 的部署硬件/QPS/延迟算出显存与尺寸天花板，再**主动检索**该档位的候选底座（不凭记忆选型），出 2–4 个候选对照表。
3. **跑三层 baseline + 底座 bake-off Level 1**（同一条 harness，只换 endpoint）：多数类/正则规则 → prompted 大模型（认真做 prompt 工程，这同时是 go/no-go 标尺、候选 teacher、和对评测系统的压力测试）→ **每个候选底座**的 prompted 零样本。
4. **Go/No-Go**：大模型能达标 → 项目性质是蒸馏（便宜，走 teacher 标注路线）；大模型远达不到 → 先修 spec/标签而不是指望微调创造能力；正则已 85% 而目标 90% → 重新评估立项。
5. 时间允许则做 **bake-off Level 2**（固定数据子集 + 完全相同的 LoRA 配方，只换底座和 template），底座定稿必须引用实测数字。

**Gate**：golden 冻结 + baseline 数字进 leaderboard 表 + 底座由 bake-off 数字定稿（硬规则 #7）。

## P2 数据工程

读 `references/data.md`。要点：

- **规模看形态速查表**（分类 500–5k 起步、guard ~10k+ 含对抗层、风格/格式 ~1k 精品）。质量 > 数量：prompt 多样性 + 响应风格统一是赢面（LIMA）；效果差先加数据/提质量，再动超参。
- **来源优先级（硬规则 #14）**：客户自带/生产日志 > **公开真实数据集检索（HF/Kaggle/论文配套）** > teacher 蒸馏（用 golden 验证过的标注 prompt）> 人工标注（golden 和 teacher 不可靠的域）> 合成增广（最后手段，只补 gap，authored ≤50%，模板池要宽否则模型学句式不学概念）。**评测集里不放合成数据。**
- **外部数据三门槛**（不占其一就拒绝，硬混只会放大口径差）：能救活死类且是"有无判断"类 / 域接近 / 带一致性 kappa 或我们缺的监督层。验真看仓库树和实际解压，不看 README。
- **拿到任何"数据+标签"先去重对账**（文本 normalized-text / 图像 aHash）—— 一次操作同时拿到泄漏风险和免费的标注一致率下界。多标签一致性**不许用严格集合匹配**（`pitfalls.md` P-15/P-16）。
- **难负例是一等公民**：用了敏感词汇的良性文本、对抗改写、近似碰撞（同名同姓/数字巧合）。guard 类任务对抗数据是独立训练层，且留一个永不入训的对抗评测 slice。
- **切分纪律**：先冻 golden 再增广；train/valid 按 id+normalized-text+group 三重断言零交集；类平衡在 train 可适度过采样，test 保持部署分布。
- **每个数据集出 manifest**：各 split 的 SHA256、按标签/来源的分布统计、去重去污染状态、种子。

**Gate**：`python scripts/check_dataset.py --train train.jsonl --valid valid.jsonl --golden golden.jsonl` 全绿（格式合法、无空 output、train 内部去重、train∩valid = train∩golden = 0）。

## P3 训练

读 `references/training-ops.md`（环境三档、**超参默认值与调整条件**、OOM 阶梯、进度监控、资源隔离）和 `references/llamafactory.md`（格式、注册、YAML 配方、坑点清单）。默认路线：

1. **环境**：优先复用现成镜像（`PYTHONPATH` 挂补充依赖，注意自建目录要排在框架路径前面）；要交付才自建镜像。机器上有线上服务（客户表 G4）→ **必须做资源硬隔离 + 熔断守护**。
2. **LoRA 先行**：r16/α32、`lora_target: all`、`lora_dropout 0.05`、lr 1e-4~2e-4、2–3 epochs（<10k 数据可 3–5）、cosine、**bf16 + liger kernel + gradient checkpointing**、有效 batch 32–128。短样本任务开 `packing` **必须配 `neat_packing`**。模板 `assets/lora_sft.yaml`。
3. `cutoff_len` 先统计 token 长度分布再定（≥ p99），截断吃 label 是静默失败。
4. 用命名 `eval_dataset`（valid 集）而非 `val_size`，`eval_steps` 上监控 eval_loss 回弹判断过拟合；保最优 checkpoint 不是最后一个。
5. 担心通用能力回归时混 5–10% 通用指令数据（单任务 guard 通常不需要——部署后它只干一件事）。
6. LoRA 到平台且离目标有差距 → 先升 rank 到 32–64，**再去补数据**，最后才考虑 full FT（lr ÷10，`assets/full_sft.yaml`）作对照实验。在超参上花的第三天，通常不如去补 500 条定向数据。
7. SFT 是主准确率杠杆；DPO 只在"输出风格/偏好性错误而非事实错误"时作为第二阶段加。
8. **进度对外可见**：从 `output_dir/trainer_log.jsonl` 生成单文件 HTML 进度页给客户，用《验收合同》的原词报成绩，不给 raw loss / lr / 报错栈。

**训前预检五项**（30 秒，能避免报废整次训练）：① template 精确匹配底座，训练/推理/导出三处一致 ② 打印 `pad/bos/eos/unk` 四个 id **互不相同** ③ 肉眼看预处理样例（labels 落在 response 上、EOS 在、没被截断）④ dump resolve 后的完整 config 进 manifest ⑤ 跑 20 步冒烟，**确认看得到 loss 在动**。

**Gate**：五项预检全过（硬规则 #6/#16）；训练曲线正常（loss 快降后平稳，不趋 0 不复读）。

## P4 评测

读 `references/evaluation.md`。要点：

- **★ 每个指标先拿金标跑一遍再用**（硬规则 #13）。金标跑到 100%/0% = 尺子坏了。同时读一遍指标实现里的过滤/跳过分支，一行 `if x > 0` 能结构性丢掉一整类样本。
- **同一条评测代码评所有模型**：把 SFT 模型合并后 `vllm serve` 起 OpenAI 兼容服务，与 prompted baseline / API 模型走同一 harness，只换 endpoint。
- 报**分 slice 指标**，不只报总分；Coverage 单列；延迟串行测（并发=1 + 预热）。
- **配对比较 + 置信区间**：n=1000 分辨率约 ±3pp；噪声带内的"提升"不许上榜宣布赢。
- leaderboard 一行一模型：模型、数据版本、config、日期、各指标。历史修过的 bug 样本进回归 slice，每版必跑。
- 可选：`llamafactory-cli eval`（MMLU/C-Eval）确认没把底座练废——只作回归检查。

## P5 迭代自省循环（训练不是一次性的）

读 `references/training-ops.md` 第 6–7 节。**每版训完先自省再决定下一步**，不自省就重训 = 用同一种方式犯第二次错。

```
训练 → 评测 → ★版本自省 → 归因 → 定向动作 → 再训练 …… 直到停止条件
                   ↓
            按三档契约同步给客户
```

1. **对照《验收合同》逐项**：达标 / 未达标 / **落在噪声带内**（±3pp 内的"提升"不算数）。
2. 在 **valid**（不是 golden）上抽样错误 → 走 **open coding → axial coding → 计频** 三步（`evaluation.md` 第 8 节）：先读 30–50 条写自由笔记、再归纳成 5–10 个失败模式、按频率排优先级。**类别要具体到别人能照着独立标注**，「效果不好」不是类别。
3. **★ 归因四选一 —— 这一步决定后面所有动作**：

| 归因 | 怎么认出来 | 下一步 |
|---|---|---|
| 数据不够 | 某类样本少且该类分数低；上次翻倍还在涨 | 定向补数据（**先搜公开真实数据**，最后才合成） |
| 数据有错/口径歧义 | 错误集中在边界；重标一致率低 | **停下，口径要客户裁定** —— 这是 spec 问题不是模型问题 |
| 指标测错东西 | 金标自检跑不到接近上限；分数与人肉观感相反 | 修指标，**历史模型全部重跑**后才能继续比较 |
| 方法到顶 | 数据翻倍不涨；模型分歧 ≈ 人类分歧 | 升 rank → 换底座（回 bake-off）→ 或宣布收敛 |

> 最常见的误判：把"数据有错"当成"数据不够"，于是拼命补数据 —— 补进去的还是同一套错口径的数据。**先看重标一致率，再看数据量。**

4. **停止条件**：(a) 目标指标带 CI 达标；(b) 数据翻倍不再涨；(c) 触到标注一致性天花板；(d) 客户说够了。

**客户沟通契约（三档）** —— 客户不需要批准每一步，但必须随时知道自己处在哪一步：

| 档 | 属于这一档的 | 怎么做 |
|---|---|---|
| **① 自主推进** | 补数据、重训、调超参、换 checkpoint、加 slice、修 bug | 不打断客户，进度页照常反映 |
| **② 主动告知** | 指标掉出验收范围、数据质量问题、换底座、工期变化、**指标本身修过** | 一条消息：发生什么 → 影响 → 我们已在做什么。**不问"可以吗"** |
| **③ 必须停下** | 改验收标准、改口径/标签定义、要额外投入、超预算/超期、发现红灯 | 停下，给现状 + 选项 + 推荐，等客户拍板 |

判据：**这件事改变的是我们的做法，还是改变了当初和客户约定的东西？** 改约定的一律进 ③。
进度页要画成**循环**不是单向进度条，并在 P0 就设好预期：「一般训 2–4 版，每版之间做一次分析和定向补数据 —— 这是正常流程，不是出了问题。」

## P6 交付

1. `llamafactory-cli export` 合并 LoRA（不能合并进量化底座）→ 标准 HF 目录。
2. **部署什么就评测什么**：要量化上线就评量化后的产物；在真实 serving 硬件上验延迟。
3. 写 model card：用途、taxonomy 版本、数据来源构成、分 slice 指标带 CI、已知失败模式、阈值建议。
4. 部署门禁全绿：golden 达标（含分 slice 下限）+ 回归 slice 无复发 + 对抗 slice 达标（guard 类）+ 延迟/成本达标。
5. 上线后把生产日志接回 P2——难例回流是 v2 最好的数据来源。

## 可移植性

这个 skill 设计成**可以整目录拷走**——放进任何仓库的 `.claude/skills/` 下即可用，不含任何项目专属路径、主机名或内部工单号。

**必需**：无。所有文件是纯 Markdown + 一个零依赖 HTML + 一个纯标准库 Python 脚本（`check_dataset.py`）。

**可选增强**（没有也能走完流程，只是要多敲几条命令）：

| 依赖 | 用在哪 | 没有时的兜底 |
|---|---|---|
| `huggingface-skills:huggingface-best` | 选底座检索 | HF Hub API：`https://huggingface.co/api/models?...` |
| `huggingface-skills:hf-cli` | 搜仓库、下权重 | `curl` + HF/ModelScope REST |
| `huggingface-skills:huggingface-datasets` | 公开数据集检索 | `https://huggingface.co/api/datasets?search=` |
| `huggingface-skills:huggingface-papers` / `hf-mem` | 论文检索 / 显存估算 | WebSearch；显存按 `training-ops.md` 第 1 节手算 |
| `WebSearch` / `WebFetch` | 外部经验检索 | 人工检索后按证据卡格式录入 |

**执行环境要求**：训练引擎是 LLaMA-Factory（`references/llamafactory.md` 对齐 v0.9.5+）。评测走 vLLM 的 OpenAI 兼容服务。两者都不由本 skill 安装。

**搬走之后要做的一件事**：`references/pitfalls.md` 里的实例来自过往项目，新环境有新环境的坑。按开头「回写」那条继续往里补，这份 skill 在新项目上才会持续增值。
