# Bug 只读排查与诊断

`spot-bug <错误描述、报错堆栈或复现现象>` 专用于显式定位与诊断 Bug。本阶段严禁擅自修改业务修复代码；仅允许在连续 2 次定位失败后插入带 `[DEBUG-xxx]` 标记的临时探针，并在输出拟议 diff 前清理还原，保持工作区干净。

先读取 `../../bundled-skills/spot-diagnosing-bugs/SKILL.md`（未找到时退回本机同名版本），严格按其诊断规范建立反馈回路并追查根因。

按以下 4 步执行：

1. **复现与建立反馈回路**：
   - 根据用户提供的报错信息、堆栈或现象，先核实事实，并核查最近相关提交与工作区改动（如 `git log -n 10` / `git diff`）排查近期变更引入点。
   - 寻找能稳定复现的最小路径（失败测试用例、单步脚本、curl 请求或 CLI 命令）。无法复现时，如实报告证据缺口与可能原因。
   - **排查熔断**：连续 2 次复现/定位失败禁止盲猜，必须插入带 `[DEBUG-xxx]` 标记的临时日志输出实际入参和上下文（用完即删）；连续 3 次未果主动提示清空上下文（使用 `/compact` 或新开独立会话）重新输入最小复现信息，防止污染。
2. **追溯调用链路与定位根因**：
   - **多假设防锚定**：非一眼明确定位时，先按概率列出 2~3 个可证伪的候选假设（假设 X → 若成立则验证条件为 Y）再逐个排除，避免锚定第一个猜想。
   - 沿端到端调用流追查：`触发入口 → 传参/校验 → 业务逻辑 → 故障点`。
   - 标出真实源码文件、关键函数及出错行号，指出“预期行为 vs 实际行为”以及引发缺陷的根本原因（`原因 X → 导致现象 Y`）。
   - **前后对照草图（按需）**：若 Bug 涉及页面表现、交互流转、接口出入参结构或业务分支走向，读取 `../../bundled-skills/spot-before-after-sketch/SKILL.md`（未找到时退回本机版本），输出「改前（现状缺陷）」与「改后（建议修复）」两段文本草图；纯底层防御或纯算法计算不强行画图。
3. **拟定最小方案与拟议 diff**：
   - 读取 `../../bundled-skills/spot-ponytail/SKILL.md`（未找到时退回本机版本），制定只触达病灶的最小修复方案。
   - 用一小段基于现有代码的拟议 diff 展示核心改动，不引入无关重构或多余封装。
4. **列出回归验证并等待确认**：
   - 列出防止复发的关键回归用例（`测什么情况 ｜ 应该看到什么结果`，最多 4 行）。
   - **举一反三**：顺带排查全仓是否存在同类调用或边界隐患，一并列入待确认范围。
   - 保持代码未改动状态。根因与方案证据足够时，按公共规则的风险路径提示「确认需求」或「开工」；无法复现或根因未确定时，先自行补证，确实需要用户提供信息才指出最关键的一项，不提示开工。

## 修复实施后流转（标准闭环）
代码改动完成且回归测试绿灯后：
- 若本轮经历过连续 2 次以上定位失败、平台/环境深坑或用户纠偏，在正文中顺手提炼 1 句防呆规则草案（供后续 `spot-learn` 沉淀），不强占主流程。
- 在【下一步操作】中**默认推荐调用 `spot-review`** 审查本次修复 diff（`【下一步操作】/spot-review`，重点复核：是否有未预期的副作用、边界防御是否漏掉、是否有冗余代码）。
- 经 `spot-review` 确认通过（无 `[Blocker]`）后再行提交或发布。
