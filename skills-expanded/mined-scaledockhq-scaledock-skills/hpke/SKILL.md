# Hybrid Public Key Encryption

This document describes a scheme for hybrid public key encryption (HPKE). This scheme provides a variant of public key encryption of arbitrary-sized plaintexts for a recipient public key. It also includes three authenticated variants, including one that authenticates possession of a pre-shared key and two optional ones that authenticate possession of a key encapsulation mechanism (KEM) private key. HPKE works for any combination of an asymmetric KEM, key derivation function (KDF), and authenticated encryption with additional data (AEAD) encryption function. ## Invariants

1. **RFC 9180 § 4.1.** "Senders and recipients MUST validate KEM inputs and outputs as described in Section 7.1."
2. **RFC 9180 § 5.1.** "The psk and psk_id fields MUST appear together or not at all."
3. **RFC 9180 § 9.5.** "In the PSK and AuthPSK modes, the PSK MUST have at least 32 bytes of entropy and SHOULD be of length Nh bytes or longer."
4. **RFC 9180 § 5.2.** "The sender's context MUST NOT be used for decryption. Similarly, the recipient's context MUST NOT be used for encryption."
5. **RFC 9180 § 5.2.** "If ContextS.Seal() or ContextR.Open() would cause the seq field to overflow, then the implementation MUST fail with an error."
6. **RFC 9180 § 7.1.4.** "The following public keys are subject to validation if the group requires public key validation: the sender MUST validate the recipient's public key pkR; the recipient MUST validate the ephemeral public key pkE; in authenticated modes, the recipient MUST validate the sender's static public key pkS."
7. **RFC 9180 § 7.1.4.** "In particular, recipients MUST check whether the Diffie-Hellman shared secret is the all-zero value and abort if so."
8. **RFC 9180 § 9.2.3.** "An ikm input to DeriveKeyPair() (Section 7.1.3) MUST NOT be reused elsewhere, in particular not with DeriveKeyPair() of a different KEM."
9. **RFC 9180 § 9.2.3.** "The randomness used in Encap() and AuthEncap() to generate the KEM shared secret or its encapsulation MUST NOT be reused elsewhere."
10. **RFC 9180 § 9.7.1.** "The primary requirement that HPKE imposes on applications is the requirement that ciphertexts MUST be presented to ContextR.Open() in the same order in which they were generated by ContextS.Seal()."
11. **RFC 9180 § 9.7.1.** "When an unrecoverable loss is detected, the application MUST discard any associated HPKE context."
