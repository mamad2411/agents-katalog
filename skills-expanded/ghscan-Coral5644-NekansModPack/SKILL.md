# Nekans 主工作流

本技能是 NetEase Mod 开发的主编排器，负责把专项技能串成一个可跨会话恢复的完整工作流。

> [!IMPORTANT]
> 目标不是把所有事塞进一个超长会话，而是把它拆成三个稳定阶段，保证上下文不会在执行中期被压缩掉。

---

## 会话分段策略

工作流强制分为三个独立会话：

### 第一会话：选工作位置 + 需求分析 + 制定计划

1. **阶段零**：询问用户在主工作区还是新建功能工作区工作
2. **阶段一**：需求分析（`brainstorming`）
3. **阶段二**：制定实现计划（`project-planner`）

> **结束信号：** 已有明确工作模式 + 已有计划文件 + 用户已确认计划  
> **动作：** 写入状态文件 + 生成"第二会话接力提示词" + 提示用户开启第二会话

### 第二会话：执行开发 + 边审查边修 + 直测 + 集成

1. 读取状态文件恢复工作模式、功能名和计划路径
2. **阶段三**：执行计划（`executing-plans`）
3. 在执行过程中持续做批次审查
4. 计划任务完成后，**通过 mcdev-tools 直接测试功能工作区代码**（无需合并到主工作区）
5. 测试失败 → 直接在功能工作区修复 → 重启游戏 → 重新测试
6. 测试通过 → 询问用户是否合并到主工作区（集成步骤）

> **结束信号：** 第二会话内的开发任务已完成，且集成测试已通过  
> **动作：** 写入状态文件 + 生成"第三会话接力提示词" + 提示用户开启第三会话

### 第三会话：最终审查 + 修复审查结果 + 收尾清理

1. 读取状态文件恢复上下文
2. **阶段四**：最终审查（深度L4）
3. 修复最终审查发现的问题
4. 若最终审查修复引入代码改动，补做一次最小回归验证
5. **阶段五**：收尾清理，删除功能工作区、整理总结

> **结束信号：** 最终审查通过，且清理动作完成或用户明确选择保留工作区

## 目录组织约定

### 1. plans 目录按业务分文件夹管理

所有同一业务的设计文档、实现计划、补充计划都统一放到同一个目录：

```text
Docs/plans/<业务名称>/
├─ <业务名称>-design-overview.md
├─ <业务名称>-execution-plan.md
└─ <业务名称>-followup.md
```

### 2. sessions 目录按业务分文件夹管理

所有同一业务的跨会话状态文件和接力信息统一放到同一个目录：

```text
Docs/sessions/<业务名称>/
├─ <业务名称>-session-1.md
├─ <业务名称>-session-2.md
└─ <业务名称>-session-3.md
```

## 会话切换前的强制交接动作

在第一会话结束和第二会话结束时，AI 必须同时完成以下动作：

1. 更新对应的 session 文件
2. 把下一会话需要的关键信息补齐到 `## 下一会话启动提示词`
3. 在对话中再输出一份**可直接复制**的提示词代码块，供用户开新会话时粘贴

> **日期格式约定：** 所有模板中的 `<日期>` 占位符统一使用 `YYYY-MM-DD` 格式，与 plans 和 sessions 的文件命名保持一致。

## 工作流执行规则

**始终从阶段零开始做快速检查。**  
即使是跨会话恢复，也先确认：

- 当前工作模式
- 是否已有设计与计划
- 是否已有状态文件
- 当前是否已经通过第二会话的集成测试

已完成的阶段可以快速通过，但不能靠猜测跳阶段。

## 开发流程

### 阶段零：工作位置选择

> **铁律：每次会话一开始都必须先问，AI 不可自行决定。**

固定询问：

> 「这次任务是在主工作区直接修改，还是新建功能工作区开发？」

- **用户选择主工作区**：记录"主工作区模式"，本会话可直接在仓库根目录工作
- **用户选择功能工作区**：使用 `parallel-worktree-dev`，先按规则保存主工作区，再创建 `<repo-name>-<名称>/`

> **退出信号：** 工作模式已明确并写入状态文件

### 阶段一：需求分析

使用 `brainstorming` 完成需求边界、风险、方案与设计确认。

快速通过条件：

- 已存在对应设计文档
- 用户已明确确认设计方向

> **退出信号：** 设计已确认

### 阶段二：任务规划

使用 `project-planner` 生成实现计划。

进入下一阶段前必须同时满足：

1. 已存在计划文件 `Docs/plans/<业务名称>/<功能名称>-execution-plan.md`
2. 计划包含任务、文件清单、步骤、验证标准
3. 用户已确认计划

> **第一会话结束点：** 阶段二完成后，保存状态，生成可直接复制的第二会话提示词，并通知用户开启第二会话

### 阶段三：执行开发 + 批次审查 + 集成测试

> 第二会话的主体全部放在这里完成。

#### 3.1 执行与批次审查

1. 使用 `executing-plans` 执行计划
2. 每一批任务完成后立即审查：
   - `code-reviewer`
   - `pragmatic-clean-code-reviewer`
   - `python27-syntax-reviewer`
3. 审查发现问题就地修复，再继续下一批

#### 3.2 计划任务完成后的功能测试

- **功能工作区模式（mcdev-tools 直测）**：
  1. 确认 `.mcdev.json` 的 `included_mod_dirs` 指向功能工作区
  2. 终止游戏并重新启动 mcdk，直接加载功能工作区代码
  3. 进行测试（手动或通过 `mcdk_dev` MCP 让 AI 辅助）
  4. 测试失败 → 直接在功能工作区修复 → 重启游戏 → 重新测试（无需任何 git 操作）
  5. 测试通过 → 询问用户是否合并到主工作区（集成步骤）
- **主工作区模式**：
  1. 无需 merge，直接在当前工作区做测试
  2. 若测试失败，直接继续本阶段修复并重新测试

#### 3.3 阶段退出条件

只有同时满足以下条件，阶段三才算完成：

1. 计划中的实现任务已全部完成
2. 批次审查问题已处理完毕
3. 当前工作模式下的集成测试已通过

> **第二会话结束点：** 阶段三完成后，保存状态，生成可直接复制的第三会话提示词，并通知用户开启第三会话

### 阶段四：最终审查

> 第三会话从这里开始。

使用 `code-reviewer` 做功能级最终审查，目标是把"执行阶段已经能跑通的代码"再做一次整体体检。

建议组合：

- `code-reviewer`
- `pragmatic-clean-code-reviewer`
- `code-simplifier`
- `python27-syntax-reviewer`

#### 4.1 修复最终审查结果

- 若最终审查发现问题，直接修复
- 若修复产生了代码改动：
  - **功能工作区模式**：用 mcdev-tools 直测验证修复（修改 `.mcdev.json` 指向功能工作区，重启游戏）
  - **主工作区模式**：直接做最小回归测试

> **退出信号：** 最终审查通过，且最终审查修复已验证

### 阶段五：收尾

1. 清理临时调试代码与 `debug_*.log`
2. 确认状态文件已记录最终结果
3. 生成功能总结
4. 用户确认后清理功能工作区与分支

#### 收尾门禁

1. 搜索 `_dbgLog|_dbgNotify|DEVONLY_START|DEVONLY_END|print\(`
2. 确认没有遗留 `debug_*.log`
3. 确认用户是否要求保留功能工作区

## 关键提醒

1. **测试走直测**：功能工作区通过 mcdev-tools 直接测试，不为测试而合并
2. **合并是集成步骤**：只在功能测试通过后才执行合并
3. **不要把最终审查提前到功能测试前**：最终审查是第三会话的内容
4. **不要跳过工作位置询问**：主工作区还是功能工作区，必须由用户决定
5. **用户可能自行合并或回退**：AI 应识别并跳过已完成的步骤
