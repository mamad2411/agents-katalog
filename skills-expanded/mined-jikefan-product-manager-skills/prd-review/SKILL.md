# PRD 产品需求评审

产出开发与产品能直接对齐的评审意见。找出“原文怎么写、系统现在实际怎么做、哪些业务含义仍未决定”，用不熟悉技术的产品也能理解的话说明原因、具体影响、建议补写和确认问题。代码用于核实事实，不能把理解代码的负担交给产品。默认只读，不自动修订原PRD、实现功能或向产品发送意见。

若用户的想法尚未形成需求、需要一起讨论真正要的效果，可在其要求共同澄清时衔接可用的 `prd-discovery`。本skill仍负责审查已有材料，不自动切换成无限追问或代写新方案。正式评审应同时取得已明确的最新决定，避免只依旧原型否定新意图；没有得到的决定也不能猜。

## 先固定证据和评审范围

- 遵守当前项目的适用约定，按需读取相关产品资料、业务规则和现有实现，不假设固定的说明文件名或目录布局。明确需求版本、涉及模块及可取得的实现版本；有仓库时记录所读分支与提交。代码事实只支持已读版本，不能代指线上已经部署。
- 有文档链接时读取原文及承载规则的附件、HTML内PRD标签、交互状态和相关评论。摘要、截图和默认首屏不能替代完整规则。使用可用文档连接器或相应skill；只有与结论相关的附件才继续展开。
- HTML的文案、线框和脚本可能相互矛盾。分别定位，不能将演示代码或固定样例直接认定为产品意图、数据定义或真实业务能力。无需运行原型即可读到规则时，先静态核对。
- 把用户明确澄清、PRD正文、原型、现有业务契约、代码实现和历史说明分开记录。最新明确澄清说明目标意图，代码说明当前行为，两者都不能抹去其他来源里的矛盾。来源不一致本身就是待修订项。
- 缺原文或代码时，先做能完成的审查，清楚限定结论。拿不到代码不能声称“与现有逻辑兼容”；也不能因此停止全部表达评审。只询问无法从已有资源取得、会改变判断的信息。

需要判断背景资料从哪里取得、如何区分产品约定和实现事实时，按需读取 [项目资料与事实核对](references/project-context.md)。没有仓库的团队也可使用，不要求另建一套知识库。

## 一、检查产品是否表达了唯一可实现的含义

先用少量文字或表格固定实际对象、入口、状态、条件、结果和计数单位。不要先替产品设计一套新系统。

主动检查产品没有明说的前提。页面上有一个名称、标签或分区，不代表系统已经按它区分类别或执行不同规则。先核实哪些只是显示文字，哪些是正式分类，哪些由独立开关或条件决定。不要将产品用词直接翻译成代码中的类型或能力。

对名称与能力的关系，追到保存、读取和实际判断处核实，不只看有没有名为type的字段。可用“只改名字，功能会不会变”作反例。若代码确实按名称判断，也要如实说明已有行为与限制，不能反过来一概断言名称都不影响逻辑。

重点找能产生两个不同实现的地方：

- 同一个词是否指不同对象，例如活动、场次、展示分组、页面层级、展示位置。一个分组含多场时，数量限制到底数哪个对象？
- 产品是否把“名字不同”误认为“系统中已有不同类别”？若PRD要求某类自动适用特殊行为，现有系统靠什么识别，还是需要新增一种可配置区别？
- 开关是在控制导航、展示、报名资格还是活动状态？“开启二级”与“在二级可见”不能凭字面认定相同。
- UI点击后去哪里，日期或筛选作用在哪里，返回哪一页，空态和失败是否明确？图与文字描述是否一致？
- 黑白名单、UID、标签、人群包是交集还是并集？继承关系、优先顺序、缺资料和游客如何处理？
- 人群是动态查询还是固定名单？“参加过”“上次”“有效”“最新”“实时”“默认”“最多”“权重”是否有稳定、可验证的定义？
- 数量、概率、优先级、展示资格和执行资格是否混用？先筛后排与先取N再过滤的结果不同。
- 按钮或文案是否暗含未定义能力？例如预览只显示布尔值，却要求解释整体排名。

每个歧义至少给一个区分不同解释的具体场景。只问能改变实现的选择，不纠结无业务影响的用词。

核对关键决策能否实现PRD声明的目标。目标与方案冲突时，给出用户实际走一遍就会失败的场景；体验偏好或个人喜欢的设计不能冒充逻辑错误。

## 二、对照现有代码判断差异属于哪一种

沿真实入口追到实际决策者，而非只搜到同名字段：

`用户动作 → 页面或接口 → 读取事实 → 业务判断 → 写入或外部效果 → 用户最终结果`

按需求选取必要上下游。检查真实消费者、数据精度、权威状态、已有约束、兼容分支和实际适用范围。测试和迁移用于理解语义，不以“测试文件存在”证明行为正确。

把差异区分为：

1. **有意的产品变更**：可以改变现状。指出需要同步调整的调用方、兼容或迁移，不能因为代码目前不支持就判产品错误。
2. **无意冲突或错误前提**：PRD假设的字段、状态、身份、数据或能力与事实不符。用具体执行路径说明影响，提出最小纠正。
3. **目标正确但数据或机制不足**：指出缺哪项事实或执行保证，例如只有出生年份却要求精确生日边界。给补数据或调整口径的选择。
4. **设计选择仍未决定**：现状与多种目标都合理。给不同选择的结果和需产品决定的点，不能替产品猜答案。
5. **可直接复用的现有能力**：说明真实拥有者与适用限制，避免重复造模块。

现有代码不自动等于正确业务规则。若代码、正式契约与已批准决策冲突，标出证据和待裁定范围，不维护错误实现，也不静默把PRD改成代码的样子。

## 三、验证规则闭环与反例

只审查需求实际触及的风险，不给所有PRD套支付、并发或合规大清单。按需参考 [易误读规则与反例](references/review-patterns.md)。

对于重要决策，走通正常路径及最容易区分解释的边界：

- 默认、缺数据、游客和登录切换；同一对象从列表、分享或其他实际入口进入。
- 同一集合在不同页面、分页、日期、缓存及预览中的一致性。
- 配置或用户事实变化后，已有记录、在途动作与历史指标怎么解释。
- 有副作用时才检查重复、失败、补偿及最终服务端执行边界。

需要用代码实验确认非明显事实时，使用隔离输入和现有允许的验证方式；不得为PRD评审改生产数据、发送真实消息、触发报名支付或执行迁移。没有实际运行就明确标为静态推演。

反例必须能说明用户看见什么、操作什么、两种实现各得到什么，以及哪项决定尚缺。不要用假设堆出没有具体影响的风险。

## 四、用产品能理解的话交付评审

评审主体默认写给不熟悉技术的产品。先讲“哪里会被误解、现在实际如何、用户会遇到什么、建议怎样写”，再给证据。产品不读代码附录，也应知道下一步补哪条规则或作哪个选择。

- 使用具体页面、按钮、用户操作和结果解释原因。少用“模型不一致”“缺少类型判别”“接口契约不闭环”等概括；需要这些判断时，先翻译成具体场景。
- 文件、函数、字段、提交和技术细节放在对应问题后的“开发核对依据”或统一附录，并保留问题编号对应关系。正文可引用产品能理解的核实结论，不能只丢一段代码让产品自己看。
- 必须使用技术名词时，第一次就解释它在本需求中的含义。说人话不等于丢掉条件、边界和证据，也不把真实冲突轻描淡写成“措辞建议”。
- 把产品要决定的业务行为与开发要核实的数据来源、字段和实现方式分开。不要让产品决定查哪个数据库字段，也不要替产品选择用户应当获得什么能力。
- 已经明确的决定只要求回写PRD，不重新发问。例如已经确定由二级开关控制跳转，就建议写明“点击行为由开关决定，与分组标题无关”。

标题与分类误解的产品表达示例，见 [易误读规则与反例](references/review-patterns.md)。

## 五、交付可直接处理的问题清单

先给评审结论和影响范围，再按严重性列有证据的问题。默认判断产品需求能否进入技术方案阶段，可使用“可进入技术设计”“补齐以下产品决策后进入技术设计”“部分范围可进入技术设计”“现有证据不足以判断”。一个局部缺口不自动阻塞所有独立工作，也不能将需求清楚等同于可以跳过必要技术设计直接上线。

评审应检查技术团队是否仍需猜测业务含义。未指定数据库、API、模块拆分或框架本身不构成PRD缺陷；只把影响用户结果或已有业务约束的工程事实反馈为产品问题，具体实现选择由技术团队负责。

严重性按具体后果判：P1会造成核心流程错误、资格或资金等重要约束失效、或重大范围返工；P2会产生不同实现、缺口或验收不一致；P3为不改变核心规则的澄清改进。P0只用于已有证据支持的紧迫严重问题，不为普通需求草案滥用。

每个问题使用稳定编号，分类可为表达歧义、规则缺失、材料冲突、现有契约冲突、数据不足、实现影响。先给产品能读懂的标题和说明。内容可以压缩成几段，但必须让读者取得：

- **定位与原文**：PRD章节、原型操作或附件函数；引用最短必要片段。没有行号就用可复找的章节和定位词，不编造行号。
- **问题和反例**：哪两种解释或哪条事实冲突，谁在什么场景下会得到不同结果。
- **核实依据与边界**：正文先说清系统目前的实际行为，开发依据中提供相关文件、符号、行号及已核对版本。明确事实、推断和未验证处，不拿未实现字段当现状。
- **建议补写或纠正**：给可直接粘贴的规则句子。尚未决定时列出少量实质选项及影响，建议明确标为建议。
- **产品需要回答的问题**：一个能作决定的具体问题，避免“请补充更多细节”或让产品重新描述整份需求。用户已经明确的选择标为“已决定，需回写材料”，不再次提问；纯工程核实任务交给开发，不伪装成产品决策。
- **验收例子**：说明选择定稿后，如何验证这一项不再有两种结果。

合并同一根因的重复发现。将产品需要决定的问题集中成一份可转发清单，与开发应自行核实的技术任务分开；未获授权不发送。保留已明确且与现状契合的关键规则，避免报告只有泛泛否定。

没有发现重大问题时直接说明，列出已覆盖范围和实际剩余限制。不要为了凑数量制造问题，也不要将候选改进写成必需功能。

## 评审自检

- 是否把已经明确的用户选择重新当成问题？是否把我的建议当成已批准需求？
- 是否把名称、标签或展示文案当成已有分类和功能？是否沿真实判断核实了产品的隐含前提？
- 不懂技术的产品不看代码附录，是否仍能理解原因、后果、建议及需要回答的问题？
- 是否实际读取了规则所在附件与关联实现，而不是根据截图、字段名或旧记忆猜测？
- 同一项是否给出了可复找证据、具体反例和可回答的补全问题？
- 是否把正常的新需求误判成错误，或将实现缺口伪装成产品已确定的规则？
- 是否仍含未确认假设，却把结论写成“完整可开发”？

默认将review直接交付给用户。需要落盘时遵守当前工作空间文档约定；修改原PRD、发布评审、分配任务或转入实现，须来自用户相应指令，不从“review”一词推导额外授权。
