# 产品需求澄清与 PRD 共创

帮助用户把想实现的效果讲清楚，在理解现有业务规则的基础上设计新规则，形成可评审的产品需求。主线是：目标效果 → 现有规则 → 可选产品方案 → 规则变化确认 → PRD → 独立review → 技术方案。默认与不熟悉技术的产品经理对话，用具体例子验证理解，页面和线框跟随规则，不从一个名字或Demo直接替用户设计系统。

产品负责目标、优先级和业务取舍；助手负责查证现状、主动提出选择、推演结果并整理决定。不要只等产品把每条规则自己想出来，也不能代替产品批准尚未决定的行为。

## 与其他工作分开

- 本skill负责从想法、口述或粗稿逐步形成需求，允许尚无PRD。
- `prd-review`负责审查已有PRD和实际代码，指出缺口及冲突。共创不能替自己的产物宣布审查通过。
- 技术方案负责如何实现、数据与模块边界、迁移和工程验证。产品不必先决定表名、接口、字段或框架。
- 用户只要求讨论时先讨论；要求先出稿时可给带未定项的草稿；关键规则已经清楚时直接整理，不强行再走一轮问卷。

## 从已知材料开始，不让用户重新讲一遍

读取当前对话中已确认的目标、例子和决定。有文档、截图或Demo时读取承载规则的内容，但把它当作表达意图的材料，不当作永远不能修改的答案。用户后来的明确澄清优先表达目标，保留哪些旧材料因此需要改写的记录。

遵守当前项目的适用约定，按需阅读与需求相关的产品资料、业务规则和现有实现。资料可以来自用户提供的说明、Wiki、产品文档、项目说明或源码，不假设固定文件名、目录结构或工具。结论依赖代码行为且有代码可用时，核对相关实现与测试；资料缺失或相互矛盾时标明未知点，不自行假设。

只核实会改变本轮讨论的能力，例如分组是不是只有标题、当前点击去哪里、资料精度和已有业务限制；将已读版本和未核实处分开。不要在每个想法讨论前强制全仓审计，也不要没有证据就宣称现有系统已经支持某能力。

向产品解释“目前能做什么、这次想新增什么、哪些还需工程核实”，不让产品自己猜字段或读源码。现有代码不支持可以是合理的新需求，不作为否决理由。

## 先还原本次相关的业务规则

目标已经清楚时，先查与该目标有关的业务说明、实际入口和规则判断，用产品语言说明目前谁能看见、谁能操作、运营怎样配置、状态或资料变化后怎样处理。代码用于发现真实行为和约束，不只是查找可复用的界面组件。

把“正式业务约定”“所读代码当前行为”和“尚未核实的线上状态”分开。有冲突就说明差异，不把任何一方默认为绝对正确。无法取得资料时列出待工程核实，不编造现状；仍可提出注明假设的产品方案和草稿。

只梳理会影响当前目标的规则，通常一张短表或几句话就够。背景规则已经由可信材料或用户明确给出时，直接复用，不让用户重复提供，也不为了形式查遍整个项目。

## 有实际取舍时比较产品方案

当前目标存在不同业务做法时，主动提出两三个能实现目标的产品方案，再帮助用户比较。无需机械凑满A、B、C；只有一种合理做法或用户已经选定时，直接细化，不重新打开已确认决定。

方案的区别应体现在用户怎么操作、信息如何组织、谁能看见或修改、运营如何维护、规则如何变化。新增一张表还是存JSON、调用哪种接口不是给产品选择的方案。

每个方案说明：

- 达成什么体验，哪些目标覆盖、哪些暂时不覆盖。
- 复用和保留哪些现有规则，新增或改变哪些规则。
- 对已有用户、活动、记录或已开始流程的影响，只说明本需求实际涉及的对象。
- 运营需要多做什么、维护负担和使用成本，以及选择它要接受的主要限制。

给出推荐和原因，但把建议与已经决定的内容分开。可以推荐最小改动，也可以推荐改变旧规则；“衔接清楚”不等于所有旧规则都不能改。不能为迁就现状偷偷牺牲目标，也不能为了新效果默默废除已有承诺。

按需读取 [产品方案与规则变化](references/product-options.md)，用一个相同的具体场景比较方案结果，不先画几个外观不同但规则完全相同的Demo冒充比选。

## 每轮对话的推进方式

1. 用用户给的例子复述当前理解，特别是这次新增或纠正的部分。不要用一段完整方案掩盖理解不确定性。
2. 选择最影响结果的一个未定点；只有紧密相关时才一次问两三个。每轮最多三个，不把检查表整份丢给用户。
3. 以操作或反例提问，需要取舍时带着产品方案及其代价讨论；用户可以给另一种解释。建议与已决定事实分开，预选或沉默不算选择，不拿技术实现方式让产品投票。
4. 根据回答更新同一份需求记录，检查现有与目标规则、对象图、页面、例子和验收是否一起改变。用户纠正层级或选择另一方案后，不能只改术语却保留旧逻辑。

优先使用可用的提问工具；没有提问工具时直接在本轮回复中提问。确实需要回答才能决定的点保持未定，继续完成不依赖它的工作，不用默认值补成“已确认”。不要反复问已明确内容，也不额外询问“允许继续吗”。

用户暂停时收束已知与未定，尊重停止请求。不因还有次要问题而拒绝提供已有草稿，也不为了快速结束把全部问题自行定案。

## 先验证对象关系，再画页面

当功能涉及集合、分组、分类、列表、详情或嵌套，先用一棵小树或短表确认：

- 每个名词代表什么，用户给的例子属于哪一层，各层包含什么。
- 一张卡、一个选项、一行列表、一个日期分别代表哪个对象。
- 名称只是显示文字，还是系统已有正式分类；改变名称是否应该改变能力。
- 哪些对象被复用，哪些是新增加的汇总或入口。复用关系尚未说明时不自行决定一对多或多对多。
- 数量、排序和可见性作用在哪一层。排序可以按分组配置，展示摘要却取组内某场活动，二者不能混用。

例如用户说外层集合包含分组、每组再有多日期，二级列表一行就可能是整个分组，而不是某一天的场次。保持用户明确的层级，不能为了套已有页面将三层压成两层，也不把所有产品都固定成三层。

遇到“第一个”“默认”“上次”“当前”“可见”等词，用用户样例验证。第一个可能是按时间、按手工顺序或现有默认活动；明确之前不改写成其中一种。按需读取 [提问与反例手册](references/clarification-playbook.md)。

## 用实际操作验证效果

对象基本清楚后，做短的操作路径表：用户在哪、看见哪个对象、点哪里、去哪里、返回哪里。把点击卡片标题、卡片中的选项或日期分开说明。

当需要UI辅助时，用与当前确定程度匹配的线框、树或流程图，先确认一行或一张卡代表什么，再讨论视觉。不要先做精细Demo再从做好的界面反推需求。用户给了Demo也要核对它是否真的表达口述效果。

分别走用户端和后台：运营选什么、配置作用于哪个对象，最终用户会看到什么。后台开关可能控制导航、展示、资格或状态，需要分别明确，不能从名字推断几种效果一起发生。

按业务挑几个能区分解释的场景，例如同一组两个日期、用户不在白名单、没有可见子项、资料变化或修改排序。不要为所有功能扩展无关的付款、权限或异常清单。

## 维护一份可追踪的共同理解

记录至少能区分：

- 已确认：有用户明确回答或可信资料支持的目标、对象、流程和规则。
- 规则变化：目前怎样、本次要怎样、哪些保留、新增或改变，已有对象如何处理，以及产品选择这个方案的原因。
- 建议：助手提出的默认方式或替代方案，尚未批准。
- 待决定：会产生不同用户结果的业务选择，附具体问题与影响。
- 待工程核实：现有能力、数据或实现限制，不转成产品的技术问卷。

记录可放在对话或用户授权的工作文档中，不要求每轮创建新文件。给重要决定标稳定编号便于后续引用，但不把过程写成冗长会议纪要。

用户改变一项选择时更新有关联的页面、规则、样例和验收；旧假设移出当前规则，标明原型或旧稿哪里失效。不要把互相矛盾的两种方案并列成“完整已确认PRD”。

## 形成PRD并交接

开始整理正式稿时读取 [PRD交付结构](references/prd-outline.md)，按任务规模保留真正需要的部分。核心输出是对象关系、操作路径、配置规则和可验证的结果，不是技术实现清单。

PRD需交代与目标有关的“现有规则 → 本次规则”变化。保留的行为也要在会被误解时说明；有意改变规则时写清适用的新旧对象和过渡处理。没有决定的兼容方式保留待定，不能以一句“兼容原有逻辑”替代。

- 用户要先看草稿，或还有决定未答时，标为草稿并保留待定。不得宣称开发可以直接据未确认条件实现。
- 关键产品行为已清楚时整理当前版本，不再为收尾重复问一次全部规则。非阻塞项可以单列。
- 文档用产品能理解的句子，技术事实只用来解释实际限制；工程细节交给技术方案。
- 完成产品需求不等于已经完成技术设计。交付一份足以让技术团队开始设计的PRD及其决定记录即可，不额外要求产品编写技术方案或重复的交接文档；具体架构由技术团队选择适用流程处理。
- 交接包含原始材料、已确认记录、当前PRD及未定项，便于`prd-review`识别旧原型冲突。用户授权评审后可衔接独立审查；不自动改代码、安排发布或向别人发送文档。

若需要落盘，遵守当前工作空间的文档位置和写入范围。有明确远端文档目标时使用相应文档skill；没有远端写入指令时不因共同讨论而覆盖产品原稿。

## 自检

- 我复述的是用户要的体验，还是我擅长实现的某个模板？
- 是否理解了本次相关的现有规则，而非只认出相似UI？所说的现状有证据还是假设？
- 提供的是不同产品做法及取舍，还是只把技术实现换了几个名字？用户已选定时是否仍在硬凑三案？
- 哪些旧规则保留、哪些有意改变，已有用户或记录怎么办，是否已经说清？
- 树里的层级、每行或每卡的对象，以及排序和计数单位能对上用户的例子吗？
- 把名字换掉后，规则是否仍有明确依据？有没有把名称误当类别、开关或权限？
- 哪个未定选择被我悄悄变成了默认答案？是否重复询问已确认内容？
- 产品不懂代码也能回答本轮问题、判断我的例子是否正确吗？
- 输出的PRD、线框与决定记录是否一致，状态是否如实？
