# Supply Chain Security: SLSA & SBOM

## Purpose

Software supply-chain attacks target the *build and distribution
pipeline* rather than application code directly — a compromised build
server, a poisoned dependency, a tampered artifact substituted between CI
and deployment, or a maintainer account takeover injecting malicious code
upstream. Two complementary practices address this: **SBOMs** (Software
Bill of Materials) give visibility into exactly what components — and
which versions — make up a given artifact, so that when a new
vulnerability is disclosed you can answer "are we affected, and where"
without an audit; and **SLSA** (Supply-chain Levels for Software
Artifacts) is a framework describing build-integrity practices (source
control, isolated builds, provenance generation) that make it harder to
tamper with an artifact undetected between source and consumption. Both
are necessary infrastructure for a mature security program, and neither
is a vulnerability scanner — an SBOM lists components, it does not tell
you they're vulnerable (that's SCA's job); SLSA provenance proves *how* an
artifact was built, not that the code it contains is safe.

## When to use

- The user asks to "generate an SBOM" for a project, container image, or
  release artifact — often driven by a customer contractual requirement,
  a regulatory expectation (e.g. US EO 14028-influenced procurement
  requirements), or an internal visibility goal.
- The user wants to sign build artifacts/container images and verify
  signatures before deployment, to detect tampering between build and
  deploy.
- The user is asked to state or improve a build pipeline's SLSA level and
  needs to understand what each level actually requires and covers.
- A new CVE is disclosed and the team needs to search existing SBOMs to
  find every artifact containing the affected component, instead of
  re-scanning everything from scratch.
- The user wants provenance attestations wired into a release pipeline so
  downstream consumers (or an admission controller) can verify an
  artifact was built by the expected pipeline from the expected source.
- The user is evaluating a vendor/third-party component and wants to
  understand what supply-chain assurances (or lack thereof) it provides.

## Prerequisites & environment

- **Syft** (Anchore) — generates SBOMs in CycloneDX or SPDX format from
  source directories, container images, or filesystems:
  ```bash
  syft myorg/myapp:1.4.2 -o cyclonedx-json=sbom.cdx.json
  ```
- **CycloneDX** and **SPDX** are the two dominant SBOM formats; CycloneDX
  originated in the AppSec/OWASP community and has stronger native
  vulnerability/VEX linkage, SPDX originated in license-compliance
  tooling and is an ISO standard (ISO/IEC 5962:2021) with broader legal/
  procurement recognition. Many tools support emitting either — pick
  based on what your consumers (customers, regulators, internal tooling)
  actually require; supporting both is common for products with external
  SBOM obligations.
- **cosign** (Sigstore project) — signs and verifies container images
  and arbitrary artifacts, supports both long-lived keypairs and
  **keyless signing** (short-lived certificate from Sigstore's Fulcio CA
  tied to an OIDC identity, e.g. a CI job's OIDC token — no long-term
  private key to manage or leak).
- **SLSA framework** (`slsa.dev`) — defines build-integrity levels (L1
  through L3 in the current v1.0 model) describing provenance generation
  and build isolation, generated by tools such as `slsa-github-generator`
  for GitHub Actions or in-toto for a custom pipeline.
- A container/artifact registry that supports storing signatures and
  attestations alongside images (OCI-compliant registries support this
  natively via the referrers API or cosign's tag-based convention).
- Note the scope honestly: none of this replaces vulnerability scanning —
  pair with [software-composition-analysis-sca](../software-composition-analysis-sca/SKILL.md)
  for that — and none of it inspects the *quality or safety* of the code
  itself, only its origin and composition.

## Step-by-step guidance

1. **Generate an SBOM at build time**, not after the fact, so it reflects
   exactly what was built and shipped:
   ```bash
   syft dir:. -o cyclonedx-json=sbom.cdx.json
   syft myorg/myapp:1.4.2 -o spdx-json=sbom.spdx.json
   ```

2. **Attach the SBOM to the artifact** in CI so it travels with the
   release rather than living in a separate, easily-desynced location:
   ```yaml
   - name: Generate SBOM
     run: syft ${{ env.IMAGE }} -o cyclonedx-json=sbom.cdx.json
   - name: Attach SBOM to image
     run: cosign attach sbom --sbom sbom.cdx.json ${{ env.IMAGE }}
   ```

3. **Sign the artifact** so consumers can verify it hasn't been
   substituted or tampered with after your build produced it. Keyless
   signing in CI (recommended over managing long-lived keys):
   ```yaml
   permissions:
     id-token: write   # required for Sigstore keyless OIDC signing
     contents: read
   steps:
     - name: Sign image (keyless)
       run: cosign sign --yes ${{ env.IMAGE }}@${{ steps.build.outputs.digest }}
   ```

4. **Generate SLSA provenance** describing the build (source repo/commit,
   builder identity, build parameters) as a signed attestation. On GitHub
   Actions, the `slsa-github-generator` reusable workflow produces this
   without your pipeline needing to implement the attestation format
   itself:
   ```yaml
   jobs:
     build:
       # ... build and push image, output digest ...
     provenance:
       needs: [build]
       permissions:
         id-token: write
         contents: read
         actions: read
       uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.0.0
       with:
         image: ${{ needs.build.outputs.image }}
         digest: ${{ needs.build.outputs.digest }}
   ```

5. **Verify signatures and provenance before deploy**, not just at
   publish time — verification with no enforcement point is just logging:
   ```bash
   cosign verify --certificate-identity-regexp "^https://github.com/myorg/myapp/.github/workflows/release.yml@refs/tags/.*$" \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com \
     myorg/myapp:1.4.2

   cosign verify-attestation --type slsaprovenance \
     --certificate-identity-regexp "^https://github.com/myorg/myapp/.*$" \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com \
     myorg/myapp:1.4.2
   ```
   In Kubernetes, enforce this at admission time with a policy engine
   (see [policy-as-code-guardrails](../policy-as-code-guardrails/SKILL.md))
   such as Sigstore's `policy-controller` or Kyverno's `verifyImages`
   rule, rather than relying on a human running `cosign verify` manually.

6. **Map current practice to a SLSA level honestly**, and state the gap,
   not just the target:
   - **L1** — provenance exists and is documented, but the build process
     isn't verified or tamper-resistant beyond that.
   - **L2** — build runs on a hosted/managed build service, provenance is
     generated automatically and signed; provides some protection against
     source tampering after the fact.
   - **L3** — build runs in an isolated, ephemeral, hardened environment
     that prevents even the build definition from tampering with the
     provenance it emits (e.g. GitHub-hosted runners with the
     `slsa-github-generator` reusable workflow model this because the
     provenance-signing step runs in a separate, more privileged workflow
     than the untrusted build step).
   Most self-hosted-runner setups without additional isolation work top
   out around L1-L2 in practice — say so explicitly rather than claiming
   L3 without the isolation guarantees it requires.

7. **Store and query SBOMs centrally** (a registry, Dependency-Track, or
   similar) so that when a new CVE drops, you can search "which shipped
   artifacts contain component X at version Y" in seconds instead of
   re-scanning your entire fleet.

## Best practices

- Generate the SBOM from the actual build output (built image / final
  artifact), not from source manifests alone — a source-only SBOM misses
  anything pulled in during the build (base image OS packages, compiled
  dependencies) that the shipped artifact actually contains.
- Prefer keyless (Fulcio/OIDC) signing over long-lived cosign keypairs in
  CI — it removes an entire class of "the signing key leaked" incidents,
  since each signature's certificate is tied to a short-lived, workflow-
  scoped identity instead of a static private key.
- Be precise about what verification actually checks: signature
  verification proves the artifact matches what was signed and the
  signer's identity matches an expected pipeline — it does not prove the
  code is free of vulnerabilities or malicious logic. State this
  explicitly when documenting controls for an audit or customer, rather
  than implying "signed" means "safe."
- Enforce verification at a real control point (admission controller,
  deploy-gate script) — an SBOM or signature nobody checks before
  deployment is documentation, not a control.
- Don't claim a SLSA level you haven't actually verified against the
  spec's requirements for that level; L3 in particular requires build
  isolation guarantees that self-hosted runners without extra hardening
  typically do not provide.
- Keep SBOMs queryable in aggregate (a central store, not just per-build
  artifacts scattered across CI logs) — the main operational payoff of
  SBOMs is fast "are we affected" answers during incident response, which
  requires being able to search across your whole fleet at once.

## Common pitfalls

- **Symptom:** The team says "we have SBOMs, so we're supply-chain
  secure" and treats the control as complete.
  **Fix:** Clarify that an SBOM is an inventory, not a scan — it must be
  paired with a vulnerability feed/SCA tool
  ([software-composition-analysis-sca](../software-composition-analysis-sca/SKILL.md))
  to actually surface risk, and with signing/provenance to address
  tampering, which an SBOM alone says nothing about.

- **Symptom:** Images are signed with cosign, but nothing in the deploy
  path actually calls `cosign verify` — a compromised or unsigned image
  deploys successfully anyway.
  **Fix:** Add an enforcement point: an admission controller policy
  (Kyverno `verifyImages`, Sigstore `policy-controller`) that rejects
  unsigned/unverifiable images at the cluster boundary, not just a
  CI step that signs and moves on.

- **Symptom:** A long-lived cosign signing key is stored as a CI secret,
  and the team worries about (or eventually discovers) it leaked.
  **Fix:** Migrate to keyless signing via OIDC (Sigstore Fulcio), which
  eliminates the long-lived key entirely in favor of short-lived,
  workflow-identity-scoped certificates — nothing persists to leak.

- **Symptom:** The org claims "SLSA Level 3" in a security questionnaire,
  but the build runs on a self-hosted runner with no additional isolation
  between the build step and the provenance-signing step.
  **Fix:** Re-assess honestly against the actual L3 requirements (isolated,
  ephemeral build environment where the build definition cannot influence
  its own provenance) — either adopt a generator model that provides that
  isolation (e.g. `slsa-github-generator`'s separate reusable workflow) or
  report the accurate current level (likely L1-L2) instead.

- **Symptom:** SBOM generation is added to CI, but SBOMs pile up as build
  artifacts with no central index, so answering "are we affected by
  CVE-2026-XXXXX" still requires manually opening dozens of files.
  **Fix:** Push generated SBOMs into a central store with search/query
  capability (Dependency-Track, a registry with SBOM-search support, or
  even a simple indexed object-store + database) as part of the pipeline,
  not as a manual follow-up task.

## Worked example

A container-image release pipeline adds SBOM generation, keyless
signing, and SLSA provenance, then a Kubernetes admission policy enforces
verification before deploy.

`.github/workflows/release.yml` (build/sign/attest stage):
```yaml
name: release
on:
  push:
    tags: ['v*']

permissions:
  contents: read
  id-token: write
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      digest: ${{ steps.push.outputs.digest }}
      image: ghcr.io/myorg/myapp
    steps:
      - uses: actions/checkout@v4
      - name: Build and push
        id: push
        run: |
          docker build -t ghcr.io/myorg/myapp:${{ github.ref_name }} .
          docker push ghcr.io/myorg/myapp:${{ github.ref_name }}
          echo "digest=$(docker inspect --format='{{index .RepoDigests 0}}' ghcr.io/myorg/myapp:${{ github.ref_name }} | cut -d@ -f2)" >> "$GITHUB_OUTPUT"

      - name: Generate SBOM
        run: syft ghcr.io/myorg/myapp:${{ github.ref_name }} -o cyclonedx-json=sbom.cdx.json

      - name: Sign image (keyless)
        run: cosign sign --yes ghcr.io/myorg/myapp@${{ steps.push.outputs.digest }}

      - name: Attach SBOM
        run: cosign attach sbom --sbom sbom.cdx.json ghcr.io/myorg/myapp@${{ steps.push.outputs.digest }}

  provenance:
    needs: [build]
    permissions:
      id-token: write
      contents: read
      actions: read
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.0.0
    with:
      image: ${{ needs.build.outputs.image }}
      digest: ${{ needs.build.outputs.digest }}
```

Kyverno admission policy enforcing signature verification cluster-side:
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-cosign-signature
      match:
        resources:
          kinds: [Pod]
      verifyImages:
        - imageReferences: ["ghcr.io/myorg/*"]
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/myorg/myapp/.github/workflows/release.yml@refs/tags/*"
                    issuer: "https://token.actions.githubusercontent.com"
```
With this in place, an unsigned or tampered image fails admission with a
policy violation instead of silently running — and the accompanying SBOM
lets the team answer "do we ship `libfoo` 2.3.1 anywhere" via a registry
or SBOM-index query the next time a CVE is disclosed against it.
