# 智能体的四组件缺口诊断

## R — 原文 (Reading)

> 理解智能体，只需要记住一个公式：智能体=模型+工具+记忆+知识。这4个组件缺一不可。
>
> — 李开复，第3章《拆解智能体：模型+工具+记忆+知识》

> 只要有一个组件缺位，它们构建的闭环就会在相应节点断开，这往往正是企业试用的AI工具"看起来很聪明，却不好使"的原因。因此，下次你试用一个AI工具并觉得"不对劲"的时候，别怪模型，先问问：模型的记忆在哪儿，能连接什么工具，是否理解企业知识？
>
> — 李开复，第3章

> 他的聪明暂时没有用武之地，因为聪明解决的是"怎么做"，而他卡在了"这里的规则是什么、这里的入口在哪儿、这里的话是什么意思"上。
>
> — 李开复，第6章（名校毕业生的入职第一天）

---

## I — 方法论骨架 (Interpretation)

一个能干活的 AI 系统由四个组件构成，任何一个缺位，闭环就在那个节点断开：

- **模型**——认知引擎。负责把模糊的意图拆解成有顺序的具体动作。它不天然拥有实时信息，也无法直接影响外部世界。
- **工具**——与外部世界交互的桥梁。不只是 API，也包括人每天在用的应用：浏览器、Excel、OA 审批流、ERP、CRM。读写不了这些系统，它的帮助就只能停在通识层面。
- **记忆**——理解具体语境的前提。没有记忆，它每次对话都从零开始，不知道你是谁、上次会议决定了什么、这个客户三天前投诉过。
- **知识**——企业的规则与事实。宏观是愿景、目标、组织架构与流程，微观是产品规格、客户档案、业务规则、定价逻辑，以及那些只存在于邮件和会议纪要里、从未被系统整理过的业务判断。

这个框架真正反直觉的地方在于**排查顺序**：人的第一反应总是"模型不够强，换个更贵的"，但四组件里模型恰恰应该排在最后查。因为绝大多数"不好使"的症状——答非所问、引用过期资料、每次重新解释、建议落不了地——都不是推理能力不足，而是记忆、工具接入或企业知识缺位。

作者用一个类比把它讲透：把顶级模型接进企业，处境和一位没人带的名校毕业生没有本质区别，**甚至更难**——新员工至少知道自己不知道什么，会开口问；模型不会，它会用听起来很专业的语言，给出一个建立在错误前提上的答案，还显得信心十足。

## A1 — 书中的应用 (Past Application)

### 案例 1：名校第一名毕业生的入职第一天
- **问题**：企业招进一位简历漂亮、逻辑过硬的顶尖毕业生，但没安排人带，也没告诉他内部规则、系统入口和业务语言。大家觉得他这么聪明应该能自己搞明白。
- **方法论的使用**：作者逐项拆解他卡在哪里——搞不清 CRM 里"潜在商机"和"跟进中"的实质区别（知识缺口）；想查回款记录却没有财务系统权限（工具缺口）；同事给的流程文档是三年前的，截图对应的系统早就换了界面（知识过期）。
- **结论**：聪明解决的是"怎么做"，而他卡在"规则是什么、入口在哪儿、这话什么意思"上。通常要 3–6 个月他才开始产生价值。
- **结果**：作者据此推出模型的五个能力缺口（不懂私有数据、不懂行话、不知道此刻状态、没有手、不懂责任边界），并指出关键差别：新员工有人引导、有机会探索；而**如果不给模型地图，它会永远停留在入职第一天的状态**。

### 案例 2：客服场景的四组件协同
- **问题**：一个客户来投诉，需要在两分钟内完整处理。
- **方法论的使用**：模型理解客户意图，工具查询订单系统，知识提供退换货政策，记忆让模型知道这个客户上周已经投诉过一次。
- **结论**：四个组件协同才构成闭环。
- **结果**：全程无须任何人工介入。反过来，缺知识就会出现"不知道退换货政策的客服智能体"，缺记忆就会让客户把上周的事再讲一遍。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. AI 助手已经在用，但输出"听着专业、落不了地"，用户在纠结是不是该换更强的模型。
2. 用户抱怨"每次都要从头解释一遍我们的业务"。
3. AI 引用了过期文档、旧模板、废弃系统里的数据，把草稿当正式件。
4. AI 能给建议但没法真正执行（查不了库、改不了状态、发不出文件）。
5. 企业内部上线的 AI 工具没人用，要找原因。

### 语言信号

- "它答得很流畅，但内容是错的"
- "每次都要我重新解释一遍背景"
- "它引用的是旧版本 / 三年前的模板"
- "是不是我们模型选得不对，要不要换个更强的"
- "它只会给建议，不会真的去做"
- "看起来很聪明，但就是不好使"

### 与相邻 skill 的区分

- 与 `agent-level-ladder` 的区别：那个用于**选型前**判断产品等级；本 skill 用于**已在使用中**定位故障组件。
- 与 `living-ontology` 的区别：本 skill 定位到"缺知识"就停；那个回答"企业知识这一块具体怎么建"，是本 skill 的下游解法。
- 与 `ai-decision-core` 的区别：本 skill 面向**单个工具**；那个面向**企业级系统**（四拼图：模型/本体/实时上下文/操作系统）。个人用户或单点工具用本 skill，企业底座规划用那个。

## E — 可执行步骤 (Execution)

**排查顺序刻意与直觉相反：先记忆，再工具，再知识，最后才是模型。**

1. **查记忆**：它知道你是谁、上次说过什么、这个客户/项目的历史吗？
   - 完成标准：能明确回答"每次对话是不是从零开始"。
   - 判停条件：若症状是"每次都要重新解释"⇒ 记忆缺口，先补记忆，不要换模型。

2. **查工具接入**：它能读写哪些真实系统？把它需要触碰的系统列出来（CRM/ERP/OA/文件仓库/邮件），逐个标记"能读 / 能写 / 都不能"。
   - 完成标准：得到一张接入现状表。
   - 判停条件：若症状是"只会给建议不会执行"⇒ 工具缺口。

3. **查企业知识**：它引用的来源有没有分级？它知道哪份是法务总监签字的正式合同、哪份是实习生存的草稿吗？它懂你们内部对"有效客户""成交"的定义吗？
   - 完成标准：能举出至少一个"它用错了术语或用了过期来源"的具体例子，或确认没有。
   - 判停条件：若症状是"引用过期资料 / 术语理解和我们不一样"⇒ 知识缺口。

4. **最后才查模型**：只有前三项都齐备、且失败发生在**需要多步推理或长链条规划**的任务上，才考虑换更强的模型。
   - 完成标准：能说出一个"四组件都在位但它仍然推不出来"的具体任务。

5. **写出一句话结论**："症状是 X，缺口在【记忆/工具/知识/模型】，下一步动作是 Y。"
   - 完成标准：结论指向一个具体的补齐动作，不是"再优化一下"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还在选型阶段、没有实际使用症状——那是 `agent-level-ladder`。
- 问题明显出在提示词写法或输出格式上。
- 用户要的是模型评测、跑分比较、供应商价格对比。
- **本框架诊断不了数据质量问题**：知识组件"在位"只说明模型接得到企业知识，不说明那些知识是对的、是最新的、是不矛盾的。数据脏、口径打架、多个"最终版"共存这类问题，本框架会误判为"知识组件已具备"。

### 作者在书中警告的失败模式

- **"别怪模型"的反面也成立**：把所有问题都归因到记忆/工具/知识，会掩盖确实存在的推理能力不足。
- **垃圾进，垃圾出**：作者明确说盲目接入一堆数据不会让输出自动变得正确、可信、可用。补"知识"不等于把档案柜整个塞给它。
- **模型对企业数据没有天然辨别力**：它会一视同仁地把所有东西吞下去，再一本正经地把充满错误和噪声的内容当成真相输出。

### 作者的盲点 / 时代局限

- **四组件齐了也不等于有用**。作者自己在第 5 章引用 MIT NANDA 的"学习鸿沟"——项目失败往往不是模型不够聪明，而是系统无法吸收真实使用中的反馈、沉淀不了业务操作经验。这是四组件之外的第五个问题，本框架看不见它。
- **框架是静态的**。它诊断某一时刻缺什么，但不诊断"补上之后会不会持续退化"（知识过期、权限漂移、记忆污染）。
- **作者是零一万物 CEO**，四组件的划分与其公司产品架构一致；这不必然是偏差，但这个划分并非行业唯一共识（也有按"感知/规划/执行/反思"划分的）。
- **"记忆"和"知识"的边界在实践中是模糊的**——客户上周投诉过一次，算记忆还是知识？框架没有给出判定规则，实际使用中容易两边都归、或两边都漏。

### 容易混淆的邻近方法论

- 与 RAG 架构诊断不同：RAG 只是"知识"这一个组件的一种实现方式。
- 与"模型/数据/算力"三要素框架不同：那是训练视角，这是应用视角。
