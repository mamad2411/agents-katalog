# 模型选型

以业务约束下的真实任务表现为决策依据。主干是“四看一测＋成本考量”，扩展为需求界定、候选调研、评测、归因、决策和上线验证的完整工作流。目标是在满足业务门槛的方案中选择合适的效果、成本、速度与交付方式，不追求脱离场景的最强模型。

## 开始与协作方式

先读已有材料，识别当前处于调研、评测设计、决赛圈实测、结果分析或上线验证哪一阶段。从缺口接着做，不让用户重新填写已有信息，不强制重跑八步。

- PoC 可用少量真实案例快速排除明显不适配的模型；生产上线、昂贵迁移或高错误代价场景需要更强证据。结论强度随证据变化。
- 用户已有候选池、Prompt、评分规则或结果时优先复用，并检查版本、适用范围与缺项。
- 未知信息标为未知；可逆的实现选择用合理假设继续。缺少会改变选择的业务门槛、费用预算或数据发送授权时，只询问当前必要问题，并继续不依赖答案的工作。
- 不在每一步设置机械确认。已约定的任务、门槛、权重、测试预算不静默改动；若必须改变，说明影响并取得相应决定后更新版本。
- 区分资料事实、实测观察、解释假设和建议。没有运行就不声称已测试；引用用户评分时说明是用户记录，不伪装成独立复评。
- Skill 自身不提供 API、评分服务或 Model Battle 自动化接口。根据当前可用工具执行；不能执行时交付可直接运行的测试包，并明确下一步需要的结果。

## 八步工作流

### 1. 界定选择范围与现有基线

明确是新建产品、替换模型、调整推理配置还是解决某类失败。确认供应商、部署方式或预算是否已有约束。保留现有模型，以及有意义的规则、检索、传统模型或人工流程作为基线；允许得出“暂不需要换模型”。

区分只比较模型能力与比较最终可部署方案。最终推荐对象至少包含：**服务商/部署方式＋精确模型版本＋推理/生成配置＋必要的 Prompt、工具和后处理版本**。不要把平台封装或网络差异全部归因给基础模型。

### 2. 将业务任务转成验收条件

形成任务卡：用户与场景、任务边界、输入输出契约、成功条件、不可接受的错误、工作量与峰值、速度预算、总成本预算、部署与数据约束、上线时间、基线、决策负责人。

一个产品有多种任务时按节点拆开，例如意图分类、知识回答、工具执行；可以分别选型，不默认整条链只能用一个模型。终端任务仍需端到端验收。

在看正式结果前区分：

1. 候选准入条件：例如支持规定输入、可获得的服务、可接受的数据处理方式。
2. 单条输出通过条件：硬性规则以及必要的质量分数下限。
3. 方案验收门槛：整体/关键分组通过率、关键错误上限、性能和成本范围。
4. 达标后的偏好：更便宜、更快或特定质量更优。

用户未给门槛时提出有业务依据的建议并标注待定；可以继续探索，但不能据此宣称正式达标。

### 3. 用“四看”建立并收窄候选池

进入调研时读取 [候选调研与证据](references/candidate-research.md)。

看任务相关榜单、公开训练数据与能力证据、相似客户案例、模型类型和运行方式。先排除不满足硬约束的方案，再保留有价值差异的少量候选；约 3—5 个是常用起点，不是固定名额。

每个候选写清来源日期、精确型号、入选理由、已知限制、重点验证假设和淘汰理由。价格、可用性、版本、许可证和 API 支持须按此次决策日期核验；查不到就保留未知，不补造信息。

### 4. 构建真实业务评测集

进入数据与评分阶段读取 [评测与执行协议](references/evaluation-protocol.md)。

从真实对话、工单、日志、素材和用户工作流取样，以“准、广、真、难、稳”检查质量。业务代表集反映真实流量，困难与风险集单独诊断；不把人为均衡的数据集直接当成线上表现。

先解决分类定义、参考依据和标注分歧，再形成金标或可核验的评分依据。合成数据可补边界，须审核、标明来源并单列；不能冒充真实数据。调试样本与留出验收样本按会话、商品、用户或相似素材组隔离，防止泄漏。

样本量按覆盖、风险及结论不确定性扩展，不承诺固定几十条就能证明上线可靠性。

### 5. 定义评分并组织公平实测

按任务选择正确性、指令遵循、业务完成、可用性、延迟、失败率与成本指标。硬门槛优先于加权分；不让美观、文风等高分抵消关键错误。开放式输出使用可观察锚点和证据记录；模型裁判须与人工校准，不能由模型名或国别判断其评分资格。

可先统一任务指令做基线，再给候选相当的优化预算做部署方案比较；两轮分开报告。固定案例、输入素材与顺序、任务语义、工具上下文和评分规则，记录所有配置差异。保存失败、取消、重试和全部尝试，不只留下成功或最佳结果。

用户采用 Model Battle 时，按 [Model Battle 衔接](references/model-battle.md) 准备和交接测试包，先核对当前能力。付费调用必须在已有测试授权、数据范围和预算内；预算耗尽、连续出现同类基础设施错误或触及预先规定的停止条件时停止扩跑，报告已完成与待解决部分。

### 6. 比较结果并分析失败原因

检查原始记录完整性，按任务类别、难度、关键业务群体和尝试次数拆分结果。判断差异来自模型能力、Prompt、检索、工具、标注、参数、服务商还是网络条件。没证据时把原因写成假设。

差距小或波动大时补做配对复测/扩样，报告样本数、重复次数及不确定性。不能将同一案例重复生成的多张图当作多个独立业务案例。

基线、优化轮和最终留出验收分开。发现关键数据错误或验收规则变更时重新计算相关候选，不只修正被偏爱的模型。

### 7. 综合效果、速度和总成本做主备决策

进入结果分析和选型时读取 [成本与决策](references/decision-and-rollout.md)。

顺序是：准入筛选 → 关键业务门槛 → 达标方案的质量、成本、速度与稳定性比较。展示权衡与适用条件；权重仅在指标可比且权重有依据时使用。不把“效果×成本×匹配度”当作数学公式。

算每请求、每合格结果及必要时每实际采用结果的成本；分清报价估算、实扣、一次性投入和持续成本。选择主模型、备选模型、各自使用条件和回退触发。没有候选达标时给出修复方向或维持基线，不能强行选一个上线。

### 8. 验证实际业务收益并设置复测条件

离线合格后根据项目范围制定影子测试、小流量或人工复核试用。检查实际采用、任务完成、返工、账单、并发和延迟。离线通过不等于生产验证通过。

将模型/Prompt/知识库/工具版本变化、流量变化、关键错误回升、成本超限等转成复测触发。未获得上线操作授权时交付验证与回退计划，不实际部署或创建持续监控。

## 产物与完成状态

需要字段、表格和交接材料时读取 [交付模板](references/artifact-templates.md)；需要图生图实例或历史方法修正时读取 [实践示例与依据](references/practice-notes.md)。按任务规模合并产物，避免为了模板制造多份重复文件。

完整证据链：任务卡 → 候选表 → 评测集与协议 → 原始运行和评分记录 → 成本与结果汇总 → 主备决策 → 上线验证/复测安排。

结尾明确本次完成到哪一层：

- **调研建议**：未实测；说明候选依据和待验证假设。
- **阶段性实测结论**：小样本/局部任务；注明覆盖与判断限制。
- **离线验收结论**：约定留出集及关键门槛完成验证；线上表现尚待核验。
- **生产验证结论**：已获取约定真实流量和业务指标；说明观察窗口及适用范围。

缺数据时交付已完成工作及具体缺口，不伪造最终排名。用户只要简述时可压缩表达，但内部不省略影响结论的检查。

## 与其他技能的边界

本 Skill 可独立完成选型全流程。若环境中有 `evaluation-assistant`，可复用其目标卡、覆盖矩阵和 Rubric；不继承其固定样本配额，也不把它“止于评分设计”的边界变成本 Skill 的终点。用户只需评测设计时交由该技能即可。网站、文档、表格、实际 API 调用等使用当前环境可用工具，不要求安装特定插件。
