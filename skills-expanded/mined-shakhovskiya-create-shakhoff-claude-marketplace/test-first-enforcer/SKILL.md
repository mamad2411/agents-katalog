# Test-First Enforcer

Жёстко принуждает писать тесты до production кода.

## Когда применять

- На каждом attempt to edit/write production файл (через hook)
- DoD validation phase (compliance verification)
- Skill читается hook'ом для understanding context

## The Rule

For every production code change в active task:
- A test file change must have preceded it within same task
- OR `/sprint:test-exempt` was invoked with documented reason

## Production file detection

Производственные файлы определяются по pattern matching:

### Production paths (from config)

```yaml
production_paths:
  - "src/**"
  - "app/**"
  - "apps/**"
  - "lib/**"
  - "internal/**"
  - "pkg/**"
  - "cmd/**"
```

Configurable per project.

### Auto-exempt paths

```yaml
auto_exempt_paths:
  - "**/migrations/*"
  - "**/migrate/*"
  - "scripts/**"
  - "config/**"
  - "*.config.*"
  - "Dockerfile*"
  - "*.yaml"
  - "*.yml"
  - "*.json"
  - "*.md"
  - "*.txt"
  - "docs/**"
  - "**/__init__.py"  # often empty package markers
```

### Auto-exempt content markers

```yaml
auto_exempt_markers:
  - "# generated"
  - "// auto-generated"
  - "# Code generated by"
```

If file content includes these markers - exempt automatically.

## Decision logic

```python
def should_block_edit(file_path, current_task):
    # Auto-exempt by path
    if matches_any(file_path, auto_exempt_paths):
        return False
    
    # Auto-exempt by content marker
    if has_exempt_marker(file_path):
        return False
    
    # Not in production paths - not affected
    if not matches_any(file_path, production_paths):
        return False
    
    # Check explicit exempt for this task
    if current_task.id in get_test_exempt_tasks():
        log_exempt_usage(current_task, file_path)
        return False
    
    # Check if test files changed in this task
    test_changes = get_test_file_changes_in_task(current_task)
    if test_changes:
        return False  # test-first satisfied
    
    # BLOCK
    return True
```

## Hook behavior

`pre-tool-use-test-first.sh` reads this skill для logic, then:

```bash
#!/usr/bin/env bash
# Hook script (simplified)

if no_active_sprint; then
    exit 0  # not active, no enforcement
fi

current_task=$(get_active_task)
if [ -z "$current_task" ]; then
    exit 0
fi

file_path="$1"  # passed by hook system

if should_block_edit "$file_path" "$current_task"; then
    cat <<EOF >&2
BLOCKED: Cannot edit $file_path

Test-first violation. Current task ($current_task) has no test file 
changes yet. Production code change requires preceding test change.

Resolution:
  1. Write/modify test for this change first
  2. /sprint:test-exempt "reason" if this change shouldn't have test
     (e.g., generated code, configuration, migration)

EOF
    exit 1  # BLOCK
fi

exit 0  # allow
```

## Test file detection

A file is "test file" if:

### By path
- `tests/**`
- `test/**`
- `**/__tests__/**`
- `**/*test*.{py,ts,tsx,js,jsx,go}`
- `**/*spec*.{ts,tsx,js,jsx}` (Jest/Vitest)
- `**/*_test.go` (Go convention)

### By content
- Contains test framework imports (pytest, vitest, etc.)
- Contains test definition patterns (`def test_`, `it(`, `test(`, `func Test`)

## Test exemption mechanism

`/sprint:test-exempt "<reason>"`:

When invoked:
1. Mark current task as test-exempt
2. Log to `.sprints/active/test-exemptions.log`:
   ```
   2026-04-30 14:32:15 - Task T-3 marked test-exempt
   Reason: "Migration script - tested via dry-run on staging"
   File pattern: migrations/0042_add_user_email.py
   ```
3. Hook will allow production edits для this task без test
4. SE reviewer flagged exemption для extra scrutiny

**Valid reasons** (что логично экземптировать):
- Generated code (already covered by generator tests)
- Configuration files (tested manually or через env-specific testing)
- Migration scripts (tested через dry-run)
- Documentation
- Build scripts

**Invalid reasons** (don't accept):
- "Will write tests later"
- "Tests are slow"
- "Already covered" (without specifying where)
- Empty reason

In strict mode: exemption requires non-empty reason >20 chars.

## Compliance verification (DoD phase)

dod-validator queries this skill для compliance check:

```python
def verify_test_first_compliance(sprint):
    violations = []
    
    for task in sprint.tasks:
        if task.id in test_exempt_tasks:
            continue  # exempted
        
        prod_changes = get_production_changes_in_task(task)
        if not prod_changes:
            continue  # no prod changes, nothing to check
        
        test_changes = get_test_changes_in_task(task)
        
        if not test_changes:
            violations.append({
                'task': task.id,
                'reason': 'Production changes without any test changes',
                'files': prod_changes
            })
            continue
        
        # Check ordering: test changes preceded prod changes
        for prod_file_change in prod_changes:
            preceding_test_change = find_preceding_test_change(
                test_changes, 
                prod_file_change.timestamp
            )
            if not preceding_test_change:
                violations.append({
                    'task': task.id,
                    'reason': f'Production file {prod_file_change.path} '
                              f'edited before any test changes',
                })
    
    return violations
```

If violations found → DoD criterion 5 (test-first compliance) FAILS.

## Strictness levels

**strict** (default):
- BLOCK production edits without test
- BLOCK with full message
- /sprint:test-exempt requires reason >20 chars

**lenient**:
- BLOCK production edits without test (still BLOCK даже в lenient - per Anton's design)
- This is non-negotiable

**permissive**:
- WARN only (does not block)
- Useful for very quick experiments
- NOT recommended для production work

## Fail modes и edge cases

### File created on disk before hook fires

Hook fires before tool use. But what if file was created via shell command (e.g., `cp`)?

- Hook also fires before Bash commands
- Bash commands creating production files без test - also blocked
- Workaround: do work in /tmp, then move (still gets blocked when moving with mv)

### Hook bypass attempts

Не должно быть. Hooks работают на Tool API level в Claude Code. Cannot bypass without disabling hooks (which is itself logged).

### Test file changes that don't actually test anything

Hook doesn't validate test quality - just presence of test changes. checkin-validator and SE reviewer handle quality check.

So: someone could write empty test, satisfy hook, write production code. Then SE reviewer катches empty test as fake test issue.

This layered approach: hook enforces structure, SE catches quality.
