# Manuscript Integrity Checker

学术论文手稿的六步完整性校验闭环。当用户质疑手稿中的数据、命名、归属或叙事一致性时触发。

## 触发

检测到以下信号即开始执行：

- 用户说"核查"/"核实"/"这个数据跑过吗"/"这个实验存在吗"
- 用户指出归属错误（"XXX 是我的工作，不是引用 YYY"）
- 用户指出命名错误（"XXX 从未存在"/"这是旧稿遗留"）
- 用户指出数据不存在（"没跑过"/"编的"/"这个消融没做"）
- 用户要求同步配图（"图需要改吗"/"涉及图了吗"）
- 用户要求叙事统一（"调整吧"/"不一致"）

## 六步闭环

### Step 1: 溯源核查

读取原始来源（原始论文/实验记录/代码），与当前手稿逐项对比。

```
操作: Read原始论文 → Grep关键术语 → 列出所有差异点
输出: 差异清单（位置、旧值、来源）
```

**关键原则**: 原始论文/代码是唯一真相来源。手稿必须与原始来源一致。

### Step 2: 影响面分析

对每个差异点，搜索手稿中所有出现位置，评估修改波及范围。

```
操作: Grep -i 目标术语 → 列出所有行号 → 标注每处是否需要改、怎么改
覆盖范围: Abstract、§正文、Table、Figure caption、脚本文件(*.py)、实验日志(experiment_log.md)
```

**特别注意脚本文件中的陈旧数值**: 当表格数据被修改后，配图脚本中硬编码的 F1/Accuracy 值极易被遗漏。Step 2 必须对脚本中所有硬编码数值执行 grep，与当前表格逐行比对。

### Step 3: 批量修改

按优先级一次性执行所有修改——先改 tex 正文，再改表格，最后改配图脚本。

**表格修改注意事项**:
- 删除行后记得更新 `\multirow{N}` 中的 N
- 删除缩写后更新 Table caption 的 Abbreviations

**配图脚本注意事项**:
- 脚本中的数据必须与手稿表格完全一致
- 修改后必须重新运行脚本生成图片

### Step 4: 残留检查

修改完成后，grep 验证旧术语在全文（含脚本）中零命中。

```
操作: Grep -i 所有旧术语 → 确认零命中或仅保留位置正确
例外: 在原始论文中合理的术语可保留（如作为架构描述而非消融变量）
```

### Step 5: 叙事一致性验证 + 脚本数据交叉校验

检查修改后的段落之间是否存在逻辑矛盾，**同时交叉校验配图脚本中的硬编码数据是否与手稿表格一致**。

**5a. 常见矛盾类型**:
| 类型 | 示例 | 检查方法 |
|------|------|----------|
| 数字矛盾 | Table 说5行但正文说3个变体 | 手动逐行计数 |
| 术语矛盾 | §4.1 说"普遍冗余"但 Conclusion 说"backbone-dependent" | Grep 关键术语全文中所有出现 |
| 证据矛盾 | 消融数据不支持某结论但 benchmark 数据支持 | 区分语境（见下方"证据矛盾处理"） |
| 标签矛盾 | Fig caption 描述与图中实际条形数不匹配 | 对照配图脚本中的 variants 列表 |
| **脚本数据陈旧** | 表格已改但 fig1_scatter() 中仍是旧 F1 值 (e.g. 0.9708 vs 应 0.9559) | **逐函数 grep 硬编码数值，与表格逐行比对** |
| **对比不公平** | fig_s1_sota 将 CE Loss 基线 (ConvNeXt=0.9904) 与 CB Focal Loss 本方法 (0.9727) 放在同一张图 | 检查每个 subplot 中数据点的 loss function/seed 来源 |

**5b. 脚本数据交叉校验（强制执行）**:
```
1. Read 配图脚本中每个 def fig*() 函数
2. 提取函数内所有硬编码的 F1/Accuracy/参数值
3. 与手稿 Table 1/Table 2 逐值比对
4. 标记所有不一致 → 记录函数名、行号、旧值、应有值
```

**5c. 证据矛盾处理**:
当消融数据(Table 2)的结论与 benchmark 数据(Table 1)的结论表面冲突时，区分移除注意力和添加注意力的不同语境：
- "移除 Transformer 注意力 → 零效应" = 注意力冗余（当已有强 backbone 特征时）
- "向弱 backbone 添加 ViT → 正提升" = 注意力可替代弱 backbone 的不足
- 两句均为真，但取决于不同基线条件 → 必须显式标注上下文

### Step 6: 记忆持久化

更新项目记忆文件，记录所有修改和最终状态。

```
操作: 查找 memory/ 目录下的项目记忆文件 → 更新修改时间线、最终架构定义、Table状态、残余注意事项
      若无 memory/ 目录则跳过，但提示用户考虑创建
```

## 项目上下文（自动检测）

首次触发时，自动扫描当前工作目录确定论文项目结构：

```
检测规则:
- 原始论文: 搜索 */tex/manuscript.tex 或用户指定
- 当前手稿: 搜索 */tex/manuscript_eaai.tex 或 *main.tex
- 配图脚本: 搜索 */scripts/generate_figures*.py
- 配图输出: 搜索 */figures/ 目录
- 记忆目录: 查询 CLAUDE.md 或 memory/ 下的项目记忆文件
```

如果无法自动检测，询问用户关键文件路径。

## 已知事实（按项目缓存）

首次核查时从以下来源提取并缓存已知事实，后续核查复用：
1. 原始论文/代码中的架构定义
2. 用户的实验记录（experiment_log.md 或对话历史）
3. 项目记忆文件中的已确认结论

缓存过期条件：用户说"修改了"/"新增实验"/"架构变更"时清空重建。

## 已知陷阱（从真实踩坑中提取，每次核查必对照）

| # | 陷阱 | 根因 | 检测方法 |
|---|------|------|----------|
| 1 | **脚本陈旧 F1 值** | 修改 tex 表格后忘记同步更新配图脚本中硬编码的数值 | `grep -n "0\.[0-9]\{4\}" scripts/*.py` 与表格逐值比对 |
| 2 | **Loss 函数混用** | CE Loss 训练的基线模型与 CB Focal Loss 训练的本方法放在同一张对比图，表面数字不可比 | 检查每个 fig 函数中数据点来源，确认是否有 CE/CB 混用 |
| 3 | **删除行后 multirow 未更新** | 从表格删行时遗漏 `\multirow{N}` 的 N 值更新 | `grep multirow` 并对照表格实际行数 |
| 4 | **陈旧计数在正文中** | 正文中的 "N comparisons/runs/variants" 等计数值在删行后未重新统计 | `grep -nE "[0-9]+ (comparisons|runs|variants|rows)" tex/*.tex` 然后手动验证 |
| 5 | **Focal ≠ Focal** | "Focal Loss"(loss 函数) 与 "Focal Attention"(架构组件) 是两个概念，grep 时可能混淆 | 视觉确认每个"Focal"的上下文 |

## 关键规则

1. **原始论文是第一真相来源** — 手稿说什么不重要，原始代码/论文说什么才重要
2. **一次性改完** — 不要分轮次，分析完整影响面后一次执行
3. **改完必 grep 验证** — 每一步修改后搜索残留
4. **表格和配图同改** — 不能只改 tex 忘了脚本；修改表格数据后必须逐函数审查配图脚本中的硬编码数值
5. **叙事一致性优先于修辞优美** — 宁可句子平淡，不能前后矛盾
6. **检查对比公平性** — 同一张图里对比的方法必须使用相同的 loss function 和评估协议
7. **核实所有计数** — "15 comparisons"、"97 runs" 等计数在表格改动后必须重新统计
