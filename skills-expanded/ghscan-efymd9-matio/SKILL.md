# Нагрузочные кампании

Методика, выстраданная кампаниями оригинального проекта. **ЖИВОЙ документ:
изменилась методика или пороги → обнови скилл тем же PR.**
Карта инфраструктуры и живых стендов — скилл `/devops`. Здесь — как вести
кампанию, чтобы цифры не врали.

## Подготовка

- **Стенд**: одноразовый клон или живой перф-стенд. Всё на выделенных
  ядрах (burstable/shared троттлится — цифры «плывут»); генератор
  ЗАВЕДОМО мощнее испытуемого; k6 копит Trend-точки в RAM — длинным
  прогонам нужен раннер с большой памятью. Генераторы гонять из того же
  региона/сети, что и стенд, не с ноутбука. Долгоживущим машинам
  auto-stop off: уснувшая машина убивает фоновые процессы и стирает /tmp.
- **Зафиксировать конфигурацию** (в отчёт): SHA кода, классы машин, число
  воркеров, пул БД, лимиты прокси-слоя ЯВНО (у Fly дефолт
  `[http_service.concurrency]` = невидимая стена 8192), ulimit —
  доказательство только `/proc/<pid>/limits` каждого воркера, не
  `ulimit -n` в шелле.
- **Бюджет соединений БД**: (pool+overflow) × воркеры × машины + фоновые
  джобы + служебные ≤ max_connections с запасом ≥25%. Managed-планы часто
  не публикуют max_connections — измерить самим.
- **Сид — ДО замера и НЕ на замеряемой машине**; исход проверять
  фактическим COUNT в БД, не живостью процесса. Домен сид-пользователей —
  поддомен реальной зоны (`.test`/`.local`/`.invalid` отвергают строгие
  email-валидаторы).
- **Перезапуск app-машин перед КАЖДЫМ зачётным прогоном** (дождаться
  healthz): уставшие процессы искажают зачёт.
- **Первый прогон дня/после простоя — прогревочный, в зачёт не идёт**:
  пустые кеши БД, холодный пул и план-кэш дают ×2–3 к латентности.
- **Смета и платные действия**: посчитать $/сутки состава, бюджет
  кампании — в issue. Создание стендов/дорогих классов — по команде
  владельца; дорогие генераторы поднимать только на время прогонов.
  Managed-БД тикает и у погашенного стенда.

## Исполнение

Профили (пороги зачёта зафиксировать один раз и НЕ менять, иначе прогоны
несравнимы):

- **ramp** — лестница до колена: равные ступени, колено уточнять
  бисекцией. Деградация = пробит любой порог ИЛИ лавина реконнектов ИЛИ
  рост очередей/оверфлоу ИЛИ event-loop-lag устойчиво высокий ИЛИ
  5xx на пользовательских путях.
- **spike** — большинство онлайн, заметная доля входит разом; ТОЛЬКО с
  разных машин-генераторов (edge-прокси режут тысячи соединений с одного
  source-IP — шторм с одной машины меряет прокси, а не сервер).
- **soak/endurance** — 70% найденного потолка, 60–90 мин (многочасовые —
  только по личной команде владельца, перед стартом — репетиция:
  телеметрия пишется, дашборды видны, чекпойнты снимаются). Критерий —
  отсутствие дрейфа (p95 второй половины не хуже первой >20%),
  память/fd/соединения на полке; после снятия нагрузки — возврат к
  baseline за час.
- **Штормовой и устойчивый потолки — два разных числа, оба в паспорт**:
  шторм — выживание под лавиной коннектов (выбор hard_limit, «переживём
  возврат клиентов после деплоя»); ramp — полноценный трафик (основа
  сайзинга). Не подгонять одно под другое.

- **Наблюдаемость** (отдельными процессами, не внутри генератора): сэмплер
  метрик раз в 60 с → CSV; сборщик логов (ретенция логов хостинга —
  часы!); ссылку на дашборд владельцу в момент старта.
- **Пульсы в issue кампании**: ОДИН «живой» комментарий-таблица,
  редактируется каждый час/чекпойнт. Отдельными комментами — только старт,
  аномалия В МОМЕНТ обнаружения, найденный потолок, финальный отчёт.
- **Длинные операции** — с записью в файл НА машине, исход проверять по
  данным; ожидание >15 мин без наблюдаемого прогресса — разбираться.
- Во время прогона ничего не менять (классы машин, параметры, пересев).
- Профилировщик (py-spy и аналоги) — только отдельным коротким прогоном:
  attach портит латентности на порядок.

## Арбитраж и анализ

- **Арбитр латентности — логи сервера, не генератор**: один процесс k6
  при тысячах VU добавляет свои накладные (у оригинала: сервер 65 мс —
  k6 показывал 71–436). Спорную ступень дробить на 2 машины. Считать по
  hold-фазе (connect-шторм рампа задирает p95 всего прогона).
- **Два генератора одного класса дают разные цифры** — сверять между
  собой и с серверным логом; независимая проба — лёгкий клиент (curl) по
  сущности ВНЕ прогонного диапазона под полной нагрузкой.
- **«Упёрся сервер, а не стенд» — обязательный раздел отчёта** с числами:
  генераторы не в edge-лимите, их loadavg/CPU в норме, ноль TLS-ошибок в
  логах ВСЕХ генераторов. Если ограничил стенд — честно «потолок ≥ N,
  не достигнут» + состояние сервера на максимуме.
- **Назвать упор** (CPU / соединения прокси / fd / пул БД / память) и
  исключить остальных кандидатов по одному с доказательствами.

## Артефакты и отчёт

- **Выкачать ВСЁ ДО stop машин** (у Fly stop/start откатывает rootfs к
  образу): summary/паспорта прогонов, HTML-отчёты, логи, CSV метрик.
- **Структура отчёта** (комментом в issue): executive summary →
  конфигурация и SHA → таблица прогонов/чекпойнтов → чем упёрлись
  (с исключением кандидатов) → доказательство «сервер, не стенд» →
  условия зачёта (сид/COUNT, прогрев, рестарт машин) → оговорки к цифрам →
  рекомендация сайзинга → вердикт **PASS / PASS WITH ISSUES / FAIL**.
- Каждая проблема: симптом, время, метрики/логи, гипотеза, влияние на
  прод, фикс, проверка фикса. Требует кода → отдельный issue — не чинить
  молча.
- Числа паспорта → эталонный issue; сайзинг → docs/deploy.md правкой
  через PR; /devops актуализировать — устаревший паспорт хуже отсутствия.

## Границы

- **Чужие стенды и кластеры НЕ трогать. Прод и staging не трогать никогда.**
- **Снос стенда — только по личной команде владельца**; после отчёта —
  предложить снос, до ответа погасить машины, чтобы не капало.
- Сценарий нагрузки и пороги зачёта не менять — иначе прогоны несравнимы.
- Старт многочасового прогона и платные действия — слово владельца.

## Грабли (проверены кровью — не переоткрывать)

1. ssh-консоль хостинга рвёт длинные операции; nohup умирает вместе с
   уснувшей машиной — писать в файл на машине, проверять по данным.
2. «Процесс жив» через grep/pgrep матчит собственную команду —
   экранировать (`[k]6`); проверять по данным, не по процессам.
3. Отказ по соединениям обвальный и невидимый: /readyz зелёный при
   необслуживаемых клиентах. Триггеры скейлинга — соединения, не CPU.
4. Долгий молчаливый стейтмент (массовый DELETE) убивает NAT-flow между
   хостингом и managed-БД: клиент вечно спит, локи висят — батчи с логом
   на батч + TCP-keepalive в настройках движка.
5. Системный монитор БД может быть слеп под пользователем приложения
   (managed-роли) — «активных транзакций нет» из пробы ничего не значит;
   смотреть pg_locks, ставить датчики в приложение (slow_sql,
   event_loop_lag, slow_request).
6. Датчик slow_sql в приложении меряет и ожидание event-loop: «медленный
   SQL» при мгновенных планах EXPLAIN = «корутина ждала» — улика
   блокировки лупа, не БД.
7. interrupted iterations у k6 — норма (сессия живёт до конца прогона);
   REST API k6 поднимается только с явным `--address`.
