# Vibe Backend Handbook

把产品 PRD、现有代码和运行约束转成一条可审查、可恢复、可验证的 Agent 产品开发路径。面向不需要自行做技术选型的产品经理，用产品语言说明关键取舍，并在每个阶段结束时给出明确的下一步。

## 权威顺序与边界

- 业务目标、用户流程、功能范围和阶段优先级以 PRD 与用户当前请求为准。
- 本 Skill 提供工程底线、默认基线和适配规则，不替代 PRD，也不要求既有项目重构成示例结构。
- 安全、隐私、数据保护、可恢复性与验收真实性属于强制底线；若与普通业务要求冲突，指出冲突并采用更严格规则，重大影响项等待确认。
- 用户只要求分析、审查或规划时，只交付相应文档；只有用户明确要求开发、修改或构建时才改代码。
- 不把 mock、静态演示或技术设想描述成真实模型、生产环境或业务效果已经验证。
- 外部发布、付费调用、生产部署、发送消息、删除数据等操作仍需用户对该动作的明确授权。

## 工作流

### 1. 读取输入并检查现场

读取 PRD、当前阶段文档、项目规则、README 和相关代码。检查：

- 当前目标用户、核心任务、输入、过程、产物与需要保留的数据；
- Agent 是一次生成、多轮对话、分阶段确认，还是受控工具调用；
- 当前阶段范围、验收标准、模型与成本约束、数据敏感性、性能和部署限制；
- 现有目录、依赖、启动方式、测试、未提交修改、已有数据、端口与外部依赖；
- 真实解释器与运行时版本、Git 状态、Key 是否就绪，但不得回显秘密。

缺失信息只有在会显著改变用户体验、成本、安全、数据迁移或交付范围时才阻塞并询问。其余缺项采用合理默认值，并在适配声明中显式记录。

新项目默认 Python 3.11.x、FastAPI、Pydantic、pytest 与 Git。已有项目优先延续合理架构和依赖方式。

### 2. 按三层规则做单一推荐

判断顺序固定为：

1. 先检查强制底线；
2. 再判断默认方案是否适配；
3. 最后只引入被需求触发的按需模块。

不要向产品经理罗列多套框架让其自行选型。给出一个推荐结论，以产品语言说明少量关键取舍。

- A 强制底线：密钥不进前端和仓库；输入输出有校验；重要数据、任务状态和人工确认点可恢复；错误不泄露堆栈；测试结论真实。
- B 默认方案：适合从零开始的大多数 Agent MVP，触发适配条件时才替换。
- C 按需模块：数据库 ORM、迁移、RAG、OCR、任务队列、对象存储、SSE 等，仅由真实需求触发。

详细决策表见 [references/engineering-baseline.md](references/engineering-baseline.md)。

### 3. 选择开发路径

- 后端先行：适合表单提交、后台生成、下载结果，以及可通过 API 独立判断核心价值的产品。
- 纵向切片：适合多轮对话、人工确认、可视化编辑、画布、音视频时间轴，或终端系统能力本身决定产品可行性的产品。

两种路径都先跑通最小用户任务。正式前端不是默认前置工作；但如果“用眼睛看、亲手操作”才能判断 Agent 质量，则提供最小验收界面。一次性后端验收工具可用 FastAPI `static/` 下的单页 HTML；已有前端优先增加最小入口；核心交互则直接成为正式前端的第一条切片。

### 4. 先输出《技术适配声明》

首次开工，以及 PRD、交付终端或架构约束显著变化时，先按 [references/adaptation-declaration.md](references/adaptation-declaration.md) 输出声明。

全部采用默认项且没有重大影响问题时，可报告后继续。偏离会显著改变成本、安全、数据迁移、交付终端或已有功能时，等待用户确认后再实施。

引导产品经理只确认三件事：

1. 对目标用户、核心任务和当前阶段的理解是否正确；
2. 是否新增 PRD 未要求的费用、外部平台、数据上传或上线范围；
3. 被暂缓能力是否影响当前阶段验收。

### 5. 生成当前阶段技术开发文档

使用 [references/stage-document-template.md](references/stage-document-template.md)，只写当前阶段，覆盖：范围与不做事项、数据与状态、API 或工具、Prompt、最小界面、双层测试、产品经理可操作的验收清单、风险和下一阶段交接。

从 PRD 推导，不发明业务规则。尚未冻结的评分公式、阈值或话术标准可用“临时方案 + 显式标注 + 可配置”跑通链路，并列为待确认项。

### 6. 仅在获授权时实现当前阶段

- 可复用业务能力放在服务或领域层，并能经 API 或等价自动化入口独立验证。
- 长任务使用 SSE 或“提交任务 + 查询状态 + 获取结果”，并持久化任务状态。
- 固定流程由代码状态机编排；动态 Agent 仅在工具白名单、参数校验、预算、最大步数、超时和人工确认点内决策。
- Prompt 独立管理和版本追踪；模型输出用确定性解析与结构校验，失败只做有限重试。
- 保留已有功能、数据与未提交修改；不为贴合示例目录整体重构。
- 每次只实现当前阶段，不提前铺开后续终端、微服务或中间件。

### 7. 运行双层验收并如实交付

涉及模型的核心链路必须同时完成：

1. mock 自动化测试：离线覆盖业务逻辑、状态流转、校验、错误路径和解析器；
2. 真实模型端到端冒烟：至少覆盖每种模型调用契约和每条关键用户链路；记录模型、耗时、成本与结果。

没有真实 Key 时继续可离线完成的开发，但把真实冒烟标为“待验”，不能声称 Agent 效果已通过。详细方法见 [references/testing-and-delivery.md](references/testing-and-delivery.md)。

交付报告必须区分：已通过、未通过、待用户验证、因缺少 Key 或外部条件而待验。涉及界面时还要完成真实浏览器中的关键交互与目标宽度检查。

## 与产品经理沟通

- 一次只给当前需要执行的少量操作：去哪里、点什么、填什么、看到什么算成功。
- 不向用户倾倒整份工程清单；需要 Key、设计参考或验收时再逐步提出。
- 每个阶段结束时明确告诉用户下一步是什么。
- 验收清单写成非技术人员可以照做的动作，不只列技术指标。
