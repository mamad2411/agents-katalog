# 算法还原与 keygen 验证

## 先说最容易犯的错

你写了个 keygen，生成一个 key，喂给自己的 `--verify`，通过了。

**这不证明任何事。** 你只是证明了自己的算法和自己的算法一致。

真正的验证只有一条：**生成的 key 能在原程序里跑通。**

而且必须用**原厂生成的合法 key** 做反向对照 —— 用它验证你的算法实现是否正确。

---

## 一、采集输入输出对

至少 3 组，越多越好，要覆盖：

```
[ ] 不同版本（v1.0 / v1.5 / v2.0 的 key 格式可能不同）
[ ] 不同功能等级（基础版 / 专业版 / 企业版）
[ ] 不同到期时间（永久 / 1 年 / 1 个月 / 试用 7 天）
[ ] 不同用户/公司名（如果 key 里编码了这些）
```

**来源**：

- 官方试用申请（最干净）
- 论坛/网盘泄露的 key（可能有坑，见下）
- 自己买一份

**注意**：泄露的 key 可能是被服务端拉黑的，用它做对照会误导你。优先用能正常激活的。

---

## 二、判断 key 的结构

### 先看格式

```
XXXX-XXXX-XXXX-XXXX        16 字符分 4 组
XXXXX-XXXXX-XXXXX-XXXXX-XXXXX   25 字符（Windows 风格）
base64 长串                 可能是签名
纯数字                      可能是序号 + 校验位
```

### 逐位测试：哪几位会变

拿 3 个合法 key，对齐比较：

```
KEY1: A1B2-C3D4-E5F6-7890
KEY2: A1B2-C3D4-E5F6-1234
KEY3: A1B2-C3D4-FFFF-7890
      ^^^^^^^^^^^^ 固定    ^^^^ 变化
```

- 固定段 → 产品 ID / 版本号 / 厂商 ID
- 变化段 → 序列号 / 随机数 / 时间编码

### 校验位在哪

**方法**：只改一位，看程序报什么错。

- "格式错误" → 格式/字符集问题
- "无效的 key" → 校验位算错
- "该 key 已被使用" → 格式对、校验对，但服务端拒绝了

**如果改任意一位都报"无效"** → 有全局校验（比如整个 key 的 CRC / 哈希）。

**如果只有某几位改了不起作用** → 那几位不参与校验（可能是填充或保留位）。

## 三、常见算法结构

### 1. 纯校验位（最简单）

```
key = 数据段 + 校验位
校验位 = f(数据段)   // 通常是加权和 / Luhn / CRC
```

**特征**：改数据段后，把校验位重算就能通过。

**还原方法**：拿多组 key，只变数据段，观察校验位变化规律。

### 2. 加密编码（中等）

```
key 是密文，解密后得到明文结构体 { product, expire, features }
```

**特征**：key 看起来随机，但同一个产品/到期日的 key 有相似性（如果用了 ECB 或固定 IV）。

**还原方法**：

1. 在解密函数下断，dump 明文
2. 收集「密文 → 明文」对
3. 判断算法（长度、块大小、是否 ECB）
4. 如果是对称加密且 key 硬编码在程序里，直接提取密钥就能自己加密

```python
# 提取硬编码密钥的常见位置
# - 全局数据段里的 16/24/32 字节常量
# - 初始化函数里构造的密钥表
# - 字符串混淆后运行时解出来的
```

### 3. 非对称签名（最难，通常不可 keygen）

```
key = 数据 + 签名，客户端用公钥验签
```

**这种情况写不出 keygen**（除非私钥泄露）。只能：

- 替换公钥（见 `license-validation-locate-patch`）
- patch 验签函数

**判断方法**：key 长度固定且很长（RSA-2048 的签名是 256 字节），或者有独立的 `.lic` 文件。

### 4. 服务端算的（不可 keygen）

key 是服务端数据库里的记录，客户端只是拿它去查。**本地算法完全不存在。**

**判断方法**：断网激活失败，或者 key 里没有任何可推导的结构。

## 四、还原流程

### 步骤 1：定位算法函数

从校验点往上追（见 `license-validation-locate-patch`），找到处理 key 字符串的那个函数。

特征：

- 入参是 key 字符串
- 内部有字符转换（`atoi` / `strtol` / 查表）
- 有循环（逐字符处理）
- 返回 bool

### 步骤 2：用调试器单步走一遍

**关键**：用一个**已知合法**的 key，单步跟到"返回 true"的那一刻，记录中间值。

```
输入: "A1B2-C3D4-E5F6-7890"
中间: 去掉横线 → "A1B2C3D4E5F67890"
     转成字节 → [0xA1,0xB2,...]
     第一轮变换 → ...
     校验和 → 0x??（应该等于某一段）
输出: true
```

### 步骤 3：用第二组数据验证理解

换一个 key，用你理解的算法手算一遍，看是否和调试器的中间值一致。

**不一致 → 你的理解有遗漏。** 回去单步，找漏掉的分支（可能有版本判断、特殊字符处理、隐藏的密钥表）。

### 步骤 4：写实现

```python
def gen_key(product: str, expire: str, serial: int) -> str:
    # 1. 组装数据段
    raw = encode_data(product, expire, serial)
    # 2. 算校验
    chk = checksum(raw)
    # 3. 编码
    return format_key(raw + chk)
```

### 步骤 5：验证（重点）

```
[ ] 用原厂 key 反推：你的算法能否算出和原厂一样的校验位？
[ ] 你生成的 key 能否在原程序里激活？
[ ] 不同 product 的 key 能否激活对应版本？
[ ] 不同 expire 的 key 是否正确反映到期时间？
[ ] 边界：最短 key / 最长 key / 非法字符 / 大小写
[ ] 重复：同一个 serial 生成两次，结果是否一致（应该一致，除非有随机数）
```

**第一项是核心**。如果你的算法能复现原厂 key 的校验位，说明算法对了；否则后面全是碰运气。

## 五、隐藏陷阱

### 陷阱 1：校验位里藏了版本信息

```
key 的最后一位既是校验位，又编码了版本号
```

表现：算法对了，但生成的 key 只能激活基础版。

**排查**：用不同版本的合法 key 对比，看最后几位是否按版本规律变化。

### 陷阱 2：字符集映射

```
输入 "0" 和 "O" 被映射到同一个值
输入 "1" 和 "I" 被映射到同一个值
```

表现：你生成的 key 里有 `O`，程序当成 `0` 处理，校验位算错。

**排查**：测试程序接受哪些字符，是否做归一化。

### 陷阱 3：时间参与运算

```
校验位 = f(数据) XOR (当前年份 & 0xFF)
```

表现：去年能用的 keygen，今年生成的全废。

**排查**：改系统时间，用同一个 key 测试，看结果是否变化。

### 陷阱 4：多处校验用不同算法

```
启动校验：算 MD5 前 8 位
功能校验：算 CRC32
```

表现：能启动，但功能报"授权无效"。

**排查**：把所有校验点都跟一遍（见 `license-validation-locate-patch` 的"单一 vs 多处"）。

### 陷阱 5：浮点/整数精度

```
C 里 int 溢出行为 vs Python 无限精度
```

表现：中间值对不上，但看起来算法一样。

**排查**：所有算术都加 `& 0xFFFFFFFF`，按 C 的 32 位语义算。

```python
def u32(x): return x & 0xFFFFFFFF
def rotl(x, n): return u32((x << n) | (x >> (32 - n)))
```

## 六、什么时候该放弃 keygen

出现以下情况，别再耗：

| 情况 | 原因 | 改走 |
| :--- | :--- | :--- |
| key 里有非对称签名 | 没私钥造不出 | 替换公钥 / patch 验签 |
| 激活必须联网且服务端校验 | 本地算法不存在 | 模拟服务端 / patch 客户端 |
| 算法依赖服务端下发的密钥 | 每次会话不同 | 中继 / hook |
| 逆向 3 天还没找到算法入口 | 投入产出不划算 | patch 判定点更快 |

**"patch 判定点"永远比"写 keygen"快**，除非你需要批量生成大量 key（比如做授权服务器）。
