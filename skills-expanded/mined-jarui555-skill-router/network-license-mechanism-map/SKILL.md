# 授权机制分类：动手前先回答这一个问题

**这个软件的"权威"在哪一端？**

客户端说了算 → 本地机制，可算法还原。
服务端说了算 → 云端机制，算法还原无效，只能替代服务端或跳过请求。

这一条判错，后面所有工作归零。最常见的浪费：把云端校验当本地算法做，花三天写完 keygen，激活时服务端照样拒绝。

---

## 一、四类机制

### A 类 · 本地纯算法

```
输入 key → 客户端内算法 → TRUE / FALSE
```

没有网络、没有签名、没有硬件绑定。key 的合法性完全由客户端自己算出来。

**攻击面**：算法还原 → 写 keygen。最干净的一类，做完不依赖任何外部条件。

**典型**：老式共享软件、国产小工具、部分 CTF crackme。

### B 类 · 本地签名链

```
license 文件（厂商私钥签名）→ 客户端内嵌公钥验签 → TRUE / FALSE
```

客户端有公钥，没有私钥。你造不出合法签名。

**攻击面**（按代价从低到高）：

1. patch 验签函数的返回值（最快，但要注意有多处验签）
2. 替换内嵌公钥为自己的公钥，然后用自己私钥签一份 license（最干净，一次搞定，但要能改二进制且不被完整性校验发现）
3. 找厂商私钥泄露（少见，但发生过）
4. 找签名算法的实现缺陷（比如只签了部分字段、没签过期时间）

**不要做的事**：试图从公钥推导私钥。RSA-2048 别想，ECC 也别想。

### C 类 · 硬件绑定

```
机器码（CPU/主板/硬盘/MAC 哈希）→ 绑定表 / 服务端登记 → TRUE / FALSE
```

判断绑定强度：**改哪个硬件会让它失效**。

| 绑定对象 | 伪造难度 | 做法 |
| :--- | :--- | :--- |
| 网卡 MAC | 低 | 直接改 MAC，或用虚拟网卡 |
| 硬盘序列号 | 中 | 部分可改，或 hook 读取 API |
| 主板 / CPU ID | 高 | 基本只能 hook API 或 patch 哈希计算 |
| 加密狗（USB dongle） | 很高 | 需要模拟狗 / 抓狗通信 / patch 调用点 |
| TPM | 极高 | 一般绕不过，考虑 patch 上层 |

**关键**：机器码通常不是直接比较，而是 `hash(硬件信息) → 查表/查库`。所以要找的是**哈希函数的输入**，不是机器码字符串本身。

### D 类 · 云端校验

```
客户端 → HTTPS → 服务端 → { valid: true, features: [...], expire: ... }
```

客户端只是个显示器。**改客户端里任何算法都没用**，因为结论是服务端给的。

**攻击面**：

1. 本地模拟服务端（hosts + 自签证书 + 假响应）
2. 中继（买一份正版，缓存响应重放）
3. patch 客户端：跳过请求，直接构造"已授权"状态
4. patch 客户端：只改响应处理逻辑（服务端说 false，客户端当 true）

**注意**：D 类经常是 **D + B 混合** —— 服务端返回的授权数据本身带签名，客户端验签后才认。这时候单改 `valid` 字段没用。

## 二、判定流程（按这个顺序，5 分钟内出结论）

### 第 1 步：断网跑

```
断网 → 启动 → 看是否还能用
```

- 完全正常 → A / B / C
- 提示"请联网激活" → D（或 D 混合）
- 能启动但功能受限 → 混合型：基础功能本地判，高级功能云端判

**注意**：有些软件断网后走"宽限期"（grace period），能用 7 天。别被骗，等宽限期过了再测。

### 第 2 步：改系统时间

```
把时间调到 1 年后 → 看试用期是否变化
```

- 提示"试用已过期" → 有本地时间校验（A 类特征）
- 无变化 → 时间由服务端给（D 类特征）

**同时注意**：有些软件会检测"时间倒退"，改完直接锁死。改之前先备份注册表/配置文件。

### 第 3 步：换机器码

```
改 MAC / 换网卡 → 看是否要求重新激活
```

- 要求重新激活 → C 类绑定
- 无变化 → 不绑定硬件

### 第 4 步：抓包

```
启动 + 激活流程，全程抓包
```

- 有 HTTPS 请求且带 key/机器码 → D 类
- 只有版本检查/更新检查 → 可能仍是 A/B/C，别把更新检查当成授权校验

**区分方法**：看这个请求的**响应是否影响授权状态**。改响应内容，看客户端行为变不变。

## 三、混合型的处理顺序

真实商业软件很少是纯一类。常见组合：

| 组合 | 表现 | 先做哪一步 |
| :--- | :--- | :--- |
| A + C | 本地算 key，但 key 绑机器码 | 先破绑定（C），再还原算法（A） |
| B + D | 服务端发 license，客户端验签 | 先看能不能 patch 验签（B），比模拟服务端省事 |
| A + 时间 | 本地算 key + 本地时间校验 | 先处理时间（改时间或 patch 时间源） |
| D + 完整性校验 | 云端校验 + 客户端自校验 | 先处理完整性，否则 patch 完启动就崩 |

**判断"先做哪个"的原则**：找**最靠近判定点的那一层**。离 `if (valid)` 越近，改动越少。

## 四、开工前的检查清单

复制这张表，逐项填：

```
[ ] 断网能否使用：           是 / 否 / 宽限期___天
[ ] 改时间是否影响：         是 / 否
[ ] 换机器码是否影响：       是 / 否
[ ] 激活流程有无网络请求：   有 / 无
[ ] 请求的响应是否决定授权： 是 / 否
[ ] 判定类型：               A / B / C / D / 混合(____)
[ ] 有无壳/反调试：          有(____) / 无
[ ] 有无完整性校验：         有 / 无 / 未知
[ ] 功能是否与校验分离：     是 / 否
```

最后一项最容易被忽略：**有些软件授权校验只挡住启动，功能代码本身不检查**。这种情况直接跳过校验调用点就行，不用管授权逻辑。

## 五、常见误判

| 你看到的 | 你以为 | 实际可能是 |
| :--- | :--- | :--- |
| 有个 `license.dat` 文件 | A 类，改文件就行 | B 类，文件里有签名，改一个字节就失效 |
| 有个 `verify_license()` 函数 | 唯一判定点 | 还有 3 个地方各自判一次 |
| 断网能用 | 纯本地 | 有缓存，缓存过期后才联网 |
| 抓包看到 `POST /activate` | 云端校验 | 只是上报统计，结果本地算 |
| 字符串里有 "Invalid license" | 搜这个就能定位 | 字符串被加密，运行时才解密 |
| 改完能启动 | 成功了 | 功能走另一条校验，用两次就崩 |

**"改完能启动"不等于成功。** 一定要跑完整功能路径，尤其是导出、保存、批量处理这些重操作 —— 它们经常有独立的二次校验。
