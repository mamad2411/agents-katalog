# 打点决策：先打哪个

手上通常是这种情况：50 个子域、300 个接口、20 个疑似漏洞。

**问题是排序，不是挖洞。**

排序错的代价：花两天打一个"技术上成立但打不进去"的点，而真正能进的那个点在第 47 位。

---

## 一、先做减法：什么点直接放弃

在排序之前，先把这几类划掉：

| 类型 | 为什么放弃 |
| :--- | :--- |
| 只读的信息泄露（无敏感数据） | 拿不到权限，报告里也只是低危 |
| 需要物理接触 | 远程场景无解 |
| 依赖 0day | 有 0day 就不在这里排优先级了 |
| 靶场/演示环境 | 打进去也没意义 |
| 已确认修复但仍报错的 | 浪费验证时间 |
| 纯前端逻辑漏洞（无服务端影响） | 除非能链到账号接管 |

**判断标准只有一条**：这个点打进去之后，我能不能拿到**新的权限或数据**。不能，就划掉。

---

## 二、排序的四个维度

对每个候选点打分（1-5），加权求和：

### 维度 1：暴露面（权重最高）

```
公网直连       5
公网但需认证   3
内网可达       2
需要特定网络   1
```

公网直连的服务，即使看起来加固了，也比内网的服务值得试 —— 因为它的攻击者多，漏洞被发现和利用的概率高。

### 维度 2：技术栈年龄

```
EOL 组件（Struts2 / Fastjson 1.x / Shiro 旧版）   5
近两年有 CVE 的框架                              4
主流框架最新版                                   2
自研框架（不明）                                 3（未知风险反而值得探）
```

**怎么快速判断**：看响应头、favicon hash、错误页、静态资源路径、`/actuator` `/swagger` 这类端点。

### 维度 3：功能复杂度

```
有文件上传 / 导入导出 / 模板渲染 / 反序列化入口   5
有 SSRF 可能（图片代理 / webhook / 抓取）        4
纯 CRUD 表单                                     2
静态站                                           1
```

功能越复杂，出洞概率越高。**上传、导入、导出、预览、回调** 这五个功能是重灾区。

### 维度 4：认证强度

```
无认证 / 默认口令 / 弱 session                    5
单一密码认证                                      3
MFA + 风控                                       1
```

## 三、快速筛：5 分钟判断一个点值不值得深入

对每个候选点，跑这套检查：

```
1. 访问首页 → 什么框架？（响应头 / cookie 名 / 报错页）
2. 访问 /robots.txt /sitemap.xml → 有什么路径
3. 访问 /admin /api /swagger /actuator → 有没有暴露
4. 随便提交一个表单 → 报错信息泄露什么（路径 / 框架 / SQL）
5. 看 JS 里的接口列表 → 有多少未文档化的接口
```

**五分钟内出现以下任一信号，优先级上调**：

- 报错页带完整堆栈或 SQL 语句
- `/actuator/env` `/swagger-ui.html` 直接可访问
- JS 里有 `/api/internal/` `/api/debug/` 这类路径
- Cookie 里是 `rememberMe=deleteMe`（Shiro）
- 响应头有 `X-Powered-By: Struts2` 或版本号
- 上传接口返回文件路径

**出现以下信号，优先级下调**：

- 全站 CDN + WAF，且 WAF 是云厂商最新版
- 所有错误都被统一成 500 页面
- 关键接口全部需要签名 + 时间戳
- 静态站 / 纯展示站

## 四、单点突破 vs 全面铺开

### 什么时候单点

- 目标明确（只有一个系统）
- 已经发现一个高价值入口
- 时间有限（比赛 / 项目截止）

**做法**：把所有精力压在一个点上，把它打穿。包括：把这个点的所有参数、所有接口、所有版本都试一遍。

### 什么时候铺开

- 目标是整个 SRC / 企业
- 没有明显的高价值点
- 有足够时间

**做法**：先横向扫一遍所有资产的"明显漏洞"（默认口令、未授权接口、已知 CVE），拿到第一个立足点再深入。

**铺开的陷阱**：扫了 200 个站，每个都只试了 3 个 payload，全是"疑似"。**没有一个确认的洞，等于零。**

---

## 五、什么时候该放弃一个点

**设定时间盒**：单点投入超过 4 小时没有明确进展，换下一个。

判断"明确进展"的标准：

```
[ ] 确认了框架和版本
[ ] 找到了至少一个可疑参数
[ ] 有一个能复现的异常行为（报错 / 延迟 / 状态码差异）
[ ] 有一条可行的利用链假设
```

四条全无 → 这个点暂时没戏，记下来换下一个。

**不要做的事**：在一个点上反复换 payload 变体。同一类方法失败 2 次就该换思路（换参数位置、换接口、换攻击类型），不是换编码。

## 六、优先级矩阵（直接用）

|  | 认证弱 | 认证强 |
| :--- | :--- | :--- |
| **功能复杂 + 技术栈老** | **P0 立刻打** | P1 找认证绕过 |
| **功能复杂 + 技术栈新** | P1 试逻辑漏洞 | P3 放后面 |
| **功能简单 + 技术栈老** | P1 试已知 CVE | P3 |
| **功能简单 + 技术栈新** | P4 基本没戏 | P4 |

**P0 的定义**：如果这里有洞，你今天就能拿到 shell。

---

## 七、常见误判

| 你看到的 | 你以为 | 实际 |
| :--- | :--- | :--- |
| 登录框 | 爆破就行 | 有风控/锁定/验证码，爆破是浪费时间 |
| 报错页带堆栈 | 有 SQL 注入 | 可能只是异常没捕获，注入点还得找 |
| 上传接口 | 直接传 shell | 有白名单 + 重命名 + 不在 web 目录 |
| 老版本框架 | 有公开 CVE | 可能已打补丁，或者利用条件不满足 |
| Swagger 暴露 | 接口都能调 | 大部分需要 token，只有几个是匿名 |
| 子域很多 | 面很大 | 90% 是同一个应用的不同入口 |

**最值钱的一条**：先找一个**已确认的、哪怕很低的洞**（比如未授权访问一个内部接口），用它来摸清这个系统的认证模型和代码风格，再打大的。比一上来就啃硬骨头效率高得多。
