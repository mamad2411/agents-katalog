# 修 bug 流程

问题：{问题描述}
线索：{复现线索}

## 1. 弄清现象
- 用自己的话复述：在什么情况下、做了什么、看到什么、本来应该是什么。
- 缺少关键信息（版本、平台、输入数据、报错原文）时先问用户，最多问 2–3 个最关键的问题。

## 2. 复现
- 找到最短的复现步骤；能写成命令或测试就写下来（运行服从本次实际权限；不新增用户禁止的测试）。
- 复现不了时：说明试过什么，列出可能的条件差异，请用户补充，不要凭猜测改代码。

## 3. 定位根因
- 从报错位置或现象入手，沿调用链读代码；用日志、断点或最小实验验证每个猜测。
- 区分「根因」和「症状」：只把报错吞掉、加判空绕过，通常不是修复。
- 顺便搜一下同样的写法在别处是否也有这个问题，列出来但不顺手改。

## 4. 修复
- 做最小、最直接的修改；不在同一次改动里重构或改无关格式。
- 说明较大修复的方案和影响；仍在已有授权内就继续，只有关键缺口或越界操作才确认。

## 5. 验证
- 按第 2 步的复现步骤再走一遍，确认问题消失。
- 运行项目已有的类型检查、lint 和相关测试；看相邻功能有没有被带坏。

## 6. 交付说明（按这个格式回复）

```
**问题**：一句话
**根因**：为什么会出现（指到文件和行）
**修改**：改了哪些文件、每处改了什么
**验证**：复现步骤结果 + 跑了哪些检查及结果
**遗留**：同类隐患、没覆盖到的情况（没有就写「无」）
```

## 使用边界

优先使用已有信息；用户的数量、格式和任务范围优先于本文默认模板。工具权限、主目录/附加只读、Plan 模式与预算以当次实际能力为准；不换工具规避拒绝。这里只给工作方法，不授权写入、命令、付费、发送、提交或发布；未执行/验证的步骤如实标明。
