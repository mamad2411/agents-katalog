# Decide: the user's decisions in one queue per project

Each ops repo keeps one queue of what waits for the user's decision, in `to-decide/`: one file per open item in `to-decide/items/`, decided ones in `to-decide/archive/`. Any agent adds to it as one step of its work; the user goes through it, most urgent first. Two kinds exist:

- **outbox**: an outgoing step (an email, a form, a post, a submission, a curated-list pull request, a thread answer), written out in full and checked against the plugin's channel registry and the project's channels page. Nothing goes out until the user approves its card.
- **question**: a decision only the user can make, with 2–4 options, each with what it buys and costs, and a recommendation. The answer is written on the item, and the next run that meets the question's `ASKED` marker applies it.

**Where the files are.** This skill's folder is named on the `Base directory for this skill:` line above this text. Beside this file: `scripts/decide.mjs` (run it as `node <folder>/scripts/decide.mjs …`), and under `references/`: `walk.md` (going through the queue), `format.md` (the item format, the card, the `ASKED` marker, the folder layout), `outbox.md` (the outbox kind's rules and records) and `registry.md` (the channels, lanes and red lines). Where that line is missing, the folder is `skills/decide/` under the `installPath` of the `ops@ops-workflow` entry in `~/.claude/plugins/installed_plugins.json`.

**Going through what's to decide** is `references/walk.md`: read it and follow it when the user asks. The rest of this file is for adding items and landing them.

## Each kind keeps its own authorisation

The walk only shows cards and collects answers. What an answer then does is the kind's own rule:

- **Outbox:** the user's Approve, in a session they are chatting in, runs that item's exact content once: only content whose SHA-256 matches the hash the card showed, and only where the registry row and the channels page allow the act. An email is only ever a link they open and send; a website form is only ever filled, never submitted; a release or tag stays a prefilled page the user publishes. Unattended runs and subagents act on nothing. This is the one exception to `ops:work-autonomously`'s list of real-world actions, and the one place it is stated; every other file that mentions it points here.
- **Question:** nothing executes. The answer is written on the item; the next run that continues the work applies it under its own rules.
- **Never, for any kind:** an answer lands code, pushes anything but `to-decide/`, opens or merges a pull request other than an approved outbox curated-list pull request, or stands in for a typed yes another workflow asks for. A later kind joins only under a decision of its own that states its authorisation.

## Adding an item

Adding an item is one step of the work you are doing; the rest of the work (research, knowledge-base entries, state, backlog) goes on as usual. Steps 1–4 are for whoever writes the item, a subagent included, in its own folder. Step 5 is for whoever commits: the session itself, or the run or cycle that spawned the subagent. A subagent never does step 5: it names its items in its summary as `Decide items: <paths>`, and its caller lands them.

1. **Which kind, if any.** An outgoing step the registry has an act for is an **outbox** item. A decision only the user can make (what the project does, promises or says, who it is for, what it costs them, a trade-off between their goals) that the work cannot settle from `charter.md`, `MEMORY.md` or the project's own rules is a **question**. Not an item: anything you may decide yourself (record it as you do today), a step with no act (a call, a meeting: leave it as `Step left for you: <what, to whom or where>`), and anything that lands code, pushes, or belongs to a run's closing decision (keep, keep except, park, merge). A session the user is chatting in asks them directly, and adds a question only for what they want to decide later.
2. **First use.** Where `to-decide/` is missing, create `items/`, `archive/` and `INDEX.md` as `references/format.md` says ("The folder"). With the first outbox item, also create `to-decide/outbox/` as `references/outbox.md` says. Nothing outside `to-decide/` changes; your summary says once that the repo's `CLAUDE.md` can take the scaffold template's `to-decide/` line (`/ops:scaffold`, adjust mode).
3. **Write** the item by its kind (below, and `references/format.md`), every common key included: `effort` (rough seconds the user needs to decide) and `recommendation` (what you advise and why). Never write anything that identifies a person other than the user; keep pointers to projects, organisations, threads or channels. This holds for every item, whoever called you.
4. **Check** each item with `node <folder>/scripts/decide.mjs card <item>` (an email without `--to`). Fix a refusal once; an item still refused is not added, and your summary says why.
5. **Land**, for whoever commits. On the default branch, housekeeping first: move outbox items past `expires` to `archive/` with a ledger row `expired` (a run on a branch of its own leaves this to the walk, so its commits only add files). Re-read `items/` and `outbox/ledger.md` where you commit, and leave out a new outbox item whose target another open item or a counting ledger row already holds, and a question whose `from` and matter another open question already holds, since a subagent's folder can be stale. Then land as "Landing to-decide items" says, name the items in your summary as `Decide items: <paths>`, and where a run nobody watches added items and a PushNotification tool is in your tool list, send one plain line: `<project>: <n> to decide`.

### Outbox items

- **In place of a file to copy-paste or a "Step left for you",** write an outbox item. Where `to-decide/outbox/HALT` exists, add none: leave the step in your summary as `Step left for you: …`.
- **Choose.** Drop a target the ledger or an open item already holds (lists, organisations and directories never twice; threads per thread), anything a red line in `references/registry.md` forbids in every lane, a thread that does not ask for what the project does, and anything above its lane. How many items to prepare is what the instruction says ("prepare 10"), otherwise your judgment. Where the instruction asks for what the red lines or the law rule out, such as "prepare 10 messages to teachers" (cold email to individuals), do the legitimate version without asking (communities, directories, organisations, through channels that invite it) and say so in one plain line in your summary and under `## Notes` in `outbox/ledger.md`: "Reached teachers through 3 communities and 2 education directories; individual teachers can't be contacted cold."
- **Write.** Fill every field and name the guesses, as `references/outbox.md` says ("Fill and flag"); follow the registry row (template, disclosure line, tracking); write in the voice of the channels page's `Voice file:`; set `expires` (72 hours after `created` for a thread answer, 30 days otherwise, unless instructed). The backlog item or plan step the item carries out is closed or trimmed as your normal work does, since the queue now holds what remains.

### Question items

- **Write the card the user decides on, not your puzzle:** what is at stake in their terms, 2–4 options that differ in something they can judge without opening a file, each with what it buys and what it costs, your recommendation, and the one question. `discuss: yes` where a pick would not do. `blocks` says what waits on the answer, if anything.
- **One decision, one item.** Before writing, look in `items/` for an open question with the same `from` and matter; add to it rather than write a second.
- **Leave the marker and go on.** Put `ASKED (decide <id>, since YYYY-MM-DD)` in the file named by `from`, right after the matter it concerns. Where the work can go on with your recommendation, it does, so the answer may later change it; where it cannot, it stops there and `blocks` says so. `references/format.md` ("The ASKED marker") says how the next run applies the answer.

## Landing to-decide items

Nothing in the queue goes out or changes the project's work before the user answers, so an item needs no second approval to reach the default branch.

- **On the repo's default branch** (a watched session, a cloud clone): commit `to-decide/` alone, by pathspec, in a commit of its own, before the run's other work where the run can order it. Fetch, then push when every commit not yet on `origin` touches only `to-decide/` (`git -C <repo> log --name-only --format= origin/<default>..<default>` lists nothing else), in full: `git -C <absolute repo path> push --no-follow-tags --no-recurse-submodules origin refs/heads/<default>:refs/heads/<default>`. Pull first: `git pull --rebase` in a clean tree, otherwise `--ff-only`; in a conflict in `outbox/ledger.md` keep both sides' rows. On a fresh clone run `git remote set-head origin --auto` once, and after the push `git ls-remote origin`, each as a call of its own. Where the push cannot go (a rule forbids it, a permission prompt is refused, the network fails), the commit waits for the next push and your summary says so; in a cloud session it says first that the items are lost with the machine.
- **Whose rules decide the push.** The plugin's default is to push without asking. Where the user's own rules forbid that push (their `CLAUDE.md`, a hook that guards pushes), a watched session asks once per session before the to-decide push, and an unwatched run leaves the commit local and says so in its summary.
- **On a branch of its own** (`/ops:get-to-work`, `/ops:batch-execute`, `/ops:batch-handle`): each task's `to-decide/` paths go in a commit of their own, before the task's other paths. They need no closing decision. When the user is back, `/ops:review-followup` lands them first, by **landing from a branch**: in a clean tree, `git switch <default>`, `git pull --ff-only`, cherry-pick the run's commits that touch only `to-decide/`, oldest first (a conflict in `outbox/ledger.md` keeps both sides; any other conflict aborts that cherry-pick and leaves the item to the run's closing merge), push as above, switch back, and merge the default branch into the run's branch, so a later merge of the run cannot bring back an item a walk has since archived. The run's `ASKED` markers stay on its branch with the rest of its work. A headless run nobody returns to keeps its items on its branch until `/ops:review-followup` runs, and a thread answer may lapse before then.
- **At a run's closing decision** (keep, keep except a named piece, park): items whose work the user leaves out are archived as `withdrawn` on the default branch in a to-decide-only commit, landed as above, since their markers and drafts will never reach it. A parked branch changes nothing: its items stay open and the markers arrive with the branch.
- **On any other branch** (a watched `/ops:handle` or `/ops:execute` on a branch the user made): commit `to-decide/` in a commit of its own and push nothing; the items reach the default branch with that branch, or earlier when the walk offers landing from a branch. Your summary says so.
- **`/ops:batch-plan`** commits nothing else: once its planners return, the session does step 5 for their items, in one to-decide-only commit landed by the branch it is on.
- **Autopilot** lands its executors' items where it writes its memory, on the default branch, never on its batch branch.
- Everything else a run did keeps its own landing rules.
