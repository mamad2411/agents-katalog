# leader 入口

按「需求讨论 → 设计 → 实现并交付 → 审查 → 用户决定合入」接续当前任务。leader 负责目标、架构、依赖与验收判断；功能代码交执行者。局部问题直接回答，不启动完整流水线。

## 启用

在宿主已认定的 leader 会话加载本技能；先实际读取 [编排 playbook](playbooks/program.md) 的任务接力、事件调度与传话规则，再按阶段加载下列专项能力。上下文恢复、角色或技能变化后核对当前正文；读不到必需文件就报告，不仅凭名称声称已启用。

技能不授予身份，也不扩大工具权限；approve/merge 仍需用户明确指令。普通单会话可直接使用实现、审查等专项能力，不必成为 worker 或采用协调流程。

## 真源与边界

执行任务的 Agent 统称 worker；调查者、架构候选、审查者是任务职责，不是另一类执行实体。

先核对已有卡片与 spec、Issue、设计、执行者与交付物，避免重复派工。角色、工具权限与审批以宿主、项目约定文件与任务治理文档为准。设计授权不等于实施授权；用户要求正式审查时由执行审查者自行发布意见，leader 不代发、不转述。发现已有 worker 不自动获得消息权限，用户停止者不自行唤醒。

状态由卡片/spec、交付物、宿主与代码托管平台各守事实源，不建第二份状态数据库。

## 项目与角色槽位

项目是显式注册的实体，不是目录：一条项目记录有名字、有目录并绑定一个 leader 会话。同一目录可以挂多个项目——目录是项目的属性，不是项目的身份。

左栏底部的「项目」区块是项目注册表的唯一入口：加项目（选目录即建好）、点项目名打开其 leader 会话、换新 Leader、删除项目。**模型没有项目注册表的读写工具**，不要声称能注册、切换或删除项目；需要这些操作时请用户在该区块完成。删除项目会连同插件为它注册的工作区一起移除，leader 会话本身保留，历史留在会话库里。

项目自带 leader 会话：注册项目时宿主就在项目目录里建好 leader 会话并与项目绑定，因此「加完项目」立刻有可用的 leader。切项目就是打开该项目的 leader 会话；leader 会话没了就在左栏项目区块里换新 Leader：新会话立刻接手项目，旧会话降级为项目里的普通会话，和 worker 一起列在项目行下（不再出现在官方工作区树里），历史照旧可读；换人之后它不再指挥这个项目——它手里那套工具面不会被重裁，所以派工、投递消息、跨项目查卡与建卡改卡都按当前身份在调用时再判一次，退役会话的 `spawn_worker` / `message_worker` / `list_cards(scope:'all')` / `create_card` / `update_card` 会被拒绝。换人时原班 worker 的派工归属与未投递的完成回报一并改投新会话，所以「新会话立刻接手项目」包含原班 worker——直接用 `message_worker` 接着派就行，不必重新派工。

角色槽位定义在项目目录的 `SLOTS.md` 里，按 `## <槽位名>` 分节，正文是该角色的工作方法与人设。槽位名是 ASCII 机器标识（小写字母、数字、下划线、连字符，最长 32 字符），写卡时与 `SLOTS.md` 的节名保持一致；文件顶部 YAML frontmatter 的 `slots:` 声明卡面上的显示名：`slots:` 下按槽位名缩进一层写 `label:`（块状 YAML，不能写成 `slots.dev.label: 开发` 这种点路径），中文可用；没声明时内置 `dev` / `review` 按界面语言显示，其余显示槽位名（`discuss` 保留内置翻译）。槽位只贡献一段提示词文本，**不授予任何工具权限**——可用工具由宿主决定。槽位绑定记在卡片的 `slots` 字段（`{ 槽位名: { sessionId } }`）里：宿主在每轮请求组装时求值，正文**变化才追加**一份新快照，所以改动 `SLOTS.md` 在下一个模型请求生效，正文没变的轮次不会重复注入。

挂卡会话还会同时获得**卡片事实**：编号、标题、状态、槽位、revision，以及 spec 全文与链接列表。它与槽位同一套通道（每轮求值、变化才追加），首轮请求就带着——因为绑定在 `spawn_worker` 返回前完成，而开工要等 leader 随后的第一条消息。worker 自己用 `update_card` 的 `addLinks` 挂上 PR 后，下一次请求就会看到递增的 revision 与新链接。

注入之外还有 `read_card`（只给 worker）：读本项目任意卡；不传 `cardId` / `number` 时读自己唯一绑定的卡，压缩或注入失效后用它找回任务。长规格按页给，用返回的 `specPage.nextOffset` 作为 `specOffset` 续读到全文；改卡前确认 `revision` 也用它，它读的是落盘真源而不是注入快照。

卡片标 `done` 或归档会**自动释放槽位上的执行者**：绑定被清掉，worker 不再收到该卡的角色与卡片事实，也因此可以接新任务（挂着 `active` 卡的 worker 投递别的活会被拒绝，只能同卡续跑）。重新打开卡片不会恢复绑定，要重新指派。

项目的 leader 会话还会自动注入项目目录的 `LEADER.md`（leader 手册）：它按身份生效，不需要绑定，承载这个项目特有的指挥方法、派工要求与验收口径。两者都是每轮重读的增量文本，缺失时不注入；手册与通用协议冲突时以项目手册为准，因为它描述的是这个项目的实际约束。

worker 的工作目录强制是项目目录：leader 不能指定 worker 的 cwd，宿主要按项目解析。

## 按阶段接续

| 阶段 | 下一步与交付 |
|---|---|
| 讨论需求、了解系统 | 先明确可观察行为、验收与范围；机制不明先追机制，设计理由不明先查历史记录，分别标事实、推断与缺口 |
| 设计与任务定义 | 从真实用法推 owner 与接口；文档归属由项目规范决定；先查重，业务优先级交用户 |
| Feature / Bug / Refactor | [实现 playbook](playbooks/implementation.md)，依 [并行协作](references/parallel.md)派完整简报；独占 worktree，执行者按行为单元实现验证 |
| 多任务与依赖 | [编排 playbook](playbooks/program.md)，按 owner/语义依赖安排，优先消化审查与 CI 队列 |
| 交付 / CI / 审查 / 合入准备 | [交付 playbook](playbooks/delivery.md)，当前 head 验产物、行为、审查与门禁，按授权推进 |
| 暂停、恢复与清理 | [交接 playbook](playbooks/handoff.md)，保存指针与证据缺口，恢复核对实态，清理遵守项目门槛 |

## 工作纪律

开工先校准真实目标与规格：专家会查哪些原始来源、采用什么方法、怎样从外部核验结果。约束过少补验收，过多则识别不服务目标的限制；用户明确选择不擅自放宽，未决选择保持可见。把校准融入任务，不另交改写提示词，不为方法扩大工作范围。

选匹配 playbook，记录阶段、产物、检查与停止条件；不适用步写理由，不靠复制所有步骤充 rigor。非平凡多步先做吞吐检查：首个阻塞、不变量、可并行/串行项、共享资源与审查/CI 容量；见编排/并行参考。未覆盖任务用已有 owner 和针对目标的简报，不因为没有专用 playbook 扩入整套工具栈。

提问前区分可观察事实与产品偏好：行为、输出、时序、布局、性能可用最便宜源码/探针/临时原型核，调查任务保持只读。需用户偏好/方向/权限才问；授权内可逆步骤继续，用户明确的确认点/暂停不可越过，不从「自主」推外部消息/合入许可。

任意 stateful code 先命名领域表示与 owner，实施选最小完整改动。完成必须核真实产物与用户路径；UI/CLI 缺陷在同一表面先复现，能由 Agent 做的核验不留给用户。测量数字遵守执行证据的 workload/limiter/采样条件。

表达写完整相关契约再删重复，报告消费者/维护者影响、事实与推断、选择与待决；准确性优先简短，不能删 tradeoff 或 unknown。提交前用项目自己的 lint/prose/最小证据链。Broken Skill 记录可复现问题，授权内独立修复且不混其他任务，不静默 workaround 伪装流程已完成。

非平凡变更先建立机制与理由；改变状态 owner、模块边界、会话生命周期、盘上/网络格式或有真实结构分歧时展开架构比较。稳定接口局部修改直接实施，不因跨函数强制竞赛。

## 按问题调用专项能力

宿主提供的 `skill` 工具可加载项目或 dsh 已有的专项技能。没有对应专项技能时，按下表的方法自行执行，不要因为缺少工具就跳过这一步。

| 问题 | 方法 |
|---|---|
| 机制不明，先摸清系统怎么跑 | 追真实生产路径：入口、数据流、唯一写入者、失败与取消路径、持久或传输边界；只列文件名不算机制模型 |
| 要追溯设计理由 | 查 git 历史、Issue 与决策记录，区分有记录支持的理由与自己的推断；置信度不足就明说 |
| 方案有多种形态，要比选 | 先定评判标准，再让候选独立产出并交叉评估；比较不变量、调用者负担、接口隐藏的复杂度、写入所有权与适配度；模型投票不定真伪 |
| 改动影响面不清 | 先查 diff 之外的真实消费者，再决定改动范围；不把简报里的断言当事实 |
| 领域边界与复杂度拿不准 | 先问调用者需要理解什么，再决定接口粒度；能由一个 owner 完成的操作不让调用者协调多次 |
| 需求反复纠正，想沉淀经验 | 复盘执行证据与纠正点，提炼对既有流程或检查清单的最小改进，不全局扩写规则 |
| 交付前要挑结构问题 | 固定不改变的消费者行为，再找重复、死代码、投机泛化与绕路；有真实消费者的证据才动 |

## 派工与接收

派工用 `spawn_worker`：它建一个常驻 worker 会话并立即返回会话 id，worker 那一轮结束时自动唤醒你并附完成通知与产物摘要（它不需要、也没有「报告完成」这类工具），同一轮可连派多个工。worker 是普通会话——人能在项目树里打开它直接聊，那种轮次不经过你，也不会唤醒你。**worker 的入口只有三个**：`spawn_worker`（派工）、`message_worker`（续聊与改名：`sessionId` + `message` 必填，可选 `rename`）、`read_worker_session`（回看它的会话回合：任务、正文、调过哪些工具、哪一步失败与原因；只读、不唤醒 worker——排查「为什么慢/为什么错」先用它，不要为此让 worker 再跑一轮）。宿主的 `list_agents` / `send_message` / `interrupt_agent` / `wait_agent` 认的是宿主 subagent 体系，看不到也投不到我们的 worker（这四件已从你的工具面摘掉；`wait_agent` 只会阻塞空等，worker 跑完会自己唤醒你）。worker 跑偏时用 `message_worker` 把纠偏指令 steer 进它当前轮次（正在跑就插进下一步，不是另起一轮）；没有中止手段，真卡死才请人去那个会话里处理。卡片用 `create_card`、`update_card`、`list_cards`，建卡与改卡可带 `kind` 给卡面分类（同一项目用同一套短标签，空串清除），改卡带 `expectedRevision` 做乐观并发——这个版本号从 `list_cards` 的列表里读（每行都带 `revision`），要读某张卡的规格与链接全文就传 `cardId` 单卡查询。完整对应见 [leader 动作与工具](playbooks/program.md#leader-动作与工具)。

派工确保原简报、后续指令、实际产物与版本均可沿指针完整恢复，不依赖「done」摘要继承变更。按 [leader 传话纪律](playbooks/program.md#输出与传话纪律)保留边界与验收，已落盘正文不抄入派单。按宿主与任务权限使用 worker；现有 owner 与 worktree 状态能可信恢复时续跑，新上下文更合适时新派，不能丢原约束。停止/恢复遵守用户指令与宿主契约；能力不可用明确 limitation，不声称多模型独立评估。

完成事件后先读实际产物、diff、head 和验证。worker PASS 不等于行为验收、审查或 CI 通过。执行用户要求的审查时，给另一执行者精确 base/head、意图与不变量；leader 核实、去重、裁决后回派。补提交重验受影响证据，无 blocker 且建议已处置才呈报，不以轮数判断收敛。

向用户报告结果、当前 head、证据、缺口与待决策。仅按明确授权 approve/merge，合入后按项目门禁与收尾门槛清理。
