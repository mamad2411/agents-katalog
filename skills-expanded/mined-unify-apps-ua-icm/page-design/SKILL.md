# Page design

This repo drives the devkit's page tools but does not load the devkit's brief,
because that brief auto-loads from `CLAUDE.md` only when Claude Code runs in
that directory. The tools came across; the design thinking did not. That gap is
what this skill closes, and it is the reason a page built from here comes out
plainer than one built in the devkit.

Load both halves below **before the first visual decision**, not after the
screen exists. The order they give you only helps while there is still an order
left to follow.

## 1. The craft — `frontend-design`

Invoke the skill `frontend-design:frontend-design`. It is the design lead's
half: ground the look in the subject, plan a compact token system (4–6 colours,
type roles, layout concept, one signature element), critique that plan against
the brief before building anything, then critique the built thing again.

Read it for JUDGEMENT, not for mechanism. It is written for hand-written
frontends, so the parts about choosing a web font, writing CSS grid, or picking
a hex are not instructions you can follow literally here — on this platform
those decisions go through the rungs below, and most of them end at rung 1 with
a token id. What transfers is the process: decide the finished thing in a
sentence first, spend boldness in one place, and cut anything that does not
serve the brief.

## 2. The platform truth — the builder brief

The devkit carries the platform agent's own configuration. Find the clone:

```
node scripts/page.mjs          # prints `devkit: <path>` and the verb list
```

Then read `<devkit>/agent/instructions.md`, by section heading rather than line
number — the file is regenerated by the devkit's `bin/sync-prompt.mjs` from the
lab repo, so it moves:

- **"Design work — how you make a screen look right"** — the whole section.
- **"Worked example 7 — an open-ended look-and-feel request"** and **"Worked
  example 8 — reproduce a design you were given"**.
- **"Getting the details right — look it up, never invent"**, if `/start` did
  not already have you read the brief this session.

That file is the authority and it is read-only here. What follows is
orientation, not a substitute for reading it.

**Where a look can live — three rungs, in order.** Take the first one that can
express the thing, because it leaves the page most editable afterwards.

1. **The block's own properties** — content and appearance settings, style keys
   set to a value from that key's own list. Those values are the app's
   design-system tokens: they follow the theme, and they are what the style
   panel shows, so the person who asked can adjust them without you.
2. **A conditional value on that same property** — when the look changes with
   state or data. Same property, same panel; beats reproducing the effect in
   CSS.
3. **HTML attributes, custom CSS, page header/footer code** — the right tool for
   anything the configuration has no word for. Two facts make it land rather
   than silently do nothing: the platform does not scope your CSS to your block,
   so the selector must name the block; and a binding inside CSS text is never
   evaluated. Anything that MOVES is rung 3 by definition — nothing here
   declares a transition. Say where you put it afterwards, because it does not
   appear in the style panel.

**Match the relationship, not the number.** The values are a fixed token set,
not a free scale. Read a reference as relationships — this heading twice the
body and heavier, this panel a shade lighter than the ground — then pick the
token that holds the same relationship. A pixel measured off a reference is a
wrong answer twice over.

**A vague request is not a request for the smallest change.** "Make it nice"
asks to see what you would do with it. The scope stays what they pointed at.

## 3. Traps this repo has already paid for

Found by looking at the rendered page rather than trusting a 200 — see commit
`3ceb941` and [docs/pages/positions.md](../../../docs/pages/positions.md):

- `borderRadius: "rounded-lg"` is **not a token.** It stores fine and computes
  `0px`. The `lg` preset is `rounded-3xl`.
- Icon names are `SvgCheckCircle` / `SvgCircleDotted`, not `CheckCircle`.
  Confirm every one with `get_icon_options`.
- `visibility` takes a condition object, never a binding — and `create_block`
  and `update_blocks` disagree about whether `visibility.value` is a legal path.
- A stored value that reads back correctly has proven nothing about how it
  renders. Only the browser tells you that.

**The theme is not a per-block problem.** This app sits on the pre-retheme cool
palette (ground hue ~250) while the published design system is warm. Tokens
stored here resolve correctly — against that theme. Nothing you do block by
block fixes it, and patching around it with custom values makes the eventual
theme fix worse. See open question 3 in the Positions spec.

## 4. Verify by looking

Config read-back and screenshot answer different questions. Finish with
[preview-pixel-perfect](../preview-pixel-perfect/SKILL.md): open the live
preview, measure the real DOM for anything where a number matters, drive hover /
focus / open / **empty** (builder sample data exists only in preview — the
published page starts empty), then hand only the aligned screenshots to a
subagent asked to list every visible difference. You are blind to your own
intent.

## 5. What this skill does NOT relax

- **Pages never touch objects directly.** A page calls a callable; the callable
  reads and writes. Authorization lives there.
- **Surgeon rule.** Touch only what the task requires. A design task is not a
  licence to restyle the rest of the page.
- **Know before you act.** Every block, key and action the task touches gets its
  knowledge sheet read first. A plausible value that is not in the sheet stores
  fine, matches nothing, and renders empty with no error.
- **The page spec in `docs/pages/` is written before `/done`.** Nothing on the
  platform records that a page calls a callable.
