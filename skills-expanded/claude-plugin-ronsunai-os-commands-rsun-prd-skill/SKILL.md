# rsun-prd — 產品需求文件（PRD）

PRD 是橋接「問題理解」與「工程實作」的核心規格文件。好的 PRD 讓工程師知道「做什麼、為什麼、成功是什麼」，同時保留實作自由度。適用於：需求確認後進估價前；或開發啟動前與工程師對齊。

---

## 何時使用

- 客戶需求已初步收集，需要書面確認範圍（→ 然後進 `/rsun-estimate`）
- 開發啟動前，需與工程師對齊（Phase 2 設計之前）
- 多方利害關係人需要共識文件
- 範圍蔓延時需要重新對齊

---

## 執行步驟（8 步驟，依序完成）

### Step 1｜摘要問題（Why Now）

三個問題必須清楚回答：
1. 這個系統／功能要解決什麼核心問題？
2. 為什麼現在要做（而不是 6 個月後）？
3. 不做的話客戶 / 用戶承受什麼損失？

> 如果 Why Now 說不清楚，停下來先問客戶，不要繼續。

### Step 2｜定義成功指標

具體、可量測的成功定義：

```
指標：[名稱]
基準值：[目前數字，若無則標注「待調查」]
目標值：[期望數字]
時間範圍：[上線後 30 天 / 3 個月]
```

常見指標類型：
- 業務：轉換率、節省人工時數、減少錯誤率、縮短處理週期
- UX：任務完成率、操作步驟數、客戶滿意度
- 技術：API P95 回應時間、uptime、錯誤率

### Step 3｜解方概述（High-Level Solution）

- 1-2 段描述解方，聚焦**用戶視角**的功能與能力
- **不要**過度規格化實作細節（那是架構設計的事）
- 可附簡單流程圖（Mermaid）或使用情境描述

### Step 4｜功能需求

每條需求必須可測試，使用以下格式擇一：

**User Story 格式：**
```
身為 [角色]，我希望 [功能]，以便 [目的]
```

**需求陳述格式：**
```
系統必須支援 [行為]，當 [條件] 時
```

優先級標注：
- **P0**（必須 Must Have）— 沒有這個無法上線
- **P1**（應該 Should Have）— 重要但技術上可延後
- **P2**（可以 Nice to Have）— 未來版本再考慮

### Step 5｜範圍邊界（Scope Boundary）

**必須明確三區間，模糊地帶是工期膨脹的根源：**

| 區間 | 說明 |
|------|------|
| ✅ In Scope | 本次開發包含的功能（估價以此為準） |
| ❌ Out of Scope | 本次明確不做的項目 |
| 🔮 Future | 未來版本再考慮的功能（避免客戶誤解） |

### Step 6｜技術考量

- 已知技術限制或框架要求（客戶指定語言、既有系統）
- 第三方整合（金流、地圖、簡訊、AI、社群登入）
- 資料遷移需求（舊系統資料如何搬移）
- 安全性 / 合規要求（個資保護、金融法規、GDPR）
- 效能需求（同時在線人數、資料量規模）

### Step 7｜相依與風險

| 類型 | 說明 | 處理方式 |
|------|------|---------|
| 外部相依 | 第三方 API、客戶提供資料 / 素材 | 先做 mock，等待確認 |
| 假設 | 目前假設為真的條件 | 列出待確認項目 + 確認人 |
| 風險 | 可能影響交付的技術或業務因素 | 緩解措施 |

> ⚠️ 「假設客戶資料格式正確」也是假設，需要列出。

### Step 8｜時程里程碑

不承諾具體日期，描述關鍵階段：

| 階段 | 內容 | 預計週數 |
|------|------|---------|
| Phase A | 核心 P0 功能完成 | X 週 |
| Phase B | 整合與測試 | X 週 |
| Phase C | UAT + 部署準備 | X 週 |

## 品質 Checklist（交付前確認）

- [ ] 問題與 Why Now 清楚陳述
- [ ] 成功指標具體且可量測（不能只是「用戶滿意度提升」）
- [ ] 範圍邊界明確（In / Out / Future 都填了）
- [ ] 每條功能需求都可以被測試驗證
- [ ] 技術考量已標注（含第三方整合）
- [ ] 風險有對應的緩解措施
- [ ] 文件 15 分鐘內可讀完
