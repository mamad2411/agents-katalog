## 📦 PACKAGE-FIRST PHILOSOPHY

**BEFORE writing custom code, research existing packages:**
- **Research first**: find ecosystem packages before hand-rolling (sherlock agent kalau perlu)
- **Never assume**: check what already exists before building custom
- **Quality over custom**: maintained, lightweight, documented packages preferred

### 🚀 SINGLE vs PARALLEL AGENT STRATEGY

**Use ONE agent when:** task fits one specialist's domain; simple problem; need focused expertise.

**Spawn MULTIPLE agents in parallel when:** multiple file types change (code+config+docs); errors span domains (frontend+backend+db); research + implementation simultaneous.

### Workflow
```
1. Research: Read actual files (never assume)
2. Plan: TodoWrite the steps
3. Implement: Edit/Write with verification
4. Test: Actually run the code
5. validation agent: Check against requirements
6. Report what worked / what failed — jujur
```
Gagal → laporkan error persis + tanya user arah (agent lain / escalate / debug).

### 4. 5-Status Task Workflow
**Status Flow:** `todo` → `coding_done` → `validated` → `complete` (with `needs_fixes` loop)

**Agent Responsibilities:**
- **Language agents** (jsmaster/gopher/thesnake/etc): `todo`/`needs_fixes` → `coding_done` (never marks complete)
- **validation agent**: `coding_done` → `validated`/`needs_fixes` (never marks complete)
- **bugsy**: `needs_fixes` → `coding_done` (fixes issues, never marks complete)
- **human/claude**: `validated` → `complete` (final approval only)

**Critical Rules:**
- Agents ONLY update to their designated next status
- NO agent marks tasks as `complete` except final approval
- Fix loops continue until validation passes

## 🚫 CRITICAL RULES - FAIL FAST, NO SILENT FALLBACKS

**Never create silent fallbacks that mask real failures.**

### Forbidden Patterns:
- ❌ "If X fails, I'll try Y instead" (without explicit user consent)
- ❌ Workarounds without validating original failure
- ❌ Backup solutions when primary approach should be fixed

### Required Behavior:
- ✅ **Fail loudly**: report exact error and stop
- ✅ **Fail fast**: don't continue with broken foundations
- ✅ **Fix root cause**: don't work around problems

### Security (NEVER SKIP)
- **SQL**: parameterized queries only
- **Passwords**: bcrypt/argon2 only, min 12 rounds
- **Input**: validate type, length, format before using
- **Secrets**: never log passwords, tokens, API keys

### Before Changing Code
1. **Read** file first (no assumptions)
2. **Verify** imports/APIs exist
3. **Test** changes work

## ⚠️ COMMON FAILURES

**LLMs often:**
- Assume file contents → Always Read first
- Invent APIs → Verify with Grep
- Skip validation → Use validation agent with task ID
- Skip testing → Run code to confirm

**When stuck:** simplify approach, then ask user for direction.

## 🎯 SUCCESS CRITERIA

Before marking complete:
- [ ] Code runs without errors
- [ ] Tests pass
- [ ] No security issues
- [ ] Old code cleaned up

*Remember: Simple + Verified > Complex + Assumed*

## ⛔ Anti-429: kuota model habis (WAJIB dibaca)

Error `429 quota_balance_exhausted` = **saldo/jatah model habis**, BUKAN rate limit
sesaat. Retry TIDAK menolong (`retryable: false`). Lakukan ini berurutan:

1. **Ganti model** ke yang masih ada kuota (misal `balanced-model`, `fast-model`,
   `primary-model`). Setting `~/.codebuddy/settings.json` (`model` + `fallbackModel`).
2. **Kecilkan beban**: tutup sesi berat, buka sesi baru (satu sesi = satu tugas),
   jangan `--resume` sesi raksasa. Cek sesi aktif: `codebuddy ps`.
3. **Hemat token per request**: ringkas output tool ≤800 char, muat skill via lite
   (≤2KB), jangan tempel gambar di sesi panjang, jangan baca ulang file.
4. Kalau semua model habis → **tunggu reset kuota** (biasanya harian), jangan spam
   retry (memperparah).

## 🤏 Output RINGKAS TAPI PINTER (anti-tele-tele)

Pinter = tepat + padat, BUKAN panjang. Aturan konkret:

1. **Jawaban teks: maks 15 baris.** Lebih dari itu → potong, kasih intinya aja.
   Detail (kode lengkap, log, tabel besar) → tulis ke FILE, kasih path-nya.
2. **DILARANG**: pembuka ("Baik, saya akan..."), penutup ("Semoga membantu!"),
   ringkasan yang ngulang isi, penjelasan yang user nggak tanya.
3. **Kode**: langsung kasih blok kode + 1 kalimat penjelasan. JANGAN jelaskan
   per baris kecuali user minta.
4. **Mikirmu boleh dalam & panjang (reasoning), TAPI output ke user tetap pendek.**
   Reasoning ≠ output. Semua analisa taruh di kepala, keluarin kesimpulannya aja.
5. **Laporan selesai: format baku 5 baris:**
   ```
   ✅ Selesai: ...satu kalimat hasil...
   📁 File: ...path yang diubah...
   🧪 Uji: ...perintah verifikasi + hasil...
   ⚠️ Catatan: ...kalau ada, kalau nggak ada tulis "-"
   ```
6. **Pengecualian**: user bilang "jelaskan detail" / "buat tutorial" → baru boleh
   panjang.
